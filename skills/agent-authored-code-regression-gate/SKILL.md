# Agent Diff Gate

## When to use this
A PR or commit is agent-authored (Claude Code, Copilot, Cursor, Codex, or any bot account/commit-trailer-tagged agent) and someone — a maintainer, reviewer, or the agent itself before opening the PR — wants a fast, targeted pre-merge check for two specific failure modes that recur in agent-authored diffs: performance regressions (memory/CPU blowups from patterns the model defaults to) and "LLM-style" UI boilerplate smells (generic, over-templated, or redundant UI code a human reviewer would flag as "obviously AI-written"). This is a standalone review step, not a CI gate — use it even if the team has no automated gate set up yet, any time before merge.

Do not use this for a general-purpose code review (security, correctness, style) — it is deliberately narrow. Do not use it on diffs with no plausible agent authorship signal; its smell patterns are tuned for agent-default behaviors and will produce noise on hand-written diffs.

## Inputs
**Data source**: Connected — reads the diff via `gh pr diff <owner/repo>#<PR number>` and commit/authorship metadata via `gh pr view --json commits,author` (GitHub CLI, a mature, already-authenticated connector in most dev environments) when given a PR reference. Falls back to a pasted unified diff (`git diff` or PR diff text) when no `gh` access exists or the user is working outside GitHub. Either way this is a single developer-initiated review of one diff, not a continuously running scan.

Required from the user, one of:
1. A PR reference (`owner/repo#123`) — the skill runs `gh pr diff` and `gh pr view --json commits,author,title` itself.
2. A pasted unified diff (`git diff`, `git show`, or a PR's "Files changed" raw diff).

Optional but improves accuracy:
- The stack/language (e.g., "React + TypeScript", "Python/FastAPI") if not obvious from file extensions.
- A one-line description of what the change was supposed to do, so a legitimate large refactor isn't flagged as smell just for being large.
- Any known authorship signal (commit trailer text, bot account name, "Claude Code generated this") if not already visible in the diff/metadata.

## Procedure
1. **Obtain the diff.** If given a PR reference, run `gh pr diff <ref>` for the diff and `gh pr view <ref> --json commits,author,title,body` for metadata. If `gh` is unavailable or errors, ask the user to paste the diff and any commit trailer text instead — never fabricate a diff.
2. **Establish authorship confidence.** Look for: commit trailers (`Co-Authored-By: <bot/agent name>`), a bot/app account as author, PR title/body language typical of agent tooling (e.g., "Generated by..."), or an explicit user statement. Label the result `CONFIRMED` (explicit trailer/bot account), `LIKELY` (strong stylistic signal, no explicit tag), or `UNCONFIRMED` (user just asked for a review, no signal found) — never claim `CONFIRMED` without a literal trailer or bot account.
3. **Scan for performance-regression risk factors.** Walk every changed hunk and check for, specifically:
   - A loop added around a call that was previously single-pass (N+1 pattern: a DB/API/file call now inside a loop that used to be outside it).
   - Removed or bypassed memoization, caching, or a short-circuit/early-return that existed before the diff.
   - New synchronous/blocking I/O (file, network, DB) introduced inside a function previously async-only or in a hot path (render loop, request handler, tight loop).
   - New full-object deep copies, repeated `JSON.parse(JSON.stringify(...))`-style clones, or string concatenation inside a loop where a buffer/array-join pattern existed or was more natural.
   - New unbounded retry/recursion without backoff or a depth limit.
   - New per-iteration allocation (object/array/regex construction) inside a loop that runs over user-scale data.
   For each hit: record file path, line number(s) from the diff, the exact snippet, a one-sentence explanation of the risk, and a severity (`HIGH` = likely user-visible slowdown/memory growth at realistic scale, `MEDIUM` = risk depends on data scale or call frequency, `LOW` = theoretical/minor).
4. **Scan for LLM-style UI boilerplate smells** (skip this step entirely if the diff touches no UI/view-layer files):
   - A new component that near-duplicates an existing one in the repo instead of parameterizing it (check for structurally similar sibling files/components).
   - Generic placeholder copy ("Welcome to our app", "Lorem ipsum", "Click here") left in shipped-looking code.
   - Redundant wrapper elements (a `<div>` wrapping a single child with no styling/semantic purpose) not matching the file's existing style.
   - Reimplementation of a utility/hook/helper that already exists elsewhere in the repo (same logic, new name) — check for an existing equivalent before flagging.
   - Naming or structuring that matches common training-data conventions (e.g., `handleClick`, `data`, `item`, `MyComponent`) rather than the repo's established naming convention, inconsistent with the surrounding file.
   - Excessive generic `try/catch` blocks with a bare `console.log(error)` or swallowed error, added where the surrounding code doesn't follow that pattern.
   For each hit: same record format as step 3 (file, line(s), snippet, one-sentence explanation, severity), but severity here means `HIGH` = will visibly look inconsistent/broken to an end user or next reviewer, `MEDIUM` = maintainability drag, `LOW` = cosmetic.
5. **Do not speculate beyond the diff.** If a flagged pattern's actual runtime impact depends on data not visible in the diff (e.g., table size, call frequency), say so explicitly rather than asserting a severity with false confidence.
6. **Produce the output report** (format below). If zero findings in a category, state that explicitly — don't omit the section.
7. **Give one overall advisory line** — `LIKELY SAFE TO MERGE`, `MERGE WITH FOLLOW-UP`, or `RECOMMEND HOLDING FOR HUMAN REVIEW` — based on the highest severity found, but always frame it as advisory, never as a block/pass gate decision the skill itself is making.

## Output format
```
# Agent Diff Gate Report — <PR ref or "pasted diff">

**Authorship confidence**: CONFIRMED | LIKELY | UNCONFIRMED — <evidence quoted>
**Files reviewed**: <count> (<list if ≤10, else count + representative sample>)

## Performance Regression Risks
| Severity | File:Line | Snippet | Risk |
|---|---|---|---|
| HIGH | src/api/users.ts:42 | `for (const id of ids) { await db.get(id) }` | N+1 query added inside loop; previously a single batched `db.getMany(ids)` call existed above this hunk. |
(or: "No performance-regression risk factors found in this diff.")

## LLM-Style UI Boilerplate Smells
| Severity | File:Line | Snippet | Risk |
|---|---|---|---|
| MEDIUM | src/components/UserCardNew.tsx:1-30 | (near-duplicate of `UserCard.tsx`) | New component duplicates existing `UserCard.tsx` structure instead of adding a prop; will diverge over time. |
(or: "No UI boilerplate smells found" or "Skipped — diff touches no UI/view-layer files.")

## Overall Advisory
<LIKELY SAFE TO MERGE | MERGE WITH FOLLOW-UP | RECOMMEND HOLDING FOR HUMAN REVIEW> — <one-sentence reason tied to the highest-severity finding>

## Notes / Limitations
<anything the review couldn't assess from the diff alone — e.g., "actual query frequency at runtime not visible in diff">
```

## Guardrails
- Never actually approve, merge, block, or comment-post on the PR — this skill produces a report for a human (or the calling agent) to act on; it has no merge authority.
- Never run the changed code, execute benchmarks, or fetch production data — review is static, diff-only.
- Never claim `CONFIRMED` authorship without a literal commit trailer or bot account in the metadata; don't let stylistic guesses inflate confidence.
- Never fabricate file/line citations — if you can't pin a finding to a specific hunk, don't report it as a finding.
- Never flag a large, well-structured refactor as a smell purely for size — boilerplate smells must be concrete repeated/generic patterns, not "this diff is big."
- If the diff is larger than can be reviewed thoroughly in one pass (very large PR), say so explicitly and ask the user to split it or scope the review to specific files, rather than silently skimming and reporting false confidence.
- If `gh` CLI calls fail (auth, not installed, PR not found), report that plainly and ask for a pasted diff — never invent diff content to keep going.
