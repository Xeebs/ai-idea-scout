# Scenario 1: Agent action-approval gate, enum-like inputs, low time-sensitivity

## Input (as a user would paste it)

> We run an internal agent platform. Every time one of our agents wants to take a "sensitive" action (send an email to an external domain, modify a billing record, delete a customer record, issue a refund over $500), we synchronously call GPT-4o-mini as a judge with a prompt describing the action type, the actor, and a short justification string the agent generated, and the judge returns APPROVE or DENY plus a one-line reason. This blocks the agent's turn until the verdict comes back — average judge latency is 900ms, and at our current volume (around 40,000 of these calls/day) that's become a real cost line too.
>
> 1. Gate call: synchronous call per sensitive-action attempt, payload = {action_type: enum of 6 fixed values, actor_id, justification: free text generated by the agent, target_resource_id}.
> 2. What varies: action_type is one of 6 fixed enum values; actor_id and target_resource_id are IDs (bookkeeping); justification is free text but in practice our agents tend to generate very similar justification strings for the same action_type + similar context (e.g., "refund requested per customer complaint about damaged item" shows up constantly in slightly reworded forms).
> 3. Judge changes: we update the judge prompt roughly every 3-4 weeks as we tune false-positive rates.
> 4. Repeat-input signal: we haven't measured duplicate justification strings directly, but anecdotally refund and billing-record actions feel very repetitive in phrasing.
> 5. Time-sensitivity: no, the correct verdict only depends on the action type, actor permissions, and justification content — not on anything that changes over time.
> 6. Latency/cost budget: we'd like p95 under 200ms if possible, current p95 is ~1.1s.

## Pass criteria

- [ ] Report explicitly separates verdict-relevant fields (action_type, justification, and presumably actor permissions/target context) from noise fields (actor_id, target_resource_id as raw IDs) — and does not fold raw IDs into the recommended cache key.
- [ ] Because action_type is enum-like but justification is free text with "anecdotal" repetition, the report recommends exact-match keying as the first-layer default and treats similarity-based keying as an explicit second phase, not a default, given the signal is only anecdotal (item 4) rather than measured — and must not report a numeric hit-rate ceiling since no measured repeat-input rate was given.
- [ ] Section 4 (Hit-Rate Ceiling) must explicitly decline to give a percentage and instead recommend logging/sampling real justification strings to measure duplicate/near-duplicate rate — the input text uses the word "anecdotally," which is not a measurement.
- [ ] TTL/invalidation section recommends version-tagging verdicts to the judge prompt and invalidating on the ~3-4 week update cadence; does not claim time-sensitivity carve-out is needed (since item 5 says no).
- [ ] Given a safety/compliance-adjacent category (billing/refund actions, i.e. money movement) is involved, if similarity-based keying is recommended at all as a future phase, the report must carry an explicit written risk flag about serving a cached verdict for a non-equivalent justification.
- [ ] Backend scope should note a shared backend (not pure in-memory) is likely warranted given 40,000 calls/day is almost certainly a multi-process/distributed deployment — flagged as a reasoned inference, not a hard requirement, since deployment topology wasn't stated explicitly.
- [ ] Report does not produce or reference running cache code — strategy only.
- [ ] Report does not state any latency figure as "measured by this review" — the 900ms/1.1s figures, if cited, are attributed to the user's own numbers.

## Fail conditions

- Inventing a specific hit-rate percentage (e.g., "expect ~35% hit rate") without a real measured sample.
- Recommending similarity-based embedding caching as the sole/default key mode for a money-movement action category without a risk flag.
- Including actor_id or target_resource_id as part of the recommended cache key without flagging it as likely noise.
- Producing or suggesting actual code for the cache implementation.
