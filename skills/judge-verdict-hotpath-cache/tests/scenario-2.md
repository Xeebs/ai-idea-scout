# Scenario 2: Chat response-quality gate, free-text inputs, partial time-sensitivity, thin info given

## Input (as a user would paste it)

> We have a customer-facing chatbot. Before sending any response to the user, we run it through a synchronous "quality + safety" judge call (Claude Haiku) that checks the response isn't hallucinated, isn't off-brand, and doesn't leak internal info. If it fails, we regenerate. This blocks the user from seeing a response until the judge returns, and it's maybe 15-20% of our total per-message latency.
>
> We don't really have a clean description of what varies — basically every response is different text generated by our main model, so every judge call input is different too. We tweak the judge prompt pretty often, honestly not on a fixed schedule, just whenever something slips through. We haven't thought about whether any of this is time-sensitive. No specific latency budget, we just want it faster and cheaper if we can.

## Pass criteria

- [ ] Report correctly identifies that item 2 (what varies) is given ("every response is different text") but this itself is the key classification signal: since the actual chatbot response text is essentially always unique, the report should flag that exact-match caching alone will have a very low ceiling for this gate, and should not falsely claim the fields are enum-like.
- [ ] Because item 3 (judge change cadence) is described as irregular/unscheduled ("whenever something slips through"), the report must mark invalidation/TTL guidance as qualitative/less certain and still recommend version-tagging on every judge prompt change regardless of cadence irregularity, rather than silently dropping the invalidation recommendation.
- [ ] Section 4 (Hit-Rate Ceiling) must explicitly state no quantitative ceiling is possible — no repeat-input signal was given, and the description actually suggests structurally low repetition (unique generated text) — and must recommend measuring real duplicate/near-duplicate rate before investing in similarity-based keying, rather than assuming it will help.
- [ ] Since time-sensitivity (item 5) was explicitly stated as "haven't thought about it," the report must not assume either way — it should ask or explicitly flag this as an open question needing an answer before finalizing TTL, rather than picking one assumption silently.
- [ ] Because the content involves hallucination/safety/off-brand checks (safety-adjacent) and the input is unbounded free text, if similarity-based keying is suggested as a future-phase option, it must carry the explicit written risk flag — same as scenario 1 — about serving a cached verdict for a non-equivalent generated response.
- [ ] Report explicitly notes "Confidence: limited" given the thin, partially-qualitative inputs (no fixed judge-change cadence, no time-sensitivity answer, no repeat-input data).
- [ ] Report does not invent a latency number ("15-20% of total latency" is the only figure given and must be attributed to the user, not restated as independently measured).

## Fail conditions

- Claiming a cache-key or hit-rate recommendation with unwarranted confidence given how thin and unique the described inputs are (e.g., recommending similarity-based caching as the primary/default approach without flagging the low-repetition signal and the safety risk).
- Silently assuming an answer to the time-sensitivity question instead of flagging it as unresolved.
- Marking "Confidence: full" despite the clearly incomplete, irregular inputs.
- Producing actual caching implementation code instead of a strategy document.
