# Hard Gate: A Portable SMT Verification Layer for Agent Actions, Benchmarked Against LLM-as-Judge

- **Status**: EXPLORING (promoted 2026-11-13 cycle 67: evidence density — ≥2 independent threads found in gap analysis beyond qwed-verification itself — an academic SMT/Z3 paper, AWS Bedrock's Automated Reasoning checks, and a commercial PolicyLayer gate — none portable or benchmarked against LLM-as-judge)
- **Date**: 2026-11-13
- **Topic**: LLM evaluation & observability
- **Source**: research/2026-11-13-llm-evaluation-observability-ii.md · P5
- **Maturity verdict**: PARTIAL — Beyond qwed-verification, found a March 2026 academic paper (SMT/Z3-based policy checking for tool-using LLM agents, evaluated on TauBench), AWS's Cedar-policy-layer + "Automated Reasoning checks" (a real shipped Bedrock feature, but vendor-specific and the natural-language-to-formal-constraint translation step is itself LLM-assisted and unproven at scale per AWS's own caveats), and a commercial PolicyLayer `check_action` SMT-backed gate (product listing, not independently evaluated). No head-to-head evaluation of solver-gating vs. LLM-as-judge was found. Real academic and early-vendor traction but fragmented, unevaluated as a general pattern, and no dominant implementation.
- **Format**: BOTH — the runtime solver-gate is persistent middleware intercepting live tool calls; translating a plain-English compliance rule into formal constraints for a given domain is a separable one-shot drafting task.
- **Data Sources**: CONNECTED — a hook into the agent framework's or MCP client's tool-call interception layer (the same stable extension point every major agent SDK and MCP client exposes today for inspecting a proposed call before execution). No mature, cross-framework connector for this exists yet — each framework's interception surface differs, so building 3-4 framework adapters is core engineering work, not a reused mature connector.

## The Gap
QWED-AI/qwed-verification's November 2026 PRs (#604, #605) show a small team actively fixing its own verifier's correctness bugs ("verify-process is UNVERIFIABLE and DENY, never VERIFIED") while enforcing a "no path bypasses verification, fail closed" checklist — real demand for deterministic, SAT/UNSAT-style action gating as a complement to probabilistic LLM-as-judge scoring, but confined to one small, still-stabilizing project. AWS's Bedrock Automated Reasoning checks prove enterprises want this badly enough that a major cloud vendor shipped it, yet it's locked to Bedrock and AWS's own documentation concedes the natural-language-to-formal-constraint translation step is itself LLM-assisted and unproven at scale. No one has built or evaluated a portable, framework-agnostic version.

## The Project
A standalone SMT-backed (Z3) action gate that sits in front of any agent's tool-call execution path. Teams author a declarative policy as explicit formal constraints (e.g., "a `transfer_funds` call is admissible only if `amount <= daily_limit AND recipient IN approved_list`"); every proposed action is checked deterministically against the policy before execution and returns SAT (admit) or UNSAT (deny, with the specific violated constraint named — not a bare "denied"), fail-closed on any timeout or evaluation error so no path silently defaults to allow. The second, equally central component is a benchmark harness that runs the identical set of proposed actions through both the solver gate and an LLM-as-judge baseline side by side, reporting catch rate, false-positive rate, latency, and cost — the head-to-head comparison that currently doesn't exist anywhere, so teams can see exactly where formal gating earns its keep versus where probabilistic judging still has to carry the load.

Components: a minimal declarative policy DSL compiling to Z3 constraints; the SMT evaluation engine with structured SAT/UNSAT-plus-reason output; adapters for 3-4 common tool-call interception points (an MCP server wrapper, LangChain/CrewAI/Claude Code hooks); the dual-track benchmark harness and comparison report.

## Tangible Impact
**Population**: Teams building agents in domains where "mostly right most of the time" is not an acceptable bar — financial-services agents executing transfers or trades, healthcare agents ordering clinical actions, infrastructure agents making IAM/deploy changes — where an auditable, deterministic admit/deny decision is a compliance or safety requirement, not a nice-to-have. This is explicitly the buyer AWS itself targets with Bedrock's Automated Reasoning checks' regulated-industry marketing, minus the lock-in to one agent stack.
**Mechanism**: Today these teams either accept LLM-as-judge's probabilistic risk on actions that genuinely need a hard yes/no (unacceptable for an auditor or a regulator), lock into AWS's proprietary Bedrock-only feature whose translation step AWS itself flags as unproven, or hand-build a bespoke SMT layer in-house the way qwed-verification is doing in public, bugs and all. A portable, benchmarked solver gate gives them a vendor-neutral, auditable, fail-closed verification step plus hard evidence of exactly where it outperforms or falls short of LLM-as-judge on their own action set.
**Measure**: (1) SAT/UNSAT decision accuracy against a hand-labeled test set of admissible/non-admissible proposed actions, targeting near-100% given formally expressible rules, benchmarked against the LLM-as-judge baseline's measured error rate on the identical set. (2) False-admit rate on deliberately violating actions = 0% under adversarial testing (the fail-closed requirement). (3) Per-decision latency and cost versus an LLM-as-judge call on the same action, establishing whether solver-gating is cheap enough to run on every action rather than a sampled subset.

## Why Now
AWS's own November-2026-documented caveat — that its natural-language-to-formal-constraint translation step is unproven at scale — is the freshest public confirmation from a funded vendor that the market wants this and that the exact weak point (translation, not the solver itself) is still unsolved anywhere, generalized or not. Z3 and comparable SMT solvers are mature, fast, and free; the gap is purely that nobody has packaged a portable version with the comparative evidence to back it.

## Skill Angle
Given a plain-English compliance rule or safety policy for a specific agent action (e.g., "transfers over $10k to a new recipient need manager approval"), draft the equivalent formal constraint in the policy DSL, flag any part of the rule that can't be cleanly reduced to a formal constraint (and therefore still needs an LLM-as-judge or human check), and note the tradeoff. This is exactly the translation step AWS's own docs flag as the unproven weak point — doing it explicitly and flagging what doesn't translate is more honest than AWS's current silent LLM-assisted translation, and it's useful immediately for any team drafting a policy before the runtime gate exists.

## MVP Sketch
A Python library wrapping Z3 with a minimal YAML-to-constraint DSL, one tool-call interception adapter (e.g., an MCP server wrapper or Claude Code hook), and the dual-track benchmark harness. Experiment: build 50-100 labeled proposed-action test cases for one semi-regulated scenario (e.g., "should this agent execute this financial transfer"), run them through both the solver gate and an LLM-as-judge baseline, and report catch-rate/false-positive/latency/cost side by side against ground truth. 3-4 weeks for 1-2 people.

## Risks & Open Questions
- Natural-language policies often resist clean formal reduction — exactly the bottleneck AWS's own caveat names — so the translation skill/DSL could become the real limiting factor rather than the solver itself.
- AWS or another well-funded agent-security vendor could generalize their own formal-verification feature across frameworks before this ships, given they already have the hard solver-integration work done.
- Solver-gating only catches violations expressible as explicit constraints; it structurally cannot catch "the action is a bad idea for reasons outside the ruleset," so it complements rather than replaces LLM-as-judge — a team expecting full replacement will be disappointed.
- qwed-verification's own public bug-fixing on verdict correctness shows this remains a correctness-hard problem even scoped to one project; a generalized library inherits that same risk at a larger surface area.
