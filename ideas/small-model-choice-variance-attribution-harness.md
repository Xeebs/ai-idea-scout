# Lever Check: A Variance-Attribution Harness for "Is Model Choice Even What Matters" Small-Model Evals

- **Status**: PROPOSED
- **Date**: 2026-11-19
- **Topic**: Small & local models
- **Source**: research/2026-11-19-small-local-models.md · P5
- **Maturity verdict**: PARTIAL (general eval infrastructure — EleutherAI's lm-evaluation-harness, local RAG-eval harnesses, an evaluation-driven-iteration framework — exists and could be adapted, but no surfaced tool packages the specific reusable methodology: building a domain eval set across many small models and attributing output-quality variance to model choice vs. prompting/retrieval, as a generalizable, cross-domain workflow)
- **Format**: PROJECT
- **Data Sources**: MANUAL (MVP) — the user uploads or pastes their own domain question set (or a small seed set the tool expands) and names which small local/open-weight models and prompt/retrieval variants to compare; the harness itself runs the models. CONNECTED upgrade path: fetching model weights/configs directly from the Ollama local registry or the Hugging Face Hub API (both mature, well-documented APIs) instead of the user manually downloading each candidate model — this is a near-term, clearly-scoped addition, not a hard prerequisite for the MVP.

## The Gap
A practitioner's Hacker News post ("I tested 12 small AI models on 2,500 design-system questions," 3 points, 2026-10-27) concluded that, for their task, "the model wasn't what mattered" — prompting and context handling dominated output quality more than which small model was running underneath. The gap-analyst confirmed general eval infrastructure exists (lm-evaluation-harness, retrieval-only RAG eval harnesses, structured-extraction eval frameworks) but found no tool that packages this specific methodology — isolating how much of a model-swap's apparent quality gain is actually attributable to the model vs. to prompting or retrieval changes made alongside it — as a reusable, cross-domain workflow. Every team that wants this finding has to build its own large manual eval set from scratch, as this one practitioner did.

## The Project
A harness that takes a team's own domain question set (or a small seed the tool synthetically expands and the team reviews/edits), runs a 2x2-style ablation — fixed-model/varying-prompt-and-retrieval vs. varying-model/fixed-prompt-and-retrieval — across whichever small local or open-weight models the team names, and reports a variance decomposition: how much of the observed score spread is explained by model identity versus by prompt/retrieval configuration. The output is a single chart and number a team can use to decide where their next engineering hour actually buys quality, instead of defaulting to "upgrade the model" because that's the easiest lever to reach for.

Core components: (1) a question-set intake and lightweight synthetic-expansion step with human review; (2) a model/config-matrix runner wrapping common local-inference backends (Ollama, llama.cpp, vLLM) alongside prompt/retrieval variants supplied by the team; (3) a scoring layer (reuses an existing judge/rubric approach rather than reinventing one); (4) a variance-decomposition report distinguishing model-attributable vs. prompt/retrieval-attributable score spread, with confidence intervals given the eval-set size.

## Tangible Impact
**Population**: Engineering teams shipping small-local-model-powered features under real constraints (cost, latency, on-device/offline/air-gapped privacy requirements) who are about to spend a sprint or more "upgrading the model" as their default response to a quality complaint — a recurring decision point across the dozens of self-hosted/local-model projects already active in this research cycle's own digest (LocalLLaMA, selfhosted communities, edge-deployment teams).
**Mechanism**: Today that decision is made on vibes or a handful of spot-checks; building the kind of 2,500-question eval set the HN practitioner built is enough manual effort that most teams skip it and guess. This harness makes the attribution cheap enough to actually run before committing engineering time, redirecting effort toward the lever (prompting/retrieval) that the evidence says actually moves the number, or confirming model choice really is the bottleneck when it is.
**Measure**: (1) the proportion of "let's try a bigger/different model" decisions that the variance decomposition would have redirected toward a prompt/retrieval fix instead, measured on teams that adopt it; (2) engineering hours spent per model-swap decision before vs. after adoption; (3) eval-set and harness reuse rate across a team's subsequent model-generation upgrades (a sign the investment compounds instead of being thrown away each time, the problem the HN practitioner's one-off effort had).

## Why Now
The last 30 days surfaced both halves of this gap independently in the same digest: a practitioner doing exactly this analysis by hand at real scale (2,500 questions), and a mature general eval-infrastructure ecosystem (lm-evaluation-harness, local RAG-eval tooling) with the right primitives but none of them wired together for this specific attribution question. Local/open-weight small models have also gotten genuinely competitive enough on cost and latency this year that "should we swap models" is now a live, recurring decision for far more teams than it was even a year ago, raising the value of making that decision cheaply and correctly.

## MVP Sketch
Scope: a CLI tool that takes a CSV/JSON question set, a list of Ollama-servable model names, and 2-3 named prompt/retrieval variants; runs the full matrix (models x variants); scores each response against a simple rubric or an existing judge call; outputs a variance-decomposition chart. Stack: Python, Ollama for local inference, a lightweight judge (small local model or cheap API call) for scoring, matplotlib/plotly for the report. Single experiment that validates or kills it: reproduce the HN practitioner's own finding on a public domain question set (e.g., a coding or support-ticket dataset) — if the tool's variance decomposition independently confirms "model choice explains less variance than prompting" on a dataset the team didn't hand-tune, the methodology generalizes; if it can't reproduce any clear attribution signal, the ablation design needs rework before further investment.

## Risks & Open Questions
- The core risk is genericity: without a tight, opinionated default rubric and prompt/retrieval variant taxonomy, this collapses into "yet another eval harness wrapper" that doesn't actually answer the attribution question better than lm-evaluation-harness used carefully already could.
- Judge reliability for the scoring layer is itself an open, actively-debated problem (see this pipeline's own LLM-as-judge-calibration ideas) — a flawed judge could produce a confidently wrong variance decomposition, which is worse than no decomposition at all.
- Teams may not have 2,500 real questions lying around the way the HN practitioner did; the synthetic-expansion step's quality determines whether smaller teams can use this at all, and that's unvalidated.
- This could be seen as adjacent to several existing ideas in this index (corpus-aware RAG strategy selection, agentic-stack benchmark selection) — the differentiator that must hold up in practice is the variance-decomposition framing (model-attributable vs. other-attributable spread) rather than just "pick the best option," which none of those existing ideas do.
