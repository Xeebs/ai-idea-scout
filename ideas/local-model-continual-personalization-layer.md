# Grows With You: An Opt-In, User-Triggerable Continual Personalization Layer for Local Small Models

- **Status**: PROPOSED
- **Date**: 2026-11-19
- **Topic**: Small & local models
- **Source**: research/2026-11-19-small-local-models.md · P4
- **Maturity verdict**: PARTIAL (no shipped consumer product does this; an active research direction — NeurIPS 2026's "Continual On-Device Personalization of Small Language Models from Hindsight," "Synapse" low-rank adapters, and a November 2025 arXiv prototype-based error-correction paper with an Android demo — reports working demos, but all are research-stage/lab-evaluated, not user-reachable production tools; a live GitHub PR on `alehar9320/agentic-odi` builds the mechanism but, by its own author's admission, leaves it unwired to anything a real user can trigger)
- **Format**: PROJECT
- **Data Sources**: CONNECTED — the host application's own interaction events, captured automatically each time the user works with the local model (e.g., a code editor extension's accept/reject/edit signal on a completion, or a local chat app's thumbs-up/down plus follow-up-edit signal), not pasted or uploaded by the user. No mature third-party connector exists for this specific "behavioral correction signal" today — the extraction hooks (an editor-extension API integration, or a browser-extension content-script integration for a web-based local-model app) are built as part of this project, scoped to one host application for the MVP.

## The Gap
A GitHub PR on `alehar9320/agentic-odi` ("feat(studio): a browser model that gets stronger the more you work," 3 reactions, 11 comments, opened 2026-11-01) builds the scaffolding for a browser-resident model that updates from a user's ongoing work — an engine, a routing seam, a scheduler — but the author's own review note states plainly: "the feature is *not* reachable by a person yet — nothing calls `setConsent`, and `scheduler.ts:90` returns early when no t[one]." The gap-analyst confirmed this isn't an isolated case: NeurIPS 2026 and a 2025 arXiv paper independently demo the same continual-personalization concept with persistence across restarts, but every one of these remains a research prototype — none is wired into a tool a real person can turn on and use.

## The Project
A reference implementation of exactly the missing piece: a consent-gated, user-triggerable continual personalization layer that sits beside a local small model (in a code editor, a local chat app, or a browser-resident assistant) and incrementally updates a lightweight adapter (low-rank, in the style of the cited Synapse approach) from the user's own accept/reject/edit signal over time — with a visible on/off toggle, a way to inspect what's been learned, and a one-click reset. The differentiator against the research prototypes is that this is built to actually be turned on: explicit consent flow, bounded and auditable adapter state, and real persistence across app restarts validated by a user, not a lab harness.

Core components: (1) an interaction-capture hook scoped to one host app (e.g., a VS Code extension capturing completion accept/reject/edit events); (2) an incremental low-rank adapter update step that runs locally, triggered on a schedule or a user-initiated "learn from today" action, never silently; (3) a consent and visibility UI — what's been learned, when, from what, with a reset button; (4) a persistence layer surviving app/model restarts, benchmarked for drift and for catastrophic-forgetting risk against the base model's general capability.

## Tangible Impact
**Population**: Privacy-conscious power users of local/open-weight AI tools — developers using a local coding assistant (a population large enough to be a named rotation topic in this pipeline's own prior cycles, and a growing share of the broader local-LLM community this digest's own evidence base is drawn from: LocalLLaMA, selfhosted) who want their tool to pick up their own conventions and corrections over time without any of that behavioral data leaving the device or going through a cloud fine-tuning pipeline.
**Mechanism**: Today, a local model's quirks and repeated mistakes stay exactly as repeated as day one unless a user manually re-prompts or re-explains the same correction every session — the research prototypes that promise otherwise are unreachable. This project gives that user an actual, visible switch: turn personalization on, work normally, periodically review and approve what's been learned, and watch repeat-correction frequency drop over subsequent sessions.
**Measure**: (1) repeat-correction rate for a tracked set of user-specific conventions/preferences, measured session-over-session, before vs. after personalization is enabled; (2) general-capability regression on a held-out benchmark (to catch the catastrophic-forgetting risk the research literature flags) after N personalization cycles; (3) opt-in and sustained-usage rate among users offered the toggle, as a direct signal of whether the consent-and-visibility framing actually gets used versus ignored like the unreachable research demos.

## Why Now
Low-rank adapter techniques (LoRA and its continual-learning variants like the cited Synapse approach) are now cheap enough to update incrementally on consumer hardware without a full retraining pass, and local small models have gotten capable enough that "my local assistant doesn't learn my preferences" has become a visible, named complaint rather than an accepted limitation — exactly what the `agentic-odi` PR and the parallel NeurIPS/arXiv research line are independently reaching for right now, with the missing piece on both sides being the same: making it reachable by an actual person.

## MVP Sketch
Scope: a VS Code extension for a single local coding-assistant model (served via Ollama or llama.cpp) that captures accept/reject/edit signal on suggestions, runs a scheduled low-rank adapter update, and exposes an on/off toggle plus a "what I've learned" panel. Stack: TypeScript extension + a local Python adapter-training service, LoRA via a standard local fine-tuning library (e.g., peft), SQLite for interaction-log persistence. Single experiment that validates or kills it: track a defined set of 5-10 personal coding conventions (naming style, preferred libraries, comment style) across a week of real use, enable personalization after day 2, and measure whether repeat-correction rate on those specific conventions actually drops in days 3-7 versus days 1-2 — if it doesn't move, the adapter-update approach isn't capturing the right signal and the mechanism needs rework before scaling to more host apps.

## Risks & Open Questions
- Catastrophic forgetting / general-capability regression from incremental adapter updates is a real, documented risk in continual-learning research — the MVP's held-out benchmark check is there specifically to catch this before anyone trusts the loop unattended.
- A genuinely mature host-app integration (editor extension APIs, browser extension APIs) is real engineering work per host app — the MVP deliberately scopes to one (VS Code) rather than promising universal coverage, and that single-app bottleneck is the main reason a research team hasn't shipped this yet either.
- The strongest reason this might stay unsolved: the research papers themselves (NeurIPS 2026, the 2025 arXiv prototype) are recent and still lab-stage — if an incremental adapter update genuinely can't be made safe/cheap/reliable enough for unattended consumer use at today's hardware tier, no amount of UI polish fixes that, and this MVP's held-out-benchmark experiment is the fastest way to find out.
- Consent/visibility UX for "what has my assistant learned about me" is itself a hard, under-explored design problem (how do you show a low-rank adapter's content in a way a non-ML-expert can audit?) — a bad answer here could make the feature feel more invasive than the cloud alternatives it's meant to replace, undermining the entire privacy-pitch premise.
