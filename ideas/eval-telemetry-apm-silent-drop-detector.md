## The Gap
DataDog/dd-trace-py PR #21690 (2026-11-11) fixed exactly this inside DataDog's own product: "Experiment spans can be silently lost when they ride inside APM traces... It then inherits every limit and drop in the APM pipeline." Even a maintained, funded observability vendor only caught this in November 2026 — meaning any team that instrumented LLM eval/experiment data through a generic APM tracer before this class of fix was silently losing evaluation data without knowing it. Web search found the same root cause independently documented across Langfuse, Groundcover, Lumigo, Braintrust, and a live Vercel AI SDK GitHub issue, each only patched per-vendor, never generalized.

## The Project
A vendor-agnostic diagnostic-and-mitigation pair. The diagnostic sends synthetic oversized eval/experiment payloads (long prompts, verbose judge rationales, multi-turn transcripts) through a team's actual OTel/APM export path and reports exactly what gets silently truncated or dropped and at which stage — cross-referenced against the known per-vendor limits already catalogued in the digest's evidence (2MB/event, 10KB/span, 2KB/field, etc.). The mitigation is a drop-in OTel span-processor that detects when a span is eval/experiment-shaped (via `gen_ai.*` / LLMObs-style attributes) and routes it through a side-channel export path — direct-send or offload-to-blob-with-reference — bypassing the generic APM pipeline's inherited limits, generalizing what DataDog just shipped for its own product into a stack-agnostic package.

Components: a synthetic-payload injection probe with per-vendor known-limit fingerprints; a drop/truncation detector comparing sent vs. received payload hashes and sizes; an OTel span-processor that forks eval-shaped spans onto a dedicated export path; a plain-text risk report.

## Tangible Impact
**Population**: Engineering teams who bolted LLM eval/experiment tracing onto an already-deployed general-purpose APM or OTel collector (Datadog, New Relic, Grafana/Tempo, a self-managed OTel collector) instead of adopting a dedicated LLM-eval platform from day one — realistically most mid-size engineering orgs shipping LLM features, since incumbent APM adoption (Datadog alone reports over 27,000 customers) predates the LLM-eval tooling wave by years, so the default path for most teams is "extend what we already pay for," not "switch vendors."
**Mechanism**: Today these teams trust their eval dashboards and judge scores as complete, when in fact a meaningful share of long prompts, completions, or judge rationales were silently truncated or dropped before scoring — exactly DataDog's own admitted failure mode. The diagnostic turns an invisible assumption ("our eval data is intact") into a measured fact before anyone trusts a score built on it; the side-channel exporter then removes the root cause going forward, independent of which APM vendor the team is locked into.
**Measure**: (1) % of synthetic oversized payloads correctly flagged as truncated/dropped across tested backends, targeting ~100% detection matched against each vendor's documented cap. (2) Bytes of eval payload preserved after deploying the side-channel exporter vs. the measured baseline loss on the same traffic. (3) Number of backtested judge-score discrepancies (score computed on a truncated payload vs. the same input replayed intact) a pilot team's historical traces reveal once probed.

## Why Now
DataDog's own November 2026 fix is the first public confirmation, from a well-resourced vendor, that this exact silent-loss pattern was live in a production observability pipeline until days ago — meaning any team on an older APM-riding setup, on DataDog or anywhere else, has an unverified blind spot right now and no way to check it themselves without this diagnostic.

## Skill Angle
Given a pasted description of a team's current tracing setup (vendor, SDK/collector version, any custom span-processor or exporter config, roughly how large their typical prompt/completion/judge-rationale payloads run), cross-reference it against the digest's catalogued per-vendor known limits and flag the specific attributes and payload sizes most likely being silently truncated or dropped today, with a recommended immediate mitigation (raise a config limit, move to attachment offload, or adopt a side-channel pattern) ranked by effort. This is the one-time audit a team runs before trusting their current setup, independent of ever deploying the runtime exporter.

## MVP Sketch
A Python OTel `SpanProcessor`-based probe that fires 10-20 synthetic oversized payloads at a pilot team's real export pipeline and diffs sent-vs-received size/content; a first side-channel exporter targeting one backend (generic OTLP collector) that forks `gen_ai.*`-tagged spans onto a direct-send path. Experiment: run the probe against one pilot team's live pipeline, confirm it reproduces at least one of the digest's documented per-vendor limits, then measure byte-retention improvement after swapping in the side-channel exporter. 2-3 weeks, 1 person.

## Risks & Open Questions
- Every major APM/observability vendor could ship DataDog's own fix pattern (direct-send for LLM spans) natively within months, narrowing this to a stopgap for teams on slower release cycles.
- Synthetic payload injection into a live production pipeline needs careful scoping (tagged/sandboxed traffic) to avoid itself becoming a cost or noise problem for the team being audited.
- The side-channel exporter's "bypass the APM pipeline" approach could itself run into a *different* backend's size limits (e.g. a dedicated eval store's own caps), so the fix needs its own documented ceiling, not an assumed unlimited path.
- Evidence base is strong (DataDog's own shipped fix plus four independently documented vendor caps) but no one has yet measured how much real eval data loss this causes in aggregate — the diagnostic itself is the first instrument to produce that number.
