# ArchPick: A Shared Benchmark Harness for the Cascaded-vs-Speech-to-Speech Decision

- **Status**: PUBLISHED
- **Date**: 2026-11-12
- **Topic**: Voice & multimodal agents
- **Source**: research/2026-11-12-voice-multimodal-agents.md · P2
- **Maturity verdict**: PARTIAL (one academic benchmark exists — EVA-Bench, arXiv 2605.13841, a live multi-turn simulation across S2S and cascade architectures — plus numerous vendor comparison posts [AWS/Nova Sonic, Inworld, Coval, Dograh, JustCall] offering ad hoc heuristics with conflicting latency claims; no single reusable, cross-vendor decision tool or rubric exists that teams adopt instead of running their own bake-off, confirmed by two separate small-team GitHub issues independently re-deriving the same comparison criteria from scratch)
- **Format**: BOTH

## The Gap
Every small team building a voice agent hits the same fork: cascaded pipeline (separate STT/LLM/TTS, independently swappable, better observability) or unified speech-to-speech model (lower theoretical latency, but vendor lock-in and harder debugging). Two GitHub issues from unrelated small repos — `changtimwu/elifalanrocha-exp#1` evaluating ElevenLabs Realtime against an existing cascaded pipeline, and `thomaseude/t3code-voice#7` explicitly listing comparison criteria (language quality, latency, barge-in handling, tool calling) for the same choice — show teams independently building their own private evaluation rubric rather than reusing one. Vendor blogs disagree with each other on the headline numbers (Coval says S2S is faster; Inworld says a well-engineered cascade can beat it; one AssemblyAI panel reports both of its surveyed teams run cascaded for ~99% of their agents specifically to avoid lock-in), which means the published guidance is actively contradictory, not just absent.

## The Project
A benchmark harness that a team points at their own use case — a set of representative call scripts/scenarios, the languages and vocabulary that matter to them, their latency and cost budget — and that runs those scenarios through both a reference cascaded stack (Whisper/Deepgram + an LLM + a TTS provider) and a reference unified S2S stack (e.g., OpenAI Realtime or Gemini Live), scoring both on latency percentiles, barge-in handling quality, tool-calling reliability, and per-minute cost, then outputs a decision report with the actual numbers for their domain rather than a vendor's. The centerpiece is that the comparison is run on the team's own scenarios, not a generic leaderboard — the two GitHub issues both show the generic published comparisons don't answer the domain-specific question teams actually have (e.g., "does this handle our technical French vocabulary").

## Tangible Impact
**Population**: small (2-8 person) engineering teams building vertical voice agents for a specific domain — healthcare intake, insurance claims, multilingual customer support, recruiting screening — who currently must choose a voice architecture with no shared tooling, evidenced by two independent small-repo GitHub issues each re-deriving comparison criteria from scratch rather than reusing an existing rubric or harness.
**Mechanism**: a runnable harness that scores both architectures against a team's own representative scenarios collapses what is currently a multi-week, ad hoc bake-off (standing up both stacks, writing eval scripts, manually scoring transcripts) into a day-long, repeatable run with domain-specific numbers — and reduces the downstream cost of picking wrong, since migrating a shipped voice agent from one architecture to the other mid-production is expensive (new integration, new observability, re-validated compliance for regulated domains like healthcare intake).
**Measure**: time from "we need to decide" to a documented architecture decision, compared against the multi-week ad hoc baseline implied by the two GitHub issues; rate of teams who re-platform (regret rate) within 6 months of their original choice; correlation between the harness's predicted latency/cost numbers and the team's actual production numbers post-launch.

## Why Now
2026 is the first year both reference architectures are simultaneously mature and cheap enough for a small team to stand up side by side (OpenAI Realtime, Gemini Live, ElevenLabs Realtime on the S2S side; Pipecat/LiveKit Agents with swappable STT/TTS on the cascaded side), which is exactly why the bake-off question has become common enough to generate the two independent GitHub issues this pattern is based on — the decision didn't used to be a live question when only cascaded pipelines existed.

## Skill Angle
A companion skill, "voice architecture triage," takes a short description of a team's use case (languages, latency tolerance, compliance/observability requirements, tool-calling needs, team size/expertise) and produces a fast, structured recommendation plus the specific risks of each path for that use case — a same-day triage that doesn't require running the full harness. It differs clearly from the project: the skill is a quick judgment call for teams who need a direction before investing in benchmarking infrastructure; the project is the actual runnable harness that produces hard numbers once a team is ready to validate that judgment.

## MVP Sketch
Build a CLI harness with two reference implementations (one Pipecat-based cascaded stack, one OpenAI Realtime S2S stack) that both accept the same scenario script format (a sequence of simulated user turns including an interruption and a tool-call-triggering request), run both, and output a comparison table (p50/p95 latency, tool-call success rate, cost per minute) plus a markdown decision summary. The single experiment: validate against 2-3 real teams' actual use cases and check whether the harness's recommendation matches what they'd have concluded after their own multi-week bake-off, in a fraction of the time.

## Risks & Open Questions
- EVA-Bench (arXiv 2605.13841) already exists as an academic benchmark — the project needs to differentiate by being a practically runnable, team-pointable harness rather than a fixed leaderboard, or it duplicates existing work.
- Reference implementations will drift out of date quickly as both cascaded component APIs and S2S model versions ship frequently; needs a low-maintenance update cadence or the harness itself becomes stale within months.
- The "right" answer may genuinely be domain-dependent and unstable (today's AssemblyAI panel shows 99% choosing cascaded for lock-in reasons that have nothing to do with raw latency numbers) — the harness must score non-latency factors (lock-in, observability, swappability) as first-class outputs, not just an afterthought.
- This idea is weighted toward developer-team impact rather than end-user impact; it only clears the bar if "named pain, named population of teams" is accepted as sufficient per methodology guidance, which it is here but is worth flagging as the weaker of this batch.
