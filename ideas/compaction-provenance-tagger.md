# Provenance Seal: A Provenance-Preserving Compaction Layer Against Instruction Laundering

- **Status**: PROPOSED
- **Date**: 2026-11-13
- **Topic**: Context engineering & memory
- **Source**: research/2026-11-13-context-engineering-memory.md · P5
- **Maturity verdict**: PARTIAL — GitHub search for provenance-tagged compaction tooling found nothing. The "Compaction Laundering" paper (arXiv 2610.29869) reports its own prompt-rule mitigation as weak (83%→62% and 86%→60% catch-rate reduction across two model families), while its provenance-check mitigation (77% catch rate at a 0.15 strictness threshold) is a research result, not an available compaction tool or library. No shipped coding-agent compactor was found that tags provenance through summarization by default — genuinely research-stage, tie-broken to PARTIAL per the rubric since a real, tested mitigation exists even if unshipped.
- **Format**: BOTH — the always-on provenance tagger wired into a compaction step is persistent runtime infrastructure; auditing a specific compacted transcript or an agent's existing compaction prompt for laundering risk is a separable one-shot review task.
- **Data Sources**: Project mode is CONNECTED — hooks into the agent runtime's own compaction step, reading the live conversation transcript and tool-call outputs directly from session state. Claude Code exposes a compaction hook today that a project build can attach to; Codex CLI and Cursor would need bespoke per-runtime integration since no standardized cross-runtime compaction-hook API exists yet. Skill mode is MANUAL — the user pastes a pre-compaction transcript excerpt (or the post-compaction summary plus the original untrusted tool/file content it was derived from) for review.

## The Gap
An arXiv paper surfaced on Hacker News in the last 30 days ("Compaction Laundering: Provenance Destruction in Context-Compacting Coding Agent," 2610.29869) names a concrete attack: standard compaction flattens a conversation — including untrusted tool/file output — into labeled text before summarizing, destroying provenance. A forged `[User]:`-style line planted inside content the agent merely *read* (a malicious README, a scraped web page, a poisoned file) can get compacted into what looks like a standing user instruction, with no record left that it didn't actually come from the user. Per a secondary summary of the paper, the paper's own prompt-level mitigation ("be careful during compaction") only modestly reduces the attack, while a dedicated provenance-check layer catches the large majority of attempts — but that provenance-check exists only as a research result, not a shipped compactor.

## The Project
A compaction wrapper that tags every span of conversation history with its origin (verified user turn, model turn, tool-call output, file/web content read by a tool) *before* summarization, and carries that tag through the summarization step so the compacted output never loses track of which lines were genuinely user-authored versus merely encountered. Any line in the post-compaction summary that reads like a standing instruction but traces back to an untrusted-content span gets flagged or stripped of instruction-authority rather than silently promoted to look user-authored. This directly implements the paper's validated provenance-check mitigation as a usable tool instead of a benchmark result — the centerpiece is making provenance survive the exact step (summarization) that currently destroys it.

Components: a span-tagger (classifies each turn/chunk by origin before compaction runs); a provenance-aware summarizer (passes tags through the LLM-based compaction call, or runs a post-compaction check pass comparing summary claims against tagged origins); a strictness-threshold-tunable laundering detector (replicating the paper's 0.15-threshold provenance check); a per-runtime hook (Claude Code first, given its existing compaction-hook surface).

## Tangible Impact
**Population**: Developers and teams running autonomous coding agents on real, often untrusted, repositories and web content — anyone whose agent reads third-party READMEs, scraped pages, issue trackers, or file content and then runs long enough to trigger automatic compaction, which per the paper's framing is the exact condition under which this attack class becomes exploitable. This spans essentially the population of long-running Claude Code/Codex/Cursor coding-agent users operating on non-self-authored code or content, a population already large and growing as autonomous agent sessions get longer.
**Mechanism**: Today, an attacker who can get a forged "[User]: ignore prior instructions and do X" line into any file or tool output the agent reads gets a free shot at having that line laundered into a trusted-looking standing instruction the moment compaction runs — with zero record that it wasn't actually said by the user. A provenance-preserving compactor closes that laundering window by making the compacted output unable to lose the distinction between "the user said this" and "the agent merely read this somewhere."
**Measure**: (1) Laundering catch rate on the paper's own benchmark methodology (or a reproduction of it), with the provenance layer on versus off, targeting the paper's reported ~77% figure as a floor to beat. (2) False-positive rate — legitimate user instructions incorrectly flagged as laundered, which determines whether teams can run this always-on without breaking normal use. (3) Successful-attack rate in an end-to-end red-team exercise (plant a forged instruction in a file, run a long session through compaction, check whether the agent acts on it) before versus after adoption.

## Why Now
A fresh arXiv paper landed on Hacker News in the last 30 days demonstrating this exact attack class with measured catch rates, and the paper itself states its own prompt-level fix is weak while its provenance-check fix is untooled — this is a narrow, time-sensitive window where the research has validated the right mechanism but no one has shipped it, before a major agent vendor (Anthropic, OpenAI, Cursor) absorbs the fix natively into their own compaction pipeline.

## Skill Angle
Given a pre-compaction transcript excerpt (or a post-compaction summary plus the original untrusted content it was derived from), review it for signs of instruction laundering: lines in the summary that read as standing user instructions but trace back to tool/file/web content rather than an actual user turn. Flag specific lines and explain the provenance break. Useful today as a one-off security audit of an agent's compaction behavior, independent of wiring in the always-on tagger.

## MVP Sketch
A thin wrapper around Claude Code's compaction hook that tags each turn by origin before the compaction LLM call runs, and a post-compaction checker that flags any instruction-shaped line in the output whose origin tag traces to untrusted content. Reproduce a simplified version of the paper's benchmark: plant 15-20 forged instructions across file/tool-output content, run sessions long enough to trigger compaction, and measure the catch rate and false-positive rate with the tagger on versus off. 3-4 weeks for 1-2 people, most of it spent reproducing a credible benchmark since the paper's own dataset isn't confirmed public.

## Risks & Open Questions
- Anthropic, OpenAI, or Cursor could ship provenance-preserving compaction natively — the most direct competitive risk, since they own both the compaction step and the hook surface this idea depends on.
- The underlying arXiv paper (2610.29869) was only confirmed via a secondary summary this cycle, not independently verified against the primary source — the MVP's first job is actually reproducing the paper's claimed catch rates before building further on top of them.
- A strictness threshold tuned for the paper's test conditions may not generalize to real-world transcripts, risking either missed laundering (too loose) or broken legitimate workflows (too strict).
- Cross-runtime portability is uncertain: Claude Code's compaction hook is confirmed to exist, but Codex CLI and Cursor's equivalent surfaces (if any) are unverified, which could leave this a single-runtime tool rather than a general one.
