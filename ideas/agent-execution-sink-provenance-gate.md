# Trace Gate: A Provenance-Tagged Execution-Sink Gate for Agent Tool Calls

- **Status**: EXPLORING (promoted 2026-11-13 cycle 56: evidence density — ≥2 independent threads)
- **Date**: 2026-11-13
- **Topic**: Tool use & MCP ecosystem
- **Source**: research/2026-11-13-tool-use-mcp-ecosystem-2.md · P4
- **Maturity verdict**: PARTIAL — GitHub search for shipped provenance-gating repos came up empty, but WebSearch found several 2026 academic prototypes with real evaluation results: Agent-Sentry (arXiv:2603.22868, provenance-graph gating, 94.3% injection block / 95.1% benign-action pass on AgentDojo/AgentDyn), Agentic Reference Monitor (arXiv:2604.04035, runtime tool-call/result tagging), and Risk-Aware Causal Gating (arXiv:2606.18550, claims zero injection success on a controlled benchmark). Research-stage, unreplicated, single-author/unreviewed preprints — real work exists but no production implementation.
- **Format**: BOTH — the runtime interceptor is a persistent tool-call-dispatch middleware; auditing a described tool catalog for sink/provenance exposure is a separable one-shot review task.
- **Data Sources**: CONNECTED — intercepts the live tool-call request stream at the agent framework's own tool-dispatch point (e.g., semantic-kernel's function-invocation pipeline, or the equivalent hook in any major agent SDK — a stable, already-existing extension point today) plus the content-ingestion adapters for whatever the agent fetches (web pages, email, file attachments) to apply trust tags at the point content enters context. No manual paste required for the runtime gate; the skill-angle version takes a pasted tool-catalog description.

## The Gap
Prompt injection doesn't need to breach a sandbox perimeter if it can redirect the agent's own reasoning into calling a legitimate, already-permitted tool (an `eval()`-backed tool, say) with attacker-controlled input — a "goal hijack" rather than an escape. [Prediction Guard](https://predictionguard.com/blog/ai-agent-code-execution-security-explained) cites CVE-2026-26030, prompt injection reaching an `eval()` call in semantic-kernel, and the OWASP Agentic Top 10 (2026) frames this class under goal hijack / unexpected code execution. Sources list generic mitigations (deny outbound network by default, cap resources/timeouts, require approval for high-risk actions) as best practices, not a shipped provenance-tracking layer that follows untrusted content through an agent's reasoning into which tools it's allowed to call.

## The Project
A provenance-tagging interceptor between an agent's reasoning loop and its tool-call dispatch. Content entering the agent's context gets tagged at ingestion with a trust label (direct user instruction = trusted; fetched web page/email/tool-result content = untrusted), and that tag propagates through the model's working context. Before any call reaches a tool the deploying team explicitly marks as an execution sink (code-interpreter, eval-backed tool, shell-exec, file-write) in a sink manifest, the gate checks whether the call's parameters trace back to untrusted content; if so, it blocks, requires human approval, or routes to a sandboxed dry-run, instead of letting the call through on the model's own judgment alone. This is scoped to a single agent's own reasoning-to-tool-call path — distinct from this index's `cross-agent-injection-firewall.md` ("Handoff Firewall"), which targets taint propagating across agent-to-agent handoffs, and `memory-retrieval-injection-sanitizer.md` ("Memory Wall"), which sanitizes retrieved memory/RAG content before it enters the prompt rather than gating which tool calls are allowed to fire once untrusted content is already in context.

Components: content-ingestion tagger (wraps fetch/email/tool-result adapters) · context-propagation tracker (span-level provenance through working context) · execution-sink manifest · gate/escalation logic (block/approve/sandbox-dry-run) · red-team eval harness reproducing CVE-2026-26030-style attacks plus the AgentDojo/AgentDyn benchmark.

## Tangible Impact
**Population**: teams deploying single agents with both broad tool access (code-interpreter/eval-backed tools, shell-exec, file-write) and exposure to untrusted content in the same context — email-processing assistants, coding agents that fetch and act on web content or issue trackers, support agents that read attachments. This directly targets the vulnerability class demonstrated in CVE-2026-26030 in semantic-kernel, a widely-used agent orchestration framework, so any of its production deployments sit in this population today.
**Mechanism**: today, a legitimate, already-permitted execution-sink tool call fires whenever the model's own reasoning decides to call it, with no structural check on whether the content that drove that decision came from the user or from something the agent merely read. The gate converts "trust the model's judgment" into "trust is structurally revoked once untrusted content enters the decision chain," stopping a goal-hijacked call even though no sandbox escape ever happened.
**Measure**: (1) block rate on a reproduced CVE-2026-26030-style attack suite plus the AgentDojo/AgentDyn benchmark, as an independent replication check against Agent-Sentry's self-reported 94.3%; (2) benign-task pass-through rate, compared against Agent-Sentry's reported 95.1% baseline; (3) added latency per gated tool call.

## Why Now
A concrete, named CVE in a widely-deployed framework (semantic-kernel) landed in the evidence window alongside three independent 2026 academic prototypes targeting the identical gap with real evaluation numbers — the research de-risking is done, nothing has moved from paper to a deployable interceptor yet, and OWASP's own Agentic Top 10 already names the failure class without naming a shipped fix.

## Skill Angle
Given a description of an agent's tool catalog and content-ingestion points (which tools fetch external content, which tools are execution sinks), audit it for goal-hijack exposure and recommend which tools need sink-manifest tagging and where the provenance boundary should sit — the same design decision the runtime gate enforces, done once by hand before committing to the interceptor build.

## MVP Sketch
2-4 weeks, 1-2 people. Implement the interceptor for semantic-kernel specifically (directly motivated by the named CVE), with a simple two-level trust tag (trusted/untrusted) propagated via a lightweight content-wrapper object rather than true dataflow tracking, a manifest marking eval-backed/shell-exec tools as sinks, and block-only gating (no sandbox-dry-run stretch goal). Experiment: reproduce CVE-2026-26030's attack path and confirm the gate blocks it, then run against a subset of AgentDojo to get an independent block-rate/false-positive number against Agent-Sentry's self-reported figures.

## Risks & Open Questions
- Provenance propagation through an LLM's own context is fundamentally leaky — the model can paraphrase untrusted content into text that looks clean, carrying the attacker's goal without an obvious taint marker; span-level tracking may be too coarse to matter or too fine-grained to maintain.
- All three cited academic results are unreplicated, single-author/unreviewed preprints — this project's first job is an independent replication check, and the numbers may not hold outside the paper's own controlled benchmark.
- If semantic-kernel or another major framework patches this CVE class with its own built-in provenance gate (plausible, given the named CVE already forced a patch), a standalone interceptor's value narrows to cross-framework portability.
- Overlaps conceptually with this index's Handoff Firewall and Memory Wall ideas — needs explicit positioning (single-agent, reasoning-to-sink-specific) to avoid being read as redundant with either.
