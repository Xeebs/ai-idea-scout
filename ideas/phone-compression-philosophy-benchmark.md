# Honest Compare: An Independent Head-to-Head Benchmark for On-Device Compression Philosophies

- **Status**: PUBLISHED
- **Date**: 2026-11-14
- **Topic**: Small & local models
- **Source**: research/2026-11-14-small-and-local-models.md · P6
- **Maturity verdict**: PARTIAL (vendor-reported comparison data exists — e.g. PrismML's own Ternary Bonsai 27B vs. a conventional 2-bit quant of the same base, AIME26 90.8 vs. 57.5 — but no independent/third-party reproduction of a head-to-head was found, a commentator explicitly called for independent verification of the vendor's own retention numbers, and the deeper point that input-handling/preprocessing — not compression method — is the real phone bottleneck turned up only one unverified blog post and no dedicated tool)
- **Format**: BOTH
- **Data Sources**: CONNECTED — pulls model weights for both compression families (ternary-native models like PrismML's releases, and compressed-from-large models like Bonsai 27B's conventional quants) directly from the Hugging Face Hub API (mature, freely accessible today) rather than asking a developer to supply weights manually; runs them on physical or emulated Android/iOS devices via existing device-farm/on-device-profiling tooling (e.g. Android Debug Bridge, Firebase Test Lab, or a self-owned device rack) to capture real latency/memory/battery numbers instead of simulated ones. The companion skill's only manual input is the developer naming their target task, phone tier, and constraints.

## The Gap
WebSearch surfaced two camps selling opposite routes to a phone-sized model — PrismML's ternary-from-scratch models (as small as 0.43GB, Apache 2.0, with vision and tool calling) versus the "compress a model that was born large" path analyzed around Bonsai 27B — each citing its own favorable numbers (e.g. PrismML's AIME26 90.8 vs. a 2-bit baseline's 57.5). No independent, third-party, same-hardware head-to-head of the two philosophies surfaced in any channel searched, and a commentator explicitly called for independent verification of the vendor's own retention claims. A second, under-addressed thread sits underneath both camps: a builder quote in the source material states "input handling, not inference, was the bottleneck on low-end phones" — suggesting the compression-method debate may be solving the wrong problem for a meaningful share of real-world phone deployments, yet only one unverified blog post on incremental tokenization was found addressing it.

## The Project
A reproducible, continuously-updated benchmark harness that runs matched tasks (tool-calling accuracy, vision-grounded QA, general reasoning) across representative ternary-native models and compress-from-large models at comparable final file sizes, on the same physical phone/SBC hardware tiers — reporting accuracy, cold-start latency, steady-state tokens/sec, peak memory, and battery draw side by side, with vendor-reported numbers shown alongside the independently reproduced ones so the gap between claim and reality is visible. A second module profiles the end-to-end request lifecycle (tokenization/image-preprocessing time vs. model-forward time vs. detokenization/output time) to settle, per task and hardware tier, whether input-handling genuinely dominates latency the way the builder quote claims — something neither vendor's benchmark currently isolates.

Core components: (1) a model-pair registry (ternary-native vs. compress-from-large, matched by final on-disk size) pulled live from Hugging Face Hub; (2) a device-farm execution harness running identical task suites on both; (3) a latency-breakdown profiler isolating input-handling time from inference time; (4) a published, re-runnable leaderboard that flags any vendor claim it could not reproduce within a stated tolerance.

## Tangible Impact
**Population**: Indie developers and small teams building on-device AI features for budget and mid-range Android phones — the devices that make up roughly 70% of global smartphone shipments by unit volume in emerging markets (per Counterpoint Research's global shipment-tier breakdowns), where RAM and thermal headroom are the binding constraint, not GPU-cloud budget. These builders currently have to choose a compression philosophy based on each vendor's own self-reported numbers with no way to check them against their own target device.
**Mechanism**: Today a developer picking between a ternary-native model and a compressed-from-large model for a budget-phone deployment relies on each vendor's cherry-picked benchmark, run on that vendor's own hardware and task set — a choice that can cost weeks of integration work if the model later performs far worse on the developer's actual device and task than advertised. An independent, re-runnable benchmark on real budget-tier hardware, plus the latency-breakdown profiler, tells a developer up front (a) which philosophy actually wins for their task/size budget and (b) whether their real bottleneck is even the model at all versus their own input-handling code, potentially saving them from compressing/swapping a model when the fix was elsewhere.
**Measure**: (1) the delta between each vendor's self-reported accuracy/latency numbers and this project's independently reproduced numbers on the same task and hardware tier (target: published for every model pair, however large the delta); (2) developer time-to-decision when choosing a compression philosophy for a target phone tier (target: under a day using the published leaderboard, versus the multi-vendor research currently required); (3) the share of total end-to-end latency attributable to input-handling vs. inference, per task and hardware tier, settling whether the community's "it's the preprocessing, not the model" claim holds generally or only in specific cases.

## Why Now
Both compression philosophies only became concretely comparable in late 2026 — PrismML's sub-1GB ternary releases with vision and tool-calling, and the Bonsai 27B compress-from-large analysis, both surfaced within the same 30-day window — meaning there was no prior point at which a matched head-to-head was even possible. The device-farm and on-device-profiling tooling needed to run it (Android Debug Bridge, Firebase Test Lab, standard mobile profiling harnesses) is already mature, so this doesn't wait on any new capability — only on someone running the comparison independently instead of trusting either vendor's self-report.

## Skill Angle
A companion decision-support skill: given a developer's target task description, phone tier (e.g. "2GB RAM Android, no NPU"), and latency/accuracy constraints, the skill consults the project's published leaderboard and latency-breakdown data and returns a recommended compression philosophy plus the specific model pairing, with the caveat if the developer's exact pairing hasn't been benchmarked yet. This differs from the project: the skill is a one-shot recommendation for a single developer's constraints; the project is the maintained, continuously-updated benchmark harness and device farm that generate the data the skill reads.

## MVP Sketch
Three to four weeks, 1–2 people: pick one ternary-native model (a PrismML release) and one compress-from-large model at a matched on-disk size, run both through 2-3 task suites (tool-calling, basic vision QA) on two real budget-tier Android devices, publish the first head-to-head table alongside each vendor's own claimed numbers, and ship the latency-breakdown profiler on at least one task to test the input-handling-bottleneck claim directly. Stack: Python/Android instrumentation (ADB-based profiling), Hugging Face Hub for weight retrieval, a small bench of physical low-end Android devices (cheaper and more credible than emulation alone for battery/thermal numbers).

## Risks & Open Questions
- Vendors may contest methodology differences (quantization calibration data, task set choice) as the reason for any reproduced-number gap — the harness needs to publish its exact methodology and invite vendor rebuttal rather than presenting one number as absolute truth.
- "Matched final file size" may not be a fair comparison axis if the two philosophies trade off size against different things (e.g. one preserves vision better, the other preserves tool-calling better) — the MVP should report per-capability breakdowns, not a single blended score.
- The input-handling-bottleneck claim came from a single unverified blog post in the digest's evidence — the profiler module needs to be built skeptically, ready to report "the model was actually the bottleneck" as a valid finding, not assume the claim is true going in.
- Device fragmentation among "budget Android phones" is itself large (NPU presence, RAM, thermal design vary widely) — the MVP must scope to 2-3 clearly named hardware tiers rather than claiming one number represents "budget phones" generally.
