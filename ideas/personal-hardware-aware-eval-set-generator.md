# Personal Bench: A Hardware-Aware Eval Set Generator Built From Your Own Task Samples

- **Status**: PUBLISHED (promoted 2026-11-18 cycle 148: evidence density — ≥2 independent threads within the digest, bmdpat.com's "your benchmark is probably lying to you" and dev.to/llm_ops's separate "I wrote my own small benchmark" piece, corroborated further by an Ask HN thread and a local-llm.net roundup)
- **Date**: 2026-11-18
- **Topic**: Small & local models
- **Source**: research/2026-11-18-small-and-local-models.md · P3
- **Maturity verdict**: OPEN — web search found only fixed-suite tools (BenchLoop's frozen YAML fixtures, PipelineScore's fixed 25-task suite, InferBench's tokens/sec-only measurement) and hardware-matching recommenders (whichllm, llmfit) that map a device to published generic benchmark scores rather than building a benchmark from a user's own task samples. No tool that turns "my actual prompts on my actual machine" into a reusable personal eval set surfaced in GitHub, web, or paper search; multiple independent blog authors (bmdpat.com, dev.to/llm_ops) describe hand-rolling this from scratch as a one-off script each time.
- **Format**: BOTH — the stored eval set, the saved score history across models, and the re-run harness are a small persistent artifact a user keeps and reuses over months; a one-time "help me assemble a good eval set from these three example tasks" judgment is a separable advisory step.
- **Data Sources**: MANUAL (task samples) + CONNECTED (hardware/model detection). The user pastes or exports 5-20 real examples of what they actually ask their local model to do (a prompt plus what a "good" answer looks like, in their own words or a reference answer) — this is the one thing that must come from the user, since no generic API can infer "my actual task." Hardware detection and candidate-model enumeration are CONNECTED and need no new connector: local system introspection (`nvidia-smi`/`rocm-smi`/platform APIs, mature, already used by comparable tools like `llmfit`) for the device profile, and Ollama's local `/api/tags` endpoint or the Hugging Face Hub API (both mature, documented) to enumerate installed or candidate models to test.

## The Gap
Independent authors are solving the identical problem by hand: a dev.to/blog post titled "Your local LLM benchmark is probably lying to you" argues published leaderboard numbers lack context for any one person's hardware or workload, and a separate author states plainly "I wrote my own small benchmark, tuned to exactly my laptop" after testing 4 of their own models. An Ask HN thread and a community roundup (local-llm.net) both frame these as scattered anecdotal field reports, not a repeatable process. Nobody has packaged "take a handful of my real examples and my hardware, and give me back an eval set and score I can trust and re-run" — every existing tool is either a fixed generic suite or a hardware-to-published-score matcher, neither of which touches the user's actual task.

## The Project
A CLI/library that takes a small set of the user's own real task examples (prompt + reference-quality answer, or a pass/fail rubric per example if there's no single right answer) and a detected local hardware profile, then: (1) runs a slate of candidate small/local models (whatever the user has installed via Ollama, plus suggested downloads that fit the detected VRAM/RAM budget) against the user's examples, (2) scores each with a configurable method — exact/rubric match where possible, an LLM-judge pass for open-ended tasks — and (3) stores the result as a durable, versioned "personal benchmark" the user re-runs whenever they add a new model or a new example, so the report tracks drift and improvement over time instead of being a one-off printout.

Components: an example-set manager (add/edit/version the user's own task examples); a hardware prober reused from the same local-introspection pattern as comparable tools; a model-candidate runner against installed/suggested Ollama models; a pluggable scorer (exact-match, rubric-match, LLM-judge); a persisted score-history store so "did the new model I just downloaded actually help my specific use case" has a real answer.

## Tangible Impact
**Population**: Hobbyists and indie developers running local models for a specific recurring personal or small-team task (a dictation cleanup rewrite, a narrow classification rule, a personal coding-assistant workflow) who today either trust a published leaderboard that doesn't reflect their task or hardware, or hand-roll a throwaway benchmark script for a single comparison and then discard it. r/LocalLLaMA's 680k+ members are the proxy population for self-hosted model experimentation at this scale; the specific pain (leaderboard numbers don't predict my hardware/workload) is independently voiced by multiple blog authors and an Ask HN thread in the same 30-day window.
**Mechanism**: Replaces "guess from a published number, download, try it, discover it's wrong for my task, repeat" with a durable, reusable personal eval set that is actually built from the user's own examples — so picking between two local models for a specific task becomes a 10-minute re-run against stored criteria, not a fresh investigation each time a new model drops.
**Measure**: (1) time from "a new model is released" to "I know if it helps my specific task," target under 15 minutes via a re-run versus the multi-hour manual comparison the cited blog posts describe; (2) correlation between a model's score on the user's personal benchmark and the user's own stated satisfaction after real-world use, to validate the benchmark actually predicts usability (the thing published leaderboards were accused of failing to do); (3) number of distinct personal eval sets created and re-run more than once (proof the tool gets reused, not discarded like the scripts it replaces).

## Why Now
Enough small/local models now ship monthly that "which one is actually best for my task" has become a recurring, not one-time, question — exactly why multiple independent people built throwaway personal benchmarks in the last 30 days — but no one has packaged the obvious next step: making that personal benchmark durable and re-runnable instead of a disposable script.

## Skill Angle
Trigger: a developer has a specific recurring local-model task and 3-5 examples of what good output looks like, but no existing eval set, and wants help designing one before building any tooling around it. Inputs: the task description and the handful of pasted examples. Output: a recommended eval-set structure (how many examples, what scoring method fits the task type — exact match vs. rubric vs. LLM-judge — and what edge cases are missing from the user's sample) — a one-time design review, separate from actually running the generator or storing score history.

## MVP Sketch
A Python CLI (`personalbench add`, `personalbench run`): `add` takes a prompt + reference answer or rubric and stores it in a local SQLite file; `run` detects installed Ollama models, runs each against the stored example set, scores with a simple exact-match-or-LLM-judge fallback, and prints a ranked table plus writes it to the score-history file. Experiment: have 5 r/LocalLLaMA-style users build a 10-example personal set for a real task they already do locally, run it against 3 models they have installed, and check whether the ranking matches their own prior hands-on experience with those models. 2-3 weeks, 1 person.

## Risks & Open Questions
- LLM-judge scoring for open-ended tasks inherits the same judge-calibration problems documented elsewhere in this pipeline's own eval-observability research — the tool needs an honest confidence caveat, not a false sense of rigor.
- A sufficiently motivated user could just keep doing this by hand in a spreadsheet; the tool's entire value proposition rests on the re-run/versioning/drift-tracking being meaningfully less friction than that, which needs validating with real users early.
- Candidate-model suggestion (recommending downloads that fit the detected hardware) risks scope creep into the already-populated hardware-matching-recommender space (whichllm, llmfit) — must stay strictly secondary to the personal-eval-set core.
- Ten examples may be too few to reliably rank models for some task types; the MVP experiment is explicitly designed to surface whether the sample size the target user actually has is sufficient.
