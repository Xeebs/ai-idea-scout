# Warm Swap: A Persistent Cross-Model-Swap Context Cache for Local Multi-Model Agent Sessions

- **Status**: PROPOSED
- **Date**: 2026-11-18
- **Topic**: Small & local models
- **Source**: research/2026-11-18-small-and-local-models.md · P8
- **Maturity verdict**: OPEN — GitHub and web search found no CLI or agent harness that keeps a session's working context usably warm across a model swap. Claude Code's own docs describe cache expiry on a TTL, not cross-model persistence; Morph's writeup confirms provider prompt caches are scoped per model, so switching models re-prefills the full context from scratch; vllm-mlx/arXiv work on persistent KV caches targets surviving a server restart, not a mid-session model swap. The only concrete instance is an open, unmerged NousResearch/hermes-agent pull request proposing exactly this mechanism for Hermes's local terminal backend — proposed new work, not prior art, and not yet shipped.
- **Format**: BOTH — the session-level cache manager that intercepts model calls and persists compacted state across swaps is infrastructure that must stay resident for the life of a session; a one-time "is my current local multi-model setup wasting recompute on every swap" diagnostic is a separable, one-shot judgment.
- **Data Sources**: CONNECTED — wraps the local agent harness's existing model-call boundary (an Ollama/llama.cpp-backed terminal agent loop, or a framework callback hook) to intercept every outgoing request and read back each backend's own usage/timing fields; no external data is pasted. The companion skill's only input is a pasted session trace or log showing model-swap events and per-turn token/latency numbers.

## The Gap
A NousResearch/hermes-agent pull request opened 2026-11-16 ("Prompt cache stays warm for every model, compacts once then waits for you, and never loses tool output," 3 reactions/18 comments) describes a local multi-model agent terminal backend that today re-sends and recompacts the full growing conversation at full cost on every turn and, implicitly, on every model swap — and proposes fixing it by keeping one cache warm per chat across model swaps, compacting once instead of repeatedly, and never discarding prior local tool output. Because literal KV-cache tensors are architecture- and tokenizer-specific, no two different local models can share the same raw cache — every multi-model local agent setup today either eats a full re-prefill on every swap or (more commonly) avoids swapping models mid-session entirely, a workaround that limits exactly the kind of cheap-model-for-easy-steps / capable-model-for-hard-steps architecture this digest's other local-first patterns are trying to enable.

## The Project
A session-level context manager that sits in front of a local multi-model agent harness and maintains one canonical, compacted representation of the conversation and its tool-output history — independent of which specific model is currently serving the session. On a model swap, instead of re-running the full growing transcript through the new model from scratch, the manager replays only the canonical compacted state (which was compacted once, not re-compacted per swap) and lets the new model's own provider-level cache (if any) warm from that single, stable prefix going forward, rather than from the raw, ever-growing turn history. Tool call outputs are stored once in the canonical state and referenced, never silently dropped during a swap-triggered context rebuild — the specific failure mode the source PR calls out.

Components: a canonical session-state store (the compacted transcript plus structured tool-output references, model-agnostic); a compaction trigger that fires once per genuine need rather than once per swap; a per-backend adapter that replays the canonical state into whichever model (Ollama/llama.cpp/vLLM-served) is currently active, warming that backend's own cache from a stable prefix; a usage-tracking layer that reads each backend's own timing/token fields to report what the swap-avoidance actually saved.

## Tangible Impact
**Population**: Developers running local multi-model agent setups that deliberately swap between a small/cheap model for easy steps and a larger/more capable local model for hard steps within one chat session — the same local-first, cost-conscious population behind this digest's confidence-escalation router pattern and r/LocalLLaMA's 680k+ members, specifically the subset using a terminal-style local agent harness (Hermes-style, Ollama-backed) rather than a single fixed model per session.
**Mechanism**: Removes the real cost of model-swapping mid-session — today either a full re-prefill of the growing transcript on every swap, or avoiding swaps altogether and losing the cost/capability benefit of picking the right model per step — by keeping one compacted, model-agnostic session state that only needs to be rebuilt once, not once per swap, and by guaranteeing tool output survives the rebuild.
**Measure**: (1) tokens reprocessed per model swap, measured against each backend's own usage fields, compared to a stock no-cache-manager baseline running the same multi-swap session; (2) wall-clock latency added or saved per swap versus the same baseline; (3) rate of tool-output loss across model swaps in a test session (target: zero, versus the source PR's documented failure mode where it's currently lost).

## Why Now
Local multi-model agent harnesses that deliberately swap models mid-session for cost/capability tradeoffs are new enough to still be proposed as unmerged work on a single project (the 2026-11-16 Hermes PR) rather than an established pattern — the underlying local inference APIs (Ollama, llama.cpp server) are mature enough to build this on today, but nobody has shipped the model-agnostic session layer that makes mid-session swapping cheap instead of punitive.

## Skill Angle
Trigger: a developer has a local multi-model agent setup already swapping models mid-session and wants to know whether that swapping is quietly costing them full re-prefills before building any caching infrastructure. Inputs: a pasted session trace or log showing model-swap events alongside per-turn token counts/latency from their harness. Output: an estimate of tokens/time wasted per swap in that session and whether a canonical-state cache manager would meaningfully help, given the session's actual swap frequency and transcript length — a one-time diagnostic, separate from deploying the actual session manager.

## MVP Sketch
A Python middleware wrapping an Ollama-backed terminal agent loop (modeled on the Hermes PR's own backend): maintain a single compacted session-state object, intercept each model call to detect a swap, and on swap replay only the canonical state into the new model instead of the raw growing history. Experiment: run a fixed 20-turn task with 3 deliberate model swaps (cheap model → capable model → cheap model) once through a stock harness and once through the wrapper, and compare total tokens reprocessed and per-turn latency using each backend's own reported usage fields. 2-3 weeks, 1 person.

## Risks & Open Questions
- If the source NousResearch/hermes-agent PR merges during development, the fastest path to impact may be contributing the canonical-state pattern upstream rather than building a separate wrapper — worth re-checking the PR's status before committing past the MVP.
- Compacting "once" risks the same information-loss failure mode as any lossy compaction step; the canonical state needs to preserve enough fidelity that a swapped-in model doesn't visibly lose context the raw transcript would have retained.
- Different local models have different context-window limits and chat-template quirks; replaying one canonical state into an arbitrary new backend needs per-architecture adapters, not a single universal serializer, which could slow coverage growth.
- The actual savings depend heavily on how often a given workflow swaps models and how long the transcript has grown by that point — short sessions or rare swaps may see negligible benefit, narrowing the addressable use case.
