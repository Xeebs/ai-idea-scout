# Co-Maker: An LLM-Guided DIY Assistive-Tech Design Assistant for Disabled Makers

- **Status**: PROPOSED
- **Date**: 2026-11-13
- **Topic**: Applied AI for underserved domains
- **Source**: research/2026-11-13-applied-ai-for-underserved-domains.md · P4
- **Maturity verdict**: PARTIAL — a CHI 2026 paper (arXiv:2602.13874, Univ. of Wisconsin-Madison) studies LLM-assisted DIY assistive-tech co-making with blind/low-vision users as a live research problem, and r/AssistiveTechnology carries multiple first-person "I had to build/hack this myself" threads (a prototype AAC keyboard, a cheap robot prototype, a Mac Head Pointer setup guide), but no reusable, maintained tool surfaced — only single-author GitHub projects (a 3-star Gemini+spatial-audio navigation tool, an ESP32 blog project, a Raspberry Pi/ONNX student project) and academic research, none productized.
- **Format**: BOTH
- **Data Sources**: MANUAL — the user describes their need in plain text: the specific physical/sensory constraint, relevant abilities/limits (grip strength, range of motion, vision), assistive devices already in use, and the tools/materials/budget actually on hand (3D printer, soldering iron, cardboard and tape, smartphone). No connector exists or is planned — the input is inherently a freeform personal/situational description, not data pullable from any API.

## The Gap
Multiple independent posters in r/AssistiveTechnology this month describe building or hacking their own assistive device or software because commercial options were "over-engineered plastic trash," generic, or didn't fit a specific need — a prototype AAC keyboard built after teacher/OT feedback, a cheap robot prototype for people with disabilities, a quadriplegic cerebral-palsy user documenting a webcam head-tracking setup because off-the-shelf alternatives weren't accessible to them. A CHI 2026 paper independently confirms this is an active, unsolved research area for LLM-assisted co-making with disabled users specifically — meaning the recurring "I built it myself" pattern isn't a one-off; it's the default path, with no shared tool making that path easier or more reliable.

## The Project
A guided design assistant for disabled people, caregivers, and OTs with no engineering background, who have a specific physical/sensory constraint and a specific unmet need. The user describes the need, their relevant abilities/constraints (grip strength, range of motion, vision, available assistive devices already in use), and what tools/materials/budget they realistically have access to (a 3D printer, a soldering iron, cardboard and tape, a smartphone). The assistant asks targeted follow-up questions, then produces a concrete, buildable spec: a parts/materials list with approximate cost, step-by-step assembly instructions, any 3D-print-ready file description or simple code (e.g., an ESP32/Arduino sketch) needed, and — critically — safety caveats specific to the user's stated condition (e.g., pinch points for someone with limited sensation). A companion community library lets other users with a similar need and similar constraints search past designs instead of starting from zero, closing the loop the CHI paper identifies as missing: individual co-making sessions that never accumulate into shared knowledge.

## Tangible Impact
**Population**: People with disabilities (and their caregivers/OTs) who build or modify their own assistive devices because commercial options don't fit — the WHO/UNICEF estimate cited in this cycle's digest research puts 2.5 billion people worldwide needing an assistive product, with roughly 1 billion currently denied access to one, a gap driven partly by cost and partly by poor fit to individual needs, which is exactly the population self-selecting into r/AssistiveTechnology's DIY threads.
**Mechanism**: Today, a disabled person or caregiver with an idea but no engineering background either gives up, pays for a generic product that doesn't fit, or spends weeks of trial-and-error research to self-teach enough to build something. A guided assistant collapses that research time into a single structured conversation and a concrete, safety-checked spec, and a shared library means the second person with the same need starts from a validated design instead of from zero.
**Measure**: (1) time from "I have this need" to "I have a buildable spec," self-reported by pilot users, versus their own estimate of how long solo research would have taken; (2) rate at which generated specs are actually built and reported working (via a simple built-it/works-for-me confirmation in the library); (3) number of community-library reuses per design — the signal that knowledge is actually accumulating instead of every maker starting over.

## Why Now
The CHI 2026 paper studying exactly this pattern, and the cluster of independent DIY-build threads landing in the same 30-day window, confirm this is live, present-tense demand with no shared tool yet — LLMs are now good enough at structured, constraint-aware technical drafting (parts lists, step-by-step instructions, basic embedded code) to do the bulk of this work today, with no model-capability wait required.

## Skill Angle
A Claude Code skill version: given a user's pasted description of their need, physical/sensory constraints, and available tools/materials/budget, the skill runs a structured intake (asking 3-5 targeted clarifying questions if key details are missing) and returns a build spec — parts list with approximate cost, assembly steps, any needed code/print-file description, and condition-specific safety caveats. This is the one-shot design-drafting task a maker or OT runs per project — the project is the persistent, searchable community library of past designs and the growing matching logic that surfaces similar past solutions. The skill is useful standalone even before any library exists.

## MVP Sketch
Scope to one device category with low build complexity and clear safety bounds (e.g., adaptive grips/mounts and simple switch-access input devices, not powered mobility or anything load-bearing on a person). Stack: a structured-intake prompt flow, a spec-generation step grounded in a small curated reference set of known-safe materials/techniques (to avoid hallucinating unsafe suggestions), and a lightweight shared library (a searchable database of past need-descriptions → specs → outcome reports). The validating experiment: run the intake-to-spec flow with 5-10 real r/AssistiveTechnology-style requests (anonymized, with consent) and have an OT or accessibility-tech practitioner rate each spec's safety and buildability.

## Risks & Open Questions
- Safety is the central risk: a bad suggestion for someone with limited sensation, cognition, or motor control could cause real harm — the MVP must scope tightly away from anything load-bearing, electrical-shock-risk, or ingestible/wearable-near-airway, and should require an explicit "this is not medical/engineering advice, have a professional review before building" gate.
- The CHI 2026 paper's own findings on where LLM co-making succeeds/fails with blind/low-vision users should be read closely before building — it may already identify failure modes (e.g., spatial reasoning gaps) this project needs to design around rather than discover independently.
- A community library needs real moderation/vetting or it risks becoming a liability vector (unvetted unsafe designs spreading); this is a cost that scales with adoption and needs a plan from day one, not an afterthought.
- Risk that existing maker communities (Thingiverse's assistive-tech tag, Makers Making Change) already serve this need well enough for simple cases — worth checking whether the gap is really "no design help exists" or specifically "no LLM-guided constraint-aware design help exists."
