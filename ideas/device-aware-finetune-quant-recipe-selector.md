# Fit Tune: A Device-Aware Fine-Tuning Method and Quantization Recipe Selector

- **Status**: EXPLORING (promoted 2026-11-18 cycle 148: evidence density — ≥2 independent threads within the digest, the 2026 MobiUK paper's healthcare-fraud validation and the separate late-2026 manufacturing preprint, each independently building the same device-aware fine-tune-method-plus-quantization pipeline on a different domain)
- **Date**: 2026-11-18
- **Topic**: Small & local models
- **Source**: research/2026-11-18-small-and-local-models.md · P7
- **Maturity verdict**: OPEN — web search found only narrow, hardware-vendor-specific quantization-only autosearch tools (AMD Quark Auto-Search, scoped to one vendor's precision/calibration search with no fine-tuning-method selection; ESP-DL AutoQuant, scoped to Espressif's ESP32 chips, quantization only). The one paper combining both decisions (HAQA, arXiv 2601.03484) states its code is not yet released. Two academic papers (a 2026 MobiUK paper, a late-2026 manufacturing preprint) each validate a device-aware fine-tuning-method-plus-quantization pipeline on one narrow dataset/domain, but neither is a general-purpose tool. No open tool that takes "my device + my task" and outputs both decisions together was found.
- **Format**: BOTH — the actual recipe-selection pipeline (profiling a device, running small comparative probe fine-tunes, emitting a validated recipe) is a tool a team runs and re-uses across projects; a one-time "given this device and task, what should I try first" recommendation without running anything is a separable advisory judgment.
- **Data Sources**: CONNECTED (device profile) + MANUAL (task/dataset). Device profiling is CONNECTED and needs no new connector: local hardware introspection (`nvidia-smi`/`rocm-smi`/platform memory APIs, the same mature mechanism comparable tools already use) plus the target base model's config pulled from the Hugging Face Hub API (mature, public). The task side is MANUAL — the user supplies a small representative sample of their actual fine-tuning dataset (10-100 rows, pasted or uploaded as CSV/JSONL) and a one-line task description, since no general connector can infer a team's specific fine-tuning objective.

## The Gap
A 2026 MobiUK paper describes exactly this as new, validated work: "a device-aware pipeline that uses a cloud teacher to generate fine-tuning data, then picks a fine-tuning method and quantization based on the target hardware," tested on a healthcare fraud dataset; a separate late-2026 preprint does the equivalent for on-premise CPU inference in manufacturing. Both prove the approach works on one domain each, but neither ships as a tool anyone outside the paper's own team can run. Today, a team deciding between full fine-tuning, LoRA, or QLoRA, and what quantization level to target, does so by guessing a combination and iterating — exactly the manual trial-and-error the papers' own device-aware pipelines were built to replace, just not released as something reusable.

## The Project
A CLI/library that profiles a target device (VRAM/RAM, compute class, whether it's a training-capable GPU or an inference-only edge target) and a user-supplied task sample, then runs a small battery of cheap comparative probes — short LoRA vs. QLoRA vs. (if the device allows) full-fine-tune training runs on a tiny slice of the user's data, each at 1-2 candidate quantization levels — and reports which method-plus-quantization combination actually fits the device's memory budget and produces the best eval score on a held-out slice of the user's own examples, instead of asking the user to guess and discover the OOM or the accuracy cliff themselves. The novel piece is running the decision as a measured probe rather than a static lookup table, so it adapts to the user's actual task difficulty, not just the device's raw specs.

Components: a device profiler (VRAM/RAM/compute-class detection); a probe-run orchestrator that trains tiny slices under each candidate method/quantization combination and times/measures memory headroom; a held-out eval scorer against the user's own sample; a recipe report (recommended method, quantization level, estimated full-run time and memory headroom) with the raw probe results so the recommendation is auditable, not a black box.

## Tangible Impact
**Population**: Small ML teams and solo developers fine-tuning open-weight models (Llama/Qwen/Gemma-class, 1B-13B) for a narrow task who have one specific target device in mind — a single consumer GPU, a specific cloud instance type, or an on-premise edge box — and today arrive at a working method/quantization combination only after at least one failed (OOM or accuracy-cliff) attempt, the exact friction both cited papers set out to remove in their own narrow domains.
**Mechanism**: Converts "try full fine-tune, hit OOM, try LoRA, hit an accuracy cliff at 4-bit, try QLoRA at 8-bit, finally works" into a single automated probe pass that surfaces the same answer in minutes instead of across several failed multi-hour training attempts, because the tool runs the comparison on tiny data slices before committing to a full run.
**Measure**: (1) number of failed full-scale training attempts (OOM or below-threshold eval score) avoided per project versus a team's own prior manual-guess baseline; (2) wall-clock time from "device + task description" to a validated recipe recommendation, target under 30 minutes on commodity hardware; (3) eval-score delta between the tool's recommended combination and whatever combination the team would have tried first by guessing, measured on the user's own held-out examples.

## Why Now
QLoRA and LoRA are now cheap enough on consumer hardware that running several short comparative probes instead of one long guessed training run is genuinely affordable, and two independent 2026 academic papers just proved the joint method-plus-quantization decision is worth automating on real domains — but neither released the tooling, leaving the general-purpose version unbuilt despite the underlying technique being validated.

## Skill Angle
Trigger: a developer has a target device and a described fine-tuning task but hasn't started any training run, and wants a starting-point recommendation before spending GPU time. Inputs: a device description (GPU model/VRAM or cloud instance type) and the task description plus a handful of pasted example rows. Output: a recommended starting method (full/LoRA/QLoRA) and quantization level with the reasoning (expected memory footprint, known accuracy tradeoffs for that combination at that model size) — a one-time advisory judgment, separate from actually running the probe battery or producing a validated recipe.

## MVP Sketch
A Python CLI (`fittune probe --model <hf-id> --device auto --data examples.jsonl`): detect VRAM via `nvidia-smi`, run 3 short probe trainings (LoRA-fp16, QLoRA-4bit, QLoRA-8bit) on a 200-example slice of the user's data for a fixed small number of steps, score each against a held-out 20% split, and print a ranked recommendation with memory headroom for each. Experiment: run against one real narrow fine-tuning task (e.g. a support-ticket classification dataset) across two device profiles (an 8GB consumer card and a 24GB card) and confirm the tool's top recommendation for each device avoids the OOM/accuracy-cliff failure a naive first guess would hit. 2-4 weeks, 1-2 people.

## Risks & Open Questions
- Short probe runs on tiny data slices may not reliably predict full-run accuracy — the MVP experiment is explicitly designed to check whether probe-scale signal actually correlates with full-scale outcome before trusting the recommendation.
- Both source papers validate on exactly one domain each; the general-purpose tool's recipe logic may not transfer cleanly across very different task types (classification vs. generation vs. extraction) without its own broader validation.
- `vllm-project/llm-compressor` or a similar well-resourced framework could generalize into this exact space given how closely adjacent it already is to quantization tooling — worth rechecking before investing past the MVP.
- Device profiling for training (which needs more headroom than inference) is less standardized than inference-time VRAM estimation; the probe-based approach is partly a hedge against that uncertainty, but it adds real GPU-time cost to every use of the tool.
