# Watchdog: A Correctness-Anomaly Detector for Unattended Local-Model Automation Jobs

- **Status**: PROPOSED
- **Date**: 2026-11-14
- **Topic**: Small & local models
- **Source**: research/2026-11-14-small-local-models.md · P7
- **Maturity verdict**: PARTIAL — general-purpose, self-hostable LLM observability tools exist and are mature (e.g. Arize Phoenix, 10,000+ stars, OpenTelemetry-native, drift detection) and could in principle be pointed at local-model automation, but none found is purpose-built or marketed for the "cron-job-style local automation with no clean error signal" niche; the cited practitioner team evidently didn't find or adopt any such tool before abandoning local models for scheduled automation entirely.
- **Format**: BOTH — the baseline-tracking anomaly detector and alerting runtime is persistent infrastructure; a one-time audit of a specific automation job's failure modes is a separable judgment task.
- **Data Sources**: CONNECTED — wraps the scheduled job's existing local-model call (Ollama/llama.cpp output) in-process, and optionally checks the job's own downstream write target (the file, database row, or queue message the output lands in) against a structural expectation; this is in-process instrumentation of a call and a write the job already makes, not an external paste — the integration points (wrapping an SDK call, checking a write) are mature today.

## The Gap
The same practitioner write-up cited elsewhere in this digest reports that debugging time spent diagnosing local models' silent failures — wrong output with no API error — "exceeded the API savings in the first month," causing the team to abandon local models for scheduled automation and rebuild with explicit cloud routing. Their response was retreat to cloud-only, not adoption of an observability tool, strongly implying no purpose-built tool for this specific failure mode was known to them or readily available: general LLM observability platforms exist, but none is framed around *unattended* automation where no human is watching a run to notice the output looks wrong.

## The Project
A lightweight correctness-anomaly layer purpose-built for scheduled, unattended local-model jobs (content-generation pipelines, data-enrichment/ETL steps, local-first batch processing) — distinct from general observability libraries like this digest's own lightweight logging-library idea, which give a human something to browse after the fact. This project is active, not passive: it tracks a rolling baseline of each job's typical output shape (length distribution, structural/schema conformance, repetition/degeneration signatures, a cheap heuristic or second-model sanity check against the task's own success criteria) and fires an alert the moment a run deviates from that baseline, so a human finds out before a bad output propagates downstream — before a broken product description gets published, before a bad enrichment row lands in the database — instead of discovering it weeks later when something else breaks.

Components: an SDK-call wrapper capturing each run's output alongside the job's declared expected shape/schema; a rolling per-job baseline tracker (statistical, not LLM-judged, where possible); a lightweight secondary check (schema validation, a cheap classifier, or an optional cross-check call) for cases a pure statistical baseline can't catch; an alert channel (webhook/Slack/email) distinct from a dashboard a human has to remember to check.

## Tangible Impact
**Population**: Solo developers and small teams running scheduled, unattended local-model automation (cron-style content pipelines, data-enrichment jobs, local-first batch processing) with no human reviewing each run's output — the same population the cited practitioner team belongs to, who today either discover silent failures only when something downstream visibly breaks, or pre-emptively abandon local models for scheduled work entirely and eat the cloud cost, specifically because the debugging cost of silent failures outweighed the savings that justified running local in the first place.
**Mechanism**: Gives this population an automated tripwire instead of a dashboard they'd have to remember to check (or the retreat-to-cloud response the cited team actually took) — a run that silently degrades gets flagged on the run it happens, not discovered downstream, converting "we can't trust unattended local automation" into "we trust it because we'd be alerted the moment it drifts."
**Measure**: (1) time-to-detection for a known/injected silent-failure case — target within the same run or the next scheduled run, not the weeks the cited team reported; (2) reduction in downstream incidents traceable to bad local-model output, pre- vs. post-adoption on a pilot job; (3) false-alarm rate on genuinely fine but novel outputs, which determines whether teams keep the alerts on or tune them out.

## Why Now
Local models are increasingly trusted for cost-sensitive scheduled automation (per this digest's own router/cascade evidence), which means more unattended jobs are exposed to exactly this silent-failure risk; the statistical baseline-tracking and schema-validation primitives this needs are not new, but no one has packaged them specifically for the "nobody's watching this run" automation case, and the cost of not doing so (the cited team's abandonment) is now a documented, real outcome rather than a hypothetical.

## Skill Angle
Trigger: a developer has an existing scheduled local-model automation job and wants to know where it's exposed to silent failure before adding any monitoring. Inputs: a description of the job (what it produces, how often it runs, what "wrong but not an API error" has looked like for it before, if anything). Output: a recommended baseline-tracking plan — which signals to track (length, schema, repetition) and which need a secondary check rather than a pure statistic — a one-time audit, separate from running the actual watchdog.

## MVP Sketch
A Python decorator/wrapper around a scheduled job's local-model call: log each run's output length, a schema-validation pass (if the job has a declared output format), and a repetition/degeneration heuristic; maintain a rolling baseline per job and fire a webhook alert on a statistically significant deviation. Experiment: take one real scheduled local-model job, inject a handful of known silent-failure cases (truncated output, repetitive degeneration, schema violation) into its historical run log, and confirm the watchdog flags all of them with an acceptably low false-alarm rate on the job's genuine historical runs. 2–3 weeks, 1 person.

## Risks & Open Questions
- Statistical baselines need enough historical run volume to be meaningful; a low-frequency job (e.g. daily) takes weeks to build a trustworthy baseline, delaying the tool's usefulness exactly for the jobs most likely to go unwatched.
- Some silent failures are subtly *wrong* rather than *anomalous* in shape (correct-looking output that's factually incorrect) — a pure statistical/structural approach won't catch these; the secondary-check component needs to be honest about this ceiling, not oversold.
- Must stay clearly scoped against general LLM observability libraries (including this digest's own passive logging-library idea) — the differentiator is active alerting for *unattended* runs, not another dashboard; blurring the two invites building a redundant, lesser Lean Log.
- Evidence for this gap is currently one team's retrospective; worth validating that other scheduled-local-automation teams hit the same wall before investing past the MVP.
