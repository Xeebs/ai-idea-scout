But a Cloud Security Alliance piece evaluating PyRIT for agentic red-teaming and the "Awesome-Agentic-AI-Security" resource list both note this coverage stops short of *agent-specific, action-level* scenarios — tool use, memory poisoning, credential misuse, downstream real-world actions. - **Data Sources**: BOTH apply differently by half — the **project** is CONNECTED: it wraps the agent's own tool/action execution layer in a sandboxed clone of its real integrations (the same tool definitions, credential-scoping, and memory store the production agent uses, pointed at test resources) to inject adversarial scenarios against real call paths rather than a mocked API surface. No new external data source is read; the harness drives the agent's existing tool stack, but no maintained tool doing this at the action level (as opposed to the prompt level) was found. The **skill** is MANUAL: the user pastes their agent's tool/action manifest — the list of tools, what each does, and what data/credentials/real-world effect each touches.

## The Gap
The live exploit write-up against an agentic debt-collection platform (6pts, 2026-11-18) demonstrates the problem is not hypothetical: an attacker manipulated an autonomous agent's real-world transactional actions in production, after the fact. Two low-engagement tooling launches from the same window (Intrusive.ai's open-source attack simulation, 3pts; a Zero-Trust-for-agentic-AI analysis, 3pts) show the community reaching for a fix, but both are early, one-off, unevaluated. Meanwhile the mature prompt-level red-teaming tools (PyRIT, Garak, Promptfoo) are explicitly flagged by the Cloud Security Alliance as not covering agent-specific architecture risks — tool-use exploitation, memory poisoning, credential misuse, chained real-world actions — leaving a gap between "we red-team the model's text output" and "we red-team what the agent actually does when it acts."

## The Project
A simulation harness that stands up a sandboxed clone of a team's autonomous agent — same tool definitions, same memory/credential-scoping configuration, pointed at disposable test resources instead of production ones — and drives it through a library of agent-specific adversarial scenarios: a poisoned memory entry designed to bias a later decision, a tool-chaining sequence that escalates privilege across two otherwise-safe tool calls, a credential-scope test probing whether the agent can be tricked into using a broader grant than the task needs, and a scripted replay of the real "AI Repo Man"-style exploit pattern adapted to the team's own domain. Unlike prompt-level red-teaming, every scenario here is evaluated by its actual effect on the sandboxed environment (did the unauthorized action actually execute?), not by scoring the model's text output — the centerpiece is testing the agent's *actions*, not its *words*.

Components: a sandbox provisioner that clones a team's tool/credential configuration against disposable test resources; a scenario library covering memory poisoning, tool-chaining privilege escalation, and credential-scope misuse; an outcome-verification layer checking the sandbox's actual state after each scenario (not an LLM judge scoring the transcript); a pre-deployment report flagging which scenarios succeeded against the agent as configured.

## Tangible Impact
**Population**: Engineering and security teams at startups and mid-size companies shipping autonomous agents with real-world transactional authority — payments, bookings, account changes, debt collection — the same category of company implicated by both the live "AI Repo Man" debt-collection exploit and United Airlines' decision to ban agent-initiated bookings outright rather than trust any accountability layer. As agent-payment protocols (Google's AP2, Visa's Trusted Agent Protocol, Mastercard Agent Pay) roll out through 2026, the population of companies authorizing agents to transact in the real world is growing fast from a small base — plausibly thousands of engineering teams within the next year, per this same digest's corroborating evidence on protocol adoption.
**Mechanism**: Today a team ships an autonomous agent with real-world action authority, red-teams its prompts with PyRIT or Garak if anything, and discovers architecture-specific exploits (memory poisoning, chained privilege escalation, credential misuse) only after an incident like the AI Repo Man case — or avoids the risk entirely by banning agent access outright, as United did. A pre-deployment harness that actually executes agent-specific attack scenarios against a sandboxed clone surfaces those exploits before launch, turning "we hope our agent's actions are safe" into a measured, pre-deployment pass/fail report a team can act on before anything real is at stake.
**Measure**: (1) Number of agent-specific scenarios (memory poisoning, tool-chaining escalation, credential misuse) that succeed against a team's sandboxed agent pre-launch, versus the number of comparable incidents that previously surfaced only in production. (2) Time from a new exploit class being publicly disclosed (like the AI Repo Man pattern) to that scenario being added to the harness's library and re-run against existing deployments. (3) Reduction in post-launch security incidents tied to agent action/tool misuse, measured on pilot teams before vs. after adoption.

## Why Now
The live, named exploit against a production agentic platform landed inside this cycle's 30-day window, giving this project a concrete, adaptable attack pattern to build the scenario library's first entry around, while the maturity of prompt-level red-teaming tools (PyRIT, Garak) means the generic text-attack problem is solved enough that differentiating at the action/architecture level — rather than competing head-on with those tools — is both necessary and newly well-defined, per the Cloud Security Alliance's explicit naming of the coverage gap.

## Skill Angle
Given a pasted tool/action manifest (each tool's name, what it does, and what data/credentials/real-world effect it touches), draft a set of agent-specific adversarial test scenarios — a plausible memory-poisoning payload targeting this agent's decision points, a tool-chaining sequence that could escalate privilege across two of the listed tools, and a credential-misuse probe tailored to the listed grants — for manual review and execution before a full sandboxed harness exists or is adopted.

## MVP Sketch
3–4 weeks, 1–2 people: build a sandbox provisioner for one common agent framework (a Claude Agent SDK or LangGraph tool-calling loop) that clones a test agent's tool configuration against disposable mock resources (a sandboxed payment/booking API stub, a disposable memory store), implement the memory-poisoning and tool-chaining-escalation scenario types first, and verify outcomes by checking sandbox state directly rather than scoring the transcript. Experiment: adapt the public "AI Repo Man" exploit pattern into a scenario against a toy debt-collection-style test agent and confirm the harness actually catches it pre-deployment — if it doesn't catch the one exploit pattern already proven to work in production, the harness isn't ready for anything else.

## Risks & Open Questions
- Building a faithful sandboxed clone of a team's real tool/credential configuration is itself nontrivial — if the sandbox diverges meaningfully from production (different auth flow, stubbed side effects that don't match real failure modes), a "pass" in the harness may not transfer to real safety.
- PyRIT, Garak, or a security vendor could extend their existing prompt-level tooling to cover agent-action scenarios directly, narrowing this project's differentiation to the sandbox-provisioning and outcome-verification layer rather than the scenario library itself.
- The scenario library's coverage is only as good as the exploit classes known at build time; like any red-team tool, it risks chasing yesterday's attack pattern (AI Repo Man-style) while missing the next novel one.
- Thin evidence: the two tooling launches (Intrusive.ai, the Zero-Trust analysis) are each 3-point posts — the stronger half of the case is the live exploit and the CSA/Awesome-Agentic-AI-Security coverage-gap analysis, not community demand for a tool yet, so a few practitioner interviews should precede a heavy build.
- Outcome verification by checking sandbox state (rather than an LLM judge) is more reliable but harder to generalize across wildly different tool stacks — the verification layer may need meaningful custom work per team rather than being fully turnkey.
