# Split Verdict: A Generalized Claim/Verdict Separation-of-Duties Middleware for Agent Tool Use

- **Status**: PROPOSED
- **Date**: 2026-11-12
- **Topic**: Tool use & MCP ecosystem
- **Source**: research/2026-11-12-tool-use-mcp-ecosystem-2.md · P5
- **Maturity verdict**: PARTIAL — framework-level guidance calls for this (NIST AI RMF, OWASP Agentic AI Top 10 both cite separation of duties as a requirement) and scattered narrow MCP marketplace listings exist (`verify_claim` / `review_verdict` / `agent-gate` tools on glama.ai, a "dsh-duty-separation-proof" post-hoc evidence server), but these are unverified, single-purpose marketplace entries, not an adopted reusable pattern. The one concrete shipped example (nomosguard, r/modelcontextprotocol, 2026-11-12, v0.7.11, stdlib-only) is explicitly scoped to one incident-response threat model ("an agent allowed to both gather evidence and declare the incident resolved"), built by its own author specifically because nothing generalized already existed.
- **Format**: BOTH — the enforcement middleware is a persistent interceptor on an agent's tool-call stream; auditing a described agent workflow for claim/verdict role-collapse risk is a separable one-shot task.
- **Data Sources**: CONNECTED — the middleware intercepts the live tool-call request/response stream of whatever agent framework or MCP client it's wired into (MCP's standard tool-call interception point, which already exists as a stable extension point in every major MCP client/SDK today). No manual paste; it reads the actual calls as they happen.

## The Gap
r/modelcontextprotocol, "nomosguard: five MCP tools that keep the agent's claims and the security verdict in separate hands (stdlib-only)" (2026-11-12): "The threat it is built around is narrow: an agent allowed to both gather incident evidence and declare the incident resolved. If one model does both, the security boundary is its judgment. nomosguard splits the roles." The poster built this themselves because nothing generalized already existed — a single, just-released, narrow point solution for one threat model, not a reusable pattern applicable to the many other agent workflows with the identical risk shape (code-review-and-merge bots, QA agents that test and then self-certify, compliance-checking agents).

## The Project
A framework-agnostic MCP middleware that enforces claim/verdict separation as a structural property of the tool-call graph, not a convention teams have to remember. Tools are tagged, once, as CLAIM-producing (evidence-gathering, action-execution) or VERDICT-producing (judging an outcome's success/safety/resolution) via a declarative manifest. At runtime, the middleware tracks which agent/model instance produced which claims in a chain, and refuses — or forcibly escalates to a separate model instance, a different agent, or a human reviewer — any attempt by the same instance that produced a claim to also issue the verdict on that claim. This generalizes nomosguard's one hard-coded incident-response rule into a reusable library any team can apply to their own tool/workflow shape.

Components: the claim/verdict tagging manifest format, a runtime interceptor that tracks claim provenance per chain and enforces the separation rule, a pluggable escalation target (a second model call, a different agent, or a human-approval queue), and a violation log recording every attempted self-certification the middleware blocked.

## Tangible Impact
**Population**: Engineering teams deploying autonomous agents that both perform an action/investigation and would otherwise self-certify its outcome — SRE/on-call teams adopting agentic incident response, teams running AI code-review-and-merge bots, and QA agents that run tests and then report pass/fail on their own work. SRE teams specifically are a fast-growing subset of this cohort in 2026 as agentic on-call tooling moves from pilot to production, the exact context nomosguard's single evidence source comes from.
**Mechanism**: Without enforced separation, a single agent's self-report collapses the security/correctness boundary to its own judgment — the same action that gathers evidence can also unilaterally declare success, with no structural check. Routing the verdict through a separate, non-colluding instance means a flawed or manipulated claim still has to pass an independent judgment before anything is marked resolved/merged/passed, converting a trust-the-same-model risk into an actually-checked one.
**Measure**: (1) Number of claim/verdict role-collapse risks identified when auditing a team's existing agent architecture (the skill-angle output) before any runtime change. (2) In production: rate of verdicts the middleware forced to escalation versus self-certification, and the outcome-accuracy delta on those escalated cases (false "resolved"/"passed"/"merged" rate) compared to a pre-adoption baseline. (3) Reproduction of nomosguard's own narrow incident-response case as a conformance test, confirming the generalized library doesn't regress the one validated real-world example it's built on.

## Why Now
Agentic workflows are moving into exactly the shape this risk targets — on-call remediation, autonomous code review and merge, self-testing QA agents — fast enough that a solo builder shipped a narrow, hard-coded version of the fix for one threat model on the same day as this digest, with both NIST and OWASP's own agentic-AI guidance already naming separation of duties as a requirement nobody has a reusable implementation of yet.

## Skill Angle
Given a description of an agent's workflow (the tools it calls, what each tool does, and who/what currently judges the outcome), identify every point where the same agent instance both produces a claim and issues the verdict on it, and recommend which tool calls should be re-tagged CLAIM vs. VERDICT and where an escalation boundary should be inserted — the same analysis the middleware enforces at runtime, done once by hand to decide whether the workflow needs it before any code changes.

## MVP Sketch
A Python middleware package implementing the MCP tool-call interceptor pattern, with a YAML claim/verdict tagging manifest, in-memory chain-provenance tracking (sufficient for a single-session pilot; durable storage is a stretch goal), and one escalation target (a second, independently-prompted model call with no access to the first instance's reasoning trace). Experiment: reproduce nomosguard's exact incident-response scenario (an agent that gathers evidence and would normally self-declare resolution) through the generalized middleware, and confirm the same self-certification nomosguard blocks is blocked here too, then add a second, unrelated scenario (a code-review-and-merge bot) to prove generalization. 3–4 weeks for 1–2 people.

## Risks & Open Questions
- "Separate model instance" doesn't guarantee independence if both instances share the same underlying model and similar biases — true separation of duties may require a genuinely different model/vendor or a human in the loop for high-stakes verdicts, raising cost and latency.
- Tagging tools CLAIM vs. VERDICT correctly is itself a judgment call that could be gamed or misconfigured by the team deploying it, silently defeating the protection.
- If MCP's own spec or a major agent framework ships a built-in role-separation primitive, a standalone middleware's differentiation narrows to cross-framework portability and the reference tagging manifest alone.
- Validated against exactly one real-world case (nomosguard's incident-response scenario) in the source evidence — generalization claims need testing against more domains before the "reusable" framing is proven, not assumed.
