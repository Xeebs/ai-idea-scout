- **Format**: BOTH — a one-shot audit/split of an existing rules file is a judgment task a skill can do; keeping the volatile half in sync automatically as the repo changes needs a persistent hook/CI job.
- **Data Sources**: Skill mode is MANUAL — the user pastes their current `AGENTS.md`/`CLAUDE.md` content verbatim. Project mode is CONNECTED — the installed CLI/git-hook reads the target repo's own rules file and live repo-state signals (recent git log, test-runner exit status, lint output, open-TODO markers) directly from the local filesystem and subprocess calls. No external API or third-party connector is needed or exists to build here; this is plain local file/process access, already fully available today — the gap is the splitting logic and regeneration safety, not data access.

## The Gap
Two independent r/ContextEngineering threads in the same week describe hitting "the exact same context rot wall": one team split their file into a hand-named `TOKENME.txt` once `AGENTS.md` passed ~150 lines of accumulated fixes; another reports "every request pastes your whole AGENTS.md into the prompt... it hit a size where the agent started [mis-handling] it." Both built one-off, repo-specific conventions rather than citing any shared tool. The gap-analyst's search confirmed only scattered blog posts describe the same manual split (stable rules vs. a separately-regenerated state file) — no named standard or packaged tool exists for which fields belong in each half or how the volatile half gets regenerated without drifting out of sync or silently corrupting.

## The Project
A CLI (and companion skill) that parses an existing monolithic `AGENTS.md`/`CLAUDE.md`, classifies each line as **stable** (build flags, test commands, lint boundaries, trade-off priorities — things that rarely change) or **volatile** (dated TODOs, "currently working on," file-count/status snapshots, anything that was true once and is now stale), and splits the file into a small sacred `CLAUDE.md` plus a separate `STATE.md` that the tool regenerates on a schedule or git hook from live repo signals instead of manual edits. The regeneration logic — never letting a human-authored stable rule silently get swept into the auto-regenerated file, and never letting the regenerated file grow unboundedly either — is the centerpiece; splitting once is easy, keeping the split clean over months of commits is the actual unsolved part.

Components: a classifier (rule-shaped heuristics + a cheap-model pass for ambiguous lines); a `STATE.md` regenerator (pulls from git log, test/lint exit codes, open-PR/TODO scanners); a drift guard that diffs each regeneration and flags anything that looks like it silently absorbed a stable rule; a pre-commit hook wiring it into normal repo workflow.

## Tangible Impact
**Population**: Developers and small teams running AI coding agents (Claude Code, Codex, Cursor) against repos whose rules file has grown past the point of being hand-maintainable — concretely, the kind of team both evidenced Reddit threads describe: running local multi-agent pipelines where every fix gets appended and nothing is removed until the agent starts mis-following its own rules. This is a large and growing population given how widely `AGENTS.md`/`CLAUDE.md` conventions have been adopted across Claude Code, Codex, and Cursor users in 2026.
**Mechanism**: Today, teams either let the rules file grow until the agent starts "butchering" parts of it, or hand-roll a bespoke split (as both evidenced posters did) that nobody else can reuse and that drifts out of sync as soon as someone forgets to update it manually. A tool that performs the split once and then keeps the volatile half fresh automatically removes both the token tax of re-pasting a bloated file every request and the silent-misfollowing failure mode caused by stale or oversized rules.
**Measure**: (1) Rules-file token count before vs. after split, and the resulting per-request token-cost reduction. (2) Agent rule-adherence rate on a labeled set of "does the agent follow its own stated constraints" test prompts, before vs. after the split. (3) Drift incidents — cases where the regenerated `STATE.md` silently absorbed or lost a stable rule — caught by the guard vs. missed, on a multi-week simulated commit history.

## Why Now
This is the fourth research pass on this topic and the pattern keeps recurring independently as repos and their rules files age through 2026's heavy adoption of `AGENTS.md`/`CLAUDE.md` conventions; the only existing responses are hand-rolled, repo-specific hacks from the exact teams hitting the wall, confirming no one has packaged the regeneration-safety piece yet.

## Skill Angle
Given a pasted `AGENTS.md`/`CLAUDE.md` file, classify each line as stable or volatile, propose the split (a trimmed stable file plus a draft `STATE.md`), and flag any line that's ambiguous with a one-line rationale for a human to confirm. Useful today as a one-time cleanup pass before anyone commits to wiring in the auto-regeneration hook.

## MVP Sketch
A Python CLI: `split-rules AGENTS.md` runs the stable/volatile classifier and writes `CLAUDE.md` + `STATE.md`; a second command `regenerate-state` re-derives `STATE.md` from git log + test/lint signals and diffs against the previous version, flagging anything that looks like it swallowed a stable-rule line. Experiment: take one of the two evidenced repos' real `AGENTS.md` history (or a comparable large real-world file), run the split, simulate 2 weeks of commits, and measure whether the regenerated `STATE.md` stays clean (no absorbed stable rules) and whether per-request token count actually drops. 2–3 weeks for 1–2 people.

## Risks & Open Questions
- Anthropic, OpenAI, or Cursor could ship a native stable/volatile convention directly into their agent tooling, which would be the most direct competitive risk given they own the rules-file format itself.
- The stable-vs-volatile classification is itself a judgment call; a bad split could misfile a genuinely stable rule into the auto-regenerated (and therefore overwritable) file, making things worse than the status quo.
- Regeneration logic needs to generalize across very different repo types (a monorepo's git-log signal looks nothing like a small library's) without per-repo hand-tuning, or the "auto" part breaks down into manual maintenance anyway.
- It's unproven whether rule-adherence failures are actually caused by file size/staleness specifically, versus other factors (model behavior drift, ambiguous phrasing) — the MVP experiment is partly testing that attribution.
