# Trace+Check: A Minimal Combined Observability-and-Eval Library for LLM-Backed Features

- **Status**: EXPLORING
- **Date**: 2026-11-18
- **Topic**: LLM evaluation & observability
- **Source**: research/2026-11-18-llm-evaluation-observability.md · P8
- **Maturity verdict**: PARTIAL — WebSearch confirmed a crowded vendor list (Langfuse, Arize Phoenix, LangSmith, DeepEval, OpenLLMetry, Helicone, Portkey, MLflow) but also confirmed real friction: Langfuse's self-host stack needs web+worker containers, Postgres, ClickHouse, and Redis/S3 — heavyweight for a team that wants one embeddable piece. The closest existing path is pairing two separate libraries (OpenLLMetry for tracing, DeepEval for eval metrics) — no single lightweight, combined observability+eval-in-one library was found, consistent with why both a tiny OSS repo and a large company (PostHog) independently chose to hand-build their own glue instead.
- **Format**: BOTH — the library and its local storage/UI are persistent infrastructure a feature team runs continuously; a one-time build-vs-buy-vs-pair assessment for a specific team is a separable judgment task.
- **Data Sources**: CONNECTED — wraps the team's own LLM API calls (OpenAI/Anthropic/etc.) directly in-process to capture traces, the same mature, trivial integration point every observability SDK uses today; eval assertions run against the same locally-stored traces and a team-supplied set of expected outputs/golden examples, so there is no external platform dependency to connect to — this library is itself the lightweight combined platform.

## The Gap
GitHub PR "feat: Observability and Evaluation" on a small open-source project (maheshnallada/ConversenseAI#2) and PostHog's own multi-PR "aio" (AI observability + evaluation-run) build (#124131, #129079, #129083) show teams at opposite ends of scale — a tiny hobby repo and a large analytics company — independently hand-rolling the same combined observability-and-eval feature from scratch within the same 30-day window, despite a long list of named vendors in this exact category. WebSearch confirmed why: the lightest existing path is pairing two separate libraries, not adopting one, and the fully combined options (Langfuse, LangSmith) require a heavier self-host footprint than either of these two teams apparently wanted.

## The Project
A single importable library — Python first — that ships both halves from one dependency: (a) an SDK-call wrapper capturing prompt/response/latency/cost as spans, the tracing half; and (b) inline eval-assertion primitives — deterministic expected-output matchers, golden-set regression checks, and an optional single LLM-judge scoring call — that run against those same captured traces and surface a pass/fail verdict right next to the trace, the eval half. One local store, one local UI, one install, instead of wiring OpenLLMetry and DeepEval together or standing up Langfuse's multi-container stack for a feature that's one piece of a larger product.

Components: SDK-call wrapper; local storage (SQLite default, Postgres optional); assertion/scoring primitives; a golden-set regression runner; a single local web UI showing traces and eval verdicts together; an explicit scope contract distinguishing this from both full enterprise platforms and from this ledger's own `minimal-self-hosted-llm-observability-library.md` ("Lean Log"), which deliberately covers tracing only — this project is the combined superset for teams that need both from day one.

## Tangible Impact
**Population**: engineering teams building an LLM-backed feature as one piece of a larger existing product — spanning a solo OSS maintainer (the cited maheshnallada/ConversenseAI PR) up to a sub-team inside a large, well-resourced company (PostHog's own multi-PR "aio" build) — who need both tracing and pass/fail eval checks for that one feature but don't want to onboard a dedicated vendor or a multi-container self-host stack just to get them. Both ends of that scale spectrum independently chose to hand-build this within the same 30-day window, which is the direct evidence this population exists today.
**Mechanism**: replaces either from-scratch glue (what both cited examples built) or a two-library integration project (OpenLLMetry + DeepEval) with one install that does both, collapsing "do I need tracing" and "do I need eval" into a single setup step — so a feature team ships observability and regression protection together instead of shipping tracing now and eval "later," which a LangChain survey cited elsewhere in this same digest shows mostly never happens (89% have tracing instrumented, only 52%/37% run offline/online evals).
**Measure**: (1) % of a pilot cohort that has at least one running eval-assertion check within their first week of adoption (vs. the LangChain survey's 52%/37% baseline); (2) time from install to viewing a combined trace+eval-verdict for the first time; (3) number of observed cases of a team replacing a hand-rolled "Observability and Evaluation"-style PR with adoption of this library instead of writing new glue.

## Why Now
The same 30-day window produced two independent, differently-scaled teams hand-building this exact combination from scratch, and the component primitives (SDK wrapping, local storage, assertion-style checks) have been mature and trivial for years — nothing here waits on new model capability, only on someone packaging the combination the current vendor landscape leaves either tracing-only, eval-only, or too heavy to adopt for a single feature.

## Skill Angle
A build-vs-buy-vs-pair skill, extending Lean Log's own skill angle to include the eval half: given a pasted description of a team's current stack, whether they need pass/fail eval checks or just tracing, and their scale, the skill recommends one of four paths — this combined library, Lean Log alone, manually pairing OpenLLMetry+DeepEval, or a full platform — and, if this library fits, sketches the first one or two assertion checks to wire up. The skill is the one-shot decision aid; the project is the running library.

## MVP Sketch
2–3 weeks, 1–2 people: a Python package wrapping an OpenAI-compatible client that logs each call to local SQLite, plus a minimal assertion API (`assert_eval(trace_id, matcher_fn)`) recording pass/fail against the same store, with a Flask read-only UI showing both together. Experiment: have the maintainer of a small OSS LLM-feature repo swap a hand-rolled logging statement plus a manual before/after eyeball check for this library's wrapper and one assertion, and confirm they can see the trace and the eval verdict together without touching two separate tools.

## Risks & Open Questions
- Overlaps closely with Lean Log already in this ledger — must stay differentiated by shipping the eval-assertion half from day one, or this becomes a redundant fourth attempt at the observability-only niche instead of the combined gap the digest actually names.
- "Minimal" eval primitives may not satisfy teams that need LLM-as-judge scoring at real scale — needs a clear line (deterministic matchers plus one optional judge call) rather than growing into a second DeepEval.
- PostHog may simply keep extending its own in-house "aio" feature rather than ever adopting an external library, narrowing the realistic addressable population toward smaller teams and OSS projects, not the large-company end of the cited evidence.
- Risk that OpenLLMetry or DeepEval ship native integration with each other before this exists, closing the "pairing is the current workaround" framing this idea is built on.
