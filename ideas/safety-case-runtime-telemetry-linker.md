# Living Case: A Runtime-Telemetry-Linked Safety Case Evidence Tracker

- **Status**: PROPOSED
- **Date**: 2026-11-14
- **Topic**: AI safety & guardrails in production
- **Source**: research/2026-11-14-ai-safety-and-guardrails-in-production.md · P6
- **Maturity verdict**: PARTIAL — an AAAI 2026 paper (CAF) prototypes a "living safety case" as a dynamic evidence graph wired to CI/CD pipeline data with a RAG case study auto-blocking deployments on policy violation, and Edge Case Guardian's commercial "Digital Safety Twin" links safety claims to live operational signals — but CAF is an unmaintained academic prototype with no incident-tracker integration, and Edge Case Guardian targets autonomous/defense systems, not LLM/agent production telemetry. No maintained, general-purpose tool keeps an AI safety case's claims linked to a production AI system's actual runtime monitoring/incident data.
- **Format**: BOTH
- **Data Sources**: CONNECTED — ingests a team's own existing production telemetry: incident/issue-tracker events (Jira/Linear/GitHub Issues API, all mature connectors), eval/regression-suite results from whatever CI eval pipeline the team already runs, and agent-runtime trace data (OTel spans, which most agent observability stacks already export). The safety case document itself (its claims/arguments/evidence-link structure) is a one-time upload per team — typically a structured doc or spreadsheet the team already maintains for this purpose — which the tool then keeps wired to the CONNECTED sources above going forward, rather than requiring re-paste on every update.

## The Gap
A January 2026 arXiv paper on reusable safety-case templates argues aviation/nuclear safety-case practice assumes "stable system boundaries" that generative/agentic AI lacks, and that cases should be "living documents... updated when new evidence arrives, capabilities jump, the system drifts, or post-deployment incidents are reported" — stated as a design goal, not something built. Google DeepMind's Frontier Safety Framework commits to a pre-deployment safety case (per ConductAtlas) and the UK AI Security Institute is piloting safety-case templates with frontier developers, but every source describes a template for writing the document or a process commitment to produce one *before* deployment. None describes a tool that automatically keeps a case's claims tied to the system's actual runtime data after launch — the gap the arXiv paper itself names as open.

## The Project
A tool that takes a team's structured safety case (claims, each tagged with the evidence type that's supposed to support it — e.g. "Claim: jailbreak attempts are caught before execution," evidence: guardrail-block-rate + red-team incident log) and continuously reconciles each claim against live data pulled from the team's own incident tracker, eval/regression results, and agent trace store. It flags three states per claim: **supported** (fresh matching evidence exists), **stale** (no new evidence since a configurable window), and **contradicted** (new incident or eval regression maps to a risk category the claim says is mitigated) — turning a document that's reviewed once before launch into one that visibly degrades or holds up as the system actually runs, which is the specific capability every framework found commits to in principle but none ships.

## Tangible Impact
**Population**: AI safety/governance teams at organizations adopting structured safety-case practice as it spreads beyond the handful of frontier labs currently piloting templates with the UK AI Security Institute — a population that's small today (safety-case practice is explicitly "exploratory, no binding requirements" per the longtermwiki.com tracker) but is the deliberate next-adopter tier once regulatory pressure or enterprise procurement starts asking for one, the same pattern SOC2 and model cards followed from frontier-only to broad adoption.
**Mechanism**: today a safety case is reviewed once pre-deployment and then effectively frozen — nobody mechanically checks it against what's actually happening in production, so a case can go stale or be silently contradicted by a real incident for months before anyone notices on the next scheduled review. This tool closes that loop automatically, turning "the case was true in March" into "the case is true as of this morning."
**Measure**: time from a disqualifying incident (e.g. a jailbreak that should have been caught per the claim) to that claim being flagged contradicted (target: same day, vs. "next scheduled case review," often 6-12 months); number of claims correctly flagged stale/contradicted on a held-out historical incident set; reduction in claims a human reviewer finds already-invalid at the next manual case review (target: near zero, since the tool should have caught it first).

## Why Now
The January 2026 arXiv paper explicitly names "living document wired to runtime telemetry" as the unmet design goal, and the AAAI 2026 CAF paper proves the core mechanism (dynamic evidence graph tied to pipeline data) is technically workable months before this digest — the pieces exist, nobody has combined incident-tracker + eval-suite + trace-store reconciliation into one maintained tool aimed at the LLM/agent production case specifically.

## Skill Angle
A companion skill takes a pasted safety case document (or its claims list) plus a pasted recent incident report or eval regression result, and flags which specific claims are now contradicted or unsupported by that evidence, drafting the specific revision language needed — a one-shot review task useful the moment a single incident happens, distinct from the project's continuously-running, multi-source reconciliation tracker.

## MVP Sketch
A CLI tool: given a safety case expressed as structured claims (YAML/JSON, each tagged with linked evidence-source types) plus a sample incident-tracker export and a set of eval-run results, computes per-claim status (supported/stale/contradicted). Validate against a synthetic test: inject one synthetic incident that should invalidate a specific claim and confirm the tool flags exactly that claim red, nothing else. Buildable by 1-2 people in 3-4 weeks using one incident-tracker API (GitHub Issues) and one eval format to start.

## Risks & Open Questions
- Safety-case structure isn't standardized across frameworks (UK AISI pilots, DeepMind's FSF, academic proposals all differ) — the tool needs a sufficiently generic claim/evidence schema to avoid locking into one framework's specific format.
- Mapping real incident/eval signals to the right safety-case claim may require meaningful per-team configuration, risking this becoming a bespoke integration project rather than a lightweight drop-in tool.
- Adoption depends on safety-case practice actually spreading past the current ~handful of frontier-lab pilots; if it stays frontier-only, the near-term addressable team count is genuinely small — this is the idea's biggest open risk, worth validating with a direct outreach check before building.
- Strongest case this is already solved: if CAF's academic prototype gets picked up and actively maintained as an open tool before this ships, differentiation narrows to adding incident-tracker integration (CAF's current scope is CI/CD-pipeline data only).
