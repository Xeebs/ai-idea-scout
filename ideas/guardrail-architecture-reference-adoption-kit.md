# Reference Rail: A Packaged Starter Kit for the Security-Specialized Guardrail Model Architecture

- **Status**: PROPOSED
- **Date**: 2026-11-13
- **Topic**: AI safety & guardrails in production
- **Source**: research/2026-11-13-ai-safety-guardrails-in-production.md · P9
- **Maturity verdict**: PARTIAL — Red Hat's TrustyAI Guardrails Orchestrator (built on the open-source FMS Guardrails Orchestrator project) is a concrete, working reference architecture using detector-server REST services coordinated by an orchestrator for span-aware pre/post-inference detection, and vendor blogs converge on a four-point pattern (before model, around retrieval, after model, around tool calls) — but the `LMA1980/jero-manager` issue opening an "Arch Evaluation" epic shows a team actively searching for this pattern and not finding it, and no NIST/OWASP canonical standard exists. This is a real awareness/consolidation gap, not an absence of any working implementation.
- **Format**: BOTH — a deployable reference-architecture starter kit wiring the orchestrator pattern to specific detector models is persistent runtime infrastructure; a one-time "where does your current setup fit this pattern" assessment is a separable judgment task.
- **Data Sources**: CONNECTED — the starter kit wires together already-existing, independently-hosted security-specialized model endpoints (Meta Llama Guard and Prompt Guard via Hugging Face Inference or self-hosted vLLM, IBM Granite Guardian via Hugging Face or watsonx, Azure Prompt Shield via its own API) plus the open-source FMS/TrustyAI orchestrator project itself — all mature, already-shipping resources; the kit's job is integration and packaging, not building a new connector. The companion skill's assessment mode is MANUAL — the user pastes a description (or config/code snippet) of their current guardrail call pattern.

## The Gap
`LMA1980/jero-manager` issue #31, opened 2026-11-01, is an explicit "Epic: [Arch Evaluation] Security, Guardrail, Prompt-Injection & Cyber-Defense Architectures" — a team publicly searching for how to architect dedicated security-specialized guardrail models rather than copying a settled pattern, because they evidently hadn't discovered Red Hat's existing FMS Guardrails Orchestrator or the four-point pattern (before model / around retrieval / after model / around tool calls) that several vendor blogs (digitalapplied, openlayer, Lakera docs) already converge on independently. The pattern exists; what doesn't exist is a packaged, discoverable, easy-to-adopt version of it that a team evaluating architecture would actually find before opening their own from-scratch design epic.

## The Project
A packaged reference-architecture starter kit built directly on top of (not competing with) the open-source FMS Guardrails Orchestrator, pre-wired with adapters for the specific security-specialized models teams already reach for — Llama Guard, Prompt Guard, Granite Guardian, and a pluggable slot for Azure Prompt Shield or any OpenAI-compatible detector endpoint — mapped explicitly onto the four-point pattern (pre-inference, retrieval-time, post-inference, tool-call-time). Ships as a deployable config/Docker-compose starter plus a decision questionnaire: a team answers a handful of questions about their stack (self-hosted vs. managed models, which detectors they already run, latency budget) and the kit generates the orchestrator config and detector wiring that matches, instead of the team re-deriving the architecture from first principles the way the `jero-manager` epic is doing.

Components: FMS/TrustyAI orchestrator deployment template; pre-built detector-server adapters for Llama Guard/Prompt Guard/Granite Guardian/Azure Prompt Shield; a four-point coverage mapper that flags which of the four insertion points a team's current config actually covers; a decision questionnaire that outputs a concrete starter config.

## Tangible Impact
**Population**: Engineering teams at small-to-mid-size companies building production LLM apps who don't have a dedicated AI-security engineer to do the deep research needed to find the FMS/TrustyAI pattern before defaulting to a from-scratch design — the same population visible in this digest's own evidence of five independent teams in one month each hand-building a bespoke guardrail layer rather than adopting a shared one (P1), and the `jero-manager` team itself as a direct, named instance of the gap.
**Mechanism**: Today, a team evaluating guardrail architecture either finds nothing (if their search doesn't surface Red Hat's project or the scattered vendor blog posts) and designs from scratch, or finds the FMS Guardrails Orchestrator but has to do the detector-wiring and four-point-mapping work themselves with no packaged starting point. A discoverable, pre-wired starter kit collapses that research-and-wiring phase into answering a short questionnaire and deploying a generated config, directly shortening time-to-a-defensible architecture and reducing the odds a team ships with an unknowingly incomplete pattern (e.g., covering post-inference but missing tool-call-time, the exact one-directional gap documented elsewhere in this digest as P4).
**Measure**: time from "starting an architecture evaluation" to "a working, four-point-covering guardrail deployment," measured against a baseline of teams doing it from scratch (self-reported via a pilot survey of adopting teams); percentage of the four insertion points (pre-inference, retrieval, post-inference, tool-call) actually covered by teams who adopt the kit versus a sample of existing from-scratch implementations found in the P1/P4 evidence; adoption count of the starter kit's detector-server pattern versus continued bespoke-implementation PRs on GitHub over time, as a proxy for whether the kit is actually closing the duplication problem.

## Why Now
Red Hat's FMS Guardrails Orchestrator is mature open-source infrastructure already in production use, and the four-point pattern has independently converged across multiple vendor write-ups in 2026 — the architectural knowledge exists and is stable, but nobody has packaged it as a discoverable, pre-wired starter kit, which is exactly the gap a live, dated GitHub epic (`jero-manager` #31, opened days before this digest) demonstrates in real time.

## Skill Angle
Trigger: a team has an existing guardrail setup (or a design doc/epic like `jero-manager`'s) and wants to know where it stands relative to the established four-point pattern before investing in a rebuild. Inputs: a pasted description or config/code snippet of their current guardrail call sites — what runs before the model call, around retrieval, after the model call, and around tool calls, to whatever extent each exists. Output: a coverage map naming which of the four points are covered, partially covered, or missing, mapped against the FMS/TrustyAI reference pattern and named detector models that would typically fill each gap, plus a pointer to the matching section of the starter kit if they choose to adopt it. The skill is the one-time gap assessment; the project is the deployable kit itself.

## MVP Sketch
A Docker-compose template deploying the open-source FMS Guardrails Orchestrator with three pre-built detector-server adapters (Llama Guard for pre-inference, a Granite-Guardian-based post-inference check, and a simple tool-call-argument scanner), driven by a short CLI questionnaire that picks which adapters to enable based on a team's answers. Single experiment: take 3–5 teams' described current guardrail setups (sourced from the kind of GitHub issues this digest already surfaces — EDDI, OpenPrep-AI, jero-manager) and show the questionnaire correctly identifies their actual coverage gaps against a manual expert review of the same setups. 3 weeks, 1–2 people.

## Risks & Open Questions
- Red Hat itself, or another vendor already close to the FMS project, could package this discoverability layer first, since the hard infrastructure work (the orchestrator) is already theirs.
- The core issue may be genuinely one of search-engine discoverability/marketing rather than missing software — if so, a starter kit alone won't fix the underlying awareness gap without real distribution effort (docs, GitHub presence, SEO).
- No standards-body (NIST/OWASP) canonical architecture exists yet, so the kit is betting on a vendor-converged pattern rather than an authoritative one — if OWASP's Gen AI Security Project later ships a different canonical shape, the kit would need to reconcile with it.
- The four-point mapper's accuracy depends on a team describing their setup honestly and completely; a team that doesn't know what they don't have (the exact `jero-manager` situation) may also struggle to answer the questionnaire precisely.
