# Panel Gate: A Merge-Gating and Per-Member Failure-Attribution Layer for Council-of-Agents Delivery Pipelines

- **Status**: PROPOSED
- **Date**: 2026-11-19
- **Topic**: Agentic AI & autonomous agents
- **Source**: research/2026-11-19-agentic-ai-autonomous-agents.md · P7
- **Maturity verdict**: PARTIAL — adjacent research exists (TRIAGE council-based failure-attribution, a conformal-error-attribution repo, AWS's ECHO hierarchical-attribution paper) and generic rollback/recovery guidance is common, but no shipped, evaluated framework combines a council-of-agents gating layer with explicit partial/failed-work recovery and per-member attribution. LoopTroop (three active bug-fix PRs within the digest window) is the closest thing found, and it is narrow, single-project, and still mid-development.
- **Format**: BOTH — the merge-gate and attribution runtime must stay wired into a live delivery pipeline (PROJECT-shaped); auditing an existing multi-agent delivery setup for the specific failure modes below is a separable one-shot review.
- **Data Sources**: CONNECTED (project) — reads each council member's task/PR status directly from the delivery platform the team already uses (GitHub's PR/check-run API for code-delivery councils, or the orchestration framework's own task-state API for non-code councils); GitHub's API is mature and ready to use today, while a generic cross-framework task-state adapter would need to be built as part of this project. MANUAL (skill) — the user pastes their council pipeline's current merge/recovery code or config, plus a description of a specific incident (an early merge, a silently-empty member response) for a one-off audit.

## The Gap
Three active GitHub PRs on `looptroop-ai/LoopTroop` within the digest window describe a "council of agents" delivery workflow where a panel of agents produces work that must pass a gating layer before merge — and all three are fixing the same class of bug: an AI merging a ticket's PR before review and the workflow then repeatedly rejecting completion (Fixes #277, 5react/36cmt); inconsistent recovery when external bead targets are involved (5react/34cmt); and, most tellingly, "an empty response from one council member could mark every member as having no visible output" (5react/19cmt) — a single silent member failure corrupting the attribution for the entire panel. This is visibly mid-development bug-fixing inside one project, not a stable, reusable pattern anyone else can adopt.

## The Project
A gating-and-attribution layer that sits between a council of agents and whatever merges their combined output. It enforces a single rule the LoopTroop bugs all violate in different ways: no individual council member's success or failure is ever inferred from another member's output. Each member's completion status, output, and any error is tracked independently; a merge only happens once the gate has an explicit per-member verdict for every seat on the panel (not "nothing visibly failed, so assume success"); and if a member times out, returns empty, or merges out-of-band before the gate runs, the recovery path is to roll that specific member's slot back to pending and re-dispatch it — never to silently blank out or duplicate the status of its neighbors.

Components: a per-member status ledger (pending/running/succeeded/failed/empty, keyed per council seat, never inferred cross-seat); a merge gate that blocks until every seat has a terminal verdict; an early-merge interceptor that detects and reverts out-of-band merges that bypass the gate, re-queuing the affected seat; a recovery policy for timeout/empty-response seats (retry-same-seat vs. escalate-to-human, configurable); an attribution report that names exactly which seat failed and why, instead of a panel-wide "something went wrong."

## Tangible Impact
**Population**: Engineering teams running "council of agents" delivery pipelines — multiple agents independently producing competing or complementary work (PRs, drafts, analyses) that must be gated and merged as a set — the exact shape of workflow LoopTroop's own active bug-fix PRs describe, and a pattern distinct from both sequential pipeline recovery (already covered by the "Last Good State" idea) and output-completeness verification (already covered by "Second Look").
**Mechanism**: Today, a council pipeline without per-seat attribution either halts the whole panel on one member's silent failure (wasting the work the other members actually completed) or, worse, lets a member merge before review and then can't cleanly recover because the recovery logic can't tell which seat actually went wrong. A gate that tracks every seat independently converts "the whole panel looks broken" into "seat 3 timed out, here's its retry status," and converts an early merge into a reverted, re-queued seat instead of a corrupted pipeline state.
**Measure**: (1) Rate of panel-wide false "all members failed" reports caused by one member's silent/empty response, before vs. after adoption, replayed against LoopTroop's own three documented bug scenarios. (2) Time from a detected early/out-of-band merge to the affected seat being cleanly re-queued, vs. the current manual-intervention baseline. (3) Percentage of recovery incidents where the attribution report correctly names the single failing seat rather than the whole panel.

## Why Now
This is one project's live, in-progress bug-fixing right now (three active PRs within a 30-day window) — the exact moment the pattern is validated as a real, recurring need but before anyone has packaged a reusable version, meaning a small team building this today would ship ahead of LoopTroop generalizing its own fix into something others can adopt.

## Skill Angle
Given a pasted description (or code/config) of an existing council-of-agents delivery pipeline, audit it for the three specific failure modes above — cross-seat status inference, no interception for out-of-band early merges, and ambiguous recovery policy for timeout/empty responses — and produce a concrete remediation plan: where to add per-seat status tracking, where to intercept early merges, and what the retry-vs-escalate policy should be per seat. Useful immediately as a one-off review before committing to building the full gate.

## MVP Sketch
A 3-seat council harness (three agents independently producing a PR against the same ticket) with a per-seat status ledger and a merge gate that blocks until all three have a terminal verdict; inject a timeout on one seat and an empty response on another, and confirm the gate correctly attributes each failure to its own seat and recovers only that seat, rather than treating the whole panel as failed. Replay LoopTroop's three documented bug scenarios directly as test cases. 2-3 weeks for 1-2 people.

## Risks & Open Questions
- LoopTroop itself could generalize its own fixes into a reusable library before this project ships, which would be the strongest evidence this gap closes on its own — worth re-checking LoopTroop's roadmap before committing resources.
- "Council of agents" delivery is still a minority pattern compared to single-agent or sequential-pipeline workflows; the addressable population may be smaller than the sequential-recovery and completeness-verification gaps already covered by other ideas in this index.
- Detecting and safely reverting an "early merge" that already landed in a shared branch is operationally risky (it's a real git revert, not a sandboxed rollback) — getting this wrong could cause more damage than the bug it's fixing.
- The per-seat attribution ledger only helps if the underlying agent framework exposes per-seat status at all; frameworks that already collapse council output into one aggregate response would need a deeper instrumentation change than this project's scope assumes.
