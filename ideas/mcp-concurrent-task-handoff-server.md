# Claim Chain: A Concurrency-Safe MCP Task Handoff Server for Multi-Session Agents

- **Format**: PROJECT
- **Data Sources**: CONNECTED — the project itself exposes an MCP server (Model Context Protocol, a mature, already widely-adopted standard supported natively by Claude Code, Cursor, Codex, and other agent clients) that any MCP-capable client connects to directly to claim/release/list tasks; there's no third-party API to integrate against — the task store is this project's own SQLite-backed state exposed through standard MCP tool calls, so the only "connector" required is the MCP protocol itself, which already exists maturely.

## The Gap
A builder on r/ContextEngineering described hand-rolling a task-handoff protocol from scratch so a different agent (different session, possibly different model) could safely pick up a task another agent saved: "Each task has a revision and an owner identified by agent and session. A claim starts a SQLite write transaction, checks the expected revision... If two AI agents try to claim from the same revision, the first successful claim changes that state." This is a real, non-trivial correctness problem — optimistic concurrency control to stop two racing agent sessions from both believing they own the same task — and the poster built it themselves because nothing off-the-shelf covered it. WebSearch found several small MCP servers attempting the same mechanic, but every one is a tiny, unmaintained proof-of-concept (2 stars or fewer, several not even indexed), meaning any team running multiple concurrent agent sessions against a shared backlog today is choosing between hand-rolling this logic themselves or trusting an abandoned side project.

## The Project
An MCP server that implements a shared, revision-versioned task queue any MCP-capable agent client can connect to: `create_task`, `claim_task` (optimistic-lock claim against an expected revision, rejected if the revision has moved), `release_task`, `complete_task`, and `list_tasks` (filterable by owner, status, and staleness). Claims are backed by SQLite write transactions exactly like the digest's evidenced pattern, so two agents racing to claim the same task can't both win — the loser gets a structured "revision mismatch, current owner is X" response it can act on (retry, skip, or escalate) rather than silently corrupting shared state. On top of the core claim mechanic, the server adds a maturity layer the one-off prototypes lack: configurable claim timeouts with automatic release (so a crashed agent session doesn't permanently orphan a task), an audit log of every claim/release/complete event per task, and a `/stale` query so a human or orchestrating agent can see tasks stuck in a claimed-but-abandoned state.

The novel pattern — concurrency-safe, cross-session, cross-client task ownership over MCP — is the entire product; everything else (timeouts, audit log) exists to make that core mechanic trustworthy enough that a team would actually run it unattended.

## Tangible Impact
**Population**: solo builders and small teams running multiple concurrent AI coding-agent sessions against a shared backlog — for example, someone running Claude Code and Codex against the same repo's task list overnight, or a small team splitting a project's open issues across several autonomous agent sessions — who today either hand-roll their own locking logic (as the digest's evidenced poster did) or accept the risk of two sessions duplicating work on the same task.
**Mechanism**: instead of building a bespoke SQLite-locking layer per project, a team points their existing MCP-capable clients at one shared Claim Chain server; duplicate-claim races that would otherwise cost real LLM-call budget on redundant work (two agents independently solving the same ticket) are structurally prevented rather than caught after the fact.
**Measure**: duplicate-claim rate under concurrent load (target: zero duplicate claims across N simultaneous claim attempts on the same task, tested with an adversarial race-simulation harness); orphaned-task rate (tasks stuck claimed-but-abandoned past the configured timeout, target: auto-released within one timeout window with zero manual intervention); wasted-compute reduction, measured as duplicate LLM-call cost avoided versus a baseline run with no locking.

## Why Now
MCP adoption has reached the point where running several different agent clients (Claude Code, Cursor, Codex) against the same project concurrently is now a common, documented practice rather than an edge case — which is exactly why the digest's evidenced poster needed this mechanic in the first place. The protocol itself (MCP) is mature and stable enough today that a shared task-handoff server can be built once and consumed by any compliant client without per-client integration work, which wasn't reliably true even a year ago.

## MVP Sketch
Scope: a single-file MCP server backed by SQLite implementing `create_task`, `claim_task`, `release_task`, `complete_task`, and `list_tasks`, with revision-numbered optimistic locking and a configurable claim timeout. Stack: Python (or TypeScript) MCP SDK + SQLite, no external services. The single validating experiment: spin up 10 concurrent simulated "agent sessions" (simple scripts, not real LLM calls) all attempting to claim from the same pool of 5 tasks as fast as possible, and confirm zero tasks end up with two simultaneous claimants and that a killed/unresponsive claimant's task auto-releases within the configured timeout.

## Risks & Open Questions
- The strongest reason this might already be solved: if any major agent-client vendor (Anthropic, Cursor, OpenAI) ships a native shared-task-queue feature for multi-session work, this becomes a redundant wrapper around something users get for free — worth re-checking vendor changelogs before building.
- Adoption risk is real: the existing prototypes (Concord MCP, agenthold, FerryCat) each have near-zero stars despite solving a real problem, suggesting either the population that needs this is smaller than it looks, or discoverability (not quality) is the actual blocker — this MVP should test distribution (where would builders even look for this?) alongside the core mechanic.
- SQLite write transactions handle single-machine concurrency well but don't solve cross-machine/cross-network task handoff without an additional sync layer — scope the MVP honestly as single-host and treat distributed deployment as a clearly separate, harder follow-on.
- It's unclear whether most teams hitting this problem would rather have a shared server (this project) or a client-side convention/library they each run locally — validating which deployment model builders actually want should happen before investing in server-hosting concerns.
