# Orchestration Face-Off: A Bring-Your-Own-Tasks Benchmark Harness for DAG Planner-Replanner vs. Message-Passing Multi-Agent Architectures

- **Status**: PUBLISHED
- **Date**: 2026-11-18
- **Topic**: Multi-agent architectures
- **Source**: research/2026-11-18-multi-agent-architectures.md · P2
- **Maturity verdict**: PARTIAL — DAG planner/replanner architectures are individually implemented and evaluated (OrchBench arXiv:2607.25656, VMAO/arXiv:2603.11445, the enterprise typed-DAG paper arXiv:2606.20058), but none of those papers runs the specific head-to-head the r/AI_Agents poster asked for — a shared task suite scored under both a DAG planner/replanner architecture and free-form peer message-passing, same models and tools, same tasks. `gh search repos "multi-agent DAG planner"` and "DAG orchestration vs message passing benchmark" turned up no dedicated comparison repo.
- **Format**: PROJECT — the value is a maintained, re-runnable harness and reference implementations of both architectures, not a one-shot judgment a prompt could render.
- **Data Sources**: MANUAL — the user uploads their own representative task suite: 10-30 multi-step task prompts plus a scoring rubric or expected-output checklist for each (the same "bring your own tasks" pattern this repo already uses for benchmark-harness ideas like ArchPick and ReviewMeter, because a single fixed public task suite would be exactly the "just your tasks" objection raised in Risks below). No external connector is needed or would strengthen this — the thing being measured is the user's own workload, not a third-party data source.

## The Gap
An r/AI_Agents post describing a DAG-based planner/replanner design explicitly asks the community "has anyone benchmarked this against message-passing approaches?" and gets no pointer to an answer; the single highest-engagement item in this run — HN's "Building a Multi-Agent System from Scratch: Architecture Patterns" (106 pts, 45 comments) — is directly about comparing architecture patterns without resolving which wins empirically. Meanwhile three separate academic papers each evaluate a DAG planner/replanner design in isolation, with no paper, benchmark, or tool running the same tasks through both a DAG architecture and free-form peer message-passing to produce a real comparative number.

## The Project
A benchmark harness that takes a user's own multi-step task suite and runs it through two reference agent architectures built on the same underlying model, tool set, and token budget: (1) a DAG planner/replanner — an explicit planner emits a subtask DAG, a replanner revises it on failure — and (2) free-form peer message-passing, where agents negotiate and hand off work via unstructured turn-taking with no pre-committed plan graph. Both architectures are implemented to a comparable quality bar (not a strawman on either side) and scored on the identical tasks for success rate, total cost, wall-clock latency, and failure mode (stuck loop, wrong subtask order, miscommunicated handoff, premature termination). The centerpiece is the two parallel, well-built reference implementations plus the scoring harness — not a leaderboard of someone else's self-reported numbers.

Components: two reference agent implementations (DAG planner/replanner, free-form message-passing) sharing one tool-calling layer and one base model config so the comparison isolates architecture, not implementation quality; a task-suite ingestion format (prompt + rubric/expected-output per task); a scoring runner computing success rate, cost, latency, and a tagged failure-mode breakdown per architecture; a comparison report generator.

## Tangible Impact
**Population**: Engineering teams building custom multi-agent pipelines on frameworks like LangGraph, CrewAI, and AutoGen who are choosing between a DAG/plan-based orchestration style and free-form peer message-passing before committing engineering time — concretely the same cohort visible in the digest's r/AI_Agents thread, the 45-comment HN architecture-patterns discussion, and the broader base of teams represented by LangGraph's and CrewAI's combined installed base (each in the tens of thousands of GitHub stars), most of whom currently pick an architecture from a blog post's prose argument rather than a number.
**Mechanism**: Today, a team choosing between these two architectures has to trust a blog author's qualitative argument or build both themselves to find out — an expensive, rarely-done experiment, so most teams commit to one architecture based on which pattern the tutorial they read happened to use. A harness that runs their own tasks through both reference architectures turns that choice into a measured decision made before most of the pipeline is built, instead of a rebuild discovered is needed after the system is in production.
**Measure**: (1) Success-rate delta between the two architectures on a pilot team's own task suite, with the failure-mode breakdown attributing *why* one won. (2) Cost and wall-clock latency delta per completed task between architectures on the same suite. (3) Number of pilot teams whose stated pre-benchmark architecture preference flips after seeing their own results, tracked across the first 10-15 teams who run the harness.

## Why Now
The underlying architectural primitives are now mature and separately well-studied — three independent 2026 papers evaluate DAG planner/replanner designs on their own, and free-form message-passing is the default pattern in most popular frameworks' tutorials — so assembling a fair head-to-head is now an integration problem, not a research problem; the convergence of a top-engagement HN post and an explicit "has anyone benchmarked this" community ask in the same 30-day window signals the comparison is wanted now, not hypothetically useful later.

## MVP Sketch
Build the two reference architectures on one model/tool-calling stack (e.g., a single model via one provider's tool-calling API), using LangGraph primitives for the DAG planner/replanner and a bare message-passing loop for the peer-chat variant. Run both against 2-3 borrowed public task domains (a coding task, a multi-step research/QA task) plus one pilot team's own 10-task suite. Validate by checking whether the harness reproduces the qualitative claims already made in the digest's community threads (e.g., does message-passing actually show more "drift" failures, does the DAG approach actually show more rigid-replan failures on genuinely dynamic tasks) — if the harness's numbers contradict the community's own stated intuitions, that's still a publishable, useful result. 3-4 weeks for 1-2 people.

## Risks & Open Questions
- Any single pair of reference implementations is contestable as not representative of "the" DAG or "the" message-passing approach — mitigated by the bring-your-own-task-suite design, but the reference implementations themselves still need to be defensibly well-built on both sides, or critics will dismiss a loss as a strawman.
- A badly-tuned DAG planner or an unusually disciplined message-passing protocol could swing results in either direction; parity in implementation effort between the two architectures is the hardest part of this build, not the scoring logic.
- One of the three cited academic groups (OrchBench, VMAO, or the enterprise A2A paper's authors) could run this exact comparison first — all three already have one half of the harness built.
- Multi-agent orchestration patterns are still evolving quickly; a one-time benchmark snapshot risks going stale, so the harness itself (re-runnable against new task suites and new reference implementations) has to be the durable deliverable, not any single published number.
