# Voice-Native Core: A Reference Agent Architecture That Treats Speech as the Primary Interaction Mode, Not a Bolted-On Output Layer

- **Status**: EXPLORING (promoted 2026-11-19: evidence-density criterion — 2 independent practitioner essays within the source digest independently name the same gap)
- **Date**: 2026-11-19
- **Topic**: Voice & multimodal agents
- **Source**: research/2026-11-19-voice-multimodal-agents.md · P7
- **Maturity verdict**: PARTIAL — streaming-TTS and voice-as-layer infrastructure is mature and shipped (AgentScope's three-layer voice design, Telnyx Agent SDK's voice mixin, LiveKit/Pipecat's streaming-synthesis-before-full-text patterns), but every framework found treats voice-out as a swappable layer or mixin bolted onto a text-first agent core by explicit design ("the agent core should stay ignorant of audio formats") — precisely the architecture two dated practitioner essays (bittide.aicompass.dev's "Voice feels like the underrated output layer for AI agents"; allenpike.com's "Building for Voice In, Visuals Out," also discussed on Hacker News) name as the design blind spot, with the latter asserting the fluid-conversation latency bar is ~200ms and most shipped systems miss it. No framework was found that inverts this and designs turn-taking/reasoning decomposition natively around voice from the start.
- **Format**: BOTH
- **Data Sources**: CONNECTED — the reference core integrates with the host's existing real-time audio transport (LiveKit or Pipecat, both mature and widely adopted) to receive/send audio streams; it reads no new external account data of its own. The novelty is the reasoning/turn-taking logic sitting on top of that transport, not a new data connector.

## The Gap
Two independently-dated practitioner essays, found via WebSearch, name the same blind spot from different angles: voice is consistently designed as an output channel added after an agent's text-first reasoning core is already built, rather than as the primary interaction mode the reasoning loop is structured around from the start. The allenpike.com piece states the fluid two-way conversation latency bar is "about 200ms," implying systems designed output-last routinely miss it. The gap-analyst's search of shipped voice infrastructure (AgentScope, Telnyx, LiveKit, Pipecat) confirms the plumbing for fast voice *output* exists, but every one of those frameworks explicitly keeps the agent's core reasoning ignorant of the fact that it's talking at all — which is the bolted-on pattern the essays criticize, not a counterexample to it.

## The Project
A reference agent-loop architecture (and a reusable library implementing it) where turn-taking and incremental response generation are first-class parts of the reasoning loop instead of a downstream TTS adapter. The core change: instead of "generate the full text response, then stream it to TTS," the reasoning model is driven to emit committable partial utterances — short, semantically complete chunks it's confident won't need revision — synced directly to a streaming synthesizer, with an explicit turn-state machine (listening/thinking/committing/speaking/interrupted) as a core abstraction the reasoning loop itself consults, not an app-level flag layered on top. Components: a chunked-commit reasoning wrapper (decides when a partial thought is safe to start speaking), a turn-state machine library, and transport adapters for LiveKit and Pipecat so teams don't have to rebuild the audio plumbing, only replace the reasoning-to-speech boundary.

## Tangible Impact
**Population**: small teams building latency-sensitive, voice-first consumer products — AI phone triage/support lines, in-car voice assistants, voice-dictation copilots for drivers — currently shipping on a text-first core with a TTS adapter glued on; and, downstream, the much larger population of phone callers and voice-assistant end users (per Edison Research's long-running Smart Audio Report, roughly a third of U.S. adults own a smart speaker and regularly interact by voice) who experience the perceptible "thinking pause" and unnatural turn-taking these bolted-on architectures produce.
**Mechanism**: a reasoning loop that can start speaking a confident partial thought while still reasoning about the rest cuts the gap between "user stops talking" and "agent starts talking" below the ~200ms naturalness threshold the essays cite, instead of waiting for a full text response to finish generating before TTS even starts; end users get a conversation that feels responsive instead of a call-center-hold-music cadence.
**Measure**: median time-to-first-audio from end of user utterance (hook on vs. a cascaded text-first baseline); correct barge-in resumption rate on a benchmark call set with scripted interruptions; blind-listener naturalness rating (MOS-style A/B) comparing the voice-native core against the same model wired through a conventional TTS-adapter pipeline.

## Why Now
Streaming LLM output and streaming TTS are both now fast and cheap enough (sub-second time-to-first-token, sub-200ms TTS synthesis start) that the previously-dominant "wait for the full response, then speak" pattern is no longer a hardware necessity — it survives mostly as architectural inertia from text-first chat-agent frameworks, which is exactly why a reference implementation that inverts the assumption is newly buildable rather than requiring new model capability. The two practitioner essays naming this gap are both within the digest's 30-day window, meaning the critique is fresh, not stale.

## Skill Angle
An architecture-audit aid: the user pastes a description (or code) of their existing voice-agent pipeline — how the reasoning model is called, when TTS synthesis starts relative to text generation, and how turn-taking state is tracked. The skill flags each place the pipeline falls into the bolted-on anti-pattern (full-text-before-TTS, turn-state as a boolean flag rather than a first-class state machine) and drafts a migration plan toward the chunked-commit pattern, including which parts of their existing LiveKit/Pipecat wiring can stay as-is. This is separable from the project: the project is the reusable core library; the skill is a one-time design-review aid for a team deciding whether migrating is worth it before committing engineering time.

## MVP Sketch
Scope: a Python reference implementation of the chunked-commit reasoning wrapper and turn-state machine, wired to one real streaming LLM and one real streaming TTS engine over a LiveKit room. Validate with a 20-scenario scripted call set (half requiring mid-response interruption handling) measuring time-to-first-audio and interruption-resumption correctness against a conventional cascaded baseline built from the same model and TTS engine. Target: 3-4 weeks for two people (core loop + turn-state machine, plus the baseline comparison harness).

## Risks & Open Questions
- Chunked, confidence-gated partial commits risk the model "speaking before it's thought things through" and having to awkwardly correct itself mid-utterance — the commit-confidence threshold is the central design risk, not a solved detail.
- LiveKit's own `MultimodalAgent` and Pipecat already give teams enough that some may judge a from-scratch core an unnecessary rebuild rather than adopt a new abstraction — the MVP's comparison benchmark needs to show a measurable naturalness/latency win, not just an architectural purity argument.
- The ~200ms bar cited is from one practitioner essay, not a controlled study; the MVP should treat it as a target to validate against real blind-listener ratings, not an assumed ground truth.
- If a frontier end-to-end full-duplex voice model (already shipping per this cycle's SATURATED P1 finding) simply obsoletes the cascaded-reasoning-then-speak question entirely for well-resourced teams, this project's addressable audience narrows to teams who still need or prefer a modular, swappable-model cascade.
