# One Record: A Unified Per-Request Provenance Ledger Binding Prompt, Model, Retriever, and Judge Versions

- **Status**: PROPOSED
- **Date**: 2026-11-20
- **Topic**: LLM evaluation & observability
- **Source**: research/2026-11-20-llm-evaluation-observability-ii.md · P4
- **Maturity verdict**: PARTIAL — MLflow's "audit-ready LLM logs" feature already links an output to its inputs, retrievals, guardrail decisions, and model version in one tamper-evident per-request record; OneUptime's guide recommends attaching prompt/index/evaluator versions per-stage. But the exact fourth field — judge/evaluator version bound into the same unified per-request record alongside prompt+model+retriever — was not found in any named product; "judge version" never appears alongside the other three. Three of four components are shipped; the unified four-field record is not.
- **Format**: BOTH
- **Data Sources**: CONNECTED — extends MLflow's existing tracing/audit-log feature (mature, already shipping today, already capturing prompt/model/retrieval) by adding a fourth bound field for judge/rubric version, pulled from whichever eval framework (promptfoo, DeepEval, an in-house harness) the team already runs. No new external data source is introduced beyond what the team's existing stack already produces; the gap is in binding, not in access.

## The Gap
An arXiv paper ("The Grand Software Supply Chain of AI Systems," cited via search) argues that without per-request metadata recording which artifact versions produced each response, even detecting a regression requires a behavioral baseline most serving stacks don't maintain. WebSearch confirmed the individual pieces exist separately — MLflow binds prompt/model/retrieval/guardrail-decision into one record; OneUptime's guide recommends per-stage versioning as a manual discipline — but no named product was found binding the judge/evaluator version into that same per-request record, leaving a structural gap exactly where root-causing most needs it: after a pipeline change of any kind, a team still has to manually correlate four separate logs to find out which component actually changed.

## The Project
A thin extension layer that sits on top of an existing per-request logging stack (starting with MLflow, which already captures three of the four fields) and adds the fourth: at generation time, it tags the request record with the exact judge/rubric identifier and version that will later score it, so every request's complete provenance — prompt version, model/version, retriever/index version, judge/rubric version — lives in one queryable record from the moment it's created, not reconstructed after the fact from four systems.

Components: a judge-version registry (hashes a judge's prompt/model/rubric config into a versioned identifier, mirroring how prompt versions are already tracked); a write-time binder that attaches the judge-version identifier to the same per-request record MLflow already produces; a query interface that, given a flagged regression, returns the full four-field provenance for the affected requests in one call instead of four lookups.

## Tangible Impact
**Population**: engineering teams running multi-component LLM pipelines — a prompt, a model, a retrieval index, and a judge that can each change independently — who already use MLflow's LLM tracing or an equivalent per-request logging stack; per LangChain's 2024 State of AI Agents survey (~51% of surveyed companies running agents in production), a meaningful share of that group runs RAG-plus-judged pipelines where more than one component changes on its own release cadence.
**Mechanism**: Today, root-causing a regression after any pipeline change means pulling prompt-version history, model-version logs, retrieval-index change logs, and judge-config history separately and manually aligning them by timestamp — a process that gets slower and more error-prone as more components change independently. A single bound record collapses that into one query: given a flagged request, the team immediately sees which of the four components was different from the last-known-good baseline.
**Measure**: time to attribute a regression to its responsible component, from today's multi-log manual correlation (commonly hours, per practitioner accounts) down to a single query; percentage of regressions correctly attributed to the right component on a test suite of synthetic multi-component changes (prompt-only, model-only, retriever-only, judge-only, and combinations); percentage of production requests carrying a complete four-field provenance record versus partial (today: 0% have all four, since no product binds judge version in).

## Why Now
MLflow's audit-ready LLM logging feature already ships the hard parts (tamper-evident per-request binding of prompt/model/retrieval/guardrail decisions) in 2026 — the remaining work is adding one more field to an existing mature mechanism, not building new logging infrastructure from scratch, which keeps this buildable by a small team rather than requiring a new observability platform.

## Skill Angle
Trigger: a team has a flagged regression and today's fragmented logs (prompt history, model changelog, retrieval index changelog, judge-config history) to manually correlate, without yet having the continuous binder installed. Inputs: the four separate log exports or changelogs, pasted or uploaded, plus the timestamp/request-ID of the flagged regression. Output: a reconstructed best-effort provenance record for that specific request — which prompt version, model version, retriever/index version, and judge version were active at that timestamp — with a confidence note on any field where the logs don't cleanly resolve to one version. The skill is a one-shot forensic reconstruction from existing fragmented logs; the project is the continuous binder that makes every future request's provenance complete from the start.

## MVP Sketch
2–3 weeks, 1–2 people: build the judge-version registry (hash a judge's system prompt + model + rubric config into a stable version ID), wire it into MLflow's existing tracing hook so every logged request carries that ID alongside the fields MLflow already captures, and build a simple query tool that takes a request ID and returns all four provenance fields in one response. Validate by deliberately rolling three independent changes (a judge rubric edit, a retrieval index rebuild, a model version bump) across a test window and confirming the tool correctly attributes a seeded regression to the right one of the three on the first query.

## Risks & Open Questions
- If MLflow (or a competing framework) ships native judge-version binding as a feature update in the near term, this becomes a thin wrapper rather than a standalone product — worth checking MLflow's own roadmap before committing to a full build.
- Judge "version" is fuzzier than prompt/model version — a judge's effective behavior can drift from provider-side model updates even with an unchanged config hash, which this ledger alone won't catch (that's the separate judge-drift-attribution gap, already covered by an existing idea in this index).
- Teams using fully closed eval SaaS products may have no hook point to tag judge version at write time, limiting addressable surface to self-hosted/in-house harnesses and frameworks like MLflow that expose a tracing hook.
- The value is entirely in attribution speed during an incident; teams that rarely change more than one component at a time may see limited benefit relative to the integration cost.
