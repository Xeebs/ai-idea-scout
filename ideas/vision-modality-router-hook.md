# See First, Reason Second: A Pre-Reasoning Modality Router Hook for Vision-Blind Text Agents

- **Status**: PROPOSED
- **Date**: 2026-11-19
- **Topic**: Voice & multimodal agents
- **Source**: research/2026-11-19-voice-multimodal-agents.md · P3
- **Maturity verdict**: PARTIAL — one practitioner write-up describes switching to "an automatic hook that runs before the model reasons" as a personal workaround, not a documented library feature. GitHub search found no repo matching the exact pre-reasoning-hook shape. Academic adjacent work exists but is narrow/unevaluated in production: ToolGate (arXiv 2606.03054, linked code) is an external controller deciding whether a proposed perceptual tool call should run, and reports only ~11.8% of baseline tool calls actually fixed a wrong answer; ToolScope (arXiv 2510.27363) has a similar pre-invocation "Global Navigator." Practitioner "modality router" patterns (CallSphere blog, OpenHands `MultimodalRouter`) route to different models/processors by input type, not the "does the text-only model even know it needs vision" decision. No mainstream agent framework ships this as a standard feature.
- **Format**: BOTH
- **Data Sources**: CONNECTED — the runtime hook reads the host application's own conversation/attachment store to see what images are actually sitting in a thread before the reasoning model runs. For the flagship use case (AI customer-support widgets), this means the Zendesk or Intercom conversation API (both mature, widely-integrated REST/webhook APIs already used for ticket data) to pull attached screenshots; for a custom in-house agent, it means the host framework's own message/attachment object (LangChain, OpenAI Assistants API threads, or a bespoke agent loop's context store). No new third-party data source needs to be built — the hook is new middleware, but it reads through connectors that already exist and are mature.

## The Gap
A WebSearch-surfaced practitioner write-up on multimodal agent architecture reports the obvious but unaddressed structural problem: "a text-only model can't reliably decide when to call a vision tool, since it can't see the image" — so the author "switched to an automatic hook that runs before the model reasons" and decides modality routing for it. The same search pass found mostly vendor tutorial stacks (Whisper + LLaVA + function-calling model + TTS) that still rely on the LLM's own function-calling judgment to decide when to look, meaning this workaround hasn't propagated past one author's blog post into the mainstream tutorials or frameworks everyone copies from.

## The Project
A small, framework-agnostic middleware library that sits in front of an agent's reasoning call. Before the main model runs, the hook inspects the current turn's context for attachments, screenshots, or image references (via regex/metadata detection plus a cheap vision classifier run on any attached image), decides whether the content is plausibly relevant to answering the user's message, and — if so — proactively runs the vision tool and injects its output into context *before* the text model ever has to decide to ask for it. The core novelty is inverting today's default: instead of "text model notices it might need vision and calls a tool," it's "a cheap pre-pass decides vision is needed and hands the text model the answer already looked up." Components: an attachment/image detector, a lightweight relevance classifier (fine-tuned CLIP-class model or a cheap vision-LLM call, not the main reasoning model), a routing policy (always-run / confidence-threshold / ask-the-user), and adapters for LangChain, OpenAI Assistants threads, and a raw webhook integration for support platforms.

## Tangible Impact
**Population**: teams running AI-first customer-support widgets that accept image attachments (a standard pattern across Zendesk, Intercom, and in-app SaaS support chat), and the end users who attach a screenshot — a billing error, a broken UI element, a damaged product photo — expecting the AI agent to actually look at it before responding.
**Mechanism**: today, a text-reasoning-only support agent frequently answers from the user's text message alone because it never decided to invoke its own vision tool on the attached image, producing an answer that ignores the screenshot entirely or misdiagnoses the issue; the pre-reasoning hook guarantees the image gets inspected whenever it's plausibly relevant, so the agent's first response is already grounded in what the user actually attached.
**Measure**: first-response resolution accuracy on tickets with an image attachment (human-graded, hook on vs. off); rate of agent responses that visibly ignore or contradict an attached screenshot; escalation-to-human rate for image-attached tickets, before and after.

## Why Now
Cheap, fast vision classifiers (sub-100ms CLIP-class models, or a single small vision-LLM call) are now inexpensive enough to run on every turn as a pre-pass without materially affecting latency or cost — which is exactly what makes a "decide first, reason second" hook newly practical rather than an extra expensive model call nobody wants to pay for twice. The ToolGate and ToolScope papers (both 2026, both with linked code) show the academic groundwork for pre-invocation perceptual gating already exists and is citable, but neither has been packaged into a drop-in library a support-widget team could actually install.

## Skill Angle
A one-shot architecture-review aid: the user pastes their current agent's tool-calling setup (the system prompt, the vision-tool definition, and a couple of example traces where an image was attached but the tool wasn't called). The skill identifies whether the pipeline relies on LLM-initiated vision-tool calling and, if so, drafts the pre-reasoning hook's routing policy and adapter config tailored to their framework (LangChain middleware snippet, or a webhook pre-processor for Zendesk/Intercom). This is separable from the project: the project is the always-running middleware; the skill is the one-time integration-design aid that gets a specific team's pipeline fitted to it.

## MVP Sketch
Scope: a Python middleware package exposing a single `route_before_reasoning(context) -> augmented_context` function, backed by a small vision-LLM relevance check, plus one reference adapter (LangChain). Validate against a 30-ticket test set of real-shaped support tickets with attached screenshots, half where the image is relevant and half where it's a decoy, measuring whether the hook correctly decides to inspect vs. skip, and whether inspection improves downstream answer accuracy versus an LLM-initiated-tool-calling baseline. Target: 3 weeks for one person (hook + LangChain adapter + eval set).

## Risks & Open Questions
- A cheap always-run relevance classifier adds latency and cost to every turn with an attachment, even when most are irrelevant — the confidence-threshold policy needs real tuning against a representative ticket mix, not a fixed default.
- If a major agent framework (LangChain, the OpenAI Agents SDK) ships an equivalent "always inspect attachments" default in the next few releases, this collapses to a thin wrapper around a built-in feature — worth checking framework changelogs before committing to a standalone adapter layer.
- The ToolGate paper's own finding — only ~11.8% of baseline tool calls actually changed a wrong answer to a right one — suggests the upside ceiling for this pattern may be more modest than the "obvious unaddressed gap" framing implies; the MVP eval needs to measure the real lift honestly, not assume it.
- Support-platform APIs (Zendesk, Intercom) rate-limit and paginate attachment access differently; the production CONNECTED integration is more plumbing work than the MVP's single-adapter scope suggests.
