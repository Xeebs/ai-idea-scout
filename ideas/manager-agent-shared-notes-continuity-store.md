# Continuity Desk: A Manager-Agent + Shared Notes Store So Per-Client Agent Context Survives Resets

- **Status**: EXPLORING (promoted cycle 210: evidence density — ≥2 independent threads)
- **Date**: 2026-11-19
- **Topic**: Agentic AI & autonomous agents
- **Source**: research/2026-11-19-agentic-ai-autonomous-agents.md · P1
- **Maturity verdict**: PARTIAL — adjacent building blocks ship widely (Cloudflare Agent Memory, Anthropic's Managed Agents memory beta, AWS AgentCore session isolation, PraisonAI's `MultiAgentContextManager`, generic "blackboard" shared-notepad repos), but no maintained package combines a supervising manager-agent with a shared per-project notes store that survives session resets in one piece — the HN-described workflow (raw SQLite + ad hoc notes files) is still hand-rolled.
- **Format**: BOTH — the manager-agent + persistent notes store is runtime infrastructure; auditing a specific freelancer's or team's current multi-project setup and designing the manager/notes-store layout for it is a separable one-shot task.
- **Data Sources**: CONNECTED (project) — reads each sub-agent's session/tool-call transcript directly through the host agent runtime's own hook/session API (e.g., Claude Code's session hooks, or an equivalent transcript-access hook for other CLI agent runtimes) to auto-populate the shared notes store; this transcript-access mechanism already exists maturely for Claude Code today, and would need an equivalent adapter built per additional runtime. MANUAL (skill) — the user pastes a description of their current per-client/per-project setup (which agents, which clients, how notes/context are currently kept) for the one-off design review.

## The Gap
An HN thread, "Ask HN: How do you manage your AI agents' context across clients and projects?" (103pts, 71cmt, 2026-11-07), surfaces people running one agent per client supervised by a hand-rolled "manager" agent, persisting project context in raw SQLite or ad hoc notes files so it survives session resets. Indie Hackers posts corroborate ("context management is honestly the biggest bottleneck right now"; "context gets lost between sessions... have to re-feed it"), and a Product Hunt memory-tool maker explicitly flags that "provenance... is still missing across most tools" even in a dedicated product. The gap-analyst confirmed no shipped package combines the manager-agent layer with the persistent shared-notes layer — teams keep re-deriving both halves themselves.

## The Project
A lightweight manager-agent runtime paired with a shared, per-project notes store that any sub-agent session can read from and write to. Each client/project gets its own notes partition (SQLite with full-text search) that persists independently of any individual agent session; a manager agent sits above the sub-agents, routes new work to the right project partition, and — critically — logs *why* each note was written (which sub-agent, which session, what triggered it), closing the decision-provenance gap the Product Hunt maker flagged. When a session resets or a new sub-agent spins up for the same project, it reads the notes store first instead of starting cold.

Components: a per-project SQLite+FTS notes store with a simple read/write API; a manager-agent process that dispatches sub-agent sessions and tags every note with its originating session/agent; a provenance log (which note came from which decision, with a timestamp and source session ID); a CLI to inspect/search notes per project; a transcript-ingestion adapter that auto-extracts durable facts from a sub-agent's session into the notes store on session end.

## Tangible Impact
**Population**: Independent consultants, freelance developers, and small agencies (the same ~2-20-person scale the HN thread and Indie Hackers posts describe) running concurrent AI-agent engagements across multiple clients or long-running internal projects, where each session reset currently means re-explaining project state from scratch.
**Mechanism**: Today, when a session resets (context window fills, a new sub-agent starts, a different tool is opened), the person either re-pastes prior context manually or the agent silently loses it — both are described directly in the HN thread as the actual daily workflow. A persistent, provenance-tagged notes store that a manager agent routes reads/writes through turns "re-explain the project every reset" into "read the last three relevant notes automatically," and makes it possible to answer "why did the agent do X" by tracing the note back to its source session instead of grepping chat logs.
**Measure**: (1) Time spent manually re-feeding context per session reset, before vs. after adoption, self-reported by a pilot group of freelancers/agencies. (2) Rate of a sub-agent re-deriving a fact or decision that was already recorded in a prior session for the same project (a measurable redundancy count). (3) Percentage of notes in the store with a traceable provenance chain back to a specific source session, vs. the current baseline of zero in hand-rolled SQLite setups.

## Why Now
The HN thread, the Indie Hackers complaints, and the Product Hunt "pmb" launch all surfaced independently within the same 30-day window, and the building blocks this project depends on (Claude Code's session hooks, mature SQLite FTS tooling) only became reliable enough this year to wire a manager-agent layer on top of without building the storage substrate from scratch.

## Skill Angle
Given a description of a freelancer's or small team's current multi-client/multi-project agent setup — which agents run where, how notes are currently kept (if at all), and where context loss has actually bitten them — produce a concrete manager-agent + notes-store layout: which facts belong in the shared store vs. stay session-local, a minimal schema for the notes partition per project, and a provenance-tagging convention. Useful immediately as a one-off architecture review, independent of whether the full runtime gets adopted.

## MVP Sketch
A single-project proof: SQLite+FTS notes store, a manager-agent script that spins up a sub-agent for a task, tags every note it writes with the sub-agent's session ID, and on the next session for the same project, pre-loads the top-N relevant notes by FTS query instead of starting cold. Experiment: run the same multi-session task (e.g., a 3-session feature build) with and without the notes store and measure how much context the person has to manually re-paste in each condition. 2-3 weeks for 1-2 people.

## Risks & Open Questions
- This is adjacent to the existing "Client Wall" idea (`freelancer-client-context-isolation-boundary.md`), which targets a different failure mode on the same rough population — leak *prevention* across clients, not context *continuity* across resets. The two could eventually compose (a notes store wrapped in Client Wall's isolation boundary), but neither subsumes the other; building this without also building leak prevention leaves cross-client leakage unaddressed.
- Auto-extracting "durable facts worth persisting" from a raw transcript is the hardest unsolved piece — too aggressive and the notes store fills with noise; too conservative and it misses the facts people actually needed re-fed.
- The manager-agent routing layer only has value once there's more than one concurrent project; a single-project user gets the notes-persistence benefit without needing the manager-agent half at all, so the two components may need to ship and be evaluated separately.
- A well-resourced memory vendor (Cloudflare, Anthropic's own managed-agents memory beta) could ship this exact combination as a platform feature before an independent project gets traction.
