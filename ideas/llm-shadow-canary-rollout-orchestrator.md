## The Gap
tianpan.co's repeated 2026 coverage of the identical manual playbook (`llm-gradual-rollout-shadow-canary-ab-testing`, `canary-deploys-llm-model-upgrades`, `gradual-rollouts-fail-ai-features`, `staging-environment-lie-ai-systems`) and an independent vendor post converging on the same three-stage framing both describe this as advice to implement yourself, not a packaged tool — explicitly distinct from generic feature-flag/canary infra because it needs prompt+model version pairing per logged event and judge-based shadow comparison, not just error-rate thresholds. Vendor features exist (LaunchDarkly, Statsig) but are beta/early-access, with no native shadow-mode feature, and no open-source implementation automates version-pairing, shadow-sample-rate selection, and judge-based promote/rollback decisioning.

## The Project
An orchestrator that sits in front of a team's existing LLM gateway, automating the three-stage playbook: (1) runs offline eval on the candidate prompt/model version against a held-out set before anything touches live traffic, (2) shadow-tests the candidate against a configurable sample rate of real production traffic — generating its output but never serving it to users — and judge-scores the shadow output against the currently-live version's output on the same inputs, (3) once shadow comparison clears a configured threshold, promotes to a small canary traffic slice with automatic rollback if canary metrics regress, all with every event tagged by exact prompt+model version pair for later audit.

Components: gateway-layer traffic duplicator (shadow mode, zero user-facing latency/cost impact); judge-based shadow-comparison scorer; configurable promote/rollback threshold engine; version-pairing event tagger; a dashboard showing a rollout's current stage and comparison scores.

## Tangible Impact
**Population**: Engineering teams shipping prompt or model version changes to a production LLM feature at least weekly without a dedicated platform/SRE team to hand-build rollout safety tooling — the same audience the tianpan.co posts are written for (a practitioner repeatedly hitting this at real companies), realistically overlapping heavily with the "teams past the prototype stage, before building in-house eval tooling" population from LangChain's 2024 survey (~51% of surveyed companies running agents in production).
**Mechanism**: Today, safely rolling out a prompt/model change means either manually wiring shadow traffic duplication and judge comparison from scratch each time (the exact repeated advice tianpan.co keeps re-explaining), or skipping the safety step and canarying blind with only generic error-rate monitoring that doesn't catch a quality regression a judge would. The orchestrator turns a from-scratch manual playbook into a repeatable, configured pipeline, so a prompt change that would silently degrade answer quality gets caught in shadow mode before any real user sees it, instead of after a canary slice already did.
**Measure**: (1) percentage of prompt/model changes that go through shadow testing before any live traffic exposure, from the current largely-skipped baseline to a majority on pilot teams; (2) number of regressions caught in shadow mode versus discovered post-canary or post-full-rollout, on a pilot team's rollout history; (3) time to safely roll out a prompt/model change end-to-end (offline eval through full promotion), compared against the hand-wired baseline tianpan.co's posts describe.

## Why Now
LLM gateway proxies (LiteLLM) mature enough to duplicate and route traffic cleanly are now widely adopted, and judge-based automated scoring is cheap and fast enough to run on a shadow traffic sample in near-real-time — both prerequisites exist today; the gap is purely that nobody has wired them into one packaged rollout pipeline, which four independent 2026 blog posts and a vendor convergence confirm teams keep re-building by hand.

## Skill Angle
Trigger: a team is about to ship a prompt or model version change to a production LLM feature and wants a rollout plan rather than shipping blind. Inputs: a description of the change (old vs. new prompt/model), the feature's current traffic volume, and any existing offline eval results. Output: a drafted rollout plan — recommended shadow sample rate and duration given their traffic volume, specific judge-comparison criteria to gate promotion, and a canary-stage rollback threshold — ready to execute manually or feed into the orchestrator. The skill is the one-time planning pass for a specific change; the project is the pipeline that executes and enforces that plan automatically.

## MVP Sketch
A LiteLLM-proxy plugin that duplicates a configurable percentage of requests to a shadow candidate version, judge-scores shadow output against live output on the same inputs using an existing judge call, and exposes a simple promote/rollback API once a configured comparison threshold is met or breached — version-pairing every event via a tag. Experiment: replay one pilot team's real historical rollout (a past prompt change they shipped without this tooling) through the shadow stage and confirm the judge comparison would have correctly flagged it as safe or risky, matching what actually happened in production. 3-4 weeks, 1-2 people.

## Risks & Open Questions
- LaunchDarkly or Statsig could graduate their beta "Online Evaluations"/"AI Evals" features to GA with native shadow-mode support, which would directly compete with and likely out-resource a third-party orchestrator.
- Shadow-testing doubles inference cost for the sampled traffic slice during the shadow window, which needs to stay small enough not to offset the safety value for cost-sensitive teams.
- Judge-based shadow comparison inherits all the known LLM-as-judge reliability issues (position bias, format sensitivity — both separate patterns in this same digest), meaning the promote/rollback decision is only as trustworthy as the judge behind it.
- This is conceptually adjacent to this repo's existing "Quiet Break" idea (post-deploy, judge-free, trace-baseline regression detection) — this project is pre-promotion and judge-based, that one is post-deploy and deterministic; worth confirming in practice they stay genuinely complementary rather than redundant.
