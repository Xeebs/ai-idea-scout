# Pattern Picker: A Framework-Agnostic Decision Tool for Choosing a Multi-Agent Orchestration Pattern

- **Status**: PROPOSED
- **Date**: 2026-11-13
- **Topic**: Multi-agent architectures
- **Source**: research/2026-11-13-multi-agent-architectures.md · P1
- **Maturity verdict**: PARTIAL — a strands-agents/harness-sdk docs PR (https://github.com/strands-agents/harness-sdk/pull/5553, 2026-10-26) explicitly complains that the framework's "Coordinate multiple agents" page "listed Graph, Swarm, and Workflow side by side without helping readers decide." WebSearch found several single-author decision aids (Agentica's decision-tree docs, Dojogenesis's interactive 5-question Pattern Selector, a Glukhov practical guide, Claude-Code-specific skill pages touching pattern selection) but `gh search repos` for "multi-agent orchestration pattern decision" returned zero results — no maintained, framework-agnostic tool with real adoption exists; the gap is real but a serious build would need to differentiate from the scattered single-page attempts.
- **Format**: SKILL — the deliverable is a one-shot recommendation given a task description, not persistent runtime infrastructure.
- **Data Sources**: MANUAL — user pastes a task/workflow description (what the agents need to accomplish, how many distinct roles/skills are involved, whether steps are fixed-order or dynamic, whether agents need to negotiate or just report up) plus any existing framework choice (LangGraph, CrewAI, Microsoft Agent Framework, Google ADK, strands-agents) they're locked into. No connector exists or is needed — this is an architectural-judgment task applied to a description, not a data-retrieval task.

## The Gap
Once a team has already decided to go multi-agent (a separate, upstream decision this pipeline has a dedicated idea for — "Two Yeses"), every major framework still presents its orchestration primitives — Graph, Swarm, Workflow, Hierarchical/Supervisor — as a flat taxonomy with no decision logic for which one fits a given task. The strands-agents maintainers are hand-patching this in prose for their own framework right now; Microsoft Agent Framework, Google Cloud's agent taxonomy, CrewAI, and LangGraph each ship their own flat pattern list with the same gap. The handful of people who've built a decision aid (Dojogenesis's 5-question selector, a couple of blog decision trees) did it as a single-page, single-framework artifact — none is maintained, cross-framework, or validated against real outcomes.

## The Project
A portable scoring tool: given a task/workflow description, score it against a small set of structural criteria — step determinism (fixed sequence vs. dynamic routing), need for peer negotiation vs. strict supervisor control, branching/looping requirements, need for parallel fan-out, and debugging/observability tolerance — and output a recommended pattern (Workflow / Graph / Swarm / Hierarchical-Supervisor) with the specific criteria that drove the call, plus a mapping to each major framework's name for that pattern (so a LangGraph user and a CrewAI user both get an actionable next step, not just an abstract label). The centerpiece is the cross-framework mapping and the worked tradeoff reasoning per criterion — not another flat glossary page.

Components: a synthesized criteria rubric (distilled from the scattered single-page attempts, cross-checked against each framework's own docs); a translation table mapping the four generic patterns to each framework's concrete primitive/class name; a scoring worksheet/prompt that applies the rubric and surfaces the reasoning, not a bare label.

## Tangible Impact
**Population**: Developers who have already committed to building a multi-agent system (distinct from the audience deciding *whether* to go multi-agent at all) on one of the handful of dominant frameworks — LangGraph, CrewAI, Microsoft Agent Framework, Google ADK, strands-agents — the same cohort visible in the strands-agents docs PR, the Dojogenesis selector's GitHub traffic, and framework-specific Discord/forum threads asking "should this be a graph or a swarm."
**Mechanism**: Today a team picks a pattern by copying whatever example is closest in the docs, often locking in a Workflow when a Swarm's dynamic handoff was needed (or the reverse), discovering the mismatch only after the system is partway built and refactoring orchestration logic is expensive. A scored, reasoned recommendation applied at design time catches the mismatch before code exists, and the cross-framework mapping means the same tool is useful whether or not a team has already picked a framework.
**Measure**: (1) Share of tool users who report their initial pattern guess changed after scoring (self-reported, via a short in-tool survey). (2) Time from "task described" to "orchestration code scaffolded" for tool-guided vs. docs-browsing baseline on a set of 5-6 representative tasks. (3) Mid-build pattern-switch rate (how often a team rips out and replaces their orchestration primitive) for tool-guided vs. baseline teams, tracked over a small pilot.

## Why Now
The strands-agents docs PR landed within the last 30 days, actively patching this exact gap in prose for one framework at the same moment several other frameworks (Microsoft Agent Framework, Google ADK) are converging on the same four-pattern taxonomy — meaning a cross-framework tool now has a stable, shared vocabulary to map onto instead of chasing a moving target.

## MVP Sketch
A markdown/CLI worksheet: 5-6 structural criteria distilled from the strands-agents docs, the Dojogenesis selector, and 2-3 framework taxonomy pages, each framework's primitive-name mapping table, and a short prompt template that scores a pasted task description and returns a recommendation with reasoning. Validate by running it against 6-8 real task descriptions pulled from framework GitHub issues/discussions where someone asked "which pattern for this?" and checking whether the tool's recommendation matches what maintainers/commenters actually suggested. 1-2 weeks, 1 person.

## Risks & Open Questions
- Any single framework (or a cross-framework body like the A2A project) could publish an authoritative decision tree and absorb this — the strands-agents PR shows this is already happening piecemeal.
- The four-pattern taxonomy (Graph/Swarm/Workflow/Hierarchical) may not cleanly generalize across all frameworks' actual primitives, forcing lossy mapping.
- This sits one step downstream of "Two Yeses" (whether to go multi-agent at all) in this repo's own ledger — close enough in audience that a reviewer could see them as one product; keeping them separate is only worth it if the pattern-choice decision proves to need meaningfully different criteria in practice, which the MVP validation step should surface quickly.
- Real-world task descriptions are often messier than clean examples, and a scoring rubric calibrated on tidy GitHub-issue descriptions may not transfer to a team's actual ambiguous first draft.
