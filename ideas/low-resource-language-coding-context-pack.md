# LangPack: Context Packs That Make AI Coding Assistants Fluent in Low-Resource Programming Languages

- **Status**: PROPOSED
- **Date**: 2026-11-13
- **Topic**: Applied AI for underserved domains
- **Source**: research/2026-11-13-applied-ai-for-underserved-domains.md · P6
- **Maturity verdict**: PARTIAL — active benchmarking work exists (CangjieBench for the Cangjie language, BigCodeBench-MultiPL extending to Julia/Fortran/R, OpenAI's own MultiLangBench released Oct 2026, a Pharo code-completion benchmark) confirming and measuring the gap, but these are all evaluation efforts, not production tools that close it. - **Format**: BOTH

## The Gap
An OpenAI blog post discussed on Hacker News ("Advanced coding in low-resource programming languages," 110pts/104cmt) names the technical gap directly: mainstream AI coding tools are strong on high-resource languages (Python, JavaScript, Java) and meaningfully weaker on niche, legacy, or regional languages with little training data (COBOL, Fortran, Pharo, domain-specific languages, regional dialects of mainstream languages). A separate HN thread, "Ask HN: As developers from low-income countries, how to cope with AI replacement?" (4pts/6cmt), shows the human cost of the same gap from the other side: developers worried about being displaced by tools that weren't built with their stack or their market in mind. The benchmarks measuring this (CangjieBench, BigCodeBench-MultiPL, MultiLangBench, the Pharo benchmark) all confirm the quality gap is real and quantifiable — none of them ship a fix a working developer can use today.

## The Project
A tool that generates and maintains a "context pack" for a specific low-resource language or codebase dialect: given the language's reference documentation, style guide, and a representative sample of real code (pulled from a GitHub repo or pasted by the user), it produces a structured pack — a condensed language reference card, a list of idioms and common patterns specific to that language/codebase, a catalogue of known AI-assistant failure modes for that language (e.g., "frequently hallucinates a Python-style list comprehension that doesn't exist in this language"), and example test-harness patterns. That pack gets loaded into a coding assistant's context (as a Claude Code skill, a CLAUDE.md/AGENTS.md section, or a system-prompt injection for any other tool) to measurably lift suggestion quality for that language without any model fine-tuning. A shared, versioned registry of packs means the next team working in Pharo or COBOL or a regional DSL starts from a maintained pack instead of rediscovering the same AI-assistant failure modes from scratch.

## Tangible Impact
**Population**: Developers maintaining production systems in low-resource programming languages — concretely, this spans two overlapping groups: (1) maintainers of legacy mainframe/enterprise languages (COBOL alone reportedly still runs an estimated $3 trillion/day in transactions through legacy systems, with a documented, aging, shrinking developer workforce per multiple 2025-2026 industry reports) and (2) developers in low-income countries working in regional or niche stacks where training-data scarcity compounds existing unequal access to AI tooling, the exact anxiety raised in the digest's Ask HN thread.
**Mechanism**: Today a developer in a low-resource language gets noticeably worse AI coding assistance with no way to improve it short of writing extensive in-context examples by hand, every session, from memory. A generated, reusable context pack front-loads that corrective context once, in a form that persists across sessions and across a whole team, converting an individual's repeated manual workaround into a shared, improvable asset.
**Measure**: (1) suggestion-acceptance rate and bug-introduction rate on a held-out set of real tasks in the target language, with vs. without the pack loaded, benchmarked against one of the existing low-resource-language benchmarks (CangjieBench, BigCodeBench-MultiPL, Pharo benchmark) for an apples-to-apples score; (2) time-to-onboard a new team member onto a legacy-language codebase, self-reported before/after; (3) number of maintained, versioned packs covering distinct languages/dialects in the shared registry over time.

## Why Now
OpenAI's own framing of this as an open research problem, landing in the same 30-day window as four independent academic benchmarking efforts (CangjieBench, BigCodeBench-MultiPL, MultiLangBench, the Pharo benchmark), confirms both that the gap is real and freshly measured and that nobody has yet turned that measurement into a usable mitigation a working developer can install today — the benchmarks did the hard part of proving the gap's size; closing it with context engineering (not fine-tuning, which no small team can do per-language) is squarely buildable with current tools.

## Skill Angle
A Claude Code skill version: given a pointer to a GitHub repository (or pasted documentation/style guide/code samples) for a low-resource language or codebase dialect, the skill analyzes the corpus, identifies idioms, common patterns, and likely assistant failure modes (by probing the base model's own suggestions against the real code and noting mismatches), and outputs a structured context pack ready to drop into a CLAUDE.md or project skill. This is the one-shot pack-generation task a team runs once per language/codebase — the project is the persistent, versioned shared registry where packs get reused, benchmarked, and improved across teams instead of regenerated solo each time.

## MVP Sketch
Scope to one well-benchmarked language with an existing eval set to validate against (e.g., Pharo, using the cited Pharo code-completion benchmark, arXiv:2607.04939, as the measurement harness) and one source (a specific public GitHub repo as the corpus). Stack: GitHub API ingestion of docs/code, an LLM-driven pack-generation pipeline (extract idioms, probe for failure modes by comparing base-model suggestions against real code, draft the reference card), and a simple versioned pack format (a structured markdown/YAML file). The validating experiment: run the target benchmark's task set through the coding assistant with and without the generated pack loaded, and measure the score delta.

## Risks & Open Questions
- Data Sources: CONNECTED via the GitHub API (mature, widely used) to pull a target repo's documentation and code as the corpus — a stronger default than asking users to manually paste large amounts of reference material, with MANUAL paste as a fallback for languages/codebases not hosted on GitHub (e.g., some internal COBOL systems).
- Risk that context-pack injection alone can't close the gap benchmarks like CangjieBench measure if the underlying failure is tokenizer/training-data scarcity rather than missing in-context examples — the MVP's benchmark experiment is specifically designed to test whether this mechanism actually moves the needle before committing further.
- Legacy enterprise codebases (COBOL, mainframe systems) are often proprietary and can't be pulled via public GitHub API, meaning the two populations named in Tangible Impact may need different ingestion paths (CONNECTED for open regional/niche languages, MANUAL/on-prem for proprietary legacy systems) — worth scoping the MVP to the open-source case first.
- A shared public pack registry for proprietary/legacy codebases raises confidentiality concerns if packs are generated from real production code; the registry should default to storing only the abstracted pack (idioms/patterns/reference card), never the source corpus itself.
