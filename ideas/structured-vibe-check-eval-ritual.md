# Vibe Check, Formalized: A Git-Native Structured Eval Ritual Teams Actually Keep Using

- **Status**: EXPLORING (promoted 2026-11-13 cycle 47: evidence density — independently raised in 2 separate posts within the digest, "In defense of vibes-based evaluations" and "Vibe Checks Are All You Need," both pushing back on the same mainstream formal-evals advice)
- **Date**: 2026-11-13
- **Topic**: LLM evaluation & observability
- **Source**: research/2026-11-13-llm-evaluation-observability.md · P8
- **Maturity verdict**: PARTIAL — the vibes-vs-formal-evals debate is real and unresolved ("In defense of vibes-based evaluations," frontierai Substack; "Vibe Checks Are All You Need," olshansky Substack, both pushing back on standard "you need formal evals" advice) and a handful of small tools attempt the structured middle ground (`vibecheck`/vibescheck.io invite-only preview, Winston-503/smoleval at 1 star, zcaceres/easy-eval), but none shows adoption or active maintenance, and no credible source treats the debate as closed.
- **Format**: BOTH — the skill is Claude running a one-off structured vibe check ad hoc on a handful of outputs; the project is a minimal local CLI that persists rubric scores as git-trackable files so runs diff against each other over time.
- **Data Sources**: MANUAL — the user pastes or points to a sample of recent LLM outputs (prompt+response pairs, e.g. a JSONL export they already have from logs, a few Slack-pasted examples, or a handful of staging-run transcripts) and, for diffing, their prior run's saved rubric-scores file. Deliberately not CONNECTED to any observability platform: the entire motivating complaint is that formal eval tooling feels like too much setup overhead for the iteration speed teams actually want, so requiring a connector before first use would reproduce exactly the friction this pattern is a reaction against. A later optional CONNECTED mode pulling a recent-traffic sample from an existing trace store (Langfuse, Phoenix) is a reasonable v2, but the MVP's whole selling point is working from files a developer already has open.

## The Gap
Two independently-authored pieces found via WebSearch — "In defense of vibes-based evaluations" and "Vibe Checks Are All You Need" — explicitly argue that formal eval frameworks (datasets, judges, dashboards) are overkill for most day-to-day LLM app iteration, directly pushing back against mainstream "you need formal evals" advice circulating in the same search results. That debate itself is the evidence of a gap: no tool was found that formalizes a lightweight "structured vibe check" — something with just enough rubric and run-over-run memory to be more than a vibe, but with none of the dataset/judge/dashboard setup overhead that makes teams abandon formal frameworks in the first place. The few tools attempting this middle ground (`vibecheck`, `smoleval`, `easy-eval`) are unmaintained or require a hosted companion app, which reintroduces the exact buy-in cost the pattern is reacting against.

## The Project
A dependency-light CLI (and matching Claude Code skill) that runs a "structured vibe check": given a handful of recent prompt+response pairs, it scores each against a short, team-defined rubric (3–5 dimensions max, e.g. "correctness," "tone," "actionability"), has the developer confirm or override each score in under a minute per item, and writes the result to a single git-trackable file alongside the code. On the next run, it diffs the new scores against the last committed run and flags any dimension that regressed, surfaced as a plain-text summary a developer reads in the same breath as a `git diff`. No dataset curation, no judge-model pipeline, no dashboard — the entire tool lives in files the team already version-controls.

Components: a rubric config file (plain YAML, 3–5 dimensions); a scoring pass (LLM-assisted first-pass score, human override); a git-trackable results file per run; a diff-against-last-run reporter.

## Tangible Impact
**Population**: Solo developers and 2–6 person teams building LLM-powered features who today do pure ad hoc manual review ("looks good to me") with zero persistent record, explicitly because they've tried or looked at formal eval frameworks and judged the setup cost not worth it for their iteration speed — the exact audience the two Substack pieces are written for and defending.
**Mechanism**: Today's two options are "formal eval framework" (abandoned by this population per the pattern's own evidence) or "no record at all" (so a regression a developer half-noticed last week is forgotten by this week). A git-native structured ritual gives this population a middle rung they'll actually keep using because it costs about as much time as the ad hoc review they already do, but leaves a diffable trail that catches a regression a pure memory-based vibe check would miss.
**Measure**: (1) week-over-week continued usage on a pilot team after the first two weeks (the specific failure mode of `vibecheck`/`smoleval` was near-zero sustained adoption — beating that bar is the core test); (2) time per run, targeting under 5 minutes for a 10-sample check; (3) at least one real regression caught by the diff report that a pilot developer confirms they would have missed with pure ad hoc review.

## Why Now
LLMs cheap and fast enough to provide a usable first-pass rubric score on a handful of outputs in seconds make the "scoring" step nearly free; the real, newly-legible problem is adoption, not capability — the debate crystallizing in two dueling Substack pieces this cycle, plus three independent small tools all failing to stick, is fresh evidence that the gap is specifically about match-fit with how this population actually works (git-native, zero hosted dependency), not about a missing technique.

## Skill Angle
Trigger: a developer has just changed a prompt or model config and wants a fast gut-check before committing, without spinning up a full eval run. Inputs: a handful of fresh prompt+response pairs (pasted or from a small file) and the team's rubric file if one exists (the skill drafts a starter rubric if not). Output: a scored table per dimension with a one-line justification each, plus — if a prior run file is supplied — a flagged list of dimensions that regressed. The skill is the on-demand single-session version of the ritual; the project is the persistent CLI that makes the run-over-run file and diff a standing habit rather than a one-off ask.

## MVP Sketch
A single-file Python CLI (`vibecheck-lite` or similar, deliberately not reusing the existing unmaintained `vibecheck` name) reading a YAML rubric and a JSONL of samples, calling one LLM pass for first-draft scores, prompting for human confirm/override in the terminal, and writing a timestamped results file plus a diff against the most recent prior file in the same directory. Experiment: give it to 2–3 indie developers already doing pure ad hoc review, and check after two weeks whether they're still running it unprompted versus having dropped it — the single number that would validate or kill the whole idea.
2–3 weeks, 1 person.

## Risks & Open Questions
- The strongest reason this might be unbuildable-as-a-product: the failure mode of all three prior attempts (vibecheck, smoleval, easy-eval) is specifically abandonment, not a missing feature — this idea could fail the exact same way without a very disciplined low-friction MVP.
- "Structured enough to be useful" and "lightweight enough to stick" pull in opposite directions; getting the rubric size and scoring-time budget right is the whole bet and isn't provable without real pilot usage.
- A sufficiently motivated team could just build this themselves in an afternoon as a throwaway script, which caps how much standalone value a packaged version can add beyond convenience and the shared rubric-starter templates.
- Evidence here is two opinion pieces plus three unmaintained tools, not an engagement-dense community thread — real but comparatively thin signal, worth validating with direct outreach to the population before heavy investment.
