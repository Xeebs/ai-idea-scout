# Make It Stick: A Cross-Host Consultation-Forcing Layer for MCP Memory Servers

- **Status**: EXPLORING
- **Date**: 2026-11-20
- **Topic**: Context engineering & memory
- **Source**: research/2026-11-20-context-engineering-memory.md · P4
- **Maturity verdict**: OPEN — WebSearch confirmed the problem is widely reported (a Claude Desktop bug report of zero tool-calls to a registered memory server, a matching Cursor forum thread, several "my agent has amnesia" DEV posts) but found no packaged adapter/forcing-layer product or library, only one commenter's one-off HTTP-hooks workaround. GitHub searches for MCP memory servers return servers that store memory, not solutions to the consultation problem itself.
- **Format**: BOTH — the forcing layer itself is persistent middleware (PROJECT); diagnosing why a specific user's existing MCP memory setup isn't being consulted and drafting the host-specific fix is a separable one-shot task (SKILL).
- **Data Sources**: CONNECTED — the target MCP memory server itself (any server implementing the MCP memory/tools spec — e.g. mem0's MCP server, OpenMemory, or a custom one, all read via the standard MCP protocol) plus the host application's own extension point. Maturity varies by host: Claude Code's HTTP hooks (cited by the one commenter who fixed this for themselves) are a mature, documented extension point today; Claude Desktop and some other hosts currently expose no equivalent hook, which is itself part of the gap this project has to work around per-host rather than assume away.

## The Gap
Standing up a memory layer as an MCP server does not, by itself, make an agent reliably read from or write to it: MCP registers a tool, but nothing forces the host's system prompt or turn loop to actually call it, so the server sits unused unless the host application is separately wired to invoke it every turn. A Claude Desktop bug report documents zero tool-calls to a registered memory server across a full session; a matching Cursor forum thread and several "my agent has amnesia" DEV posts confirm this is a cross-host pattern, not a single misconfiguration. The one fix found in the wild — a commenter using Claude Code's HTTP hooks to force retrieval — is a hand-built, single-user workaround, not a packaged solution any MCP memory server author or user can adopt.

## The Project
A host-agnostic middleware layer that sits between an MCP memory server and whichever host application is running it, and guarantees the server actually gets consulted every turn regardless of whether the host's own wiring would have called it. On hosts with a hook/extension system (Claude Code's HTTP hooks today), the layer registers itself there and issues the retrieval/write calls directly, bypassing reliance on the model choosing to call the tool. On hosts without a native hook system, the layer runs as a thin proxy sitting in the MCP transport path, injecting a synthetic "check memory now" tool-call turn before the model's real turn when the host hasn't already made one recently — turning "the server is registered" into "the server was actually called this turn," the gap every cited report names.

Components: a per-host adapter registry (starting with Claude Code's HTTP hooks as the first mature target); a transport-level proxy fallback for hosts without native hooks; a per-turn consultation ledger (so a user or the memory server author can verify consultation actually happened, not just that the server is reachable); a configurable policy for how often forced consultation fires (every turn vs. on a staleness/keyword trigger, to control added latency).

## Tangible Impact
**Population**: Developers and power users who have deployed an MCP memory server (mem0's MCP server, OpenMemory, or a custom build) expecting cross-session recall, and are hitting the specific, widely-reported failure where the server is correctly registered but never actually called — the exact population in the Claude Desktop bug report, the Cursor forum thread, and the cluster of "my agent has amnesia" posts the gap-analyst verified.
**Mechanism**: Today, a correctly-configured MCP memory server provides zero practical benefit if the host's model never chooses to invoke it, and the only known fix is a hand-rolled, host-specific hook written by one person for their own setup; a packaged, host-agnostic forcing layer converts "memory server registered" into "memory server guaranteed-consulted," closing the exact gap the bug report and forum thread describe without requiring every user to discover and re-build the HTTP-hooks workaround themselves.
**Measure**: (1) Tool-call invocation rate to the memory server per session, before vs. after installing the layer, directly answering the Claude Desktop bug report's "zero calls" finding. (2) Recall accuracy on a held-out cross-session fact-recall task (ask the agent something only answerable from a prior session's stored memory), with vs. without the layer. (3) Added latency per turn from the forced-consultation check, to confirm the fix doesn't trade "never remembers" for "always slow."

## Why Now
The problem is confirmed independently across at least three channels (a filed bug report, a separate forum thread, and multiple blog posts) within the last 30 days, and Claude Code's HTTP hooks — the one proven workaround — are a mature, documented extension point today, meaning a first real adapter can ship immediately on at least one major host without waiting on any vendor to add new capability.

## Skill Angle
Given a description of a user's MCP memory server setup (which server, which host, how it's configured) plus a transcript or log showing the agent never consulted it, diagnose the likely cause (no hook wiring on this host, model simply didn't choose the tool, a misconfigured tool description discouraging invocation) and draft the specific fix — a Claude Code HTTP hooks snippet, a system-prompt nudge, or a note that this host currently has no fix short of the full proxy layer. Useful immediately for anyone hitting this today, independent of whether the packaged forcing layer exists yet.

## MVP Sketch
Build the Claude Code HTTP-hooks adapter first (the one host with a proven, documented extension point), wire it to force a retrieval call against a real MCP memory server (mem0's MCP server) at the start of every turn, and add the consultation ledger. Experiment: run a held-out cross-session recall task suite (ask 15-20 questions only answerable from prior-session memory) with the layer on vs. off, measuring tool-call rate and recall accuracy. 2-3 weeks for 1-2 people, scoped to one host before attempting the harder no-native-hook proxy fallback.

## Risks & Open Questions
- Host vendors (Anthropic, Cursor) could ship native "always consult registered memory tools" behavior directly, which would be the right fix and would make this layer's Claude Code adapter obsolete overnight — though the no-hook-host proxy fallback would likely remain useful longer.
- Forcing a consultation call every turn adds latency and token cost even when memory isn't relevant to that turn; the staleness/keyword-triggered policy is unproven and needs real tuning, not a fixed interval.
- The transport-level proxy fallback for hosts without native hooks is the harder, riskier half of this project — it may require intercepting traffic in ways a host's terms of service or sandboxing don't cleanly allow, which needs checking per host before committing engineering time.
- A single commenter's informal fix is thin evidence that the hooks-based approach generalizes cleanly beyond their specific use case; the MVP experiment is the first real test of that.
