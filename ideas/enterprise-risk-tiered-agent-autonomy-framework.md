## The Gap
The digest's WebSearch synthesis surfaced a VentureBeat-sourced claim that "the companies getting the most value from AI agents ... have drawn tighter boundaries around what agents can do alone," alongside a Gartner-sourced projection that 40% of enterprises will demote or decommission agents by 2027 because of governance gaps discovered only after production incidents — attributed to "treating governance as all-or-nothing." The digest's own engine run independently corroborates the binary-ban failure mode in the wild: Hacker News's "United Airlines bans AI agents from booking flights on behalf of travelers" (682 pts, 710 comments, 2026-11-11) and "Basically no one is using AI agents for their DoorDash orders" (178 pts, 336 comments, 2026-11-02). Risk-tiering is described everywhere as a goal companies are reaching for — no named product implements it as a usable, cross-task-type framework.

## The Project
A declarative policy engine that lets an organization define risk dimensions (reversibility, financial exposure, blast radius, regulatory sensitivity) per task type, maps each task type to one of a small set of graduated autonomy tiers (observe-only, propose-and-confirm, auto-execute-with-audit, fully autonomous), and enforces the resulting tier via middleware hooks around any agent action — instead of a single global on/off switch. An org that would otherwise ban agents entirely after one bad high-risk incident (the United Airlines pattern) can instead keep full autonomy for low-risk, reversible tasks (checking a flight status) while gating the highest-risk ones (a non-refundable purchase) behind human confirmation — with the tier assignment auditable, versioned, and immediately adjustable per incident rather than requiring a scheduled policy review or a blanket ban.

Components: a policy DSL for declaring risk dimensions and tier mappings, a tier-to-enforcement-action translator (block / confirm / audit-and-proceed / proceed), a middleware enforcement hook wrapping the agent/MCP tool-call layer, and an audit log tying every gated action to the tier and policy version active at the time.

## Tangible Impact
**Population**: Mid-size-to-large enterprises deploying AI agents for customer-facing or operational tasks (travel/logistics booking, procurement, customer support, financial transactions) that are currently choosing between unrestricted rollout and an outright ban — the exact two concrete cases the digest surfaces (United Airlines's wholesale flight-booking ban; DoorDash's near-zero AI-agent order usage) — rather than scoping agent permission by actual task risk. The cited Gartner-sourced 40%-by-2027 demote/decommission projection, while flagged in the digest as unverified secondary data, is a directional proxy for how many enterprises are on this exact collision course today.
**Mechanism**: A binary allow/ban switch forces an org to pick one extreme for every task an agent might perform, so a single high-risk incident (or just fear of one) collapses all low-risk, genuinely safe use cases along with it. A declarative, enforced tier mapping lets the same org keep agents working on the 80% of tasks that are low-risk and reversible while specifically gating the narrow slice that carries real financial, regulatory, or irreversibility exposure — turning "ban everything" into "gate the risky 20%."
**Measure**: (1) % of previously wholesale-banned use cases (replaying scenarios shaped like the United Airlines/DoorDash cases) that the framework's tiering logic would classify as safely re-enablable at a lower tier without added incident risk. (2) Incident rate observed per tier over a pilot deployment, validating that the tiering rubric's risk dimensions actually track real-world outcomes rather than being theoretical. (3) Time-to-policy-adjustment after an incident — how quickly an org can re-tier a specific task type via the policy DSL, compared to the "ban everything" default reaction time the evidence shows enterprises currently default to.

## Why Now
Three independent, dated signals converged in this single 30-day window: a concrete binary-ban incident at enterprise scale (United Airlines, 682 pts/710 comments), a concrete binary-abandonment pattern (DoorDash, 178 pts/336 comments), and an analyst-sourced governance diagnosis naming "all-or-nothing" as the structural cause. The underlying enforcement mechanism — intercepting tool calls before execution — is already a mature, stable extension point across major agent SDKs and MCP clients, so the missing piece is purely the declarative risk-tiering and policy-DSL layer on top, not new infrastructure.

## Skill Angle
Trigger: a team is about to grant an agent a new capability or task type and wants to know which autonomy tier it belongs in before writing a policy entry. Inputs: a description of the task (what the agent would do, its reversibility, financial/regulatory exposure, and blast radius if it goes wrong). Output: a recommended tier assignment with reasoning against the framework's risk dimensions, plus a drafted policy-DSL entry ready to paste into the live system — a one-shot authoring/review aid distinct from the always-on enforcement middleware.

## MVP Sketch
A policy DSL (YAML) defining risk dimensions and tier mappings, a middleware wrapper for one agent framework (e.g., the Claude Agent SDK) and direct MCP client interception as a second path, implementing the four-tier enforcement actions, plus an audit log. Experiment: construct 10–15 task-type scenarios shaped after real-world cases in the evidence (flight booking variants, food-delivery order variants, a financial-transaction variant) across a deliberate risk spread, have the framework assign tiers, and have a small panel of practitioners independently rate whether each assignment matches their own risk judgment — measuring rubric-to-practitioner agreement as the single validating experiment. 3–4 weeks for 1–2 people.

## Risks & Open Questions
- This is explicitly a governance/policy framework, not a technical capability — its value depends entirely on orgs actually adopting and maintaining the policy DSL rather than reverting to the ad hoc rules they already improvise; adoption friction is the single biggest risk.
- Risk-dimension scoring (reversibility, blast radius, regulatory exposure) is itself a judgment call that could be gamed or misjudged, especially for novel task types with no incident history to calibrate against.
- Overlaps conceptually but not substantively with `historical-risk-conditioned-autonomy-gate.md` (coding-agent-specific, PR-revert-history-driven) and `agent-individual-policy-approval-middleware.md` (indie-builder-scoped, two-mode approve-every-step vs. heavy-isolation) already in this index — this project must stay clearly cross-domain and declaratively tiered (not learned from one domain's revert history, not a two-mode indie tool) to justify a separate build.
- A well-resourced platform vendor (AWS, Microsoft, an agent-framework maker) could ship a native version of this faster than an independent project, given AWS's own architecture-blog pattern already names the probation/supervised/trusted shape; differentiation would need to be the cross-framework, cross-vendor portability of the policy DSL itself.
