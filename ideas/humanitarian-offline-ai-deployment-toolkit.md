# FieldPack: A Reusable Offline-Deployment Toolkit for Humanitarian AI Across Problem Domains

- **Status**: PUBLISHED
- **Date**: 2026-11-12
- **Topic**: Applied AI for underserved domains
- **Source**: research/2026-11-12-applied-ai-for-underserved-domains.md · P8
- **Maturity verdict**: PARTIAL — WebSearch surfaced one direct, nascent attempt (`offline-mcp` on PyPI, ~68 weekly downloads, single maintainer) and a catalog-only effort (Wakoma's "OfflineAI," a list of tools, not a toolkit); SHIFA, VectorCam, and ResQMesh AI Platform each remain independently-engineered, project-specific stacks with no shared layer between them — the gap is real but a better-resourced build would be clearly differentiated from the existing nascent attempt, not unprecedented.
- **Format**: BOTH
- **Data Sources**: MANUAL at MVP — the deploying org supplies its own model weights/config and a target-device profile (RAM, storage, connectivity tier) when packaging a deployment; this is infrastructure tooling, not a data-reading product, so there is no third-party API to connect to for the core packaging function. A CONNECTED upgrade is plausible for the sync layer specifically (reading from a Mobile Device Management API for live device-inventory data, if the deploying org already runs one), noted as a later enhancement rather than an MVP requirement.

## The Gap
SHIFA (built for Sudan, DRC, Somalia, Nigeria, Rwanda) states its own operating assumption as "internet that drops in and out, if it exists at all"; VectorCam (Visilant), a separately-built open-source smartphone tool for mosquito identification, was also built to run with zero internet access. Both solve the same zero/intermittent-connectivity, on-device-inference problem independently, in different countries and problem domains, with no shared toolkit between them in any search result — a sign each humanitarian AI project still engineers its own offline-deployment stack from scratch rather than reusing one.

## The Project
A reusable deployment layer — model packaging, intermittent-connectivity sync, and on-device inference runtime — that a humanitarian AI project in any domain (health diagnosis, disease-vector identification, crop advisory, disaster logistics) can adopt instead of re-solving "how do we run AI with no reliable internet in a crisis zone" from zero. It provides: a standard packaging format for quantized open-weight models plus their runtime dependencies, a sync protocol that queues and reconciles updates/logs over whatever connectivity window becomes available (satellite burst, occasional Wi-Fi, SMS-triggered pull) without requiring a persistent connection, and a thin inference-runtime abstraction (wrapping llama.cpp/MediaPipe/ONNX runtime) so a project swaps models without re-engineering the deployment pipeline. The toolkit deliberately doesn't build any domain logic itself — it's the plumbing SHIFA and VectorCam each built independently, made reusable for the next project instead of the fourth from-scratch build.

## Tangible Impact
**Population**: Humanitarian AI projects and the communities they serve across connectivity-constrained crisis and low-resource settings — SHIFA's own deployment footprint spans five countries (Sudan, DRC, Somalia, Nigeria, Rwanda), and the broader population is the estimated 2.6 billion people the ITU reports remain offline or on severely constrained connections globally, who are the end beneficiaries whenever a humanitarian AI project succeeds at actually deploying under these conditions.
**Mechanism**: Today, each humanitarian org building an AI tool for a connectivity-constrained setting spends a meaningful share of its engineering budget re-solving packaging and sync from scratch — time and money that doesn't go toward the actual domain problem (triage, vector identification, crop advice). A shared toolkit shifts that engineering cost from "rebuild the plumbing" to "configure the plumbing," freeing resource-constrained humanitarian tech teams to spend more of a fixed budget on the domain-specific model and evaluation work that actually determines whether the tool helps anyone.
**Measure**: (1) engineering time-to-first-working-offline-deployment for a new project using the toolkit vs. the multi-month from-scratch timelines implied by SHIFA/VectorCam's independent builds; (2) sync reliability — percentage of queued updates/logs successfully reconciled within a defined window under simulated intermittent-connectivity conditions; (3) number of independent humanitarian-AI projects across distinct problem domains adopting the toolkit within a year, the direct test of whether the "reusable across domains" claim holds in practice.

## Why Now
Quantized open-weight models now run acceptable-latency inference on commodity/field hardware, and the specific gap — a reusable packaging-and-sync layer rather than per-project bespoke stacks — is confirmed by both SHIFA and VectorCam independently needing and building the same primitives in the last cycle's search results, while the only existing attempt at generalizing it (`offline-mcp`) remains a low-adoption, single-maintainer effort a better-resourced build can clearly surpass rather than duplicate.

## Skill Angle
A Claude Code skill version: given a project's domain description, target device/connectivity profile, and chosen model, the skill drafts a tailored deployment plan — which packaging format and sync cadence to use, what connectivity-window assumptions to build around, and a checklist of field-condition edge cases to test before shipping (overlapping with, but distinct from, this digest's separate field-condition stress-test-harness idea, which actually runs the test rather than planning it). This is a one-time planning task a project runs at kickoff; the project itself is the persistent packaging/sync/runtime infrastructure the plan points toward building.

## MVP Sketch
Scope to the two highest-value pieces first: a standard model-packaging format (weights + runtime config in one versioned bundle) and a basic intermittent-connectivity sync protocol (queue-and-reconcile over whatever connection becomes available, tested against simulated satellite-burst and SMS-triggered-pull scenarios). Stack: a packaging CLI wrapping llama.cpp/ONNX runtime, a lightweight local queue (SQLite-backed) for pending syncs, and a reconciliation protocol tolerant of out-of-order or partial delivery. The validating experiment: package one real open-weight model for one humanitarian-style use case (e.g., a vector-identification classifier similar to VectorCam's), deploy it under a simulated intermittent-connectivity test harness, and confirm it packages, runs, and syncs correctly without a persistent connection.

## Risks & Open Questions
- `offline-mcp`'s existing (if low-adoption) attempt means this needs a direct technical evaluation of that project first — building a parallel, better-resourced version only makes sense if it's genuinely differentiated, not just better-marketed.
- Each humanitarian domain's actual hardware/connectivity constraints vary enough (a mosquito-ID phone app vs. a clinic-laptop triage tool) that "reusable across domains" is a claim the MVP's cross-domain test needs to genuinely stress, not assume.
- Humanitarian orgs (SHIFA, VectorCam's maintainers) may already have unpublished internal generalization efforts underway — worth direct outreach before committing significant engineering time.
- Adoption, not feasibility, is likely the real risk: a toolkit only wins if it's genuinely faster to adopt than to build in-house, which needs validating with a real second project's engineering team, not just a solo MVP demo.
