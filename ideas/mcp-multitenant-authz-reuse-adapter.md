# Tenant Bridge: A Reusable Authorization Adapter for Multi-Tenant MCP Servers

- **Status**: EXPLORING (promoted 2026-11-12: evidence density — 2 independent r/modelcontextprotocol threads two weeks apart, each hand-rolling the same bespoke per-tenant/per-call authorization scheme with no library cited by either, clearing the ≥2-thread bar)
- **Date**: 2026-11-12
- **Topic**: Tool use & MCP ecosystem
- **Source**: research/2026-11-12-tool-use-mcp-ecosystem-2.md · P2
- **Maturity verdict**: PARTIAL — gap-analyst found tenant-isolation frameworks and auth-provider docs (Descope's multi-tenant MCP reference, MCP Plexus, Sage MCP, Auth0's "treat MCP like any API" guide, Scalekit) but none ship a ready mapping from an *existing* app's authorization model onto MCP without re-issuing tokens/claims through a new provider — confirmed by two r/modelcontextprotocol builders independently hand-rolling bespoke per-call schemes two weeks apart with no library cited by either.
- **Format**: BOTH — the adapter runtime is infrastructure that must stay up and intercept every call; auditing an existing app's authorization model and drafting the adapter mapping is a separable one-shot task.
- **Data Sources**: CONNECTED — the adapter calls back into the host SaaS app's *own existing* authorization surface (a REST authz/entitlement endpoint, a Postgres row-level-security policy, or an in-process permission-check function the app already has) rather than reading any new external API. This connector is customer-specific and would need a thin reference-adapter built per common backend shape (REST authz endpoint, Postgres RLS, JWT claims) as part of this project — no single mature off-the-shelf connector covers "your app's bespoke authz model" by definition.

## The Gap
r/modelcontextprotocol, "How should multi-tenant SaaS backends expose MCP safely?" (2026-10-23): "An MCP server shouldn't create a second security model — ideally it reuses the backend identity/permissions." Twelve days later, a different builder posted their own from-scratch answer, "Multi-tenant SaaS over MCP: where each tenant, plan and cost check lives in my server" (2026-11-04), explicitly framed as answering the first post's unanswered question — "one way to do it, not the only one." Two independent teams re-derived bespoke per-call tenant/plan/cost logic inside their own MCP server code, with no shared library to reach for.

## The Project
A pluggable authorization middleware that sits in front of an MCP server's tool-call handler and, on every single call (not just at connection time), resolves the tenant and user from the incoming MCP auth context and forwards the decision to an `AuthorizationAdapter` — a small interface the host app implements once, pointing back at whatever authorization logic the app's web API already trusts. Ships with three reference adapters covering the common backend shapes found in the gap evidence: a REST-callback adapter (hits the app's existing `/authz` or entitlement endpoint), a Postgres RLS-aware adapter (runs the query as the resolved tenant/user so existing row policies apply unchanged), and a JWT-claims adapter (decodes tenant/plan/scope directly from the token MCP already carries). Per-call cost/plan metering hooks are first-class, not bolted on, since both source threads treat cost-limit enforcement as inseparable from the authorization check itself.

Components: the per-call interceptor (wraps any MCP server framework's request handler), the `AuthorizationAdapter` interface and its three reference implementations, a cost/usage metering hook, and a conformance test suite a team runs against their own adapter to verify every MCP tool call gets the same verdict their web API would give for the same tenant/user/resource.

## Tangible Impact
**Population**: Engineering teams at B2B SaaS companies adding an MCP server to an existing multi-tenant product rather than building MCP-native from scratch — the official MCP Registry already lists 20,000–30,000 servers, and multi-tenant SaaS is the dominant B2B architecture, so a meaningful and growing share of new server builders hit this exact "don't re-implement my authz model" wall, as the two independent r/modelcontextprotocol threads two weeks apart already demonstrate.
**Mechanism**: Without a shared adapter, each team either re-implements tenant/plan/cost checks by hand inside the MCP layer (duplicating and risking divergence from the web API's enforcement) or re-issues tokens/claims through a new identity provider just to bolt MCP on. A reusable adapter means every MCP tool call is checked by the exact same function the main app already trusts, so there is one source of authorization truth instead of two that can drift apart.
**Measure**: (1) Time to ship a production-ready multi-tenant MCP server, measured against the two source threads' multi-week bespoke builds as baseline. (2) Count of authorization-logic divergence bugs found between a team's web API and its MCP API in a pre/post-adoption audit. (3) % of real-world backend shapes (REST authz endpoint, Postgres RLS, JWT claims) a team can cover using a shipped reference adapter with zero custom code.

## Why Now
MCP adoption has moved from toy servers to real multi-tenant production backends fast enough that two unrelated builders solved the identical problem from scratch two weeks apart on the same subreddit in late 2026, with every auth-vendor response so far requiring a new token-issuing layer rather than reusing what the app already has.

## Skill Angle
Given a description of an existing app's authorization model (its data model, the permission checks its web API already runs, and its tenant/plan structure), produce a drafted adapter mapping: which of the three reference adapter shapes fits, what the per-call check function signature should look like, and a flagged list of tool calls in a proposed MCP tool manifest that would need cost/plan metering versus a plain allow/deny. This is the exact analysis the project's conformance suite later tests against, done once by hand before any runtime code is written.

## MVP Sketch
A TypeScript middleware package wrapping the official MCP SDK's server request handler, with the `AuthorizationAdapter` interface plus the REST-callback and JWT-claims reference adapters built first (Postgres RLS adapter as a stretch goal). Experiment: wire it in front of a toy multi-tenant SaaS app (e.g., a simple ticketing app with existing REST-API role checks) and verify every MCP tool call gets identical allow/deny results to the equivalent REST call, across a matrix of tenant/role/resource combinations. 3–4 weeks for 1–2 people.

## Risks & Open Questions
- Every host app's authorization model is different enough that "pluggable adapter" risks becoming "write custom code anyway" — the value only holds if the three reference shapes cover a real majority of cases, which needs validating against more than the two source threads.
- A well-resourced auth vendor (Auth0, Descope, Scalekit) could ship a true reuse-the-existing-model adapter faster than an independent OSS project gains adoption — their current docs still require re-issuing tokens, but that's a product decision, not a technical limitation.
- Per-call authorization checks add latency to every tool call; the middleware needs a caching story that doesn't reintroduce stale-permission bugs.
- If the official MCP spec itself standardizes an authorization-passthrough pattern, a third-party adapter's differentiation narrows to the reference-adapter library alone.
