# Pocket Vault: A Turnkey, Zero-Server Embedded RAG Toolkit for Privacy-First Local Apps

- **Status**: PROPOSED
- **Date**: 2026-11-14
- **Topic**: RAG techniques
- **Source**: research/2026-11-14-rag-techniques.md · P4
- **Maturity verdict**: PARTIAL — the gap-analyst found that the individual building blocks are mature and maintained (PGlite, ElectricSQL's WASM build of Postgres with pgvector support, under 3MB gzipped; VecLite/EdgeVec for WASM vector search in IndexedDB; the academic MeMemo on-device retrieval work), but no single maintained product assembles them into a turnkey "full RAG stack, zero server, one file" experience. The cited Show HN, Db4, is a brand-new 3-point release that requires manual assembly of its own pieces, not a packaged toolkit.
- **Format**: PROJECT
- **Data Sources**: MANUAL — the host app's own local files, notes, or transcripts, loaded directly from the device's own storage into the embedded index by the toolkit at runtime. By design, no cloud API, external connector, or network call is ever made during indexing or query — that is the entire point of the gap this closes (see Why Now). A CONNECTED version would defeat the purpose: the moment this toolkit calls out to a cloud embedding API, it stops being the thing teams in this gap are asking for.

## The Gap
Hacker News Show HN "Db4 is open source: local RAG on Postgres in a browser tab" (lab4.app, 2026-10-21, 3 points) and a WebSearch-corroborated hit about "Sub-Millisecond RAG on Apple Silicon. No Server..." both frame the same recurring, still-niche desire: a full RAG stack (storage + embedding + retrieval) that runs inside one local process or browser tab, with no server and no separate vector database to provision. Mainstream RAG tooling (LangChain/LlamaIndex plus a hosted vector DB) is built for the opposite assumption. The building blocks to do this properly now exist and are maintained, but nobody has packaged them into a one-import, zero-config library — every attempt so far is either a brand-new point-solution demo or requires hand-assembling several separate WASM primitives.

## The Project
Pocket Vault is a single importable package (an npm module, with a Python/PyInstaller-friendly equivalent) that bundles PGlite+pgvector for storage/retrieval with a small local embedding model compiled to WASM/ONNX, exposing exactly two calls — `index(docs)` and `query(text)` — with zero servers, zero cloud calls, and zero separate vector-DB provisioning. The novel pattern is the centerpiece, not a bolt-on: today, adding semantic search to a local-first app means either standing up a hosted vector DB (breaking "your data never leaves this device") or hand-wiring 3-4 separate WASM libraries together, which is exactly the toil Db4's Show HN and the broader WebSearch thread are reacting to. Components: (1) a PGlite+pgvector storage layer, (2) a bundled, license-clear small embedding model (e.g. an MIT/Apache ONNX build of a MiniLM-class model) running entirely in-process, (3) a thin, zero-config API surface, (4) a packet-capture CI test proving zero outbound network calls during indexing/search.

## Tangible Impact
**Population**: Developers of local-first, privacy-marketed personal-data apps — journaling apps, private case-note tools used by therapists and legal-aid caseworkers, and offline research/notebook apps used by field journalists and human-rights documentarians working in low-connectivity or surveillance-risk contexts — who today cannot add semantic search/RAG to their app without either breaking their own "nothing leaves this device" promise (by calling a cloud embedding API) or skipping semantic search entirely.
**Mechanism**: Supplying one importable, zero-config package closes the gap between "we market zero-data-egress" and "we actually built it that way." A team that previously had to choose between no semantic search or a quiet privacy compromise can now ship real semantic search over the user's own documents with a verifiable guarantee that nothing leaves the device — which matters concretely for end users handling therapy notes, legal case files for self-represented people, or interview transcripts in contexts where a leaked cloud API call could expose a source.
**Measure**: (1) integration time/LOC to add working semantic search to an existing local-first app (target: under 1 day / under 50 lines, vs. the multi-day vector-DB-provisioning status quo); (2) a CI-enforced, packet-capture-verified zero outbound network calls during indexing and search; (3) adoption — number of local-first app projects that integrate the toolkit within 6 months of release, and whether any publicly cite it as what let them ship a "fully offline, zero cloud calls" feature.

## Why Now
PGlite matured through 2026 into a genuinely small (under 3MB gzipped), actively maintained WASM Postgres build with first-class pgvector support, and small embedding models are now good and compact enough to run via ONNX/WASM without a GPU. The last-30-days Db4 Show HN and the WebSearch-surfaced "sub-millisecond RAG on Apple Silicon, no server" discussion both show renewed community pull toward exactly this pattern within the last month — but each is a point solution or demo, not a packaged library, which is the window this project fills before someone else does.

## MVP Sketch
Build the npm package wrapping PGlite+pgvector for storage with a bundled small ONNX embedding model, exposing `index(docs)` / `query(text)` with zero config. Validate by porting one existing small open-source local-first note-taking app to use it instead of its current (or absent) search, and measuring: integration time, and a packet-capture test confirming zero network calls during indexing/search. Target: 2-4 weeks, 1-2 people.

## Risks & Open Questions
- WASM-compiled embedding inference may be too slow or too large (model size) for low-end or older devices — needs real benchmarking before claiming broad device support.
- pgvector's ANN search inside PGlite likely won't scale past a few thousand chunks — this toolkit should be explicitly scoped to "personal" corpus sizes (single user's own notes/documents), not enterprise-scale RAG, and that scoping should be stated up front, not discovered by a disappointed adopter.
- The strongest reason this might already be solved: if Db4 itself gains traction and its maintainer packages it properly over the next few months, this idea is redundant — worth re-checking Db4's repo trajectory before committing to a from-scratch build.
- Competing WASM vector-search projects (VecLite/EdgeVec) could assemble a competing packaged offering first; differentiation should lean on the bundled embedding model and zero-config developer experience, not raw vector-search benchmark numbers.
- Needs to verify, before build, that a suitably small (under ~50MB) and permissively-licensed ONNX embedding model actually exists and bundles cleanly — if not, the "one import, no setup" promise breaks.
