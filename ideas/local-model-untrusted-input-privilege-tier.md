# Low Trust Tier: A Capability-Restriction Policy Engine for Local Models Processing Untrusted Input

- **Status**: PROPOSED
- **Date**: 2026-11-14
- **Topic**: Small & local models
- **Source**: research/2026-11-14-small-local-models.md · P5
- **Maturity verdict**: PARTIAL — adjacent, real implementations exist for agent privilege separation generally: Simon Willison's Dual LLM pattern, a 2026 arXiv type-directed privilege-separation paper (arxiv.org/html/2509.25926v1, reports driving attack success to zero in its case studies), a three-tier provenance-based hierarchy paper (arxiv.org/pdf/2606.19660), and OS-level tool allow-lists (Claude Code's `--tools`/`--disallowedTools`, Sophos's "nono"). None of these is specifically framed around small/local models needing a lower default tier because they're more injection-prone — that framing remains one practitioner's write-up, not a named reusable library.
- **Format**: BOTH — the policy engine that intercepts and restricts tool calls at runtime is persistent infrastructure; auditing a described agent stack's tool grants against untrusted-input exposure is a one-shot review task.
- **Data Sources**: CONNECTED — intercepts the agent framework's existing tool-dispatch layer (LangChain/LangGraph callback hooks, or an MCP server's tool-call boundary) to enforce tier restrictions in-process; both integration points are mature, documented today. No external data is pasted — the policy acts on calls the stack is already making, tagged with which input source (web fetch, email, user upload vs. the operator's own instruction) triggered them.

## The Gap
A production-focused practitioner write-up states plainly that small local models "are more prompt-injection-prone, so they shouldn't get high-privilege tools while processing untrusted input" — a hard-won lesson from a team whose debugging time on silent local-model failures exceeded the API costs it was meant to save (see the related P7 gap in this same digest). This appears only as a one-team retrospective, not as a named framework, checklist, or library: no reusable privilege-tiering implementation targeting small/local models specifically was found in the search.

## The Project
A tool-privilege-tiering middleware that sits at an agent stack's tool-dispatch boundary and restricts which tools a local model is allowed to invoke based on the trust provenance of its current input — e.g., a request derived from a fetched web page, an inbound email, or an untrusted file upload is capped at a "read-only / no side effects" tier regardless of what the model outputs, while a request originating from the operator's own direct instruction gets the full tool set. This is deliberately a different, complementary layer to content-based injection detection (classifiers, decoys): it assumes detection will sometimes fail and limits blast radius structurally, so a successful injection still can't reach a dangerous tool. It differs from this digest's separate hardening-sidecar idea for small models (which screens *content* for injection attempts) by restricting *capability* instead — the two are meant to stack, not compete.

Components: a provenance tagger that marks each inbound context chunk with its trust source; a declarative tier policy (e.g. YAML mapping trust tier → allowed tool set); an enforcement hook at the tool-dispatch boundary for common local-agent frameworks (LangChain/LangGraph, a raw Ollama-backed loop); an audit log of every tier-driven block.

## Tangible Impact
**Population**: Developers and small teams running local-first agent stacks (home-lab automations, browser-extension page-summarizers, local email-triage agents) that feed untrusted external content — fetched web pages, inbound emails, uploaded files — directly into a small local model that also has tool access (send email, write files, make API calls). This is the same self-hosting population behind r/LocalLLaMA's 680k+ members, specifically the subset wiring a local model into any workflow that both reads untrusted content and holds tool access — exactly the combination the cited practitioner write-up flags as under-protected.
**Mechanism**: Today these builders either accept the exposure (no tiering at all) or hand-roll a one-off "don't let the model call X when Y" check per deployment, as the cited team did before abandoning local automation entirely. A reusable tiering layer gives them a drop-in, declarative way to cap tool access by input provenance, so a successful injection — even one that evades whatever content filter is in front of it — still can't trigger a high-privilege action.
**Measure**: (1) containment rate — the share of a red-team suite's successful injections (ones that do manipulate the model's output) that are still blocked from reaching a high-privilege tool, target near-100% for correctly-tiered inputs; (2) false-restriction rate on benign requests that genuinely need a high-privilege tool from a low-trust-tagged context; (3) added latency per tool call from the enforcement hook, target single-digit milliseconds.

## Why Now
Small-local-model-in-agent-stack architectures are scaling fast enough in the last 30 days to generate their own dedicated cost-tactics and hardening discussion (per this digest's P1 and the companion small-model-hardening idea), and the underlying privilege-separation research (type-directed separation, provenance hierarchies) was published recently with case-study results showing the structural approach works — but it has not been packaged as something a small-model builder can just install, and the risk it addresses is growing alongside the pattern, not shrinking.

## Skill Angle
Trigger: a developer has described their local-model agent stack (which inputs are untrusted, which tools it can call) and wants to know where it's exposed before building any enforcement. Inputs: a description of the stack's tool list and which inputs feed it (fetched content, email, user instruction). Output: a flagged list of every tool a low-trust-tagged input path can currently reach, with a recommended tier assignment per tool — a one-time audit, separate from deploying the actual middleware.

## MVP Sketch
A Python middleware wrapping tool dispatch in a LangChain/LangGraph agent: tag each context chunk's source at ingestion, enforce a two-tier policy (trusted/untrusted → full tool set / read-only tool set) via a declarative YAML file, and log every block. Experiment: build a small email-triage agent with both a destructive tool (send-reply) and a read-only tool (summarize), run a public prompt-injection test suite against emails as the untrusted input, and confirm the tier restriction blocks 100% of attempts to trigger send-reply from email-sourced content while a direct operator instruction still can. 2–3 weeks, 1 person.

## Risks & Open Questions
- Provenance tagging through an LLM call is leaky in the same way taint-tracking is for multi-agent systems: the model can paraphrase untrusted content into something that looks operator-originated if context isn't carefully segmented at the prompt-construction layer, not just logically labeled.
- Overly coarse tiers could break legitimate workflows that genuinely need a tool triggered from untrusted content (e.g., "read this email and file a support ticket about it") — the policy needs an escalation path, not just a hard block.
- A well-resourced framework (LangChain, Ollama's own agent tooling) could ship this as a built-in feature, since the underlying primitive (tagging source + gating tool calls) is not exotic engineering.
- Demand evidence is currently one practitioner's retrospective, not a wave of independent complaints — worth validating with a second source before over-investing past the MVP.
