# Budget Lock: A Local-First Agent Orchestrator With Crash-Survivable Hard Spend Caps

- **Status**: PROPOSED
- **Date**: 2026-11-20
- **Topic**: Agentic AI & autonomous agents
- **Source**: research/2026-11-20-agentic-ai-autonomous-agents.md · P4
- **Maturity verdict**: PARTIAL — `gh search repos` for "local agent orchestrator spending limit" / "agent crash recovery checkpoint budget" and a direct repo lookup on the one named indie project ("Irrigator") returned zero matching projects — it has no visible GitHub presence beyond a single low-engagement (3pt) HN post and a landing page. Dev-blog search confirms the specific combination is a known, named pain point ("budgets reset on crash") with checkpointing frameworks like LangGraph/Temporal restoring *state* but explicitly not *spend counters*. One early, unverified solo implementation plus a vaguely-mentioned "AgentGuard" exist, but neither is mature or evaluated.
- **Format**: BOTH — the always-on local orchestrator with a durable spend ledger is persistent runtime infrastructure; reviewing a planned task's step list and recommending checkpoint placement plus a spend-cap schedule before committing to the full runtime is a separable one-shot design task.
- **Data Sources**: BOTH apply differently by half — the **project** is CONNECTED: it wraps the local agent loop's own LLM provider API calls (reading the token-usage/cost fields every major provider's API response already returns — Anthropic, OpenAI, local-model token counts) and persists checkpoint + spend-ledger state to local disk (SQLite or an embedded file store). The usage-reporting fields it reads already exist maturely at every provider; what's missing is a connector that treats that usage data as a durable, crash-surviving budget counter rather than a per-request log line. The **skill** is MANUAL: the user pastes their planned agent task's step list and a rough per-step cost estimate for a design review.

## The Gap
A solo indie launch, "Irrigator: Local AI agent orchestration with recovery and spending limits" (Hacker News, 2026-11-16, 3pts), packages exactly this combination as its pitch — a brand-new, low-engagement Show-HN-style project rather than a feature of any existing major framework, itself a signal that nobody has shipped this well yet. Dev-blog commentary independently corroborates the gap from the other direction: checkpointing frameworks (LangGraph, Temporal) restore an agent's *execution state* after a crash, but explicitly do not restore or persist a *spend counter* — so a runaway local agent loop that crashes mid-run and auto-resumes can silently reset its budget tracking and blow past an intended dollar cap on the very next run, with no framework-level protection against it.

## The Project
A local-first orchestrator — runs on the developer's own machine, not a hosted service — that wraps an agent loop with two coupled guarantees: automatic recovery from a mid-task crash (resuming from the last checkpoint rather than restarting from zero), and a hard, persistent dollar-spend cap per run/task that survives that crash. The centerpiece is the coupling: today's checkpoint-and-resume tools treat "what the agent was doing" and "how much it has spent so far" as two separate concerns, and only the first one survives a crash. This project makes the spend ledger itself part of the durable checkpoint — so a crash-and-resume cycle can never reset the budget clock, and a loop that's already near its cap resumes still near its cap, not at zero.

Components: a local task-runner wrapping any LLM provider's API calls to read per-call token/cost usage; a durable checkpoint store (SQLite) recording both execution state and cumulative spend together, written atomically per step; a hard-cap enforcement check that refuses to issue the next LLM call once the persisted spend ledger would exceed the configured limit, even on a freshly-resumed process; a crash-recovery runner that restores both state and spend together on restart.

## Tangible Impact
**Population**: Indie developers and hobbyists running self-hosted, local-first agentic automation on personal machines — overnight scraping/research loops, personal coding-agent batch jobs, home-lab automation — rather than enterprise teams with ops budgets and hosted-platform safety nets. This is the self-hosted/local-first agent-builder community (Ollama alone reports roughly 8.9 million monthly active developers as of July 2026 per TechCrunch, a meaningful fraction of whom are experimenting with agentic, not just chat, loops), a population that today has no equivalent to a hosted platform's built-in spend alerts and relies entirely on hand-rolled scripts.
**Mechanism**: Today a local agent loop that crashes mid-task either loses all progress (restart from zero, re-paying every already-completed step's cost) or resumes via a checkpoint that restores *what it was doing* but not *how much it has already spent* — so a developer who set a $5 cap can wake up to a bill well past $5 because each crash-and-resume cycle silently reset the counter to zero. Coupling the spend ledger to the same durable checkpoint as execution state closes that gap directly: the cap holds across any number of crashes, because the ledger never resets without the developer explicitly resetting it.
**Measure**: (1) Total spend on a simulated long-running task deliberately crashed and resumed 5+ times, confirming it stays within the configured cap versus a baseline checkpoint-only tool (e.g. a bare LangGraph checkpointer) that resets the counter each time. (2) Task progress recovered after a crash (percentage of completed steps not re-run), to confirm recovery quality isn't sacrificed to add the spend guarantee. (3) Time-to-first-overspend-incident reported by pilot users, before vs. after adoption.

## Why Now
Local-first agent orchestration tools are proliferating fast enough in 2026 that a solo developer felt the combination worth launching as a named product (Irrigator) within the last 30 days, and every major LLM provider's API already returns per-call token/cost usage in its response — the raw data needed to build a durable spend ledger exists maturely today; what's missing is the discipline of persisting it alongside checkpoint state rather than as an ephemeral in-memory counter, which requires no new model capability.

## Skill Angle
Given a pasted description of a planned agentic task's step list and a rough per-step cost estimate, recommend where checkpoints should be placed (before/after which steps), what a sane hard spend cap would be given the task's expected total cost, and flag any step whose failure-and-retry pattern could silently blow past that cap if spend tracking isn't made durable — a design-time review useful before committing to building or adopting the full runtime.

## MVP Sketch
2–3 weeks, 1–2 people: build a thin wrapper around one LLM provider's API (Anthropic or OpenAI) that logs every call's token usage into a SQLite ledger keyed by task-run ID, checkpoint both execution state and the running total together after every step, and enforce a hard stop once the ledger would exceed a configured cap. Experiment: run a multi-step synthetic task, kill the process mid-run at 3 different points, and confirm the resumed run's spend ledger picks up exactly where it left off rather than resetting — if a single crash-resume cycle ever loses track of prior spend, the core guarantee has failed and the design needs rework before anything else is built on top of it.

## Risks & Open Questions
- Thin evidence: a single 3-point HN post is weak demand signal on its own; the dev-blog corroboration of "checkpoints don't restore spend counters" as a named pain point is the stronger half of the case, and should be validated with a few direct practitioner interviews before a heavier build.
- A well-resourced local-orchestration project (or a future LangGraph/Temporal release) could ship a durable spend-ledger feature directly, since the underlying data (per-call usage) is already theirs to instrument — differentiation has to come from the crash-coupling guarantee being load-bearing and tested, not just claimed.
- Atomic, crash-safe writes to the combined state+spend checkpoint are the hardest engineering piece (a partial write on crash could corrupt the ledger in the wrong direction, either resetting it or double-counting); this needs real failure-injection testing, not just happy-path demos.
- Cost visibility varies across providers and local-model setups (a self-hosted model has no per-call dollar cost at all, only compute time) — the hard-cap mechanism needs a sane fallback (e.g. a wall-clock or compute-unit cap) for setups where dollar cost genuinely isn't metered.
