## The Gap
Google Research's own blog names "the accessibility gap — the delay between the release of a new feature and the creation of an assistive layer for it" — as a problem its own framework is only beginning to address, not a solved one. Separately, an independent analysis of NVDA's 2026 roadmap (integrating LLMs directly into the open-source screen reader) calls it "the most consequential technical shift this year," while noting the most transformative commercial accessibility products "carry price points that limit adoption." The American Foundation for the Blind explicitly warns that AI-driven "overlay" fixes are often low-accuracy and conflict with users' own assistive tech — meaning the few shipped point-solutions (alt-text generators) don't generalize, and no mature middleware fills the window between a feature shipping and its vendor's own accessibility team catching up.

## The Project
A browser-extension-based middleware that watches a web application's live DOM for new or changed interactive elements — a newly-added button, modal, data table, or custom widget lacking proper ARIA roles/labels — and, using a vision-language model given a screenshot of the element plus its surrounding DOM context, generates a patch: missing ARIA roles, labels, live-region announcements, or caption hooks, injected client-side so a screen reader or captioning tool picks it up immediately, without waiting for the vendor's own accessibility team to ship a fix. Every auto-generated patch is logged with a confidence score and surfaced to the user as a reviewable, toggleable layer (never silently overriding the vendor's own markup if one later ships), directly answering AFB's warning that low-accuracy overlays must not conflict with a user's existing assistive tech.

## Tangible Impact
**Population**: Blind, low-vision, and deaf/hard-of-hearing users of mainstream web applications during the specific window between a new feature's release and its vendor's own accessibility fix — a population the WHO estimates at over 2.2 billion people globally with some form of vision impairment and 430 million with disabling hearing loss, concentrated here on the subset actively using screen readers (NVDA, JAWS, VoiceOver) or live-caption tools on apps that update frequently (SaaS dashboards, social platforms).
**Mechanism**: Today, when a vendor ships a new UI feature, assistive-technology users are locked out of it entirely until the vendor's own team notices and remediates — Google's own framing of this as an unsolved "gap," not a historical one. A middleware that auto-patches the missing layer within minutes of a DOM change collapses that window from weeks/months (the typical vendor remediation cycle) to effectively zero, without requiring the vendor to do anything.
**Measure**: (1) median time from a new UI element appearing to a usable auto-generated accessibility patch being available, vs. the vendor's own historical remediation-cycle time for comparable past features; (2) screen-reader task-completion rate on patched vs. unpatched versions of the same new feature, tested with real assistive-tech users; (3) patch accuracy rate (correct role/label/announcement) against a human accessibility-expert-labeled test set, directly addressing AFB's low-accuracy-overlay concern.

## Why Now
NVDA's 2026 roadmap integrating LLMs directly into the open-source screen reader, described by independent analysis as "the most consequential technical shift this year," confirms the underlying capability (an LLM reasoning about accessible markup in real time) is now mature enough to ship — and Google's own blog naming the gap as unsolved within the last 30 days signals even well-resourced teams haven't closed it yet, leaving an open window for a vendor-agnostic, browser-side version before any single platform's proprietary framework becomes the de facto standard.

## Skill Angle
A Claude Code skill version: a developer pastes the HTML (or a screenshot) of a specific new UI element they're about to ship, and the skill returns a reviewable diff — the specific ARIA roles, labels, and live-region markup it's missing, with suggested additions — as a one-time pre-release accessibility review a team runs in their own workflow. This differs from the project, which is the always-on, live-DOM-watching runtime that patches already-shipped features for end users in real time; the skill is a shift-left design aid for teams who want to catch the gap before release, not after.

## MVP Sketch
Scope to one widget category first (custom interactive components lacking ARIA roles — buttons, toggles, modals — since these are the most common and highest-impact screen-reader blockers) and one target app the team controls or has permission to instrument. Stack: a Manifest V3 browser extension with a MutationObserver-based content script, a vision-language model call per newly-detected element, and a lightweight local patch-injection layer (ARIA attribute insertion via the DOM). The validating experiment: instrument one real, frequently-updated web app, let it run for two weeks, and have a screen-reader user attempt the newly-patched features, comparing task completion against the unpatched baseline.

## Risks & Open Questions
- AFB's specific warning — that low-accuracy AI overlays can conflict with a user's own assistive tech — is the central risk this project has to design against from day one, not discover later; the reviewable/toggleable patch layer is the mitigation, but it needs real assistive-tech-user testing before claiming it works.
- A vision-language model generating ARIA semantics from a screenshot alone (without deeper app context) may miss functional intent (e.g., what a custom widget actually does), producing technically-valid but behaviorally-wrong labels.
- Browser-extension-based middleware can't reach native mobile apps, which is where a large share of assistive-tech usage actually happens — the MVP's web-only scope is a real limitation, not just a starting point.
- Strongest reason this might already be solved: an overlay vendor (accessiBe-class) may already attempt something close to this under the hood — worth a direct technical trial against a real inaccessible feature before assuming this is unbuilt, especially given AFB's overlay criticism is aimed at exactly that category of product.
