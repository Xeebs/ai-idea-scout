- **Format**: BOTH
- **Data Sources**: CONNECTED — the runtime middleware hooks directly into a voice-agent framework's own tool-execution and TTS-playback-queue events (LiveKit Agents or Pipecat Python SDKs, both mature and widely deployed today) to observe when a tool call is dispatched, how long it has been pending, and when barge-in occurs. No audio or transcripts are pasted during operation; the framework SDKs already exist, the sequencing policy engine is the new piece.

## The Gap
Hugging Face's "Voice Agent Latency Playbook" frames playing a short filler/holding phrase during an in-flight tool call as a standard production workaround; Soniox's voice-agent-tool-calling wiki and a Speechify post both independently describe tool-call silence as a recurring pain point, and a Netguru article notes "why is my bot slow when the model is fast" as a recurring complaint. Every source describes the same fix — don't let dead air during a slow backend call read as broken — but every source also describes it as something each team wires up itself: what sound, when to trigger it, how to sequence it with barge-in. No reusable, cross-framework primitive exists; it's reinvented per project.

## The Project
A middleware library that watches a voice agent's tool-execution lifecycle and, once a configurable latency threshold passes (e.g. 700ms) without a result, starts a contextually appropriate spoken filler ("let me check that for you," "one moment while I pull that up" — not a generic beep) via the agent's existing TTS pipeline. It cancels the filler instantly on two triggers: the tool call resolving, or the caller barging in — the two failure modes that make filler audio feel broken if mishandled are "it's still talking after I interrupted" and "dead air returned because the filler never started." Phrase selection is tool-category-aware (lookup vs. transaction vs. search) and escalates ("still working on it...") if the wait runs long, instead of looping the same clip.

Components: a per-tool latency-threshold watcher, a contextual filler-phrase library (configurable per deployment/language), a barge-in/completion cancellation hook, and a telemetry log of filler-onset timing and cancellation correctness for post-call debugging. The library ships thin adapters for LiveKit Agents and Pipecat, matching the plugin footprint of this repo's own published `voice-agent-speculative-tool-calling-middleware` (Speculate) — this project is explicitly a complementary fallback for tool calls that can't be sped up or predicted (a slow third-party API with no useful partial-transcript signal), not a competing fix for the same latency Speculate already targets by firing calls early.

## Tangible Impact
**Population**: callers to AI voice agents whose calls invoke at least one backend lookup or transaction with latency the system can't eliminate — insurance claims intake, order-status checks, benefits-eligibility lookups — within the segment Forrester's 2026 Wave research reports now carries roughly 19% of inbound contact-center volume (up from 6% in 2024), where 79% of callers still say they'd rather talk to a human, meaning every stretch of unexplained silence reinforces that preference.
**Mechanism**: an unfilled silence during a slow tool call reads to a caller as "the bot is broken" or "the call dropped," driving early hang-ups and repeat calls; a correctly sequenced filler phrase signals the system is still working, reducing the perception of failure without changing the underlying backend latency at all — a cheap fix for calls where the latency itself genuinely can't be removed.
**Measure**: call-abandonment rate during tool-call-pending segments before vs. after adoption; caller perceived-naturalness/satisfaction score on an A/B pilot comparing filler-on vs. silent calls; rate of cancellation-correctness failures (filler audio still playing after barge-in or after the tool result returns — target near zero in a labeled test suite).

## Why Now
Streaming, low-latency TTS makes on-the-fly contextual filler generation (not canned pre-recorded clips) cheap enough to run per-call, and current voice-agent frameworks (LiveKit Agents, Pipecat) now expose the tool-execution and barge-in hooks a sequencing policy needs to time filler injection precisely. The volume of independent 2026 vendor blog posts (Hugging Face, Soniox, Deepgram, getstream.io, AWS Builder) each re-explaining a bespoke version of this same pattern is itself the signal that it's ripe for a shared, reusable primitive instead of another one-off recipe.

## Skill Angle
A companion skill, "filler coverage designer," takes a pasted tool manifest (function names plus typical/observed latency ranges per tool) and produces: which tools cross the filler-worthy latency threshold, a recommended phrase set per tool category, and the barge-in/completion cancellation policy to wire into the runtime middleware. This is the one-time design decision a team makes before touching code; the project is the live engine that executes the resulting policy during real calls.

## MVP Sketch
Build a Pipecat or LiveKit Agents plugin: a latency-threshold watcher on tool-execution events, a small library of 5-10 contextual filler phrases spanning common tool categories, and streaming-TTS playback that starts mid-wait and cancels immediately on tool completion or barge-in. Test against ~20 simulated calls with artificially delayed tool calls at varying latencies. The single experiment: does adding filler audio to a latency-injected test corpus measurably lower a labeled panel's "this feels broken" ratings compared to raw silence, without introducing new audio-glitch or overlap complaints?

## Risks & Open Questions
- Poorly tuned filler audio can feel patronizing or robotic and make the experience worse than silence — this needs real listener testing, not just engineering correctness on cancellation timing.
- Must stay clearly positioned as complementary to speculative tool-calling (this repo's own published Speculate idea), not a competing fix for the same latency — the differentiator is covering calls speculation can't help (truly unpredictable, un-speedupable third-party latency).
- A framework vendor (LiveKit, Deepgram) could ship its own opinionated filler feature before an independent library gains adoption; differentiation has to be the pre-built, tool-category-aware phrase libraries and cross-framework sequencing policy, not just "play a sound."
- Depends on barge-in detection itself being reliable (a documented adjacent gap elsewhere in this digest); if barge-in detection lags, filler audio risks talking over a caller who already started speaking.
