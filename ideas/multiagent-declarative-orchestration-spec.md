# Contract Layer: A Declarative Orchestration Spec and Static Validator for Multi-Agent Pipelines

- **Status**: EXPLORING (promoted 2026-11-13 cycle 42: evidence density — ≥2 independent threads, talvinder.com, ice-ice-bear.github.io, and dev.to all independently naming the same missing-contract-layer gap, corroborated by OpenAI's Symphony as a narrow but real shipped precedent)

- **Maturity verdict**: PARTIAL — WebSearch found OpenAI shipped a real, named spec in this space (Symphony, Apache 2.0, announced on openai.com), but it's narrow: a Linear-only adapter for polling an issue tracker, claiming issues, and running per-issue coding-agent sessions, not a general declarative contract layer for arbitrary agent input/output/failure-handling. `gh search repos "orchestration spec agents"` and "declarative multi-agent orchestration spec" returned no general-purpose implementation. Three independent opinion/analysis pieces (talvinder.com, ice-ice-bear.github.io, dev.to) argue the general layer *should* exist, none point to one that does.
- **Format**: BOTH — the validator/runtime is PROJECT-shaped infrastructure, but drafting a contract spec for an existing hand-coded pipeline (given a description of its agents) is a separable one-shot drafting task.
- **Data Sources**: MANUAL — the user authors or pastes a spec file (in the project's declarative DSL) describing each agent node's expected input schema, output schema, and failure-handling policy; for the skill companion, the user instead pastes a description of their existing pipeline (what each agent consumes and produces, in prose or source excerpt) and gets a drafted spec back. Upgrade path noted in Risks: a later version could statically analyze a user's own LangGraph/CrewAI source files directly (standard AST parsing of files the user already has, not an external API) instead of requiring a hand-authored spec, but that auto-derivation is out of scope for the MVP.

## The Gap
Three independent 2026 analysis pieces argue the same thing from different angles: talvinder.com's "Orchestration Specs Like Symphony Are the Missing Layer for Multi-Agent Engineering" names the missing layer explicitly; ice-ice-bear.github.io's "Why Multi-Agent Orchestration Doesn't Work Well" and dev.to's "Multi-agent orchestration is just hope masquerading as architecture" both independently argue current orchestration fails not because individual agents are weak but because the hand-coded connections between them compound failures with no checkable contract. OpenAI's own Symphony proves the idea is buildable and valuable enough to ship — but only for one narrow case (Linear issue polling), leaving the general ask (a machine-checkable contract for arbitrary agent-to-agent input/output/failure-handling) still open.

## The Project
A declarative specification format plus a static validator for multi-agent pipelines: each agent node declares its expected input schema, its guaranteed output schema, and its failure-handling policy (retry-with-backoff, escalate-to-human, abort-pipeline, fall-back-to-default) in a small DSL (YAML or a typed Python builder). A validator checks, before the pipeline ever runs, that every node's declared inputs are actually satisfiable by its upstream nodes' declared outputs — including on each declared failure path, not just the happy path — and fails the build with a specific, located error if not. The spec is the centerpiece, not a wrapper around an existing framework: it's a contract layer any orchestration framework's runtime can be made to enforce, the same role OpenAPI plays for REST APIs or a type system plays for function calls, but for the connections between agents instead of the agents themselves.

Components: a spec DSL and parser; a static compatibility checker (input/output schema matching across every edge, including failure edges); a CI-runnable validation command; a thin runtime adapter for one framework first (LangGraph) that enforces the contract live and rejects a non-conforming handoff before it executes rather than only at build time; a migration guide for retrofitting an existing hand-coded pipeline.

## Tangible Impact
**Population**: Engineering teams running hand-coded multi-agent pipelines on LangGraph, CrewAI, or AutoGen in production — the same population the three independent critique pieces are writing for and the one OpenAI built Symphony to serve in its one narrow case; broadly, any team past the demo stage where "agent B assumed a field agent A doesn't always produce" has already caused or nearly caused a production incident.
**Mechanism**: Today, the contract between two agents in a pipeline exists only as implicit assumptions buried in each agent's prompt and code — nothing checks that agent A's output under a failure or edge-case path still satisfies what agent B expects, so a mismatch surfaces as a silent downstream failure discovered in production, sometimes much later than the deploy that introduced it. A declarative, statically-checked spec moves that same check to build/CI time, turning an undetected runtime compounding failure into a specific, located build error the person who introduced it sees immediately.
**Measure**: (1) Count of production incidents attributable to an agent-to-agent contract mismatch (a downstream agent receiving data it didn't expect, including on a failure path), before vs. after adoption on a pilot team's pipeline. (2) Percentage of pipeline changes that introduce a contract violation caught at CI time vs. discovered only in production. (3) Time for a new engineer to understand what a given agent in an existing pipeline actually guarantees, with the declared spec available vs. having to read the implementation.

## Why Now
Multi-agent pipelines crossed from demo to production-decision infrastructure in 2026 at the same time three independent practitioner/analyst voices converged on naming "no checkable contract between agents" as the actual root cause of orchestration failures — and OpenAI shipping Symphony in the same window proves a declarative spec approach is now considered worth shipping, just not yet generalized past one issue-tracker use case.

## Skill Angle
Given a description of an existing multi-agent pipeline — what each agent consumes, what it produces (including under known failure modes), and how failures are currently handled, in the user's own prose or a code excerpt — draft a contract spec instance in the project's DSL: typed input/output schemas per node and an explicit failure-handling policy per edge, plus a flagged list of any gaps the description left ambiguous (e.g., "agent B's expected input doesn't say what happens if agent A times out"). This is useful the moment someone describes their pipeline, independent of whether they adopt the validator or runtime.

## MVP Sketch
A YAML-based spec parser, a static validator checking schema compatibility across declared edges (happy-path and failure-path), and a LangGraph runtime adapter that enforces the same checks live. Experiment: take one existing hand-coded LangGraph pipeline with a known or plausible contract-mismatch bug (a field one agent assumes but another doesn't always provide), retrofit the spec, and confirm the static validator flags it before the pipeline is run — if the validator can't catch a real, previously-discovered bug of this class, the core value claim fails. 3–4 weeks for 1–2 people.

## Risks & Open Questions
- Symphony or a similar OpenAI/vendor effort could generalize past the Linear-only adapter before an independent build gains adoption — OpenAI has already shown willingness to invest here.
- A spec that's too rigid for genuinely dynamic agent behavior (an agent whose output shape depends on what it discovers mid-task) could force teams into brittle schemas that don't match how LLM agents actually behave — the DSL's expressiveness for conditional/variable outputs is the hardest design problem, not the validator logic itself.
- Hand-authoring a spec duplicates information already implicit in the pipeline's code, which teams may resist; the auto-derivation upgrade path (static analysis of existing source) is the real adoption unlock but is a materially larger build than the MVP.
- If the failure-handling taxonomy (retry/escalate/abort/fallback) doesn't match how a given framework's runtime actually propagates errors today, the live-enforcement adapter may need framework-specific workarounds that weaken the "one spec, any framework" promise.
