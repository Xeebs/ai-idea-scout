# Quarantine Line: A Recency-Bias-Resistant Supersession Layer for Append-Only Agent Memory

- **Status**: PROPOSED
- **Date**: 2026-11-13
- **Topic**: Context engineering & memory
- **Source**: research/2026-11-13-context-engineering-memory.md · P3
- **Maturity verdict**: PARTIAL — GitHub search for memory-conflict/versioning tools found nothing matching. WebSearch found a NeurIPS 2026 paper ("Keep the Receipts") reporting a "quarantine" policy (place possibly-superseded turns below a reference divider rather than deleting) outperforms deletion/labeling on 3 benchmarks — a real but single, unreplicated research result, not a shipped library. Vendor blogs (mem0.ai, MemClaw, a book chapter) describe bi-temporal/pointer-chain designs as narrow, vendor-specific, unverified-claim features. The evidenced "Zenod" memory-product builder is still asking the community for a fix, confirming no mature shipped solution exists.
- **Format**: BOTH — the context-assembly reordering/quarantine mechanism is persistent infrastructure wired into how memory gets read back into a prompt; reviewing an existing memory schema and drafting a quarantine policy for it is a separable one-shot design task.
- **Data Sources**: CONNECTED — wraps the read path of the user's existing agent-memory backend (a custom Postgres/vector store, or a shared cross-client memory product like Zenod) to intercept context assembly before it reaches the model. No general-purpose "agent memory store" connector exists maturely today across backends, so this is built as a thin adapter per backend, starting with a custom Postgres/pgvector store as the MVP target — no manual pasting is involved since it operates on memory the team already has stored and connected.

## The Gap
The builder of "Zenod" (shared memory for Claude, Codex, and Cursor) posted to r/ContextEngineering describing their own shipped append-only design failing in production: two old rules "still said 'don't wait for approval' after we'd decided every post waits for mine," and an agent reading the old line first acted on it — despite the newer rule existing elsewhere in the same memory store, correctly marked superseded. The poster, who builds and sells this exact product, is asking the community for a fix, confirming their own shipped design doesn't solve it today. This is a correctness problem distinct from memory tampering/authenticity (already SATURATED per a prior cycle's digest) or concurrent multi-writer conflicts (already covered by this repo's "Whose Memory Wins" idea) — it's what happens when a single, honestly-recorded supersession still loses to recency/positional bias at read time.

## The Project
A context-assembly middleware that sits between a memory store's read API and the prompt it feeds the model. Rather than relying on "never delete, mark superseded" alone and hoping ordering sorts itself out, it enforces the quarantine policy the NeurIPS paper found effective: any entry marked superseded gets physically moved below an explicit reference divider in the assembled context (visible for audit, but structurally demoted so it can't out-compete the active rule by appearing earlier or more prominently), and the active replacement is always placed where the model reads it first. A companion test harness runs a labeled battery of "old rule vs. new rule" conflict scenarios against the target model and reports the stale-rule-still-followed rate with the quarantine layer on versus off — turning "does this actually fix the Zenod problem" from a vibe into a number.

Components: a supersession-aware context assembler (intercepts the memory read, detects `superseded`/`active` tags, reorders/quarantines); a reference-divider renderer (keeps superseded text visible for audit, never silently deleted); a conflict-scenario eval harness (seeded stale-vs-current rule pairs, measures compliance); adapters for a custom Postgres/pgvector store as the reference backend.

## Tangible Impact
**Population**: Teams and builders running shared, append-only memory products across coding-agent clients — the same population the evidenced Zenod product (shared memory for Claude, Codex, and Cursor) sells to, plus any team running a long-horizon agent whose memory store accumulates revised decisions over weeks or months rather than deleting old ones.
**Mechanism**: Today, marking a rule "superseded" without changing its position in the assembled context does nothing to stop the model from still finding and following the old line if it happens to sit earlier or more prominently — exactly the failure the Zenod builder describes in production. A quarantine-ordering layer removes the positional/recency advantage from stale entries structurally, instead of hoping the model infers "superseded" means "ignore this" from a label alone.
**Measure**: (1) Stale-rule-still-followed rate on a labeled conflict-scenario benchmark, with the quarantine layer on versus off. (2) Time-to-detect for a real production conflict (how long a Zenod-style user runs with a silently-reverted rule before noticing) versus a baseline of discovering it the way the evidenced poster did — by the agent visibly acting on the old rule. (3) Audit completeness — the fraction of superseded entries still retrievable/inspectable after quarantine, versus a deletion-based alternative that loses the history entirely.

## Why Now
A memory-product builder posted this exact production failure to the community in the last 30 days asking for a fix, and a NeurIPS 2026 paper independently validated a specific mechanism (quarantine-below-divider) that outperforms deletion/labeling on benchmarks — but it exists only as an unreplicated research result, not something any shipped memory product (Zenod, mem0, MemClaw) has adopted, leaving a short window before one of them absorbs the fix natively.

## Skill Angle
Given a description of an existing memory store's schema (how entries are tagged, how supersession is marked, roughly how context gets assembled for a prompt) and 2-3 examples of entries that have been superseded, review it for the Zenod-style failure mode — could a stale entry still out-rank its replacement by position or recency — and draft a quarantine/ordering policy (what gets reordered, what stays visible for audit, what the reference-divider convention looks like). Useful today as a design review before a team commits to building the enforcement middleware.

## MVP Sketch
Wrap a Postgres-based memory table with a read-intercept layer that detects `superseded`/`active` tags and re-renders the assembled context with superseded entries moved below a divider. Build a labeled set of 15-20 synthetic "old rule says X, new rule says Y" conflict scenarios. Experiment: run each scenario through the target model with quarantine on versus off, and measure the stale-rule-still-followed rate. 2-3 weeks for 1-2 people.

## Risks & Open Questions
- mem0, Zenod, or another shared-memory vendor could ship this exact ordering fix natively once enough users hit the same production failure — the most direct competitive risk, since the gap is now publicly named by one of their own builders.
- The NeurIPS paper's result is single and unreplicated; the MVP's own eval harness needs to independently confirm quarantine-ordering actually beats simple deletion or label-only approaches before treating it as validated.
- Must stay clearly differentiated from "Whose Memory Wins" (concurrent multi-agent write-write conflicts) and "Projection Lock" (staleness contracts for versioned projections) — this idea is specifically about single-writer, honestly-recorded supersession losing to positional bias at read time, not detection of contradictory writes or invalidation of stale projections.
- It's unproven whether positional reordering alone is sufficient, or whether some models need an explicit instruction-level cue (not just physical position) to reliably deprioritize quarantined content — worth testing both in the MVP.
