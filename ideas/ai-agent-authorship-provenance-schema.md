# Attributed: A SoftwareAgent Authorship Extension and Validator for RO-Crate Research Artifacts

- **Status**: PROPOSED
- **Date**: 2026-11-19
- **Topic**: Agentic AI & autonomous agents
- **Source**: research/2026-11-19-agentic-ai-autonomous-agents.md · P8
- **Maturity verdict**: OPEN — searched GitHub and web for a shipped alternative: found only a February 2026 W3C mailing-list discussion draft proposing an Agent Ontology (not an adopted schema.org type), vendor C2PA proposals targeting AI-generated *media* authenticity rather than research-artifact/commit authorship, and informal conventions (git `Co-authored-by` trailers) that aren't a metadata-schema standard. No credible implementation of a `SoftwareAgent`-type provenance field for RO-Crate/schema.org-style artifacts exists.
- **Format**: BOTH — the schema extension and validator library is a maintained artifact other tools depend on (PROJECT-shaped); given an existing crate and agent-run details, drafting the correct `SoftwareAgent` entity to insert is a separable one-shot task.
- **Data Sources**: CONNECTED — reads the researcher's own `ro-crate-metadata.json` file, a file they already generate via their existing research-data packaging tool (RO-Crate is a mature, widely-adopted JSON-LD format in the research-data community); the file is uploaded once and the validator/inserter operates on it directly rather than requiring the user to retype its contents. No external API needs to be built to read the file — the new piece is the `SoftwareAgent` JSON-LD context and the validation logic that doesn't exist today.

## The Gap
A GitHub issue on `ResearchObject/ro-crate`, "How to capture when an AI agent 'authors' an RO-Crate" (2026-11-16), points out that schema.org's `creator`/`author` fields only support `Person` or `Organization` — there is no way to correctly represent an autonomous agent as the author of a dataset, commit, or research artifact packaged as an RO-Crate. This is thematically echoed by a separate Product Hunt memory-tool maker (surfaced under P1 of this same digest) independently flagging that "who made each decision and why" is still unrepresented in most agent tooling. As AI agents increasingly generate datasets, run analyses, and produce code commits inside research pipelines, the metadata standard researchers rely on to describe who/what made an artifact has no vocabulary for "an agent did this," forcing either misattribution to a human supervisor or silent omission of authorship entirely.

## The Project
A JSON-LD context extension that defines a `SoftwareAgent` type usable anywhere schema.org's `creator`/`author` fields are used in an RO-Crate, plus a validator library that checks whether a crate's agent-authorship claims are well-formed and (where possible) traceable to a run record — which model/version, which invocation, and under whose supervision. Rather than waiting for the W3C draft or a schema.org vote to land, this ships as a drop-in companion package researchers and crate-generation tools can adopt today, proposed upstream to RO-Crate as a profile extension in parallel.

Components: a `SoftwareAgent` JSON-LD context (extends `schema:Person`/`schema:Organization`'s sibling slot, with fields for model identity, version, invocation ID, and supervising-human reference); a validator CLI/library that checks a given `ro-crate-metadata.json` for correct `SoftwareAgent` usage and flags artifacts with no authorship claim at all; a crate-authoring helper that, given a description of which artifact an agent produced and under what run, inserts a correctly-formed entity; a reference profile submitted as a PR to the RO-Crate specification repo.

## Tangible Impact
**Population**: Research-data engineers, institutional repository maintainers, and computational-research groups who package outputs as RO-Crates today (RO-Crate is the packaging format behind WorkflowHub and is referenced across multiple national research-data infrastructure projects) and are starting to have AI-agent-produced datasets, analysis code, or derived artifacts enter the same pipelines as human-produced ones, with no standard way to say so.
**Mechanism**: Without a `SoftwareAgent` type, a repository either attributes an agent-produced artifact to the supervising researcher (a misattribution that misrepresents provenance and can undermine reproducibility audits or authorship disputes) or drops authorship metadata for that artifact entirely (breaking the provenance chain FAIR-data practices depend on). A validated, adoptable extension lets a crate correctly record "this dataset was produced by agent run X, supervised by researcher Y," which a reproducibility audit, a citation record, or a later dispute over who's responsible for an error can actually consult.
**Measure**: (1) Number of RO-Crates in the wild correctly using the `SoftwareAgent` type after the package is published and the RO-Crate PR is open, tracked via a GitHub code-search query re-run periodically. (2) Validator pass/fail rate on a sample of recent real-world crates from repositories known to include agent-produced artifacts, before vs. after researchers adopt the helper. (3) Whether the RO-Crate maintainers merge, request changes to, or reject the proposed profile extension — a direct signal of whether the standards community accepts this as the right shape for the gap.

## Why Now
The RO-Crate maintainers themselves opened this exact question in a GitHub issue within the last 30 days, and it's landing at the same moment AI agents are shifting from occasional co-pilot assistance to autonomously producing full research artifacts (datasets, analysis scripts, derived results) inside computational pipelines that already use RO-Crate — the standards gap and the volume of artifacts that need it are both growing in the same window.

## Skill Angle
Given a description of an artifact an AI agent produced (what kind of artifact, which model/tool, under what invocation or session, and who supervised the run) plus the existing `ro-crate-metadata.json` the researcher already has, draft the correctly-formed `SoftwareAgent` entity and the `creator`/`author` reference to insert, and flag any other artifacts in the same crate that look agent-produced but currently lack any authorship claim at all. Useful as a one-off fix for a specific crate, independent of whether the researcher adopts the full validator pipeline.

## MVP Sketch
Draft the `SoftwareAgent` JSON-LD context (model name/version, invocation ID, supervising-human reference fields), build a small Python validator that loads a `ro-crate-metadata.json`, checks any `creator`/`author` claims against the new type, and reports artifacts with no authorship claim; run it against 5-10 real public RO-Crates pulled from WorkflowHub to see how many already have agent-produced-looking artifacts with missing or human-misattributed authorship. Open the PR to `ResearchObject/ro-crate` proposing the profile. 2-3 weeks for 1-2 people, most of it spec-drafting and community engagement rather than code.

## Risks & Open Questions
- This is a standards-adoption project as much as a software project — even a well-designed extension is worthless if the RO-Crate maintainers or the broader research-data community don't adopt it; the PR-acceptance measure above is the real test, not the code.
- The W3C mailing-list Agent Ontology draft could formalize a competing or incompatible vocabulary first, which would fragment adoption rather than close the gap — worth tracking that thread directly rather than working in isolation.
- The addressable population (RO-Crate users specifically) is a narrow slice of the broader "AI agents need authorship attribution" problem; if the real demand turns out to be generic (any artifact, any format) rather than RO-Crate-specific, a narrower schema.org-level proposal might serve more people than an RO-Crate-first implementation.
- "Supervising human reference" fields raise their own disclosure/liability questions (who's named as responsible when an agent-authored artifact turns out to be wrong) that this project surfaces but doesn't resolve on its own.
