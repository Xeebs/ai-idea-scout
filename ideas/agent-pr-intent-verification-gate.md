## The Gap
A Harvard-research-cited Hacker News item (60 pts, 93 comments, 2026-11-17) confirms AI coding agents have shifted the engineering bottleneck to code review. The digest's WebSearch synthesis names the specific failure mode inside that bottleneck: teams are pointing a second AI pass at agent-generated PRs as a review gate, but that reviewer checks the code for internal consistency with itself, not against the original spec or intent — "a false sense of assurance." Every named vendor (CodeRabbit, Greptile) is a general review-automation layer, not an intent-verification layer; the one vendor explicitly targeting this exact gap (Aviator Verify) is self-described as still piloting.

## The Project
A CI-integrated gate that captures the originating task's intent at the moment a PR links to an issue/ticket, extracts a small set of testable acceptance criteria from it via LLM, and checks the PR's diff against those criteria specifically — separately from, and in addition to, any generic code-quality review. Where the criterion is behaviorally checkable (e.g., "returns a 400 on invalid input"), the gate attempts to map it to an existing or generated test and actually runs it against the app; where it's structural (e.g., "uses the existing auth middleware, not a new one"), it does a targeted static check. The output is a distinct "intent-alignment report" on the PR — pass/fail/uncertain per criterion, with the specific diff region cited — so a human reviewer can immediately see spec drift that a generic "LGTM, consistent with itself" review would miss.

Components: an issue/ticket-to-acceptance-criteria extractor, a criteria-to-diff mapper (test-execution path + structural-check path), a PR-comment formatter distinct from code-quality comments, and an outcome ledger tracking which flagged criteria later correlated with a revert or hotfix (to calibrate extraction quality over time).

## Tangible Impact
**Population**: Engineering teams that have adopted AI coding agents for PR authorship and rely on a second AI pass (generic bots like CodeRabbit/Greptile, or a custom LLM reviewer) believing it catches intent drift — the exact blind spot the digest's sourced commentary names. The same digest cites secondary-aggregator figures (flagged unverified) that AI-agent PRs take 4.6–5.3x longer for a human to pick up and contain ~1.7x more defects than human PRs — a proxy for how large and under-served this reviewing cohort already is.
**Mechanism**: Today a generic AI reviewer validates that code is internally coherent — it can approve a PR that perfectly implements the wrong thing, because nothing checks the diff against what was actually asked for. Extracting acceptance criteria from the linked task and checking the diff against those specifically, separately from code-quality review, surfaces spec drift before merge instead of after a user files a bug against behavior that technically "passed review."
**Measure**: (1) % of historical merged PRs (sampled from an OSS repo with linked issues) where the gate's intent-alignment check would have flagged a criterion that a generic code-quality reviewer passed clean. (2) Correlation between flagged-and-ignored criteria and later reverts/hotfixes on those PRs, validating the flag actually predicts spec-drift bugs. (3) Added review-cycle time from the intent-check step vs. reported time saved by catching spec mismatches pre-merge rather than post-merge.

## Why Now
The Harvard-research bottleneck finding and Aviator Verify's still-piloting status both landed in this exact 30-day window, confirming the problem is acute and that the one vendor targeting it directly hasn't shipped broadly yet — a narrow window to build a differentiated, cheaper, or open alternative before the space consolidates around a single VC-backed player.

## Skill Angle
Trigger: a user has a PR diff and the originating issue/ticket text (pasted or pulled via the connector) and wants to know whether the diff actually satisfies the original ask before merging. Inputs: the diff, the task description, and (optionally) the repo's test suite location. Output: the same structured intent-alignment report the project produces — per-criterion pass/fail/uncertain with cited diff regions — as a one-shot check, without needing the always-on ledger or CI wiring. This differs from the project in persistence only: the skill is the judgment; the project is the always-on capture-and-calibrate pipeline around it.

## MVP Sketch
A GitHub Action triggered on PR-closes-issue events: pull the issue body, extract 3–5 criteria via LLM, attempt to map each to an existing test (via file/function name heuristics) or generate a minimal check, run what's runnable, LLM-judge the rest against the diff, and post a structured comment. Experiment: run against 20–30 real closed PRs with linked issues from an active OSS repo, and check whether the intent-alignment flags correlate with which of those PRs were later reverted or had a follow-up bugfix PR. 3–4 weeks for 1–2 people.

## Risks & Open Questions
- Aviator Verify is explicitly building toward this and is VC-backed; if it ships broadly before this gets traction, the differentiation narrows to "open/cheaper," which may not be enough.
- Acceptance-criteria extraction quality is bounded by how well-written the originating issue is — vague tickets produce vague criteria, and garbage-in-garbage-out risk is real.
- An LLM judging "does this diff satisfy criterion X" without an independently runnable test risks reproducing the exact self-referential weakness this project exists to fix; the test-execution path must stay the primary mechanism, with LLM judgment as a fallback only.
- Scope discipline is required: this is not a full QA/test-generation platform, only an intent-alignment flag layered onto existing review tooling.
