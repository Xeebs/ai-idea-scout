# Decision Thread: A Cross-Tool Schema and Correlation Layer for Guardrail Verdict Events

- **Status**: EXPLORING (promoted 2026-11-18 cycle 149: evidence density — ≥2 independent threads, NeMo Guardrails' OTel GenAI exporter, Langfuse/ClickHouse's score-as-trace pattern, and Arize's scoring endpoint each independently wiring up incompatible guardrail-verdict schemas)
- **Date**: 2026-11-18
- **Topic**: AI safety & guardrails in production
- **Source**: research/2026-11-18-ai-safety-guardrails-in-production.md · P6
- **Maturity verdict**: PARTIAL — NVIDIA NeMo Guardrails switched its tracing to OTel GenAI semantic conventions in v0.16.0, and Langfuse (acquired by ClickHouse) records guardrail verdicts as scores attached to the trace they protected, so the base capability (trace guardrails, not just gate on them) already ships in multiple maintained tools individually. But the OpenTelemetry GenAI spec itself defines no guardrail-verdict attribute yet, so each vendor's shape is bespoke — the cross-tool schema the digest names as missing is still genuinely open.
- **Format**: BOTH
- **Data Sources**: CONNECTED — the project's adapters read from and write to named, mature APIs/exporters: NeMo Guardrails' OTel GenAI exporter (v0.16.0+, open source), Langfuse's score-on-trace API (mature, documented), and Arize's guardrails-scoring endpoint. No new connector needs to be invented, only a canonical intermediate schema each adapter maps to/from. The companion skill's one-shot mapping check is MANUAL — the user pastes a sample guardrail-verdict log line, config snippet, or exported trace from whichever tool they currently run.

## The Gap
Guardrails AI's OpenTelemetry blog post, a ClickHouse guide describing Langfuse's guardrail-verdict-as-trace-score pattern, and Arize's framing line "you can't block what you can't trace" all show guardrail decisions moving from a silent allow/block checkpoint to a traced, queryable event — but each vendor is wiring this up bespoke. NeMo Guardrails' OTel GenAI spans, Langfuse's score objects, and Arize's scoring endpoint each capture different fields for the same underlying event (which check fired, what confidence, what verdict, against which span), and the OTel GenAI semantic-conventions spec itself has no guardrail-verdict attribute defined. A team running more than one guardrail enforcement point across different backends has no way to reconstruct "which check blocked this interaction, and why" without manually reconciling three different schemas.

## The Project
A small open schema spec for a `gen_ai.guardrail.verdict` event (check name, category, verdict — allow/block/escalate/warn —, confidence score, policy version, latency, and a reference to the triggering span) plus an adapter library that translates between that canonical shape and each vendor's native format: reading NeMo Guardrails' v0.16 OTel-exported guardrail spans, and writing canonical events into Langfuse as scores attached to the protected trace or into Arize's guardrails endpoint. A team emits or captures a guardrail verdict once in the canonical shape and the adapter handles getting it into whichever observability backend(s) they actually run, rather than hand-wiring each integration separately or losing the confidence/category detail when a verdict crosses from one tool's export to another's import.

Components: the canonical verdict schema (versioned, tracking the OTel GenAI SIG's eval-attribute conventions where they overlap); NeMo Guardrails and Langfuse adapters to start, Arize next; a replay CLI that re-emits a captured verdict log through any configured adapter for backfill/migration.

## Tangible Impact
**Population**: ML-platform and trust-and-safety engineers at companies running more than one guardrail enforcement point on different backends — for example NeMo Guardrails at the pre-inference layer, a custom post-inference check, and Langfuse for trace storage, the exact shape this digest's own evidence describes as already shipping piecemeal. Combined GitHub stars across the tools that would need bridging (NeMo Guardrails, Guardrails AI, Langfuse) run well into five figures, a rough proxy for thousands of teams running at least one of these tools today, a meaningful fraction of them running more than one.
**Mechanism**: today, reconstructing "which specific check fired, with what confidence, against which user interaction" during an incident post-mortem or compliance audit means manually cross-referencing each backend's own export format, losing fidelity (a confidence score or category label that doesn't survive the hand-translation) at every hop. A shared canonical schema and adapter layer turns that reconciliation into a single query across backends instead of a multi-tool forensic exercise, and makes it possible to compare guardrail-stack accuracy or false-positive rates across tools on equal footing for the first time.
**Measure**: median time to answer "which check(s) fired, in what order, with what confidence" across tool boundaries during a simulated incident review, before vs. after adopting the adapter; percentage of a vendor's native verdict fields (category, confidence, policy version) that round-trip losslessly through the canonical schema; number of cross-tool comparisons (e.g., false-positive rate of NeMo's pre-inference check vs. a post-inference check recorded in a different backend) made possible that weren't visible from any single vendor's dashboard alone.

## Why Now
NeMo Guardrails' switch to OTel GenAI conventions and Langfuse's score-as-trace-attachment pattern both shipped within the same window this digest covers — the base "trace, don't just gate" capability has just arrived across multiple vendors independently, and the OTel GenAI SIG's own eval-attribute conventions are still unstable, meaning there's a real but narrow window to propose a canonical shape before each vendor's bespoke format fossilizes into a de facto standard nobody can walk back from.

## Skill Angle
Trigger: a team hands over a sample of their current guardrail-verdict output — a NeMo Guardrails config and a captured span, a Langfuse score export, or a raw log line — and wants to know how it maps onto a portable schema before committing to wiring up a cross-tool adapter. The skill produces a field-by-field mapping table against the canonical schema and flags which verdict metadata (reason code, confidence, triggering check, latency) isn't currently captured at all in their setup, as a one-shot diagnostic. The project is the continuously running adapter that translates live verdict events between backends; the skill is the one-time "here's what you'd gain and what you're currently missing" assessment.

## MVP Sketch
Draft the canonical `gen_ai.guardrail.verdict` schema as a JSON Schema document, then build two adapters: one reading NeMo Guardrails v0.16's OTel-exported guardrail-check spans into the canonical shape, one writing canonical events into Langfuse as scores attached to the protected trace. Single experiment: run the same adversarial prompt through a NeMo Guardrails pipeline, capture the exported span, translate it through the canonical schema, push it into Langfuse, and confirm the verdict, category, and confidence score (not just a pass/fail boolean) are all queryable there. 3 weeks, 1-2 people.

## Risks & Open Questions
- If the OTel GenAI SIG ships its own guardrail-verdict attribute and vendors adopt it natively, a third-party canonical schema becomes a temporary bridge rather than a durable standard — worth tracking spec progress closely before investing further.
- Vendor verdict-export shapes are new and less stable than core tracing APIs, so adapters risk breaking on silent format changes more often than a tracing-only bridge would.
- Community signal this cycle is vendor blog posts describing their own integrations, not a practitioner complaint thread — real validation is whether a team adopts the canonical schema voluntarily, not whether the fragmentation gets written about again.
- Conceptually adjacent to a separate idea bridging eval-score schemas across the same observability vendors (Score Bridge, `eval-score-telemetry-schema-adapter.md`) — distinct artifact (verdict events vs. quality scores) today, but worth monitoring for a natural merge if both get built.
