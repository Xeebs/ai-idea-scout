# Pipeline Shape: A Risk-Triage, Size-Discipline, and Explicit-SLA Gate Purpose-Built for Agent-Authored PRs

- **Status**: PUBLISHED
- **Date**: 2026-11-17
- **Topic**: Agentic AI & autonomous agents
- **Source**: research/2026-11-17-agentic-ai-autonomous-agents.md · P5
- **Maturity verdict**: PARTIAL — WebSearch found real but fragmented point solutions: Tenki (labels/routes agent PRs to a faster review track), Cubic (automates initial PR triage risk-level scoring inside GitHub), and Shiplight (hosted CI runners pitched for "agent-written code," but only an uptime SLA, not a review-triage SLA). A GitHub Blog post ("Agent pull requests are everywhere, here's how to review them," 2026-03-30) confirms this is an acknowledged live problem being patched piecemeal. No consensus pipeline design or shared triage-SLA standard combining risk-based routing, an explicit review SLA, and PR-size discipline together was found across any source.
- **Format**: BOTH — the live pipeline is persistent infrastructure (holds SLA state, routes incoming PRs, tracks breach history); recommending how to split and classify one specific oversized PR is an independently useful one-shot judgment.
- **Data Sources**: CONNECTED — the GitHub/GitLab Pull Requests API (mature) supplies diff size, files-touched count, and change metadata at PR-open time; the same platforms' review-assignment and label APIs (mature) are used to route PRs and track SLA-clock state, so no manual paste is required for the live pipeline.

## The Gap
The digest's WebSearch synthesis cites secondary-aggregator figures (flagged as unverified, but directionally consistent across two independent sources): AI-agent-authored PRs reportedly take 4.6–5.3x longer for a human to pick up for review than human-authored PRs (LinearB via Synodus; Faros AI), and contain roughly 1.7x more defects (LeadDev-sourced). Addy Osmani is quoted in the same synthesis: "The bottleneck moved from writing code to proving it works." The remedies found — Tenki, Cubic, Shiplight — each address one slice (routing, initial risk scoring, CI uptime) but none combines risk-based triage, an explicit review SLA tied to that risk tier, and enforced PR-size discipline into one pipeline; teams described as "pulling ahead" are said to have assembled this ad hoc themselves.

## The Project
A PR-pipeline layer that, at PR-open time for agent-authored changes, (1) scores the PR's risk/complexity from diff size, files-touched count, and change type (new feature vs. refactor vs. config-only); (2) if the PR exceeds a configured size threshold for its risk tier, blocks it from entering the normal review queue and instead returns a structured decomposition recommendation (suggested split points by file/module boundary) before it can proceed; (3) assigns an explicit, risk-tier-specific review SLA clock (e.g., high-risk/large PRs get a shorter mandatory pickup window and a named reviewer, not a flat org-wide SLA applied identically regardless of size or risk); and (4) tracks SLA breaches and decomposition-recommendation acceptance over time to tune the thresholds against a team's own actual pickup-time and defect data, rather than the secondary-aggregator benchmarks the industry is currently flying blind on.

Components: a PR risk/complexity scorer, a size-threshold-to-decomposition-recommendation generator, an SLA-clock-and-routing engine tied to the risk tier, and a breach/outcome tracker feeding threshold tuning.

## Tangible Impact
**Population**: Engineering teams whose agent-authored PR volume is high enough that review has become the measured bottleneck — the same cohort the digest's cited Harvard-research-based HN item (60 pts, 93 comments) and the 4.6–5.3x pickup-time multiplier describe, specifically teams currently applying one flat review process to every PR regardless of whether an agent produced a 20-line config change or an 800-line multi-module feature.
**Mechanism**: A single review SLA and no enforced size discipline means a team's limited review bandwidth gets consumed unpredictably by whichever PR happens to be biggest or riskiest that day, and the empirically-worse defect rate on large agent PRs goes unaddressed because nothing structurally discourages them. Tying size discipline and an explicit, risk-tiered SLA together means oversized high-risk PRs get decomposed before they ever enter the queue, and the SLA clock itself reflects actual risk instead of a one-size-fits-all number — converting an invisible, growing backlog into a measured, triaged one.
**Measure**: (1) Median and p95 review pickup time per risk tier, before and after adopting the pipeline, against the team's own baseline (replacing reliance on the unverified LinearB/Faros figures with the team's own measured numbers). (2) Defect rate (post-merge bugs/reverts) on PRs that were decomposed per the pipeline's recommendation vs. PRs of comparable original size that weren't. (3) SLA breach rate per risk tier over time, confirming the tiered SLA is actually achievable and not just a stricter number nobody meets.

## Why Now
The 4.6–5.3x pickup-time and 1.7x defect-rate figures, Addy Osmani's bottleneck framing, and the GitHub Blog's own acknowledgment post all landed within the same 30-day window the digest covers, making this an acute, currently-discussed problem rather than a stale one — and the PR metadata needed (size, files touched, change type, review-assignment state) is already fully queryable via mature, existing GitHub/GitLab APIs, so no new data-access primitive needs to be built.

## Skill Angle
Trigger: a reviewer or team lead has one specific oversized or ambiguous-risk agent-authored PR and wants a quick triage read before it enters (or stays stuck in) the review queue. Inputs: the PR diff (or its size/files-touched metadata) and the change's stated intent. Output: a risk/complexity tier assignment, a recommended review SLA for that tier, and — if oversized — concrete suggested split points by file/module boundary, mirroring the live pipeline's logic as a one-shot check without requiring the always-on routing infrastructure.

## MVP Sketch
A GitHub App that scores each new PR from a configured bot/agent author on diff size and files-touched count, applies a simple two-dimensional risk matrix (size x change-type) to assign one of three tiers, posts a decomposition recommendation on PRs exceeding the tier's size threshold, and labels the PR with its SLA deadline. Experiment: run against a sample of 20–30 real recent agent-authored PRs from an active OSS repo, compare the pipeline's recommended tier/SLA against what actually happened (how long pickup took, whether a later bug was filed), and check whether the decomposition recommendation would have produced a smaller, faster-reviewed PR. 3–4 weeks for 1–2 people.

## Risks & Open Questions
- The core evidence (4.6–5.3x, 1.7x figures) is explicitly flagged in the digest as secondary-aggregator and unverified — the MVP experiment is designed to validate against a team's own numbers rather than assume the industry figures generalize.
- Decomposition recommendations risk being mechanically plausible (split by file) but semantically wrong (splitting a change that's only coherent as one unit) — needs a human override path, not a hard block.
- Overlaps conceptually with several narrower existing ideas in this index — `ai-coding-agent-architecture-boundary-gate.md` (architecture-fitness checks), `agent-authored-code-regression-gate.md` (specific regression classes), and `ai-review-coverage-honesty-gate.md` (coverage honesty) — this project must stay focused on triage routing, size discipline, and SLA enforcement specifically, not duplicate those ideas' detector logic.
- A well-resourced reviewer-automation vendor (CodeRabbit, Greptile, or GitHub itself) could ship risk-tiered SLA routing as a platform feature, given GitHub's own blog post already acknowledges the problem publicly.
