# Role Mesh: A Shared Role-Scoped Agent Pool for Teams

- **Status**: PROPOSED
- **Date**: 2026-11-12
- **Topic**: Multi-agent architectures
- **Source**: research/2026-11-12-multi-agent-architectures-ii.md · P3
- **Maturity verdict**: PARTIAL — mature adjacent infrastructure exists (CrewAI Enterprise workspace-scoped roles/RBAC, Microsoft 365 Copilot org-wide agent sharing, OpenAI ChatGPT Workspace Agents, Agno v2.6 multi-tenant provisioning, Seekr RBAC) but all of it solves tenancy/access-control for agents a team shares a *login* to, not the specific architecture of role-scoped agents that each hold their own persistent memory and hand work to each other directly. `gh search repos` for "shared agents team role-scoped" / "multi-tenant agent team memory" returned zero matches. The vendor cited in the evidence (Dock, YC S26) is itself still spec'ing the pattern in public, and the cited HN paper ("Worse Together") frames multi-user multi-agent performance as an open, newly-documented failure mode, not a solved one.
- **Format**: BOTH — the agent pool + handoff runtime is PROJECT-shaped (persistent per-role memory stores, a handoff protocol between agents); deciding how to carve an existing single-agent-per-person setup into roles is a one-shot design task. See Skill Angle.
- **Data Sources**: CONNECTED — reads from the team's existing work tools via whatever connectors the team already has wired up (e.g., a CRM API/MCP connector for a sales-role agent's pipeline state, an accounting API/MCP connector for a finance-role agent's late-payer memory). These per-tool connectors already exist maturely for mainstream SaaS (Salesforce, HubSpot, QuickBooks, Xero all ship first-party or community MCP servers); what doesn't exist is the layer that lets several *role-scoped* agents share and hand off state built from those connections instead of each person's agent re-deriving it.

## The Gap
The builder of Dock (YC S26) posted "What changes when 8 people share AI agents instead of each running their own" (r/AI_Agents, 2026-11-12), arguing that most agent setups are single-player and listing, as an open design problem, what has to exist for a team to share role-scoped agents that hand work to each other directly instead of every employee running an isolated chat. The same day, Hacker News surfaced "Worse Together: How Performance Breaks Down in Multi-User Multi-Agent Teams" (alignment.anthropic.com), documenting fresh failure modes specific to this configuration. Both signals point the same direction: teams want to stop paying for N isolated agent seats, but nobody has shipped the shared-role architecture that would let them.

## The Project
A runtime where a team provisions a small pool of role-scoped agents — one per function (sales, finance, support, ops) — each backed by its own persistent memory store and its own set of tool connections, instead of one agent per employee. Agents hand work to each other through a typed handoff protocol (e.g., the sales agent flags a deal as closed-won, which triggers the finance agent to open an invoice record) rather than a human copy-pasting context between separate chat windows. A lightweight access layer lets any team member address any role-agent, but the agent's memory and tool scope stay tied to its role, not to whoever's talking to it — directly answering the "each agent has one job and its own memory" requirement from the evidence.

Components: role-agent registry (one memory store + tool-scope manifest per role); a handoff event bus agents publish/subscribe to; a per-member addressing layer (anyone on the team can talk to the finance agent and get the finance agent's actual memory, not a stub); an admin view showing which roles exist and what each remembers.

## Tangible Impact
**Population**: Small-business and startup teams (roughly 2–99 employees) already paying for multiple individual AI seats per person — the SBE Council's February 2026 survey of 517 U.S. small-business owners found 82% use at least one AI tool, with the median AI-using owner running five separate tools, the exact fragmentation (one tool/seat per task, no shared institutional memory) this pattern targets. Dock's own target market is this same cohort.
**Mechanism**: Today, institutional knowledge ("who owes us money," "what's in the pipeline," "which support tickets are escalated") lives in whichever employee's personal agent session happened to touch it last, re-explained from scratch every time someone new needs it; a shared role-pool makes that knowledge a property of the role, not the person, so a new hire or a covering teammate gets the finance agent's actual payment history instead of a blank chat.
**Measure**: (1) time for a team member to get a correct answer from the "right" role-agent on a question outside their own usual work, vs. today's baseline of hunting through someone else's chat history or Slack thread; (2) number of duplicate/contradictory answers given by different employees' personal agents on the same factual question (pipeline status, late-payer list) before vs. after switching to shared roles; (3) per-seat AI spend per employee, which should drop as N individual subscriptions consolidate into a handful of role agents.

## Why Now
The Dock founder is actively recruiting design input in public on exactly this problem in the last 30 days, and the "Worse Together" paper gives a fresh, named failure-mode vocabulary (performance degradation specific to multi-user multi-agent setups) that a shared-role architecture needs to design against rather than discover the hard way. Mature per-tool MCP connectors for the SaaS systems role-agents would read from (CRM, accounting, support-desk) already exist, so the only new build is the handoff/addressing layer gluing them together.

## MVP Sketch
3–4 weeks, 1–2 people: build the role-agent registry and handoff bus for exactly two roles (sales, finance) wired to two real SaaS connectors (e.g., a CRM and an accounting API), plus a Slack-bot-style addressing layer so any of 5–8 pilot team members can message either role-agent. Validate with one real small business: run it for two weeks alongside their existing per-person agent setup, and measure whether cross-role questions (e.g., a support person asking "is this customer's invoice paid?") get answered correctly without a human relaying the answer.

## Risks & Open Questions
- CrewAI Enterprise, Microsoft 365 Copilot, or OpenAI's Workspace Agents could ship the handoff/shared-memory layer as a feature of their existing RBAC tenancy products before this reaches a pilot — the strongest already-adjacent-and-moving risk.
- "Worse Together" documents real performance degradation in this configuration; the MVP needs to actively test against (not just assume past) those failure modes before claiming the architecture works.
- Role boundaries are fuzzier in practice than "sales" and "finance" — ambiguous handoffs (who owns a churn-risk customer?) may need a human-arbitration fallback the MVP doesn't yet scope.
- No independent demand signal beyond one Reddit thread and one adjacent paper; worth a handful of SMB interviews before committing past the two-role pilot.
