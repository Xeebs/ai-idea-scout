# Decide, Don't Run Everything: A Confidence-Gated, Cost-Aware CI Test-Selection Layer

- **Status**: PROPOSED
- **Date**: 2026-11-19
- **Topic**: LLM evaluation & observability
- **Source**: research/2026-11-19-llm-evaluation-observability.md · P9
- **Maturity verdict**: PARTIAL — `cjlee1/PruneTest` (MIT, GitHub) is a near-exact match — a layered pipeline (static import analysis → embedding similarity → GBDT → LLM layer, invoked only on medium-confidence cases, fail-open by design) — but has only 1 star and minimal visible adoption. `CloudBees Smart Tests` is a real shipped commercial product doing confidence-threshold-based test selection, but it's ML-based rather than the LLM-"Decision API"-over-diff approach. Real attempts exist on both open-source and commercial sides; nothing has executed the specific LLM-confidence-gated, cost-aware version well yet.
- **Format**: BOTH
- **Data Sources**: CONNECTED — the Project reads the PR diff via the GitHub API (mature, widely used) and a versioned suite catalog stored as a file in the repo itself (read directly, not pasted). No manual data entry is required once installed; this mirrors github/gh-aw's own evidenced internal approach. The Skill Angle is MANUAL — the user pastes a sample PR diff and their current suite catalog for a one-shot triage-strategy review before committing to the full CI integration.

## The Gap
github/gh-aw PR #77203, "Add fail-open CI Front Door and cache-first daily researcher" (2026-11-12, 1 reaction/19 comments — active review discussion), describes a "Decision API" call over a capped local diff plus a versioned suite catalog to decide which CI/eval suites actually need to run per PR, running everything only when the decision is low-confidence, while keeping mandatory security checks unconditional. This is still internal tooling inside GitHub's own project, under active review with fail-open safety semantics being hashed out, not a portable, product-agnostic version other teams running expensive LLM-judged CI/eval suites can adopt. `PruneTest`'s near-identical approach exists but with 1 star and no visible adoption; CloudBees' commercial product solves a related but structurally different (ML-classifier, not LLM-decision) version of the problem.

## The Project
A portable CI middleware ("Front Door") that sits in front of a repository's eval/test suites and, on every PR, makes a single confidence-scored decision — via one LLM call over a capped diff plus the repo's own versioned suite catalog — about which suites genuinely need to run. High-confidence decisions skip clearly-irrelevant suites (e.g., a docs-only change skipping the full LLM-judged regression suite); low-confidence decisions fall back to running everything, fail-open by design so uncertainty never silently under-tests a risky change. A small, explicitly-configured set of mandatory checks (security scans, compliance gates) always run regardless of the decision, never subject to the confidence gate. Ships as a GitHub Action with a pluggable suite-catalog format and a logged decision history so a team can audit, in retrospect, every skip decision the Front Door ever made.

Components: the Decision API call (diff-capping, suite-catalog lookup, confidence scoring); the fail-open fallback path; the mandatory-check allowlist (never gated); a decision-history log for post-hoc audit; a GitHub Action wrapper.

## Tangible Impact
**Population**: Engineering teams running expensive LLM-judged CI/eval suites on every PR — teams whose test suite includes LLM-as-judge regression checks, agent-behavior evals, or other LLM-involved gates that are slow and costly enough that running the full suite on every trivial change is a real, felt tax. github/gh-aw's own evidenced PR shows this friction inside GitHub's own tooling; `PruneTest`'s and CloudBees' independent existence confirms the pain is recognized broadly, not a one-off complaint.
**Mechanism**: Today, a team either runs every expensive suite on every PR (burning CI minutes and LLM-judge cost on changes that obviously don't need it) or hand-maintains brittle path-based skip rules that miss cross-cutting changes; the confidence-gated Decision API replaces both with a single calibrated judgment that scales down cost on clearly-safe changes while never silently skipping a genuinely risky one, because low confidence always falls back to running everything.
**Measure**: % reduction in CI compute minutes/LLM-judge calls per PR, aggregate over a month, versus a run-everything baseline; % of real regressions still caught post-adoption (target: no measurable drop versus the run-everything baseline, validated via a shadow-mode period where both paths run and are compared); false-skip rate (a suite skipped that would have caught a real issue) tracked via the decision-history log.

## Why Now
LLM-judged CI/eval suites became common and expensive enough through 2026 that cost-aware triage moved from "nice to have" to active engineering priority — evidenced by GitHub's own team building exactly this internally right now, with fail-open safety semantics still being actively debated in a 19-comment PR review — meaning the design questions (how conservative must low-confidence fallback be, what stays mandatory) are freshly being worked out in public and a portable version built now can learn directly from that discussion.

## Skill Angle
Trigger: a team wants to evaluate whether confidence-gated test selection would actually save meaningful cost on their repo, or wants a first-pass triage strategy before installing the full Action. Inputs: a sample PR diff and the team's current suite catalog (names, what each suite covers, approximate cost/runtime), pasted in. Output: a decision-strategy proposal — which suites this diff would trigger under a Decision API gate, which are flagged as always-mandatory, and an estimated cost-reduction range based on the sample's diff shape. This is a one-shot design review distinct from the project, which runs the actual gate continuously in CI.

## MVP Sketch
3–4 weeks, 1–2 people: build the GitHub Action wrapper with a single diff-capping-plus-suite-catalog Decision API call (one LLM call per PR), a fail-open fallback that runs everything below a configurable confidence threshold, and a hardcoded mandatory-check allowlist. Validate by running the Front Door in shadow mode (logging its decision without actually skipping anything) against 20–30 real historical PRs on a repo with an existing eval suite, comparing its skip decisions against which suites actually caught something, and confirming zero real regressions would have been missed.

## Risks & Open Questions
- Fail-open safety semantics are the single hardest design question (per the 19-comment PR debate itself) — getting the confidence threshold wrong in either direction either erodes cost savings or risks a missed regression; the shadow-mode validation step in the MVP is load-bearing, not optional.
- A single LLM call deciding test triage introduces its own non-determinism and potential drift as the judge model changes versions — needs its own calibration-monitoring layer, ideally reusing this same digest's judge-calibration-drift pattern rather than assuming the Decision API stays stable unmonitored.
- `PruneTest`'s existing near-identical open-source approach, despite low adoption, means this isn't a greenfield build — differentiating on portability, fail-open rigor, and auditability (the decision-history log) is necessary, not just re-shipping the same idea.
- Teams with simple, fast CI suites may not have enough cost pain to adopt this — the addressable population is specifically teams whose suites are slow/expensive enough that the tradeoff is worth the added complexity.
