## Candidate patterns

### P1: Opt-in, provenance-tagged, context-budget-capped RAG bolted onto a quote-grounded verification agent
- **What it is**: A verification/fact-checking agent whose default mode is deliberately NOT retrieval-augmented — it only fetches a prospect's own first-party pages and quotes them directly, to stay grounded. The team is now designing an *opt-in* external-source RAG layer on top, with explicit per-request provenance tracking (which external source backed which claim) and a hard context-budget cap, rather than just turning on a generic retriever.
- **Evidence**: GitHub issue "Add opt-in external-source research with provenance and context-budget controls" on `YourAKShaw/irisveil` (#10, 2 reactions, 2026-11-10) — "IrisVeil's current verification is intentionally first-party and quote-grounded, not retrieval-augmented generation (RAG) over an external knowledge base."
- **Why it looks unbuilt/untested**: Most RAG tooling treats "turn retrieval on" as binary. This issue is explicitly designing retrieval as a bounded, auditable, opt-in escalation path for a system that otherwise avoids it — a governance pattern, not a retrieval algorithm — and no general framework for "RAG as an opt-in, budgeted, provenance-tracked escalation" surfaced elsewhere in this run.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search found narrow, early tooling that covers pieces of this — `ctxbudgeter` (PyPI; token-budgeted context assembly with an auditable "Context Bill of Materials" and a CI risk-budget gate, fronting LangGraph/CrewAI) and `Provena` (github.com/sm21707/provena, PyPI; provenance hash-chaining with a policy engine that can block unprovenanced context, LangChain/LlamaIndex adapters). Neither is a widely-adopted, maintained framework, neither clearly defaults retrieval to opt-in/off, and no project combines provenance-tracking + context-budget-cap + opt-in-escalation as one governance layer the way IrisVeil's issue describes — so the specific gap is real but a serious build would be differentiated from these niche point-solutions.

### P2: Retrieval-gated tool/skill definitions ("tool-RAG") to stop large MCP toolsets from bloating agent context
- **What it is**: Instead of loading every MCP tool's full schema/description into context up front, retrieve only the tool definitions relevant to the current step — the same retrieve-then-inject shape as document RAG, applied to the tool-definition corpus instead of a document corpus.
- **Evidence**: Reddit r/LLMDevs, "Skills + Code Mode MCP: How I taught an AI agent to use hundreds of tools without bloating its context" (2026-11-13) — "When there are a lot of MCP methods, their detailed descriptions really bloat the LLM's context... If you hide them behind Code [Mode]..."
- **Why it looks unbuilt/untested**: The author is hand-rolling this ("Code Mode MCP") rather than using a packaged retriever-for-tools library; the post frames it as a problem they personally ran into twice (one personal agent, one work MCP server), not something they found a reusable solution for.
- **Maturity**: SATURATED
- **Verdict notes**: This exact gap is already closed by a well-resourced team's shipped product: Anthropic's Tool Search Tool (API, Nov 2025; rolled into Claude Code Jan–Feb 2026, GA Feb 2026) retrieves only the 3–5 relevant tool definitions on demand instead of loading the full catalog, reporting ~85% token reduction — the native "retrieve tool definitions on demand" fix for MCP context bloat. Independently, the RAG-MCP paper (arXiv 2505.03275) formalizes the identical retrieve-then-inject-for-tools approach (>50% prompt-token cut, 3x tool-selection accuracy) with a public reference implementation, and `rocket-connect/mcp-rag` on GitHub packages a Neo4j-backed version of the same idea. Multiple independent, maintained solutions (one from the platform vendor itself) make this a closed gap, not an unbuilt pattern.

### P3: Fully client-side, zero-backend RAG stack running entirely in the browser
- **What it is**: Running the whole RAG stack — embedding, vector storage, and retrieval — inside a browser tab via a WASM-native database, with no server round-trip at all, as opposed to a thin client calling a hosted vector DB.
- **Evidence**: Hacker News, "Db4 is open source: local RAG on Postgres in a browser tab" (3 points, 2026-10-21, lab4.app).
- **Why it looks unbuilt/untested**: Single low-engagement launch post, no discussion thread, no comparison to existing in-browser vector DB projects (e.g. client-side SQLite/WASM efforts) — framed as a new OSS release, not an established pattern; thin signal, flagged honestly rather than padded.
- **Maturity**: SATURATED
- **Verdict notes**: Web search surfaced at least eight independent, non-trivial implementations of a full client-side embed+store+retrieve RAG stack via WASM: MeMemo (arXiv 2407.01972, browser-native HNSW with a public RAG Playground demo), VecLite, idbvec, Vecnest, vrom.js, velesdb-wasm, the ruvector-router-wasm crate, and GraphRAG-rs's WASM-only mode — spanning Rust/WASM and JS ecosystems. The specific "Db4" launch post is one more reinvention of an already crowded pattern (multiple maintained libraries across separate projects/authors), not a novel gap, even though no single implementation dominates.

### P4: Vector-store "deletion completeness" gap blocking real GDPR Art. 17 erasure
- **What it is**: Deleting a record's reference from a vector index (or marking it "deleted") does not remove the underlying vector values, which can persist in storage until the database compacts/vacuums — so a RAG system can satisfy "stops retrieving it" without satisfying "actually erased the personal data," and teams conflate the two.
- **Evidence**: WebSearch results for "RAG vector database GDPR right to be forgotten delete document unlearning 2026": tianpan.co, "The Third Copy: Vector Stores, Deletion Completeness, and the GDPR Gap RAG Teams Keep Missing" (2026-04-27); sota.io, "Art.17 Right to Erasure: LLM Training Data Removal & RAG Vector Store Deletion 2026"; both argue soft-delete ≠ erasure and that provable/verifiable erasure (audit trail of deleted record IDs) is not something major vector DBs ship out of the box.
- **Why it looks unbuilt/untested**: Sources are practitioner/vendor blog posts (2026-04), not an adopted open-source tool or standard; one source claims no major commercial vector DB offers a *provable* deletion mechanism. No GitHub project or product squarely closing this gap turned up in this run.
- **Maturity**: PARTIAL
- **Verdict notes**: Only narrow, partial fixes found, not a completeness guarantee. A Kestra workflow blueprint (kestra.io/blueprints/pinecone-gdpr-vector-erasure) chains delete-by-ID with an existence check and audit trail for Pinecone specifically; vendor docs confirm delete-by-ID/filter primitives exist (Weaviate, Chroma, pgvector) per Twig's help docs. But per tianpan.co (2026-04-27) and a DEV Community piece, no major commercial vector DB offers a *provable*/cryptographic erasure guarantee, and the research-stage fix (Eisenhofer et al. verifiable-unlearning framework, Trillian-style append-only logs) has no applied implementation for vector stores. GitHub search for "vector database deletion GDPR" / "vector store unlearning erasure" returned nothing further. Narrow workflow-level mitigations exist; the actual completeness/provability gap is unaddressed — PARTIAL rather than OPEN per the tie-break rule.

### P5: No standardized router between vector/graph RAG and text-to-SQL for mixed structured + unstructured enterprise data
- **What it is**: Enterprises hold both structured data (rows in relational/graph DBs) and unstructured documents, but today each system hand-builds its own decision layer for whether an incoming query should become a SQL/graph query or go through embedding-based retrieval — there's no reusable, adopted router for this specific structured-vs-unstructured decision (distinct from the already-covered naive-vs-agentic RAG routing pattern, which is about retrieval *depth*, not retrieval *modality*).
- **Evidence**: WebSearch for "text-to-SQL hybrid RAG structured data retrieval agent 2026": arXiv "CSR-RAG: An Efficient Retrieval System for Text-to-SQL on the Enterprise Scale" (Jan 2026, reports ~40% precision/80%+ recall, ~30ms latency); SurrealDB engineering blog "Agentic retrieval for structured data with text to SurQL" (May 2026); eSapiens (arXiv 2025) pairing a text-to-SQL component with a separate RAG component; a Peru marine-institute preprint (Oct 2026) combining LightRAG-on-Neo4j with a text-to-SQL agent over MCP.
- **Why it looks unbuilt/untested**: Every hit is a one-off paper or vendor tutorial building its own bespoke Decision Agent/router from scratch; no shared library or standard decision layer for "RAG vs. text-to-SQL, per query" surfaced, and no Reddit/HN community discussion of the problem turned up (WebSearch explicitly returned none).
- **Maturity**: SATURATED
- **Verdict notes**: Contrary to the digest's framing, a standardized, maintained router for exactly this decision already ships inside LlamaIndex (tens of thousands of GitHub stars, actively developed): `SQLAutoVectorQueryEngine` and the current `SQLRouterQueryEngine`/`RouterQueryEngine` pattern use an LLM selector to route a query to a SQL engine or a vector engine per-request (LlamaIndex blog, "Combining Text-to-SQL with Semantic Search for RAG"; developers.llamaindex.ai SQLRouterQueryEngine docs; Arize engineering tutorial on setting it up). The bespoke one-off routers the digest's papers (CSR-RAG, SurrealDB, eSapiens) each built are reinventions of a decision layer that a major, widely-adopted framework already standardizes and ships.

### P6: LLM-synthesized query expansion to train dense retrievers beyond literal query/document overlap
- **What it is**: Rather than fine-tuning a dense retriever only on real user queries, generate synthetic queries/expansions with an LLM that capture semantic relationships a literal query wouldn't surface, and train the retriever on those — a training-time technique, distinct from the already-covered "contextual retrieval" (which modifies chunks at index time, not the retriever model itself).
- **Evidence**: GitHub PR "Add ExpandR (EMNLP 2025) to 6.5 Retrieval-Augmented Generation" on `pengr/LLM-Synthetic-Data` (2026-11-04) — adding "ExpandR: Teaching Dense Retrievers Beyond Queries with LLM G[enerated expansions]" to a literature-tracking repo.
- **Why it looks unbuilt/untested**: Evidence here is thin and worth flagging honestly — this is a bibliography entry in a paper-tracking repo (0 reactions, no discussion), not a production adoption signal. Included because it names a specific, concrete technique not seen in prior digests, not because the signal strength is strong.
- **Maturity**: PARTIAL
- **Verdict notes**: An implementation exists but is a single-paper research artifact, not adopted: `github.com/NEUIR/ExpandR` is the authors' own EMNLP 2025 code release, with no PyPI/Hugging Face package, no downstream integration, and no adoption signal found in web search beyond citation trackers. A real, narrow, unevaluated-outside-its-own-paper implementation puts this at PARTIAL, not OPEN.

### P7: Swapping the generation model under a tuned RAG system silently breaks retrieval/prompt tuning, with no standard regression harness
- **What it is**: Teams that replace the underlying LLM in a production system (while keeping the surrounding application — frequently a RAG pipeline — unchanged) report the swap itself, not the model quality, as the expensive part: retrieval thresholds, prompt templates, and citation formatting tuned against the old model's quirks don't transfer, and there's no standard regression suite for "did the RAG behavior survive the model swap."
- **Evidence**: Reddit r/LLMDevs, "In a VentureBeat survey, 69% of people who swapped the model in a production AI system said it took weeks of engineering. What was the slow part for you?" (2026-11-13), citing VentureBeat Intelligence VB Pulse (Oct 2026): of 45 respondents who'd made a swap, 69% reported "a few weeks or more" of engineering work, 36% "more than a month."
- **Why it looks unbuilt/untested**: The survey and the Reddit discussion are about production AI systems generally, not RAG-specific tooling, and no dedicated "RAG model-swap regression harness" project surfaced — flagged as a RAG-adjacent gap rather than a strictly RAG-native one; weaker fit than P1–P5, included to round out the pattern count.
- **Maturity**: PARTIAL
- **Verdict notes**: General-purpose LLM/RAG regression-testing tools exist (DeepEval, Evidently, promptfoo, Traceloop per web search) and can be pointed at a golden set to catch model-swap breakage, and a FutureAGI blog post walks through a pytest harness + CI gate for exactly this failure mode — but none of these is purpose-built and packaged as a "did my RAG behavior survive the model swap" regression suite; teams are assembling the generic eval tools themselves each time. GitHub search for "RAG regression test model swap" / "RAG evaluation harness prompt regression" returned no dedicated repo. Real but narrow/DIY tooling → PARTIAL.
