### P1: Deterministic post-deploy behavioral regression detection from production traces, no LLM judge
- **What it is**: Tools that diff live production-trace metrics (tool-error rate, retry/loop counts, tool-call volume, answer length, cost, latency) between an agent's current release and its prior baseline, flagging "quiet" degradation that doesn't crash and wouldn't trip a standard error alert — explicitly avoiding an LLM-as-judge score.
- **Evidence**: Show HN "Apgar – Catch agent regressions without an LLM judge" (github.com/oimo-ai/apgar), posted 2026-10-29, 3 points on Hacker News. Repo: 9 stars, 2 forks, 29 commits, Apache-2.0, Docker/Helm/OTel+Langfuse ingestion.
- **Why it looks unbuilt/untested**: Single early-stage, single-maintainer project with 9 stars; no second maintained implementation of this specific "no-LLM-judge, production-trace baseline diff" approach turned up in the same search window.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch (GitHub + product + paper) found Apgar (9 stars, confirmed) plus a second real-but-narrow match, `agentevals` (OTel-trace-based scoring, no re-run, no LLM judge) and a DEV.to writeup advocating deterministic-checks-before-judge; also a June 2026 arXiv paper on a deterministic, no-LLM layer-isolated eval harness. No second *maintained, adopted* production-trace-baseline-diff tool found — Apgar remains single-maintainer/9★ and agentevals' maturity/adoption is unverified — so the gap is real but a careful build would be differentiated, not greenfield.

### P3: Tool-call-sequence snapshot/diff regression testing for agents, converging independently across multiple small tools
- **What it is**: Recording an agent's tool-call sequence (which tools, what parameters, what order) as a baseline "snapshot," then diffing new runs against it in CI to flag behavioral drift — independent of scoring output text.
- **Evidence**: Three separate Show HN launches pursuing the same idea within months: "EvalView – Catch agent regressions before you ship (pytest for agents)" (github.com/hidai25/eval-view, 2026-01-07, 2 points; repo has 142 stars/27 forks/PyPI package, but README self-describes as "a young project built mostly by one developer" and its latest release depends on the soon-deprecated OpenAI Assistants API); "Cobalt – Unit tests for AI agents, like Jest but for LLMs" (github.com/basalt-ai/cobalt, 2026-02-20, 3 points); "Evalcraft – cassette-based testing for AI agents (pytest, $0/run)" (github.com/beyhangl/evalcraft, 2026-03-06, 1 point).
- **Why it looks unbuilt/untested**: Three independent single-maintainer tools converging on the same core idea in under two months signals real, unmet demand — but none has consolidated adoption (highest is 142 stars), and the most-starred one is mid-deprecation-break on its underlying API dependency.
- **Maturity**: SATURATED
- **Verdict notes**: Beyond the digest's three (EvalView 142★/PyPI/GH-Action, Cobalt, Evalcraft), fresh GitHub + WebSearch turned up at least three more independent, packaged implementations of the identical mechanism: `agentsnap-py` (PyPI, pytest plugin, Jest-style snapshot diffing of tool-call traces), `AgentDiff`/`agent-trajectory-diff` (PyPI, pytest plugin + CLI, divergence-threshold assertions, PR-comment workflow), and `tracediff` (structural trajectory diff CLI, Markdown reports). ### P5: High-cardinality LLM telemetry (full prompt/completion text as span attributes) spikes observability cost with no standard mitigation
- **What it is**: Auto-instrumentation that captures entire prompts and completions as trace-span attributes creates high-cardinality data that spikes storage/ingestion cost in a way traditional APM telemetry doesn't — a cost-shape problem specific to LLM/agent tracing.
- **Evidence**: Comment by user `jas-park-dev` on the same Superlog thread (news.ycombinator.com/item?id=48195021): "auto-tracing drove storage costs up through attribute cardinality... The 'installs itself' magic is only useful if it doesn't blow up the bill," asking how the product handles high-cardinality AI prompt data (left unresolved in the visible thread). Separately, Show HN "Oodle.ai – $10 per million agent traces" (2026-07-14, 31 points / 12 comments) prices agent-trace ingestion as its own line item, treating this as a live, unsolved cost axis rather than a solved APM feature.
- **Why it looks unbuilt/untested**: Flagged as an open concern against a funded product with no resolving answer; no general technique (e.g., automatic prompt/completion sampling or cardinality-aware redaction built specifically for LLM spans) surfaced in the search.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found no packaged product or library that automatically solves LLM-span cardinality cost, but it did find several concrete, documented mitigation techniques already in individual practitioner use: capping/truncating `gen_ai.prompt`/`gen_ai.completion` attributes (~2KB, root-span-only), tail-based sampling policies that keep 100% of errors/high-cost traces and sample the rest, three-tier attribute classification (always-safe / hashed-truncated / excluded-by-default), and "record prompt identity (template ID) not content" schemas (tianpan.co, Gravitee, futureagi.com write-ups). These are one-off/ad-hoc practices spread across several blogs, not a shipped tool — real but narrow/unconsolidated mitigation knowledge, not a solved problem.

### P7: Tiered judge pipelines built to compensate for documented LLM-as-judge bias
- **What it is**: Combining deterministic checks on all traffic, a sampled LLM-judge pass, and a small human-labeled gold set used only to calibrate the judge — instead of trusting one LLM-as-judge score — in direct response to published findings that LLM judges carry measurable, stable biases even when internally self-consistent.
- **Evidence**: arXiv preprint 2606.19544 (surfaced via WebSearch), evaluating 21 judges across 9 providers, finding high test-retest reliability (>0.95) coexisting with severe position bias (>0.10) in two production-deployed judges; Google's public statement, reported late October 2026 via IT Brief, that "LLM judges are not objective arbiters of truth... they are subjective models with their own distinct biases"; a practitioner mitigation write-up (Adaline.ai blog, April 2026) reporting an +11.2 point agreement lift from position-swapping + chain-of-thought + rubric. No vote/engagement metric is available for any of these (academic paper, press coverage, vendor blog — not social-platform posts); recorded as explicit WebSearch results per the research-quality allowance for non-social evidence.
- **Why it looks unbuilt/untested**: Found only as scattered, individually-authored mitigation advice (one paper, one blog post, one press statement) rather than a shared, benchmarked reference implementation that others reuse — no widely-adopted "judge calibration layer" tool or library surfaced in the search.
- **Maturity**: PARTIAL
- **Verdict notes**: Beyond the digest's paper/blog/press evidence, WebSearch found an actual shipped implementation: `judicator` (PyPI, v0.2.4, 2026) — an open-source Python library that auto-detects judge type and screens for concreteness/yes-bias on binary judges. Also found a May 2026 arXiv paper (2605.09227) comparing hierarchical-Bayesian and Neural-ODE calibration methods, and an NUS project with a publicly released pipeline/dataset/code for modeling per-judge true/false-positive rates. These are real, usable implementations of the *calibration* piece, but none packages the full three-tier pipeline (deterministic-checks-on-everything → sampled-judge → human-gold-calibration) as one adopted product — the Grepture write-up describing that full tiered design is marketing-adjacent, not a tool. Narrow/unconsolidated but genuinely implemented in parts — PARTIAL, not OPEN.
