## Candidate patterns

### P1: DIY prompt-injection/jailbreak guardrail layers reinvented per-project, no shared library
- **What it is**: Across unrelated codebases, teams are hand-building near-identical input/output sanitizers, delimiter-based prompt-injection filters, and "jailbreak guard" modules from scratch inside their own app rather than adopting a shared, battle-tested layer.
- **Evidence**: Independent GitHub PRs/issues in the last 30 days each shipping a bespoke guardrail: `labsai/EDDI` PR #1064 "feat(llm): input and output guardrails on LLM tasks"; `nishit546/OpenPrep-AI` PR #2354 "AI Token Bucket Rate Limiting, Prompt Injection Guardrails & Daily Quota Guard"; `Prajna0106/PayPal-Seed` PR #13 "multi-agent guardrails, evals... 18-attack adversarial injection corpus"; `Sumit-ai-dev/Adaptive-Agent-Memory-OJT-G146` issue #39 "[SECURITY] Input Prompt Injection & Jailbreak Guardrail"; `kamisaberi/xtorch-examples` issue #313 "GenAI / LLM Prompt Injection Firewall (aryo trism)" — five separate from-scratch implementations of the same defense primitive in one month (last30days GitHub section).
- **Why it looks unbuilt/untested**: Each repo treats this as novel, bespoke work with its own corpus/delimiter scheme rather than pulling in an existing, independently-evaluated guardrail package — the duplication itself is the complaint-shaped signal (nobody reaches for a shared solution first).
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained, widely-adopted shared libraries already solve exactly this: NVIDIA NeMo Guardrails, Guardrails AI (guardrails-ai/guardrails), LLM Guard, OpenAI's official `openai-guardrails-python`, and Meta's Llama Guard/Prompt Guard are all actively maintained and squarely cover prompt-injection/jailbreak guardrail layers. The gap is adoption/awareness (teams not reaching for these), not absence of a shared library — GitHub search and WebSearch both surface a mature ecosystem, not a hole.

### P2: No visibility into LLM calls routed through third-party APIs — "run your own proxy or you're blind"
- **What it is**: Teams want (or have built) a self-hosted LLM proxy sitting between their app and the model provider specifically so they can see/intercept what's actually being sent and returned, instead of trusting the provider's own logging.
- **Evidence**: HN thread "If you don't run your own LLM proxy, how do you know whats going on?" — 303 points, 220 comments, 2026-10-18 (last30days HN section, item #11 in ranked clusters).
- **Why it looks unbuilt/untested**: High engagement (220 comments) on a thread framed as a complaint/plea ("how the f*** do you even know") rather than a product announcement — strong "I wish there was" signal with no dominant tool named in the thread title.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained, self-hostable proxy/observability products already do exactly this: LiteLLM's proxy, Helicone (self-hosted via docker-compose), Langfuse (self-hosted, OTLP traces), Portkey's gateway, and Bifrost are all shipped and actively used for intercepting/logging LLM traffic through third-party APIs. The HN thread's engagement reflects awareness/adoption friction, not a missing tool.

### P3: Guardrail classifiers inspect prompt segments; the model reasons over the full context — multi-turn/long-context evasion gap
- **What it is**: Guardrail/jailbreak classifiers (Llama Prompt Guard, IBM Granite Guardian, Perplexity BrowseSafe, Azure Prompt Shield, Meta Prompt Guard) score isolated chunks of a conversation, but the downstream LLM integrates the full multi-turn context — so attacks that spread intent across turns slip past the classifier even though the model "sees" the combined attack.
- **Evidence**: arXiv "Prompt Overflow: What the Guardrail Inspects Is Not What the Model Infers" (May 2026, via alphaxiv.org, surfaced in WebSearch supplement); a Reddit-sourced report (via aiweekly.co aggregator) of a "12-turn gradual-framing attack" defeating signature-based defenses in an internal bot; Lasso Security reporting a 36% bypass rate against Perplexity's BrowseSafe guardrail model; arXiv 2504.11168 "Bypassing LLM Guardrails: An Empirical Analysis of Evasion Attacks" also surfaced independently in the last30days GitHub tracker (`billbrietstout/ai-security-whitepaper-monitor` issue #529).
- **Why it looks unbuilt/untested**: Multiple independent papers/vendors across 2025-2026 are still documenting new evasion routes against the same handful of commercial classifiers — the problem is acknowledged repeatedly in research but no shipped guardrail product claims to have closed the segment-vs-context mismatch.
- **Maturity**: PARTIAL
- **Verdict notes**: Active but unsettled research area — THRD (arXiv 2606.01738, June 2026) is a training-free defense tracking cumulative intent across turns, and the Echo Chamber paper (NeuralTrust, Jan 2026) and aggregate reviews (character-injection/evasion up to 100% bypass against Azure Prompt Shield and Meta Prompt Guard) confirm the attack surface is real and current. No shipped, widely-adopted guardrail product claims to have closed the segment-vs-context gap — only defense papers and vendor acknowledgments, so this stays a genuine, differentiable build target rather than solved.

### P4: Guardrails only cover tool outputs, not the user's message or the model's final answer (one-directional screening)
- **What it is**: A common half-built state: teams add a guardrail on tool-call *results* (what a tool returns to the model) but leave the inbound user message and the model's final answer ungoverned, so a jailbreak or PII leak can pass through either end without a policy check, audit record, or metric.
- **Evidence**: `labsai/EDDI` PR #1064 problem statement, quoted verbatim in the last30days GitHub evidence: "Only tool results were governed (`ToolResultGuardrail`). Nothing screened the user's message or the model's final answer, so a jailbreak or PII could pass in either direction without a policy, an audit record or a metric."
- **Why it looks unbuilt/untested**: This is a maintainer explicitly diagnosing a gap in their own shipped system mid-fix — a real-world "we only did half of this" admission, not a hypothetical.
- **Maturity**: SATURATED
- **Verdict notes**: Bidirectional (input + output) screening is a built-in, composable pattern in multiple maintained frameworks already: LLM Guard ships separate input-scanner/output-scanner pipelines, Guardrails AI's validators run on both inputs and outputs via Guardrails Hub, NeMo Guardrails defines rails for both directions, and Bastion-Sentinel explicitly implements entry (Sentinel-IN) and exit (Sentinel-OUT) gateways. The EDDI repo's gap is a specific project not having adopted one of these yet, not evidence the general capability is missing.

### P5: Agent sandboxes stop code execution but not credential/egress exfiltration from a compromised agent
- **What it is**: Execution sandboxing (containers, microVMs) for agent-run code is treated as solved-enough, but the harder unsolved layer is what a compromised agent can still reach afterward — network egress to arbitrary endpoints and exposure of every API key/credential the agent was handed for its task.
- **Evidence**: NVIDIA's "OpenShell – A safe, private runtime for fleets of autonomous AI agents" drew 508 points / 217 comments on HN (2026-10-22, last30days HN section) — unusually high engagement for a sandboxing tool launch, suggesting the problem is top-of-mind; WebSearch supplement on agent sandboxing found vendor consensus that "without egress controls, a compromised agent can exfiltrate data to any endpoint" and "without secure credential delivery, a compromised sandbox exposes every API key the agent needs," plus a cited sandbox-escape CVE (WebAssembly Micro Runtime, CVE-2025-43853) and a note that wrapper scripts can bypass a sandbox's own approval/safety controls.
- **Why it looks unbuilt/untested**: The sources agree sandboxing is necessary-but-not-sufficient and explicitly flag egress/credential handling as the open problem, but none names a mature, widely-adopted product that solves the egress+credential layer specifically (as opposed to execution isolation).
- **Maturity**: SATURATED
- **Verdict notes**: Multiple shipped products already address this layer specifically: Vercel Sandbox enforces host-level (outside the microVM) deny-all-default egress with SNI/CIDR policy and credential injection so secrets never enter the sandbox; Straiker Heimdall issues resource-scoped, time-bounded credentials with independent egress/telemetry controls; Onyx and Akto Argus both do policy-gated egress proxying with placeholder-credential injection; Pipelock is an open-source forward-proxy firewall for exactly this. This is a well-resourced, actively-contested product category, not an open gap.
