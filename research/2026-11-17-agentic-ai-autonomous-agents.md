## Candidate patterns

### P1: Second-AI code review checks consistency with the first agent's output, not the original intent
- **What it is**: Teams increasingly point a second AI pass at agent-generated pull requests as a review gate, but the pattern people describe is the reviewer agent validating that code is internally consistent with itself rather than checking it against the original spec/intent — a false sense of assurance.
- **Evidence**: WebSearch synthesis on "AI coding agents shifted bottleneck to code review 2026" surfaced commentary (via coderabbit.ai, hackernoon, and related write-ups) framing this exactly: "the agents check code against itself rather than against intent," concluding a second AI pass "provides weaker guarantees than most teams assume." Separately, the Hacker News front-page item "Harvard researchers find AI coding agents shifted the bottleneck to code review" (60 pts, 93 comments, 2026-11-17, https://complexdiscovery.com/harvard-researchers-find-ai-coding-agents-shifted-the-bottleneck-to-code-review/) corroborates the bottleneck claim from an independent research angle.
- **Why it looks unbuilt/untested**: No named tool or methodology in the search results claims to verify agent-authored code against the *original task spec/intent* rather than internal code consistency — every vendor mentioned (CodeRabbit, Greptile) is pitched as a general review-automation layer, not an intent-verification layer.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found Aviator ("Verify") positioned almost exactly against this gap — it captures intent from the coding session, runs acceptance criteria against the running app, and explicitly markets itself against "same-model reviews it itself" blind spots by using a different model as reviewer (aviator.co/verify, docs.aviator.co/verify/how-it-works). But a StartupHub writeup of a 2026 AI Engineer talk by Aviator's co-founder describes it as still "piloting," and no second vendor or open-source project doing intent-level (vs. code-consistency) verification turned up in GitHub search (`gh search repos "code review intent verification agent"` returned zero results) or further web search — single-vendor, early-stage, narrow enough that a differentiated build remains viable.

### P2: Cost-threshold circuit breakers that force human escalation on expensive-to-run or expensive-to-review agent actions
- **What it is**: Rather than letting an agentic workflow run unconstrained, some teams are wiring per-action dollar-cost estimates into the gate itself: if the estimated cost of a review (or presumably any agent action) exceeds a configured limit, the automation skips/declines and escalates to a human instead of proceeding blind.
- **Evidence**: Direct GitHub evidence from the engine run — a real PR (pingdotgg/t3code #26254, 2026-10-28, 103 reactions / 25 comments) shows the "macroscopeapp[bot]" review bot literally skipping review with the message "Macroscope skipped reviewing this pull request. Per-review cost limit exceeded (workspace setting). This review would cost an estimated $26.45, which exceeds your per-review limit of $15.00," followed by a second comment flagging "Verdict: Needs Human Approval."
- **Why it looks unbuilt/untested**: This is a single vendor's one-off workspace setting inside a PR-review product, not a generalized pattern/library for cost-threshold gating across arbitrary agent actions (tool calls, API spend, compute time) — nothing in the evidence suggests this exists as a standalone, tool-agnostic circuit-breaker component.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search (`gh search repos "cost circuit breaker agent"`) surfaced exactly two repos matching this pattern — `devsoniclk/tripwire` (1 star, created 2026-11-15) and `rejisterjack/fuse` (0 stars, created 2026-11-08) — both literally days old with no adoption signal. WebSearch found `ai-loopguard` (github.com/deghosal-2026/ai-loopguard) escalates to a stronger model rather than a human on breach, and the Macroscope bot (cited in the digest) is a narrow one-off workspace setting inside one vendor's product. Dozens of dev.to posts describe the pattern as something teams hand-roll themselves ("combine a cost counter with a human-review queue yourself"), confirming no mature, tool-agnostic, human-escalating circuit breaker exists yet — real but immature/narrow implementations, so PARTIAL not OPEN.

### P3: Continuous "unsupervised" production evaluation to catch runaway/silent agent loops before cost accumulates
- **What it is**: A shift in framing from periodic offline benchmark evals to continuous online monitoring that watches live agent traffic for anomalies (loops, drift, unexpected tool use) rather than only testing before deployment.
- **Evidence**: WebSearch on agent observability surfaced a practitioner post (tianpan.co forum, https://tianpan.co/forum/t/your-ai-agent-loops-indefinitely-and-hallucinates-in-production-why-agent-observability-is-a-first-class-engineering-concern/918) describing a concrete incident: an agent "looped for 47 minutes and cost about $83 before anyone noticed," used to argue for continuous online evaluation over periodic benchmarks. Arthur's evaluation guide (surfaced in the same search) explicitly splits "supervised evals" (offline/regression) from "unsupervised evals" (continuous production monitoring) as the load-bearing distinction. The Hacker News item "OpenTelemetry and AI Agents' Observability" (9 pts, 2026-11-16, https://signoz.io/blog/opentelemetry-ai-agent-observability/) is dated signal that this is an active, current discussion, not stale.
- **Why it looks unbuilt/untested**: The sources name tracing vendors (Langfuse, Galileo, OpenTelemetry-based setups) but no one in the results describes a packaged, agent-specific "unsupervised eval" product that ships default anomaly/runaway-loop detectors out of the box — teams are assembling this from generic observability primitives themselves.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up WebSearch found this is more built-out than the digest's framing suggests: Prefactor ships runtime guardrails with named default detection signals (max-iteration hits, repeated-tool-call patterns, per-run cost outliers) plus continuous eval suites and per-agent anomaly alerts out of the box; Maxim AI runs periodic rule-based quality checks on production logs to "catch loop regressions early"; FutureAGI explicitly frames loop detection as a first-class eval+trace feature; Arthur's evaluation guide formalizes the supervised/unsupervised split the digest cites as the gap. At least 3 maintained, well-resourced vendor platforms already ship packaged continuous-production-monitoring with default loop/anomaly detectors — this gap is being closed, not open.

### P4: Risk-tiered autonomy scoping instead of binary "agent is allowed" / "agent is banned"
- **What it is**: Enterprises getting the most value from agents are reported to draw tighter, graduated boundaries on what an agent can do unsupervised based on task risk, rather than a single global autonomy switch — the opposite of both unrestricted rollout and outright bans.
- **Evidence**: WebSearch on "enterprises banning restricting autonomous AI agents 2026" surfaced a VentureBeat-sourced claim (via enterprisedna.co) that "the companies getting the most value from AI agents ... have drawn tighter boundaries around what agents can do alone," and a Gartner citation (via enterprisedna.co/beri.net) projecting 40% of enterprises will demote/decommission agents by 2027 due to governance gaps found only after production incidents, attributing the core problem to "treating governance as all-or-nothing." This pairs directly with real-world binary-ban incidents seen in the engine run itself: Hacker News "United Airlines bans AI agents from booking flights on behalf of travelers" (682 pts, 710 comments, 2026-11-11) and "Basically no one is using AI agents for their DoorDash orders" (178 pts, 336 comments, 2026-11-02) — concrete evidence of the all-or-nothing failure mode in the wild.
- **Why it looks unbuilt/untested**: The analyst commentary describes risk-tiering as a *goal* companies are reaching for, not a standardized framework or off-the-shelf tool — no named product in the results implements graduated per-task-risk autonomy policies; the Gartner/VentureBeat sourcing is secondary aggregation, not a verified primary methodology.
- **Maturity**: OPEN
- **Verdict notes**: Genuine multi-channel search confirmed the gap. GitHub: `gh search repos "risk tiered autonomy agent"` and `"agent autonomy policy tier"` both returned zero results. WebSearch surfaced only papers and architecture guides, not products: an arXiv governance paper separating capability from permission (2607.23438), an AWS Architecture Blog pattern description (probation/supervised/trusted tiers), a Data Science Dojo traffic-light tutorial, and an enterprise "A0-A4" framework writeup — explicitly concluding "I did not find a named, shipping commercial product for this specific tiered-autonomy model." Only discussion/frameworks/blog patterns exist, no implementation — genuinely OPEN.

### P5: No standard review/CI pipeline purpose-built for agent-authored code's distinct failure shape (bigger PRs, slower pickup, more defects)
- **What it is**: People are quantifying that agent-authored pull requests behave differently from human PRs — larger, slower to get picked up for review, and more defect-prone — and arguing this needs its own pipeline design (automated first-pass gates, risk-based triage, explicit SLAs, PR-size discipline), not a bolt-on to existing review tooling.
- **Evidence**: WebSearch synthesis cites specific (vendor-sourced, flagged as unverified) figures: "PRs created by autonomous AI agents take 5.3 times longer for a human to pick up and review than unassisted PRs" (LinearB 2026 benchmark via Synodus) and a parallel 4.6x figure from Faros AI; a LeadDev-sourced figure that "AI-generated pull requests contain about 1.7x more defects than human ones," with "29% of respondents report slower reviews with AI." Framed directly by Addy Osmani (quoted in the same synthesis): "The bottleneck moved from writing code to proving it works."
- **Why it looks unbuilt/untested**: The same sources note current remedies are vendor-specific partial fixes (CodeRabbit, Greptile) rather than a consensus pipeline design; the "teams pulling ahead" are described as having "invested in review infrastructure" ad hoc, not adopted a shared standard.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found real but fragmented point solutions: Tenki (labels/routes agent PRs to a faster review track), Cubic (automates initial PR triage risk-level scoring inside GitHub), and Shiplight (hosted CI runners pitched for "agent-written code," but only an uptime SLA, not a triage SLA). A GitHub Blog post ("Agent pull requests are everywhere, here's how to review them," 2026-03-30) confirms this is an acknowledged live problem being patched piecemeal. No consensus pipeline design or shared triage-SLA standard found across any source — narrow vendor point-fixes, not a built standard, so PARTIAL.

### P6: Fragmented sandbox/isolation layer for running fleets of agents, with no consensus abstraction level
- **What it is**: Multiple competing isolation primitives for executing untrusted/autonomous agent code are emerging in parallel — container-based (Docker/runc), user-space kernels (gVisor), microVMs (Firecracker/E2B), ephemeral worker sandboxes (Cloudflare Dynamic Worker Loader), and Kubernetes-native custom resources — with commentary that the older container-only approach "isn't cutting it anymore."
- **Evidence**: Engine-sourced Hacker News item "OpenShell – A safe, private runtime for fleets of autonomous AI agents" (508 pts, 217 comments, 2026-10-22, https://github.com/NVIDIA/OpenShell) is itself direct evidence of a new entrant trying to solve this. WebSearch on "sandboxed runtime for fleets of autonomous AI agents 2026" corroborates with a guide (dev.to) explicitly walking through "Firecracker, gVisor, runtimes, isolation strategies" as unsettled tradeoffs, and names at least five distinct commercial/open approaches (Fly.io, E2B, Browserbase Runtime, Blaxel, Kubernetes Agent Sandbox) competing on the same problem with no shared abstraction.
- **Why it looks unbuilt/untested**: 508 points and 217 comments on a brand-new entrant (OpenShell) in a space that already has five-plus competing approaches is itself the signal that nothing has consolidated — the WebSearch sources explicitly caution there is "no authoritative comparison" across these primitives yet.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up WebSearch found the unification layer the pattern implies is itself already being actively built by multiple well-resourced parties, not just the raw runtime fragmentation: ComputeSDK (open-source, unified API across 9+ sandbox providers, multi-provider failover), Rivet's Sandbox Agent SDK (Feb 2026, unified session-event schema, 15MB Rust binary), OpenAI's Agents SDK (Apr 2026 update adding a provider-agnostic sandbox Manifest reported to work across 7 providers), and OpenSandbox under the Agentic AI Foundation (Oct 2026, lifecycle API in front of Docker/Kubernetes). Four-plus maintained efforts, including one from OpenAI itself, are already racing to close exactly this abstraction gap — not consolidated into one winner yet, but clearly being closed by well-resourced teams rather than sitting open.

### P7: Enterprises lack basic visibility/inventory into which AI agent identities exist and what they can access
- **What it is**: Distinct from *delegating* permissions to agents, this is the more basic discovery problem — organizations don't have a reliable inventory of what autonomous agent identities are running inside their systems or what access each one actually holds, before any permissioning question is even reached.
- **Evidence**: WebSearch on enterprise agent restrictions surfaced a security-vendor-cited survey finding "92% of organizations have no full visibility into their AI identities and agents," linked to teams not fully adopting autonomous agents "because of fears about the access and permissions those agents hold." This is echoed by the Fortune-sourced framing (via the same search) of CIOs "racing to put guardrails around" agents described as "going rogue."
- **Why it looks unbuilt/untested**: The sources frame this as an open, unresolved survey finding rather than pointing to a mature, widely-adopted agent-identity-inventory product; this is a discovery/visibility gap, which is a narrower and earlier-stage problem than the permission-*delegation* tooling gap noted in prior digests on this topic.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up WebSearch found this gap is already being closed by well-resourced identity-platform vendors: Microsoft Entra Agent ID is confirmed generally available (Microsoft's own docs/blog, licensing included for all Entra customers) and explicitly targets "shadow AI and agent sprawl" inventory; Okta for AI Agents reached GA on 2026-04-30, with Universal Directory extended to "register AI agents across any agent framework, cloud, or SaaS environment" — a direct hit on the inventory/visibility gap described; Google's Agent Identity for Vertex AI is also cited as modeling agents as first-class identity principals. Two independently shipped, GA, well-resourced platform products (Microsoft, Okta) squarely cover the described gap — SATURATED, not the open discovery problem the digest framed it as.
