## Candidate patterns

### P1: Ambiguous agent-facing tool descriptions on eval-platform APIs causing systematic, misdiagnosed validation errors
- **What it is**: An eval/observability platform's API is called directly by AI agents (not humans), and an ambiguous tool description leads agents to pass the wrong target type on every call — producing a steady stream of validation errors that look like noise until someone traces them to one bad sentence in the tool's description.
- **Evidence**: PostHog/posthog PR #129079 "fix(aio): tell agents llma-evaluation-run takes generation evals only" (2026-11-04, 4 comments). PR body: "Agents call `llma-evaluation-run` with trace- and session-target evaluations, and the API rejects every call with `evaluation_target_mismatch`. This bucket holds most of the tool's validation errors over the last 14 days, across many users. The tool description says 'a specific $ai...'" (truncated, ambiguous). Corroborating context from WebSearch: a tianpan.co post ("the tool description that rotted while your agent kept calling it", cited via search) describes the identical failure shape generically — a description that goes stale after an API field changes required-ness, producing repeated failing calls that dashboards misread as transient.
- **Why it looks unbuilt/untested**: Patched as a one-line copy fix inside PostHog's own tool description; no general tool/observability layer was found that detects "this cluster of API validation errors is actually an agent-facing tool-description bug" and flags it distinctly from genuine user error, across eval/observability platforms broadly.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub + web search found real but narrow/immature adjacent tooling, none squarely covering the gap: `vtensor/mcpolish` (static linter flagging vague/colliding MCP tool descriptions pre-deployment, created 2026-05, no visible star traction), `mcp-tool-lint` (npm, similar static pre-deployment check), FlareCanary and DriftGuard-style hosted schema-drift monitors (compare manifests over time, not post-hoc error-cluster diagnosis), plus academic TOOLFUZZ (arXiv 2503.04479, tests tool docs for description-caused failures) and AgentFixer (arXiv 2603.29848, failure-detection-to-fix for agentic systems generally). All of these address tool-description quality or drift at authoring/monitoring time; none does the specific thing this pattern needs — correlating a cluster of live `validation_error` responses on an eval/observability platform's own API back to "this is a stale tool description, not user error," distinct from the PostHog one-line fix. No ≥2 maintained, widely-adopted products found doing this specifically, so not SATURATED; real fragmented prior art rules out a clean OPEN.

### P2: Dry-run / live preview of a new LLM eval against sampled real traffic before it's committed
- **What it is**: Letting someone see what a newly-configured evaluation (filter, judge, or check) would actually flag on real production traffic before it's switched on for real — rather than finding out only after creation that the filter was wrong.
- **Evidence**: PostHog/posthog PR #130326 "feat(aio): show a live preview of a new evaluation on real traffic" (2026-11-05, 7 comments). PR body: "People setting up an evaluation see no result until it runs on live traffic, so a wrong filter or check shows up only after they create it." Follows PR #130086 (merged) adding a summary side panel.
- **Why it looks unbuilt/untested**: Solved internally as a PostHog UI feature. WebSearch supplement on "shadow mode" / online-vs-offline eval practice found consistent generic advice to shadow a candidate judge on live traffic before trusting it, but no portable, vendor-neutral tool or library that previews an eval definition against sampled live traffic independent of one platform's own UI.
- **Maturity**: PARTIAL
- **Verdict notes**: "Shadow testing" is a well-documented generic practice (Arize glossary/blog, Statsig, tianpan.co's "shadow traffic for AI systems" post) and LiteLLM ships a real, maintained vendor-specific implementation ("auto-router shadow evaluations," docs.litellm.ai) — but that shadows candidate *model/routing* versions against production, not a newly-authored *eval definition* (filter/judge/check) being previewed before activation, which is PostHog's specific feature. No standalone, vendor-neutral tool or library found that does eval-definition preview-on-live-traffic independent of one platform's UI, confirming the digest's framing. Mechanism (shadow/replay live traffic) is SATURATED as a general concept with maintained implementations; the specific "preview an eval before you commit to it" packaging is not — PARTIAL per the tie-to-PARTIAL rule.

### P3: Losing in-progress eval configuration when switching authoring method, and no way to backtest against past traffic at create time
- **What it is**: In an eval-authoring UI, switching between configuration methods (e.g., prompt-based vs. code-based judge) silently discards the user's in-progress prompt/code, and there's no way to check a new eval against *past* traffic while still at the creation step (only going-forward preview, and only after a trip through separate configuration flows to pause/resume).
- **Evidence**: PostHog/posthog PR #129476 "feat(aio): tighten the eval create flow and eval page" (2026-11-04, 6 comments). PR body: "People creating an evaluation lose their prompt or code when they switch method and back. A team roast of the eval creation flow found the create page and eval page dense and slow to act on: no way to cover past traffic at create time, pausing needs a trip through the configuration f[low]."
- **Why it looks unbuilt/untested**: Fixed as an internal UX pass inside one product (explicitly surfaced by an internal "team roast," i.e. dogfooding feedback, not a feature request from outside). No generalized eval-authoring pattern (state-preserving method switching + historical-traffic backtest at creation time) was found documented or packaged as a reusable library/spec.
- **Maturity**: PARTIAL
- **Verdict notes**: The "backtest against past traffic" half is mature and multiply-implemented — LangSmith/LangChain's documented backtesting (builds a dataset from production inputs), PromptLayer's "backtesting prompt changes" (exact-match/semantic/LLM-judge/human comparison), and Sift's route backtesting (24h result caching) are all maintained, shipped features. But none combine that with the *other* half of this pattern — preserving an in-progress draft across a method switch *at creation time itself* — which stays product-specific: Langfuse's "restore evaluator versions" (2026-08-27 changelog) lets you test a restored draft before saving, and Glean's agent lifecycle has discard/rollback, but neither addresses losing state mid-switch during initial authoring. No reusable library/spec packaging both halves together was found. Backtesting-alone would be SATURATED, but the pattern as described (the combined authoring-flow gap) is not squarely covered — PARTIAL.

### P4: Naive structural (bracket-balance) checks in automated code-fix judges produce false "truncated" flags on valid fixes
- **What it is**: A code-review judge/evaluator that scores whether an LLM-proposed fix is well-formed uses a cheap structural heuristic (does a bracket/opener ever close) instead of real parsing with context — so a fix that replaces lines cut mid-block inherits the pre-existing imbalance of the code it replaced and gets wrongly flagged as truncated.
- **Evidence**: kodustech/kodus-ai PR #2302 "fix(code-review): do not flag a fix as truncated when it inherits the imbalance of the lines it replaces" (2026-10-29, 17 comments — real back-and-forth). PR body: "`checkFix` returned `'truncated'` whenever `isStructurallyBroken(fix)` found an opener that never closes, without looking at `existingCode`. When the lines a finding quotes cut a block, the fix replaces those lines and inherits the same open bracket, so a fix the judge had p[roposed]..." gets wrongly rejected.
- **Why it looks unbuilt/untested**: Patched ad hoc inside one AI code-review product's internal judge; no general-purpose "is this diff actually truncated, accounting for inherited structural imbalance from the replaced context" validator was found as a standalone library usable by other LLM-judge-based code-review tools.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos` for "code review judge truncated fix bracket balance", "diff truncation detector", "LLM code fix validator truncation detection", and "diff parser truncated code detection AST" returned nothing relevant (irrelevant classroom/lab repos only). WebSearch for the inherited-imbalance failure shape surfaced only tangential academic work — arXiv 2505.17928 ("Towards Practical Defect-Focused Automated Code Review," proposes code-slicing for cross-hunk context and a false-positive filtering step, but doesn't address bracket-balance truncation specifically) and arXiv 2603.00539 (documents LLM judges over-rejecting correct code generally). No standalone library, product, or paper was found that does structural-imbalance-aware truncation detection for LLM-judged code fixes. Genuine multi-channel search found only discussion-adjacent papers and the single kodustech ad-hoc patch — OPEN.

### P5: Replacing LLM judges/classifiers with a cheap deterministic decision model where the LLM's judgment isn't actually load-bearing
- **What it is**: A push to identify the subset of LLM-judge or LLM-classification calls in a pipeline that are really just routing/threshold decisions in disguise, and swap those specific calls for a small deterministic decision model — cutting judge latency/cost without touching the calls that need genuine LLM judgment.
- **Evidence**: Hacker News "Not Everything Needs an LLM" (newsletter.posthog.com/p/decision-models, 2026-11-17, 186 points/75 comments — the highest engagement item in this run, strong complaint-shaped signal against reflexive LLM-judge use).
- **Why it looks unbuilt/untested**: The cited piece is an essay/newsletter post, not a tool. WebSearch supplement surfaced abundant generic "when to use LLM as judge" vendor guidance but no tool that profiles an existing eval/observability pipeline's judge calls and identifies which ones are decision-model-replaceable (as distinct from this digest's P2/P8-style prior-cycle patterns on caching or skipping LLM judges, which assume the call stays an LLM call).
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos` for "LLM judge replace deterministic decision model" and "LLM judge cost profiler pipeline" returned zero relevant results. WebSearch found two adjacent-but-not-matching items: Openlayer's "jevals" lets a team manually swap an already-identified LLM-judge step for a typed decision definition (the mechanism exists, but requires the user to already know which calls qualify — it doesn't discover them), and a DEV Community reference to a "PAJAMA" paper on distilling judges into programs (unverified, paper not retrieved, and distillation of one judge differs from auditing a whole pipeline to find which calls are decision-model-replaceable). The specific discovery/profiling tool this pattern describes — scan an existing pipeline, flag which judge calls are secretly deterministic routing decisions — was not found anywhere. OPEN.
