## Candidate patterns

### P1: Supervisor + narrow-worker orchestration over free-form multi-agent "debate"
- **What it is**: Production multi-agent systems converging on a supervisor agent routing to narrow, specialized worker agents with explicit handoff schemas (2-4 agents), rather than unconstrained debate-style agent-to-agent negotiation.
- **Evidence**: WebSearch (`"has anyone built" AI agents multi-agent orchestration reddit 2026`) surfaced a synthesis of builder advice: "production setups tend to use 2-4 specialized agents with explicit handoff schemas... threads overuse debate patterns; supervisors + narrow workers ship faster" (infinisynapse.com, unverified attribution to Reddit discussion), and a separate guide (heyuan110.com) naming Pipeline/Router/Orchestrator-Worker/Evaluator-Optimizer as the recurring named architectures.
- **Why it looks unbuilt/untested**: No single reusable framework enforces the narrow-worker-boundary + handoff-schema combination as a built-in primitive; the advice circulating is pattern-naming, not a shipped library people point to.
- **Maturity**: SATURATED
- **Verdict notes**: `langchain-ai/langgraph-supervisor-py` is exactly this primitive (prebuilt `create_supervisor`/`create_handoff_tool` for narrow-worker handoff schemas), 1,653 stars, 264 forks — now folded into the core `langgraphjs`/`langgraph` monorepo rather than abandoned (the "archived" flag reflects the merge, confirmed by the companion JS repo's "REPOSITORY MOVED" notice). Microsoft Agent Framework (GA April 2026, merger of AutoGen + Semantic Kernel) ships named Handoff/Magentic orchestration patterns, and CrewAI/AutoGen both document orchestrator-worker roles directly (per an Arize comparison updated October 2026). This is a built-in feature of ≥2 well-resourced, maintained frameworks, not just circulating advice.

### P3: Missing practitioner-facing test harness for AI agent memory systems
- **What it is**: A reusable benchmark/eval harness that runs standard scenarios (session persistence, deduplication, fact drift, lifecycle/expiry) against whichever memory backend a team has plugged in — the equivalent of LangSmith for prompts or Ragas for RAG, but for agent memory specifically.
- **Evidence**: WebSearch (`AI agent memory evaluation "I wish there was" OR "why is there no" 2026`) found a DEV Community 2026 post stating plainly: "prompts have LangSmith, RAG pipelines have Ragas, and APIs have Postman, but agent memory lacks an equivalent," proposing a harness to run scenarios against multiple memory backends. A NeurIPS 2026 abstract separately argues memory evaluation is "stuck in a question-answer format" and should instead measure the actions agents take.
- **Why it looks unbuilt/untested**: Academic benchmarks are just emerging (MemoryAgentBench at ICLR 2026, MELT from mid-2026) but are research artifacts with code/datasets, not integrated developer tooling; the complaint is specifically about the absence of the practitioner-facing product, which the academic work doesn't fill.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found a genuine gold-rush of attempts in this exact window — `ProsusAI/MemEval` (63 stars, pushed 2026-11-10), `nuk3s/memeval` and `Anupam1612/memeval` (0 stars each, confirmed via `gh api`), Supermemory's "MemoryBench" (authors themselves caution small runs don't establish reliable rankings), `memtrust`, MELT, and Veracium (arXiv paper + pip package) — plus mem0's own "DolphinBench" leaderboard from a well-resourced 68.9k-star vendor. But no single harness has consolidated adoption or cross-backend neutrality (mem0's own benchmark is vendor-run, not independent); most are <6 months old with near-zero stars. Real attempts exist, no Ragas-equivalent has won — textbook PARTIAL.

### P4: Converting production agent failures into standing regression-test suites
- **What it is**: A workflow where specific agent failure traces captured in production are systematically mined into an evaluation dataset, so a bug caught once becomes a permanent regression check rather than a one-off fix.
- **Evidence**: WebSearch (`agentic AI production failures observability debugging agents 2026`) surfaced a practitioner write-up stating "the best teams convert problematic traces into evaluation datasets — creating a feedback loop where production failures become regression tests," alongside a cited (unverified-methodology) figure that roughly 89% of teams running agents in production have some observability, but only ~52% have eval pipelines that validate behavior quality.
- **Why it looks unbuilt/untested**: Described explicitly as something only "the best teams" do, by hand; the 37-point gap between observability adoption and eval-pipeline adoption is the gap itself — most teams collect the trace data but have no systematized tool to turn it into tests.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained, well-resourced commercial products already ship this exact loop as a built-in feature: Braintrust lets teams add failed production cases directly into regression datasets alongside evals/traces; Arize's "Signal" groups recurring production trace patterns into investigations with a save-to-dataset action; Judgment Labs' docs describe the full "failed production trace → dataset row → regression test → run comparison → production monitoring" pipeline natively. Some hand-off steps still need manual curation per Arize's own admission, but the core workflow is a shipped, maintained product feature at ≥2 vendors, not just something elite teams duct-tape by hand.

### P5: No tooling reliably catches silent/latent agent failures (fabricated tool results, context corruption)
- **What it is**: Agents that skip actual tool execution and fabricate plausible-looking results, or that corrupt internal context several turns before a visible symptom appears, with nothing resembling a crash to alert anyone.
- **Evidence**: Same WebSearch supplement cites a vendor write-up calling fabricated tool results "a documented failure across major frameworks," and another describing "context corruption that happened three turns ago and silently propagated forward through every subsequent decision"; a separately cited (flagged-unverified) stat claims tool-call errors account for 42% of pipeline failures reaching end users.
- **Why it looks unbuilt/untested**: Named observability tools in the same results (Langfuse, Arize Phoenix, Braintrust, LangSmith, Datadog LLM Observability) are described as capturing traces, but the sources note detection of silent fabrication is still manual trace review, not an automated flag.
- **Maturity**: PARTIAL
- **Verdict notes**: Research is live (a NeurIPS 2026 paper, "When Tools Fail, Agents Fabricate," studies the exact failure mode; an arXiv preprint reports a rule-based detector with high recall on one extraction workload) and narrow OSS attempts exist (a small "TrueCall" post-condition verifier claimed on a blog, though it could not be located/verified on GitHub under that name; a DEV Community "Silent Failure Detector"). General observability platforms (Galileo, Langfuse, Arize) capture traces but, per the sources themselves, don't automate fabrication detection as a distinct flag. Real but narrow, unevaluated, pre-product — PARTIAL, not OPEN, given the active research + indie-tool activity.
