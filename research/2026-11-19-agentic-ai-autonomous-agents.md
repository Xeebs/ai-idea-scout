## Candidate patterns

### P1: Per-project agent context isolation via a manager-agent + shared-notes-store pattern
- **What it is**: Rather than one long-lived agent session, people run one agent per client/project supervised by a "manager" agent, with project context persisted outside the chat (SQLite with full-text search, or a shared notes tool every sub-agent reads/writes) so context survives session resets and doesn't leak across clients.
- **Evidence**: Hacker News "Ask HN: How do you manage your AI agents' context across clients and projects?" (103pts, 71cmt, 2026-11-07, https://news.ycombinator.com/item?id=50403153) — commenters describe the manager-agent-plus-SQLite-plus-shared-notes setup. WebSearch corroboration: Indie Hackers posts ("context management is honestly the biggest bottleneck right now"; "context gets lost between sessions... have to re-feed it"); a Product Hunt launch ("pmb") scopes memory per-workspace specifically so one client's memory doesn't leak into another's, and its maker states "provenance... is still missing across most tools."
- **Why it looks unbuilt/untested**: The HN thread is people describing hand-rolled duct-tape (raw SQLite, ad hoc notes files), not a shared tool or standard; the PH maker explicitly flags the decision-provenance piece as still missing even in a dedicated memory product.
- **Maturity**: PARTIAL
- **Verdict notes**: Searched GitHub + web: adjacent building blocks ship widely (Cloudflare Agent Memory service, Anthropic Claude Managed Agents memory beta, AWS AgentCore session isolation, PraisonAI `MultiAgentContextManager`, the "blackboard" shared-notepad repo) but none combines a supervising manager-agent with a shared per-project notes store in one maintained package — the exact HN-described workflow is still hand-rolled (raw SQLite + ad hoc notes), so the gap is real even though isolated pieces exist.

### P2: Model-judged context pruning (swap junk tool output for a one-line summary, not full-transcript retention)
- **What it is**: Instead of keeping every raw tool-call result in context forever, let the model itself decide when a tool output is "junk" and replace it with a one-line summary immediately, paying the summarization cost once rather than re-reading bloated output every subsequent turn.
- **Evidence**: GitHub feature request on `google-antigravity/antigravity-cli`, "[Feature Request]: Let the model replace a junk tool output with a one-line summary (model-judged context pruning)" (2react, 2cmt, 2026-11-05, https://github.com/google-antigravity/antigravity-cli/issues/1429). WebSearch corroboration: an arXiv preprint ("Less Context, Better Agents") found pruning to the last 5 tool call/response pairs beat full history on a 50-task benchmark (79.0% vs 71.0% accuracy) while cutting tokens ~64%; Anthropic's multi-agent engineering writeup describes subagents writing large outputs externally and passing back only lightweight references.
- **Why it looks unbuilt/untested**: The GitHub issue is an open, barely-engaged feature request (2 reactions) against a specific CLI, not a shipped capability; WebSearch found guides and one research paper but explicitly "did not find a named 2026 agent framework that ships 'junk tool output' pruning as a built-in feature."
- **Maturity**: SATURATED
- **Verdict notes**: Despite the narrow GitHub issue being thin, the general capability is already shipped by multiple well-resourced teams: Anthropic's own API/cookbook offers first-party context editing with `clear_tool_uses`, Agno ships automatic tool-output compression, Relevance AI ships goal-aware compaction (claims 80%+ token reduction), and the open-source `pi-context-prune`/`pi-condense` family implements model-judged pruning directly (model calls `context_prune`, cheap summarizer model). Research corroborates (Squeez/arXiv 2604.04979, ACON, DTOC). The specific CLI feature request is unbuilt, but the pattern itself is closed.

### P3: With-skill vs. without-skill A/B evaluation + trigger-check for agent skills
- **What it is**: A testing discipline that measures whether a given "skill" (prompt/tool bundle) actually improves agent task performance by running the same tasks with and without the skill loaded, and separately checking whether the agent even invokes the skill when it's relevant.
- **Evidence**: Hacker News "Ask HN: How do you evaluate the skills your AI agents use?" (25pts, 8cmt, 2026-11-09, https://news.ycombinator.com/item?id=50426070). WebSearch found this pattern already has multiple implementations: Tessl's research framework (claims ~20% absolute accuracy gain from skill access across a skill corpus), a LangChain blog pipeline that also flags when Claude Code never triggers a given skill, an arXiv paper (2606.17819) testing 500 open-source skills, and PyPI packages `coder-eval` and `agent-skill-eval`.
- **Why it looks unbuilt/untested**: The HN question itself (low engagement, people still asking "how do you evaluate skills") suggests the existing frameworks found by WebSearch haven't reached mainstream awareness/adoption — worth flagging to gap-analyst as likely PARTIAL rather than OPEN given the Tessl/LangChain/arXiv/PyPI hits.
- **Maturity**: SATURATED
- **Verdict notes**: Confirmed multiple maintained implementations covering both halves of the pattern: PyPI `coder-eval` (UiPath, 40+ releases, explicitly has a `skill_triggered` activation check plus an A/B experiment layer and CI gates), PyPI `agent-skill-eval` (0.14.0, runs the same agent CLI with/without the skill across OpenCode/Claude Code/Codex), and `caliper-eval`. Tessl ships this commercially as "Task Evals" (runs each skill with/without, reports ~20% accuracy gain across a skill corpus), and an arXiv paper benchmarked 500 skills. Low HN engagement reflects awareness lag, not absence of tooling.
