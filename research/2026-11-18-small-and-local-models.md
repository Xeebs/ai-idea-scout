## Candidate patterns

### P1: Classifier-based local-first router with cloud fallback
- **What it is**: A small local model (often a 1-4B classifier or a 2B generalist like Gemma4-2B) handles every request first; a lightweight confidence/quality gate decides whether to escalate to a cloud model, instead of routing by task type alone.
- **Evidence**: WebSearch surfaced the "Cactus Hybrid Router" (local Gemma4-2B + Gemini fallback) reported to match Gemini 3.1 Flash-Lite quality while sending only 15-55% of tasks to the cloud (per specpicks.com and aiweekly.co coverage); a parallel "SLM-default, LLM-fallback" pattern documented for Microsoft's Agent Framework + Azure AI Foundry (strathweb.com) and a "Local Preflight for Cloud Agents" writeup for Codex CLI (codex.danielvaughan.com) describing a confidence gate that escalates below a score threshold.
- **Why it looks unbuilt/untested**: Every example found is a single vendor's blog writeup or a bespoke home setup (one person's Ollama+Hermes rig per johnnybilotta.com) — no shared, reusable open-source router library with a trained classifier came up; LiteLLM's fallback is a dumb retry-on-failure, not quality-based routing.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found only hobby-scale implementations: EdgeRouteAI (github.com/harishkotra/edgerouteai, 1 star, last push 2026-01), LFO (github.com/MasteraSnackin/LFO, 2 stars, last push 2026-02), and LocalForge (github.com/al1-nasir/LocalForge, 7 stars, last push 2026-04) — all single-author, low-adoption confidence-gated routers. Cactus Hybrid Router and the Microsoft Agent Framework pattern are vendor blog writeups, not open libraries; LiteLLM's routing is error/timeout fallback, not quality-based. No maintained, widely-adopted router with a trained classifier exists yet.

### P2: Small decoy model as a prompt-injection firewall for agentic tool use
- **What it is**: Untrusted input (web pages, tool output, log lines) is routed through a small, disposable local model first; only its sanitized judgment — not the raw untrusted text — reaches the production model or triggers tool calls.
- **Evidence**: WebSearch found Hermes Labs' "little-canary" (Qwen 2.5:1.5B decoy) reported to raise attack refusal from 69.2% to 98.6% on a 208-prompt benchmark (hermeslabs.substack.com, vendor-reported); "CourtGuard," a local multi-agent classifier using small models as prosecution/defense/judge (arxiv.org/html/2510.19844v1); and an October 2026 preprint testing Phi-4-mini (4-bit) as a security log-triage assistant that concluded "the verdict should be decided outside the language model" because prompt-based warnings failed to stop injected instructions.
- **Why it looks unbuilt/untested**: The academic paper explicitly states the small model alone is insufficient and recommends external deterministic checks; the "little-canary" and CourtGuard results are single-vendor/single-paper, not independently reproduced, and a secondary (unverified) claim reports local models comply with injected prompts up to 95% of the time in red-teaming.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search surfaced real narrow attempts — llm-fw (github.com/PIsberg/llm-fw, 9 stars, actively pushed 2026-11-17, docs admit a small generative judge over-blocks benign traffic), secuprompt (github.com/caviraoss/secuprompt, 14 stars, stale since 2025-11), Armorer Guard (deterministic Rust scanner, not a decoy model), and Hermes Labs' "little-canary" (single-vendor, unreproduced benchmark). The arXiv paper on tool-output firewalls explicitly recommends deciding outside the LLM. No implementation is both well-adopted and independently validated as a small-model decoy specifically.

### P3: DIY hardware-specific benchmark suites replacing generic leaderboards
- **What it is**: Individuals write their own small, personal eval sets tuned to their exact laptop/GPU and actual task, because public leaderboard scores for small/local models don't predict real-world usability on their hardware.
- **Evidence**: WebSearch found a dev.to/blog post titled "Your local LLM benchmark is probably lying to you" (bmdpat.com) arguing reported numbers lack context like missing denominators; another author states "I wrote my own small benchmark, tuned to exactly my laptop" (dev.to/llm_ops, "Your smallest local model might be your best one — I measured 4 of mine"); an Ask HN thread ("What is the best LLM for consumer grade hardware?") and a community roundup (local-llm.net) both frame Reddit/HN posts as anecdotal field reports rather than controlled measurement.
- **Why it looks unbuilt/untested**: Multiple independent people are solving the same "benchmark doesn't match my hardware/workload" problem by hand-rolling one-off scripts; no shared tool for generating a personal, hardware-aware eval set from a user's own task samples surfaced in any source.
- **Maturity**: OPEN
- **Verdict notes**: Web search found only fixed-suite tools — BenchLoop (frozen YAML task fixtures, custom tasks listed as a future item), PipelineScore (fixed 25-task suite), InferBench (tokens/sec only, no task quality), and recommender tools whichllm/llmfit (match hardware to published benchmark scores, don't build a benchmark from a user's own samples). No tool that generates a personal, hardware-aware eval set from a user's own task samples surfaced; a dev.to guide explicitly frames this as a manual, hand-rolled exercise.

### P4: On-device persistent memory layer for small local agents
- **What it is**: A storage/retrieval layer that lets a small local model (Phi-4 class or smaller) maintain agent memory across sessions on-device, without calling an LLM for memory operations and without sending state to the cloud.
- **Evidence**: WebSearch found "cognee-RS," described by Cognee as an "experimental" Rust SDK for private, on-device AI memory targeting Phi-4-class models with a config flag to switch to hosted models (cognee.ai/cognee-rust-sdk-for-edge); and "memU," a vendor blog describing a memory service that makes no LLM calls and argues small local models need external storage for memory to persist (memu.pro/blog).
- **Why it looks unbuilt/untested**: The company's own label is "experimental"; both sources are single-vendor blog posts, not independently validated projects, and no comparison or adoption signal (GitHub stars, community threads) was found for either.
- **Maturity**: SATURATED
- **Verdict notes**: Mem0 (github.com/mem0ai/mem0, ~69k stars, pushed 2026-11-17) officially supports fully offline/on-device operation pointing its LLM and embedder at local Ollama + a local vector store — this alone squarely covers the gap. Additional maintained options compound this: memlayer (divagr18/memlayer, active, pushed 2026-11-13, "plug-and-play memory for LLMs in 3 lines of code"), Engram (MIT, SQLite + local embeddings, MCP-native), and ClawMem (~180 stars per third-party listing). Multiple well-resourced, actively maintained implementations already close this gap.

### P5: Local small model as a PII-redaction pre-processor before cloud escalation
- **What it is**: A lightweight on-device model scans text for sensitive spans, replaces them with placeholders, and keeps a local placeholder-to-original mapping — so only redacted text, not raw PII, is sent to a cloud model when escalation is needed.
- **Evidence**: WebSearch found "MemPrivacy" (arxiv.org/pdf/2605.09530), a research framework for edge-cloud agents reporting the approach "beats general-purpose LLMs at span extraction and keeps memory useful better than plain masking."
- **Why it looks unbuilt/untested**: This is a single arXiv paper with no accompanying open-source repo or product found in the search; it's a research prototype, not a deployable tool anyone referenced using.
- **Maturity**: SATURATED
- **Verdict notes**: PasteGuard (github.com/sgasser/pasteguard, 837 stars, pushed 2026-11-17) is a close, actively maintained match — a local-first proxy that masks PII/secrets before cloud calls and has an explicit "route" mode sending sensitive spans to a local model instead of the cloud. Microsoft Presidio (github.com/microsoft/presidio, ~11,938 stars, pushed 2026-11-14) is the well-resourced, long-established baseline for redacting PII before text reaches an LLM provider. Two independently maintained, well-adopted implementations already cover this gap; the MemPrivacy arXiv paper is incremental research on top of an already-addressed problem, not evidence of a gap.

### P6: Single-consumer-GPU teacher-to-student distillation recipes
- **What it is**: Hobbyists and small teams distill a large teacher model (8B-27B) down to a small student (0.6B-4B) entirely on local/consumer hardware (one or two GPUs), using teacher answers, token probabilities, and QLoRA, for a single narrow task.
- **Evidence**: WebSearch found a hands-on writeup distilling a 4B Qwen student from a 27B teacher on two networked local GPUs (mindstudio.ai), converging to a score the author reads as a "capacity ceiling"; a separate case study distilling document-processing work into a 0.6B student trained with QLoRA, answering in under a second with summary faithfulness as the remaining weakness (dev.to, Adham Sersour); and hardware guidance that QLoRA can fine-tune a 7B model on a single RTX 4090 (blog.premai.io).
- **Why it looks unbuilt/untested**: Every example is an individual's one-off blog post describing their own pipeline from scratch; no shared, repeatable local-distillation toolchain (pick teacher + task + hardware, get a recipe) was found — each person re-derives the method.
- **Maturity**: PARTIAL
- **Verdict notes**: Two maintained, reasonably-adopted toolkits exist — EasyDistill (github.com/modelscope/easydistill, 488 stars, pushed 2026-09-25, backed by Alibaba's ModelScope, includes a Qwen2.5-7B→0.5B example) and DistillKit (github.com/arcee-ai/DistillKit, 1,095 stars, pushed 2026-05-12, backed by Arcee AI, offline mode designed for single-GPU VRAM constraints). Neither, however, automates "pick teacher + task + hardware, get a recipe" — both require the user to configure the pipeline manually, so the specific hobbyist pain cited (re-deriving the method each time) is only partially closed.

### P7: Device-aware quantization and fine-tuning method selection
- **What it is**: A pipeline that, given a target device's constraints, automatically picks both the fine-tuning method (full, LoRA, QLoRA) and the quantization level, rather than a human guessing a combination and iterating.
- **Evidence**: WebSearch found a 2026 MobiUK paper (dcs.gla.ac.uk/~josecr/pub/2026_MobiUK.pdf) describing a "device-aware pipeline that uses a cloud teacher to generate fine-tuning data, then picks a fine-tuning method and quantization based on the target hardware," validated on a healthcare fraud dataset; and a late-2026 preprint (preprints.org/manuscript/202609.0007-adjacent) on distilling/fine-tuning/quantizing a model for on-premise CPU inference in manufacturing.
- **Why it looks unbuilt/untested**: Both sources are academic papers validated on one narrow dataset/domain each (healthcare fraud, manufacturing); no general-purpose open tool that takes "my device + my task" and outputs a recipe was found.
- **Maturity**: OPEN
- **Verdict notes**: Web search found only narrow, hardware-vendor-specific quantization-only autosearch tools — AMD Quark Auto-Search (precision/calibration search, no GitHub link found, no fine-tuning-method selection) and ESP-DL AutoQuant (scoped to Espressif's ESP32 chips, quantization only). The one paper combining both decisions (HAQA, arXiv 2601.03484) states code is not yet released. No general-purpose open tool that takes "my device + my task" and outputs both a fine-tuning method and a quantization level was found.

### P8: Persistent warm prompt-cache across local multi-model agent sessions
- **What it is**: Instead of re-sending a growing conversation at full token cost every turn, an agent harness keeps one cache per chat warm across model swaps, compacting it once rather than repeatedly, and never discards prior local tool output from that cache.
- **Evidence**: Direct engine evidence (GitHub, via last30days) — a NousResearch/hermes-agent pull request ("Prompt cache stays warm for every model, compacts once then waits for you, and never loses tool output," opened 2026-11-16, 3 reactions/18 comments) describing exactly this mechanism for Hermes's local terminal backend.
- **Why it looks unbuilt/untested**: This is an open PR (not yet merged/shipped) on a single project; the mechanism is framed as new work being proposed, not an established pattern with prior art cited in the PR itself.
- **Maturity**: OPEN
- **Verdict notes**: GitHub and web search found no CLI or agent harness that keeps a prompt cache warm across a model swap — Claude Code's own docs describe cache expiry on a TTL rather than cross-model persistence, Morph's writeup confirms caches are scoped per model (switching models re-prefills the full context), and vllm-mlx/arXiv work on persistent KV caches targets server restarts, not cross-model swaps within one session. The only concrete instance is the open, unmerged NousResearch/hermes-agent PR itself — proposed new work, not prior art.
