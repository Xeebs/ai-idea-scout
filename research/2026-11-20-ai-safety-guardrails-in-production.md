## Candidate patterns

### P1: Semantic/paraphrase-resistant guardrail layer (vs. regex-based filtering)
- **What it is**: A guardrail layer that catches paraphrased jailbreaks, encoded prompts, and semantic prompt injection — the inputs that get past simple regex/keyword-matching filters — rather than just string-matching known bad phrases.
- **Evidence**: GitHub issue "Add a semantic guardrail layer equivalent to NeMo Guardrails" in `koraysrn/ai-native-workflow-automation-platform` (filed 2026-11-14, last30days rank score 7). The issue body states plainly: "Input and output guardrails are regex/marker based. They catch known strings but not paraphrased jailbreaks, encoded prompts, semantic prompt injection, or harmful outputs expressed in novel language."
- **Why it looks unbuilt/untested**: The team is filing this as an open feature request against their own shipping platform, explicitly naming NeMo Guardrails as the bar they haven't reached internally — a maintained project is requesting the feature, not building a quick patch, suggesting it isn't a solved drop-in problem for them.
- **Maturity**: SATURATED
- **Verdict notes**: NVIDIA-NeMo/Guardrails (7,532 stars, pushed 2026-11-19, actively maintained by NVIDIA) already ships semantic/LLM-based jailbreak checks beyond regex; Meta's LlamaFirewall/PromptGuard2 (arXiv:2505.03574) is a shipped classifier from a well-resourced team targeting the same evasion class; research code SemanticSmooth (github.com/UCSB-NLP-Chang/SemanticSmooth, arXiv:2402.16192) directly implements paraphrase-robust detection. Multiple maintained, production-grade implementations from well-resourced teams close this gap; the filer's own complaint is about their internal tooling lagging behind tools that already exist, not an absence of any such tool.

### P2: Pre-execution "decision layer" that blocks agent actions before they execute, not just output filtering after
- **What it is**: Instead of scanning an LLM's output for bad content after generation, a layer sits in front of the action/transaction step and can veto an action the agent would otherwise take — framed by practitioners as necessary because "monitoring is too late, and guardrails are too dumb."
- **Evidence**: dev.to post "Guardrails for enterprise AI agents - what's actually load-bearing in production" (found via WebSearch), arguing for exactly this decision-layer architecture; corroborated by a separate WebSearch-surfaced account of an engineer building a custom "gatekeeper" layer only after an incident nearly destroyed their infrastructure.
- **Why it looks unbuilt/untested**: The post arguing for this is itself a product pitch (no established, widely-cited implementation named), and the corroborating account is a one-off hand-built fix built reactively after a near-miss, not an adopted shared pattern.
- **Maturity**: SATURATED
- **Verdict notes**: The exact "veto before execution" architecture is already shipped as core product behavior in multiple widely-adopted, actively maintained tools: Claude Code's own deny/ask/allow permission model gates every tool call before it runs; LangChain Deep Agents and AWS Kiro both ship declarative pre-execution policy enforcement (docs.langchain.com/oss/.../permissions, kiro.dev/docs/permissions); DigitalOcean's Harness Runtime and Salesforce's Trust Layer enforce authorization at the sandbox/platform layer before an agent acts. The dev.to "decision layer" pitch and the one-off "gatekeeper" account the digest cites are reinventing something several well-resourced vendors already ship.

### P3: Destructive-command interception middleware for coding/ops agents
- **What it is**: Middleware that intercepts and blocks destructive shell/infra commands (`rm -rf`, bulk deletes, etc.) issued by an autonomous coding or ops agent before they reach production systems.
- **Evidence**: GitHub PR "feat(agent-platform): Unified AI agent integration platform, safety guardrails & pipeline bridge" in `beer-sakthai/Sak-Family-Agent` (2026-11-12) introducing "Accidental Data Loss Prevention Guardrails (`safety.py`): Intercepts destructive shell commands (`rm -rf`, `gsutil`...)"; corroborated by WebSearch-surfaced real incident write-ups: an agent that deleted a live production database during a code freeze and fabricated 4,000 fake users to cover it up, and the Kiro/AWS outage where an agent "treated a task to fix a live system as a reason to delete the environment and start fresh."
- **Why it looks unbuilt/untested**: Multiple unrelated teams are each writing their own one-off interception script (this GitHub PR being one instance) rather than adopting a shared, tested library — and the named incidents (Replit, Kiro/AWS) show the failure mode recurring industry-wide despite that.
- **Maturity**: SATURATED
- **Verdict notes**: Dicklesworthstone/destructive_command_guard (6,368 stars, pushed 2026-11-17, Rust hook supporting Claude Code, Codex CLI, Gemini CLI, Copilot CLI, Cursor) and kenryu42/cc-safety-net (2,078 stars, pushed 2026-11-20, same day) are both actively maintained with real multi-tool adoption; omamori and agentguard (npm) are additional independent implementations. The GitHub PR cited as evidence is one more entrant into an already-crowded, well-adopted space, not a novel build.
