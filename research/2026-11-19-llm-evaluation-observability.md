## Candidate patterns

### P1: Judge-prompt drift between calibration and runtime in auto-generated LLM-judge eval setups
- **What it is**: Products that auto-draft an "LLM judge" for a team's eval suite calibrate that judge against a sample of traffic, but the calibration pass and the actual runtime judge call can silently diverge (different context length, missing tool catalog, stale copy of the system prompt) — so the judge a team believes was validated isn't the judge actually scoring production evals.
- **Evidence**: PostHog/posthog PR #136283 "feat(aio): calibrate suggested judges on gemini" (2026-11-16, 2 reactions/6 comments) and its direct follow-up PR #136602 "fix(aio): calibrate suggested judges on the runtime judge's prompts" (2026-11-16, 1 reaction/5 comments), whose body states: "Calibration sent a few hundred characters of each call, without the tool catalog" and "Its copy of the judge's system prompt had drifted from the runtime one." Corroborating skepticism: Hacker News "Using LLM for confidence scoring is a bad idea" (rumple.github.io, 2026-10-21, 228 points/107 comments).
- **Why it looks unbuilt/untested**: PostHog is patching this ad hoc, inside its own product, as a bug fix rather than a reusable safeguard; no general, vendor-neutral tool that diffs/verifies a calibrated judge prompt against the exact runtime judge call before trusting its score.
- **Maturity**: OPEN
- **Verdict notes**: GitHub + web search found only PostHog's own internal bug-fix PRs (the cited evidence itself) and `homayoun-safarpour/judge-drift-sentinel` (0 stars, repo created 2026-11-08, a brand-new personal side project) — but that tool attributes eval-*score* movement to system-vs-judge via a frozen human anchor set and kappa, a different question from verifying the runtime judge prompt/context matches what was calibrated. Langfuse's published "judge calibration skill" only compares judge labels to ground truth on a dataset, with no check that the production judge call uses the same prompt/tool-catalog/context as calibration. No credible implementation closes this specific gap.

### P2: Catching agent regressions without relying on an LLM judge
- **What it is**: A detector for agent-behavior regressions (did this change break the agent's trajectory/output quality?) that deliberately avoids using an LLM as the judge, implying teams see LLM-judge-based regression checks as unreliable, slow, or expensive enough to actively route around.
- **Evidence**: Show HN "Apgar – Catch agent regressions without an LLM judge" (github.com/oimo-ai/apgar, Hacker News, 2026-10-29, 3 points). The title itself is the complaint-shaped signal: "without an LLM judge" is framed as the selling point.
- **Why it looks unbuilt/untested**: Extremely low engagement (3 points, no visible discussion) — a lone indie Show HN, not an established project; no maintained alternative-to-LLM-judge regression framework with real traction was found in this run.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub search for `hidai25/eval-view` confirms a real, actively maintained competitor to Apgar: 142 stars, created 2025-11-17, last pushed 2026-11-19 (today), description "Regression testing for AI agents. Snapshot behavior, diff tool calls, catch regressions in CI... no LLM-as-judge required for core checks," supports LangGraph/CrewAI/OpenAI/Anthropic, ships as a GitHub Marketplace Action. Web search also surfaced `agentdbg` (a `@trace` decorator + GitHub Action replaying test suites on each PR with zero LLM calls) and `eval-sanity` (zero-dependency deterministic trajectory checker). Multiple maintained implementations already squarely cover "catch agent regressions without an LLM judge" — Apgar is a late, low-traction entrant into an already-served niche.

### P3: Pass/fail semantics for conditionally-skipped judges in multi-judge eval harnesses
- **What it is**: In eval harnesses that run several LLM-judges per case, a judge whose `if:` condition never triggers for any selected case needs an explicit "N/A" outcome rather than being scored as a failed `min_pass_rate`/`min_mean` threshold — a correctness bug in how "no applicable cases" is distinguished from "failed."
- **Evidence**: fullsend-ai/agent-eval-harness PR #312 "feat(eval-run): treat all-skipped conditional judges as N/A" (2026-11-12, 2 reactions/20 comments — the comment count signals real back-and-forth on the right semantics). PR body: "Before this change they were reported as an `n/a` regression and failed the run."
- **Why it looks unbuilt/untested**: Fixed as a one-off inside a single company's internal eval harness; the 20-comment debate suggests the "right" semantics for conditional judges isn't yet a settled, documented pattern anyone else can just adopt.
- **Maturity**: PARTIAL
- **Verdict notes**: Web search found no dedicated tool for this, but confirmed the gap is real and handled inconsistently across the ecosystem: InstructorPHP's eval docs, `agent-exam`'s task-yaml spec, flow-ai's judge-eval docs, and Drupal's `ai_eval` module each define their own ad hoc skip/N/A/fail-closed semantics for conditional or errored judges, none citing a shared standard. Multiple narrow, framework-specific implementations exist (hence not OPEN) but none generalized or cross-adopted (hence not SATURATED) — a serious, documented reusable pattern would be differentiated.

### P4: Caching LLM-judge verdicts to take the judge off the latency-critical hot path
- **What it is**: Moving an LLM-as-judge gate check out of a request's synchronous hot path by caching the gate verdict, so judge-call latency/cost doesn't sit on every request.
- **Evidence**: ThePlenkov/bro PR #747 "perf(hooks): cached gate verdict, judge off the hot path (bro-36sx7.4)" (2026-10-28, 3 reactions/13 comments).
- **Why it looks unbuilt/untested**: A narrow, internal perf patch to one project's hook pipeline; no generalized "judge verdict cache" library or documented pattern for eval/observability tooling broadly was found alongside it.
- **Maturity**: PARTIAL
- **Verdict notes**: Web search found no dedicated standalone library, but real adjacent implementations: the `swink-agent-eval` Rust crate ships a bounded (1024-entry default) in-memory + optional-disk judge-verdict cache with versioned keys; an Apple research paper (Krites, semantic caching) keeps judge calls off the synchronous serving path; Microsoft Azure AI Foundry documents judge-prompt restructuring for provider-side prefix caching (5-16% latency reduction in their A/B test). These are real but narrow/niche (one Rust crate, vendor blog guidance, a research paper) — no widely-adopted, generalized "take the judge off the hot path" library.

### P5: A shared trajectory/lineage interchange format for agent observability
- **What it is**: A versioned format (streaming-capable, with lineage and "strong semantics") for recording an agent's full execution trajectory, aimed at making multi-step/multi-agent runs inspectable and comparable across tools rather than locked into one framework's internal trace schema.
- **Evidence**: harbor-framework/harbor PR #4134 "RFC: ATIF v2.0 with streaming, lineage, and strong semantics" (2026-11-06, 12 reactions/12 comments). A reviewer's top comment: "This is a major upgrade for agent trajectory observability!"
- **Why it looks unbuilt/untested**: Still an open RFC inside a single framework's repo, not yet a cross-framework/vendor-neutral spec that other agent-observability tools (Langfuse, Arize, PostHog) have adopted.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub confirms ATIF itself is still thin — the only companion tool found, `dentiny/atif-arrow` (converts ATIF to Apache Arrow), has 0 stars and was last pushed 2026-11-17. But the broader need (a shared, cross-tool agent-trajectory format) already has real competing partial coverage: OpenTelemetry's GenAI semantic conventions (gen_ai.* spans for model/tool/agent calls, reportedly parsed by Datadog, Langfuse, Phoenix, OpenLLMetry, AgentOps per vendor docs, though one source says the spec is still dev-status/opt-in) and Arize's separate OpenInference convention. Neither is a settled single standard and ATIF's "lineage/strong semantics" angle isn't covered by either — real but fragmented/early coverage, not SATURATED, not OPEN.

### P6: Precomputed rollups to keep LLM observability dashboards from re-scanning raw event history
- **What it is**: Replacing "re-read every raw sample on every dashboard load" with precomputed/incremental metric rollups so that 7- and 30-day tiles (including percentile histograms) stay fast and don't silently fail at scale.
- **Evidence**: PostHog/posthog PR #138497 "feat(metrics): answer dashboard-v2 metrics tiles from precomputed metrics" (2026-11-19, 1 reaction/7 comments; explicitly "Layer 3 of 3" of a staged rollout). Problem statement in the PR: "7- and 30-day metrics tiles on dashboards re-read every raw sample, so they are slow and long-range histogram percentiles can fail."
- **Why it looks unbuilt/untested**: Solved internally, vendor-specific, as a three-PR stack inside PostHog's own product; the underlying scaling problem for any team building its own LLM-eval dashboards on raw traces doesn't have an off-the-shelf, portable rollup layer evidenced here.
- **Maturity**: SATURATED
- **Verdict notes**: Precomputed metric rollups/downsampling is a long-solved general time-series-observability pattern with multiple maintained, portable implementations: `tsink` (open-source Rust, persistent downsampling policies with checkpointed materialization), TimescaleDB continuous aggregates, ClickHouse materialized views, and Prometheus recording rules all do exactly this today, plus commercial products (Instana, SolarWinds, Splunk Observability) that auto-select rollup granularity by query range. PostHog's PR stack is just one more team applying an already-common, widely-available technique to its own dashboard — not a gap needing a new portable tool.

### P7: Health/liveness metrics blind to work that's been claimed but not yet flushed
- **What it is**: A class of observability bug where a liveness/health endpoint counts only an in-memory buffer, so work that has been handed off to a "drain" process but not yet persisted disappears from health, doctor, and stats endpoints entirely — making the system look healthier (lower backlog) than it is.
- **Evidence**: joshuaswarren/remnic PR #3445 "fix(core): report claimed drain backlog in /health extraction liveness (#3442)" (2026-11-16, 2 reactions/7 comments). PR body: "`/engram/v1/health` `extraction.pendingTurnCount` counted only the in-memory buffer... so every session handed to a `buffer drain` claim vanished from health, doctor and stats. ... health reported 10,512 pending [vs. a higher real backlog]."
- **Why it looks unbuilt/untested**: Patched locally in one project's own health endpoint; no general "claimed-but-unflushed work" accounting pattern for observability pipelines (relevant to any async LLM eval/trace ingestion pipeline) was found as a reusable library.
- **Maturity**: OPEN
- **Verdict notes**: GitHub + web search found nothing specific to this bug class — only generic liveness-vs-readiness separation guidance (NVIDIA Dynamo docs, Pomerium blog) and LiteLLM's proxy backlog endpoint, which reports in-flight requests but does not distinguish "claimed by a drain/worker but not yet persisted" from genuinely-pending work. No library or documented pattern models "claimed-but-unflushed work" as its own observability-accounting bug class; only the digest's own one-off internal fix (`remnic` PR) addresses it.

### P8: Pausing (not blindly retrying) an eval pipeline's LLM connection on provider rate limits
- **What it is**: When an eval run hits a provider 429, pausing that connection (backoff at the connection level) rather than retrying in-call, to avoid hammering a rate-limited provider mid-evaluation and corrupting run timing/cost accounting.
- **Evidence**: langfuse/langfuse PR #20289 "fix(evals): pause an LLM connection after a provider 429 instead of retrying in-call" (2026-11-16, 3 reactions/7 comments).
- **Why it looks unbuilt/untested**: Fixed inside Langfuse's own eval runner specifically; not generalized as a documented resilience pattern that other eval tools (DeepEval, Promptfoo, Braintrust) are known to share.
- **Maturity**: PARTIAL
- **Verdict notes**: Each major eval tool has its own narrow, tool-specific 429-handling rather than a shared pattern: Promptfoo auto-retries with exponential backoff and adaptively *reduces concurrency* under rate limits (a scheduler-level backoff, conceptually close to "pause the connection"); LangSmith and DeepEval docs both just recommend client-level retry/backoff; Langfuse itself (pre-fix) only retried in-call. No portable library implements "pause the connection, don't retry in-call" as a reusable pattern across tools — real but fragmented prior art.

### P9: Confidence-gated, cost-aware test/suite selection for LLM-involved CI checks
- **What it is**: Using a single "Decision API" call over a capped diff plus a versioned suite catalog to decide which CI/eval suites actually need to run per PR, running everything only when the decision is low-confidence, while keeping mandatory security checks unconditional — a risk-based triage layer in front of expensive LLM-judged checks.
- **Evidence**: github/gh-aw PR #77203 "Add fail-open CI Front Door and cache-first daily researcher" (2026-11-12, 1 reaction/19 comments — active review discussion). PR body: "Reduce PR test cost using one Decision API request over a capped local diff and versioned suite catalog... Uncertain decisions run all applicable suites; mandatory security checks remain unconditional."
- **Why it looks unbuilt/untested**: Internal tooling inside GitHub's own `gh-aw` project, still under active PR review (19 comments) with fail-open safety semantics being hashed out; no portable, product-agnostic version of this triage layer for general LLM-eval/observability CI pipelines was found.
- **Maturity**: PARTIAL
- **Verdict notes**: `cjlee1/PruneTest` (MIT, GitHub) is a near-exact match — a layered pipeline (static import analysis → embedding similarity → GBDT → LLM layer, invoked only on medium-confidence cases, fail-open by design) — but it has only 1 star and minimal visible adoption. `CloudBees Smart Tests` is a real shipped commercial product doing confidence-threshold-based test selection, but it's ML-based rather than the LLM-"Decision API"-over-diff approach described here. Real attempts exist on both the open-source and commercial side; nothing has executed the specific LLM-confidence-gated, cost-aware version well yet.
