## Candidate patterns

### P1: Cross-project/cross-client context continuity for coding agents
- **What it is**: Developers running multiple AI coding agents (CLI-based) across several concurrent client projects have no standard way to persist and share context — decisions, task state, cross-task impacts — between sessions and across different agent CLIs. People are hand-rolling file-based state systems and manager-agent patterns instead.
- **Evidence**: Hacker News "Ask HN: How do you manage your AI agents' context across clients and projects?" (103 pts, 71 comments, 2026-11-07, from the `AI agent engineering patterns` last30days run). WebSearch supplement surfaced a dev.to builder post describing a self-built "Project Overseer" — a file-driven system that propagates cross-task impacts to dependent tasks and reloads state from disk on every context switch — explicitly framed as a DIY answer to the gap. Vendor products named in the same search (Conare, "MemClaw") pitch themselves as neutral context layers, confirming the gap is recognized but not consolidated.
- **Why it looks unbuilt/untested**: The HN thread is people trading ad-hoc personal setups (SQLite notes, a "Memento" tool, per-project manager agents), not converging on a standard. The dev.to "Project Overseer" is a single builder's custom tool, not a maintained open project. No one WebSearch surfaced an evaluated, widely-adopted cross-CLI context standard.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found an active but fragmented landscape, not a converged standard: Code Relay (~299 stars, multi-repo AGENTS.md workspace), Memento (MCP memory server, per-project SQLite, no cross-task-impact propagation), crossmem and projectmem (small/early PyPI/Product Hunt tools), plus a single-author dev.to "Project Overseer" post. WebSearch also found a Feb 2026 study reporting AGENTS.md-style context files didn't generally improve task success and raised inference cost >20%, undercutting the leading approach. No tool does cross-CLI (Claude/Cursor/Codex), cross-client, cross-task-impact-propagation continuity as one evaluated system — genuine gap for a focused build.

### P2: Human code-review capacity as the new bottleneck behind agent-generated PRs
- **What it is**: As AI coding agents generate a growing share of pull requests, the rate-limiting step in software delivery has shifted from writing code to a human (or second agent) verifying it — and most teams don't yet have a workflow redesigned around that shift.
- **Evidence**: Hacker News "Harvard researchers find AI coding agents shifted the bottleneck to code review" (168 pts, 225 comments, 2026-11-17). WebSearch supplement found cited figures: LinearB data that agent-authored PRs take "5.3x longer for a human to pick up and review than unassisted PRs"; Faros AI telemetry (22,000 developers) showing PRs merging with zero review up 31.3% during high-adoption periods; Sonar's 2026 survey finding 96% of developers don't fully trust AI-generated code accuracy, with only 48% saying they always verify before committing.
- **Why it looks unbuilt/untested**: The supplement surfaced several commercial point-solutions (CodeRabbit, Greptile, Qodo) selling AI-reviewer tools, but also a countervailing January 2026 study ("More Code, Less Reuse") reportedly finding agent-authored code adds more redundancy/technical debt per change than human code — i.e., the "AI reviews AI" fix is itself unproven. No consolidated, evaluated answer to "how should review scale when the author is an agent" surfaced.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple well-resourced, maintained products already sell exactly this fix: CodeRabbit, Greptile, Qodo (cross-repo review + "Codebase Wisdom"), and Graphite (stacked-PR workflow redesign with AI triage baked in) — WebSearch confirmed all are shipping products, not demos, with GitHub itself publishing guidance (May 2026) acknowledging the bottleneck it's also building Copilot features around. The "is AI-reviews-AI actually sound" debate (the "More Code, Less Reuse" study) is a real open research question, but the tooling/workflow gap the community describes is being actively closed by well-funded teams, which is the SATURATED bar.

### P3: Harness-induced variance undermining trust in agent benchmark scores
- **What it is**: The surrounding execution harness (tool-calling scaffold, retry logic, prompt wrapper) changes an agent's benchmark score by more than swapping the underlying model does, making published leaderboard numbers hard to compare across papers or products.
- **Evidence**: WebSearch supplement surfaced an arXiv paper "Harness-Bench" (May 2026) measuring this effect directly, a harness-aware-evaluation survey (preprints.org) arguing scores must be interpreted alongside the full execution config, and a practitioner claim that "the evaluation harness can introduce more ranking variance than changing the underlying model."
- **Why it looks unbuilt/untested**: The proposed fix found in the same search — the ICLR 2026 "Holistic Agent Leaderboard (HAL)" paper, standardizing harness and orchestrating evaluation across hundreds of VMs — is a fresh academic proposal, not a tool builders have adopted yet. OpenAI reportedly stopped trusting SWE-bench Verified (per the same search) rather than fixing it, which is itself evidence no consolidated solution exists.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirmed the "Holistic Agent Leaderboard" (HAL, ICLR 2026, Princeton et al.) is the only direct proposed fix found — an open-source, framework-agnostic standardized harness, validated with 21,730 rollouts across 9 models/9 benchmarks (~$40k run). It's a fresh academic artifact with no evidence of third-party/vendor adoption surfaced in search; GitHub search for a harness-variance tool returned nothing. OpenAI reportedly abandoning trust in SWE-bench Verified rather than fixing it reinforces that no adopted solution exists yet.

### P4: Long-horizon evaluation gap — agents pass short benchmarks, fail in production
- **What it is**: Agent benchmarks that run short task horizons systematically miss the failure modes (drift, compounding errors, state loss) that show up only over long-running, multi-step production tasks; model rankings reportedly reverse when the same models are tested long-horizon vs. short-horizon.
- **Evidence**: WebSearch supplement found a blog post titled "The Long-Horizon Evaluation Gap: Why Your Agent Passes Every Benchmark and Still Fails in Production" (tianpan.co) and an Arize "field guide" describing long-horizon agent benchmarks as "fragmenting," each measuring something different.
- **Why it looks unbuilt/untested**: Multiple competing, non-converged long-horizon benchmark efforts were found (the search literally frames them as "fragmenting"), rather than one evaluated standard practitioners can point to.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub and WebSearch found a genuinely fragmented field, not one standard: SWE-Marathon, AgencyBench (ACL 2026, 138 tasks), Long-Horizon-Terminal-Bench, plus several small GitHub repos (vigil, longhorizon-bench, Horizon-Eval), and a CUBE proposal explicitly asking the community to converge on a shared MCP/Gym-based protocol before fragmentation deepens. Arize's own June/Oct 2026 field guide frames the space as "fragmenting." Real implementations exist but none is the single evaluated standard the gap describes — a differentiated build (or a consolidation layer) remains viable.

### P5: No standard authorization/trust protocol for agentic commerce transactions
- **What it is**: Businesses are responding to autonomous agents attempting transactions on users' behalf by banning them outright rather than adopting any agent-authorization standard, because no trusted mechanism exists yet to verify an agent is acting with genuine user consent and within scope.
- **Evidence**: Hacker News "United Airlines bans AI agents from booking flights on behalf of travelers" (682 pts, 710 comments, 2026-11-11, citing CBS News).
- **Why it looks unbuilt/untested**: The resolution reported is prohibition, not a protocol — i.e., the community-visible response to "agents want to transact on a user's behalf" is currently binary blocking rather than a scoped-permission or verifiable-intent standard. No WebSearch in this run surfaced a maturing agent-authorization standard being adopted by a major commerce player.
- **Maturity**: SATURATED
- **Verdict notes**: This gap is already stale as framed — WebSearch and GitHub both found multiple shipped/announced standards from well-resourced teams: OpenAI+Stripe's Agentic Commerce Protocol (maintained GitHub org, multiple implementer repos including NVIDIA, Vercel, Magento, Cryptorefills), Google's AP2/UCP, Visa's Trusted Agent Protocol (built with Cloudflare), Mastercard's Verifiable Intent (co-developed with Google, announced March 2026), and a joint FIDO Alliance submission by Google, Mastercard, Visa, PayPal, Amex, and OpenAI. The United Airlines ban (the digest's cited evidence) reflects one merchant's choice, not an absence of protocols — multiple competing but real authorization standards already exist; the remaining problem is consolidation/adoption, not invention.

### P6: Functional (non-compacting) context management as an alternative to lossy summarization
- **What it is**: An architecture bet that most agent context-window problems come from lossy compaction/summarization, and that keeping context "functional" (structured, addressable, never compacted) avoids the information loss that causes agents to forget or hallucinate earlier decisions.
- **Evidence**: Hacker News "Gnosh.ai for 'Functional AI'; functional context management, no compaction" (4 pts, 1 comment, 2026-11-01, from the `AI agent engineering patterns` last30days run).
- **Why it looks unbuilt/untested**: Single-source, very low engagement (4 points, 1 comment) — this is a founder/early-product post, not a validated community pattern. Flagged here specifically because it's complaint-shaped against the dominant compaction approach, but the evidence is thin and should be weighted accordingly by the gap-analyst.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found real non-summarization alternatives, each narrow/early: an arXiv paper proposing "CWL" (typed episodes + agent-authored dependency graph + deterministic LLM-free eviction), JetBrains' "observation masking" (deletes rather than rewrites old tool output), and a Towards-AI practitioner write-up finding keep-everything-plus-caching beat summarization on one production tutor eval. None is a consolidated, adopted "functional context" product category — Gnosh.ai itself (the digest's source) is a single 4-point founder post. Real but fragmented engineering practice, not a shipped standard.
