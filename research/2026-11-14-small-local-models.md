## Candidate patterns

### P1: Confidence-scored local-to-cloud escalation routing
- **What it is**: An architecture where a small local model handles a request by default and a cheap confidence/classification check decides whether to escalate the same request to a cloud frontier model, instead of routing by task type alone.
- **Evidence**: A Microsoft-oriented write-up on "SLM-default, LLM-fallback" design (strathweb.com) describes scoring a local agent's output and escalating on low confidence, citing a 2025 survey on small language models for agentic systems. Tom Tunguz's post describes sending background work through a small on-device classifier so only the hardest tasks reach the cloud, which he reports roughly tripled single-Mac throughput. Vendor posts (BetterClaw, CallSphere) claim 60-80% of agent requests can stay local, though those numbers are vendor-sourced and unverified.
- **Why it looks unbuilt/untested**: Every example found is a single blog's bespoke implementation or a vendor claim; no shared library or benchmark for the confidence-scoring step itself was surfaced. The actual escalation-decision logic (not just "local vs cloud") is described in prose, not as a reusable component.
- **Maturity**: PARTIAL
- **Verdict notes**: Research-grade implementations exist with code (`github.com/BuffaloTechRider/zero-shot-llm-confidence-estimation` for arXiv 2605.02241, `github.com/NYCU-NLP-Lab/ConfDrivenInference` for arXiv 2602.22090) plus a maintained cloud-to-cloud routing framework (`lm-sys/RouteLLM`) and a shipped OpenRouter guidance feature — but OpenRouter's own blog post states explicitly "we do not make that call for you," and no reusable component targets local-model-to-cloud confidence escalation specifically; every concrete example is either a research repo or one vendor's bespoke write-up (Strathweb/Azure, Tom Tunguz).

### P2: Small-model tool-calling reliability gap
- **What it is**: Sub-14B local models reliably fail at multi-step agentic tool use — calling nonexistent tools, emitting malformed parameters, or silently answering from memory instead of invoking a tool at all.
- **Evidence**: A r/LocalLLaMA thread titled "What are your struggles with tool-calling" (surfaced via mirror) collects exactly this complaint pattern. A separate r/LocalLLaMA comment thread on "reliable function calling with vLLM" reports trouble getting consistent outputs for most agentic use cases with open-source models. The LlamaIndex community forum shows a user whose React agent "kept trying to call nonexistent tools," with a reply stating 14B-32B models struggle with consistent function calling. A dev.to benchmark post on Llama-3B names tinyllama and qwen2:0.5b as unsuitable for tool use outright.
- **Why it looks unbuilt/untested**: Multiple independent threads describe the same three failure modes (wrong tool, malformed params, skip-and-hallucinate) but no one has shipped a standard small-model-specific tool-calling harness or fine-tuning recipe that the threads treat as solved — people are still trading anecdotes about which parameter count "starts working."
- **Maturity**: SATURATED
- **Verdict notes**: The Berkeley Function Calling Leaderboard (BFCL) is a maintained, field-standard benchmark with an active fork/integration ecosystem (confirmed via `gh search repos`, multiple 2026-dated forks). `antoinezambelli/forge` is a maintained MIT-licensed reliability harness specifically for self-hosted small-model tool calling (2,270 stars, pushed 2026-11-12, reports lifting multi-step success from ~53% to ~99% without changing the model). Fine-tuning recipes also ship as code (`cactus-compute/needle`, TinyToolCaller via QLoRA on Qwen2.5-1.5B). Between a maintained benchmark, a maintained harness, and shipped fine-tuning recipes, this gap is substantially closed by well-resourced/active projects.

### P3: Prompt-only fine-tuning ("vibe-tuning") of small models for a narrow task
- **What it is**: A workflow where a non-ML-expert supplies a prompt plus a handful of examples, and a tool fine-tunes a small local model to match that behavior without the user writing training code.
- **Evidence**: distil labs is described (via its own docs/guide pages) as exactly this: fine-tune a small model "with just a prompt and a few dozen training examples," aimed at teams without ML staff. Meta's distillation guide separately documents a teacher-generates-completions → student-fine-tunes workflow, claiming an 8B model can match a 17B model on a specific task.
- **Why it looks unbuilt/untested**: The only concrete implementation found is a single commercial vendor (distil labs); Meta/Azure's versions are still framed as "guides," not productized self-serve tools, and a distillation-focused guide notes only the classification task has full support in one library — coverage is narrow and vendor-fragmented, not a general pattern anyone can self-host.
- **Maturity**: PARTIAL
- **Verdict notes**: distil labs (commercial, hosted) and Radal (Product Hunt no-code listing) are the only close matches to "prompt + a few examples, no training code"; LlamaFactory is a popular maintained no-code *interface* but still requires the user to assemble a training dataset, not just a prompt. `distillops` (OSS, verifier-gated distillation) and Arcee's DistillKit are open source but target large curated datasets (e.g. 200k examples), not the few-dozen-example "vibe-tuning" workflow. No self-hostable OSS tool matches the exact prompt-only workflow; coverage stays vendor-fragmented and narrow.

### P4: Hardware-to-model fit decision paralysis
- **What it is**: People running local LLMs repeatedly ask which hardware (GPU/VRAM tier, unified memory) fits which model size and use case, rather than finding a settled answer.
- **Evidence**: "Ask HN: What hardware are you using to run local LLMs?" drew 52 points and 46 comments on Hacker News (2026-11-02) — strong engagement for a recurring question. A separate guide notes "RAM/VRAM headroom matters more than model size," implying the naive heuristic (just match parameter count to VRAM) people reach for is wrong.
- **Why it looks unbuilt/untested**: The HN thread's framing as an open "Ask HN" rather than a link to a canonical resource suggests no widely-trusted, continuously-updated hardware-fit guide exists yet that the community defers to.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch surfaced well over a dozen live VRAM/hardware-fit calculators covering exactly this computation (flaviocopes.com, InventiveHQ, LocalAIMaster, Mustafa.net, PromptZone, ModemGuides, among others), several explicitly accounting for KV-cache/context headroom rather than naive parameter-count matching — the specific naive-heuristic gap the evidence cites. The recurring "Ask HN" question looks like a discoverability/trust problem (no single canonical tool dominates), not an absence of implementations.

### P5: Privilege-tiering for local models exposed to untrusted input
- **What it is**: A governance/architecture pattern that restricts which tools a local small model is allowed to call based on whether its current input is untrusted, because small models are more susceptible to prompt injection than frontier cloud models.
- **Evidence**: A production-focused practitioner post explicitly states small models "are more prompt-injection-prone, so they shouldn't get high-privilege tools while processing untrusted input," reported alongside the same team's experience that debugging silent local-model failures ate more time than the API costs it was meant to save, leading them to pull local models from scheduled automation.
- **Why it looks unbuilt/untested**: This appears as a hard-won lesson in one team's write-up, not as a named framework, checklist, or library — no reusable privilege-tiering implementation was found in the search.
- **Maturity**: PARTIAL
- **Verdict notes**: Adjacent, real implementations exist for agent privilege separation generally — Simon Willison's Dual LLM pattern, a 2026 arXiv paper on type-directed privilege separation (arxiv.org/html/2509.25926v1, reports driving attack success to zero in its case studies), a three-tier provenance-based hierarchy paper (arxiv.org/pdf/2606.19660), and OS-level tool allow-lists (Claude Code's `--tools`/`--disallowedTools`, Sophos's "nono"). None of these is specifically framed around *small/local models* needing a lower default tier because they're more injection-prone — that specific framing remains a single practitioner's write-up, not a named reusable library, but the surrounding building blocks are real and would make a serious build differentiated rather than novel from scratch.

### P6: Local small model as a pre-flight quality gate for expensive cloud agent calls
- **What it is**: Using a small local model to screen or validate a request/response before it is allowed to reach (or be trusted from) a costlier cloud agent call, rather than using the local model as a full substitute.
- **Evidence**: "Local Preflight for Cloud Agents: Small Models as Quality Gates for Codex CLI" (codex.danielvaughan.com) frames exactly this pattern for Codex CLI-style agentic workflows.
- **Why it looks unbuilt/untested**: Only one blog post describing a single author's implementation was found; no general-purpose, tool-agnostic "local gate" middleware or shared pattern library surfaced.
- **Maturity**: PARTIAL
- **Verdict notes**: Real but small/narrow implementations exist: a `local-model-suitability-mcp` MCP server returning LOCAL/CLOUD/EITHER verdicts per call, and PyPI packages `llm-preflight` and `model-preflight` — but those two check model/prompt changes at development time, not per-request runtime quality-gating, which is the actual pattern described. No package or product found does live pre-flight screening of a request/response pair before it reaches a cloud agent call; coverage is fragmented, unverified-adoption, and partially mismatched to the exact use case.

### P7: Silent-failure observability gap for local-model automation
- **What it is**: Local models fail in ways that don't surface as clean errors (wrong output rather than an API error), and teams lack tooling to catch this the way they catch cloud API failures.
- **Evidence**: The same practitioner write-up cited in P5 reports the cost of debugging time to diagnose these silent failures "exceeded the API savings in the first month," causing the team to abandon local models for scheduled automation and rebuild with explicit cloud routing.
- **Why it looks unbuilt/untested**: The team's response was to retreat to cloud-only rather than adopt an observability tool for local-model output quality — implying no such tool was known to them or readily available.
- **Maturity**: PARTIAL
- **Verdict notes**: General-purpose, self-hostable LLM observability tools exist and are mature (Arize Phoenix, 10,000+ stars, OpenTelemetry-native, drift detection) and could in principle be pointed at local-model automation. But none found is purpose-built or marketed for the specific "cron-job-style local automation with no clean error signal" niche the evidence describes, and the cited practitioner team evidently didn't find or adopt any such tool before abandoning local models — suggesting a real discoverability/fit gap even though generic building blocks exist.

### P8: One-off domain-specific small-model benchmarking instead of a reusable eval framework
- **What it is**: Practitioners write bespoke, single-use benchmark blog posts to figure out which small model works for their narrow domain, rather than using a standard reusable evaluation harness for domain-specific small-model selection.
- **Evidence**: "I tested 12 small AI models on 2,500 design-system questions" (Hacker News, 2026-10-27, 3pts) is exactly this pattern — a one-off, hand-built benchmark against a specific question set, with the post's own framing ("the model wasn't what mattered") suggesting the benchmarking methodology itself was the hard part.
- **Why it looks unbuilt/untested**: Low engagement (3pts) relative to the general topic suggests this kind of domain-specific benchmarking work is done in isolation repeatedly rather than via a shared, reusable tool others build on.
- **Maturity**: SATURATED
- **Verdict notes**: `EleutherAI/lm-evaluation-harness` is a maintained, field-standard reusable eval framework (14,468 stars, pushed 2026-11-04) that explicitly supports custom domain tasks via config and local backends (Ollama, vLLM) — directly matching "a reusable evaluation harness for domain-specific small-model selection." Multiple other maintained eval frameworks also compete in this space (promptfoo, DeepEval, Confident AI). The one-off blog-post benchmarking pattern looks like an awareness/habit gap, not a tooling absence.
