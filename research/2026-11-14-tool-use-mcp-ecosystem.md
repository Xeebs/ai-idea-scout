## Candidate patterns

### P1: No general effect-journal / compensating-action layer for externally-committed MCP tool-call side effects
- **What it is**: Agent checkpoint/restore (shadow files, git snapshots) only resets local state; once a tool call has sent an email, made a payment, or written to an external database, there is no generic way to reverse it. The fix pattern emerging is a per-tool-call mutation journal paired with a declarative "compensating action" (the inverse operation), plus idempotency keys to stop a timed-out call from double-applying on retry.
- **Evidence**: WebSearch ("MCP agent tool call undo rollback side effects") surfaced dev.to's ACRFence post arguing local checkpoint/restore "can't reverse effects like payments or emails"; an Agent-Undo MCP server that journals every mutating tool invocation alongside a compensating undo action; Walkback (file-only rollback via shadow restore points); a Strayspark blog post naming the retry-double-apply failure mode and proposing idempotency keys + an effect journal as the fix; and the Autonomous SDLC Command Center's `sdlc_rollback` tool, which is dry-run-only unless `confirm=true` is passed, plus PolicyLayer's tool-risk listing labeling a Novyx `rollback` tool "Critical Risk."
- **Why it looks unbuilt/untested**: Every named implementation (ControlKeel, Context+, Open Subagent, Walkback) covers only the filesystem via git checkpoints or shadow restores. No source named a cross-domain framework that generalizes the compensating-action pattern to network calls, payments, or email — ACRFence and Strayspark both frame this as an open, unsolved mechanism rather than pointing to an incumbent that already closes it.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search (Bash `gh search repos`, WebSearch "MCP tool call rollback compensating action framework github 2026") found at least 5 implementations beyond the digest's original set — `agent-undo` (AAH20, saga-style journaling + reverse-order undo across MCP tools), `react-agent-compensation` (PyPI, auto-discovers compensation pairs via `x-compensation-pair` tool annotations), `mcp-compensator` (mohithhhh, proxy that journals mutating calls, undo via snapshot/inverse, flags irreversible calls), `ModelActionProtocol` (DeadpxlStudio, reverser registry + capture-before-write for CRUD APIs), plus `walkback`. None is a maintained, widely-adopted framework: several are single-author, days-to-weeks old, one (`agent-undo`) cites unverifiable model names in its own README, and the WSO2/Strayspark commentary explicitly treats "true" cross-domain compensation (payments, email) as unsolved and recommends human approval for irreversible actions rather than pointing at an incumbent. Real gap remains, but enough scattered prior art exists that a build here would need real differentiation, not a greenfield claim.

### P2: Fragmented client/SDK support for elicitation as the lone surviving bidirectional MCP capability
- **What it is**: MCP's spec update (protocol version 2026-07-28) deprecated the `sampling` capability (servers asking the client's LLM to generate a completion) and scheduled it for removal, recommending direct provider-API integration instead. `elicitation` (servers asking the client to collect structured user input) survived as the only non-deprecated bidirectional feature, but its delivery mechanism changed to a multi-round-trip pattern, and client/SDK support is uneven months after the spec change.
- **Evidence**: WebSearch ("MCP server elicitation sampling capability adoption 2026") found modelcontextprotocol.io's own client-concepts docs confirming the sampling deprecation; a dev.to post ("Elicitation didn't die in the MCP stateless rewrite") framing elicitation as the sole bidirectional survivor; a DEV-authored adoption matrix claiming 13 of 24 surveyed clients treat elicitation as a progressive enhancement while 2 of 24 still build against the deprecated sampling capability (single-source, unverified against an independent tally); and a Pydantic AI guide noting that, as of March 2026, the documented `FastMCPToolset` still does not support elicitation or sampling integration.
- **Why it looks unbuilt/untested**: The protocol-level decision (deprecate sampling, keep elicitation, change its transport) is settled, but no source names a converged, consistent client-side UX or fallback behavior for elicitation across hosts — adoption figures are described as a patchwork (progressive enhancement in roughly half of surveyed clients, no action in others), and major SDKs are reported as still missing the integration months after the spec changed.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch ("MCP elicitation sampling client SDK support adoption 2026") confirms the spec decision is real and already implemented at the protocol-maintainer level: the official Go, TypeScript, C#, Ruby, and Python SDKs all document elicitation support, and sampling keeps working during a 12-month deprecation window per the official client-concepts docs — this is well-resourced-team territory, not a greenfield gap. But convergence is still incomplete: Pydantic AI's `FastMCPToolset` is documented (March 2026) as still missing both elicitation and sampling integration, and a PHP SDK issue reports sampling support but no elicitation. Uneven-but-actively-closing adoption across official and third-party SDKs is a PARTIAL, not SATURATED (no single converged UX/fallback standard yet) and not OPEN (the core mechanism already ships in most major official SDKs).

### P3: No standard metering/billing primitive for paid MCP tools — every vendor hand-rolls auth + usage metering + payment
- **What it is**: As MCP servers move toward monetization, there is no standard way to meter and bill a tool call; each vendor (Polar, MCP-Billing, ATXP, Nevermined, xmcp.dev) ships its own bespoke combination of API-key auth, usage metering, and Stripe (or stablecoin) billing bolted onto MCP. Agent-initiated payment protocols (Stripe's Machine Payments Protocol, x402-based tooling) are emerging as an alternative but are themselves new and uncoordinated with each other.
- **Evidence**: WebSearch ("MCP server monetization usage-based billing paid tools 2026") surfaced dev.to's "The State of MCP Monetization in 2026" and "How to Monetize Your MCP Server in 2026" guides describing four competing pricing models (per-call, subscription, freemium, outcome-based) delivered through at least five different marketplace/billing-gateway products; Nevermined's "Pricing for AI Agents" posts pitching usage/outcome/value-based models; and a vendor-authored analysis claiming "95% of MCP servers earn nothing," attributing it to integration/infrastructure effort rather than lack of demand (unverified single-source claim, flagged as such).
- **Why it looks unbuilt/untested**: The sheer number of competing, incompatible billing bolt-ons (at least five named products, each with its own revenue-share/fee model) for the same problem is itself evidence that no standard has emerged — this looks like an early, fragmented land-grab rather than a solved problem, and the cited adoption numbers (if directionally correct) suggest the tooling that exists hasn't meaningfully lowered the barrier yet.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search (`gh search repos "MCP billing metering"` / `"MCP monetization"`) turned up 10+ repos (xpaysh/awesome-mcp-monetization, xpack-ai/XPack-MCP-Marketplace, Payloadhq/mcp-monetization-kit + demo + payload-sample-mcp-server using x402, Lulu-The-Narwhal's starter kit, etc.), and WebSearch confirms well-resourced entrants: Coinbase's x402 (Cloudflare added edge-native support Feb 2026), Stripe's Machine Payments Protocol (launched March 2026), Cloudflare's Monetization Gateway, and an AWS WAF "Monetize" action (shipped July 2026) — plus a single-author-group "MCP Billing Spec v1" draft that is explicitly unratified. This is a land-grab among several large, well-resourced players rather than silence, but none has converged into *the* standard metering/billing primitive the pattern describes — competing, non-interoperable approaches from Stripe/Coinbase/Cloudflare/AWS is the textbook PARTIAL case (real implementations, narrow/uncoordinated, differentiation still possible), not OPEN.

### P4: WASM-based sandboxing for untrusted/local MCP servers is emerging but fragmented across runtimes
- **What it is**: Running local or third-party MCP servers directly on a host is a named attack vector (arbitrary code with file/network access); WebAssembly sandboxing is the proposed containment layer, letting an untrusted tool run with minimal default privileges without a full container. Multiple independent efforts are building this at different layers (OS-level component model, edge/serverless runtime, in-browser).
- **Evidence**: WebSearch ("MCP server WASM zero-cloud local-only privacy sandboxed browser 2026") found Microsoft's Wassette (open-source, loads WASM components from local paths or OCI registries into a trusted execution environment for untrusted MCP tools), the Spin/wasmcp project (runs the same sandboxed MCP server binary locally, at the edge via Fermyon Wasm Functions, or on Kubernetes — explicitly framing unsandboxed local MCP servers as "an attack vector for exploiting host resources"), an early-preview "WebMCP" bringing MCP into browser environments, and a Hacker News item in this run's engine pass, "PaperPilot – Zero-Cloud, Pure-Rust PDF Engine with WASM and MCP" (2026-10-26, 236 points, 88 comments), shipping a concrete zero-cloud document-processing MCP tool compiled to WASM.
- **Why it looks unbuilt/untested**: The MCP security-best-practices doc only recommends running local servers "in a sandboxed environment with minimal default privileges" without specifying WASM as the mechanism, and the implementations found (Wassette, Spin/wasmcp, WebMCP, PaperPilot) sit on different runtimes (Wasmtime-based component model, Fermyon's Spin, in-browser) with no shared packaging format — a developer wanting this today has to pick one of several non-interoperable stacks rather than a converged standard.
- **Maturity**: SATURATED
- **Verdict notes**: `gh search repos` plus WebSearch confirm at least two independently maintained, well-resourced implementations squarely covering "WASM sandboxing for untrusted MCP servers": (1) `microsoft/wassette` — Microsoft-backed, Wasmtime-based, actively committed (last push 2026-11-12, this run's date), with its own docs site, FAQ, and a growing adopter ecosystem (luisquintanilla/wassette-dotnet, attackordie's QR component, etc.; star counts vary 500–800+ across aggregators as of this run); and (2) `wasmcp/wasmcp` — a maintained org (not a single repo) with `wasmcp/tools` middleware and a real production adopter (`akamai-developers/serverless-decision-log-mcp-server` built on it, plus Fermyon/Spin backing). The pattern's own "fragmented across runtimes" framing is accurate on interoperability, but the maturity bar is about whether the gap is closed by well-resourced teams, not whether they agree on one format — two maintained, shipping, differently-backed implementations meets the SATURATED bar even though a single converged packaging standard doesn't exist yet.

### P5: Scoped, time-limited credential brokering for agent/MCP tool calls remains rare and ad hoc
- **What it is**: Instead of handing an agent a long-lived, broadly-scoped API key for every MCP tool it can call, the emerging pattern is a credential-broker layer that issues short-lived, narrowly-scoped proxy tokens per tool/task (e.g., a `certificate:renew` scope against one named audience), with explicit human approval or biometric confirmation shown to the user, not the agent, before a credential's policy can be loosened.
- **Evidence**: WebSearch ("MCP agent password manager credential scoping approval token renewal") found a password-manager-style MCP server ("Keymaster") whose per-credential policy grants only time-limited "confirm" access via native dialog/Touch ID, with the agent unable to loosen or purge a credential without that approval; Pincer-MCP, which keeps real API keys in a gateway and issues the agent a limited proxy token (its authors note this doesn't stop an *authorized* bad action — a prompt-injected agent can still request a destructive call the proxy token permits); a conference talk describing exchange of a broad key for a single-scope, single-audience task token; and a cited report that only 18% of MCP server deployments implement any form of access scoping for tool permissions at all.
- **Why it looks unbuilt/untested**: The 18%-scoping figure (if directionally correct) means the vast majority of deployments skip this entirely, and the few named implementations (Keymaster, Pincer-MCP, WorkOS's secrets-management writeup) are point solutions from different vendors with no shared protocol for scope negotiation, approval UX, or renewal — teams are re-deriving the same primitives (scoping, time-bounding, approval) independently rather than converging on one.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "MCP credential broker scoped token"` / `"keymaster MCP"` / `"pincer-mcp"` found multiple small, overlapping implementations (HappyMonkeyAI/keymasterMCP, archetech/keymaster-mcp-server, two separate AInoAKARI "keymaster" repos, VouchlyAI/Pincer-MCP) — duplication across near-identical forks rather than one converged, adopted solution, consistent with the digest's "point solutions, re-derived independently" framing. WebSearch corroborates: an IETF draft "Credential Broker 4 Agents (CB4A)" was published March 2026 describing two credential-brokering models, and vendor writeups (Gravitee, agentgateway.dev, nhimg.org, mintmcp) describe converging best practice (short-lived, narrowly-scoped, workload-identity-rooted tokens) but explicitly state there is "no settled standard yet." Real implementations exist and the direction is converging, but nothing here is a maintained, broadly-adopted implementation squarely closing the gap — PARTIAL, not SATURATED; not OPEN given the IETF draft and multiple shipped point solutions.
