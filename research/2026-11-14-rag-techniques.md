## Candidate patterns

### P1: "App, not pipeline" — people want RAG abstracted away entirely
- **What it is**: Builders are increasingly framing RAG infrastructure itself (chunking, embedding, vector store ops, retrieval tuning) as toil they'd rather not own, wanting to just ship the application logic on top of a managed retrieval layer.
- **Evidence**: Hacker News Show HN "We wanted to build an AI application, not maintain RAG pipelines" (akropolys.cloud, 2026-11-10, 3 points / 1 comment). Corroborated by a cluster of near-identical community threads surfaced in WebSearch — e.g. "Why does RAG complexity actually disappear when you stop managing vector stores yourself" and "How RAG actually becomes practical when you're not building vector stores yourself" (community.latenode.com threads).
- **Why it looks unbuilt/untested**: The framing itself ("we wanted X, not Y") is a direct complaint about current DIY RAG stacks; the repeated near-duplicate thread titles across a forum suggest a recurring, unresolved frustration rather than a single vendor's marketing push, but no dominant managed solution is being cited back at the complainers.
- **Maturity**: SATURATED
- **Verdict notes**: Managed "RAG abstracted away" is a crowded, well-resourced product category: LlamaCloud (LlamaIndex's hosted parsing/ingestion/retrieval service), Vectara (managed RAG-as-a-service with hallucination scoring), RAGFlow (infiniflow/ragflow, actively maintained agent-native RAG engine), plus Pinecone Assistant, Google Vertex AI Search, AWS Bedrock Knowledge Bases, and Ragie — all shipped products squarely targeting "don't manage your own RAG pipeline." GitHub search also surfaced a dozen+ "RAG as a Service" repos. The complainers' gap is already being closed by well-resourced teams, even if awareness is uneven.

### P2: Golden-set RAG evaluation is still a one-off script, not a standard tool
- **What it is**: Teams are hand-rolling small Python scripts that run a RAG pipeline against a curated "golden set" of question/answer pairs to catch regressions, rather than using an established eval framework.
- **Evidence**: Hacker News Show HN "Python script to evaluate your RAG pipeline against a golden set" (infrixo-systems/rag-evaluation-starter, 2026-10-24, 4 points). Also a GitHub issue thread (mcpmark-eval-liuhezi/rag-lit-scan) explicitly tracking a literature review of "Evaluation of Retrieval-Augmented Generation: A Survey" (arXiv 2405.07437) as a still-open research question for the team doing the scan.
- **Why it looks unbuilt/untested**: The Show HN is a single-file starter script (not a maintained product), and the literature-review issue shows a team still in "reading papers to figure out how to evaluate RAG" mode rather than using a settled tool — both are signs this is still being reinvented ad hoc.
- **Maturity**: SATURATED
- **Verdict notes**: The specific pattern (golden-set Q&A regression testing for RAG) is a solved problem at the tooling level: ragas (truera/trulens is a separate, also-mature alternative) and DeepEval both ship maintained, widely-adopted metrics (faithfulness, context precision/recall) plus golden-dataset regression workflows, and Vectara's own open-rag-eval (maintained, Nov 2026 commits) does golden-answer-free RAG evaluation. GitHub search turned up 10+ actively-updated RAG eval frameworks in the last few months alone. The individual Show HN script is a one-off, but the gap it's filling already has mature, free tools — the author just didn't use them.

### P3: Tiny CPU-only decision models as cheap RAG relevance/guardrail checks
- **What it is**: Instead of calling a large LLM to decide whether a retrieved chunk is relevant or safe to use, a small (sub-1B parameter) decision model runs the check locally on CPU.
- **Evidence**: Hacker News Show HN "Arc-decide – an MIT 0.4B decision model for RAG checks that runs on CPU" (docs.docsgpt.cloud, 2026-10-26, 3 points).
- **Why it looks unbuilt/untested**: Framed as a fresh Show HN release with minimal traction yet (3 points, no comments) — a novel architecture pattern (cheap local arbiter model in front of/inside the RAG loop) that hasn't accumulated adoption or scrutiny yet.
- **Maturity**: PARTIAL
- **Verdict notes**: Adjacent building blocks are mature and widely deployed — CPU-friendly cross-encoder rerankers (bge-reranker, ms-marco-MiniLM, FlashRank-Pro at 149M params) are standard in production RAG stacks for relevance scoring on CPU — but a purpose-built sub-1B *decision/guardrail* model (vs. a reranker) is genuinely thin: the closest comparable, `smallevals`' CRC-0.6B context-relevance classifier, is listed as "Incoming"/unreleased per its PyPI page, and no other shipped safety-decision model of this size was found. The specific guardrail framing is a real, differentiated gap even though reranking itself is saturated.

### P4: Zero-infra, browser-embedded local RAG (no server, no separate vector DB)
- **What it is**: Running a full RAG stack (storage + retrieval) inside a single local process or even a browser tab, using Postgres as the vector store, instead of standing up a dedicated vector database service.
- **Evidence**: Hacker News Show HN "Db4 is open source: local RAG on Postgres in a browser tab" (lab4.app, 2026-10-21, 3 points).
- **Why it looks unbuilt/untested**: A brand-new open-source Show HN with no measurable community traction yet; the "no server, no API, one file" framing (echoed in a WebSearch hit about "Sub-Millisecond RAG on Apple Silicon. No Server...") suggests a recurring but still-niche desire for zero-ops local RAG that mainstream RAG tooling (LangChain/LlamaIndex + hosted vector DBs) doesn't optimize for.
- **Maturity**: PARTIAL
- **Verdict notes**: Building blocks are maintained and real — PGlite (ElectricSQL's WASM build of Postgres, under 3MB gzipped, with pgvector support, actively maintained) is exactly "Postgres in a browser tab," and VecLite/EdgeVec (Rust/WASM vector search in IndexedDB) and the academic MeMemo (arXiv 2407.01972, on-device retrieval) cover adjacent ground. But no single maintained product assembles these into a turnkey "full RAG stack, zero server, one file" experience the way Db4 pitches — Db4 itself is a brand-new, 3-point Show HN, and the underlying pieces require assembly, not a shipped product.

### P5: Agent memory layers leak far more than raw RAG retrieval — need memory-specific leakage auditing
- **What it is**: A security framing that separates "RAG retrieval" (treated as low-leak) from "agent memory" (treated as high-leak), implying agentic systems that persist/recall memory across turns need their own dedicated privacy/leakage evaluation distinct from standard RAG evals.
- **Evidence**: Hacker News Show HN "Show HN: Raw RAG leaks 0%, but agent memory leaks 67%" (harishbalasubramanian/sentinel-eval, 2026-11-09, 3 points).
- **Why it looks unbuilt/untested**: The headline number (67% leak rate) is presented as a novel finding from a new eval tool (sentinel-eval) with essentially no community engagement yet (3 points, 0 comments) — i.e., the problem is newly named and the tooling to audit it is a single researcher's fresh repo, not an established practice.
- **Maturity**: PARTIAL
- **Verdict notes**: Real research is accumulating fast — the AgentLeak benchmark (Feb 2026, tests 7 leakage channels incl. shared memory) and a channel-aware comparative framework (CIPL, arXiv) explicitly separate memory-channel leakage from RAG-retrieval leakage and report divergent rates, which validates the pattern isn't fabricated. But no maintained, adopted auditing *tool* exists yet — sentinel-eval is a single fresh repo with zero engagement, and the comparative papers are research-stage, not packaged products. A serious build auditing agent memory leakage specifically (vs. generic PII scanners) would be differentiated.

- **Why it looks unbuilt/untested**: The 239-point HN response (vs. single-digit points for every other item in this run) shows this is a live, unresolved, high-interest research direction rather than a solved problem — multiple competing approaches (compression, reranking speedups) are emerging in the same window without a clear winner yet.
- **Maturity**: SATURATED
- **Verdict notes**: This exact gap is already being closed by multiple well-resourced labs with released code: Meta Superintelligence Labs' REFRAG (arXiv 2509.01092, NeurIPS 2025 workshop, reports 30.85x time-to-first-token speedup at 32x compression, code at facebookresearch/refrag) and Apple/Edinburgh's CLaRA (arXiv 2511.18659, joint reranker+generator compression, code released at github.com/apple/ml-clara, SOTA across 4 QA benchmarks). High community interest (239 points) reflects that this is a hot research area, not that it's unaddressed — it's actively being solved by teams with far more resources than an independent build could bring, even though a "clear winner" hasn't settled yet.
