## Candidate patterns

### P1: Ad hoc fixes for MCP "tool overload" blowing up agent context and accuracy
- **What it is**: Loading many MCP servers at once means every tool's full schema sits in context before the user even asks anything, and tool-selection accuracy degrades once an agent has more than a few dozen tools to choose from.
- **Evidence**: Multiple independent builder write-ups surfaced via WebSearch (`archestra.ai` reports mounting 20 MCP servers can burn ~240K tokens before the user types anything; a three-server setup reportedly used 72% of a 200K context window before the agent read the first message; `jentic.com`'s "MCP Tool Trap" and several DEV Community posts — e.g. `dev.to/deathsaber "Too many MCP tools make agents worse, here's how I fixed it"`, `dev.to/focused_dot_io "Stop eager-loading MCP tools"` — describe the same failure independently). Cursor's own community forum has a thread titled "Tool limit reached on MCP" (forum.cursor.com) confirming Cursor hard-caps at ~40 MCP tools total as a stopgap.
- **Why it looks unbuilt/untested**: Every fix found is a personal blog-post workaround or a hard product-level cap (Cursor's 40-tool ceiling), not a general solution; authors explicitly frame these as "here's how I fixed it" one-off hacks rather than adopted standards.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch confirms the underlying problem is now addressed by well-resourced, shipped products rather than just blog hacks: Anthropic's "Tool Search Tool" with `defer_loading` is GA on the Claude API (and reported live on Azure, Vertex AI, and Amazon Bedrock per platform.claude.com docs), reporting an 85% token-usage reduction; Cloudflare's "Code Mode" independently reports cutting a 52-tool/4-server setup from ~9,400 tokens to ~600. Two independent, well-resourced vendors have shipped general fixes for exactly this gap, closing what the digest's evidence (gathered before these shipped) still framed as one-off hacks.

### P2: Lazy / on-demand MCP tool discovery ("meta-tool" pattern) as the proposed fix for P1
- **What it is**: Instead of loading every tool schema from every connected MCP server up front, the agent discovers and loads only the tool schemas it needs at call time via a small set of meta-tools (search/describe/invoke), cutting initial context cost by an order of magnitude.
- **Evidence**: Several small OSS projects implement this directly — `lazy-mcp` (PyPI/docs.rs, multiple point releases, claims ~16K+ tokens upfront reduced to ~1.5K), `mcpx` (github.com/cs50victor/mcpx, discovery via shell commands instead of tool definitions), and a VibeCody demo of a lazy-loading tool registry. Anthropic shipped an official version — "Tool Search Tool" and `defer_loading` on the Claude Developer Platform (per a DEV Community write-up) — and an arXiv paper (MCP-Zero, "Active Tool Discovery for Autonomous LLM Agents") frames it as a research problem.
- **Why it looks unbuilt/untested**: The pattern exists in parallel as several incompatible small libraries (lazy-mcp, mcpx) plus one official-but-narrow vendor feature (Claude's defer_loading) and one academic paper — no cross-client standard yet, and a DEV Community post on deferred loading flags an unresolved tradeoff: the discovery round-trip itself adds latency that nobody has benchmarked well.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up search confirms "official-but-narrow" has since widened: Anthropic's Tool Search Tool/`defer_loading` is reported GA and multi-platform (Anthropic API, Azure, Vertex AI, Bedrock per platform.claude.com), plus Cloudflare's Code Mode (code-execution alternative to schema listing) ships the same effect via a different mechanism. GitHub search also turned up several more independent "meta-tool" implementations beyond the digest's list (`day50-dev/mcp-search-and-run`, `Flexksx/toolpool`, `maheshyaddanapudi/testrail-mcp-server` explicitly framed as "solving MCP tool bloat"). Multiple maintained OSS projects plus two well-resourced vendors' shipped, GA features squarely cover this gap now, even though per-call latency tradeoffs remain an open tuning question rather than a blocking gap.

### P3: Fragmented, unverified MCP server trust/registry landscape
- **What it is**: Because anyone can publish an MCP server and the official MCP Registry does no security vetting of submissions, several independent third parties have each built their own trust-scoring layer for MCP servers, with no consensus on method or authority.
- **Evidence**: WebSearch found at least three competing attempts — `mcp-trust` (open-source, A-F danger grades, "mcp-trust.vercel.app", not yet on PyPI properly), `CraftedTrust` (commercial-leaning registry claiming "7-factor trust scoring" over 3,400+ packages), and `HVTracker MCP` (a `verify_mcp_server` pre-connect check tool). A DEV Community security analysis cited in the same search reports the official MCP Registry has "no verification or security vetting of submitted entries" and that 82% of HTTP-transport servers in the registry require auth but don't declare it in their metadata. Separately, a low-engagement Hacker News submission from the engine run itself — "USB: A trust layer for AI skills and MCP servers" (HN, 11 points, 3 comments, 2026-11-09, github.com/PeepSick/usbplus) — is yet another independent attempt at the same problem.
- **Why it looks unbuilt/untested**: Three-plus competing, non-interoperable trust layers plus a fourth barely-noticed HN side project (11pts/3cmt) is the signature of a real gap nobody has closed — none of the found projects shows signs of becoming the default, and the official registry explicitly declines to vet anything itself.
- **Maturity**: SATURATED
- **Verdict notes**: Deeper search surfaces well-resourced, actively maintained players the digest's pass missed: Manifold (an $8M seed-funded supply-chain security vendor, per SiliconAngle May 2026) scores 7,700+ MCP servers; CraftedTrust is a public registry with a free API that has indexed 6,975+ servers (12-category CoSAI-aligned scoring); Dominion Observatory reports behavioral trust scores for 14,824+ servers. GitHub search also turned up 4+ independently-named `mcp-trust-registry` repos and 8+ distinct `mcp-*-security-scanner` repos. The lack of a single consensus standard is real, but the rubric's SATURATED bar (multiple maintained implementations/shipped products squarely covering the gap) is met — three funded/maintained scoring products already cover thousands of servers each.

### P4: "Who evaluates the evaluator" problem in MCP tool-calling eval frameworks
- **What it is**: A growing set of MCP-specific eval tools (beyond generic agent evals) try to score whether an agent selected the right tool, passed correct arguments, and left the right system state — but the evals themselves are reported to be unreliable.
- **Evidence**: WebSearch surfaced Braintrust's "what is an MCP eval" and "ultimate guide to MCP testing" guides describing trace- and state-based scoring (e.g. catching a duplicate write when a `create_record` call times out after the server already wrote the record); the open-source `mcp-evals` GitHub Action (LLM-based scoring with PR comments); and an arXiv framework (MCPEval) built specifically because "static benchmarks" were seen as inadequate. Most tellingly, a DEV Community post titled "My eval said a perfect MCP server was broken — it was the eval that was lying" describes an LLM-based eval initially flagging a server as failing tool selection 62% of the time due to a bug in the grader itself.
- **Why it looks unbuilt/untested**: The cautionary post is explicit first-person "I built this and it lied to me" signal; none of the eval tools found have an agreed-on way to validate the grader itself before trusting its numbers — every framework assumes its own scoring is ground truth.
- **Maturity**: PARTIAL
- **Verdict notes**: Found general-purpose grader-validation tooling that could be adapted but nothing MCP-eval-specific and shipped: NVIDIA's skillevaluator ships "grader validation" (checks a judge against independently labelled cases) but explicitly caveats itself as a narrow synthetic set, "not a reliability benchmark"; `agentscope-ai`/ModelScope's OpenJudge is a maintained general grader-validation toolkit (MAE/F1 metrics, k-fold cross-validation) but not MCP-specific. A 2026 arXiv paper ("Benchmarking the Benchmarks") audits four tool-calling benchmark families (BFCL v4, τ2-Bench, LiveMCPBench, MCP-Atlas) for reward-basis mismatch and judge variance — real research attention, but it's an audit/proposal, not a shipped meta-eval product. No one has packaged "validate the MCP eval's own grader" as a product; adjacent generic tooling exists but the specific gap is real and differentiable.

- **Why it looks unbuilt/untested**: This is a single engineering team's own admission of a gap in their own product (a PR description, not a shipped fix), with no general cross-runtime MCP-bridge reliability layer visible anywhere else in this research pass.
- **Maturity**: OPEN
- **Verdict notes**: GitHub search for "ACP MCP bridge" turns up only point-to-point translation bridges (`oijkn/copilot-acp-mcp-bridge`, `krkr521/dsh-acp-mcp-bridge`, `yjloong/kimi-mcp-bridge`) — these ARE the components that fail, not reliability/observability layers on top of them. WebSearch found a March 2026 arXiv field study proposing protocol-level primitives (timeout budgeting, structured failure semantics) and the official `agentclientprotocol.com` RFD on MCP-over-ACP error semantics, plus scattered practitioner blog posts on symptoms (hung calls, duplicate side effects on retry, inconsistent error typing across SDK versions) — but no implementation of a general cross-runtime bridge-reliability/observability layer anywhere. ### P6: Letting agents add their own tools/plugins without a fork — and the sandboxing gap that follows
- **What it is**: Plugin systems that let an agent runtime add panels, commands, styles, and new agent tools at runtime (no fork of the host project needed) create a new class of "trusted but unsandboxed" code path that existing review tooling isn't built to gate.
- **Evidence**: From the engine run — a `pingdotgg/t3code` PR ("feat(plugins): plugins add panels, commands, styles and agent tools without a fork", 2026-11-09, 9 reactions/9 comments) was flagged by an automated reviewer bot (Macroscope) with the verdict "Needs Human Approval," specifically because the PR "adds trusted, unsandboxed plugins spanning server execution, agent tools and browser UI."
- **Why it looks unbuilt/untested**: The gate that caught this was a generic PR-review bot repurposed for the job, not a purpose-built sandboxing/approval layer for dynamically-added agent tools — the review comment itself reads as an ad hoc catch rather than an enforced policy.
- **Maturity**: PARTIAL
- **Verdict notes**: A broader generic ecosystem exists for agent tool sandboxing/approval — an arXiv survey (2605.24309) catalogs 5 academic papers, 15 production systems, and 4 plugins that ship some runtime-approval mechanism; vendor products (Gravitee's deny-by-default + ephemeral sandboxes, Snyk's access-hook for tool-list gating) and a Brown University EuroMLSys'26 paper proposing context-specific sandboxes for tool combinations all address agent tool execution risk generally. But none found is purpose-built for the specific pattern here — plugins/tools an agent adds to itself mid-session without a host fork — which is still being caught by repurposed generic PR-review bots (as the digest's own evidence shows) rather than an enforced policy layer. Real, differentiable gap at the intersection of "dynamic self-extension" and "sandboxing," even though adjacent generic tooling is mature.
