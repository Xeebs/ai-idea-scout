## Candidate patterns

### P1: Barge-in interrupt latency (not end-to-end p99) as the real perceived-latency metric, undermined by self-interruption/echo
- **What it is**: Builders report that standard end-to-end p99 latency dashboards don't track what users actually feel — the time from a user's first interrupting syllable to the agent's audio actually stopping (barge-in latency) — and that voice agents frequently fail this specifically because they mishear their own TTS output as the caller speaking and cancel themselves mid-word.
- **Evidence**: A DEV Community post by a named practitioner ("Marcus Chen") reports a 380ms barge-in delay for their own agent versus 60ms for a competitor, arguing "barge-in interrupt rate is the metric users actually feel." A secondhand aiweekly.co recap of an r/AI_Agents post describes a voice agent with a 280ms p99 that still felt slower than a competitor's 450ms, attributing the mismatch to barge-in/silence-detection handling (Reddit source itself unreachable due to the 403 block — treat as secondhand). A separate DEV Community post on self-interruption describes the system "hearing itself, mistaking its own voice for the caller, and cancelling its own speech mid-word," remedied only by echo cancellation.
- **Why it looks unbuilt/untested**: No general-purpose barge-in-rate measurement tool or echo-cancellation-by-default standard was found — each source describes a one-off internal fix or metric the author built for their own stack, not a shared library or convention other builders adopt.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found `openbenchmarks-labs/voice-agent-latency` and `signalwire/latency_checker`, but both measure first-response latency, not barge-in-stop latency specifically; one GitHub-listed project (`media-ui`, via awesome.ecosyste.ms) names "barge-in latency" as one metric in a broader voice-agent testing/debugging tool, but it is a narrow, unverified-maturity single tool, not an adopted standard. Vendor docs (Picovoice's Voice UX guide, Deepgram's Latency Report, Cloudflare's Nov-2026 "voice diagnostics turn metrics" changelog) define/surface related turn-level metrics but none specifically target self-interruption/echo-mishearing-own-TTS as a solved, shared problem — each practitioner source (DEV Community posts) still describes a bespoke internal fix. Real but thin/fragmented coverage keeps this PARTIAL rather than OPEN.

### P2: "Deployed but unsatisfied" — no standard diagnostic layer for post-launch conversational quality, as opposed to infra uptime
- **What it is**: Builders ship a voice agent to production successfully (infra works) but remain dissatisfied with the actual conversation quality once real callers hit it — accents, background noise, degraded audio, and long-tail phrasing that demo/synthetic testing never caught.
- **Evidence**: An AssemblyAI 2026 Insights Report, cited in a February 2026 NYC voice-agents meetup write-up, found 87% of respondents have deployed a voice agent to production, yet 75% are not satisfied with what they built. Vapi's own testing docs separately note that "synthetic callers don't fully represent real callers," so manual calls and production recordings are still needed for accents and noise.
- **Why it looks unbuilt/untested**: The gap named (diagnosing *why* a technically-deployed agent underperforms on real calls) is described only as a stat and a caveat in vendor docs — no dedicated diagnostic/observability tool targeting this specific "deployed vs. satisfied" delta (as opposed to general uptime/latency dashboards) turned up in this run.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple funded, maintained products squarely target exactly this delta: Cekura (YC F24, raised $2.4M per cekura.ai, covers both pre-production testing and live production monitoring, traces failures to audio/STT/LLM/tool/TTS stage rather than just uptime), Coval (synthetic-caller simulation at scale + native voice-agent eval integration per Langfuse), Hamming (production monitoring with native OTel ingestion plus direct audio-signal analysis, claims 95-96% agreement with human evaluators), Maxim AI, and Cognigy's "Conversation Analyzer" (LLM-based qualitative scoring of 100% of conversations). An independent academic paper (arXiv 2511.04133, "Testing the Testers") benchmarked Coval, Cekura, and Evalion head-to-head on exactly this simulation/eval quality question. This is a well-resourced, multi-vendor, independently-benchmarked category — the "deployed but unsatisfied" gap is actively being closed, not open.

### P3: Drop-in compatibility shims across competing voice-agent frameworks (LiveKit Agents vs. Pipecat)
- **What it is**: Because LiveKit Agents and Pipecat (the two dominant open voice-agent orchestration frameworks) have incompatible APIs, some builders are writing their own small compatibility/hook libraries so the same logic (e.g. turn segmentation) works against either framework instead of locking into one.
- **Evidence**: A real, dated GitHub PR: "Voice agent hooks for LiveKit Agents and Pipecat; fence-aware Segmenter" (`berkerbatur/speechready`, PR #11, 2026-11-02, score 3) — described in its own summary as "drop-in hooks for the two main voice agent frameworks, checked against their current APIs (livekit-agents 1.8.10, pipecat-ai 1.15.0)." Separately, a comparison piece (forasoft.com, "Pipecat vs LiveKit Agents... same models, same latency, different regrets") and a NVIDIA-AI-Blueprints repo PR ("Add the Generic Assistant on LiveKit and restructure the repository into one package with a folder per framework," `NVIDIA-AI-Blueprints/nemotron-voice-agent`, PR #219, 2026-11-19) both show real production repos restructuring specifically to support both frameworks side by side rather than picking one.
- **Why it looks unbuilt/untested**: `speechready` is a single narrow repo (one maintainer, segmenter-focused) rather than an adopted cross-framework standard; the NVIDIA blueprint PR is a one-off internal restructure, not a reusable library other projects depend on. WebSearch for a general-purpose neutral abstraction layer over both frameworks returned only vendor comparison articles debating lock-in, not a shipped shared library.
- **Maturity**: PARTIAL
- **Verdict notes**: Found one real but one-directional and incomplete compatibility layer — SignalWire's "LiveWire," which exposes `livekit-agents` class/function names so LiveKit-authored code runs on SignalWire infrastructure, but accepts pipeline plugin params (stt/tts/vad/turn_detection) as no-ops rather than real compatibility, and only goes LiveKit→SignalWire, not the reverse or LiveKit↔Pipecat directly. Pipecat's own LiveKit transport is a transport adapter, not an Agents-API-level shim. Combined with `berkerbatur/speechready` (single-maintainer PR) and the NVIDIA blueprint's internal restructure, every found implementation is narrow/one-off/vendor-specific — no adopted neutral abstraction layer between LiveKit Agents and Pipecat exists, confirming the gap is real but partially chipped at.

### P4: Hybrid voice-agent eval — real-call replay + synthetic adversarial callers + auto-promoting production failures to permanent regression tests
- **What it is**: Builders are converging on testing voice agents with three combined layers instead of one: replaying real recorded production calls, running synthetic/adversarial simulated callers for inputs never yet seen, and turning any real production failure into a permanent regression test (e.g. via a thumbs-down in a dashboard).
- **Evidence**: A DEV Community post argues that replaying 312 recorded production calls as a regression suite missed a code-switching failure that never appeared in the recordings, concluding "replaying real call transcripts as your test set is a trap — the failures come from the inputs a user produces exactly once." Vapi's docs explicitly separate "Evals" (checking the next decision from a given state) from "Simulations" (checking whether a full conversation reaches the right outcome) and recommend turning production failures into regression tests. An open-source tool, `voicetest` (Apache 2.0, per WebSearch), replays production call transcripts against a voice agent's current graph.
- **Why it looks unbuilt/untested**: The practice is fragmented across one vendor's proprietary docs (Vapi) and a single open-source replay-only tool (`voicetest`) — no single open framework was found that combines all three layers (replay + synthetic adversarial + auto-promotion-to-regression) in one adopted workflow; each source implements only part of it.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search confirms each of the three layers has real but separate tooling: `voicetest` (voicetestdev/voicetest, Apache 2.0, PyPI-published, supports Retell/VAPI/Bland/LiveKit import + replay + LLM-judge eval) handles replay only; `xray-eval/xray` is a LiveKit replay framework but under the non-OSI Elastic License 2.0; academic EVA-Bench (arXiv 2605.13841) and VAmoS-Bench (arXiv 2607.27453) do synthetic/adversarial caller simulation with acoustic perturbation as research benchmarks, not a shipped product; Eve Legal's engineering blog describes auto-promoting single-turn failures to permanent regression tests but as a proprietary in-house harness, not a reusable tool. No single open, adopted framework combines all three layers — confirms the digest's own "fragmented across one vendor's docs and one replay-only OSS tool" framing rather than contradicting it.

### P5: Vision-triggered proactive turn-taking in multimodal agents (speaking because of what changed on screen/camera, not just what was heard)
- **What it is**: Current multimodal voice+vision agents can "see" via a camera or screen feed, but still only take a turn (speak) in response to the user's speech — none proactively initiates a new turn purely because something changed in the visual scene mid-conversation.
- **Evidence**: An arXiv study on ChatGPT's voice mode (surfaced via WebSearch) found that although it "uses vision but does not proactively start turns based on what it sees," and that "current models can't yet respond to changes in the visual scene mid-utterance." Separately, Stream's open-source Vision Agents framework and the older i-Code Studio research prototype both combine real-time video, audio, and conversation in one session, but turn-taking in both is still speech-triggered.
- **Why it looks unbuilt/untested**: The arXiv finding is explicitly framed as a current limitation ("cannot currently... respond to changes... by uttering a new turn"), and no shipped framework or repo surfaced in this run implements scene-change-triggered proactive speech as a general capability — every multimodal stack found uses vision only as context *for* a speech-triggered turn, not as a turn trigger itself.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirms the OpenAI Realtime API explicitly does not trigger turns from video alone (developer community thread, staff-adjacent reply: "all triggering is either voice-based or manual"). Pydantic AI's documented "Watch mode" camera example is the closest shipped approximation but verified (via direct fetch of the docs) to be a fixed 3.5-second timer nudge the model can choose to ignore, not an actual frame-difference/scene-change trigger — frames are explicitly "context only" and "do not start a model turn." A single independent dev's "Iris" blog post (Gemini Live) does implement real frame-diff thresholding (threshold 20, 8s cooldown) that sends a text nudge on genuine visual change, but it's a one-person blog prototype with no located repo, not an adopted library. Combined with the arXiv/CHI findings that current voice agents overwhelmingly use silence-based turn-taking, this is a real but narrow/demo-level gap — PARTIAL rather than OPEN since at least one working (if tiny) implementation of true scene-change triggering exists.

### P6: Exploratory unification of typed and spoken turns into one literal in-memory conversation state (single runtime, not separate pipelines)
- **What it is**: Rather than running separate text-chat and voice-call pipelines that each maintain their own conversation history, one project is prototyping a single in-memory conversation object that both typed and spoken turns write into and read from, in one TypeScript/JS runtime.
- **Evidence**: A real, dated GitHub PR: "Spike shared chat and Inworld calls with LiveKit JS" (`gianpaj/sexyvoice`, PR #712, 2026-11-16, score 12, 2 reactions, 9 comments) — described in its own summary as evaluating "shared text and Inworld voice calls in one TypeScript repository before choosing a replacement for the Python agent," where "typed and spoken turns share the same in-memory conversation."
- **Why it looks unbuilt/untested**: The PR's own title calls it a "spike" (an explicitly exploratory, throwaway investigation) made specifically to decide whether to replace an existing Python agent — it is a single team's early prototype, not a released pattern, and no second implementation of the same literal shared-state approach turned up in this run.
- **Maturity**: SATURATED
- **Verdict notes**: This exact gap is already closed by multiple maintained, shipped products. Cloudflare's official Agents SDK ships `withVoice(Agent)`/`withVoiceInput(Agent)` (package `agents/voice`, documented at developers.cloudflare.com/agents/communication-channels/voice/): voice runs over a WebSocket into the *same* Agent class instance, same Durable Object, and same SQLite-backed conversation history as text — "these are all just different inputs to the same agent." Telnyx's Agent SDK ships an equivalent `voice()` mixin that adds a turn engine to a normal Agent class while its durable state, messages, and RPC stay unchanged, giving "one conversation across phone and chat." Vapi's Chat API (shipped, $50M Series B company) advertises agents running across both voice and chat "using the same config, tools, and memory." Three independently maintained, well-resourced products already implement a single shared runtime/state object spanning typed and spoken turns — the `gianpaj/sexyvoice` spike is reinventing something the market has already productized, just not in that team's specific stack.

### P7: Granular, user-controllable consent for cross-call voice-agent memory, instead of all-or-nothing capture
- **What it is**: Multiple vendors now offer persistent memory that carries context across separate voice-agent calls (keyed to a phone number or customer profile), but every implementation found captures and reuses history as an all-or-nothing default rather than giving callers granular control over what's remembered, surfaced, or forgotten.
- **Evidence**: A Twilio blog post (via WebSearch) cites research that 66% of consumers said they would feel uneasy or wouldn't prefer providing an AI agent with all previous context from past interactions, directly alongside Twilio's own "Conversation Memory" feature description, which links phone/email/messaging identities into one profile and stores whatever the system extracts as "mattering." Mem0, Synthflow, and ElevenLabs were all found shipping similar always-on cross-call memory features with no mention of per-item deletion or opt-out controls in the material found.
- **Why it looks unbuilt/untested**: The 66%-uneasy figure comes from the same vendor pushing the all-or-nothing memory feature, and no product or open project surfaced in this run offers caller-facing granular consent/forget controls (e.g., "forget what I said about X" or a visible memory-review step) — the privacy concern is acknowledged in vendor marketing copy but not addressed in any shipped control surface found.
- **Maturity**: OPEN
- **Verdict notes**: Genuine multi-channel search found no shipped voice-agent product with caller-facing granular memory consent/deletion. Telnyx's own Agent Memory docs explicitly state per-memory ("forgetting a single memory") deletion is "not yet available" — only profile-level or whole-session deletion exists. A relevant hit is a USPTO patent ("Voice-activated selective memory for voice-capturing devices") describing undo-by-voice deletion, but it is a filed patent, not a shipped product. Text-chat products (ChatGPT, Claude, Copilot Studio, Azure AI Foundry) do offer per-item memory deletion, but that's a different modality/UX (a settings menu, not something a caller can invoke mid-call) and doesn't address the voice-specific gap the digest names. A 2025 arXiv paper on episodic agent memory argues users *should* get this control, confirming it as an acknowledged-but-unaddressed need rather than something built. No GitHub repo, product launch, or paper implementing voice-channel granular consent surfaced — discussion and a patent filing only.
