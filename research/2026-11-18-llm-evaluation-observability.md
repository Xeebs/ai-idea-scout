## Candidate patterns

### P1: Silent judge-model-upgrade drift in LLM-as-judge pipelines
- **What it is**: Production LLM-as-judge eval pipelines silently shift their scores whenever the provider upgrades the underlying judge model, with no code change on the team's side and no automated alert — the drift is discovered only after metrics unexpectedly move.
- **Evidence**: tianpan.co blog posts surfaced via WebSearch: "LLM-as-Judge Drift: When Your Evaluator Upgrades and All Your Numbers Move" (2026-04-23) and "The Eval Harness Whose Judge Model Was Upgraded Silently" (2026-06-02); a companion post "The Eval Automation Trap: When Your Pipeline Drifts Away From What Users Actually Want" (2026-05-02) states judge errors "accumulate in consistent directions rather than averaging out."
- **Why it looks unbuilt/untested**: every source's fix is manual — "pinning the judge model version, prompt, and parameters in eval metadata" and recalibrating "on a fixed cadence" (one source cites a 60-90 day window, another a 5% drift trigger) are described as practitioner heuristics people apply by hand. No cited tool auto-detects a judge-model version change and automatically re-baselines or flags affected historical eval runs.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found only blog posts/papers describing the problem (tianpan.co series; an arXiv recommendation-explanations paper that manually re-tunes behind a review gate; an anchor-based-monitoring paper distinguishing "judge changed" vs "product changed" via a fixed human-labeled anchor set) — no shipped tool does auto-detection + auto-re-baselining of historical runs. General AI-drift platforms (Arize, Future AGI, Evidently, WhyLabs, Fiddler) claim broad "drift detection" coverage and one roundup names Future AGI for judge-drift specifically, but these are broad platforms bolting judge-drift onto generic drift monitoring, not a dedicated, evaluated solution for this exact failure mode — real gap remains for a differentiated build.

### P2: Observability tools built around single request/response traces, not agent execution graphs
- **What it is**: Current LLM observability products default to tracing one request-response pair, but agentic systems make roughly 10 LLM calls and 20 tool calls per single user action — the unit of analysis the tools assume doesn't match the unit of work agents actually produce.
- **Evidence**: Respan.ai blog post (via WebSearch) arguing today's observability tools are "built around the request-and-response trace" while agents make many more calls per action; a LangChain survey cited in the same search found 89% of teams have agent observability instrumented but only 52% run offline evals and 37% run online evals — tracing adoption is far ahead of actual evaluation coverage.
- **Why it looks unbuilt/untested**: the complaint names a structural mismatch (unit of analysis), not a missing feature in any one named tool — it's framed as an industry-wide gap rather than something any vendor has solved.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found multiple maintained, widely-used products that already market full-agent-execution-graph tracing rather than single request/response: LangSmith (full agent execution tree per node, inputs/outputs/latency), Langfuse (MIT, self-hostable, OTel-based multi-agent trace support), and Arize Phoenix (OTel-based agent graph visualization). The actual gap in the LangChain survey evidence (89% have tracing instrumented but only 52%/37% run offline/online evals) is an eval-coverage gap, not a trace-structure gap — the pattern as framed ("tools default to single req/resp") is contradicted by the leading vendors' own stated capabilities.

### P3: Human-designed eval APIs being systematically misused by autonomous coding agents
- **What it is**: Teams are discovering that LLM-driven coding agents misuse eval/observability APIs that were designed for human callers — calling the wrong evaluation-scope parameter, omitting required IDs — at a rate high enough to require dedicated bug-tracking and API-description fixes.
- **Evidence**: PostHog GitHub PRs found via the engine run: `fix(aio): tell agents llma-evaluation-run takes generation evals only` (PostHog/posthog#129079, 2026-11-04) states "Agents call llm-evaluation-run with trace- and session-target evaluations, and the API rejects every call with evaluation_target_mismatch. This bucket holds most of the tool's validation errors over the last 14 days, across many users." Companion PRs `fix(aio): say backfill tools need an evaluation id` (#129083, 2026-11-04) and `feat(aio): record offline evaluation usage in postgres` (#124131, 2026-10-27) show the same team instrumenting usage specifically to catch this failure pattern.
- **Why it looks unbuilt/untested**: PostHog is patching this reactively, one tool-description PR at a time, after observing the error bucket — there is no general-purpose pattern yet for making an eval API self-describing enough that an agent caller doesn't need trial-and-error (and a human noticing the error bucket) to use it correctly.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found plentiful practitioner advice (Pinecone, NordicAPIs, tianpan.co) on designing agent-friendly error messages/API docs in general, plus a related but broader commercial product — Future AGI's "Error Feed" (formerly Agent Compass), which clusters agent failures by semantic similarity against a 30+ type taxonomy including an "insecure API usage" category and proposes immediate/long-term fixes. An arXiv paper on API-misuse detection/repair in LLM-generated code is adjacent but targets code-gen, not live eval-API callers. No tool found that specifically detects an eval/observability API's own agent-misuse error bucket and auto-patches its descriptions the way PostHog does by hand — general guidance and a broader adjacent product exist, but this narrow gap stays real.

### P5: Distilled cheap classifiers replacing LLM-as-judge for ground-truth-having production checks
- **What it is**: For narrow production classification tasks where ground-truth labels exist, teams are reporting that a small trained classifier can match "frontier" LLM-judge quality at a fraction of the inference cost, rather than running a large LLM as the judge/evaluator at every call.
- **Evidence**: Airbnb engineering post "Frontier quality at 1% of the cost: a production benchmark of LLM classifiers" (airbnb.tech, HN, 2026-11-06, via the engine run); corroborated by a WebSearch-surfaced "skeptic's view": "closed-form tasks with ground truth are better served by classifiers... Use the classifier."
- **Why it looks unbuilt/untested**: both sources are a single company's internal benchmark write-up and a general opinion post, not a packaged workflow — no tool was found that automates "detect when an eval task actually has ground truth and swap the expensive LLM judge for a trained classifier."
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found substantial supporting material beyond the digest's two sources — vendor playbooks describing a three-tier setup (heuristics + distilled judge + human gold set), a ZeroEntropy "distillation-drift" playbook warning distilled judges silently degrade on production distribution shift, and an academic SAGE framework (arXiv 2602.07840) that distills a frontier judge into student surrogates. None of this is a packaged, automated "detect ground-truth availability and auto-swap" tool — it's all manual playbooks/guides and a research framework, so the gap the pattern names is real but adjacent prior art is denser than the digest implies.

### P6: LLM judges deployed without ever sample-validating agreement against human raters
- **What it is**: Teams ship LLM-as-judge scoring into production eval pipelines without a continuous process to check the judge's verdicts against human-labeled samples, so a poorly-calibrated judge can run unnoticed indefinitely.
- **Evidence**: "Using LLM for confidence scoring is a bad idea" (rumple.github.io, HN, 2026-10-21, via the engine run — 228 points / 107 comments); a WebSearch-surfaced study reference (summarized by layerlens.ai/Grepture posts) of "21 judges and ~541,000 judgments" where 85% raw agreement corresponded to a Cohen's kappa near only 0.48; Respan.ai (via WebSearch) states plainly that "most teams never sample-validate it against humans."
- **Why it looks unbuilt/untested**: the universally cited fix is a manual, periodic human-labeling spot-check — no tool found that builds continuous human-agreement sampling into an eval pipeline as a first-class, automated feature.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch confirmed this is already a shipped product feature: LangChain's LangSmith "Align Evals" (launched July 2025, documented at docs.langchain.com/langsmith/improve-judge-evaluator-feedback) builds exactly this — human reviewers correct a sample of judge verdicts, corrections become ground truth, agreement is tracked over time, available on both cloud and self-hosted LangSmith. Galileo documents an equivalent calibration-loop product feature (stratified sampling, SME feedback, anchor updates, Cohen's kappa). Two open-source libraries (Potato Judge Calibration, Axion/CaliberHQ) also exist for this exact workflow, though CaliberHQ shows 0 stars/0 forks on GitHub (real but unadopted). With a well-resourced, maintained, widely-used platform (LangSmith) plus a second vendor (Galileo) squarely shipping this as a first-class feature, the gap as described is already closed for teams on those platforms.

- **What it is**: Instead of static question-answer eval sets, a new benchmark style pits teams of LLM agents against each other in a simulated competitive environment (e.g., soccer) to surface emergent multi-agent behavior that static evals can't capture.
- **Evidence**: Show HN "Soccer-Bench – Watch teams of LLM agents play 5v5 soccer" (darksinian.github.io, HN, 2026-11-17, via the engine run; 9 points / 1 comment at capture).
- **Why it looks unbuilt/untested**: a same-day Show HN launch with minimal engagement — an early signal of interest in simulation-based agent eval, not an established or adopted approach yet.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found Soccer-Bench's specific game is novel but the broader pattern (dynamic/game-like multi-agent benchmarks replacing static QA) is a well-populated, multi-year category: DSGBench (StarCraft II, Civilization, Diplomacy, Werewolf, Stratego — open, multi-game, maintained), WereWolf-Plus (open-source, scalable eval framework), Stanford's Agent Island (Survivor-style, May 2026, released game logs), LieCraft (deception benchmark, March 2026), LLMsPark (game-theory settings), and a Blood-on-the-Clocktower social-deduction harness — multiple maintained implementations already cover this exact approach, just not soccer specifically.

### P8: Teams hand-rolling combined observability+eval glue instead of adopting a mature platform
- **What it is**: Despite a crowded field of dedicated LLM observability/eval vendors, individual teams at very different scales are each building their own basic "observability and evaluation" feature from scratch inside their own product rather than integrating an existing platform.
- **Evidence**: GitHub PR "feat: Observability and Evaluation" on a small open-source project (maheshnallada/ConversenseAI#2, 2026-11-14, via the engine run); PostHog independently building its own in-house "aio" (AI observability) evaluation-run feature across multiple PRs (#124131, #129079, #129083) in the same window; a WebSearch roundup lists Langfuse, Arize Phoenix, LangSmith, Braintrust, Datadog LLM Observability, Helicone, Portkey, MLflow, and Bifrost as existing, named options in this exact category.
- **Why it looks unbuilt/untested**: the two projects are at opposite ends of scale (a tiny OSS repo and a large analytics company) yet both chose to build rather than integrate, despite the WebSearch-surfaced vendor list — suggesting integration friction, cost, or a missing lightweight/embeddable option rather than a true absence of tools.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirmed the crowded vendor list (Langfuse, Arize Phoenix, LangSmith, DeepEval, OpenLLMetry, Helicone, Portkey, MLflow) but also confirmed the friction: Langfuse's self-host stack requires web+worker containers, Postgres, ClickHouse, and Redis/S3 — heavyweight for teams wanting a single embeddable piece. The closest thing to a solution is pairing two separate libraries (OpenLLMetry for 2-line-of-code OTel tracing, DeepEval for eval metrics) — no single lightweight, combined observability+eval-in-one library was found, which is consistent with why both PostHog and a tiny OSS repo independently chose to build their own glue rather than adopt. Real, differentiable gap for a minimal combined library.
