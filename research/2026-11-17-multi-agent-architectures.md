## Candidate patterns

### P1: Adversarial re-verification of multi-agent majority votes
- **What it is**: A verification pass that checks the output of a multi-agent "vote" (several agents independently answer, majority wins) and overturns the majority when it's provably wrong, rather than trusting consensus as ground truth.
- **Evidence**: Hacker News, "Verify, Then Vote: Overturning Wrong Majorities in Multi-Agent LLMs" — 4 points, 2026-11-03, https://github.com/grainulation/papers (per last30days engine run).
- **Why it looks unbuilt/untested**: Low engagement (4pts) suggests this is a fresh research-paper-stage idea, not a shipped tool; no production framework surfaced in the same run with a built-in "overturn the majority" verifier.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search surfaced only research-stage work: "Debate or Vote" (arXiv 2508.17536, code at github.com/deeplearning-wisc/debate-or-vote) finds voting alone drives most multi-agent-debate gains but doesn't ship an "overturn-the-majority" verifier; "Auditing Multi-Agent LLM Reasoning Trees Outperforms Majority Vote" (AgentAuditor, arXiv 2602.09341, Feb 2026) is the closest conceptual match but no code repo found; "Beyond Majority Voting" (ICML 2026) is theoretical with no code. No production framework or maintained tool implements this verification pass.

### P2: Trust/provenance layer for inter-agent claims
- **What it is**: A layer that lets one agent verify what another agent actually did or asserted (provenance, attestation, audit trail) before acting on its output, instead of implicitly trusting a peer agent's report.
- **Evidence**: Hacker News, "Are we building multi-agent systems without a proper trust layer?" — 4 points, 2026-11-14, https://www.sinapsdata.com.br/en (per last30days engine run).
- **Why it looks unbuilt/untested**: The post is framed as an open question ("are we building... without"), the classic complaint-shaped signal that the gap is recognized but not solved; low point count means no consensus answer has surfaced yet.
- **Maturity**: PARTIAL
- **Verdict notes**: Several narrow/early attempts exist but none mature: KYA ("veldt-kya" on PyPI, Ed25519 signing + trust scoring, arXiv 2605.25376, self-reported results only); atrib (GitHub, Ed25519 + Merkle-log provenance, ~5 stars); attest (mcpservers.org artifact verifier, had a hardcoded signing-key bug); Agent Manifest / TRACE (described only in an awesome-list); ArkForge Trust Layer (vendor marketing-stage proxy); agentmem (Thezenmonster/agentmem, GitHub, "trust, provenance, conflict detection," created 2026-10-08). No dominant, widely-adopted standard.

### P3: Privacy-leak testing harness specifically for multi-agent LLM systems
- **What it is**: A dedicated test suite/tool that probes multi-agent pipelines for cross-agent data leakage (one agent exposing another's or the user's private context where it shouldn't).
- **Evidence**: Hacker News Show HN, "AgentLeak – open-source privacy testing for multi-agent LLM systems" — 3 points, 2026-11-13, https://github.com/Privatris/AgentLeak (per last30days engine run).
- **Why it looks unbuilt/untested**: A brand-new Show HN launch with only 3 points — the category (privacy testing scoped to *multi-agent*, not single-model) is being proposed as novel by the poster, and no competing tool appeared elsewhere in the same run.
- **Maturity**: PARTIAL
- **Verdict notes**: AgentLeak itself (github.com/yagobski/agentleak, companion to arXiv 2602.11510) is already a real tool — Python SDK, CLI, web UI, CI checks, 1,000-scenario dataset — but low-adoption (~37 stars). Two adjacent academic benchmarks also exist: MAGPIE (arXiv 2510.15186, Oct 2025) and ToolPrivacyBench (arXiv 2606.28061, June 2026), neither multi-agent-specific or widely adopted. Real gap remains (no mature/maintained product), but the exact pattern described is already built in narrow form, so this is not OPEN.

### P4: Peer-to-peer learning/knowledge transfer between agents on a team
- **What it is**: Mechanisms for agents on the same team to learn from each other's successes/failures mid-task (not just top-down supervisor instructions), so the team improves collectively rather than each agent repeating the same mistakes.
- **Evidence**: Hacker News, "Peer Learning Between Agents in a Multi-Agent Team" — 3 points, 1 comment, 2026-11-06, https://github.com/Mininglamp-AI/Octo (per last30days engine run).
- **Why it looks unbuilt/untested**: Thin engagement (3pts/1cmt) on a freshly posted project; most frameworks referenced elsewhere in the research (LangGraph, CrewAI, AutoGen Studio) are described as orchestration topologies, not peer-learning mechanisms — the gap is structural, not just unpopular.
- **Maturity**: OPEN
- **Verdict notes**: The cited repo (Mininglamp-AI/Octo) returns 404 on GitHub — confirmed via `gh api repos/Mininglamp-AI/Octo` and a repo listing for that owner (only OctoASR, Mano-P, cider, etc. exist, no "Octo"); likely gone or mis-cited. WebSearch for peer-to-peer knowledge transfer between LLM agent teams surfaced only old reinforcement-learning research (LTCR model-distillation paper 2020, a 2025 decentralized-MARL arXiv preprint) with no code found and no relevance to LLM-based agent teams. No implementation found for the LLM-agent version of this pattern.

### P5: Multi-vendor agent relay for coding sessions
- **What it is**: Infrastructure to route a single coding session across agents from different vendors/tools (e.g., Claude Code, Codex, others) so they can hand off or collaborate on the same task without being locked to one vendor's orchestration.
- **Evidence**: Hacker News Show HN, "Agent-relay for multi-vendor coding sessions" — 8 points, 1 comment, 2026-10-27, https://github.com/saranyan/agent-relay (per last30days engine run).
- **Why it looks unbuilt/untested**: Single Show HN launch, low comment count, no competing "multi-vendor relay" product surfaced elsewhere in the run — vendor-specific multi-agent orchestration (Claude Code's own sub-agents, OpenHands' agent-server) is common, but cross-vendor relay is not.
- **Maturity**: PARTIAL
- **Verdict notes**: The cited agent-relay repo itself is a self-described prototype (11 stars, 1 fork; WebFetch confirms only simulated-client testing plus one "verified live" Codex-leads-Claude-Code run). WebSearch turned up a crowded field of similarly early/narrow competitors: Handoff (TStansel/handoff), Claude↔Codex Bridge (experimental), cross-agent_mcp, superharness, continues/casr, Capacitor, Relayvora, ai-memory. All depend on undocumented vendor CLI formats and are new/small/unproven — no dominant maintained product closes this gap yet.

### P6: Stale shared-context bugs from unordered writes in multi-agent memory stores
- **What it is**: A distinct failure mode where two or more agents write to the same shared memory/state store without ordering guarantees, so a value that was correct when written becomes invalid after another agent acts — described as a coordination bug, not a context-length problem.
- **Evidence**: WebSearch summary of an r/AI_Agents post (via aggregator write-up at enterprisedataairealities.substack.com/p/multi-agent-systems-shared-memory): "commenters confirmed it most often when two agents write to the same memory store without ordering guarantees. Multiple production builders confirm the pattern in comments."
- **Why it looks unbuilt/untested**: The aggregator frames this as commenters confirming a recurring production pain point with no named fix; general "shared memory" products (Mem0, Redis) address memory persistence but the ordering/invalidation problem specifically is described as still open.
- **Maturity**: PARTIAL
- **Verdict notes**: No dedicated library/product found, but partial mitigations exist: AutoGen's actor model sidesteps the bug by design (no shared memory, state passed explicitly via messages); blog writeups cite the "Atomix" paper (arXiv 2602.14849, transactional tool-use runtime, no code release found) and discuss optimistic-locking/version-tracking/per-region-isolation patterns as practitioner advice. One aggregator explicitly states "every approach tried reduces to last-write-wins with no principled conflict resolution" — confirming the gap is real even though partial architectural workarounds (actor model) exist today.

### P7: Constraint and identity transfer at agent handoffs (not just data/context transfer)
- **What it is**: The claim that multi-agent systems fail in production not because agents forget *information* but because they forget their *rules/constraints/identity* when a task is handed to another agent — a different problem from context-window or memory-store design.
- **Evidence**: WebSearch summary of a second r/AI_Agents-sourced post (via aiweekly.co/alerts/multi-agent-ai-breaks-on-constraint-transfer): "the real gap is transferring constraints and identity between agents, not storage... breaking in production not because agents forget information, but because they forget their rules."
- **Why it looks unbuilt/untested**: Framed explicitly as a mislabeled/overlooked category (the community keeps building shared-memory tools that solve the wrong problem); no named product addressing "constraint transfer" specifically turned up in the same searches.
- **Maturity**: OPEN
- **Verdict notes**: WebSearch for "constraint transfer"/"identity transfer" at agent handoffs found only blog/practitioner discussion (aiweekly.co's summary of the originating Reddit post, tianpan.co, urandom.io, futureagi.com glossary entry, channel.tel) describing the failure mode and recommending ad hoc "handoff contracts," but no named product, library, or paper that implements constraint/identity transfer as a first-class mechanism. No GitHub repo surfaced for this specific framing.

### P8: Decision heuristic / guardrail against reaching for multi-agent when a single agent would do
- **What it is**: A concrete rule or tool that helps a builder decide *before* building whether a task genuinely needs multiple agents (parallelizable, needs isolation, needs specialization) versus a single agent with better tools/context — because the default instinct is to over-architect.
- **Evidence**: Hacker News, "Learning by building a multi-agent design lab. Yet, single agent works better" — 4 points, 2026-10-21 (per last30days engine run); corroborated by WebSearch: "A widely shared post argues that a system needs roughly two or more yes answers to justify multiple agents, and otherwise a single agent with good tools is enough" and a Latenode community thread asking "does orchestrating them actually reduce complexity or just move it somewhere else?"
- **Why it looks unbuilt/untested**: Recurs as a repeated question/discussion across HN and multiple community forums (Latenode threads, r/AI_Agents) rather than a settled, tool-backed answer — people are trading informal heuristics in prose, not using a shared decision tool.
- **Maturity**: PARTIAL

### P9: Cost/value accounting for multi-agent code review
- **What it is**: Concrete measurement of what running a multi-agent code-review pipeline actually costs (tokens, latency, $ ) versus what additional issues it catches compared to a single reviewer agent — turning "more agents review better" from a vibe into a measured tradeoff.
- **Evidence**: Hacker News, "What Claude Code's multi-agent code review costs and finds" — 3 points, 4 comments, 2026-10-21, https://quickchat.ai/post/claude-code-multi-agent-code-review (per last30days engine run).
- **Why it looks unbuilt/untested**: Only one such cost/benefit write-up surfaced in the run, framed as a single team's informal experiment rather than a repeatable benchmark or tool other teams could run on their own pipelines.
- **Maturity**: PARTIAL
- **Verdict notes**: Several independent cost datapoints already exist: "Adversarial Review" (arXiv 2608.18167, pre-registered, finds a 2-agent writer/critic setup Pareto-optimal on cost-quality, but a 5-agent variant worse); a LeadDev study on 116 LiveCodeBench tasks reporting concrete cost/latency deltas ($0.19→$0.44, 38.5s→112.4s) and an accuracy *drop*; "CodeHealth" (arXiv 2610.21914, 465 PRs); and a GitHub repo literally named for this gap (PROrunner926/copilot-cache-scout, "Multi-Agent Code Review Cost Benchmark 2026," created 2026-11-12). No single standardized, repeatable benchmark tool other teams can run on their own pipelines has emerged yet, so the gap is real but not unaddressed.
