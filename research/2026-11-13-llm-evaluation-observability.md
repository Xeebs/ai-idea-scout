## Candidate patterns

### P1: Self-hosted LLM proxy as the only reliable observability lens into third-party LLM API traffic
- **What it is**: Teams running production LLM features on hosted APIs (OpenAI, Anthropic, etc.) have no visibility into their own traffic — latency, cost, failure modes, retries — unless they interpose their own proxy layer in front of the vendor API.
- **Evidence**: Hacker News, "If you don't run your own LLM proxy, how do you know whats going on?" (jrdsgl.com), 2026-10-18, 303 points / 220 comments — per the last30days engine run (Query 2).
- **Why it looks unbuilt/untested**: The post's own title is the complaint — framed as a near-rhetorical "how the [heck] do you even know" — with 220 comments of engagement suggesting this is a live, contested pain point rather than a solved one; no dominant off-the-shelf answer surfaced in the evidence.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub search and WebSearch both surfaced multiple large, actively maintained self-hosted LLM proxies built specifically as this observability lens: LiteLLM proxy (BerriAI, ~61-63k GitHub stars, "1B+ requests proxied" per vendor, logging/cost-tracking hooks built in), Langfuse (~37k stars, acquired by ClickHouse Jan 2026), Portkey gateway (~12.4k stars, OTel-compatible), and Helicone (widely recommended drop-in proxy, though one competing vendor claims it's now in maintenance mode post-Mintlify-acquisition). Multiple well-resourced, well-adopted implementations squarely close this gap.

### P2: Deterministic / non-LLM-judge regression testing for AI agents
- **What it is**: Instead of using an LLM to judge whether an agent's new version regressed, builders are shipping tools that detect behavioral regressions with deterministic, non-LLM checks (golden baselines, structural diffs) to avoid the cost, latency, and non-determinism of LLM-as-judge.
- **Evidence**: Show HN, "Apgar – Catch agent regressions without an LLM judge" (github.com/oimo-ai/apgar), Hacker News, 2026-10-29 — per the last30days engine run (Query 2). Corroborated by WebSearch (run live this session): an existing open-source project "EvalView" that does deterministic regression checks against golden baselines with LLM-as-judge as only an optional add-on, and a blog post "Why your agent needs a regression gate" (agentdbg-web.pages.dev) independently arguing the same anti-LLM-judge position.
- **Why it looks unbuilt/untested**: Multiple independent, small/unendorsed projects (Apgar, EvalView, the agentdbg blog) are converging on the same complaint about LLM-judge evals without any one of them being an established, widely-adopted standard — low HN score (3 points) on the Apgar launch itself suggests this hasn't broken into mainstream tooling yet despite the recurring argument.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for "agent regression testing" turned up a long tail of small/fragmented attempts — Trajectly (now archived), agentest ("record, replay, diff, and judge"), agent-ci, ai-eval-forge, somenpatra-acn's agentic-regression-testing — none with major adoption. WebSearch found a June 2026 arXiv paper (2606.11686) proposing a layered, LLM-free testing framework and several practitioner blogs (tianpan.co, dev.to) advocating "behavioral contracts" as a deterministic layer, but every source frames deterministic checks as a complement to, not a replacement for, LLM judges — no dominant standalone tool exists, confirming a real, differentiable gap.

### P3: Using an LLM's self-reported confidence score as an eval/calibration signal is unreliable
- **What it is**: A critique-driven pattern: teams have been using LLM-generated confidence scores (the model stating how sure it is) as a proxy signal for output quality or calibration in evals, and this is being called out as fundamentally unreliable.
- **Evidence**: Hacker News, "Using LLM for confidence scoring is a bad idea" (rumple.github.io), 2026-10-21, 228 points / 107 comments — per the last30days engine run (Query 2).
- **Why it looks unbuilt/untested**: High engagement (107 comments) on a critique with no clear, agreed-upon replacement technique surfaced in the evidence — suggests the community knows the current common practice is broken but hasn't converged on what to do instead.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found genuine research-grade alternatives — SelfCheckGPT (potsawee/selfcheckgpt on GitHub, sampling-consistency hallucination detection), logit-based confidence, and post-hoc calibration methods described in multiple 2026 arXiv papers (e.g. ConfidenceBench, 2601.08064, 2601.08134) — but these are research reference implementations, not packaged production eval tools that replace self-reported confidence as a drop-in signal. No maintained product surfaced; the gap a serious build would target (practical, adoptable calibration tooling) is real.

### P4: Windowed/incremental discovery for continuous evaluation-sampling pipelines over production AI event streams
- **What it is**: Systems that continuously sample production LLM/agent events for evaluation (e.g., an hourly clustering sampler) need an efficient way to discover *which* teams/events actually have new activity worth sampling, rather than re-scanning the full event table every run.
- **Evidence**: GitHub, PostHog/posthog PR #122573, "fix(aio): discover eval sampler teams from the run's window", 2026-10-23, 2 reactions / 6 comments — per the last30days engine run (Query 2). PR body (quoted verbatim from engine output): "The hourly evaluation clustering sampler spends almost all of its ClickHouse time finding nothing. Team discovery returns every team with any AI events in the last days, and the coordinator starts one sampler child per team and evaluation job."
- **Why it looks unbuilt/untested**: Even a well-resourced, shipping product team hit this as a fresh bug/inefficiency in their own eval infrastructure rather than reusing an existing solved pattern — the fix is a one-off windowed-query patch, not a reusable "which traces need eval" router that other teams building similar continuous-eval pipelines could adopt directly.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found that "continuous production trace sampling for eval" as a general capability is already a mature, shipped feature across multiple well-funded, maintained platforms: W&B Weave Online Evaluations (filter + random sampling), Agenta (filter + sampling rate), Langfuse (configurable-rate online evaluators), Arize Phoenix (interval-based sampling), and Traceloop. The specific PostHog PR is an internal ClickHouse-query efficiency fix inside one product, not an externally unmet need — teams building this today would reach for an existing platform rather than build the discovery mechanism themselves.
