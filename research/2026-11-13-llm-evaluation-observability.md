## Candidate patterns

### P1: LLM-as-judge version drift with no pinning/recalibration workflow
- **What it is**: Eval harnesses call out to a hosted judge model (e.g. GPT/Claude/Opus) to score outputs; when the provider silently upgrades that model, judge scores shift even though nothing in the product changed, and dashboards keep showing the old label as if nothing happened.
- **Evidence**: Multiple tianpan.co posts ("The Eval Harness Whose Judge Model Was Upgraded Silently," "LLM-as-Judge Drift: When Your Evaluator Upgrades and All Your Numbers Move") found via WebSearch describe exactly this failure; a Modelwire summary of an arXiv paper ("When the Judge Changes, So Does the Measurement," arXiv 2412.12509) frames it as hidden measurement drift undermining reproducibility; an Enterprise DNA practitioner review (sourced from Reddit discussion) reports LLM-as-judge reaching only 60-70% agreement with human labels at best.
- **Why it looks unbuilt/untested**: Sources describe ad-hoc mitigations only — "pin judge versions in eval metadata," "run periodic human calibration," "use anchor sets" — with no consensus cadence (one source suggests weekly, another quarterly), and no named tool that automates judge-version pinning + auto-recalibration-on-drift as a built-in feature.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos` for "judge model pinning" / "judge calibration drift" returned nothing relevant beyond tiny repos (TrustifAI/typed_evals 19 stars, evalhawk 1 star). WebSearch found the Attest framework (attest-framework.github.io) keys calibration metrics by rubric-name/version/prompt-hash and bumps invalidate stale data on purpose — a real but narrow, docs-only building block, not a confirmed auto-pin+auto-recalibrate product. Everything else is tianpan.co blog posts describing the problem, not tooling. No shipped tool automates the full pin+recalibrate loop.

### P2: Golden/eval dataset decay with no production-drift-triggered refresh
- **What it is**: Static "golden" eval sets used to gate LLM app releases quietly stop reflecting real traffic as users, docs, tools, and policies change — the eval suite keeps reporting high pass rates while real-world failures climb.
- **Evidence**: tianpan.co's "Golden Dataset Decay" post and oneuptime.com's "Why Did Your LLM Golden Dataset Go Stale?" (found via WebSearch) both describe a suite reporting 87% pass rate while users complain about broken outputs; a vendor post notes golden datasets become outdated before teams even finish building them, and that post-update comparisons to prior versions break.
- **Why it looks unbuilt/untested**: Proposed fixes in the sources are manual heuristics ("rebuild when system prompt/model/retrieval config changes," "compare prod sample to golden set periodically") rather than an automated trigger that watches production-vs-eval divergence and fires a refresh — no shipped tool doing this was found.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for "eval golden dataset drift"/"eval dataset drift detection" surfaced only 0-star, single-commit repos (angie091120-cpu/llm-regression-gate, rbumg/evalgate, manuelbomi/golden-dataset-eval-framework) that do CI regression gating, not drift-triggered refresh. WebSearch confirms drift-detection methodology (embedding divergence vs. production sample, Arize/Galileo/oneuptime blog posts) exists as a monitoring concept inside broader observability platforms, but no tool that closes the loop — detect drift and auto-fire a golden-set refresh — was found anywhere.

### P3: DIY span-based LLM tracers built instead of bought, to avoid vendor lock-in/data sharing
- **What it is**: Teams skip commercial LLM observability platforms and build their own lightweight spans-table tracer for LLM calls, explicitly trading commercial features for data control and tight product integration.
- **Evidence**: A r/LLMDevs thread "Is anyone building LLM observability from scratch" (found via WebSearch, surfaced through redlib mirrors since Reddit's own API 403'd the engine directly) has a commenter stating "We built our own tools instead of buying, which got us total flexibility, tight integration into our product and prevented our data from being shared with another third party," with a second commenter confirming they "paid the cost of building" and wrote up the rationale; Mesa's engineering blog ("why we built our own observability") independently describes ripping out Sentry for a custom spans-table tracer.
- **Why it looks unbuilt/untested**: This is explicitly a recurring one-off build, not a reusable package — each team re-implements the same spans-table pattern from scratch rather than adopting a shared minimal self-hosted library.
- **Maturity**: SATURATED
- **Verdict notes**: The exact motivations teams cite for DIY'ing (data control, no third-party sharing, self-hosting, tight product integration) are already squarely covered by multiple maintained, well-resourced OSS projects: Langfuse (MIT, self-hostable, 37.4k GitHub stars, pushed today), Arize Phoenix (source-available, self-hosted, OTel-based), and OpenLLMetry/Traceloop (Apache-2.0 OTel instrumentation, 7.5k stars). `gh search repos` for a reusable minimal "spans table" micro-library found nothing (only unrelated construction/CSS/SQL repos), confirming no one ships the exact minimal shape teams build by hand — but the broader self-hosted-tracing gap these DIY efforts are solving for is already closed by well-resourced, actively maintained projects.

### P4: Self-hosted LLM proxy as the only way to see what's actually happening with hosted-API usage
- **What it is**: Developers who call third-party LLM APIs directly (not through their own infra) have no visibility into what's actually being sent/returned/costed unless they route everything through a self-run proxy layer.
- **Evidence**: HN thread "If you don't run your own LLM proxy, how do you know what's going on?" surfaced directly by the last30days engine run — 303 points, 220 comments (strong engagement for this niche), https://jrdsgl.com/if-you-dont-run-your-own-llm-proxy-how-the-fuck-do-you-even-know-whats-going-on/.
- **Why it looks unbuilt/untested**: The framing of the post itself ("how do you even know what's going on" without one) is a complaint that this should be table-stakes tooling but isn't a default/easy setup for individual devs and small teams today.
- **Maturity**: SATURATED
- **Verdict notes**: `gh search repos "self hosted LLM proxy"` and related queries returned a dense, active field: BerriAI/litellm (63.2k stars, pushed today, "the fastest, litest AI Gateway" with cost tracking/logging/guardrails) and Helicone/helicone (6.3k stars, YC W23, pushed yesterday) are both mature, maintained products squarely solving "see what's happening with hosted-API usage," plus a dozen+ newer self-hosted proxy repos created in the last few months (apiguard-opensource, gate-llm, tiller-router, llmtee, Stockyard). The HN post's "how do you even know" framing is a discoverability/onboarding complaint, not evidence the tooling doesn't exist.

### P5: No automatic clustering of annotated eval failures into shared failure categories
- **What it is**: After practitioners manually annotate failed LLM outputs with free-text notes ("wrong tone for investor," "too casual for luxury buyer"), existing eval tools don't recognize these as one underlying pattern and propose a unified category (e.g. "persona-tone mismatch") automatically.
- **Evidence**: hamel.dev's "Evals FAQ" (Hamel Husain & Shreya Shankar), found via WebSearch, names this directly as "Gap 1: error analysis and pattern discovery" and states most eval tools only handle "table stakes" — trace logging, metric tracking, prompt playgrounds, annotation queues — not this.
- **Why it looks unbuilt/untested**: The source explicitly frames it as a gap teams must fill themselves, and advises readers to "watch for vendors addressing these gaps" as a sign of quality — implying it is not yet commonly solved.
- **Maturity**: PARTIAL
- **Verdict notes**: Narrow implementations do exist: faultmap (PyPI/GitHub, embedding-space clustering + statistical hypothesis testing to surface failure slices) but at only 1 GitHub star and last pushed April 2026 — essentially unmaintained/unadopted; Snorkel AI's SDK ships an `ErrorAnalysis` clustering API as a commercial feature; Atla AI published a comparative write-up of clustering methods for this exact problem. None is a widely-adopted, evaluated standalone tool, and hamel.dev (a credible practitioner source, cited in the digest) still names this as an open gap as of this search — consistent with PARTIAL rather than SATURATED.

### P6: Emerging standard for agent trajectory interchange (lineage + streaming), very early stage
- **What it is**: A proposed format/spec ("ATIF" — Agent Trajectory Interchange Format) for representing agent execution trajectories with streaming, lineage, and strong semantics, intended to let different observability tools share trajectory data.
- **Evidence**: GitHub RFC "RFC: ATIF v2.0 with streaming, lineage, and strong semantics" in harbor-framework/harbor, surfaced directly by the last30days engine (8 reactions, 7 comments, 2026-11-06), with a reviewer comment calling it "a major upgrade for agent trajectory observability."
- **Why it looks unbuilt/untested**: It is an open RFC under active discussion, not a shipped/adopted standard — exactly the "partially built, in-flight" signal this digest is meant to surface.
- **Maturity**: PARTIAL
- **Verdict notes**: harbor-framework/harbor itself is very mature (7,026 stars, pushed today), and WebSearch found ATIF (the base format, v1.0–v1.8) already has multiple independent implementations — NVIDIA's NeMo Agent toolkit, Arize Phoenix (ATIF trajectory import/export), and a Rust crate (vtcode-exec-events) — so the underlying interchange-format concept is not a blank slate. But the specific thing named in this pattern, the v2.0 RFC adding streaming + lineage + strong semantics (8 reactions, 7 comments, opened 2026-11-06), has no shipped implementation yet — it's genuinely in-flight on top of an otherwise-adopted base format.

### P7: Eval-as-CI-gate for agent/code-review behavior changes, built ad hoc per project
- **What it is**: Projects wire an LLM-judge-scored eval set directly into CI so that a pull request automatically gets an eval smoke test (comparing F1 or similar metrics against a gold set) before merge, gating agent-behavior changes the way unit tests gate code changes.
- **Evidence**: kodustech/kodus-ai GitHub PR "feat(review): lean finder with embedded verify, dedup and enrichment," surfaced directly by the last30days engine — PR description cites "30-PR light set rerun... CI eval smoke on the head... Opus 5.5 final F1: main 43.0 → branch 45.3" with a linked CI run.
- **Why it looks unbuilt/untested**: This is a one-off, project-specific CI wiring (bespoke script + gold set for one repo), not a reusable "eval-as-CI-gate" tool/action that other agent projects could drop in.
- **Maturity**: PARTIAL
- **Verdict notes**: Established vendors (Braintrust, FutureAGI, Cursor's Agent SDK) document and support wiring their eval SDKs into CI as a PR gate, and tutorials (OpenRouter, oneuptime, kinde) describe the pattern in detail — but `gh search repos` for a dedicated, broadly-adopted drop-in "eval-as-CI-gate" GitHub Action found only several independently-named `evalgate`/`Evalgate` repos, all at 0 stars (AgentPostmortem/Evalgate, sam0690/evalgate, Kyrollo/evalgate, muhammadshayan124/evalgate). No single reusable action has real adoption; teams still wire this bespoke per-project exactly as the digest's kodus-ai example shows.

### P8: "Vibes-based" lightweight eval as a deliberate reaction against heavyweight eval frameworks
- **What it is**: A visible counter-movement arguing that formal eval frameworks (datasets, judges, dashboards) are overkill for most LLM app iteration, and that fast, informal "vibe checks" by a human reviewing outputs are what most teams actually need and actually do.
- **Evidence**: Two pieces surfaced via WebSearch directly defending this position: "In defense of vibes-based evaluations" (frontierai Substack) and "Vibe Checks Are All You Need" (olshansky Substack) — both explicitly positioned as pushback against the standard "you need formal evals" advice circulating elsewhere in the same search results (e.g. deeplearning.ai's "We need better evals for LLM applications").
- **Why it looks unbuilt/untested**: The debate itself signals a gap — no tool was found in this run that formalizes a lightweight "structured vibe check" (something between a full eval framework and purely ad hoc manual review) that practitioners on both sides would accept as sufficient rigor without the overhead.
- **Maturity**: PARTIAL
- **Verdict notes**: A handful of small tools already attempt exactly this middle ground — a `vibecheck` YAML-first CLI (hevmind case study, hosted companion at vibescheck.io in invite-only preview), `smoleval` ("minimal & lightweight evaluation framework for AI agents," Winston-503/smoleval), and zcaceres/easy-eval — but `gh api` confirms Winston-503/smoleval sits at 1 star, and none shows signs of wide adoption or active maintenance. The format-level debate (vibes vs. formal evals) is real and unresolved, and no credible, evaluated tool has closed it.
