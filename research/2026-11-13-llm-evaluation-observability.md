## Candidate patterns

### P1: Self-hosted LLM proxy as the only reliable observability layer for hosted-API calls
- **What it is**: Teams calling hosted LLM APIs (OpenAI, Anthropic, etc.) run their own reverse proxy in front of every call specifically to capture the request/response telemetry the provider's own dashboard doesn't expose — logging, replay, and request-level debugging bolted on from outside the vendor's stack.
- **Evidence**: Hacker News post "If you don't run your own LLM proxy, how do you know whats going on?" — 303 points, 220 comments, 2026-10-18 (last30days engine, Hacker News).
- **Why it looks unbuilt/untested**: The high comment count on a post framed as a DIY necessity ("how do you even know what's going on") suggests no off-the-shelf proxy-as-observability product has become the obvious default for typical teams — people are still building and justifying their own.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub + WebSearch found multiple actively maintained self-hosted LLM proxies built exactly for this: `BerriAI/litellm` (OSS proxy for 100+ LLM APIs with built-in OTel export, de facto default), Portkey's gateway (MIT, self-hostable, built-in observability), and Helicone (self-hosted stack with Cloudflare Workers proxy + ClickHouse logging, though reportedly in maintenance mode post-acquisition). Langfuse and Arize Phoenix are also commonly paired with these as the observability backend. The HN DIY framing reflects adoption lag / NIH, not an absence of off-the-shelf options.

### P2: LLM-as-judge confidence scores are unreliable and unaudited
- **What it is**: Using an LLM to emit a numeric "confidence score" (for routing, guardrails, or escalate-to-human decisions) is being publicly challenged as a flawed pattern, with no standard calibration or audit layer to check whether the scores mean anything.
- **Evidence**: Hacker News post "Using LLM for confidence scoring is a bad idea" — 228 points, 107 comments, 2026-10-21 (last30days engine, Hacker News). Corroborating academic signal: arXiv paper "DramaGrow: A Regime-Aware Benchmark for Auditing LLM Judges of Multi-Episode Drama" (2026-11-10), surfaced via a GitHub "Frontier watch" research-tracking issue in `imhurl23/evals_research_repo` (last30days engine, GitHub).
- **Why it looks unbuilt/untested**: The HN discussion is a critique, not a pointer to a fix; the only concrete auditing work found is a brand-new benchmark proposal (a paper, not a tool), meaning there's no deployed judge-auditing layer teams can actually install.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found `judgekit` (PyPI/GitHub `mohammadi-hadi/judgekit`) — a pip-installable CLI that audits judges for agreement, bias, and calibration (ECE/Brier) — but it is brand new (pushed 2026-11-03, 0 GitHub stars, single author, no adoption signal) and unverified for production use. The OECD-catalogued "Audit the Judge" targets pairwise verdicts, not confidence calibration specifically, and `TH-Score`/the DramaGrow benchmark are research metrics/papers, not packaged tools. No maintained, adopted calibration-audit product exists; a serious build here would be clearly differentiated.

- **Evidence**: Three separate GitHub PRs surfaced in the same 30-day window (last30days engine, GitHub): `carlos17031691/base-ai` "feat(BASE-026): deterministic AI eval suite with LLM-as-judge" (YAML-driven `base-ai eval` CI runner); `jerryliu-playground/curb` "Phase 3: pnpm eval with deterministic checks and an LLM judge" (writes `evals/report.md` + versioned `evals/runs/<id>.json`); `reoneo97/echo-vault` "Agent-first generation: MLflow tracing, tutor agent, eval harness, vault scoping" (MLflow autolog tracing + per-batch session IDs). Corroborated by WebSearch: Mura's "BOLT" engineering post stating off-the-shelf eval tools "didn't fit their data model or workflows, and most teams they spoke with had rolled their own"; Joshua Gomes's blog "Why I Built Our Own LLM Eval Stack" describing building a "Prompt Observability Console" after evaluating LangSmith, Braintrust, and Phoenix.
- **Why it looks unbuilt/untested**: Multiple unrelated projects are each separately building the same deterministic+judge+versioned-history CI primitive from scratch in the same month — a sign there's no lightweight, composable, self-hostable building block for this that fits typical CI pipelines without pulling in a full platform.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub + WebSearch confirm this exact primitive is already a mature, widely-adopted open-source category: `promptfoo/promptfoo` (27,143 stars, pushed today 2026-11-13, declarative YAML config, deterministic assertions (`exact`/`contains`/`regex`/`json_schema`), LLM-judge rubrics, maintained GitHub Action, `promptfoo view` run history UI) and `confident-ai/deepeval` (19,474 stars, pushed yesterday, pytest-style CI runner, deterministic DAG metrics + LLM-judge metrics, Confident AI dashboard for run history). `gh search repos` also surfaced a dozen small personal/learning repos re-implementing this same pattern, which is NIH/discoverability failure rather than a real tooling gap — the hand-rolling teams in the digest's evidence appear not to have found promptfoo/deepeval, not to have found nothing.

### P5: Production eval pipelines can silently fail and nobody notices
- **What it is**: A team turns on evaluation against live production traces and the pipeline runs without error but produces no usable scores — a failure mode that isn't surfaced as an alert or flagged by the eval tool itself.
- **Evidence**: WebSearch surfaced a dev.to post titled "I switched on production evals for my LLM app and they scored nothing" describing exactly this failure.
- **Why it looks unbuilt/untested**: The existence of this write-up as a cautionary tale implies current eval tooling has no built-in "is my eval pipeline actually scoring anything" health check — an observability gap in the observability layer itself.
- **Maturity**: OPEN
- **Verdict notes**: Multi-channel search (GitHub + WebSearch for monitoring/alerting products and for the specific failure mode) found only after-the-fact blog write-ups of the failure (the dev.to post itself, plus `gorelik.net`'s "When your LLM pipeline silently returns zero", `tianpan.co`'s on-call postmortem) and generic advice to build your own Prometheus/Grafana alerting (DeepEval's docs mention exporting scores to Prometheus, but that's DIY wiring, not a built-in "did my eval actually run" sanity check). No vendor (Langfuse, Braintrust, Confident AI, FutureAGI) advertises a dedicated zero-score/dead-pipeline health check as a feature.

### P6: Eval frameworks don't gracefully handle swapping the judge model
- **What it is**: Switching the LLM used as the "judge" in an eval (e.g., via API or MCP) can break on model-specific settings carried over from the old judge, such as a saved reasoning-effort level the new model doesn't support.
- **Evidence**: GitHub PR `PostHog/posthog#133640`, "fix(aio): drop a saved reasoning level when an eval switches models" (2026-11-11, 3 reactions, 5 comments) — describes agents switching an eval's LLM judge to a different model via API/MCP getting a 400 error because the eval still has an incompatible saved reasoning level from the prior model; the UI path already handled this but API callers didn't (last30days engine, GitHub).
- **Why it looks unbuilt/untested**: This is a live bug in a maintained, shipping product (PostHog), not a solved abstraction — judge-model portability/versioning is still being patched reactively rather than designed for upfront.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found only reactive, narrow fixes and advice, not a general solution: PostHog's own PR patches this one symptom after the fact; blog posts (`tianpan.co`'s "The Eval Harness Whose Judge Model Was Upgraded Silently" and "Model Migration Bills You Twice") recommend manually pinning judge snapshot IDs and re-running against a frozen judge, but describe this as a known pain point teams work around rather than something eval frameworks (promptfoo, deepeval) handle natively. No framework was found that advertises graceful judge-model migration as a designed-for feature.
