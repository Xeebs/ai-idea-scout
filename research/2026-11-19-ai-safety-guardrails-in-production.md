## Candidate patterns

### P1: Per-layer false-positive tracking for stacked guardrail pipelines
- **What it is**: Production guardrail stacks (PII redaction + prompt-injection classifier + policy/structured-output checker, run in sequence) compound their individual false-positive rates — a team can end up blocking a much higher share of legitimate traffic than any single layer's stated rate suggests, with no standard way to attribute a given bad block to which layer caused it.
- **Evidence**: tianpan.co practitioner writeup: a team's "aggressive early guardrails reached a 15 percent false-positive rate," which pushed users to route around them; jacar.es: guardrail frameworks catch 60-85% of real problems but misfire on 5-15% of turns; tianpan.co explicitly notes false-positive rates "compound across guardrail layers."
- **Why it looks unbuilt/untested**: Multiple independent practitioner posts describe discovering the compounding effect after the fact (users already routing around the system) rather than citing a tool that attributes/forecasts it per-layer before shipping. qaskills.sh separately argues current FP measurement practice ("zero false positives in 20 cases") is statistically too weak to trust — i.e., the measurement layer itself is immature.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search (`guardrail pipeline false positive`, `guardrail false positive attribution`) found only `R123456-123/layered-guardrails` (1 star, created 2026-10-30) — a small ablation-evaluation repo reporting ASR/FPR/latency per layer, i.e. a demo, not an attribution product. WebSearch for the productized version found only vendor-blog claims (FutureAGI glossary pages claim "per-evaluator FPR tracking on every release" but no published benchmark or demo was surfaced to verify it) and Openlayer/DZone describing manual per-layer telemetry as advice, not a shipped feature. No evaluated, adopted tool found — demo-level implementation + unverified vendor claims = PARTIAL.

### P2: Agent tool-call/parameter policy enforcement as a layer distinct from prompt-level guardrails
- **What it is**: A dedicated runtime policy engine that checks an agent's actual tool calls and parameters before execution (least-privilege/allow-list style), separate from and complementary to text-level input/output guardrails that only look at prompts and completions.
- **Evidence**: Airia blog, titled "why every tool has guardrails but few have agent constraints yet," frames this explicitly as a gap: "Guardrails operate at the prompt-response boundary, analyzing text before and after model interaction," while constraint-checking of tool calls is separate and underbuilt; Arthur AI column lists "runtime policy engines" as one of several governance pillars enterprises are still assembling piecemeal; a Geordie piece states cross-tool enforcement mechanisms "are incompatible, and none share a unified view of the workflow as it spans systems."
- **Why it looks unbuilt/untested**: All three sources describe this as a current-state gap ("few have," "incompatible," "no universal standard for how much should be handled by the model layer versus the broker layer" per a Non-Human Identity journal FAQ) rather than citing a shipped, broadly-adopted cross-tool runtime policy product.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found multiple well-resourced, shipped implementations squarely covering this: AWS Bedrock AgentCore's Policy gateway (GA since March 2026, Cedar-based tool-call policies), a Microsoft open-source runtime toolkit that intercepts/evaluates tool calls at execution (reported April 2026), Galileo's "Agent Control" centralized guardrails platform (March 2026), C1.ai's "Agent Runtime Governance," and the open-source Spice runtime policy layer plus GitHub repos `jstxn/agentgate` and `Sparshg3011/tripwire` (both 2026, policy-enforced tool-call gateways). ≥2 maintained, well-resourced products already close this gap — the digest's framing ("few have") is outdated relative to 2026 launches.

### P3: Conversation-level (multi-turn) jailbreak detection vs. single-turn classifiers
- **What it is**: Current production jailbreak guardrails are largely single-turn LLM classifiers scoring one prompt/response pair at a time; attackers evade them by spreading an attack across multiple turns, switching languages, or encoding payloads, none of which a single-turn classifier is positioned to catch.
- **Evidence**: Zenity's analysis of OpenAI AgentKit's guardrail found its jailbreak check "relies on an LLM classifier" and that disguised attacks "written in another language, encoded, or spread across multiple turns, can slip past detection entirely"; alice.io's post is titled "LLM guardrails are being outsmarted by roleplaying and conversational prompts."
- **Why it looks unbuilt/untested**: Both sources describe this as a live, currently-exploitable weakness in a named shipped product (AgentKit), not a solved problem — the complaint is about a specific guardrail that exists today failing against a known evasion class, with no counter-tooling cited.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found only research-stage coverage: ICML-2026 benchmark `MultiBreak` (10,389 multi-turn adversarial prompts), `MT-JailBench`, and ICLR-2026 `SafeDialBench` — all evaluation datasets for measuring model safety, not deployable detectors. GitHub search (`multi-turn jailbreak detection`) found only `Yash-001100/jailguard` (0 stars, created 2026-06-08, inactive since). No shipped production detector for conversation-level jailbreaks was found; benchmarks exist but nothing deployable/evaluated in production — demo/research-only implementations = PARTIAL.

### P4: Guardrails scoped to direct user input missing indirect/tool-ingested prompt injection
- **What it is**: Guardrail systems are commonly built to screen the user's direct chat input, but agents also ingest content via tools (uploaded files, retrieved web pages) that can carry hidden instructions the agent treats as developer-level, bypassing input-scoped guardrails entirely.
- **Evidence**: A security vendor writeup (prompt.security) describes the concrete scenario: "a user uploads a PDF that contains hidden instructions in white-on-white text; the agent reads them as if they came from the developer" — the guardrail never saw this as "user input" to screen.
- **Why it looks unbuilt/untested**: The source frames this as an architectural blind spot in current guardrail scoping (input vs. tool-content) rather than describing an existing content-provenance-aware guardrail that handles it; no counter-tool was surfaced in this search.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch confirmed Microsoft's Azure AI Content Safety ships a dedicated "Document attack" / indirect-attack shield distinct from its user-prompt shield, explicitly designed to catch hidden instructions embedded in grounded/retrieved documents before they reach the agent (per Microsoft Learn docs and a hands-on training module demo) — exactly the scenario the digest's P4 describes. Lakera Guard (now Check Point) is cited across multiple vendor comparison guides as a second commercial API covering indirect injection in RAG/document pipelines. Two well-resourced, maintained, shipped products squarely cover this gap.

### P7: Containment/blast-radius design as the explicit alternative to jailbreak prevention
- **What it is**: Instead of trying to make jailbreak guardrails airtight (acknowledged as not fully achievable), teams design for containment: least-privilege tool scoping, isolated credentials per tool, and capability minimization, so a successful jailbreak has a bounded blast radius rather than full account/system access.

- **Why it looks unbuilt/untested**: Both sources present this as architectural guidance/talk content aimed at builders who haven't yet done it, not a reference to a standard, pre-packaged containment framework that teams adopt off the shelf — it's described as discipline each team has to build for itself.
- **Maturity**: PARTIAL
