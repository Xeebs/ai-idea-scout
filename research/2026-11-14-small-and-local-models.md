## Candidate patterns

### P1: Fail-closed privacy router between local and cloud models
- **What it is**: A routing layer that classifies a request as sensitive and pins it to a local/small model permanently — never silently falling back to a cloud model, even on timeout or local failure. Distinct from latency-motivated hybrid routing (which optimizes cost/quality and treats cloud fallback as acceptable).
- **Evidence**: WebSearch surfaced an open-source project described as "llm-localfirst" that pins sensitive calls to a local model with no cloud fallback, and a developer write-up describing the failure mode this guards against — a local-inference timeout that defaulted to a cloud provider "to ensure high availability," which the author concluded was the wrong trade for a privacy-first system. A separate benchmark (Cactus hybrid router pairing a local Gemma4-2B with Gemini fallback) reported matching Gemini 3.1 Flash-Lite quality while routing only 15–55% of tasks to the cloud, per the "Cactus Hybrid Router: Gemma4-2B Local + Gemini Fallback" result.
- **Why it looks unbuilt/untested**: The WebSearch synthesis itself flagged the gap: "few sources explain how to make privacy classification reliable, since most routers depend on a sensitivity flag set by the caller" — i.e., the classification step that decides "is this sensitive" is manual/caller-declared, not automatic, across every example found.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found an exact-match project, `shaxzodbek-uzb/llm-localfirst` ("Fail-closed privacy routing + manager-worker delegation, MCP-native"), but it has 0 stars and hasn't been pushed since 2026-08-16 — a narrow, unadopted solo project. The Cactus hybrid router (Gemma4-2B + Gemini fallback) is a different, cost/quality-motivated pattern, not fail-closed. No tool anywhere automates the sensitivity-classification step itself; every example still relies on a caller-declared flag, so the core gap the community raised is real and unaddressed.

### P2: Tool-calling reliability treated as a model problem when it's a harness/parser problem
- **What it is**: A diagnostic/conformance layer that isolates whether a local model's tool-calling failure is caused by the model itself, the chat template, the streaming/parsing layer, or the serving stack — rather than users abandoning a model after assuming it's incapable.
- **Evidence**: A WebSearch-surfaced r/LocalLLaMA thread ("what are your struggles with tool-calling") drew multiple replies over several days; synthesis notes include a developer who spent days testing Gemma 4 12B QAT before giving up on tool-call consistency, a recurring report that calls work with streaming disabled and break with it on ("the model may have produced a perfectly usable call. The server simply choked on the wrapper state around it"), and other replies blaming an "upstream chat-template bug, not the model." A HN-adjacent signal (`I tested 12 small AI models on 2,500 design-system questions`, 3 pts) is titled around the finding that "the model wasn't what mattered" for a narrow task.
- **Why it looks unbuilt/untested**: Threads repeatedly disagree about root cause (model vs. template vs. server) with no shared tool to isolate it; one HF forum thread's only fix was "use an external agent framework as a workaround" rather than diagnosing the local serving stack.
- **Maturity**: PARTIAL
- **Verdict notes**: Found `Code-byte404/toolhound`, which attributes tool-calling failure to one of four causes (template bug / parser gap / model format / model decision) with bootstrap CIs — a close match to the pattern. But it's MLX-native/Apple-Silicon-only, 7 stars, last pushed 2026-07-06 (~4 months stale), i.e. a narrow single-platform tool, not a cross-runtime (llama.cpp/vLLM/Ollama) diagnostic. The broader community disagreement (model vs. template vs. server) documented in the digest's evidence remains unresolved for those mainstream serving stacks.

### P3: Cohort-level eval for distilled/task-specific small models
- **What it is**: An evaluation workflow for small models fine-tuned or distilled for one narrow production task that checks performance per user-segment/cohort, not just an aggregate benchmark score — because aggregate scores can rise while a high-value cohort silently regresses.
- **Evidence**: WebSearch found vendor guidance describing exactly this failure: a team distills a model, sees the global eval score drop two points, ships anyway, then discovers "the regression is concentrated on the highest-value cohort" (FutureAGI glossary content), with a second source (Redwerk) explicitly listing "no real eval data exists" as a reason distillation should not start.
- **Why it looks unbuilt/untested**: The recommendation ("build a production-shaped eval set from labeled real-world examples, not synthetic data," "evaluate per cohort") appears only as vendor-blog advice, not as a shared or open tool; no GitHub project or benchmark suite surfaced in the search for cohort-level small-model eval specifically.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos` for cohort/segment-level model-eval tooling returned zero results. WebSearch likewise found only vendor advice (FutureAGI glossary, Redwerk blog, Predibase's distillation playbook) recommending per-cohort regression tracking, plus ModelScope's EasyDistill toolkit which is a distillation pipeline with no cohort-eval feature. No GitHub project, benchmark suite, or product implements per-cohort regression gating for distilled models — genuine multi-channel search found only discussion and advice.

### P4: Hand-wired, fragile persistent-memory stacks for local agents
- **What it is**: Developers bolting external storage/retrieval (vector DB, markdown file, SQLite+sqlite-vec) onto a local small model to give it memory beyond its context window, because the model itself can't retain state.
- **Evidence**: WebSearch surfaced a Mem0 + Ollama + Qdrant integration guide where the author explicitly notes it is "not the official @mem0/openclaw-mem0 plugin" and warns that "the embedding dimensions in config must match the embedding model, or writes silently fail"; an LM Studio community plugin stores memory as a plain markdown file, with the author noting reliability "depends on the model's tool-use ability, and larger models are more reliable"; a dev.to post framed as "why do local AI agents forget you."
- **Why it looks unbuilt/untested**: Every example found is a DIY/community plugin with explicit fragility caveats (silent write failures, reliability tied to model size) rather than a robust packaged solution; one LocalLLaMA-sourced finding (full-history context stuffing "actively harmed recall at every tested model size") suggests the community hasn't converged on a standard fix even at the architecture level.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for "local agent persistent memory" / "mem0 ollama" / "sqlite-vec agent memory" returned a dozen+ repos (ollama-mem0-AI-chatloop-ts, self-learning-agent, mem0-broker, mem0-personal-ai-agent, ai-memory-assistant, mem0-persistent-ai-memory, etc.), but every one has 0–1 stars and is a solo DIY integration, confirming the digest's framing: many hands have built this, none robustly. No packaged, widely-adopted solution found.

### P5: Sparse/selective reading layer to cut agent token and latency costs
- **What it is**: A "reading control layer" that governs how much of a webpage/document/tool-response an agent actually admits into context, instead of reading entire objects when only sparse evidence is needed — aimed at the token/latency cost problem that's especially acute for small/local models with limited context budgets.
- **Evidence**: A paper surfaced directly by the last30days engine from r/LocalLLaMA (score 0, dated 2026-11-14): "[Paper] Read Less, Solve More: Token-Efficient Sparse Reading of External Content for AI Agents," describing "SparseRead, a reusable reading control layer that governs content admission" because "over-reading increases token and latency costs and can dilute relevant evidence." ### P6: Extreme (ternary/sub-1-bit-class) quantization vs. compress-from-large as competing on-device compression philosophies
- **What it is**: Two different routes to a model small enough to run on a phone: (a) design/train with ternary weights from the start for extreme size (sub-1GB) while keeping vision + tool-calling, or (b) start from a large capable model and compress it down to fit phone memory.
- **Evidence**: WebSearch surfaced "PrismML releases ternary AI models as small as 0.43GB for local agents" (runtimewire.com) under Apache 2.0 with vision and tool calling, and a separate analysis of "Bonsai 27B: What It Takes to Run a 27B-Class Model on a Phone" (braindetox.kr) explicitly contrasted as "the opposite path: compress a model that was born large."
- **Why it looks unbuilt/untested**: No head-to-head evaluation of the two approaches on the same tasks surfaced in search; both are vendor-reported figures (PrismML's own numbers per the source), and the Neowin counterpoint ("you can now run local AI models on your phone, but that doesn't mean you should") plus a builder quote that "input handling, not inference, was the bottleneck on low-end phones" suggests the actual on-device bottleneck (input/preprocessing pipeline) is separate from the model-compression debate and under-addressed by either camp.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirmed vendor-reported comparison data exists (PrismML's Ternary Bonsai 27B vs. a conventional 2-bit quantization of the same base model, e.g. AIME26 score 90.8 vs. 57.5), but no independent/third-party reproduction of a head-to-head was found, and a commentator explicitly called for independent verification of the vendor's own retention numbers. The digest's deeper point — that input-handling/preprocessing, not compression method, is the actual phone bottleneck — turned up only one unverified blog post on incremental tokenization and no dedicated tool or library addressing it; this sub-gap looks genuinely open but the overall pattern ties to PARTIAL per the rubric's tie-break rule.

- **Why it looks unbuilt/untested**: Found only as a single line-item in a vendor comparison page with no independent benchmark, adoption, or community discussion surfaced — no GitHub repo, no Reddit thread, no second source corroborating it in this run.
- **Maturity**: SATURATED
- **Verdict notes**: Needle is far more than a vendor line-item: it's `cactus-compute/needle` on GitHub (MIT, Show HN front-page, reached GitHub Trending), distilled from Gemini 3.1 Flash-Lite, with weights on Hugging Face under multiple mirrors (Cactus-Compute/needle, deobfre/needle, WillowVoiceAI/needle, nvcky/needle) and independent third-party bindings (`qipking/bevy_needle`, `lib-x/needle-go`).
