## Candidate patterns

### P1: Unmeasured error compounding when guardrails are stacked
- **What it is**: Teams chain multiple independent guardrail checks (PII redaction, injection/jailbreak detection, output validation, toxicity) in sequence, but nobody tracks how per-check error rates compound across the stack — five checks at 90% accuracy each yields ~59% end-to-end correctness, not 90%.
- **Evidence**: Practitioner writeup found via WebSearch ("AI guardrails production LLM safety news November 2026" query): a blog post explicitly working the 0.9^5 ≈ 0.59 math and warning "if you stack five guardrails and each one operates at 90% accuracy, your overall system correctness is not 90% - it is 59%"; corroborated by a November 2, 2026 Openlayer guide on guardrail placement changing "what you can reliably catch."
- **Why it looks unbuilt/untested**: The math is being pointed out as a warning in blog posts, not solved by tooling — no cited project computes or optimizes compounded guardrail reliability across a pipeline; teams are apparently stacking checks without a way to see the compounded miss rate.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos` for "guardrail compounding error rate pipeline" and "guardrail confidence score graded verdict" returned zero results. WebSearch surfaced only explanatory blog posts (tianpan.co, zof.ai "compounding interest of reliability debt", mindstudio.ai giving the R1×R2×...×Rn formula) that explain the math by hand — none link to or describe a tool, calculator, or product that actually computes/monitors compounded guardrail reliability across a live pipeline. Genuine multi-channel search found only discussion.

### P2: Binary allow/block verdicts discard the underlying confidence signal
- **What it is**: Guardrail classifiers for prompt injection and jailbreak detection return a yes/no decision even though the underlying detection is inherently probabilistic, throwing away confidence information that downstream logic (escalate vs. block vs. allow-with-logging) could use.
- **Evidence**: HN item "Binary Logic Breaks AI Safety: 'Yes, No, Probably'" (medium.com/@kate8382, 3 points, 2026-11-14), surfaced by the last30days engine's second run.
- **Why it looks unbuilt/untested**: The piece argues binary framing makes analyzing prompt injection "pointless" but names no shipped graded-verdict guardrail framework — it's a design complaint airing the gap, not a built alternative.
- **Maturity**: SATURATED
- **Verdict notes**: The specific complaint (binary allow/block discards confidence) is already closed by well-resourced, maintained products: BerriAI/litellm (large, actively maintained OSS AI gateway, confirmed via `gh search repos`) ships an "LLM-as-a-judge" guardrail that scores 0–100 against weighted criteria and blocks only below a threshold (default 80), not a binary verdict; Arize's guardrails offering does graded 0–2 scoring with confidence + distribution routing to allow/block/human-review with different thresholds per risk tier. Academic corroboration from two 2026 papers (FlexGuard, arXiv 2602.23636, calibrated 0–100 risk score; SelfGrader, arXiv 2604.01473, logit-derived confidence score) shows this is an active, multi-team area, not an unaddressed gap.

### P3: Legalese/formal-register text as a prompt-injection vector for document-reading agents

- **Why it looks unbuilt/untested**: The only cited defense is "a stronger, more explicit system prompt" — generic prompt hardening, not a guardrail product that specifically screens ingested documents for legal/formal-register injection patterns.
- **Maturity**: PARTIAL

### P4: In-house, low-latency, multi-signal guardrails gateway (built, not bought)
- **What it is**: A centralized guardrails microservice sitting in front of the LLM that screens inputs for prompt injection, jailbreaks, and harassment in one pass, enforced in full blocking mode across products, rather than adopting an off-the-shelf OSS guardrail library.
- **Evidence**: Reddit's own engineering writeup (found via WebSearch, mirrored at cluster-site.onrender.com) reporting an F1 of 0.97 at sub-25ms p99 latency for this in-house classifier, fully enforcing blocking in production.
- **Why it looks unbuilt/untested**: The company built this itself rather than using an existing option; named OSS guardrail frameworks (NeMo Guardrails, Guardrails AI, LLM Guard) are validator/orchestration layers, not pre-trained, single-pass, multi-signal classifiers hitting this latency/accuracy bar — nothing surfaced offers an adoptable equivalent.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found several adoptable alternatives that overlap but don't exactly match the stated bar (single-pass, multi-signal, F1 0.97, sub-25ms p99, full blocking enforcement): Meta's Llama Prompt Guard 2 (~20-50ms on H100, injection-only), an npm `llm_guardrail` package claiming <10ms running 3 parallel models (injection/jailbreak/malicious-content, unverified latency claims), "LLM Guard" (local scanner, no LLM call, claimed <10ms), and an open-source "AgentGuard" FastAPI service running 7 parallel checks. None of these report a verified F1 at that latency combined with full production blocking enforcement the way the Reddit writeup does, so the specific build-vs-buy gap is real but adjacent off-the-shelf options exist that a serious build would need to differentiate against.
