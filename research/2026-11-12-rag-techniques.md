## Candidate patterns

### P1: Agentic (iterative/self-correcting) retrieval built ad hoc, with no standard framework
- **What it is**: Developers are hand-rolling "agentic RAG" — an LLM loop that plans queries, retrieves, critiques its own retrieval, and re-queries — without realizing it is a named pattern, and without a shared library for the control loop (retry logic, stopping criteria, malformed-tool-call handling).
- **Evidence**: Blog post "You Might Not Need RAG" describes the author building a homegrown retrieval loop and only later learning it was "agentic retrieval," noting it works for hundreds-to-low-thousands of documents, not millions. Vectorize's practitioner post "How I finally got agentic RAG to work right" describes early struggles including invalid JSON returned by the model mid-loop.
- **Why it looks unbuilt/untested**: Both sources are single-author narrative write-ups of custom-built loops, not references to a maintained shared library; the "I didn't know this had a name" framing signals the control-loop plumbing isn't commoditized yet.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "agentic RAG framework"` returned dozens of repos (DualStack-Agent, Corax-RAG-Agent, artoo, Crux, RAGents, rag-engine, py-jrag, etc.) but nearly all are single-author, narrow-scope, or thesis/hobby projects with no evidence of broad adoption. WebSearch found one packaged PyPI library (`retrievalagent`, built on LangGraph, with retry/evaluate/rewrite loop and max-iteration cap) and one research method (Stop-RAG, arXiv, learns when to stop retrieving) — both real but neither is an established, widely-adopted standard. No consensus shared library for the control loop (retry/stopping/malformed-tool-call handling) was found; the gap is real but partially addressed by narrow/unevaluated implementations.

### P2: No systematic, corpus-aware way to choose a retrieval technique (eval-framework fragmentation)
- **What it is**: Teams want a way to pick the right retrieval strategy (dense vs. hybrid vs. reranking vs. graph) for their specific corpus, but the evaluation tooling landscape is fragmented across many competing, non-interoperable frameworks.
- **Evidence**: WebSearch surfaced at least five distinct, actively-promoted eval frameworks in the last few months — RAGAS, DeepEval, TruLens, SCARF (arXiv 2504.07803, with code), and RAG Playground (arXiv 2412.12322) — each with its own metric set and no consensus. A 2025 arXiv survey (2504.14891) explicitly tabulates how differently each framework defines "relevance," "correctness," and "faithfulness." An OpenAI community forum thread ("RAG is not really a solution") frames RAG as brittle specifically because there's no systematic way to pick a technique.
- **Why it looks unbuilt/untested**: Multiple parallel academic frameworks with no winner, plus a practitioner forum explicitly complaining about the lack of a systematic selection method, indicates the "pick the right RAG config for my data" problem is still open tooling-wise even though evaluation *metrics* individually exist.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos "RAG evaluation framework"` confirms fragmentation — ~10+ actively-created repos (RAGnarok-AI, evalkit, BenchRAG, EdgeRAG, DeepEval-based projects, etc.), each with its own metric set, none dominant. But the specific gap is *automatic corpus-aware selection* of a retrieval technique, not eval metrics themselves. WebSearch found only a research benchmark (RAGRouter-Bench, Jan 2026, standardizes 5 RAG paradigms across 7,727 queries) whose own April-2026 follow-up paper explicitly states "no classifier has been trained on this benchmark" as of that writing. No product, library, or maintained tool that actually performs corpus-aware retrieval-strategy selection was found — only discussion and an unsolved benchmark.

### P3: Chunking strategy causes silent, hard-to-debug retrieval failures
- **What it is**: Chunk boundaries (fixed-size vs. semantic vs. sliding-window) silently drop or fragment relevant context, and teams only discover this after the fact through ad hoc debugging rather than a built-in diagnostic.
- **Evidence**: An r/ArtificialIntelligence-sourced post (surfaced via WebSearch) walks through a developer's debugging of "failure modes that kept breaking my RAG system: chunking, stale index, hybrid search." A Hugging Face Discuss thread titled "Why does RAG still feel clunky in 2025?" asks whether anyone has found a setup that "actually feels smooth and scalable." Multiple independent vendor/practitioner posts (Redis, AWS Builder, Stack Overflow blog) each separately re-derive chunking-strategy fixes, suggesting no shared diagnostic tool exists.
- **Why it looks unbuilt/untested**: The repeated pattern of individual practitioners re-discovering and re-writing chunking post-mortems (rather than citing one standard profiling tool) indicates no commoditized "why did my retrieval miss this chunk" debugger exists yet.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found two actively maintained, widely-adopted products that squarely cover this gap: **Arize Phoenix** (open-source LLM/RAG observability platform with trace visualization and retrieval-quality evaluators specifically for diagnosing embedding/search/chunk-attribution failures) and **Langfuse** (MIT-licensed, self-hostable, with tracing, evals, and chunk-attribution write-ups citing it for exactly this failure mode). Both are well-resourced, maintained projects, not demos or one-offs. A narrower beta tool (RAG-TUI, v0.0.1, Show HN) also exists for visualizing chunk splits. The original "no shared diagnostic tool" framing undersells existing observability tooling that already instruments this.

### P4: "Confidently wrong" RAG outputs — no production-grade faithfulness/confidence signal surfaced to users
- **What it is**: RAG systems in production generate fluent, well-cited-looking answers that are subtly unsupported by the retrieved context, and teams have no standard way to flag low-confidence or unfaithful generations at serve time (as opposed to offline eval).
- **Evidence**: A post surfaced via WebSearch under r/ArtificialIntelligence states plainly: "Most RAG apps in production are confidently wrong and nobody talks about this enough." Industry-survey figures cited secondarily in 2026 blog posts put production RAG failure rates at 40–60%, concentrated in retrieval (unverified — cited only as secondary-source claims, flagged here as low-confidence evidence per the rules).
- **Why it looks unbuilt/untested**: The complaint is specifically that nobody is talking about it (i.e., perceived as an unaddressed, unglamorous problem) distinct from P2's offline eval-framework fragmentation — this pattern is about a missing *runtime* faithfulness gate, not an offline benchmark.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found multiple shipped, maintained products from well-resourced teams squarely covering runtime faithfulness gating: **Fiddler's Fast Faithfulness Guardrail** (real-time blocking on a faithfulness score), **Amazon Bedrock Guardrails** contextual grounding check (returns grounding/relevance scores, blocks ungrounded output), and **Cleanlab's Trustworthy Language Model** guardrail (blocks low-confidence outputs, triggers fallback). An open-source option (RagWarden, PyPI) also exists as a policy layer over these signals. The community complaint that "nobody talks about this" is about awareness/calibration (vendor thresholds are uncalibrated, per a 2025 arXiv critique), not about the capability being unbuilt — the runtime gate itself is already commoditized by at least three independent, maintained vendor implementations.

### P5: GraphRAG is being tried and abandoned in production due to entity-resolution and cost blowup
- **What it is**: Teams adopt graph-based RAG (entities/relations extracted into a knowledge graph for multi-hop retrieval) expecting better reasoning, then hit token-cost blowups, graph-maintenance debt, and entity-resolution failures that make it impractical at their scale.
- **Evidence**: An r/Rag thread ("My experience with GraphRAG," dated Aug 2025, surfaced via a Reddit mirror in WebSearch) describes a developer concluding GraphRAG is "not mature enough" for production, citing thin documentation, poor scaling, and graph connections that become unmanageable as the document set grows. Independent blog analysis (tianpan.co GraphRAG production series, cited via WebSearch) reports naive GraphRAG token consumption can run orders of magnitude higher than standard RAG for equivalent retrieval, and that production deployments "fail quietly" after successful pilots. A LlamaIndex community thread is summarized as members viewing GraphRAG as "not yet useful or production-ready."
- **Why it looks unbuilt/untested**: One named practitioner thread plus corroborating independent blog analysis describing the same three failure points (entity resolution, token cost, graph upkeep) and no counter-evidence of a mature, widely-adopted production GraphRAG stack.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "GraphRAG"` confirms several maintained implementations exist — microsoft/graphrag, HKUDS/LightRAG, FalkorDB (ships a "GraphRAG SDK 1.0" explicitly targeting production pipelines), neo4j-labs/llm-graph-builder — so the *technology* is not unimplemented. But WebSearch corroborates the specific failure modes in the digest: Atlan's 2026 guide rates GraphRAG production maturity "early-to-mid... limited enterprise tooling"; a practitioner post cites Gradient Flow's assessment that production deployments with real business value are rare and "most implementations remain experimental"; cost-blowup claims (one source: ~6,000x token cost vs. standard RAG) recur across independent blogs. No implementation specifically solving entity-resolution-at-scale or cost-control for production GraphRAG was found — existing frameworks are the thing people report failing with, not a fix for it.

### P6: Retrieval-pipeline prompt injection / knowledge-base poisoning defenses are early and fragmented
- **What it is**: Adversarial documents inserted into a RAG knowledge base can hijack the pipeline into following attacker-specified instructions; defenses that scan retrieved chunks before they reach the LLM are only just emerging and disagree on approach.
- **Evidence**: An arXiv paper, "CleanBase: Detecting Malicious Documents in RAG Knowledge Databases" (2026), proposes a detector for this specific threat. WebSearch also surfaced early-stage commercial/OSS point-tools (a RAG-defense feature in one vendor's docs, a regex-based "RAG injection guard" in another) plus a knowledge-base-poisoning eval in a third vendor's benchmark suite. Practitioner commentary (surfaced via a tianpan.co blog post) argues detection is the weaker control compared to permissioning, suggesting no consensus solution yet.
- **Why it looks unbuilt/untested**: Only one dedicated research paper plus a handful of small, regex-level vendor point-tools with disagreement among practitioners about whether detection (vs. permissions) is even the right approach — no maintained, broadly-adopted open-source defense surfaced.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos "RAG prompt injection detection"` returned only small, unmaintained-looking research prototypes (nadeem015/rag-prompt-injection-detection: "research prototype," rule/TF-IDF/hybrid detectors in a Streamlit app; two near-empty repos with no description; a niche JS SDK for Japanese-language injection). WebSearch found further research-only prototypes (RAGDefender, FilterRAG/ML-FilterRAG, an ECCWS proof-of-concept, provenance-based RAGShield) — none confirmed as released, actively-maintained tools; RAGDefender's own paper says the authors merely "plan to open-source it." No credible maintained implementation found after genuine multi-channel search — only discussion, research prototypes, and disagreement over approach (detection vs. permissioning).

### P7: Low-latency retrieval at scale without an accuracy tradeoff (efficient-retrieval research hitting mainstream attention)
- **What it is**: Research into making the retrieval step itself faster without sacrificing recall/accuracy — distinct from generation-side optimizations — is drawing high engagement but hasn't yet shown up as adopted open infrastructure.
- **Evidence**: "Faster Retrieval for Better, More Efficient RAG" (Apple Machine Learning Research, via Hacker News, 2026-11-11) scored 210 points and 38 comments — the single highest-engagement item the last30days engine surfaced for this topic.
- **Why it looks unbuilt/untested**: High community engagement with a fresh research write-up but no evidence surfaced of a corresponding widely-used open-source implementation yet; worth checking whether this is genuinely novel or restates known ANN-index tricks.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirmed Apple's paper ("Amortizing Maximum Inner Product Search with Learned Support Functions," ICML 2026) has no released code library in the search results. Narrow/early-stage implementations exist in the same space — zvec (released Aug 2026, in-process HNSW/DiskANN), Wax (independent Apple-Silicon vector lib, self-reported benchmarks only), DS SERVE (Berkeley framework, DiskANN-based, code published) — but none is an established, widely-adopted production standard for low-latency RAG retrieval specifically; Apple's own MicroNN on-device engine has unconfirmed open-source status. Real but fragmented/early/unevaluated-at-scale implementations, not a shipped consensus solution.

### P8: Vertical-specific RAG tools for underserved professional domains are one-off hacks, not a reusable pattern
- **What it is**: Rather than a generalized, configurable "domain-specific RAG" toolkit, practitioners in specific professions (e.g., legal) are each building bespoke, narrow point-tools from scratch for their vertical's document types and citation conventions.
- **Evidence**: "Show HN: CaseCite – Free RAG caselaw research and document analysis for lawyers" (Hacker News, 2026-10-25, 14 points, 2 comments; GitHub repo thomasunise/casecite) — a single-author, low-engagement, narrow-scope tool built specifically for legal caselaw RAG.
- **Why it looks unbuilt/untested**: Low engagement and single-maintainer scope suggest this is a one-off rather than a maintained or generalized framework; no evidence surfaced of a reusable "domain-pack" approach to vertical RAG (e.g., swappable citation/chunking rules per profession).
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "legal RAG"` confirms the one-off pattern — at least 9 distinct single-vertical, mostly single-author legal-RAG repos surfaced (casecite, tw-legal-rag, GraphAugmented-Legal-RAG, legal_rag, Clustered-Dynamic-RAG, eu-ai-act-legal-rag-prototype, cbr-for-legal-rag, iattorney-french-legal-rag, id-legal-rag), none generalized across verticals. WebSearch found one candidate reusable "domain-pack" framework — Fennec's `domain_rag` module, which wraps any RAG backend with swappable presets for medical/legal/technical/financial/academic domains — plus research-only frameworks (UltraRAG, RAGSmith) that study per-domain configuration but aren't packaged products. Fennec appears to be a small/community project with unconfirmed adoption, so the gap is partially but not robustly addressed.
