## Candidate patterns

### P1: Turn-level incident replay for voice agents (audio + trace + reasoning linked, not generic APM)
- **What it is**: A debugging surface purpose-built for voice agents that links call audio, STT output, LLM reasoning/tool calls, and TTS output into one replayable trace per call, instead of forcing teams to reconstruct an incident from separate logs.
- **Evidence**: Multiple voice-infra vendor posts converge on the same complaint independently — a Coval post frames a single unreplayable production incident as costing more than a year of eval tooling; Cekura pitches "a single trace that links call audio, STT output, LLM reasoning, tool calls, and TTS quality" as the fix; a Voicerun roundup of nine voice-observability platforms says comparing trace/replay features from docs alone is hard, and that Twilio's own Voice Insights sits at the infra layer, not the agent/turn-decision layer (WebSearch, `voice agent production debugging observability cost...`).
- **Why it looks unbuilt/untested**: Every source making this case is a vendor selling the fix, which itself signals no dominant/open answer exists yet; a 2026 agent-observability guide separately notes the generic-APM gap is specifically "the missing context is the audio itself" — teams can't tell why an agent responded wrong without hearing how the user actually phrased it.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained vendor products already pitch exactly this (audio+trace+reasoning linked per call): Hamming, Cekura ("trace as a tree" with STT/LLM/tool/TTS spans), Future AGI (session replay against captured audio+state), and a Voicerun/Cekura roundup of 9+ competing voice-observability platforms. Open-source confirms it's not just vendor talk: `finchvox/finchvox` ("Open-source observability and session replay for Pipecat voice agents — replay conversation audio alongside OpenTelemetry traces, logs, per-stage latency, and interruption metrics," created 2026-09) and `dograh-hq/dograh` (self-hostable, logs STT/LLM-decision/tool/TTS/interruption per turn) both ship this today. (WebSearch `voice agent call trace replay audio STT LLM TTS debugging platform 2026`; GitHub search for dograh/pipecat observability repos.)

### P2: Maintained, platform-agnostic open-source library for attended SIP warm transfer
- **What it is**: A reusable library (not a hosted platform) that implements the full attended-handoff flow for AI-to-human call transfer — a consultation leg, briefing the human, SIP REFER-with-Replaces, and NOTIFY-based completion tracking — usable across any voice-agent stack rather than locked into one vendor.
- **Evidence**: A WebSearch for exactly this (`voice agent "warm handoff" OR "human handoff" SIP REFER open source library missing`) surfaced only a LiveKit open-source phone-assistant example explicitly marked outdated and limited to cold transfer, plus Dograh (a platform, not a library) handling the flow internally; vendor docs (Synthflow, Dograh blog) describe the attended pattern piecemeal but no shared implementation.
- **Why it looks unbuilt/untested**: The search explicitly could not find "a dedicated open-source library for warm handoff over SIP REFER" independent of a specific platform — every attended-transfer implementation found is bundled inside one vendor's product, meaning every team re-solves consultation-leg + REFER-with-Replaces + NOTIFY tracking from scratch.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search for a dedicated, maintained, platform-agnostic warm-handoff library found none — only generic SIP building blocks: SIP.js's transfer guide, PJSIP's XFER module, Asterisk's `res_pjsip_refer.c`, sipsorcery's attended-transfer example (signaling only, no media), and a Go REFER/NOTIFY package (LingByte), plus LiveKit's SIP transfer API (an open GitHub issue #91 asking about REFER support) and Dograh's platform-bundled implementation. These are real, usable primitives (so not a pure OPEN), but every attended-handoff flow found is either generic-protocol-level or locked inside one vendor's product — nobody has packaged the consultation-leg+REFER-with-Replaces+NOTIFY flow as a reusable voice-agent library. (WebSearch `open source SIP warm transfer library attended handoff REFER voice agent github`.)

### P3: Carrier-agnostic SIP signaling abstraction for voice agents
- **What it is**: A layer that normalizes telephony signaling events (DTMF press, transfer, hold, hangup mid-sentence) across carriers for voice agents, so agent logic doesn't have to special-case each carrier's SIP profile.
- **Evidence**: Exotel's engineering blog states plainly that "a caller pressing 1, an agent transfer, a hold, a customer hanging up mid-sentence... these are signalling events, and they live in SIP, not in the audio stream," and that teams "discover [carrier] differences one production incident at a time"; a Caller.Digital post on an Indian enterprise deployment reports every fourth call drops on transfer to a human because every regional cloud-telephony provider has a slightly different SIP profile; a Start Telecom piece (unverified, vendor-sourced) claims 40-60% of AI-to-human transfers fail industry-wide for lack of proper SIP REFER/warm-handoff architecture (WebSearch, `"multimodal agent" OR "voice agent" telephony SIP integration pain...`).
- **Why it looks unbuilt/untested**: Exotel's own framing — "across a few thousand calls a day, quality problems become anecdotes rather than tickets" — is a direct admission that no systematic tooling exists yet to surface these failures reliably; the fix each vendor offers is a proprietary cloud connector, not a shared open abstraction.
- **Maturity**: PARTIAL
- **Verdict notes**: No shared open abstraction found; only proprietary vendor gateways that partially normalize carrier SIP differences — SignalWire's protocol-normalization pitch, a telephony-bridge vendor claiming testing against ~7 carriers for DTMF variants (RFC 2833 vs. SIP INFO), didlogic's transfer-reliability guide, and LiveKit's telephony docs (REFER-based transfer, DTMF, SRTP). Each is a closed cloud connector, not a shared open library teams can adopt across carriers, and the sources themselves (Exotel, Caller.Digital) describe the problem as still being discovered "one production incident at a time." (WebSearch `carrier-agnostic SIP signaling abstraction layer voice agent telephony normalize DTMF transfer`.)

### P4: Consent-linked liveness/watermark verification for live voice-agent calls
- **What it is**: A verification layer for live calls that goes beyond a bare deepfake-confidence score — pairing watermark detection, spectral-artifact detection, and a liveness challenge with an actual recorded consent record tied to the voice-print, so a call can be checked for "is this clone authorized" rather than just "is this synthetic."
- **Evidence**: Resemble AI's own material concedes "the absence of a watermark doesn't prove a voice is human, since most generators don't add one," and that detection "answers with a confidence score... it does not read intent or confirm consent"; Future AGI pitches a 2026 combined standard (watermark + spectral-artifact + liveness) but frames it as a vendor guide, not an adopted standard; the same search surfaced Lovo's Chapter 7 bankruptcy while a voice-actor lawsuit over unconsented cloning was still pending — evidence the consent gap is actively causing legal harm, not just a theoretical risk (WebSearch, `voice cloning consent watermark detection AI agent calls complaint 2026`).
- **Why it looks unbuilt/untested**: The search found no system that answers "has anyone built" a consent-verification layer for agent calls — only partial, vendor-specific detection pieces, with the EU AI Act's Article 50 disclosure deadline (cited as August 2026, unverified against the primary text) creating fresh regulatory pressure with no clear compliant off-the-shelf answer yet.
- **Maturity**: PARTIAL
- **Verdict notes**: One real open-source attempt exists — Voice Truthgate, an "open-core, MIT-licensed MCP server" for enrolling a voiceprint and checking a call clip — but its own maker reports a targeted clone was accepted 63% of the time at the operating threshold and recommends it only as one signal among several, not a standalone verdict; it also doesn't tie the check to a recorded consent record (just similarity/liveness). Commercial watermarking (Resemble) explicitly concedes a missing watermark proves nothing. No system combining watermark+spectral+liveness+linked consent record was found, but the Truthgate repo means this isn't a bare OPEN either. (WebSearch `voice clone consent verification liveness watermark system open source "voice agent" calls`.)

### P5: Context-triggered (not continuous) capture firmware for always-on multimodal wearables
- **What it is**: A capture mode for AI pendants/wearables that activates recording on a contextual or tap-based trigger instead of continuously streaming audio, aimed at resolving the same device's privacy backlash and battery drain with one fix instead of trading one for the other.
- **Evidence**: Coverage of the Friend pendant and Amazon's Bee device both report real-world battery life far below advertised figures specifically during active listening (Bee's advertised 7-day battery reportedly drops to 1.5-2 days with active listening); the same sources report bystander-recording-without-consent complaints and uplinked transcripts despite "on-device processing" claims; a newer entrant (Button, from ex-Apple engineers) is explicitly positioned as "tap-to-activate... directly address[ing] privacy concerns that have plagued other AI hardware launches" (WebSearch, `AI wearable pendant voice assistant complaints battery privacy 2026`).
- **Why it looks unbuilt/untested**: The market pattern itself is the evidence — CES 2026 saw pendants "return... after early setbacks," and the privacy-vs-battery tradeoff is still being solved device-by-device (Button's tap model vs. Friend/Bee's always-on model) rather than via a shared selective-capture approach any maker has settled on.
- **Maturity**: SATURATED
- **Verdict notes**: The pattern's own definition includes "tap-based" triggers, and multiple shipped products now use exactly that as the fix for the privacy-vs-battery tradeoff: Button (ex-Apple engineers, tap-to-activate, explicitly positioned against always-on pendants), Pebble's Index 01 smart ring ($75, open-source firmware+app, on-phone transcription, tap/press activation, shipped Dec 2025), and the Taya necklace (button-tap record, mic off by default). This directly closes the "tap-based" half of the gap with multiple maintained/shipped implementations; only the more exotic "automatic contextual trigger" (no manual tap) variant remains unaddressed, which is a narrower slice than the pattern as written. (WebSearch `tap to activate wearable pendant firmware open source context-triggered capture privacy battery 2026`.)

### P6: Unified cross-modal data labeling and provenance pipeline for multimodal agent training data
- **What it is**: A single labeling schema and provenance-tracking pipeline spanning text, image, audio, and video for teams building/fine-tuning multimodal agents, replacing the current practice of separate tools and schemas per modality that then have to be reconciled.
- **Evidence**: An Encord-adjacent source states multimodal data "is often annotated with separate tools and schemas for text, images, audio, and video, which leads to disconnects," proposing a unified schema as the fix; the same search found that "video curation can take 10-50x longer than text curation for equivalent dataset sizes" (single-vendor figure, unverified) and that "retrofitting provenance tracking onto an existing dataset is far harder than building it in from the start" (WebSearch, `multimodal agent dataset curation labeling voice vision pain point 2026`).
- **Why it looks unbuilt/untested**: Every fix cited is a single vendor's internal framework or product pitch (Encord, Turing, Wirestock) rather than a shared open pipeline; the sources agree the core failure mode — "a file can pass every single-modality check and still fail once the modalities are combined" — is unresolved by current per-modality tooling.
- **Maturity**: PARTIAL
- **Verdict notes**: No single open-source tool covers labeling+provenance across text/image/audio/video end to end — confirmed by search. Pieces exist: CVAT (open source, vision-only, now with SAM3/YOLO11 auto-annotation), Label Studio (open source, 27k+ stars, general but no cross-modal provenance), Voxel51/FiftyOne 3.0 (claims 4 provenance layers across images/video/3D/audio, but unclear which ship in the open-source FiftyOne tier vs. enterprise-only), and a NiFi+Pixeltable stack (handles lineage/movement, not labeling). The gap is real but not untouched — a serious unified build would differentiate from these narrow/enterprise-gated options rather than inventing from zero. (WebSearch `unified multimodal data labeling provenance pipeline text image audio video open source tool 2026`.)

### P7: Local tool-dispatch framework for on-device multimodal agents (vs. manual loop-closing)
- **What it is**: A reusable framework that handles tool-call dispatch and name resolution for on-device multimodal models (Gemini Nano-class), so developers don't have to manually close the agent loop and hand-pin exact tool names into the system prompt to stop the model inventing plausible-but-wrong tool names.
- **Evidence**: A 2026 developer field guide on building with Gemini Nano reports "on-device tool calling... required closing the agent loop manually, and... the model invented a plausible but wrong tool name until the exact names were pinned in the system instruction," and that Google's own guidance is a hybrid split (cloud orchestrates tools, on-device sub-agents stay text-only) rather than full on-device tool calling; the same guide flags hard platform limits on simultaneous requests and daily invocations to manage battery (WebSearch, `on-device multimodal agent edge deployment latency battery smartphone 2026`).
- **Why it looks unbuilt/untested**: The source frames this explicitly as *not* a solved, flip-a-checkbox capability ("on-device tool calling isn't a checkbox you flip") — the described workaround is a manual, per-app hack, not a packaged framework other developers can reuse.
- **Maturity**: PARTIAL
- **Verdict notes**: For the exact Gemini Nano case, no library was found — Google's own ML Kit function-calling and ADK-for-Android on-device backends are reported (third-party field accounts) to lack a tool-execution path, requiring the manual loop-closing the pattern describes. But the general problem (local tool-dispatch framework avoiding hand-pinned/invented tool names) is not fully unsolved elsewhere: `lemcoder/koog-edge` is a maintained Kotlin framework that ships tool-calling for other on-device models (Qwen3, LFM2 via Cactus Compute/Leap SDK), and `uny/koog-ondevice` wraps Gemini Nano itself through Koog (though its listing doesn't confirm tool-calling support). A Gemini-Nano-specific, loop-closing, name-resolution framework is still missing, but adjacent maintained frameworks solving the same shape of problem exist. (WebSearch `on-device tool calling framework Gemini Nano local LLM mobile dispatch library github`; GitHub search for koog repos.)
