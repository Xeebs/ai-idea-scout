## Candidate patterns

### P1: No standard way to test/debug MCP tool-selection correctness when every individual tool passes its own tests
- **What it is**: Agents choose the wrong MCP tool for a user's intent even when each tool independently passes functional tests — the failure is in routing/selection, not tool implementation — and there's no established evaluation methodology (predefined scenarios, automated tests, or end-to-end intent tests) for this failure class.
- **Evidence**: r/modelcontextprotocol, "MCP tools all passed testing but the agent keep choosing wrong one. How to test tool selection?" (2026-10-13, https://www.reddit.com/r/modelcontextprotocol/comments/1x4vgh2/): "all the rest of tools were callable and direct tests passed all good. But when agent was asked a brand sentiment it selected another tool instead of relevant capability... How i test for this kind of failure? Do you use predefined evaluation scenarios, automated tests or end to end testing with real prompts?"
- **Why it looks unbuilt/untested**: Posed as an open question to the community with no cited existing tool/framework offered as the answer — a direct "has anyone built this" signal.
- **Maturity**: PARTIAL
- **Verdict notes**: Found `accenture/mcp-bench` (516 stars, GitHub, but last pushed 2025-10-07 — >6 months stale) and PyPI's `mcp-tool-selection-bench` (small CI-oriented package benchmarking tool-selection accuracy via the GitHub Copilot SDK), plus a GitHub Engineering blog post describing an internal offline-eval pipeline for the GitHub MCP Server and Apify's `actors-mcp-server` evals folder (exact-match + LLM-judge). These prove the methodology exists in pockets, but none is a widely-adopted, maintained standard a practitioner would find by searching — consistent with the Reddit asker getting no answer. Academic benchmarks (BFCL-style, Switchcraft/arXiv 2605.07112) evaluate general function-calling accuracy, not this specific "all tools individually pass, routing still fails" debugging workflow.

### P2: Hybrid deterministic state-machine + LLM routing to make tool/action selection reliable instead of trusting the LLM to pick freely every turn
- **What it is**: Rather than letting the model freely choose tools/actions each turn, extend an existing deterministic conversation/slot/tool lifecycle and invoke the LLM only for the narrow semantic decisions deterministic routing genuinely can't make — explicitly rejecting a full rewrite to LLM-driven routing.
- **Evidence**: GitHub `NickMonrad/kernel-ai-assistant` issue #1682, "Design: deterministic conversation action state and reliable structured transitions" (89 comments across the thread, opened/updated 2026-10-29/30): "Recommendation: extend Jandal's existing conversation/slot/tool lifecycle, and use the already-pinned [...] native [...] response-format API for the small semantic decisions that deterministic routing cannot make. Do not fork [the LLM-driven path]."
- **Why it looks unbuilt/untested**: Live, unresolved design debate inside one project (explicit "required before closing" review follow-up, a draft spike PR marked "debug/test-only, no production transition implementation") — not a published, reusable pattern or library.
- **Maturity**: SATURATED
- **Verdict notes**: This is a well-established, shipped architectural pattern, not a gap. Google Dialogflow CX (actively maintained product) ships exactly this split — deterministic flows own transitions, a generative fallback handles only narrow unmatched-intent decisions. `InfinitiBit/graphbit` (GitHub, actively pushed 2026-11-11) is a maintained open-source framework built around the same node-can-be-deterministic-or-LLM design. Multiple other write-ups (ChainWeaver, llama-conductor, `tool4ai`, LangGraph-style graphs) describe the identical pattern as common practice. One team debating how to apply it internally doesn't make the pattern itself unbuilt.

### P3: MCP client authorization/trust UX that doesn't double as a phishing vector
- **What it is**: A way for users to trust their own MCP clients during OAuth-style authorization flows without the redirect-URI trust mechanism itself becoming an exploitable phishing/open-redirect surface.
- **Evidence**: Hacker News, "Letting users trust their own MCP clients, without opening a phishing hole" (2026-11-04, 35 pts / 6 comments, https://streamvessel.com/blog/mcp-trusted-redirect-uris).
- **Why it looks unbuilt/untested**: Single technical blog post proposing a fix to a named, unresolved security gap in the current MCP authorization flow — no evidence the spec or major clients have already adopted a fix.
- **Maturity**: PARTIAL
- **Verdict notes**: The MCP spec's 2026-07-28 revision hardened the general redirect-URI validation story (exact pre-registered-URI matching, localhost-redirect warnings via SEP-837, SSRF considerations for Client ID Metadata Documents — per modelcontextprotocol.io security-considerations docs and a Tigera writeup on the six new OAuth SEPs). But the blog post itself (confirmed via fetch) says the spec explicitly leaves "trust" undefined for self-hosted servers doing dynamic registration from anonymous clients, reports a related Claude Code issue closed as "not planned," and that the author's own test of 119 live MCP servers found 114 still accept arbitrary redirect URIs. The spec-level fix exists; the practical implementation gap the post targets does not appear closed.

### P4: No standard trust/signing/provenance layer for AI skills and MCP servers before a user installs them
- **What it is**: An "app-store"-style trust layer that verifies and signs AI skills and MCP servers before they're added to a client, addressing the fact that anyone can currently publish an MCP server or skill with no vetting of what it actually does.
- **Evidence**: Hacker News, "USB: A trust layer for AI skills and MCP servers" (2026-11-09, 11 pts / 3 comments, https://github.com/PeepSick/usbplus).
- **Why it looks unbuilt/untested**: Single-maker, fresh (just-launched) project with minimal engagement — proposing a trust layer because, by its own framing, none exists yet.
- **Maturity**: PARTIAL
- **Verdict notes**: Several narrow, non-unified efforts exist: `dotsetlabs/countersign` (Sigstore-based signature/provenance checks before MCP install), ToolHive (build-provenance checks + registry provenance metadata for MCP servers, skip/warn/block modes), NVIDIA's documented "agent skill trust pipeline" (review, scan, sign with detached `.oms.sig` via OpenSSF Model Signing), the draft `PromptSign/spec` for keyless skill-signing + trust policy, and an independent STSS Merkle-tree/Ed25519 attestation layer. A Claude Code feature request for an "official verified marketplace for Skills, MCP Servers, and Custom Agents" was filed and closed without evidence Anthropic built one. No single standard covers both skills and MCP servers together, so the specific "app-store" gap USB targets is real, but it is not a greenfield space — a serious build would need to differentiate from at least five existing narrow point-solutions.

### P5: Auto-generating an MCP server from an arbitrary existing website instead of hand-building one per service
- **What it is**: A tool that turns any website into an MCP-compatible interface for agents on demand, instead of requiring every service/site to ship and maintain its own bespoke MCP server.
- **Evidence**: Hacker News, "Launch HN: Pomerado (YC F26) – Turn any website into an MCP for agents" (2026-11-11, 56 pts / 44 comments, https://news.ycombinator.com/item?id=50455811).
- **Why it looks unbuilt/untested**: Fresh YC launch (Fall 2026 batch) with active discussion (44 comments) but no established, dominant incumbent cited in the thread — the long tail of sites without MCP servers is framed as the open problem.
- **Maturity**: SATURATED
- **Verdict notes**: Crowded space with many live products and repos beyond Pomerado itself: Yavy and toMCP (Product Hunt-launched crawl-and-serve converters), `sitemcp` (open-source, "Turn Any Website Into a Living MCP Server"), Web2MCP (OpenAPI/JSON-LD auto-detection), OmniMCP, WebBridge (browser-traffic recording), plus GitHub repos `onbuyuka/website2mcp`, `lbsa71/website-to-mcp`, `nshekhawat/url2mcp`, and Anchor Browser's documented "wrap any site as MCP" tutorial. Pomerado's YC framing as a novel category is not supported by the landscape.

### P8: Unclear boundary between "skills" (prompt/procedure packaging) and MCP servers (tool packaging) for distributing agent capabilities
- **What it is**: As both "skills" (packaged, prompt-driven procedures, e.g. Claude Code's Skill format) and MCP servers (packaged callable tools) proliferate as ways to extend an agent, there's open debate about which capabilities should be shipped as which, and how/whether the two should interface with each other.
- **Evidence**: Hacker News, "MCP servers interfaced through skills – thoughts?" (2026-10-17, 3 pts / 2 comments, https://mochow13.github.io/keen-code/docs/mcp-skills.html).
- **Why it looks unbuilt/untested**: Framed explicitly as an open question ("thoughts?") to the community with minimal engagement and no settled consensus cited.
- **Maturity**: PARTIAL
- **Verdict notes**: Anthropic itself has published guidance on this exact split ("Extending Claude's capabilities with skills and MCP servers," claude.com/blog), and there are dozens of third-party explainer posts (dev.to, Substack, morphllm.com) converging on the same "skills = procedural knowledge, MCP = live external connectivity, they can compose" framing — the *decision* question is well-covered. But the *technical interfacing* question the HN post actually raises (wrapping/interfacing MCP servers through skills programmatically) has no dedicated tooling or settled pattern found — only the single low-engagement HN thread itself. Decision guidance is saturated; the interfacing mechanism remains an open, narrow build.
