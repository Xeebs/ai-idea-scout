## Candidate patterns

### P1: Backchannel-vs-real-interruption classification architecture
- **What it is**: Voice agent pipelines need to distinguish a filler sound ("mm-hmm", a cough) from a genuine attempt by the caller to take the floor, then decide whether to stop audio playback immediately or keep talking. Several vendors describe a "detect → classify → cancel → capture → resume" pipeline, with the classifier running in parallel to a provisional new-turn start.
- **Evidence**: Quiq's engineering blog frames the problem as architectural, not a single setting, describing a parallel barge-in classifier (via WebSearch: quiq.com/blog/why-the-interruption-problem-is-architecture). Hamming's "Interruption Handling: Barge-In, Backchannels, and Turn Detection" runbook catalogs production failure modes like false barge-ins from noise/echo (via WebSearch: hamming.ai/blog/voice-agent-interruption-handling-runbook). A live bug report on the Retell AI community forum (community.retellai.com/t/agent-speaks-the-remainder-of-its-sentence-as-a-separate-turn-after-barge-in/3580) shows a production agent still mishandling this in practice, with the poster noting that prompting alone did not fix it.
- **Why it looks unbuilt/untested**: Every vendor (Deepgram, Quiq, CallSphere, Smallest AI, Retell) has built its own bespoke, undocumented-standard version of this classifier, and live community bug reports from November 2026 show it still fails in shipped products. No shared open benchmark or reusable library for backchannel classification turned up in search.
- **Maturity**: SATURATED
- **Verdict notes**: LiveKit Agents (github.com/livekit/agents, 15,266 stars, pushed within the last day) ships a maintained, built-in "adaptive interruption" mode that classifies backchannels vs. real barge-ins as a first-class feature, and Deepgram markets a Flux STT model that fuses turn detection into transcription for the same purpose (deepgram.com/blog/backchannels-vs-interruptions-voice-agents) — two well-resourced, actively maintained implementations already closing this gap, beyond the smaller OSS attempts found (attenlabs/saa-sdk, 168 stars; bargekit; bnovikov/bargein-classifier).

### P3: Bolt-on cross-call memory via webhooks instead of native platform memory
- **What it is**: Mainstream managed voice-agent platforms (Vapi named specifically) have no built-in memory that persists across separate phone calls from the same caller; builders patch this in themselves using webhooks, keyed on phone number/caller ID, with Redis for the active session and Postgres/Mongo for cold storage after the call ends.
- **Evidence**: A vendor post (hindsight.vectorize.io/blog/2026/06/03/vapi-persistent-memory, surfaced via WebSearch) states "Vapi has no built-in cross-call memory" and that its assistant-request webhook "only fires for inbound calls," so outbound calls need memory overrides built at call creation. A DEV Community tutorial (dev.to/voipbin/build-ai-voice-bots-that-remember-persistent-context-across-multiple-calls-412h) walks through the Redis-then-Postgres DIY pattern explicitly because no native equivalent exists.
- **Why it looks unbuilt/untested**: Third-party "memory layer" vendors (Mem0, MemU) are emerging specifically to sell what the base platforms don't ship, and the DIY tutorials exist because the gap is real enough that individual builders write their own glue code rather than flip a setting.
- **Maturity**: PARTIAL
- **Verdict notes**: Mem0 (github.com/mem0ai/mem0, 69,136 stars, "drop-in memory infrastructure... built for production") is a mature, widely-adopted general agent-memory layer that could back this, but it is not telephony/voice-specific and still requires the caller-ID-keyed webhook glue the digest describes; MemU and Vectorize/Hindsight are vendor posts targeting the exact niche but their code maturity/license couldn't be confirmed via WebSearch. No out-of-the-box native solution exists on any major voice platform, so the DIY gap remains real even though a strong generic building block (Mem0) exists.

### P5: Manual, ad hoc regression testing for voice-agent prompt changes
- **What it is**: Builders shipping production voice agents report having no automated way to catch regressions when they tweak a prompt — the workflow is literally placing a phone call to the bot by hand after every change and listening for breakage across many corner cases.
- **Evidence**: An Indie Hackers contractor post (indiehackers.com/post/ai-voice-agent-building-experience-as-a-contractor-9ee96ec7ff, via WebSearch) states plainly: "we need to manual call the AI phone agent each time when we change some prompt" because "there are many corner cases."
- **Why it looks unbuilt/untested**: This is a direct first-person "we hacked together/we have to do this by hand" complaint from someone actively building and billing for voice-agent work in 2026, not a hypothetical. It names the exact unmet need: an automated regression/eval harness for voice-agent prompt changes that plugs into a normal dev loop.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained commercial products already sell exactly this — Hamming.ai, Coval.dev ("three-layer testing framework: regression, adversarial, production-derived"), and Cekura.ai ("Voice AI Orchestration Benchmarks... regression testing after prompt changes," explicitly covering Retell/Vapi/Pipecat/LiveKit) — plus open-source options (voicetestdev/voicetest on GitHub, "import from Retell/VAPI/Bland/LiveKit, run autonomous simulations, evaluate with LLM judges"; LangWatch's `@langwatch/scenario` package with several demo repos; Pipecat's first-party Evals tooling). The contractor's manual-call complaint reflects non-adoption of existing tooling, not an absence of it.

### P6: Fragmented, non-adopted voice/multimodal agent evaluation benchmarks
- **What it is**: Multiple academic benchmarks for scoring voice/multimodal agents (FOCAL, MM-tau-p2, MultiVox, VoiceAssistant-Eval) have shipped in roughly the same window, each testing a different slice (error propagation across STT→LLM→TTS, text-vs-voice parity, omni-modal role-play), but none has become a standard that working teams adopt.
- **Evidence**: Via WebSearch: "FOCAL: A Novel Benchmarking Technique for Multi-modal Agents" (themoonlight.io review, referencing arxiv.org/abs/2601.07367); "VoiceAssistant-Eval: Benchmarking AI Assistants across Listening, Speaking, and Viewing" (aitopics.org/doc/arxivorg:7C24DBF3); Dialpad's engineering blog (dialpad.com/blog/text-benchmarks-arent-enough-for-voice-agents) reporting "there was no universal voice penalty" and that the text-vs-voice performance gap "varied by model."
- **Why it looks unbuilt/untested**: The same WebSearch explicitly found no single agreed-upon voice benchmark — multiple competing, still-in-development research frameworks rather than one that practitioners have converged on. This sits one layer above P5 (practitioners doing manual testing precisely because no usable standard eval exists yet to automate against).
- **Maturity**: PARTIAL
- **Verdict notes**: Confirms the digest's own read: FOCAL, VoiceAssistant-Eval, and MultiVox are real, citable academic benchmarks (arxiv.org/abs/2601.07367 and others), satisfying the letter of "implementations exist," but Dialpad's own engineering analysis (dialpad.com/blog/text-benchmarks-arent-enough-for-voice-agents) confirms "no universal voice penalty" and no convergence — the unmet need is specifically a *standard* practitioners adopt, and proliferation of competing, unevaluated-in-practice benchmarks is the opposite of that, so the gap stays open despite academic activity.

### P7: Echo-aware transcript filtering to disambiguate real interruptions from agent self-talk
- **What it is**: A speech-to-text technique where the model takes the agent's own outgoing text as an additional input signal and filters the agent's own voice out of the live transcript, specifically to make it easier to tell when the caller — rather than acoustic echo of the agent's own speech — is the one talking.
- **Evidence**: last30days engine's second run surfaced "Soniox STT v6" (released 2026-11-03 per the voiceaispace.com Nov 8 weekly roundup picked up via WebSearch) described as taking "the agent's own text as input and filters the agent's voice out of transcripts, which helps when users interrupt."
- **Why it looks unbuilt/untested**: This is a single vendor's just-shipped (Nov 3) feature announcement, not an established pattern with multiple implementations — it directly targets the same unresolved interruption-detection problem as P1 but from the transcript layer rather than the audio layer, and no second implementation of this specific technique surfaced in any search.
- **Maturity**: PARTIAL
- **Verdict notes**: Soniox STT v6's text-conditioned self-voice filtering is a real, shipped single-vendor feature (Nov 3 2026), but WebSearch on Deepgram's and AssemblyAI's own docs/blogs shows both rely on a different approach (device-level acoustic echo cancellation plus keyterm boosting / pausing mic capture during playback), not text-conditioned transcript filtering — no second implementation of this specific technique, and no open-source equivalent, turned up anywhere.

- **Maturity**: PARTIAL

So implementations exist for the adjacent contact-center case but are narrow (wrong channel) and contested (unevaluated/weak on the actual target channel) — the specific emergency-dispatch gap the HN thread complains about remains unaddressed by anything found.
