## Candidate patterns

### P1: No execution boundary beyond "container as sandbox" for agent tool calls
- **What it is**: When an MCP tool call results in code execution (a code-interpreter tool, a generated-script tool, etc.), the near-universal mitigation today is a Docker-style container, but practitioners increasingly argue containers share the host kernel and aren't a real security boundary — yet lighter-weight microVM alternatives (Firecracker, gVisor, E2B, Daytona) are cited as recommendations, not something most agent stacks have actually adopted.
- **Evidence**: WebSearch supplement surfaced a documented sandbox-escape CVE in Claude Code's own Bubblewrap sandbox (CVE-2026-25725, CVSS 7.7, per [Cymulate](https://cymulate.com/blog/the-race-to-ship-ai-tools-left-security-behind/), patched in v2.1.2); OWASP's ASI05 entry explicitly states "software-only sandboxing is insufficient" (cited via [softwareseni.com](https://www.softwareseni.com/understanding-ai-agent-sandboxing-why-production-deployment-remains-unsolved-in-2026/)); [Tian Pan's write-up](https://tianpan.co/blog/2026-04-19-sandboxing-agents-least-privilege-tool-calling) argues API-key scoping "does not limit what generated code can do on the host"; a cited (secondary, unverified) HiddenLayer 2026 figure claims 90% of organizations grant agents excessive permissions.
- **Why it looks unbuilt/untested**: Every source frames microVM/least-privilege execution as the recommended fix, not as something already standard in agent frameworks — the write-ups exist because teams are still shipping container-only isolation in production and getting bitten by it (the Claude Code CVE itself is the proof point).
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch confirmed multiple maintained, shipped microVM sandbox products already exist and are in production use: E2B (open-source, Firecracker-based, used by Manus and Perplexity), AWS Bedrock AgentCore Code Interpreter (dedicated microVM isolation), Modal (gVisor-based standard sandbox runtime), Daytona (Docker+gVisor), and Northflank (Firecracker/Kata/gVisor options). The digest frames this as "not widely adopted," but the rubric asks whether implementations exist, and well-resourced teams (AWS, Modal, E2B) have already shipped and maintain exactly this execution-boundary alternative to plain containers.

### P2: No mature framework for testing agent tool-call behavior, only mock-server libraries
- **What it is**: Several small libraries exist to mock an individual MCP server's responses for unit tests (stub the transport, return canned tool results), but nothing combines that with scripted/model-in-the-loop agent behavior and assertions on the actual sequence of tool calls an agent makes — the thing teams actually need to catch "agent picked the wrong tool" or "agent called tools out of order" bugs before shipping.
- **Evidence**: WebSearch supplement enumerated the existing point-solutions — `zeph-mcp`'s `MockMcpServer`, the `mcpkit-testing` Rust crate, the npm `mcp-server-mock` package, `vaayne/mcphub`'s internal testing package — and a [DEV Community post](https://dev.to/aidevhub/building-an-mcp-tool-call-test-rig-with-the-python-sdk-in-2026-4iln) on building a tool-call "test rig," alongside a separate [DEV Community piece](https://dev.to/rupa_tiwari_dd308948d710f/why-testing-mcp-servers-with-real-ai-models-matters-2026-55e9) arguing mocks alone "miss how real models behave" because tool-calling habits differ per model family.
- **Why it looks unbuilt/untested**: The WebSearch synthesis itself concluded there is "no evidence of a single mature framework that combines mocked tool responses, scripted agent or model behavior, and assertions on tool-call sequences" — every hit was a small library, a vendor blog, or a tutorial, not a converged tool.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search surfaced real but fragmented point solutions: `AgentProof` (pytest plugin with `assert_tool_order`/`assert_tool_called`/`assert_max_steps`), `assay-core` (Rust crate with exact/subsequence/must-not-call trace assertions), `agentguard` (trace replay + assertion builder), plus `itsPremkumar/mcptest` and `guruambati/agent-tool-call-testing-framework` on GitHub. None combine mocked transport + model-in-the-loop behavior + sequence assertions in one maintained, adopted framework — confirms the digest's own "no converged tool" conclusion, so the gap is real but not greenfield.

### P3: No standard tool to detect silently-breaking MCP tool/schema changes
- **What it is**: MCP server maintainers can change a tool in ways that break calling agents without the JSON schema itself changing — altered side effects, pagination semantics, error handling, a narrowed enum, changed units, or even just a reworded natural-language description that shifts which tool an agent picks. Multiple blog-length proposals (CI schema diffing, compatibility matrices, pinning versions instead of `latest`) exist but no shared tool implements them.
- **Evidence**: WebSearch supplement across [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/05/28/mcp-server-versioning-backwards-compatibility-managing-breaking-changes/), [Gravitee's corpus posts](https://gravitee.io/corpus/gen-2286/833a/mcp-server-versioning-and-compatibility-management.html) on versioning/deprecation governance, and a [Hashnode post](https://hashnode.com/blog/mcp-stateless-migration) specifically on the 2026-07-28 MCP spec revision ("MCP is going stateless, and the upgrade breaks in both directions") disagreeing with other sources on whether that revision is even final — itself evidence the ecosystem hasn't converged.
- **Why it looks unbuilt/untested**: Every source describing a fix frames it as "teams should do X" (pin versions, diff schemas in CI, publish a compatibility matrix) rather than naming an adopted tool that does it; one cited "72% of schema changes cause silent agent failures" statistic traced to an unsourced conference slide deck, underscoring how little rigor exists in this space currently.
- **Maturity**: PARTIAL
- **Verdict notes**: Web search found several young CI schema-diff tools already attempting this exact gap — `mcp-contracts`/`mcpdiff` (snapshot/diff/validate with breaking/warning/safe buckets and a GitHub Action; confirmed via `gh repo view`: only 8 stars, last push 2026-11-10), `mcp-compat` (PyPI, BREAKING/WARN/SAFE classifier with `--ci` flag), `Bellwether` (dotsetlabs, schema-drift CI check), and `Naim-arg/mcp-compatibility-checker` (GitHub, loadable/not-loadable checker against MCP Inspector). All are narrow, brand-new (weeks old), single-digit-star projects with no evidence of adoption — real attempts exist but nothing converged or trusted enough to call the gap closed.

### P4: No intent/provenance gate between agent reasoning and code-execution tool sinks
- **What it is**: Prompt injection doesn't need to breach a sandbox perimeter if it can redirect the agent's own reasoning into calling a legitimate, already-permitted tool (e.g., an `eval()`-backed tool) with attacker-controlled input — a "goal hijack" rather than an escape. The fix space discussed is upstream of sandboxing: gating *which* tool calls are allowed to reach execution sinks based on where the triggering content came from.
- **Evidence**: WebSearch supplement cites CVE-2026-26030 (prompt injection reaching an `eval()` call in semantic-kernel, per [Prediction Guard](https://predictionguard.com/blog/ai-agent-code-execution-security-explained)) and the OWASP Agentic Top 10 (2026) framing this class under goal hijack / unexpected code execution.
- **Why it looks unbuilt/untested**: Sources list generic mitigations (deny outbound network by default, cap resources/timeouts, require approval for high-risk actions) as best practices, not as a shipped provenance-tracking layer that follows untrusted content through an agent's reasoning into which tools it's allowed to call — the gap is structurally distinct from P1's sandbox-escape problem (P1 = contain the blast radius after a call happens; P4 = decide whether the call should happen at all).
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for shipped provenance-gating repos came up empty, but WebSearch found several 2026 academic prototypes with real evaluation results squarely targeting this gap: Agent-Sentry (arXiv:2603.22868, provenance-graph gating, reports 94.3% injection block / 95.1% benign-action pass rate on AgentDojo/AgentDyn), Agentic Reference Monitor (arXiv:2604.04035, runtime tool-call/result tagging), and Risk-Aware Causal Gating (arXiv:2606.18550, claims zero injection success on a controlled benchmark). These are research-stage, unreplicated, single-author/unreviewed preprints, not adopted frameworks — real work exists but no production implementation, keeping this short of SATURATED.

### P5: No general approval-gate middleware for high-risk agent tool calls
- **What it is**: A Show HN-style post exposes wallet/AML screening as something an AI agent can call over MCP before, e.g., approving a crypto transaction — implying the actual unmet need is a reusable "approval gate" pattern that intercepts any high-risk tool call (financial transfer, delete, external send) and routes it through a risk-scoring or human-approval step before execution, rather than every tool author hand-building compliance checks into their own server.
- **Evidence**: Hacker News via engine, "Wallet screening your AI agent can call over MCP" ([prax-labs.com](https://prax-labs.com/wallet-screening)), 2026-11-05, 4 points, 2 comments — low engagement, but the WebSearch sandboxing supplement independently names "require approval for high-risk actions like deletes or transfers" as a generic recommended mitigation with no named implementation, corroborating the gap from a different angle.
- **Why it looks unbuilt/untested**: Both the low-traction HN item and the generic (unattributed) "require approval" advice point to the same place — people know high-risk tool calls need a gate, one startup built a narrow point solution (wallet screening specifically) rather than a protocol-level or framework-level reusable approval-gate primitive.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found the generic, reusable primitive already shipped by multiple well-resourced parties, contradicting the digest's framing: Microsoft Agent Framework ships built-in human-in-the-loop tool-approval middleware (a `DelegatingChatClient` in the `IChatClient` pipeline that gates selected high-risk function calls, documented March 2026), Gravitee's API gateway offers productized approval-gate workflows that bind an immutable request to a reviewer sign-off before execution, and Connic implements configurable runtime approval gates on sensitive tool calls. A framework-level HITL approval primitive from Microsoft closes this gap for most builders already.

### P6: No build-time linter for MCP tool-description/schema quality
- **What it is**: Distinct from runtime tool-selection retrieval (RAG-style tool search, already a saturated space per prior cycle research): a static, pre-deployment checker that scans an MCP server's tool definitions for the specific description/schema traits research says cause agents to mis-select tools — vague descriptions, overlapping tool purposes, ambiguous required fields — and flags them before the server ships, the way a linter catches code smells before runtime.
- **Evidence**: WebSearch supplement (testing/mocking query) surfaced the recurring claim that "vague descriptions are the number-one cause of agents calling the wrong tool" and that "tool calling isn't standardized behavior — each model family has its own habits," both raised as open problems in 2026 practitioner posts rather than tied to any shipped authoring-time tool.
- **Why it looks unbuilt/untested**: Every mitigation surfaced in this research run is runtime (retrieval, mocking, sandboxing); none of the testing/mocking sources named a static analysis step performed on tool definitions themselves before deployment, despite practitioners explicitly naming description quality as the root cause.
- **Maturity**: SATURATED
- **Verdict notes**: A dedicated search found this space is already crowded: GitHub alone returned 10+ repos named `mcp-lint`/`mcp-linter` (several created within days of this digest, e.g. `tick-ai/mcp-lint`, `robert19001-cmyk/mcp-lint`, `cavan1977/mcp-lint`, `linhongyu510/mcp-lint`), plus `mcpolish` (PyPI, cites peer research cataloguing 18 description "smells," arXiv:2602.18914), `mcp-tool-lint` and `mcp-schema-lint` (npm, CI-friendly severities), `@fernforge/mcp-conform` (deterministic author-side linter incl. injection-phrase detection), and `AgentDX` (static lint paired with an LLM tool-selection benchmark). Individually small, but the sheer density of independent, research-informed implementations means the specific gap described is already being actively closed.
