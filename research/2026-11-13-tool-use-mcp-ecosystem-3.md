## Candidate patterns

### P1: Retrieval/routing layer for tool-selection accuracy at scale
- **What it is**: As agents connect to dozens of MCP servers, flat tool lists cause mis-selection; the proposed fix is a retrieval or routing layer that surfaces only the 3-10 most relevant tools per request instead of dumping the full catalog into context every turn.
- **Evidence**: WebSearch supplement ("too many tools...") cites tianpan.co's "Tool Explosion Problem: Why Your Agent Breaks at 30 Tools" and "The Tool Belt That Grew a Long Tail Nobody Uses," dev.to's "We gave LLMs 150 tools, here's what broke," getunblocked.com's "MCP Tool Overload: A Measured Guide to Context-Window Bloat," and mintmcp.com's "How Jenova Solved the AI Tool Scalability Problem." Sources disagree on the exact degradation onset (10-50 tools) and even cite conflicting RAG-MCP accuracy numbers (one reading: 13%→43% improvement; another reading of the same framework: 43%→14% degradation as tool count grows).
- **Why it looks unbuilt/untested**: The cited mitigations are vendor blog posts and practitioner heuristics, not a converged benchmark; the conflicting RAG-MCP numbers across sources is itself a signal that no one has run a controlled, agreed-upon evaluation.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained implementations and shipped products from well-resourced teams close this gap: Anthropic's own MCP tool-search feature in Claude Code, LiteLLM's maintained "MCP Semantic Tool Filter," Stacklok's MCP Optimizer (shipped, built into the Stacklok platform), Airia's MCP Gateway (dynamic per-user tool routing, announced Aug 2026), and a July 2026 arXiv paper reporting 98% Top-15 recall at 3,000+ tools via hybrid retrieval. GitHub search also surfaced numerous smaller retrieval-routing repos (`shivab8/rag-mcp-tool-selector`, `nulltyto/mcp-orchestrator`, `DanielTobi0/Semantic-Tool-Discovery`). The conflicting RAG-MCP numbers cited in the digest are a benchmarking-reporting inconsistency, not evidence the underlying mitigation is unbuilt.

### P2: Per-turn tool-definition caching inside the agent loop
- **What it is**: Distinct from retrieval/filtering (P1), this is a caching problem — MCP tool-schema JSON is reportedly reloaded into the prompt on every single turn of an agent loop rather than cached once per session, multiplying the token tax for long-running agent sessions.
- **Evidence**: getunblocked.com's "MCP Tool Overload" (WebSearch supplement) states plainly that "MCP tool definitions are not cached across model calls inside the agent loop, so the full schema list reloads every turn."
- **Why it looks unbuilt/untested**: The claim is stated as a named, uncorrected inefficiency in a single blog post — no competing source named a caching layer that already solves it, and the primary mitigations discussed elsewhere (filtering, routing) address tool count, not the reload-per-turn mechanism itself.
- **Maturity**: PARTIAL
- **Verdict notes**: Partial, narrow mitigations exist but nothing closes the specific "reload every turn" mechanism end-to-end: the OpenAI Agents SDK ships a `cache_tools_list` flag (caches `list_tools()`, but is lost if the server instance is recreated each run, and doesn't address per-turn prompt-token reload), and a live, open GitHub issue against Claude Code ("Tool catalog (~24k tokens) sent uncached on every API request — cache_control breakpoint missing") shows the dominant client has not fixed this; a third-party reverse proxy is cited as the only workaround. GitHub search for `MCP tool cache` / `MCP schema cache session` found only two near-zero-star personal repos. Real gap, but addressable by a differentiated build.

### P3: Re-prompt-on-change consent to stop MCP tool-description "rug pulls"
- **What it is**: MCP clients typically ask for one-time user approval of a tool, but most don't re-prompt if the server later changes that tool's description or behavior — so a server can get approved once, then silently swap in a malicious description later with no new consent screen.
- **Evidence**: WebSearch supplement (consent fatigue query) surfaced eseospace.com's "MCP approval fatigue" and "MCP confused deputy" write-ups describing this exact rug-pull mechanism, and christian-schneider.net's "Why MCP security is different" arguing for a defense-first, per-client consent architecture instead of one-time approval.
- **Why it looks unbuilt/untested**: My direct search for "has anyone built" / "I wish" phrasing on this exact problem returned zero results — the sources describe and diagnose the gap (consent fatigue, rug-pull vector) but none names a widely adopted client or server-side tool that re-prompts on description change.
- **Maturity**: PARTIAL
- **Verdict notes**: Only small, individually unendorsed attempts exist — GitHub search for `MCP consent` / `MCP tool description change detection` surfaced narrow, low/no-star repos (`candpixie/mcp-consent-audit`, `Venkatchavan/mcp-consent-ledger`, `dev.to/alex_spinov`'s "pin the manifest, block rug pulls in 40 lines" gist-level fix, `H3llKa1ser/MCP-Server-Security-Scanner` which detects but doesn't re-prompt). WebSearch confirms the core finding: one study reports Claude Desktop/Cursor sometimes warn on a detected rug pull, but a separate study found MCP clients forced re-approval in 0 of 8 tested rug-pull techniques. No widely-adopted client ships a standard re-prompt-on-description-change mechanism.

### P4: Trusted-redirect-URI defense against MCP OAuth/dynamic-client-registration phishing
- **What it is**: A proposal to let end users explicitly trust their own MCP client via OAuth dynamic client registration, without opening a phishing hole where an attacker's client obtains a token through a malicious redirect URI and no new consent screen appears.
- **Evidence**: Hacker News via engine, "Letting users trust their own MCP clients, without opening a phishing hole" (streamvessel.com/blog/mcp-trusted-redirect-uris), 2026-11-04, 35 points, 6 comments.
- **Why it looks unbuilt/untested**: The post is framed as raising and patching a specific trust-UX gap in MCP's OAuth authorization layer, not citing an already-adopted fix; 35 points/6 comments on Hacker News indicates the problem registered with the community but did not generate a flood of "already solved" replies pointing to an incumbent.
- **Maturity**: PARTIAL
- **Verdict notes**: The protocol's own maintainers have moved on this at the spec level — the MCP draft security-considerations doc now states authorization servers "SHOULD only automatically redirect the user agent if it trusts the redirection URI" and requires exact redirect-URI matching, and the November 2025 spec update made Client ID Metadata Documents (CIMD) the default identity mechanism, relegating DCR to a fallback specifically to reduce this phishing surface. However, this is general protocol-level guidance, not the specific user-facing "explicitly trust your own client" opt-in UX the HN post (streamvessel.com) proposes, and GitHub search for `MCP OAuth redirect` / `MCP dynamic client registration` returned zero implementation repos — only IETF mailing-list discussion. The specific UX gap remains open even though the underlying protocol risk is being mitigated.

- **What it is**: Testing whether an agent calls the right tools in the right sequence is complicated by non-determinism — the same query can produce different tool-call sequences depending on which MCP servers happen to be connected at test time, not just which model is used.
- **Evidence**: WebSearch supplement surfaced dev.to's "The MCP Evaluation Framework Nobody Talks About But Should" naming this exact non-determinism, plus braintrust.dev's "What is an MCP eval" arguing for separating tool-choice/argument/execution/outcome scoring instead of one pass/fail number, and warning that harnesses using a shortened tool list or skipping production auth measure a different configuration than what ships.
- **Why it looks unbuilt/untested**: Every named framework in this search (mcp-eval, mcpjam, DeepEval's MCP-use metric) is described as a point tool for one slice of the problem (pytest integration, CI regression runs, CI/CD unit metric) — no source named a framework that explicitly handles the "variable connected-server set changes the correct answer" case.
- **Maturity**: PARTIAL
- **Verdict notes**: The general MCP-eval space is saturated (`lastmile-ai/mcp-eval`, `dylibso/mcpx-eval`, `alpic-ai/mcp-eval`, MCP-Bench, MCP-Atlas grading 1,000 tasks across 36 servers), but WebSearch confirms the digest's specific framing: every named framework addresses general non-determinism (multiple trials, LLM-judge scoring) rather than the narrower claim that the *correct* tool-call sequence itself changes depending on which servers happen to be connected at test time. No source — dev.to's "MCP Evaluation Framework Nobody Talks About," Braintrust's 2026 MCP-testing roundup, or Toloka's write-up — names a framework that explicitly models connected-server-set as a variable affecting ground truth. Crowded adjacent space, but this specific sub-problem is unaddressed.
