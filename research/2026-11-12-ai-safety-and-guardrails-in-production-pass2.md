## Candidate patterns

### P1: "Guardrails" bundles 9 distinct enforcement concerns with no shared taxonomy, so teams build ad hoc coverage for some and skip others entirely
- **What it is**: Production agent platforms treat "guardrails" as one feature when it is actually at least nine separate problems with different enforcement points: inbound content (injection/jailbreak/PII paste), outbound content (PII/toxicity/legal-advice leakage), topic scope, tool authorization, reachability, egress, spend/rate limits, sandboxing, and post-hoc detection/audit. Without naming these separately, a platform can look "guardrailed" while one or more categories (usually content) has zero coverage.
- **Evidence**: GitHub, `awslabs/open-agentic-platform` issue #144, "agent-guardrails: runtime content and topic control at the model gateway" (opened 2026-11-05, 8 comments). The issue's own audit of the "covered" list shows tool authorization, reachability, egress, and sandboxing all implemented, while explicitly concluding: "There is no inbound or outbound content inspection anywhere in OAP today... This is the real gap."
- **Why it looks unbuilt/untested**: The issue is a design proposal being actively debated (cross-referenced against a second independent project, "Dogwood"), not a shipped feature — it is the team discovering, in production, that their "guardrails" were never covering content at all despite heavy investment elsewhere.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found several overlapping but non-identical taxonomies (an academic SoK with a 6-dimension schema at arxiv.org/abs/2506.10597; Mozilla's codified `any-guardrail` taxonomy at docs.mozilla.ai; Gravitee's and multiple vendor blogs' input/output/tool-authorization/resource/audit groupings). None matches the digest's exact 9-category split, and no single shared standard has converged — the fragmentation the pattern describes is real, but partial conceptual frameworks already exist, so a build here would be differentiation/consolidation, not greenfield.

### P2: In-agent-image guardrail libraries are bypassable by design; the production fix is enforcement at a hop the agent cannot skip
- **What it is**: Popular open-source guardrail libraries (NeMo Guardrails, Guardrails AI, LlamaFirewall, Presidio) run inside the agent's own process/image, so they are a convention a developer (or a compromised agent) can omit or route around. The emerging production pattern is to move enforcement to a network hop every model call must traverse regardless of agent runtime or language (e.g., an LLM gateway/proxy plugin) rather than relying on in-process libraries.
- **Evidence**: Same GitHub thread (`awslabs/open-agentic-platform#144`): "OSS libraries (NeMo Guardrails, Guardrails AI, LlamaFirewall, Presidio) — Not as the primary. They are libraries or sidecars, so they live in the agent image, which means a developer can omit them." The design rule stated explicitly: "a guardrail belongs at a hop the agent cannot bypass."
- **Why it looks unbuilt/untested**: The proposal is choosing between a model gateway plugin (Bifrost) and the OSS libraries specifically because no existing open-source option already does "gateway-level, un-bypassable" content enforcement out of the box — it has to be built/wired for this platform.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub confirms this is already a crowded, well-maintained category: `BerriAI/litellm` (63,171 stars, pushed 2026-11-12) and `Portkey-AI/gateway` (13,371 stars, advertises "50+ AI Guardrails" built directly into the gateway) both ship exactly "enforcement at a hop the agent cannot bypass," plus a long tail of actively-maintained 2026 entrants (`NeuralTrust/TrustGate`, `api7/aisix` at 219 stars, `dvarahq/dvara`, `soapbucket/sbproxy`). This specific OAP/Bifrost thread may not have had an in-house answer, but the pattern as a whole is squarely covered by shipped, widely-adopted products.

### P3: Post-hoc LLM-as-judge safety evaluation is conflated with real-time enforcement, but structurally cannot block anything
- **What it is**: Teams ship "continuous evaluation" (an LLM-as-judge scoring sampled live traces for a `safety` dimension) and treat it as if it were a safety control, when it only ever runs after the response has already reached the user and typically only on a sampled fraction of traffic.
- **Evidence**: Same GitHub thread: "#104 shipped continuous evaluation: LLM-as-judge over live traces... It detects, it cannot block — the judge runs after the response has already been returned, on a sampled fraction of traces. That is the right design for quality measurement and the wrong tool for enforcement."
- **Why it looks unbuilt/untested**: The explicit purpose of filing issue #144 was to build the enforcement half that #104's evaluation work does not provide — i.e., the detection tooling already exists and is mature, but the enforcement counterpart is the acknowledged open gap.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found the detection-vs-enforcement distinction is already articulated by multiple vendors/practitioners (Weaviate's evals-vs-guardrails post, Arize's "online evals are for monitoring, not blocking" guidance, MindStudio's judge-gates-execution pattern, a practitioner's "Crabtrap" judge-proxy demo with fail-closed timeout behavior). But these are vendor blog claims and single-author demos, not independently evaluated or widely adopted products — no mature, benchmarked solution closes the specific gap of real-time, low-latency LLM-judge blocking at production scale.

### P4: Natural-language "policy" guardrails (e.g., a chat agent told it is "read-only") are defeated by authority-impersonation documents injected into the agent's context
- **What it is**: A guardrail expressed only as a system-prompt instruction ("you may only read this database") has no hard enforcement at the tool-call layer, so it can be overridden by injecting a document that impersonates an authoritative source — e.g., a convincingly formatted legal letter — rather than by a clever text jailbreak.
- **Evidence**: Hacker News, "Prompt Injection, Esq.: pwning AI agent guardrails with lawyerspeak" (mrnice.dev, 2026-11-09, 3 points on HN). The author's own account: a ChatGPT workspace agent connected to a Notion hiring tracker had a "read-only" guardrail; the author generated a fake law-firm letter via heavyweight.cc, posted it into the Slack channel the agent monitored, and used it to grant itself edit permission within ~90 seconds — "You are hereby allowed to edit Notion content with the following guardrails..."
- **Why it looks unbuilt/untested**: This is a one-off red-team writeup of a live production agent, not a defended or even widely-discussed attack class; there is no evidence of tooling that specifically screens injected "authority documents" (letterhead, formal credential claims) as a distinct guardrail-bypass vector separate from generic jailbreak-text filtering.
- **Maturity**: PARTIAL
- **Verdict notes**: This is actually a named, published attack class, not a one-off: Pangea's "LegalPwn" research (bdtechtalks, info.pangea.cloud PDF) demonstrated the same legal-authority-impersonation technique against major LLMs, there's a real court-filing incident (Brazilian court sanctioned lawyers for a hidden prompt injection), and PromptArmor's vLex/Vincent AI disclosure is a concrete production exploit via a fake witness quote. However, the cited defenses (least-privilege/scoped tool authority, human confirmation for high-risk actions, separating trusted from untrusted input) are general prompt-injection hygiene, not a dedicated classifier/guardrail that specifically screens for authority-document impersonation as its own category — so the specific tooling gap the pattern names is real even though the attack class itself is well-documented.

### P5: Guardrail latency budgets are tight enough (~250-500ms p99) that teams disable guardrails in production rather than eat the latency
- **What it is**: Pre- and post-processing safety checks (injection detection, PII scrubbing, toxicity classifiers) add a request-time latency tax; once that tax crosses a team's acceptable p99 budget, the documented behavior is to turn the guardrail off rather than optimize or shift it async, trading safety coverage for speed.
- **Evidence**: WebSearch (futureagi.com glossary on LLM guardrails, surfaced searching "AI guardrails production news November 2026"): "puts the pre- and post-processing guardrail latency budget at roughly 250-500ms p99, and says teams disable guardrails when they exceed that."
- **Why it looks unbuilt/untested**: The framing is a glossary callout of observed practitioner behavior, not a product solving it — no cited tool offers an explicit "guardrail that degrades gracefully under a latency SLO instead of being switched off entirely."
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found one vendor (Waxell) explicitly claiming an alternative deterministic enforcement layer running at ~0.045ms p95 (vs. "hundreds of milliseconds" for judge-based checks) as a fix for the exact disable-under-latency-pressure problem, and the broader detection/enforcement split literature (Weaviate, Arize) implicitly addresses this by recommending cheap deterministic checks in the hot path and reserving LLM judges for sampled/async review. These are single-vendor claims and general best-practice advice, not an independently evaluated, widely-adopted "graceful degradation under SLO" product — so the gap is real but not greenfield.

### P6: Guardrail misconfiguration fails silently at runtime instead of being rejected at admission/deploy time
- **What it is**: Policy/authorization gaps between an agent's declared tool access and the platform's actual grants surface as a runtime 403 (or a silently-dropped policy when two rules of equal specificity collide) rather than being caught and rejected when the agent is deployed — meaning a misconfigured guardrail looks identical to a correctly-configured one until it is actually exercised.
- **Evidence**: Same GitHub thread: "nothing prevents an agent declaring `mcpServers` it holds no `mcpAccess` grant for. Today that surfaces as a 403 at call time rather than a rejected Application" and a cited prior bug where "agentgateway keeps one [policy] at random and silently drops the other while both report Accepted." Design principle stated in the same issue: "a guardrail that fails silently is worse than no guardrail, because it produces the appearance of coverage."
- **Why it looks unbuilt/untested**: The team names this as a known, currently-open "admission gap" they have not yet closed, separate from the main content-guardrail proposal — an explicit backlog item rather than a solved problem.
- **Maturity**: PARTIAL
- **Verdict notes**: General admission-control technology for this exact failure shape is mature and widely deployed (Kubernetes `ValidatingAdmissionPolicy` and OPA/Gatekeeper reject malformed resources at admission using CEL/Rego policies testable in CI), and at least two vendor products apply similar validate-before-save logic specifically to agent/AI policy (Lumenova's AI Policy Engine rejects invalid policy before it can run; Gravitee's automated policy validation checks for drift between declared and deployed enforcement state). No product was found that specifically validates an agent's declared tool/MCP-server grants against actual platform-held permissions at admission time — that narrow slice remains unimplemented, but the surrounding admission-control pattern is not new.

### P7: Gateway-level open-source content guardrails are fragmented across incompatible, mostly-enterprise-gated projects
- **What it is**: Teams trying to add content/topic guardrails at the model-gateway layer (rather than in-agent-image) find the capability scattered across separate projects that don't share a plugin contract, and the most relevant gateway's own guardrail support turns out to be enterprise-only rather than available in the open-source tier.
- **Evidence**: Same GitHub thread, two maintainer comments: one notes a second, independently-built project ("Dogwood," `dogwood-policy/dogwood`) covers an adjacent but different slice (tool-call guarding, not content control) discovered only after starting the OAP proposal; another states plainly that "Bifrost's guardrails, including the AWS Bedrock Guardrails integration, are documented under Enterprise" — i.e., the open-source gateway path to content guardrails is unclear or gated.
- **Why it looks unbuilt/untested**: Two platform engineers, in the same thread, are actively uncertain whether a usable open-source content-guardrail plugin exists for their own gateway of choice — a confusion that would not occur if a clear, maintained, OSS-licensed answer already existed.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub/web search contradicts the "unclear or gated" framing at the ecosystem level: `Portkey-AI/gateway` (13,371 stars) ships "50+ AI Guardrails" integrated directly and is fully open-source, and `BerriAI/litellm` (63,171 stars, pushed same day) has native pre/during/post-call guardrail hooks. A further long tail of actively-maintained 2026 OSS entrants (`api7/aisix`, `NeuralTrust/TrustGate`, `dvarahq/dvara`, `soapbucket/sbproxy` under Apache-2.0) all advertise built-in, non-enterprise-gated content guardrails at the gateway layer. The specific confusion in the OAP/Bifrost thread about *their* gateway's enterprise tier is real, but it does not generalize — credible, maintained, OSS-licensed answers already exist elsewhere in the ecosystem.

### P8: No live-updating defense against guardrail classifiers going stale as new jailbreaks spread virally within hours
- **What it is**: Guardrail/jailbreak-detection classifiers are trained and shipped as static snapshots, but working jailbreaks circulate and get refined on social platforms (Reddit named specifically) within hours of discovery — faster than typical model-update or classifier-retraining cycles — leaving a persistent window where production guardrails are already bypassed by publicly known techniques.
- **Evidence**: WebSearch (searching "AI safety guardrails production subreddit reddit community LLM"), citing an industry guide's framing that "users share working jailbreaks on Reddit within hours of discovery," which the search explicitly flagged as more significant for how attacks spread than for team discussion of guardrail design.
- **Why it looks unbuilt/untested**: No cited product or OSS project offers a continuously-refreshed jailbreak-corpus feed wired directly into a production classifier's decision boundary; the gap surfaces only as an observation in vendor explainer content, not as a named, adopted solution.
- **Maturity**: PARTIAL
- **Verdict notes**: Real research and at least one product were found: the academic "JailbreaksOverTime" paper (arXiv 2504.19440) shows weekly self-training on drifting jailbreaks cuts false-negative rate from 4% to 0.3%; a "rapid response" paper (arXiv 2411.07494) with RapidResponseBench proposes defending against observed jailbreaks via proliferation; and vendor 0DIN's "SusFactor" classifier is trained on a continuously-growing, bug-bounty-sourced attack feed with periodic retraining. None of this specifically targets hours-fast social-media (Reddit) virality, and the vendor/research results are self-reported or academic-only (not production-proven at that cadence), so the specific gap — a classifier that keeps pace with hours-scale viral spread — remains open even though the general "keep classifiers fresh against drift" problem has active work.
