## Candidate patterns

### P1: End-to-end full-duplex voice models positioned as the successor to cascaded STT→LLM→TTS pipelines
- **What it is**: Instead of chaining separate speech-to-text, LLM, and text-to-speech stages, some teams and commenters argue the architecture itself is a dead end for natural, overlapping conversation, and are pushing toward single end-to-end audio-in/audio-out models.
- **Evidence**: A Hacker News thread surfaced via WebSearch (on building for "voice in, visuals out") includes a commenter stating plainly that "STT -> LLM -> TTS is a dead end, and that the future is end-to-end," with another commenter pointing to endpoint-detection tricks (Soniox) as a stopgap. A separate practitioner piece, "Voice Agents Are Not Chat Agents With a Microphone: The Half-Duplex Tax" (tianpan.co, via WebSearch), frames the cascaded approach as a tax paid for using chat-agent architecture in a voice context.
- **Why it looks unbuilt/untested**: The commentary is explicitly "the future is end-to-end," i.e. a stated direction rather than a shipped, adopted architecture — the same WebSearch pass found only stopgap mitigations (better endpoint detection) layered onto the cascaded approach, not a widely-used end-to-end replacement.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple well-resourced teams have already shipped exactly this: OpenAI GPT-Live (full-duplex voice in ChatGPT, launched 2026), NVIDIA NemotronLabs VoiceChat (open-weight 11B full-duplex model with tool calling), ByteDance Seed full-duplex speech LLM (rolled out in the Doubao app), and Boson AI's Higgs Realtime Duplex (previewed with forthcoming API). On the GitHub side, `adventists-ai/sophon-realtime` (open full-duplex voice model, vLLM-Omni/MLX, OpenAI-Realtime-compatible, created 2026-11-19) is a direct open-source instance. Academic benchmarking is also mature and contested rather than nascent: M3-DuplexBench, SPEARBench, FLEXI, Full-Duplex-Bench, and Lychee-FD (ACL 2026 Outstanding Paper) all target this exact architecture shift. The "end-to-end is the future" framing in the digest is already several shipped products deep, not an unaddressed wish.

### P2: Granular, per-tool/per-call interruption policies instead of one global barge-in setting
- **What it is**: Voice-agent frameworks today mostly expose a single barge-in/interruption behavior for the whole session; a concrete framework PR found in this run adds the ability to configure interruption mode per individual tool call (e.g., don't allow barge-in mid-critical-tool-execution, but allow it during small talk).
- **Evidence**: A real, dated GitHub PR from the engine run: "Add per-tool voice interruption modes" (timbal-ai/timbal, PR #246, 2026-11-04, 1 comment) — flagged by an automated reviewer bot as "Large changes to voice turn-taking and interrupt handling in `VoiceSession`... Medium Risk."
- **Why it looks unbuilt/untested**: This is a single, very recent (Nov 4) PR in one framework, not an established pattern — the reviewer bot itself flags the change as large/risky, meaning the framework's existing interruption model had no such granularity until this PR.
- **Maturity**: SATURATED
- **Verdict notes**: ElevenLabs' shipped Agents product already has a per-tool `interruption_mode` field (docs: elevenlabs.io/docs/eleven-agents/.../tool-interruptions) with modes like `disable_during_tool_and_turn`, overridable per-tool and per-server, superseding an older boolean `disable_interruptions` flag — i.e. a maintained commercial product moved through exactly this granularity already. Several other vendors (Dograh, Verloop, AudioCodes LiveHub, Telnyx, Jambonz) ship adjacent per-node/per-block/per-assistant interruption configuration. The timbal-ai PR is a smaller framework catching up to a pattern a market leader already shipped, not a novel unaddressed gap.

### P3: Heuristic "modality router" hooks replacing LLM-driven decisions about when to invoke a vision tool
- **What it is**: In multimodal agents, a text-only reasoning model structurally cannot decide when it needs to look at an image, because it can't see the image to know it's relevant — so some builders report switching from "let the LLM call a vision tool via function-calling" to an automatic hook that runs before the model reasons and decides modality routing for it.
- **Evidence**: A hands-on write-up surfaced via WebSearch (multimodal agent architecture search) reports that "a text-only model can't reliably decide when to call a vision tool, since it can't see the image," and that the author "switched to an automatic hook that runs before the model reasons."
- **Why it looks unbuilt/untested**: This is described as one author's workaround ("switched to"), not a documented library feature or convention — the same search returned mostly vendor tutorial stacks (Whisper + LLaVA + function-calling model + TTS) that still rely on the LLM to decide when to call the vision tool, i.e. the workaround hasn't propagated into the mainstream tutorials.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for "modality router"/"vision tool routing hook" turned up nothing matching the exact pre-reasoning-hook shape. Academic work exists but is narrow/unevaluated-in-production: ToolGate (arXiv 2606.03054) is a lightweight external controller deciding whether a proposed perceptual tool call should run before its output enters context, with linked code, and reports only ~11.8% of baseline tool calls actually fixed a wrong answer; ToolScope (arXiv 2510.27363) has a similar pre-invocation "Global Navigator." Practitioner-level "modality router" patterns (CallSphere blog, OpenHands `MultimodalRouter`) exist but route to different models/processors by input type rather than deciding when a text-only reasoning model needs to pull in vision — not the same mechanism. No mainstream agent framework ships this as a standard feature, so a real build would be differentiated.

### P4: Push toward a single unified realtime multimodal session, without a converged reference architecture
- **What it is**: Multiple vendor engineering posts independently argue that voice, text, and vision work better as one realtime session with shared turn-taking and tool-routing logic than as three pipelines stitched together after the fact — but each post proposes a different set of required layers (VAD + turn policy + tool router + event memory in one; perception + fusion + reasoning + memory + action + transport in another).
- **Evidence**: A getstream.io-style architecture guide (via WebSearch) states that "voice, text, and vision work better as a single realtime session than as separate pipelines stitched together, with shared rules for turn-taking and tool use," listing "a voice activity detector, a turn policy, a tool router, and memory of recent events" as requirements. A second, differently-structured guide from the same search describes "perception, fusion, a reasoning model, memory, a tool-calling action layer, and real-time transport" as the stack, and notes "a single model suits a pure voice turn, while a cascaded setup suits vision, compliance, or domain jargon" — i.e. even vendors agree cascading is sometimes still necessary.
- **Why it looks unbuilt/untested**: Two independent sources describe the same destination (unified session) with non-matching layer breakdowns, and one source openly concedes the cascaded approach is still needed for some cases — evidence of a converging direction with no settled, agreed-upon architecture yet.
- **Maturity**: SATURATED
- **Verdict notes**: The practical capability is already covered by multiple maintained, widely-adopted open-source frameworks: LiveKit Agents (large GitHub org with starter apps in Python/Node/React, a LangGraph adapter, and a dedicated `MultimodalAgent` wrapping OpenAI's Realtime API for voice+video+text in one session with tool calls), Pipecat (pipecat-ai, vendor-neutral real-time multimodal agent framework with many downstream mirrors/forks indicating heavy reuse), and OpenAI's own hosted Realtime API (accepts audio/image/text, outputs audio/text, supports tool calling and remote MCP). The lack of one agreed internal layer-naming convention across vendor blog posts (VAD+turn-policy+router vs. perception+fusion+action) is a documentation/terminology disagreement, not evidence the underlying unified-session capability is unbuilt — it is shipped and in production use today.

- **Why it looks unbuilt/untested**: This is a single very early-stage repo (a PR literally scaffolding the directory structure, with demo/labeled assets rather than a trained production model) — no second implementation of a dedicated voice-authenticity shield layer turned up in the same run.
- **Maturity**: SATURATED
- **Verdict notes**: While open-source detectors specifically are weak (a 2026 Resemble AI/Podonos benchmark found open-source models Wav2Vec2/RawNet2/LCNN/AASIST scoring only 48-67% accuracy, trained on the stale ASVspoof 2019 LA dataset), the actual gap — a deployable voice-authenticity/anti-deepfake shield layer for voice pipelines — is already closed by multiple well-resourced shipped commercial products: Resemble AI's DETECT-World (on-prem commercial detector), Aurigin AI's VoxGuard (sub-50ms real-time scam-call detection, Docker/Kubernetes on-prem deploy), and OmniSpeech AI Detect (shipped in the Zoom App Marketplace). VaniShield is one early-stage hobby repo competing against an already-served, commercially-saturated need; an open-source angle could still be differentiated but the core problem is not unaddressed.

### P6: Crowded, fragmented local-first voice-dictation agents signal unmet demand for a standard OS-level voice input layer
- **What it is**: A cluster of small, often single-maintainer, local/offline push-to-talk dictation tools (Hex, Ghost Pepper, aqua voice, and several same-named forks) compete for the same niche — voice-to-text input layered on top of any app — each shipping overlapping but incompatible implementations rather than converging on one adopted standard or library.
- **Evidence**: WebSearch for "Hex Voice Dictation hacker news comments" surfaced at least three separately-maintained projects literally named "Hex" (an Anomaly/OpenCode MIT-licensed cross-platform app, a Mac-only WhisperKit app by Kit Langton, and a separate Rust tool), plus an adjacent "Show HN: Ghost Pepper – Local hold-to-talk speech-to-text for macOS" entry describing itself as entering "the crowded field of whisper-style dictation apps." An HN-mirrored comment independently calls one of the Hex variants "the leanest (& cleanest) free option" among several competitors tried.
- **Why it looks unbuilt/untested**: The sheer name collision (three unrelated "Hex" projects) and explicit "crowded field" framing from one of the newer entrants both indicate this is a popular, actively re-invented category with no dominant open standard or shared library that new entrants build on top of instead of rewriting from scratch.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos` confirms the crowding directly: dozens of near-identical local-dictation repos created/updated in just the last 30 days (anomalyco/hex, infiniV/VoiceFlow, zachswift615/speak2, cleanunicorn/earheart, bluejacketblackhawk/saysomething, tristanmuzzu/parakeet-dictation, futurminds/whispertool, romarayt/VoxLocal, Aurathex/Aural, pe-menezes/never-type, webrapidromania/WR-Voice). So the end-user app layer is itself saturated. But the specific gap named — a standard, shared OS-level/library layer other apps build on instead of rewriting — remains only narrowly attempted: `dictare`'s "OpenVIP" (an open protocol for voice input to AI agents, HTTP/SSE-based) and `transcribe.cpp` (a library extracted from the Handy app to unify local STT backends) are the only two real attempts found, both early/narrow and not adopted by the dozen-plus apps above. A serious shared-library/standard build would still be differentiated from the fragmented app layer.

### P7: Voice treated as an under-designed "output layer" bolted onto text-first agents rather than a native interaction mode
- **What it is**: Several practitioner posts frame voice output specifically (not voice input) as the neglected half of voice-agent design — agents are built text-first and have speech synthesis added afterward as an output channel, rather than being designed around voice as the primary interaction surface from the start.
- **Evidence**: A WebSearch-surfaced practitioner essay is explicitly titled "Voice feels like the underrated output layer for AI agents" (bittide.aicompass.dev). A separate essay found in the same research pass, "Building for Voice In, Visuals Out" (allenpike.com, also discussed on Hacker News), argues "voice is never going to be the only input mode for computers" and that for a fully fluid two-way voice conversation "the latency bar is about 200ms" — implying most current systems, designed output-last, don't hit that bar.
- **Why it looks unbuilt/untested**: Both pieces are framed as naming a design blind spot ("underrated," a bar most systems miss) rather than pointing to an existing agent framework that treats voice-out as a first-class design input from the start.
- **Maturity**: PARTIAL
- **Verdict notes**: Streaming-TTS and voice-as-layer infrastructure is mature (AgentScope's three-layer voice design, Telnyx Agent SDK's voice mixin, LiveKit/Pipecat's streaming-synthesis-before-full-text patterns, state machines for listening/thinking/speaking/interrupted), so the plumbing for low-latency voice output exists and is shipped. But every framework found treats voice-out as a swappable layer/mixin added to a text-first agent core by design ("the agent core should stay ignorant of audio formats"), which is precisely the bolted-on architecture the practitioner essays criticize — and the essays themselves (dated within the window) assert most shipped systems still miss the ~200ms fluid-conversation bar. No framework was found that inverts this and designs the agent's reasoning/turn-taking natively around voice-first from the start, so the specific critique remains a real, differentiable gap rather than a solved problem.
