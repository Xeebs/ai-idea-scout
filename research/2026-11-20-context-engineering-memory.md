## Candidate patterns

### P1: Layered memory taxonomy replacing "big context window = memory"
- **What it is**: Splitting agent memory into distinct layers — policy memory (e.g. CLAUDE.md/AGENTS.md-style static rules), preference memory, fact memory, structured work summaries, and raw append-only execution traces — instead of treating a large context window as a single undifferentiated memory store.
- **Evidence**: DataCamp practitioner essay (WebSearch, "context engineering new systems design for ai") explicitly argues "give the model everything we have" is the default wrong answer and proposes the policy/preference/fact/trace split; an IndieHackers interview (WebSearch, "context windows are not memory... an interview with Sreekanth Ramakrishnan") makes the same "context ≠ memory" argument independently.
- **Why it looks unbuilt/untested**: Both sources frame this as a conceptual taxonomy / one practitioner's opinion, not a shipped framework — no named open-source library implements the full layered split as a reusable primitive; teams are each inventing their own version.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub has many maintained, even widely-adopted memory frameworks with typed/tiered stores — mem0ai/mem0 ("the memory layer for AI agents," production-used), Letta/MemGPT (explicit core/archival/recall memory tiers), EngramX ("pluggable storage, lifecycle policies"), GraphMem, ReasoningBank — so "layered memory beyond a single context window" as a general idea is well covered. But none implement the specific policy/preference/fact/trace split described here (particularly a distinct "policy" layer mirroring CLAUDE.md/AGENTS.md-style static rules separate from preferences/facts) as a named reusable primitive — a differentiated build targeting that exact taxonomy remains viable.

### P2: Structured context eviction/pruning as an alternative to LLM-summarization compaction
- **What it is**: Instead of the mainstream "compact" pattern (a blocking LLM call that summarizes history and restarts the window), structure-aware pruning removes low-value context deterministically and only summarizes when unavoidable; a related technique ("observation masking") simply hides old tool-call outputs rather than summarizing them.
- **Evidence**: Atlassian's Rovo Dev engineering blog (WebSearch) describes structure-aware pruning as faster and avoiding a lossy summary step; a DEV Community post (WebSearch) reports observation masking "roughly halved cost while matching the task completion rate of LLM summarization" and cites OpenAI's Codex team finding automated compaction "gradually hurt performance over time"; a preprint, "Beyond Compaction: Structured Context Eviction for Long-Horizon Agents" (WebSearch, hosted on HuggingFace), frames compaction as expensive, blocking, and error-introducing because it lands mid-task when the agent has least budget to catch mistakes.
- **Why it looks unbuilt/untested**: The digest's own sources call the evidence "mostly vendor blogs and preprints, not peer-reviewed work" — pruning/masking are reported as internal engineering choices (Atlassian, OpenAI Codex team) rather than available as a general-purpose, swappable library other agent builders can drop in.
- **Maturity**: PARTIAL
- **Verdict notes**: Real research backs this — JetBrains Research's "The Complexity Trap" (arXiv 2508.21433) measures observation masking roughly halving cost at matching/better solve rate vs. summarization; a June 2026 preprint "Beyond Compaction: Structured Context Eviction" (arXiv 2606.11213) proposes Context Window Lifecycle but has no public code repo found. Only narrow/small tooling exists: the `ambi` Rust framework does plain FIFO eviction, and a `shipshitdev` Claude skill library implementing masking+compaction has just 31 stars. No mainstream, swappable, drop-in library for structure-aware pruning/masking was found — internal vendor engineering choices (Atlassian, OpenAI Codex) remain unpackaged.

### P3: Cross-client/cross-project agent context handoff (no shared memory across tools)
- **What it is**: People running multiple coding/chat agents across different clients and client projects have no standard way to share context between sessions or tools — they're hand-rolling solutions like a manager-agent supervising per-project sub-agents, or a personal notes store in SQLite with full-text search.
- **Evidence**: "Ask HN: How Do You Manage Your AI Agents' Context Across Clients and Projects?" (last30days engine: Hacker News, 2026-11-07, 103 points, 71 comments — classic "how do you even do this" complaint-shaped post); WebSearch follow-up on the thread (via a zeli.app mirror) found commenters describing a self-built manager-agent-over-sub-agents system and a separate SQLite-based personal notes/skills store, confirming these are duct-taped individual solutions, not a shared standard.
- **Why it looks unbuilt/untested**: The same WebSearch surfaced several commercial point products already chasing this (PMB, Relay, ContextVault, ContextPool) — strong sign real demand exists, but the HN thread itself shows practitioners still improvising rather than converging on one of these tools, 71 comments in without a clear winner named.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub's "ContextVault" and "ContextPool" names are already taken by unrelated small projects (a docs-loader CLI, a RAG knowledge base, an empty repo), confirming these aren't mature products on that channel. WebSearch found a real cluster of early-stage competitors — MemoryBridgeAI (Product Hunt, inconsistent launch dates: Sep 2025 vs Aug 2026), Cross Context, Context Sync, AgentBridge, Contorium, Stele — but all are indie/Product Hunt-stage, and the HN thread itself (103pts/71cmt) shows practitioners still hand-rolling solutions rather than adopting any of them. No well-resourced/dominant product found; gap is real but contested by small players, not closed.

### P4: MCP memory servers can't actually get agents to consult them without extra plumbing
- **What it is**: Standing up a memory layer as an MCP server does not, by itself, make an agent reliably read from or write to it — MCP alone doesn't modify the agent's system prompt or force retrieval, so the memory server sits unused unless the host application is separately wired to call it every turn.
- **Evidence**: WebSearch summary of an HN comment thread on a memory-layer product: "another notes that adding an MCP server alone does not modify the agent's system prompt... a commenter says Claude Code's new HTTP hooks solved this for them" — a concrete workaround being hand-built per user, not a documented pattern.
- **Why it looks unbuilt/untested**: The fix described (HTTP hooks) is a one-off workaround reported by a single commenter, not a packaged solution; no general adapter pattern for "make any MCP memory server force its way into agent context" was found.
- **Maturity**: OPEN
- **Verdict notes**: WebSearch confirmed the problem is widely reported (a Claude Desktop bug report of zero tool-calls to a registered memory server, a matching Cursor forum thread, several "my agent has amnesia" DEV posts) but found no packaged adapter/forcing-layer product or library — only individual workarounds (one commenter's HTTP hooks fix, write-ups suggesting "move retrieval into the workflow" as a design idea). GitHub searches for MCP memory servers return servers that store memory, not solutions to the consultation problem itself. Genuine open gap.

### P5: Durable external KV/vector store as the actual "agent memory," context window as scratch space only
- **What it is**: Treating the context window purely as transient working memory and pushing all durable state (facts, history, long-term state) into an external key-value or vector store (e.g. Valkey) that the agent explicitly reads from and writes to, rather than relying on compaction/summarization inside the window.
- **Evidence**: GitHub PR "Add blog post: How AI Agents Forget: Engineering Memory Systems with Valkey" (last30days engine: GitHub, valkey-io/valkey-io.github.io, 2026-11-14, score 10, 2 reactions/3 comments) — based on a ValkeyConf 2026 Prague talk, explicitly contrasts "context windows versus durable agent memory."
- **Why it looks unbuilt/untested**: This is a single talk-derived blog post from one infra vendor (Valkey) proposing the pattern, not an existing cross-framework library or standard; it's pitched as a new idea to the Valkey community, not something already adopted broadly.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch shows this is already a mainstream, multi-vendor pattern, not a new Valkey idea — Redis's own "long-term memory architectures for AI agents" blog, AWS's "building persistent memory for multi-agent AI systems with Amazon S3 Vectors," Oracle's "from RAG to memory systems" post, and a MinIO architecture guide all describe and ship the identical "context window = short-term/scratch, external vector/KV store = durable long-term memory" split. Combined with mem0/Letta/Zep already implementing this in widely-used libraries, multiple well-resourced teams have shipped this exact architecture — Valkey's post is simply the newest vendor restating an already-closed pattern.

### P6: Event-driven agent execution replacing the "while true" agent loop
- **What it is**: Structuring an agent around discrete triggered events rather than a continuous polling/reasoning loop, which changes what context needs to be persisted between invocations (only event-relevant state, not a running conversation).
- **Evidence**: "Show HN: Pizza – An event-driven AI agent, no while true" (last30days engine: Hacker News, 2026-11-15, 5 points, 1 comment).
- **Why it looks unbuilt/untested**: Very low engagement (5 points, 1 comment) — a single hobby Show HN submission with no discussion establishing whether the approach actually solves a context/memory problem better than the loop model; essentially an unvalidated one-off.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found an academic framework, Amico ("Event-Driven Modular Framework for Persistent and Embedded Autonomy," arXiv 2507.14513), plus a small npm package Mozaik (`@mozaik-ai/core`) modeling the agent loop as an event-driven state machine, plus a bare reference implementation (sandipan1/event-driven-agent on GitHub, asyncio-based). These are real but narrow/early — none widely adopted or evaluated against the specific context/memory-footprint claim the pattern makes. Pizza itself (the digest's source) remains an unvalidated one-off, but the broader technique has more than zero prior art.

### P7: Version-controlled (git-like) agent context/state
- **What it is**: Applying git-style versioning — branches, commits, merges — to an agent's working context/state, so context changes can be rolled back, diffed, or forked the way code changes can.
- **Evidence**: "Show HN: Mallard: Git for the age of AI agents" (last30days engine: Hacker News, 2026-11-03, 3 points, 2 comments).
- **Why it looks unbuilt/untested**: Extremely thin engagement (3 points, 2 comments) for a brand-new Show HN submission — the idea of versioned agent context is being pitched but has essentially zero community validation yet.
- **Maturity**: PARTIAL
- **Verdict notes**: This is a surprisingly crowded research/tooling cluster: arXiv papers "AgentGit" (2511.00628, LangGraph-based commit/revert/branch) and "Git Context Controller" (2508.00031, COMMIT/BRANCH/MERGE/CONTEXT ops over agent memory-as-filesystem), plus small packages agmem (PyPI, git-style CLI with diffs/content-addressable storage), memora (commit/branch/merge/rollback/replay), and products re_gent (Product Hunt, file+prompt rollback) and Planarian (arXiv, environment-side snapshot/rollback/fork). None are widely adopted/maintained at scale — mostly papers and small packages — and a real gap remains (full rollback across external side effects, noted by Planarian and a re_gent commenter, is unsolved). Mallard itself is unvalidated, but the pattern is not undiscovered; differentiation would need to beat this cluster, not invent from scratch.

### P8: "Functional," immutable context management with no compaction step at all
- **What it is**: An architecture that avoids lossy summarization/compaction entirely by managing context in an immutable, functional style (each context transformation produces a new value rather than mutating/summarizing history in place).
- **Evidence**: "Gnosh.ai for 'Functional AI'; functional context management, no compaction" (last30days engine: Hacker News, 2026-11-01, 4 points, 1 comment).
- **Why it looks unbuilt/untested**: Single low-engagement Show-HN-style post naming a specific architectural claim ("no compaction") that directly contradicts the mainstream compaction consensus found in P2's evidence — worth checking whether this is a real technique or marketing framing, since it has had essentially no community scrutiny.
- **Maturity**: PARTIAL
- **Verdict notes**: A 2026 research cluster covers close variants: "LCM: Lossless Context Management" (arXiv 2605.04050, verbatim immutable store + derived summarized view, reversible via lcm_expand), "Contextual Memory Virtualisation" (DAG of immutable session snapshots with branches), "Context Window Lifecycle" (priority-based eviction instead of summarization), and "Addressable Recall Compaction" (archival store + on-demand recall). All are papers/write-ups, not shipped libraries, and each differs on whether the model-facing view is summarized, trimmed, evicted, or addressed — none is a widely-used "fully immutable, zero-compaction" product. Gnosh.ai's specific claim is unverified but sits in real, unsettled research territory rather than being either fabricated or already solved.
