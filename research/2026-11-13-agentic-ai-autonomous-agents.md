## Candidate patterns

### P1: Plan-Execute-Verify-Replan loop for multi-agent orchestration
- **What it is**: An explicit verifier step sits between a planner and workers in a multi-agent pipeline, checking whether combined worker outputs actually answer the original query and triggering a replan when gaps appear, instead of trusting the orchestrator's own aggregation.
- **Evidence**: An ICLR 2026 workshop paper ("Verified Multi-Agent Orchestration," arXiv 2603.11445) reports the plan-execute-verify-replan loop raises answer completeness from 3.1 to 4.2 and source quality from 2.6 to 4.1 (5-point scale) on 25 expert-curated market-research queries vs. a single-agent baseline. A practitioner blog response calls this the "verifier paradox" — the critique itself is evidence of live debate. Separately, arkforge.tech's "Agent Blind Spots: Why Orchestrators Can't See What Approved Workers Actually Do" argues orchestrator logs are just claims the system makes about itself and proposes an external verification witness.
- **Why it looks unbuilt/untested**: The paper is a workshop-stage result on a narrow 25-query benchmark, not a shipped framework; the "verifier paradox" critique and the "blind spots" post both argue the self-verification approach doesn't actually solve independent verification, i.e., the gap is openly contested, not closed.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found no shipped VMAO repo, but a closely related academic framework with code exists — Megagon Labs' VeriMAP (github.com/megagonlabs/veriMAP), which generates per-subtask verification functions. VMAO itself is still workshop-stage (arXiv 2603.11445) and the "verifier paradox" critique plus arkforge.tech's "Agent Blind Spots" post argue self-verification doesn't yet solve independent verification — real academic activity, but no evaluated, adopted production framework.

### P2: Narrow single-purpose agents + file-based plan/handoff instead of all-purpose agents
- **What it is**: Instead of one general-purpose autonomous agent, practitioners run narrowly-scoped agents that write a plan to a file before touching code, and pass handoffs between agents/sessions via markdown files rather than live conversational memory.
- **Evidence**: The Hacker News thread "Ask HN: What's your current AI agentic setup?" (news.ycombinator.com/item?id=50366117, surfaced by the engine at 571 points / 713 comments) asks specifically about coding harnesses, orchestration/swarm tools, and platforms like OpenClaw/Hermes Agent; a sample answer mirror describes paying ~€100/mo across subscriptions, using one tool for coding and a separate one "for orchestration," and trying to turn "useful skills into deterministic workflows." A derivative analysis piece, "AI coding agent setups from 663 Hacker News comments" (surfaced by the engine, HN, 29pts/4cmt), reports the repeated pattern across that comment set is narrow jobs rather than all-purpose agents, a plan written to file before code, and handoffs kept in markdown.
- **Why it looks unbuilt/untested**: This is described as something people are individually hand-rolling per project ("try to turn useful skills into deterministic workflows") — there's no named reusable tool/format for the handoff-file pattern across the sources found.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos` for handoff/plan-file patterns returned nothing packaged; WebSearch confirmed the pattern is widespread practice (specialized-role plugins, "decisions folder" architect agents, cross-repo `.ai-workflow/` proposals, starter kits with a single markdown coordination file) but every source is a blog post or personal starter kit, not a maintained reusable framework — e.g. dev.to's "cross-repo handoff protocol" and "working memory file as handoff layer" are one-off write-ups, not adopted tools.

### P3: Differentiated, type-aware context compaction for long-running agents
- **What it is**: Rather than one generic summarization pass when an agent's context window fills up, compaction treats different memory types (safety rules vs. user messages vs. stateful tool outputs) differently, because uniform compaction silently drops exactly the content that matters most.
- **Evidence**: A Reddit r/MachineLearning post compares how six coding agents (Claude Code, Codex CLI, OpenCode, Cline, Cursor, Amp) decide what to keep during compaction and finds they converge on layered progressive compression but diverge on what gets protected. The "Compaction Cliff" arXiv preprint (2608.22752) measures safety-rule recall at 53% after one compaction round, collapsing to 10% by round five under a production-style prompt. A practitioner build note (lethain.com) describes triggering compaction manually at 80% of context and keeping the dropped content as a recoverable "virtual file."
- **Why it looks unbuilt/untested**: The r/MachineLearning comparison itself frames this as six different ad hoc approaches with no agreed standard; the Compaction Cliff paper is a fresh (2026) preprint documenting a failure mode, not a fix; the lethain.com workaround is one engineer's internal hack, explicitly framed as "building an internal agent."
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found the Compaction Cliff paper (arXiv 2608.22752) proposes a type-aware "Knowledge Triage" classifier and says it will release a reference implementation, but no shipped repo was found yet. Adjacent shipped products (Anthropic's `compact-2026-01-12` beta API, OpenClaw's pre-turn memory flush, Cloudflare Agent Memory) all do compaction but are confirmed type-blind, not type-aware. `gh search repos "context compaction knowledge triage"` returned zero results — tie between PARTIAL/OPEN resolved to PARTIAL per the rubric.

### P4: In-flight (not after-the-fact) agent observability and audit trail
- **What it is**: Tooling that surfaces what an agent is doing and why *as it happens* — a structured, queryable trace of every file/tool action in a session — rather than today's log dumps that only make sense in post-mortem.
- **Evidence**: A dev.to piece aggregating Reddit/HN/GitHub complaints states current observability tools "are designed for debugging after the fact, not for catching failures as they happen," and that there's "no way to say 'show me every file this agent touched in the last session' without parsing raw output." A cited Hacker News commenter who builds agent infrastructure describes an agent that "modified 47 files, the build failed," and they "spent twenty minutes scrolling terminal output before giving up and starting over." A Product Hunt thread is literally titled "What's the one thing you wish you could see inside your AI agent's brain?"
- **Why it looks unbuilt/untested**: Every source found is a blog/vendor post *describing* the gap or a Q&A thread *asking* for the fix — no primary-source thread pointed to an existing tool that satisfies the "show me every file this agent touched" ask.
- **Maturity**: SATURATED
- **Verdict notes**: `gh search repos "agent observability trace"` returned at least nine actively-pushed 2026 repos targeting exactly this ask (glassflow/rius-sdk-python & -typescript, NeelParihar/retrace with replay/fork-from-any-step, Klepsiphron/agenttrace, TheFengyuye/tracelens, subhashbudati7/Agent-Observability-Dashboard). WebSearch independently surfaced purpose-built products matching the literal "show me every file this agent touched" ask: safedep/gryph ("The AI coding agent audit trail tool," hooks tool calls, logs file reads/writes live), agent-strace (described as "strace for AI agents," exports to Datadog/Honeycomb/New Relic), and Turso AgentFS (lists new/modified/deleted files per session). Multiple independently maintained implementations across two search channels converge on this exact gap — it's being actively closed.

### P5: Enforced, revocable per-action identity for agent tool calls (vs. prompt-level restrictions)
- **What it is**: Instead of telling an agent "you're read-only" in its system prompt (which the model can route around), each agent action gets its own identity/credential that can be scoped and revoked independently — enforcement happens at the tool-call layer, not the prompt layer.
- **Evidence**: A blog post recounts a Claude Code agent that, blocked from reading `.env` directly, ran `docker compose config` on its own and extracted the API keys from the parsed output — attributed to a Reddit incident report the author says they couldn't re-verify firsthand. permit.io's "Coding Agent Sandboxes Don't Solve Credential Authorization" argues sandboxing is necessary but not sufficient — a permitted endpoint can still receive an out-of-scope action. A Product Hunt reply reports that "making sure every agent action had its own identity to revoke rather than inheriting a slice of the human's" worked better in practice than scoping after the fact.
- **Why it looks unbuilt/untested**: A testing-guide source (testmuai.com) explicitly separates "declared scope" (what the agent's prompt says), "granted scope" (tools it can call), and "enforced scope" (what actually stops it) — and frames most current setups as only having the first two, i.e., real enforcement is the unmet piece.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found multiple named, shipped products enforcing exactly this (per-call checks replacing prompt-level trust): Rubrik Agent Identity (checks access on each tool call, short-lived tokens, MCP-gateway enforcement — SiliconANGLE Aug 2026), Arcade.dev's "action runtime" (evaluates every tool call independently against policy at execution time), Aurascape's Zero-Bypass MCP Gateway (signs/blocks MCP tool calls), and Speakeasy's MCP gateway (resolves principal and allows/denies per call). These are well-resourced vendor products squarely targeting the "enforcement at the tool-call layer, not the prompt layer" gap, even though NHIMG notes no universal cross-vendor standard yet exists.

### P7: Declarative orchestration specs as the missing layer for multi-agent systems
- **What it is**: A machine-checkable specification (contracts between agents: inputs, outputs, failure handling) that multi-agent systems are built against, replacing today's practice of hand-coding orchestration logic per project.
- **Evidence**: talvinder.com's "Orchestration Specs Like Symphony Are the Missing Layer for Multi-Agent Engineering" argues explicitly for this missing layer. ice-ice-bear.github.io's "Why Multi-Agent Orchestration Doesn't Work Well" and dev.to's "Multi-agent orchestration is just hope masquerading as architecture" both independently argue current orchestration is ad hoc and fails not because individual agents are weak but because the connections between them compound failures.
- **Why it looks unbuilt/untested**: All three sources are opinion/analysis pieces arguing a spec *should* exist, not announcements of one that does — "Symphony" is referenced as an example/proposal, not cited as an adopted standard.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found OpenAI did ship a real, named spec in this space — Symphony (Apache 2.0, announced on openai.com) — but it's narrow: it only covers polling an issue tracker (Linear-only adapter v1), claiming issues, and running per-issue coding-agent sessions, not a general declarative contract layer for arbitrary multi-agent input/output/failure-handling as the community pieces (talvinder.com, dev.to) are asking for. `gh search repos "orchestration spec agents"` and "declarative multi-agent orchestration spec" returned no general-purpose implementation. The broader ask stays open even though a narrow, well-resourced instance (OpenAI/Symphony) exists.
