## Candidate patterns

### P1: No enforced, propagating access control at RAG retrieval time
- **What it is**: Document-level permissions (who can see what) are checked, if at all, after retrieval or only in the prompt — not as a hard filter baked into the retrieval query itself — so revoked/restricted source documents keep surfacing through stale index entries, caches, citations, and logs, and a query that is merely semantically adjacent to a restricted document can pull it in even without malicious intent.
- **Evidence**: Multiple independent 2026 vendor/practitioner write-ups (via WebSearch) converge on the same specific failure modes: a tianpan.co post ("The PII Leak in Your RAG Pipeline") frames this as chatbots "knowing things they shouldn't"; a named guide states access-control inheritance is "the most common compliance failure in enterprise RAG deployments"; OWASP guidance is cited stating that system-prompt restrictions on sensitive info can be bypassed by prompt injection, i.e. prompts are not a valid control.
- **Why it looks unbuilt/untested**: The complaint is structural and repeated across independent sources — permission metadata gets lost between source system and chunk, ACL revocations don't propagate to the index/cache, and "agentic RAG" widens the blast radius by chaining retrieved documents into downstream actions — yet every source describing the fix is prescriptive guidance (how it *should* work), not a citation to one maintained, broadly-adopted open-source implementation that does per-chunk ACL-filtered retrieval out of the box.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for `rag access control` / `RAG ACL retrieval` surfaced a dozen+ repos (sagarhande/rag-access-control, elliotaplant/role-based-rag, ssdeanx/secure-rag-multi-agent, AgentPostmortem/VaultRAG, tohfas/RAG-Access-Control, etc.) but every one is a hobby/demo project, max 19 stars, most 0-1 stars and several stale since 2023-2024. Building blocks exist (SpiceDB Zanzibar-style authZ per Pinecone's own tutorial, OpenSearch document-level security) but these are generic authZ/search-engine primitives, not a maintained, broadly-adopted "ACL-filtered RAG retrieval" product — confirms the digest's framing of prescriptive guidance without a shipped reference implementation.

### P2: Embedding-model migration is a full, costly, downtime-prone re-index with no standard zero-downtime tooling
- **What it is**: Switching embedding models (upgrade, deprecation, provider forced migration) requires re-embedding the entire corpus because the new vectors are not comparable to the old ones; teams report six-figure re-index costs, multi-week downtime windows, and "Frankenstein" mixed-vector-space indexes from partial migrations.
- **Evidence**: Independent 2026 blog posts (tianpan.co's "Embedding Refresh" and "Embedding Models in Production" series, DEV Community's "Embedding Model Upgrades Without Re-Indexing," Microsoft's own Azure AI Search guidance on vector drift) all separately describe the same cost/downtime pain and the same mitigations (shadow indexes, pinned model-version metadata, learnable transformation layers to map new query embeddings into the old index's space) — independent convergence on a problem with no single standard tool.
- **Why it looks unbuilt/untested**: One legal-document case cited an 11% nDCG@10 regression after a model swap that looked like an upgrade on public benchmarks (MTEB +4), forcing a rollback — teams are improvising ad hoc shadow-index/rollback processes per-company rather than reaching for a shared migration tool; no maintained open-source "embedding migration manager" was surfaced.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for `embedding migration reindex` / `vector embedding zero downtime migration` returned only 0-star repos (rbumg/reindexer, mgkgopikrishna/veccore, Hkayy47/alembicio). WebSearch confirms the only credible options are vendor-native, narrow features (Weaviate's alias-based zero-downtime migration tutorial, Milvus/Zilliz column-based upgrade) plus one academic method (Drift-Adapter, EMNLP 2025, arXiv 2509.23471) that is a technique, not a packaged tool — no standalone, vendor-agnostic "embedding migration manager" was found anywhere.

### P3: Multimodal RAG (tables, charts, images) is lossy and immature in production
- **What it is**: RAG pipelines that must retrieve over mixed content — tables, charts, scanned PDFs, slide decks — still mostly flatten visuals to text via LLM summarization before indexing, which a cited 2025 arXiv study says causes "substantial information loss" versus direct multimodal embedding; table-structure parsing in nested/multi-column layouts remains error-prone.
- **Evidence**: Independent 2026 sources (tianpan.co's "Multimodal RAG in Production," a genai-systems-lab write-up, bigdataboutique.com, O'Reilly's "Hands-On RAG" Ch. 8) converge on the same complaints: charts/tables "never make it into the index" under text-only RAG, models sometimes hallucinate descriptions of visuals not actually in the retrieved context, and document parsing (distinguishing tables from figures, slide vs. PDF layout) is "insufficiently mature for seamless integration."
- **Why it looks unbuilt/untested**: Sources explicitly call the 2026 toolchain "more cost- and latency-intensive than text-only RAG" and recommend hybrid stopgaps (layout-aware parsing + vision-LLM chart descriptions + hybrid search) rather than pointing to one dependable, broadly-adopted multimodal-RAG library that solves ingestion end-to-end.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple actively-maintained, widely-adopted implementations close this gap: HKUDS/RAG-Anything (24.5k stars, built on LightRAG, handles text/images/tables/equations as first-class entities, pushed same day), docling-project/docling (70.5k stars, actively maintained PDF/table/figure parser), illuin-tech/colpali (2.85k stars, vision-based multimodal retrieval), and SciPhi-AI/R2R (8.1k stars, production RAG engine with multimodal ingestion). Residual info-loss/cost concerns are real per the digest's cited sources, but the "no dependable, broadly-adopted library" claim does not hold up against these stars/activity levels.

### P4: Semantic caching for RAG has unresolved tuning and poisoning risk, not a settled recipe
- **What it is**: Teams cache RAG/LLM responses keyed by embedding similarity to cut repeated-query cost, but threshold tuning is workload-specific and brittle, actual cache hit rates vary wildly (18-60% cited across sources, versus vendor "95%" figures that actually describe match accuracy on hits, not hit frequency), and an attacker able to influence what gets cached could poison responses served to many subsequent users.
- **Evidence**: Independent 2026 practitioner/vendor posts (tianpan.co's "Semantic Caching for LLMs," Percona's and a DEV Community piece's conflicting cost-savings claims, a cited AWS evaluation on 63,796 chatbot queries) disagree on the real-world payoff and explicitly flag the cache-poisoning risk as a known-but-unaddressed concern rather than something with a shipped mitigation.
- **Why it looks unbuilt/untested**: The spread in cited savings (40-80% per one source vs. "may never pay off for some apps" per another) and the explicit, unresolved security caveat (no cited mitigation for cache poisoning) indicate semantic caching for RAG is still a DIY tuning exercise per team, not a commoditized, safely-defaulted layer.
- **Maturity**: PARTIAL
- **Verdict notes**: Basic semantic caching itself is SATURATED as a mechanism (zilliztech/GPTCache, 8.2k stars, LangChain/llama_index-integrated; codefuse-ai/ModelCache, 933 stars), but the specific gap the digest cites — safe, tuning-robust, poisoning-resistant semantic caching — is not closed: an NDSS 2026 paper (Wu et al.) demonstrates a 75% poisoned-hit rate against GPTCache under realistic thresholds and states existing defenses don't fully stop it; proposed fixes (LaCache, arXiv 2608.01718; SAFE-CACHE) are brand-new research proposals, not shipped, evaluated products. A serious, safely-defaulted implementation would be clearly differentiated.

### P5: Contextual retrieval's accuracy gain comes with an unresolved cost/latency tax that teams must solve themselves
- **What it is**: Anthropic's "contextual retrieval" technique (prepending LLM-generated context to each chunk before embedding/BM25-indexing) is cited as cutting top-20 retrieval failure by up to 49% (67% with reranking added), but generating that per-chunk context at index time is described as "highly resource-intensive," and prompt caching is the only commonly-cited mitigation.
- **Evidence**: Anthropic's own engineering post states the headline failure-rate reductions; secondary 2026 sources (freeCodeCamp, Omdena, GradientFlow, PromptLayer's glossary) repeat the technique approvingly but one explicitly flags that LLM-based chunk expansion "significantly increas[es] both costs and processing times," with only Anthropic's own cookbook offered as a reference implementation.
- **Why it looks unbuilt/untested**: No WebSearch result surfaced independent production-adoption data, a cost-calibrated decision framework for when contextual retrieval is worth its indexing cost, or any implementation beyond Anthropic's own cookbook — the technique is well-publicized but its cost tradeoff is still something every adopter is left to work out alone.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for `contextual retrieval` turned up several reproductions (autollama/autollama, 33 stars, stale since 2025-09; NeuralVulture/contextual-retrieval-by-anthropic, 28 stars, stale since 2024-09; kakopappa/contextual-retrieval-demo) — all small, abandoned demos, not maintained tooling. WebSearch found Denser AI's open-model reproduction (swapping in bge-en-icl/local reranking) but no independent cost-calibrated adoption framework beyond Anthropic's own cookbook, confirming the digest's claim.

### P6: No widely-adopted open-source router for "RAG vs. stuff-the-full-context" decisions
- **What it is**: Rather than always retrieving, some queries are better served by dumping relevant documents straight into a long-context model's window — but deciding which approach to use per query, instead of locking into one architecture, is still mostly a research-prototype-level capability.
- **Evidence**: A May 2026 arXiv paper ("Route Before Retrieve," Pre-Route) argues the established precedent (Google's "Self-Route") always tries RAG first as a fallback rather than deciding up front; a cited 2026 benchmark found long-context prompting scored higher on correctness but "at 26 times the per-query token cost" of RAG, while another found RAG overtakes long context above roughly 128K tokens for most open models.
- **Why it looks unbuilt/untested**: WebSearch found real research precedent (Self-Route, Pre-Route) and vendor blog commentary describing simple heuristic routers ("a small fast model classifies the query"), but no clear, widely-adopted open-source reference implementation that teams can drop in — routing logic is currently re-derived per-team from heuristics or left unaddressed (always-RAG or always-long-context).
- **Maturity**: OPEN
- **Verdict notes**: GitHub search for `RAG vs long context router` / `self-route RAG` / `context window router retrieval` found only one repo (Rahulraj31/Self-Route-Rag-Longcontext-ADK, 0 stars, a personal reproduction of the Self-Route paper). WebSearch confirmed only research precedent (Self-Route/arXiv 2407.16833, Route Before Retrieve/arXiv 2605.10235, RAGSmith/arXiv 2511.01386) and vendor-blog mentions of ad hoc heuristic routers — no widely-adopted open-source reference implementation exists; genuine multi-channel search came up empty beyond papers and a one-off hack.

### P7: "We wanted to build an AI application, not maintain RAG pipelines" — RAG infra maintenance fatigue
- **What it is**: Builders complain that the ongoing maintenance burden of running a RAG pipeline (ingestion, chunking, indexing, re-indexing, retrieval tuning) competes directly with time spent on the actual application logic, and some are explicitly building/seeking ways to make retrieval a solved, maintenance-free substrate instead of DIY infrastructure.
- **Evidence**: Hacker News Show-HN post "We wanted to build an AI application, not maintain RAG pipelines" (2026-11-10, 3 points, 1 comment, surfaced directly by the last30days engine run) states this complaint as its own framing/title. A second, same-run HN item ("Db4 is open source: local RAG on Postgres in a browser tab," 2026-10-21, 3 points) is an independent, low-engagement attempt at the same "make RAG infra disappear" goal via embedding retrieval directly into an existing datastore.
- **Why it looks unbuilt/untested**: Both pieces of evidence are single-author, low-engagement Show-HN launches (3 points each) rather than citations to an established, broadly-adopted "RAG infrastructure that gets out of your way" product — the complaint recurs but the fixes on offer so far are tiny, unproven, single-maintainer projects.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch for `"managed RAG" OR "RAG as a service"` found well-resourced, shipped managed products squarely targeting exactly this complaint: Amazon Bedrock Managed Knowledge Base (GA June 2026, full ingestion/parsing/chunking/embedding/rerank pipeline with SharePoint/Confluence/Drive/S3 connectors), Vectara, Google Vertex AI RAG Engine, Azure AI Search, and Pinecone Assistant. The two cited single-maintainer Show-HN launches are not the only response to this gap — large vendors have already made RAG infrastructure "disappear" as a managed offering (one smaller competitor, Ragie, reportedly shut down per one source, but the major cloud players remain active).
