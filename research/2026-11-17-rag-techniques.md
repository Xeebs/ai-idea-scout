## Candidate patterns

### P1: Adaptive/router RAG — a query classifier picks the pipeline per request
- **What it is**: Instead of one fixed RAG pipeline, a lightweight classifier inspects each incoming query and routes it to a cheap single-shot retrieval path for simple lookups or an expensive multi-hop/agentic path for ambiguous, multi-source questions.
- **Evidence**: Taskade's agentic-RAG writeup frames this as the direct response to developers hitting "the ceiling of classic RAG: brittle retrieval, poor multi-hop reasoning, hallucination when the first-shot retrieval missed." Starmorph's guide names "Adaptive RAG" as the 2026 emerging best practice and quantifies the tradeoff it's solving: an agentic pipeline runs "about 10x the cost of naive RAG and adds roughly 5 seconds of latency." Lyzr's pattern catalog lists Router agent / Corrective RAG / Self-RAG / Adaptive RAG / Agentic GraphRAG as the six recurring shapes.
- **Why it looks unbuilt/untested**: All evidence is vendor-blog prescription ("the best practice is...") rather than a maintained, benchmarked reference implementation; no GitHub repo or HN discussion in this run's evidence shows a widely-adopted router actually in production with measured cost/accuracy numbers.
- **Maturity**: SATURATED
- **Verdict notes**: This is a textbook pattern, not a gap. The original Adaptive-RAG paper (Jeong et al., NAACL 2024) plus a dedicated 2026 academic baseline study (arXiv 2604.03455, "RAGRouter-Bench") already benchmark exactly this classifier-routing idea. `gh search repos` for "adaptive rag router" returns dozens of implementations (e.g. `vikrant-sahu/Adaptive-RAG-Router-`, `limda8194/adaptive-rag-router`, `jayy1506/Adaptive-Rag-Router`) plus a second cluster combining Adaptive/Self/Corrective RAG (`Md-Emon-Hasan/All-Types-Retrieval-Augmented-Generation-RAG`, `Adarsh-Menon/Argus-Arch`). LangGraph and vector-DB vendors (Actian, Fareed Khan's architecture catalog) ship official adaptive-RAG tutorials. Individual repos are low-star/student-tier, but the combination of a peer-reviewed paper, a named 2026 benchmark, and official framework tutorials means the gap the community describes is already closed by well-resourced parties, not merely discussed.

### P2: Chunking-specific RAG evaluation metrics (eval frameworks grade the wrong thing)
- **What it is**: Current RAG eval tooling measures end-to-end answer quality but has no metric isolated to chunking quality, so teams can't tell whether a failure is the chunker, the retriever, or the generator.
- **Evidence**: A GitHub issue from `funshothanni/marginalia` ("RAG Evaluation", 2026-11-06, score 2 in the engine's ranking) explicitly asks to build "a testing system that measures: Retrieval accuracy, Answer relevance, Citation correctness, Hallucination frequency, Response latency" — i.e., this doesn't exist yet in their stack. A dev.to post titled "Your RAG eval is grading the chunker, not the retriever" argues eval sets built from the same chunker being tested make chunking failures invisible. The Nixiesearch Substack post "How [not] to evaluate your RAG" says the team "fell back on hands-on, trial-and-error testing" because mainstream frameworks offered no chunking-specific metrics. The one open-source attempt found, `leo310/rag-chunking-evaluation`, has "very little adoption, with 1 star and no open issues."
- **Why it looks unbuilt/untested**: The one GitHub repo built for exactly this has 1 star and zero issues (effectively unused); the Tencent HiChunk arXiv paper (2509.11552) independently confirms "existing RAG benchmarks don't properly assess chunking quality," meaning both industry practitioners and academics are naming the same gap from different directions with no converged tool.
- **Maturity**: PARTIAL
- **Verdict notes**: Mature, widely-used general RAG-eval frameworks exist and are maintained (RAGAS, TruLens, DeepEval — confirmed via WebSearch comparison pieces and `gh search repos` turning up a dozen current eval-framework repos like `2501Pr0ject/RAGnarok-AI` and `mcello23/llm-evaluation-framework-example`), but all of them score faithfulness/answer-relevance/context-precision/recall end-to-end and none isolates a chunking-specific metric — multiple 2026 vendor posts explicitly note chunk answerability/boundary-loss metrics are DIY, not framework built-ins. The one dedicated attempt (`leo310/rag-chunking-evaluation`) remains at 1 star with no issues. Real, converged gap; a serious build would be differentiated from the incumbents rather than redundant with them.

### P4: Per-feature long-context-vs-RAG decision engine ("context engine")
- **What it is**: Rather than picking RAG or long-context stuffing architecture-wide, a runtime component decides per feature (or per query) whether to retrieve-and-rerank or just stuff the context window, based on corpus size, freshness needs, and cost ceiling.
- **Evidence**: tianpan.co's "Long-Context vs RAG in 2026: Why It Is a Per-Feature Decision, Not an Architecture Religion" and a companion post describing "a 'context engine' — an intelligent system that decides what information to load into the model's context window." A cost study cited via WebSearch reports long-context prompting beat semantic RAG on correctness (73.1% vs 65.4%) but cost "26 times as much per query" (unverified numbers, flagged as such in the search). Redis's engineering blog frames the split as accuracy/traceability/cost (RAG) vs. full-document understanding (long context).
- **Why it looks unbuilt/untested**: Every source describing the "context engine" concept is a blog post proposing the idea, not a shipped, named tool; no GitHub repo or product surfaced implementing the per-feature decision logic itself (as opposed to one-off hybrid pipelines built ad hoc per team).
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed via WebSearch that "context engine"/"context runtime" is a live but unconverged label — a Hugging Face community post describes an open-source "Context Runtime" doing retrieval/memory/model-routing/planning, and `gh`-adjacent search turned up small, narrow projects using the same framing (`melandlabs/opencontext` ~50 stars, `CIGAR` governed-context-runtime, `lean-ctx`), none of which specifically implements the per-feature RAG-vs-long-context decision this pattern describes — they're adjacent context-assembly tools, not this decision engine. Chalk.ai's "context engine" product is about customer-data assembly at inference time, not the RAG/long-context choice. Real but fragmented gap: pieces exist, nothing converged squarely on this decision.

### P7: Retrieval-architecture-over-embedding-model as the real accuracy lever
- **What it is**: A counter-intuitive finding surfacing in practitioner writeups: swapping embedding models produces little to no measurable accuracy change, while retrieval pipeline architecture (chunking, reranking, hybrid search) is what actually moves results — contradicting the common assumption that "better embeddings" is the first lever to pull.
- **Evidence**: dev.to post "I spent 3 days on a RAG pipeline and the embedding model didn't matter at all." Superlinked's chunking/retrieval evaluation (via WebSearch) independently found "simple methods like SentenceSplitter outperform complex ones like SemanticSplitterNodeParser, and reranking gave consistent gains" — i.e., chunking/reranking choices dominated over embedding choice in their tests too.
- **Why it looks unbuilt/untested**: No converged guidance or tool yet tells builders which architectural levers to prioritize over embedding-model shopping; each writeup is an individual team's isolated finding, not a benchmarked, reusable decision framework.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found substantial academic benchmarking already underway on this exact question: a 2026 empirical eval ("Chunking, Retrieval, and Re-ranking," arXiv 2601.15457), a 36-strategy/6-domain/5-embedding-model chunking benchmark (1,080 configs), and a systematic review (arXiv 2507.18910) all independently show chunking/reranking choices dominate over embedding-model choice. So the underlying finding is being actively studied, not purely anecdotal — but no source converts this into a reusable, benchmarked decision tool/framework for builders; it remains scattered ablations and isolated blog posts. Real gap for a practical tool, not for the finding itself.
