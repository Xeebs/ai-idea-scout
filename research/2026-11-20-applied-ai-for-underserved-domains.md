## Candidate patterns

### P1: Offline/low-bandwidth local LLM assistants for community health workers
- **What it is**: Lightweight, locally-run LLM assistants (small quantized models via tools like Ollama, or fine-tuned lightweight dialogue models) for community health workers (CHWs) in low-connectivity areas, often paired with a "tiered backbone" that shrinks data footprint on poor networks and falls back to offline mode for core tasks.
- **Evidence**: dev.to "NiDaan" write-up (India) — solo developer built an offline diagnostic assistant on Ollama with a small local model citing unreliable rural internet, then switched to Groq llama-3.1-8b-instant to get response time to 12 seconds; a Nepal-focused arXiv paper (2511.00514) fine-tuned DialoGPT as a lightweight offline-capable model for low-resource clinical settings; Last Mile Health's 2026 guidance explicitly calls for "designing for low-power, offline reality"; a Purdue graduate thesis proposes a phone-call-based voice assistant for low-bandwidth rural healthcare; a lablab.ai hackathon entry built a "low-bandwidth chatbot for healthcare in rural areas." All found via the "rural healthcare worker AI chatbot offline low connectivity" WebSearch, 2026-11-20.
- **Why it looks unbuilt/untested**: every example is a solo-developer build, student thesis, or hackathon entry — no maintained, multi-deployment product. The NiDaan piece and Purdue thesis each independently frame themselves as solving the "constant internet / heavy UI" problem from first principles, implying no shared, reusable offline-first CHW assistant framework exists for others to build on.
- **Maturity**: PARTIAL
- **Verdict notes**: Real builds exist at varying scale, most notably Google/Crane AI Labs' EaseHealth — a fine-tuned on-device MedGemma 4B app for Ugandan CHWs, feasibility-tested across 15 facilities with 268 health workers and 87+ fully-offline assessments (per Google's HAI-DEF showcase) — plus the SHIFA GitHub repo (Mist-Labs, multi-country humanitarian scope, 0 stars, low activity), Microsoft Research/Khushi Baby's ASHABot (published but WhatsApp/online, not offline), and several hackathon/solo-dev entries (NiDaan, ZafyaLM, AfyaPack). Even Google's effort is explicitly "under clinical validation" and narrow to one country's guidelines, not a reusable framework — no shared, maintained open-source offline-first CHW assistant platform surfaced.

### P2: Translation-layer wrapper instead of a native low-resource-language LLM
- **What it is**: Pairing an existing general-purpose or medical LLM with a separate machine-translation (MT) model to serve a low-resource language, instead of training or fine-tuning a dedicated model in that language — chosen explicitly because a native model is judged too costly for low-resource settings.
- **Evidence**: A Gates Foundation grant page describes a Rwanda malnutrition-support tool pairing a translation model with GPT-4 for Kinyarwanda-speaking CHWs, stated explicitly to avoid building a language-specific LLM that would be "too expensive for low-resource nations"; the L2M3 arXiv paper (2404.08705) frames itself around pairing MT with an LLM for CHWs in low- and middle-income countries; ITU's 2026 "AI for Good — Innovate for Impact" interim report flags MT-based approaches as "susceptible to inaccuracies, particularly with complex content." Found via the translation WebSearch query, 2026-11-20.
- **Why it looks unbuilt/untested**: ITU's report and a separate case on Tetun medical translation (Maluk Timor, Timor-Leste) both state that MT output "typically requires substantial post-editing" — the pattern is in active use, but every cited instance is self-described as accuracy-limited and none reports a solved, evaluated post-editing workflow.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for "translation LLM low resource language health" returned nothing; WebSearch found only paper-stage work (L2M3, no public repo), one real funded pilot (Gates Foundation Rwanda/Kinyarwanda malnutrition tool pairing MT with GPT-4), and OpenWHO (public repo github.com/raphaelmerx/openwho-code — a health translation corpus, not an MT+LLM deployed product). ITU's 2026 report and a Tetun medical-translation case both describe MT output as still needing substantial post-editing — no cited instance reports a solved, evaluated post-editing workflow.

### P3: Community-curated low-resource-language benchmark datasets for frontline use
- **What it is**: Benchmark datasets for machine translation into specific minority/tribal languages that are curated by community members rather than only researchers, intended to eventually feed frontline health/education AI tools.
- **Evidence**: "AdiBhashaa: A Community-Curated Benchmark for Machine Translation into Indian Tribal Languages" (arXiv 2512.04765), found via the same translation-focused WebSearch query, 2026-11-20, names translation support for frontline health and education workers as a prospective downstream use.
- **Why it looks unbuilt/untested**: the paper describes a benchmark only — no cited tool or deployment actually consumes it yet; the frontline use case is explicitly framed as "possible," under discussion, not implemented.
- **Maturity**: PARTIAL
- **Verdict notes**: The benchmark-creation half of this pattern is becoming well-covered — besides AdiBhashaa (arXiv 2512.04765, IIT Delhi, ~80k Hindi-tribal pairs across 4 languages), there's also BHEPC (110k Bhili-Hindi-English sentences) and the MMLoSo 2025 shared task built on the same data. But the "feeds frontline health/education AI tools" half is still prospective in every source found — no cited deployment actually consumes any of these benchmarks yet, so a build that closes that integration gap would be differentiated.

### P4: Voice/IVR-first AI assistants bypassing app UI for low-literacy or low-smartphone populations
- **What it is**: AI health assistants delivered as a phone call or voice interface instead of a smartphone app or chat UI, targeting users with low literacy or limited smartphone access.
- **Evidence**: MIT Solve entry "AI Assisted Healthcare Workers with Myna Bolo ('Speak' in Hindi)"; a Purdue thesis proposing a phone-call-based AI voice assistant for low-bandwidth rural healthcare environments. Both found via the "has anyone built" and "offline connectivity" WebSearch queries, 2026-11-20.
- **Why it looks unbuilt/untested**: both are early-stage — an MIT Solve competition entrant and an unpublished graduate thesis prototype, not deployed products; no maintained open-source voice-first CHW assistant surfaced in either search.
- **Maturity**: SATURATED
- **Verdict notes**: Two independent, well-resourced, actually-deployed (not hackathon) products squarely cover this gap: Viamo's "Ask Viamo Anything" generative-voice layer on its existing IVR platform, piloted in Zambia and documented by a March 2025 GSMA case study plus an independent academic article on uptake among women/youth; and Sarvam's voice agents, used by India's National Health Authority for PM-JAY scheme awareness, reaching ~1.4M citizens without requiring smartphones (vendor-reported). Both are purpose-built for low-literacy/low-connectivity populations, which is exactly this pattern.

### P5: "Community rejects existing tools first" co-design loop
- **What it is**: A workflow where a project explicitly asks its target community to evaluate existing AI health tools before building anything, documents an outright rejection, and only then builds a new tool with residents as active co-designers — rebuilding core infrastructure (e.g., connectivity handling) based on what that evaluation surfaced.
- **Evidence**: Springer Nature "Building a primary care chatbot with people, not for them" — the team asked community members whether existing AI health tools would help and "got a clear 'no,'" then found their own prototype "unusable" on local networks before rebuilding with a tiered/offline backbone alongside resident co-designers. Found via the "has anyone built AI tool underserved community" WebSearch, 2026-11-20.
- **Why it looks unbuilt/untested**: reported as a single case study, not packaged as a repeatable methodology — no generalized "reject-first co-design protocol" or toolkit for AI-in-underserved-health projects was found elsewhere in the search.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed as a single documented case (Springer Nature "Building a primary care chatbot with people, not for them," China, dual-track role-play co-design framework, reportedly validated in an RCT of 2,100+ participants) — real and evaluated, but a one-off, not generalized. Two further targeted searches found no packaged "reject-first co-design protocol" or toolkit anywhere else (only unrelated co-design studies for LGBTQ+ teen sexual health and rural mental-wellbeing chatbots) — a productized, reusable version of this methodology would be differentiated.

### P6: AI-assisted accessibility auditing beyond automated WCAG scanning
- **What it is**: Tooling that goes beyond automated WCAG scanners — using AI (e.g., multimodal description generation) to assess real screen-reader/switch/voice-control usability rather than just markup compliance — to catch the failure classes automated testing structurally misses.
- **Evidence**: WebAIM's 2026 report (cited via an IT Brief Australia piece) found automated testing "detects only about 30% to 40% of WCAG success criteria failures," against 95% of the top 1,000,000 homepages having at least one WCAG failure; a Salesforce blog frames the accessibility gap as "a gap in process," not technology; a Cognizant piece says multimodal AI is "beginning to close that gap" by generating spoken descriptions of visual content in real time. Found via the "disability accessibility AI assistive technology gap" WebSearch, 2026-11-20.
- **Why it looks unbuilt/untested**: the cited sources describe the 60-70% automated-testing blind spot as still open and "beginning to close" — explicitly unsolved; no specific shipped tool is named as actually closing that gap, only directional vendor framing.
- **Maturity**: PARTIAL
- **Verdict notes**: One research prototype (ScreenAudit, arXiv 2504.02110 — LLM-driven Android TalkBack checker, validated against 6 experts incl. a blind screen-reader user, outperforming existing rule-based checkers) and one vendor product announcement (AudioEye "Agentic Audits"), but a University of Maribor paper concludes LLM auditors "lack the stability and accuracy required to properly support human accessibility auditing," and Silktide's 2026 commentary says no scanner can yet judge whether alt text makes contextual sense — the 60-70% automated-blind-spot gap this pattern targets remains explicitly open per these sources.

- **Evidence**: AFB's March 2026 report "The AI Quagmire" found more disabled than nondisabled job seekers reported difficulty with automated tests/interviews, including having to turn off assistive technology to use the AI system, and states that accessibility-barrier risks from AI hiring tools "have not yet been fully explored." Found via the accessibility-gap WebSearch query, 2026-11-20.
- **Why it looks unbuilt/untested**: AFB itself frames this as an open, unexplored risk area; the search surfaced no counter-example of an AI hiring tool built accessible-by-default.
- **Maturity**: PARTIAL
- **Verdict notes**: Found guidance (WCAG 2.2 baseline, DOL/ODEP/EARN/PEAT eRecruiting checklist) and one vendor claim (Sapia.ai's chat-based, untimed interview format marketed as fairer for disabled candidates) but no vendor-independent test data, no certification standard, and no counter-example of a comprehensively accessible-by-default AI hiring pipeline. AFB's own framing of this as unexplored holds up under search — one narrow, self-reported vendor claim keeps this at PARTIAL rather than OPEN.
