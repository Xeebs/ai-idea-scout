## Candidate patterns

### P1: Standardized agent-memory interoperability protocol ("OpenTelemetry moment for agent memory")
- **What it is**: A proposed shared standard for agent memory — a data model, semantic conventions, a wire protocol, and conformance tests — modeled explicitly on how OpenTelemetry unified observability in 2019, so memory written by one agent/tool can be read by another instead of being locked into incompatible formats.
- **Evidence**: Hacker News "Agent memory needs its OpenTelemetry moment" (191 pts, 110 comments, 2026-11-08, https://www.lorekit.io/blog/open-agent-memory-format) — per secondary summary, proposes four shared layers while leaving storage/retrieval/embeddings competitive; TechBytes coverage (2026-11-08) frames the motivation as: coding tools store memory in incompatible formats today — AGENTS.md, Anthropic memory files, Copilot facts, and MCP JSONL stores — that "can't read each other."
- **Why it looks unbuilt/untested**: A commenter on the thread pushes back that "the moment isn't here yet," calling it "a solution looking for a problem" and arguing storage should stay invisible to agents — i.e. even the top discussion of this exact idea is split on whether it should exist yet, and no shared protocol has converged.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for "agent memory protocol" surfaced 10+ independent repos all reusing the name "AMP"/"Agent Memory Protocol" (LeoYeAI/talewell 550★, akshayaggarwal99/amp 31★, smriti-memcore/amp 13★, mmorris35/agent-memory-protocol 8★, deep-thinking-lab/open-agent-memory-protocol, agentmemoryprotocol/agentmemoryprotocol, etc.) — none dominant, none interoperating with each other, confirming fragmentation rather than convergence. WebSearch found early-stage standards process (W3C "AI Agent Memory Interoperability Community Group," chartered July 2026; an IETF "agentproto" BoF at IETF 126, July 2026; arXiv preprints memorywire 2606.01138 and MemTools 2607.21404) — all unfinished, none adopted. Implementations exist but are competing, non-interoperable, and the community itself (per P1's own HN thread) disputes whether the standard should exist yet — a real gap, not yet closed.

### P2: Sub-agent context isolation paired with a consistency-reconciliation layer
- **What it is**: Splitting exploratory/messy work (search, backtracking, failed attempts) into isolated sub-agent context windows that each return only a short digested answer to a lead agent, keeping the lead agent's own context clean — but without an established mechanism for reconciling inconsistencies this isolation introduces across sub-agents.
- **Evidence**: WebSearch-sourced engineering blogs (tianpan.co, "Four Strategies for Engineering Agent Context"; levelup.gitconnected, "why more context makes AI coding agents worse") describe sub-agents doing messy search/backtracking in their own windows and handing back ~150-token answers; blogs cite (unverified, single-vendor-sourced) an Anthropic multi-agent result of a 90.2% performance improvement attributed to the lead agent's context staying clean.
- **Why it looks unbuilt/untested**: One of the sourced guides explicitly states "isolation solves the context length problem but creates a consistency problem" with no named production-ready resolution; the headline 90.2% figure could not be verified against Anthropic's own primary publication in this search.
- **Maturity**: OPEN
- **Verdict notes**: GitHub search for "agent context reconciliation" and "subagent merge conflict resolution" returned zero results. WebSearch found plenty of coverage of isolation itself (Claude Code sub-agents, Cursor 2.0's 8-parallel-agent git-worktree isolation) but no named, packaged "reconciliation layer" — only scattered, unimplemented practitioner suggestions in blog comments (a DEV.to commenter floating a "lightweight conflict-detection step before merging," another suggesting verification sub-agents propose patches rather than edit directly) and a March 2026 aggregator noting "empirical evidence is thin" on whether isolation's benefits even clear its coordination overhead. Genuine multi-channel search found only discussion and unbuilt suggestions, not an implementation.

### P3: Threshold-triggered proactive context compaction (compact before rot sets in, not after)
- **What it is**: Instead of compacting a context window reactively once it's nearly full, trigger compaction proactively at a fixed point (e.g. ~70% of the effective window) — before context rot degrades the content being summarized — and reserve compaction specifically for preserving reasoning across long dialogues, using tool-result clearing as the primary everyday mechanism.
- **Evidence**: WebSearch-sourced production guide (via "context rot compaction sub-agent isolation technique 2026" query) recommends the ~70%-of-window compaction trigger "because once context rot sets in, the summary will itself be degraded"; the same search surfaced that Anthropic reportedly shipped a Compaction API with Claude Opus 4.6 (March 2026, per secondary source).
- **Why it looks unbuilt/untested**: The 70% threshold is presented as hard-won, ad hoc practitioner advice in a single production guide rather than a built-in adaptive feature most agent frameworks expose — teams appear to be reimplementing their own fixed thresholds from scratch.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found this is now a standard, shipped feature across multiple maintained frameworks: Everruns (proactive compaction at 85%, configurable), Inspect/AISI (default 0.9 threshold, multiple strategies, built into ReAct agent), Hermes Agent (default compressor fires at 50%, pluggable), kaged (two-threshold design, ADR-0024), Aura (auto-compacts at 80% default), and OpenClaw (pre-prompt pressure estimate). GitHub also surfaced dedicated repos (elci-group/compactd "proactive context compaction daemon," tutu359/pi-auto-compact "configurable threshold, dedicated compaction model"). The specific 70% number in the digest is just one threshold choice among several already shipped (50-90% across these tools); the general pattern — proactive, threshold-triggered compaction instead of reactive — is already closed by well-resourced, actively-maintained frameworks.

### P6: Offline "dreaming" memory-consolidation pass that judges salience and writes structured notes between sessions

- **Evidence**: Per secondary summaries of Anthropic's "The Components of Agent Memory" (published 2026-11-06, https://www.anthropic.com/research/components-of-agent-memory; surfaced by the engine as an HN item at 189 pts/105 comments): prompting Sonnet 4.6 to read its memory files and test its theories "nearly doubled" its CL-Bench score, and a dreaming-built wiki raised one test from 13% to 48% of graded criteria.
- **Why it looks unbuilt/untested**: Both headline figures come from Anthropic's own single-run evaluations on its own research blog — not independently reproduced — and secondary coverage explicitly flags "I couldn't confirm elsewhere," indicating thin independent corroboration of the mechanism outside Anthropic's own platform.
- **Maturity**: PARTIAL

### P7: Dynamic "tool loadout" scoping to prevent tool-choice confusion as a context failure mode
- **What it is**: Rather than exposing an agent's full tool catalog on every step, dynamically scope down to a minimal, task-relevant subset of tools per step — one of several named remedies (alongside quarantine, pruning, offloading, summarization, augmentation) for the "confusion" failure mode where too many available tools degrades an agent's tool-selection accuracy.
- **Evidence**: Per an ai-tldr.dev summary (2026-10-24) of Drew Breunig's AGNTCon talk, also surfaced by the engine as Hacker News "The State of Context Engineering" (275 pts, 67 comments, 2026-10-25, https://www.dbreunig.com/2026/10/24/the-state-of-context-engineering.html): names four long-context failure modes (poisoning, distraction, confusion, clash) and lists "tool loadout" as a remedy, illustrated as "about 16 lines" of changes to a DSPy agent.
- **Why it looks unbuilt/untested**: The only implementation detail available is a demo-scale, ~16-line DSPy example in a conference talk writeup — not a reusable, generalized mechanism that automatically determines the right tool subset per step across arbitrary agent frameworks.
- **Maturity**: PARTIAL
- **Verdict notes**: More mature than the digest's "16-line demo" framing suggests — kyegomez/swarms (7,372★, actively maintained, pushed today) ships a real `dynamic_tools=True` option with a `tool_search` mechanism and plan-based preloading (`swarms/tools/dynamic_tool_loader.py`); Slite's engineering blog describes a production progressive tree-based loader reporting -23% cost/-12% latency; arXiv's AutoTool (2512.13278) proposes a learned anchor-token tool-selection mechanism. But each solution is tied to one specific framework/product (Swarms) or one company's internal stack (Slite) rather than being a portable, generalized mechanism usable across arbitrary agent frameworks — the exact gap the digest names remains real even though the narrow pattern itself is not unbuilt.
