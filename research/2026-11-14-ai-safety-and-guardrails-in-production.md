- **Evidence**: GitHub PR, `dsailajakrishna0-ship-it/customer-compass-v3` #77, "Stage 5.3: guard comparison (rules, classifier, Llama Guard, NeMo Guardrails) and an optional Presidio PII guard" (2026-11-13): "compares our rule-based guard with our LLM classifier, Llama Guard 4 and NeMo Guardrails on one bigger adversarial set... prints one results table (detection rate, false positives, latency)."
- **Why it looks unbuilt/untested**: This is a one-off, single-repo harness being built from scratch rather than adopted off the shelf — no existing open benchmark surfaced in the same run that lets a team drop in their own prompt set and get a standardized detection/false-positive/latency table across the popular guard options. The HN-sourced complaint (P3 below) about not knowing "what's going on" in an LLM pipeline reinforces that teams lack a reusable, vendor-neutral eval harness for this exact comparison.
- **Maturity**: PARTIAL
- **Verdict notes**: Real benchmarking work exists — an academic SoK (arXiv 2506.10597) framing security/efficiency/utility tradeoffs, a GuardBench pre-deployment framework (4,200 jailbreak prompts, reports ASR/FP/P95 latency with CIs), and a vendor benchmark site (Artificial Analysis, in partnership with NVIDIA, plotting F1 vs. latency across guards) — but none of these is a self-service tool a team can run with its own prompt set. The one GitHub project matching that exact shape, `Virtue-Research/guard-eval-harness`, has only 19 stars and was last pushed 2026-06-26, confirming the digest's framing that no adopted, reusable drop-in harness exists yet.

- **Evidence**: GitHub issue, `eslam-aboutaleb/ai-fullstack-roadmap` #43, "[P0][Content] AI safety beyond authorization: moderation, fairness, red teaming and release gates" (2026-10-21): "Strong current authorization/prompt-injection content is not equivalent to full AI safety engineering... without conflating application permission checks with m[odel safety]."
- **Why it looks unbuilt/untested**: The issue is explicitly framed as a roadmap gap to be filled — i.e., it's flagging that a clear, practical reference distinguishing input/authorization guardrails from moderation/fairness/red-teaming/release-gating doesn't exist yet in the project it's filed against, and (per the issue author) more broadly in available educational content.
- **Maturity**: PARTIAL
- **Verdict notes**: Pieces of this taxonomy exist (MIT's AI Risk Mitigation database cataloging 831 mitigations from 13 frameworks, the WEF Presidio AI Framework, NIST AI RMF, scattered vendor blog posts like getmaxim.ai's "AI Safety Stack") but WebSearch found no single canonical, practical reference that cleanly separates authorization/prompt-injection guardrails from moderation, fairness, red-teaming, and release-gating the way the issue calls for — the material is fragmented across academic taxonomies and vendor marketing rather than consolidated into one operator-usable guide.

- **What it is**: The pattern of routing all LLM calls through a self-hosted proxy layer specifically so a team can see and control what's actually happening (prompts, responses, tool calls) rather than trusting a vendor's dashboard or no instrumentation at all.
- **Evidence**: Hacker News, "If you don't run your own LLM proxy, how do you know what's going on?" (2026-10-18, 303 points, 220 comments) — a high-engagement complaint-shaped thread. Reinforced by a second, lower-engagement HN Show: "Log every LLM call with tokens, cost, latency, and time to first token" (2026-11-11, 10 points, `github.com/garritfra/llmtee`), i.e., someone hand-built a logging tool to fill the same gap.
- **Why it looks unbuilt/untested**: 220 comments on the "how do you even know" thread signals this is a widely-felt gap, not a solved problem, and the Show HN logging tool is a narrow one-off script (single repo, no guardrail/policy layer attached) rather than an integrated proxy+guardrail+observability stack.
- **Maturity**: SATURATED
- **Verdict notes**: The self-hosted-proxy-for-observability/control pattern itself is covered by multiple large, actively-maintained open-source products: `helicone/helicone` (6,280 stars, Apache-2.0, YC W23, pushed 2026-11-12, one-line self-hosted proxy logging prompts/responses/cost), `langfuse/langfuse` (37,418 stars, MIT, pushed 2026-11-14, self-hostable AI gateway + observability built on OpenTelemetry), and `BerriAI/litellm` (63,242 stars, pushed 2026-11-14, self-hosted proxy for every LLM call). The specific gap (seeing/controlling what's happening without trusting a vendor dashboard) is squarely closed by well-resourced, continuously-shipped teams, even though tight guardrail-policy integration on top of the proxy layer varies by product.

### P4: Formal/legalese-register prompt injection as a guardrail blind spot
- **What it is**: An attack technique where injected instructions are phrased in dense legal/contractual jargon ("lawyerspeak") specifically because guardrails tuned to detect casual jailbreak phrasing don't flag formal-register text as suspicious.
- **Evidence**: Hacker News, "Prompt Injection, Esq.: pwning AI agent guardrails with lawyerspeak" (2026-11-11, 3 points) — low engagement but a concrete, named novel bypass technique with a write-up (`mrnice.dev/posts/heavyweight-guardrails`).
- **Why it looks unbuilt/untested**: Low HN point count suggests this is freshly surfaced, not yet widely discussed or defended against — no corresponding guard/detector for register-shifted injection text turned up elsewhere in this run's evidence (the P1 multi-guard harness list — rules, classifier, Llama Guard, NeMo Guardrails — doesn't name register-aware detection as a category it tests).
- **Maturity**: OPEN
- **Verdict notes**: WebSearch for jailbreak/prompt-injection detectors tuned to formal/legal register came up empty — Meta's Prompt Guard 2, a 0DIN SusFactor classifier paper, Vektor-Guard v2, and the P1 Hybrid Jailbreak Detector are all general classifiers with no mention of legal-jargon or formal-register as a tested category, and the 0DIN paper itself notes technique-oriented detectors (0.657 AUROC on WildGuardTest) degrade on semantically natural-sounding jailbreaks — consistent with this being a genuinely unaddressed blind spot, not just undiscussed.

- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found a scattered set of narrow, early-stage scanners aimed at exactly this vector — InjectScan (hidden-HTML + MCP tool-poisoning scanner), Palisade Scanner (PyPI, flags CSS-hidden text), Trap Scout, an "Injection Detection" pip tool, a Chrome extension (InjectGuard), an Apify actor, and `Vick606/subcanopy-guard` (new, 2026-11-12, claims 86.5% on AgentDojo v1) — plus Google's own April-2026 billion-page indirect-injection crawl (reported by Decrypt). None of these is a widely-adopted, maintained standard a team would reach for by default; most are single-author, unverified, or very recent, so the real-world gap the HN thread surfaced is still live even though prior art now exists.

### P8: Using an LLM to self-score its own confidence/safety as an anti-pattern
- **What it is**: The widespread technique of asking the same LLM "how confident are you in this answer" (or using it to self-rate potential harm) as a cheap substitute for calibrated confidence or a separate safety classifier.
- **Evidence**: Hacker News, "Using LLM for confidence scoring is a bad idea" (2026-10-21, 228 points, 107 comments, fun:56) — high engagement for a technique-critique post.
- **Why it looks unbuilt/untested**: 228 points / 107 comments on a critique post, with no competing evidence elsewhere in this run of a widely-adopted calibrated alternative, suggests teams keep reaching for LLM self-scoring anyway and a well-known-good replacement pattern hasn't propagated yet.
- **Maturity**: PARTIAL
- **Verdict notes**: Calibrated alternatives exist in the research literature (hidden-state probes like CCPS, calibrated-judge training with Brier-score loss, multicalibration for hallucination probabilities, a "Calibrated Entropy Score" black-box statistical test) but every one found requires either white-box model access, log-probs, or labeled training data — none is a maintained, drop-in production tool a team can swap in for "ask the LLM how confident it is," so the practical gap the HN critique raised is real even though the underlying research is not new.

### P9: SSRF + semantic-domain-safety gating specifically for agent tool calls that fetch external content
- **What it is**: A guardrail layer scoped not at the prompt level but at the outbound tool-call level — blocking server-side request forgery and off-topic/abusive domains when an agent's tool (e.g., a PDF/web retrieval step in a research pipeline) reaches out to fetch external content.
- **Evidence**: GitHub PR, `saumyashah0510/Multi-Agent-Research-System-Architecture` #90, "feat(security): implement input prompt injection guardrails, semantic domain safety, and SSRF defense" (2026-11-05): "addresses external attack surfaces (malicious prompt injections, off-topic query abuse, and server-side request forgery during PDF retrieval)."
- **Why it looks unbuilt/untested**: This is a from-scratch feature implementation inside one project's own pipeline rather than a drop-in dependency — none of the guard frameworks named elsewhere in this run (Llama Guard, NeMo Guardrails, Presidio) are described as covering SSRF/tool-call-level network safety, suggesting that layer is still being hand-rolled per project.
- **Maturity**: PARTIAL
- **Verdict notes**: Several small libraries now exist specifically for SSRF-guarding agent tool calls — `agentguard` (Rust/Node egress firewall with declarative domain allowlist), `synaptic-middleware`'s `ssrf_guard.rs`, Warlock.js's outbound-policy SSRF guard (resolves DNS before checking for private IPs), and `yoker`'s web guardrail — but none combines SSRF defense with the "semantic domain safety" (off-topic/abusive-domain content classification) half of the pattern, maintenance/adoption of these libraries is unverified and likely low, and the SATURATED bar of multiple well-resourced maintained implementations covering the full combined pattern isn't met.
