## Candidate patterns

### P1: Built-in cost/loop governors for agentic RAG
- **What it is**: Treating agentic RAG as a control loop (plan → retrieve → evaluate → decide → retrieve again) that needs explicit budgets, stop rules, and execution traces — without them, the first visible symptom of a failure is a spike in the cloud bill rather than a caught error.
- **Evidence**: Found via WebSearch "agentic RAG production problems reddit discussion 2026" — theaiengineer.substack.com's "Why AI Agents Keep Failing in Production" frames agentic RAG explicitly as a loop lacking budgets/stop-rules/traces; a DEV.to post in the same result set separately pegs agentic RAG at roughly 2-4x the token cost of standard RAG and recommends reserving it only for high-stakes answers.
- **Why it looks unbuilt/untested**: Both sources describe the failure mode and recommend a fix in prose; no named open-source "RAG loop governor" or budget-enforcement tool surfaced in the search.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search found research-only prototypes (BCAS_RAG — LSU budget-constrained-search study; Cost-Aware-RAG — evidence-access-tier research code) plus generic, RAG-agnostic agent-cost tools (Gravitee's cost governor, a Rust "Microloop" loop-detector, a `dingdawg-governance` npm package). None combine retrieval-loop-aware budgets/stop-rules/traces into one maintained, adopted tool — the specific gap (a RAG-loop governor, not a generic LLM cost meter) is real.

### P2: Source-credibility scoring layered on top of semantic relevance
- **What it is**: A separate scoring pass that down-ranks stale or low-credibility retrieved content, since pure embedding-similarity ranking can surface a joke post or outdated page as if it were authoritative.
- **Evidence**: Same theaiengineer.substack.com piece (via the "agentic RAG production problems" WebSearch) proposes "source quality scoring alongside semantic relevance, plus freshness filters that down-rank stale content" as its fix for exactly this failure mode.
- **Why it looks unbuilt/untested**: Presented as the author's own proposed remedy, not a citation of an existing shipped product or library that already does this.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch surfaced only academic work implementing this: "Retrieval-Augmented Generation with Estimation of Source Reliability" (arXiv 2410.22954, weighted similarity+reliability score), RA-RAG (cross-source reliability via majority voting), and SourceBench (arXiv 2602.16942, a relevance/objectivity/freshness rubric). All are research papers/benchmarks, not a shipped library or product feature — no mainstream RAG framework (LangChain, LlamaIndex) ships credibility scoring as a default or built-in pass.

### P3: Stale-index-vs-source drift as a silent production failure
- **What it is**: RAG systems keep serving answers from a vector index that has quietly fallen months behind the source documents, because nothing in the stack automatically detects document-vs-index drift.
- **Evidence**: A blog post surfaced in the "agentic RAG production problems" WebSearch reports users getting answers based on information "months out of date" after source docs changed but the index didn't; separately, the access-control WebSearch surfaced multiple sources (Paragon's permission-aware-RAG blog post, dev.to/pykero) flagging "stale permissions" — ACL drift between the source system and the vector index — as "the main risk."
- **Why it looks unbuilt/untested**: Both threads describe this as an open operational pain point needing "ongoing sync," not something a named tool already solves end-to-end.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found three nascent PyPI packages — `ragfresh` (github.com/nac7/ragfresh, detection-only, no reindex support for chunked stores, 0 GitHub stars per a third-party directory, created Aug 2026), `raghealth` (one-off scan across pgvector/Chroma/Qdrant/Pinecone/Weaviate), and `rag-staleness-check` — plus vendor blog guidance (Oracle, Microsoft/Azure AI Search, kapa.ai) describing checksum/CDC-based detection patterns in prose. No maintained, widely-adopted tool actually closes the drift-detection-and-resync loop end-to-end; this is early and narrow.

### P4: Permission-aware retrieval enforced inside the vector query, not filtered after
- **What it is**: Pushing tenant/user ACL filtering directly into the vector search itself (namespaces, Postgres/pgvector row-level security, relationship-based permissions à la SpiceDB) so unauthorized chunks never come back, instead of retrieving broadly and filtering afterward — and never delegating the enforcement decision to the LLM itself.
- **Evidence**: WebSearch "RAG multi-tenant access control permissions vector database" surfaced dev.to/pykero's "permission-aware RAG: what it really costs to get right," a levelup.gitconnected Next.js/pgvector-RLS write-up, an Authzed SpiceDB-based multi-tenant RAG tutorial (Dec 2025), and Microsoft's "secure multitenant RAG" architecture guide — all converging on "filter inside the query" as the consensus pattern, with one source explicitly warning that LLM-based access enforcement is "non-deterministic and unsafe for sensitive data."
- **Why it looks unbuilt/untested**: The search found vendor guidance and several one-off tutorials but, per the search's own synthesis, "no single first-hand report of a team's production deployment" at scale, and a cited arXiv paper (2605.03275) argues a single vector database as the sole data layer still causes tenant leakage and sync problems.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "permission aware RAG"` returned 10+ repos (e.g. `sahil1605/permission-aware-rag` — OpenFGA+Milvus benchmark on 50K chunks; `ranajahanzaib/multi-tenant-rag`; `sohanmaheshwar/spicedb-testcontainer-rag`), all created within the last ~1-13 months, all small demos/reference implementations with no indication of stars or production adoption. Supabase and Microsoft both publish official how-to guides for the pattern, and Cerbos sells a commercial policy-plan product, confirming the consensus approach is well-known — but no dominant maintained open-source implementation or evaluated production deployment exists; it's many narrow one-offs, matching the digest's own "no first-hand production report" finding.

### P5: Reranker skepticism — default-off reranking based on measured regression
- **What it is**: Teams running their own A/B tests and finding that adding a reranker actually hurts retrieval quality on their corpus, then disabling it by default — contradicting the "always rerank" guidance in most tutorials.
- **Evidence**: WebSearch on chunking/reranking ("duct tape" query) surfaced a practitioner write-up reporting Hit@1 fell from 58.3% without a reranker to 43.0% with one, prompting the author to disable it; the same result set contained an OpenRouter tutorial describing rerank-by-default (retrieve 30 chunks, rerank, keep top 3) as the standard pipeline.
- **Why it looks unbuilt/untested**: No repeatable harness or tool surfaced for deciding when a reranker helps vs. hurts for a given corpus — it's reported as a manual, one-off A/B test each team redoes for itself.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "RAGScope"` and `reranker evaluation harness"` found one close match, `Sidd27/ragscope` ("PASS/WARN/FAIL scores for your retrieval pipeline," OTel-based, works with LangChain/LlamaIndex/Langfuse) — a real but early, narrow, unverified-adoption tool (created mid-2026, maturity/stars not confirmed). No standard or widely-adopted reranker-regression-detection harness exists; teams still run their own bespoke before/after A/B tests, as the digest's own evidence shows.

### P6: Semantic/structure-aware chunking as a cheap, high-leverage fix over fixed-length chunking
- **What it is**: Switching from fixed-length chunking to semantic or structure-aware chunking (respecting sentence/list/section boundaries) produces large precision gains for comparatively little engineering effort.
- **Evidence**: A dev.to write-up (same chunking/reranking WebSearch) reports context precision jumping to 0.68 after switching to semantic chunking, describing the change as "two hours of work"; kapa.ai's post in the same batch independently describes fixed-length-chunked RAG as feeling "duct-taped" once it scales.
- **Why it looks unbuilt/untested**: Framed in both sources as a bespoke fix individual teams discover by trial and error, not something shipped as a default in common RAG framework starter templates.
- **Maturity**: SATURATED
- **Verdict notes**: Semantic/structure-aware chunking is already a built-in, shipped option in both LangChain and LlamaIndex (confirmed via WebSearch — "LangChain and LlamaIndex both offer it as an option"), with an arXiv study (2410.13070) and a Vectara writeup specifically evaluating it against fixed-size chunking, plus numerous `gh search repos` hits (e.g. `pavanbelagatti/Semantic-Chunking-RAG`) demonstrating widespread hands-on adoption. The remaining gap is only that it isn't the *default* — the technique itself is squarely covered by maintained, well-resourced frameworks, so this doesn't clear the bar for a differentiated build.

### P7: Grep/exact-match retrieval used selectively instead of (or alongside) RAG for coding agents
- **What it is**: Coding agents increasingly favor deterministic grep-style search over vector RAG for codebases, because code changes too fast for an index to stay fresh and an exact-identifier miss is a clear miss rather than a plausible-looking wrong chunk; RAG is kept only for cases where the user can't name the exact target.
- **Evidence**: WebSearch "agent grep codebase search vs RAG retrieval" surfaced an itnext.io benchmark ("the same grep hits scored 10, 30, or 34 of 40" depending on ranking method), a dev.to/harrisonsec piece framing retrieval choice as "a cost-curve problem," and a secondhand (explicitly unverified in the search's own synthesis) report that an Anthropic engineer described Claude Code dropping a local-vector-DB RAG approach in favor of grep.
- **Why it looks unbuilt/untested**: The search's own synthesis calls this "anecdotes and one small benchmark" — no general, verified decision framework exists for when an agent should pick grep vs. RAG vs. a hybrid.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirmed via multiple independent sources (dev.to/harrisonsec, Towards AI, a Zilliz vendor rebuttal, Chinese-language technical analyses) that Claude Code runs live ripgrep rather than a persistent vector index in production — a maintained, well-resourced shipped product validating the core technique. However, Cursor/Aider reporting is contradictory (hybrid or disputed), and no general, reusable decision framework/tool for choosing grep vs. RAG vs. hybrid exists beyond one academic benchmark (arXiv 2605.15184, "Is Grep All You Need?") and a small ITNEXT blog benchmark — so the specific "decision framework" angle remains a real, differentiated gap even though the underlying grep-primary technique is already proven at scale by one bespoke implementation.

### P8: Fragmented RAG evaluation landscape with a specific gap in abstention-behavior testing
- **What it is**: Many academic hallucination-detection benchmarks and leaderboards already exist (RAGTruth, RAGBench, BERGEN, Vectara's faithfulness leaderboard), but no single turnkey harness unifies them, and the gap called out most explicitly is testing whether a RAG system correctly abstains ("I don't know") instead of guessing when it lacks grounding.
- **Evidence**: WebSearch "RAG evaluation harness has anyone built" surfaced the named benchmarks/papers above plus a preprint (arXiv 2608.26385) explicitly arguing that binary-graded benchmarks "reward guessing over abstaining" and proposing penalty-aware scoring with "knowledge-gap canary" questions.
- **Why it looks unbuilt/untested**: The search's own synthesis states it "did not surface a single turnkey harness that covers all of these at once" — multiple point solutions exist but nothing unified and widely adopted.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found several academic-only point solutions: LIT-RAGBench (arXiv 2603.06198, has an explicit Abstention category, code released but turnkey-ness unconfirmed), Secure-RAG (non-peer-reviewed preprint proposing a unified suite), FATHOMS-RAG (arXiv 2510.08945, multimodal pipeline benchmark). Established eval libraries (RAGAS, DeepEval, TruLens) are widely adopted but, per Secure-RAG's own framing, require manual assembly to cover abstention — no single mature, turnkey harness unifies abstention + hallucination scoring, confirming the gap is real.

### P9: "RAG doesn't learn" — no persistent memory/feedback loop from past retrieval mistakes
- **What it is**: A recurring complaint that RAG systems treat every query independently, with no mechanism to remember that a past retrieval picked the wrong chunk (and was corrected) the way a human analyst would carry that correction forward.
- **Evidence**: Surfaced via the "has anyone built"/"I wish there was" WebSearch — a freeCodeCamp piece argues RAG systems don't learn; a discuss.huggingface.co thread titled "Why does RAG still feel clunky in 2025?" and a community.openai.com thread titled "RAG is not really a solution" raise the same complaint from two separate practitioner communities.
- **Why it looks unbuilt/untested**: All three are discussion/complaint threads (HuggingFace forum, OpenAI community forum, a critical blog post) with no product named as having solved persistent cross-query learning.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found academic research prototypes addressing this — RFM-RAG (arXiv 2508.17862, persistent evidence pool + completeness evaluator), SEGMEM-RAG (AAAI, feedback-evaluator that tunes source selection), GAM-RAG (arXiv 2603.01783, code at an anonymous 4open.science link, explicitly warns naive memory updates "accumulate spurious correlations") — plus isolated one-off GitHub repos (`Emmimal/memory-leak-rag`) and practitioner blog posts. None is a mainstream, maintained, shipped product; this is scattered research-stage work, so the community complaint about no learning loop remains substantively unaddressed.
