## Candidate patterns

### P1: Translation/validation proxy layer for small-model tool calling
- **What it is**: A middleware shim sitting between a small local model (7B and under) and an agent framework that repairs malformed tool-call arguments and reconciles small-model-specific tool-call formats before they reach the actual tool executor, instead of relying on the model to emit valid structured output directly.
- **Evidence**: WebSearch synthesis (query: `local LLM agent tool calling unreliable small model reddit`) of multiple dev.to write-ups: a Rust-coding-agent test across 7 local models found malformed arguments the dominant failure mode; a HuggingFace forum thread ("Tool/Function calling abilities of LLM's that are used locally pulled through ollama") reports that without an agent framework, "the models that support tool calling are limited"; a CrewAI community post says Qwen2.5-7B "still doesn't handle function calling or tool use reliably"; one practitioner estimated "a translation proxy... the format mismatch alone costs you 0-17%."
- **Why it looks unbuilt/untested**: Every source describes the fix as a one-off workaround inside a single project (a proxy someone wrote for their own pipeline, or "hard-coding known facts into the system prompt") rather than a reusable, named, maintained tool other teams can adopt.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub search found `forge` (antoinezambelli/forge, 2,268 stars, pushed 2026-11-12, MIT, OpenAI/Anthropic-compatible proxy with "rescue parsing, retry nudges, tiered compaction" explicitly aimed at unreliable ~8B local tool-calling) and a maintained `ToolCallRepairMiddleware` inside the LangChain ecosystem — both are reusable, actively maintained tools squarely covering this exact gap, not one-off hacks. Smaller/narrower entrants (filthy-tool-fixer, 2 stars, last pushed Feb 2026; tooltalk) confirm the space is active, not that it's unbuilt.

### P2: Cost-per-successful-task router between local and cloud models
- **What it is**: A routing layer that doesn't just classify "easy vs. hard" prompts to send to a local vs. cloud model, but explicitly scores whether a cloud fallback call is "worth it" against a Cost-Per-Successful-Task (CPST) metric — accounting for the human time cost when a free local model silently fails.
- **Evidence**: WebSearch synthesis (query: `"has anyone built" OR "I wish" local small model router cloud fallback cost`) — one practitioner explicitly names "Cost per Successful Task (CPST)" as the missing metric, arguing "a free local model that fails often still costs human time"; another post frames the gap directly as the router needing to know whether a cloud API call is "worth it" or not; a home-lab setup's author admits "the first version just errored when the GPU machine was down, and fallback was an afterthought."
- **Why it looks unbuilt/untested**: The CPST framing and the "worth it" decision logic appear only as stated wishes/critiques in blog posts about routers the authors already built (NadirClaw, Kronaxis Router) — none of the named projects actually implements CPST-based routing; it's flagged as the next thing missing.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed via GitHub + web: NadirClaw (doramirdor/NadirClaw, 666 stars, active) and Kronaxis Router (4 stars, last pushed 2026-07-22) do local/cloud routing, and LiteLLM's docs report a "cost per solved task" benchmark — but none implements the CPST-as-decision-metric ("is this cloud fallback worth it, accounting for human correction time") described in the evidence; it remains an explicitly named gap in the authors' own write-ups, not shipped logic. Real, narrow routers exist; the specific differentiator is unbuilt.

### P3: Hardware-to-model fit finder as a standalone tool
- **What it is**: A tool that takes a user's actual hardware specs (VRAM, RAM, GPU) and recommends which local LLMs (and quantization levels) will actually run well, replacing the current practice of manually cross-referencing scattered benchmark threads.
- **Evidence**: Hacker News, "I built a tool to find local LLMs that fit your hardware" (3pts, 4cmt, 2026-11-13, https://thinkidiot.com/tools/local-model-finder); same-window HN thread "Ask HN: What hardware are you using to run local LLMs?" (52pts, 46cmt, 2026-11-02, https://news.ycombinator.com/item?id=50337431) shows the crowd-sourced, ad hoc version of the same need.
- **Why it looks unbuilt/untested**: The tool that exists is a single hobbyist's low-traction side project (3 points); the much higher-engagement thread (52pts/46cmt) is people manually trading personal hardware/model combos in comments rather than using a canonical resource — suggesting no tool has reached the audience that actually needs this.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found `llmfit` (AlexsJones/llmfit, 39,122 GitHub stars, pushed 2026-11-18, MIT) — a mature, actively maintained CLI that detects hardware (CUDA/Apple Silicon/ROCm/OneAPI), scores models across quality/speed/compatibility/context, and recommends quantization levels across Ollama/llama.cpp/MLX, covered in multiple independent write-ups (Hongkiat, dev.to, BetterStack). Additional entrants `whichllm` and a RunLocal-built picker confirm this exact niche is well-served; the HN tool cited in the digest is a redundant, lower-traction reimplementation of an already-solved problem.

### P4: Homegrown comparative benchmarking because vendor claims aren't trusted
- **What it is**: Practitioners running their own from-scratch comparative benchmarks across a dozen-plus small local models rather than relying on published leaderboards or vendor claims, specifically to check whether a hyped small model ("the Qwen 3.8 35B we didn't get") actually delivers.
- **Evidence**: Hacker News, "I benchmarked 22 local LLMs looking for the Qwen 3.8 35B we didn't get" (3pts, 2cmt, 2026-11-19, https://sevangelatos.github.io/spiruxbench-results/blog/).
- **Why it looks unbuilt/untested**: A single author built a bespoke benchmark suite from scratch for this one check; no reusable, standardized small-model benchmark harness is cited or linked in the thread.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found multiple maintained, standardized harnesses built specifically to address distrust of vendor-reported numbers: `local-bench.ai` (hash-pinned test suites, seeded decoding, sandboxed execution, multi-axis "Local Intelligence Index"), Mozilla's `LocalScore` (official-models comparability set, hosted on HuggingFace), and `homebench` (31 deterministically-graded tasks for laptop-run models). The one author in this digest's evidence chose to roll a one-off script rather than adopt an existing standard, but the standard options already exist and are maintained — the gap is adoption/awareness, not availability.

### P5: Distilling from logged production behavior instead of synthetic teacher output
- **What it is**: Training a small student model directly on a large model's logged production outputs/decisions (not synthetic imitation data generated for the purpose) via supervised fine-tuning, as a cheaper and more faithful way to shrink a narrow-task workflow down to an SLM.
- **Evidence**: WebSearch synthesis (query: `small local model fine-tuning distillation narrow task workflow 2026`) of a NeurIPS 2026 paper, "Iterate on an LLM, Serve on an SLM" — "distill the recorded production behavior (not synthetic imitations of it) into an SLM through supervised fine-tuning (SFT)"; contrasted with the standard practitioner pattern described elsewhere in the same search ("a strong teacher labels training data, and a small student learns to imitate it").
- **Why it looks unbuilt/untested**: Surfaced only as a paper abstract (research-stage, no linked code or reproducible pipeline found in this search); all the practitioner-reported workflows in the same search use the older synthetic-teacher-labels approach instead.
- **Maturity**: PARTIAL
- **Verdict notes**: `OpenPipe` (OpenPipe/OpenPipe, 2,838 stars) logs real production request/response pairs and fine-tunes smaller models from them — closest existing match — but its GitHub repo has had no push since 2024-05-25 (18+ months stale, effectively abandoned per the rubric), and commercial equivalents (CoreWeave Model Distillation, Azure Stored Completions) are in private preview / unconfirmed open availability. The NeurIPS 2026 paper itself has no linked code. A maintained, evaluated, open pipeline specifically for this pattern does not exist.

- **Evidence**: GitHub, "NeoRouter – Self-hosted routing for free, paid and local LLMs" (3pts, 2cmt, 2026-11-02, https://github.com/NeoLabs-Systems/NeoRouter) via Hacker News cross-post.
- **Why it looks unbuilt/untested**: Very low engagement (3 points, 2 comments) for a newly launched project — the specific "free + paid + local in one router" framing hasn't been validated by any visible adopter discussion in this window.
- **Maturity**: SATURATED
- **Verdict notes**: `LiteLLM` (BerriAI/litellm, 63,577 stars, pushed 2026-11-20 — same day) already does exactly this: its proxy fronts Ollama/vLLM local models, OpenRouter free-tier models, and paid cloud APIs behind one OpenAI-compatible gateway with fallback chains, confirmed by multiple independent write-ups and homelab tutorials. Bifrost, Olla, and Kong were also cited as alternative gateways doing the same thing. NeoRouter (the digest's cited project, 5 stars) is a redundant reimplementation of an already-dominant, well-resourced category.

### P7: Single-controller prompt-cache lifecycle (warm → compact → offload/expire) for local model serving
- **What it is**: A unified state-machine/controller that manages a local model's prompt cache through one clock — keeping it warm while paying, compacting or offloading on idle, and counting the unload against usage — instead of separate ad hoc TTL and eviction logic.
- **Evidence**: GitHub PR on `NousResearch/hermes-agent`, "Prompt cache kept warm while it pays, then the idle chat compacts or offloads" (7 reactions, 19 comments, 2026-11-16, https://github.com/NousResearch/hermes-agent/pull/156455); a reviewer comment requests the controller's constants be exposed as config, calling the "single-controller design (warm → compact → expire, one cache clock)" worth generalizing beyond this one project.
- **Why it looks unbuilt/untested**: Built inside one specific agent project's PR, not extracted as a standalone library; the reviewer's own ask ("expose the controller's constants as config") signals it isn't yet reusable outside this codebase.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found only scattered point-solutions covering individual stages — a `prompt-cache-keepalive` Python package and a Go `eyrie` CacheWarmer both just "touch" a cache to keep it warm; `pi-fabric` documents a lease/hold model with compaction triggers but is tied to one ecosystem; `dirge-agent` (Rust) implements TTL-tier selection only. No standalone library unifies warm→compact→offload→expire under one clock as a reusable controller — exactly as the digest's own PR evidence suggests, this remains unextracted from individual codebases.
