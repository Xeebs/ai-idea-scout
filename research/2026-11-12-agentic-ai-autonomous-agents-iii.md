## Candidate patterns

### P1: Model-judged context pruning (summarize-and-discard junk tool output)
- **What it is**: Instead of an agent re-reading a noisy/large tool-call result on every subsequent turn, the model itself judges when a tool output is "junk" and swaps it for a one-line summary immediately, paying the summarization cost once instead of re-processing bloated context every turn.
- **Evidence**: GitHub feature request on `google-antigravity/antigravity-cli` (#1429, opened 2026-11-05, 2 reactions, 2 comments): "When a tool call returns junk the model didn't intend, let the model swap that output for a one-line summary before the turn ends. Pay for it once; keep the context clean for the rest of the session." (per last30days engine output).
- **Why it looks unbuilt/untested**: It's filed as an open feature request against a CLI agent harness, not a shipped capability — the asker is proposing it as something the harness doesn't yet do.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained implementations already do exactly this: the `pi-context-prune` extension has a shipped `agentic-auto` mode where the model itself decides when to call `context_prune` to summarize finished tool-call batches (with originals retrievable); Kapa.ai ships model-judged RAG-chunk pruning on by default in its Product Agent SDK; and recent 2026 research (Squeez, SWE-Pruner Pro, DTOC) all target this exact judge-and-discard problem with reported eval numbers. This is an actively worked, multi-team-solved space, not a gap.

### P2: OAuth-style identity/delegation broker for autonomous agents
- **What it is**: A dedicated identity-and-delegation layer that lets an AI agent act on a human's behalf against third-party services with scoped, revocable, auditable credentials, instead of agents holding raw API keys or impersonating the user.
- **Evidence**: Show HN: "Agentic Identity Broker, OAuth Delegation for AI Agents" (`zalando-incubator/agentic-identity-broker`, 2026-11-06, 25 points / 4 comments on HN) (per last30days engine output). Corroborated by a separate HN item the same week, "Trust Under Fire: How Agentic AI Tests Zero-Trust" (IEEE Spectrum, 2026-11-09, 3 points).
- **Why it looks unbuilt/untested**: A large company incubator (Zalando) is shipping a first-party OSS project for this specifically because no standard, mature delegation layer exists yet for agent-to-service auth — a Show HN launch, not an established standard.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found several early implementations beyond the digest's Zalando pick — `ideksec/agent-identity-broker` (explicitly labeled "POC," SPIFFE-based), `CloudbrokerAz/vault-agentic-identity-broker`, and `infamousjoeg/idira-disco-mcp` — plus an unadopted individual IETF draft (draft-sweeney-wimse-credential-delegation) proposing a credential delegation protocol. No converged standard or dominant product exists yet; these are competing early-stage/POC approaches, so the gap is real but already being chipped at by multiple small teams.

### P3: Claim-later / keyless provisioning for agent-initiated cloud resources
- **What it is**: An agent (Cursor, Claude Code, Codex, an MCP client, or a CLI) can spin up a working cloud environment and start building/triggering real workflows *without* the human signing up first; the human claims the environment via a hand-off link only once they want to keep it.
- **Evidence**: `novuhq/novu` PR #12905 (2026-10-15, 2 reactions / 6 comments): "Lets an AI agent... get a working Novu Cloud environment without signing up, build and trigger workflows with it, and hand the human a claim link." (per last30days engine output).
- **Why it looks unbuilt/untested**: This is a single vendor's just-merged PR solving its own onboarding friction for agent-driven signup — not a generalized pattern or library other products have adopted yet.
- **Maturity**: SATURATED
- **Verdict notes**: This is already a named, shipped pattern at multiple well-resourced vendors, not just Novu's PR: Cloudinary's "Claimable Cloud" (24-hour no-signup provisioning with a claim_url), Pulumi's "agent accounts" (auto-detects agent CLIs, 72-hour write window, 30-day claim), and Cloudflare's "Temporary Accounts" (Wrangler flag, 60-minute live Worker + claim link, GA'd with a ProductHunt launch) all implement the identical claim-later flow in production infrastructure products.

### P4: Peer learning between agents in a multi-agent team
- **What it is**: Instead of agents in a multi-agent system operating in isolation (each re-learning the same lessons), agents share learned strategies, corrections, or skills with each other mid-run or across runs — "peer learning" as a first-class mechanism rather than a shared scratchpad.
- **Evidence**: HN item "Peer Learning Between Agents in a Multi-Agent Team" linking to `Mininglamp-AI/Octo` on GitHub (2026-11-06, 3 points) (per last30days engine output).
- **Why it looks unbuilt/untested**: Framed and linked as a single project's novel contribution/experiment rather than a widely adopted technique — low engagement (3 points) suggests early/unproven, not yet validated by a broader audience.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for the `Mininglamp-AI/Octo` link in the digest found the project actually lives under `Mininglamp-OSS` (5k+ stars) and its documented feature set is preference learning from human review feedback, not peer-to-peer mid-run sharing between agents — the specific claim is weakly sourced. WebSearch found only RL-era academic precedent (Derstroff et al., arXiv 2312.09950, action-advice bandit-based peer learning for RL agents, not LLM agents) and one qualitative/observational 2026 paper (arXiv 2603.16663) noting emergent skill-sharing behavior in agent communities. No engineered, evaluated mid-run peer-learning mechanism for LLM multi-agent teams was found; this stays an open research direction.

### P5: Narrow single-purpose agents + plan-written-to-file + markdown handoffs (anti-"god-mode agent" pattern)
- **What it is**: A workflow discipline where practitioners deliberately avoid one broad do-everything agent, instead running several narrow-scoped agents, writing the plan to a file *before* any code lands, and using markdown files as the hand-off/state mechanism between agent runs or between agents and humans.
- **Evidence**: Surfaced from Ask HN "What's your current AI agentic setup?" (2026-11-04, 571 points / 713 comments — one of the highest-engagement threads found this run) (per last30days engine output). A third-party synthesis of the thread (via WebSearch) reports the replies converge on: "narrow jobs beat god-mode agents, a plan is written to a file before code lands, and handoffs live in markdown files." One mirrored comment also described removing custom skills in favor of running 5+ tasks in parallel after a recent model release, to avoid idle wait time.
- **Why it looks unbuilt/untested**: This is informal practitioner habit reported secondhand (via a thread synthesis, not the raw comments), not a packaged tool or framework — nobody has turned "plan-to-file + markdown handoff" into a reusable, opinionated harness; everyone seems to be hand-rolling it.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub's own `spec-kit` ("Toolkit to help you get started with SDD or any other process!") is a maintained, actively-pushed (last push within the last day), 149,556-star implementation of exactly this discipline — spec/plan files written before implementation, with memory files and breakpoints for human review — backed by GitHub itself. WebSearch corroborated multiple other named frameworks doing the same thing (`spec-kitty`, a "plan-md" PLAN.md/PROGRESS.md convention, an `agent-handoff` plan→execute→verify project, Copilot's `gem-planner`). The "nobody has packaged this" framing in the digest doesn't hold up — this is one of the most heavily adopted patterns in the current coding-agent ecosystem.

### P6: Permissions/trust — not model intelligence — as the real agentic AI production bottleneck
- **What it is**: The claim, recurring across several independent sources, that the limiting factor on deploying autonomous agents in production is not model capability but authorization/permissions scoping, organizational trust, and undocumented workflows that can't yet be handed to an agent safely.
- **Evidence**: Ask HN "What is the main bottleneck facing Agentic AI today?" (2026-10-25, 7 points / 19 comments) (per last30days engine output). Corroborated via WebSearch supplement by multiple independent pieces: oodaloop's "The AI agent bottleneck isn't model performance, it's permissions," and an essay framing it as "agentic AI isn't hitting an intelligence ceiling, it's hitting a reliability ceiling," plus a cited survey of 30+ startup founders and 40+ enterprise practitioners naming workflow integration, employee trust, and data privacy — not model quality — as the toughest deployment challenges.
- **Why it looks unbuilt/untested**: Everyone agrees this is the bottleneck but the WebSearch supplement turned up diagnosis essays, not a converged tooling answer — no dominant permissions/scoping framework for agents was named as already solving this.
- **Maturity**: PARTIAL
- **Verdict notes**: The diagnosis is converged (multiple independent sources — oodaloop, essays framing a "reliability ceiling," a cited 70+ practitioner survey — all name permissions/trust/workflow-integration over model quality), but the tooling answer is fragmented: vendor products attacking pieces exist (Obsidian Security's least-privilege-for-agents content, Airia's "scoped access" positioning, Aurascape), plus one ICML 2026 workshop research prototype (dynamic capability scoping, synthetic 600-prompt dataset) — but no dominant, evaluated, generally-adopted permissions/scoping framework for agents exists yet. Real gap, but not virgin territory — a build here competes with active vendor attempts, not a vacuum.

- **What it is**: A small model that tags intent, dialog act, entities, numbers, PII, profanity, and safety risk word-by-word as speech arrives from an ASR stream (or as text is typed), so a voice agent can react mid-sentence instead of waiting for a full turn to end.

- **Why it looks unbuilt/untested**: Framed explicitly by its own builder as a from-scratch personal project ("I built") solving a gap they identified — not citing or building on an existing standard tool for this.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for a packaged streaming intent/dialog-act tagger found nothing. WebSearch found only academic precedent, and it's dated and narrow: word-level incremental intent-closing detection and streaming spoken-language-understanding papers (IJCAI 2021, RNN-T slot-tagging work, a 2022 caller-intent-detection study) address pieces of this (intent timing, slot tags) but none bundles intent + dialog-act + entities + PII + profanity + safety-risk tagging as one streaming tagger, and none is a maintained current product. The r/MachineLearning poster's own framing as a from-scratch solo build is consistent with what the search found — real prior art pieces, no converged or current implementation.
