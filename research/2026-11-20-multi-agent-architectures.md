## Candidate patterns

### P1: Note-passing handoffs instead of live multi-agent chat
- **What it is**: Instead of two agents holding a live, shared-context conversation, one agent writes a structured note/summary and a second agent reviews it fresh with no shared conversation history — deliberately severing context rather than streaming it.
- **Evidence**: An r/openclaw thread about getting two agents to collaborate in Telegram surfaced via WebSearch ("multi-agent architectures subreddit reddit community discussion" query): top reply states "Works better if they don't actually chat in real time. Have Agent 1 write a structured note, then trigger Agent 2 to review it fresh with no shared conversation history." No direct engagement numbers available (Reddit API blocked; signal is via secondary aggregation).
- **Why it looks unbuilt/untested**: This is described as a workaround practitioners discovered ad hoc inside a chat tool, not a packaged primitive — no named framework offers "note-handoff mode" as a first-class orchestration primitive distinct from shared-memory chat.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos` for "agent note handoff" and "multi-agent asynchronous handoff" returned zero results. WebSearch found only a personal-project doc (spinchange/vulture-nest) describing a manual shared-note convention (not a reusable library), plus Microsoft Agent Framework's and cortexai-crew's "handoff" features — both of which broadcast full conversation history to the next agent, the opposite of the context-severing pattern described. No implementation of deliberately-severed-context handoff as a first-class primitive found.

### P2: Practitioner pushback on multi-agent-as-first-resort
- **What it is**: A recurring practitioner view that multi-agent frameworks are reached for too early, when a single agent with better context/tools would suffice; multi-agent is positioned as suited only to genuinely parallelizable work.
- **Evidence**: r/AI_Agents thread (via WebSearch aggregation) asking builders "when multi-agent setups actually beat a single agent with better context," summarized as "a growing view that multi-agent frameworks get reached for too early." Corroborated by an AWS-hosted architecture guide (found via "multi-agent architecture patterns November 2026" WebSearch) advising "a single agent with suitable tools may be simpler, faster, and easier to evaluate," and an essay by Yoav Goldberg (surfaced in the same search) arguing many systems called "multi-agent" are really modular single agents.
- **Why it looks unbuilt/untested**: No tooling exists to help a team decide, with evidence rather than vibes, whether their task actually needs multi-agent decomposition — this is an unmet decision-support need, not a technique.
- **Maturity**: OPEN
- **Verdict notes**: WebSearch surfaced numerous blog-post decision frameworks (Consultevo's 1-35 point scorecard, a DEV Community context-window-usage heuristic, Salesforce's "3 signs," a task-graph-density checklist) but every one is prose advice for a human to apply manually — no actual software/tool that ingests a task description or codebase and outputs a recommendation was found on GitHub or the web. This is discussion-shaped signal (abundant, but all discussion), not an implementation.

### P3: Consensus-as-false-signal in multi-agent voting/aggregation
- **What it is**: Multiple agents agreeing with each other is being shown to be a weak or false confidence signal — agents can echo each other's hallucinations — and raw majority voting underperforms independent verification or trust-weighted voting.
- **Evidence**: HN "Verify, Then Vote: Overturning Wrong Majorities in Multi-Agent LLMs" (2026-11-03, 4pts, via engine HN results, URL github.com/grainulation/papers). Corroborated by WebSearch: a DEV Community benchmark post reporting a council of agents scoring worse than the strongest single model alone ("Qwen got nine right alone. The council got six"), an ArkForge blog on "Agent Consensus Blindness... coordinated hallucinations" ("Agent B just echoed A's hallucination"), and an arXiv paper (AgentAuditor, Feb 2026) reporting auditing reasoning trees beats majority vote by up to ~5% accuracy across five multi-agent settings.
- **Why it looks unbuilt/untested**: The academic/vendor pieces propose trust-weighted voting (DynaTrust) or reasoning-tree auditing, but these are research prototypes or marketing posts, not adopted-in-practice tooling that a builder could drop into an existing crewAI/LangGraph pipeline.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed research-prototype-only landscape: DynaTrust (arXiv 2603.15661, trust-weighted jury voting), Deliberative Curation (arXiv 2606.00007, commit-reveal anonymous voting), and Roundtable Policy (arXiv 2509.16839, confidence-weighted consensus) are all academic papers with no evidence of adoption. One implementation reference (nexus-agents docs site, naming `weighted-voting.ts` and a CP-WBFT protocol) exists but reads as a single project's internal docs, not a maintained general-purpose library. No GitHub repo search turned up a maintained drop-in library for crewAI/LangGraph pipelines.

### P4: Missing trust layer between delegating agents
- **What it is**: Multi-agent systems routinely delegate tasks/tool calls between agents (including agents from different vendors/orgs) without any verification that the receiving agent is trustworthy, authorized, or behaving as expected — framed as agents "talking to strangers."
- **Evidence**: HN "Are we building multi-agent systems without a proper trust layer?" (2026-11-14, 4pts, via engine). Corroborated by WebSearch: DEV Community post "Your AI Agents Are Talking to Strangers: Why Agent-to-Agent Trust Verification Is the Security [gap]" and "Why Your Multi-Agent System Needs Trust Checks (and How to Add Them in 3 Lines)" — both framed as a gap builders are patching themselves with small ad hoc snippets rather than using an established layer.
- **Why it looks unbuilt/untested**: Multiple independent vendor/dev posts converge on "builders are hand-rolling 3-line trust checks" — i.e., the gap is acknowledged repeatedly but no standard/adopted trust-verification layer exists across the major frameworks (crewAI, LangGraph) yet.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "agent trust layer"` returned 10+ distinct repos literally named "agent-trust-layer" (recommend-dev, Anish0104/vouch, paramsrinivas, Vivekananda-S, davyjones7321, kauf3r, karanjadavi, jgreismit — spot-checked 4, all at 0-1 stars), confirming the gap is real and widely felt but every attempt is an isolated, unmaintained weekend/hackathon project. Also found 3 non-finalized IETF Internet-Drafts (draft-tonyai-a2a-trust, draft-kiliram-agent-trust-auth-framework) and one vendor promo post (AXIS Agent Trust Infrastructure) with unverifiable adoption. No mature, adopted standard across crewAI/LangGraph.

### P5: Multi-agent performance degrades specifically under multi-user load
- **What it is**: A distinct failure mode where multi-agent team performance breaks down not just from agent-count overhead, but specifically when multiple human users are interacting with the same multi-agent team concurrently.
- **Evidence**: HN "Worse Together: How Performance Breaks Down in Multi-User Multi-Agent Teams" (2026-11-12, 3pts, via engine, URL alignment.anthropic.com/2026/worse-together/).
- **Why it looks unbuilt/untested**: Single data point from one alignment-research post; no corroborating WebSearch hit found this cycle (the targeted "worse together" search returned no exact match), and no tooling surfaced that specifically isolates/mitigates multi-user contention in multi-agent systems as opposed to generic scaling.
- **Maturity**: OPEN
- **Verdict notes**: Follow-up WebSearch confirmed the paper (arXiv:2610.00583 / alignment.anthropic.com) plans a benchmark (MAMUBench, 74 scenarios) but no released tooling. The only "mitigation" sources found were a generic AWS CloudWatch composite-alarm pattern (not specific to multi-agent contention) and a documented anti-pattern writeup (agentpatterns.ai) — advice, not an implementation. No dedicated tool or library addressing multi-user multi-agent contention specifically was found on GitHub or the web.

### P6: Privacy leakage across agent-to-agent handoffs has no standard test harness
- **What it is**: A dedicated open-source privacy-testing tool for multi-agent LLM systems, implying the gap it fills — there is no standard way to test whether sensitive data leaks as it passes between agents in a pipeline.
- **Evidence**: HN "Show HN: AgentLeak – open-source privacy testing for multi-agent LLM systems" (2026-11-13, 3pts, via engine, URL github.com/Privatris/AgentLeak).
- **Why it looks unbuilt/untested**: A brand-new Show HN single-repo launch (3 points) — the fact that someone just built this from scratch, as a fresh single-maintainer repo rather than a feature of an existing framework (crewAI/LangGraph), signals the major frameworks don't ship this check natively.
- **Maturity**: PARTIAL
- **Verdict notes**: Verification found this is more substantial than a weekend hack: AgentLeak has a backing benchmark paper (IEEE Access 2026 per repo description, 1,000 scenarios, 7 channels, 5 LLMs) and a real tool (Python SDK, CLI, MCP server — github.com/yagobski/agentleak) hooking into LangChain/CrewAI/AutoGPT/MetaGPT traces. But both repos were created within the last two weeks (Nov 2026), have no visible star/adoption history, and the check isn't shipped natively by any major framework — real but unproven, hence not SATURATED.

### P7: Agent-relay for cross-vendor/cross-tool multi-agent coding sessions
- **What it is**: A relay layer letting multiple different coding-agent tools/vendors (not just multiple instances of the same agent) participate in one coordinated coding session together.
- **Evidence**: HN "Show HN: Agent-relay for multi-vendor coding sessions" (2026-10-27, 8pts, 1cmt, via engine, URL github.com/saranyan/agent-relay).
- **Why it looks unbuilt/untested**: Single fresh Show HN repo with low engagement (8pts) — a one-person solution to a problem (vendor lock-in / tool interop in multi-agent coding) that isn't addressed by any major framework's own docs.
- **Maturity**: PARTIAL
- **Verdict notes**: Verification found more activity than the single HN post suggested: a PyPI package `agent-relay-tool` ("local-first CLI for handing coding sessions between agents without losing context," supporting Claude Code and Codex), a separate low-traction `codervisor/agent-relay` repo (1 star, last pushed Dec 2025), Coder.com's commercial "Agent Relay" (cloud-hosted execution, adjacent but single-vendor-focused), and a funded startup listed on Dealroom explicitly connecting Claude Code/Codex/OpenCode/Cursor/Devin to message each other. Real, fragmented activity across several independent attempts, but no dominant or mature cross-vendor solution yet.

### P8: Peer learning between agents within a running multi-agent team
- **What it is**: Agents in a multi-agent team learning from each other's outputs/behavior during a session (peer learning), rather than each agent being a static, independently-prompted role.
- **Evidence**: HN "Peer Learning Between Agents in a Multi-Agent Team" (2026-11-06, 3pts, 1cmt, via engine, URL github.com/Mininglamp-AI/Octo).
- **Why it looks unbuilt/untested**: Low-engagement single repo link; no corroborating discussion found. Framed here as a candidate pattern worth the gap-analyst's explicit search rather than an established technique.
- **Maturity**: PARTIAL
- **Verdict notes**: Note: the digest's cited URL (github.com/Mininglamp-AI/Octo) does not resolve — a GitHub API search of that org found only an unrelated repo, `Mininglamp-AI/OctoASR` (149 stars, a speech-recognition tool), so that specific evidence citation appears broken/mismatched. Independently, WebSearch found a real adjacent implementation: CoMAS (ICLR 2026, github.com/xxyQwQ/CoMAS, 59 stars, pushed Jan 2026) — "agents improve by learning from their interactions with each other, with no external reward" — plus ChatDev's "Experiential Co-Learning" feature (reusing past-task experience, a related but distinct asynchronous mechanism, inside a 34.8k-star repo, though that specific feature alone isn't what drives ChatDev's popularity). CoMAS is real but narrow, research-grade, and unevaluated outside its own paper's benchmarks — not adopted into any major multi-agent framework as a runtime feature.
