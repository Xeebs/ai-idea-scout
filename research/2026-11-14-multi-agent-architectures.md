## Candidate patterns

### P1: Stitched tracing across agent handoffs (correlation IDs, boundary-level context diffing)
- **What it is**: A tracing layer purpose-built for multi-agent systems that follows one correlation ID across every agent-to-agent handoff and records exactly what context was dropped, truncated, or transformed at each boundary — not just per-agent logs.
- **Evidence**: WebSearch practitioner roundup (fiddler.ai, atlan.com, qawerk.com) reports teams saying "ordinary logging doesn't capture why an agent handed off, what context was dropped at the boundary, or whether guardrail state transferred"; one cited example has Agent B emitting a 14,000-token context while Agent C's input is truncated to 8,000 tokens with no visibility into the loss. Sources recommend "carrying a correlation ID on every LLM call and every agent handoff" and building "one stitched trace before anything else."
- **Why it looks unbuilt/untested**: Multiple independent write-ups (fiddler.ai, atlan.com, getmaxim.ai) converge on the same gap — standard observability tooling wasn't built for cross-agent boundaries — and each proposes a DIY recipe (manual correlation IDs, custom distributed tracing) rather than pointing to an existing off-the-shelf tool that solves it.
- **Maturity**: PARTIAL
- **Verdict notes**: Mature, maintained observability products already cover general cross-agent tracing — LangSmith, Langfuse (multi-agent graph view), Arize Phoenix, plus OpenTelemetry GenAI semantic conventions with `invoke_agent`/handoff spans and the cross-vendor OpenInference format. But a 2026 dev.to evaluation of "every AI agent observability tool on the market" explicitly concludes none of them do boundary-level context diffing — they show *that* a handoff happened, not *what context was lost* at it. The specific pattern (diffing dropped/truncated context at the boundary) remains a DIY gap inside an otherwise saturated general-tracing market, so PARTIAL rather than SATURATED or OPEN.

### P2: Checkpoint-and-rollback state management for mid-run multi-agent failures
- **What it is**: A pattern where shared state is checkpointed after every agent step so that if a downstream agent fails partway through, the system can roll back to the last consistent checkpoint instead of leaving outputs in an inconsistent half-applied state.
- **Evidence**: WebSearch found a Latenode community builder describing a three-agent customer-analysis pipeline: "If agent two fails partway through processing agent one's output, you're left in an inconsistent state. Recovery logic is complex." Another practitioner in the same thread described checkpointing shared state after each step and rolling back to the last checkpoint as their workaround.
- **Why it looks unbuilt/untested**: The practitioners describing this are hand-rolling the checkpoint/rollback logic themselves rather than citing a framework feature; the complaint is phrased as "recovery logic is complex," i.e., a problem they solved ad hoc, not one a library solved for them.
- **Maturity**: PARTIAL
- **Verdict notes**: LangGraph, CrewAI, and Google ADK already ship checkpointing primitives (confirmed via `gh search repos "langgraph checkpoint"` — multiple maintained checkpoint-saver backends: MySQL, DynamoDB, Firestore), and academic work (COCO, arXiv 2508.13815; a NeurIPS 2026 reliability/fallback-patterns paper with a 150-question benchmark) targets rollback directly. But a Feb 2026 Diagrid engineering post explicitly argues "checkpoints are not durable execution — why LangGraph, CrewAI, Google ADK and others fall short for production agent workflows," noting no built-in fallback routing or dead-letter queue. Practitioners (Latenode community) are still hand-rolling true rollback-to-last-consistent-state logic, so the gap is real but partially addressed by existing framework primitives — PARTIAL.

### P3: A standard "orchestration contract layer" above agent-plumbing frameworks
- **What it is**: A missing layer above LangChain/LangGraph-style agent plumbing that would standardize dynamic agent discovery, fault tolerance, and handoff contracts for production multi-agent deployments, rather than leaving every team to build this themselves on top of the plumbing frameworks.
- **Evidence**: A dev.to/personal-blog essay (talvinder.com, "Orchestration Specs Like Symphony Are the Missing Layer for Multi-Agent Engineering") argues explicitly that "LangChain and LangGraph provide plumbing for building agents but lack production orchestration features," framing this as a "missing contract layer" for coordination — close to a "why is there no" framing.
- **Why it looks unbuilt/untested**: The author is proposing a new spec ("Symphony") precisely because, in their account, nothing standard fills this role yet; it's a single blog-post proposal, not a maintained, adopted project.
- **Maturity**: PARTIAL
- **Verdict notes**: Found one real, governance-backed candidate: OpenEAGO, a FINOS (Linux Foundation) project defining a contract layer (standard message schema, signatures, policy bundles) above LangGraph-style plumbing for regulated multi-agent workflows — but it's pre-1.0 (v0.1.0) with 2026 roadmap items still pending, no evidence of adoption found. `gh search repos "multi-agent orchestration framework"` returns a long list of plumbing frameworks (swarms, agency-swarm, Shannon, Mentis) but none of these are the missing contract layer itself — they're exactly the plumbing layer the pattern says needs something above it. Gap is real; a resourced org is attempting to close it but hasn't yet — PARTIAL.

### P4: Automated regression testing that catches context loss at specific agent-to-agent boundaries
- **What it is**: Test tooling that treats each agent handoff as a testable contract (input/output schema capture at each boundary) and runs automated regression tests specifically to catch context loss or schema drift introduced at a given transition, rather than only testing end-to-end task success.
- **Evidence**: WebSearch (qawerk.com "Testing Multi-Agent AI Systems: How to Catch Handoff Failures Before They Reach Users") and getmaxim.ai both recommend "capturing input and output schemas at each boundary" and "automated regression testing that catches context loss at specific agent transitions" as mitigations, implying this isn't standard practice yet.
- **Why it looks unbuilt/untested**: Framed as a recommended practice in guide-style content rather than a named, widely-adopted testing product; the MAST study (Cemri et al., NeurIPS 2025, cited secondhand by multiple sources) reports multi-agent failure rates of 41-86.7% with handoff/specification issues as the largest cluster (~41.8%), suggesting the testing gap is real and large, not yet closed.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch and `gh search repos "agent handoff testing"` found no dedicated, adopted off-the-shelf product for automated handoff-contract regression testing. What exists: a cluster of vendor/consultancy DIY recipes (Braintrust's three-level testing, Autonoma, ITECS fixture replay, qawerk, a Testomat.io Claude Code + Playwright pipeline using a handoff.json contract), one narrow research prototype (a DVCon paper on hardware-verification regression triage), and a GitHub repo (PromptSentry) that bundles "multi-agent handoff testing" as one minor feature inside a broader red-teaming toolkit, not a dedicated regression tool. Real, large gap (per the MAST failure-rate data) with only narrow/DIY coverage — PARTIAL.

### P9: Standardized agent-trajectory format for cross-system reuse (RL, continual learning, analytics)
- **What it is**: A shared data format (ATIF) for recording full agent trajectories — not just final outputs — so the same trajectory data can power reinforcement learning, continual learning, and analytics across different tools, instead of each system logging agent runs in its own bespoke shape.
- **Evidence**: GitHub PR "RFC: ATIF v2.0 with streaming, lineage, and strong semantics" (harbor-framework/harbor, 2026-11-06, 8 reactions/7 comments) states "ATIF has become the de facto standard for sharing trajectories and is widely used throughout the industry. Agent trajectories have become a multi-purpose data source powering RL, continual learning, analytics, and more," and proposes streaming/lineage additions.
- **Why it looks unbuilt/untested**: The RFC itself argues the *current* v1 spec is insufficient (no streaming, no lineage, weak semantics) for the uses people are already trying to put it to — i.e., the standard exists but practitioners are already outgrowing it, which is a live gap in the format rather than a solved problem.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch confirms ATIF already has multi-vendor, maintained adoption: Harbor's own docs, an Arize Phoenix import/export integration, NVIDIA's NeMo Agent Toolkit (`nat.atif` across three doc versions, v1.7/v1.8/latest), a Go implementation (go.googlesource.com/exp), and a Rust crate (`vtcode-exec-events`). Multiple agent runtimes (Terminus-2, OpenHands, Mini-SWE-Agent, Gemini CLI, Claude Code, Codex) generate ATIF trajectories automatically. The v2.0 RFC cited in the digest is an incremental versioned evolution of an already-adopted cross-vendor standard (v1.4 → v1.7 already shipped subagent references), not evidence the pattern itself is unbuilt — SATURATED.
