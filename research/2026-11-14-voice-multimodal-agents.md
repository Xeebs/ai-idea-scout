## Candidate patterns

### P1: Single local multimodal model replacing the STT+LLM+TTS vendor pipeline
- **What it is**: Instead of chaining separate Deepgram/Cartesia-style STT and TTS vendors around an LLM, builders are running one local audio-native model (e.g. LFM3-Audio-2B) that does STT, reasoning, and TTS in one process, with native `tool_calls` support instead of parsing `<tool_call>` text out of a transcript.
- **Evidence**: GitHub PR `ArpanSM/forge-voice#1` ("Spike: voice booking policy, WebRTC and turn-taking (do not merge)", 2026-11-06, 1 comment) — commit note: "The local profile now works end to end without Deepgram or Cartesia... STT/TTS/LLM: LFM3-Audio-2B on 127.0.0.1:8082; no API key or per-minute cost... native tool_calls once the tools are attached to the Agent."
- **Why it looks unbuilt/untested**: This is a single work-in-progress PR explicitly marked "do not merge" — a spike, not a shipped pattern. No packaged framework surfaced in this run that productizes "local omni-model replaces the 3-vendor voice pipeline with native tool calling" as a reusable component.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found ~6 independent repos built in the last two weeks on LFM3-Audio-2B doing exactly this (`MhaWay/lfm3-realtime` "no ASR/LLM/TTS pipeline", `baka-onii/VoxLoop`, `Red-fuchs/kitsune` with a tool router, `oki/poc-lfm3-audio`), but all are brand-new, single-maintainer, un-starred hobby projects, not a maintained framework. WebSearch found only vendor cloud products doing the structural equivalent (Gemini 3.1 Flash Live, PolyAI Dialog-RSN-1) and a benchmark paper (EVA-Bench) listing open components for a hybrid stack — no evidence of a reusable, evaluated local-tool-calling package. Real gap, already being chased by hobbyists in parallel.

### P2: Telephony-specific fine-tuning of turn-detection models via phone-audio augmentation
- **What it is**: General-purpose turn-detection models (e.g. "Smart Turn") trained on wideband audio mis-fire far more often on real phone-channel (narrowband/Telnyx) audio, cutting callers off; builders are fine-tuning with phone-audio augmentation data to close the gap.
- **Evidence**: GitHub issue `timbal-ai/timbal#242` ("Voice agents: latency & quality roadmap", 2026-11-04) — "On a simulated phone channel, I measured v3.2 cutting callers off about 1.8x as often as on wideband (18.05% vs 9.86%). I fine-tuned it with phone-audio augmentation and got 8.64% vs 11.09% for a control."
- **Why it looks unbuilt/untested**: One contributor's own measurement and one-off fine-tune, reported as a roadmap issue rather than a published dataset, benchmark, or reusable augmentation pipeline others can adopt.
- **Maturity**: OPEN
- **Verdict notes**: GitHub search for turn-detection repos (`pipecat-ai/smart-turn`, `TurnWave`, `vogent/Vogent-Turn-80M`, `miuda-ai/smart-turn-rs`) found open checkpoints that are fine-tunable but none documents training or evaluation on narrowband (8kHz) phone audio; LiveKit's own docs only suggest VAD-threshold tweaks for noisy phone audio, not a turn-detection fine-tune. WebSearch for a published telephony-augmentation dataset or pipeline came up empty — only the single roadmap issue cited in the digest.

### P4: WebMCP — standardized tool exposure for in-browser agents (voice or otherwise) to act on web UIs
- **What it is**: A proposed web standard (WebMCP) letting a web page register tools that any AI agent running in the browser — including voice-driven agents — can call directly, instead of each agent scraping the DOM or screenshotting the page.
- **Evidence**: GitHub PR `streamlit/streamlit#17593` ("[spec] WebMCP tools for Streamlit apps", 2026-10-21, 6 comments, 1 reaction) — "Adds a product spec for exposing Streamlit apps to browser agents through WebMCP... a proposed web standard that lets a page register tools for AI agents running in the user's browser."
- **Why it looks unbuilt/untested**: Explicitly a "[spec]" PR for one framework (Streamlit), not an adopted cross-framework standard; WebMCP itself is described as "proposed," with no evidence in this run of multimodal/voice agents actually consuming it yet.
- **Maturity**: SATURATED
- **Verdict notes**: WebMCP is already a well-resourced, multi-party effort, not an open gap: official spec repo `webmachinelearning/webmcp`, Google's own `GoogleChromeLabs/webmcp-tools` adoption toolkit, Chrome 149 origin trial with DevTools support, Microsoft Edge support reported, and multiple independent third-party implementations already on GitHub (`MiguelsPizza/WebMCP`, `runtypelabs/persona`, `choyiny/saasmail` using it, `aozorae/Edgechat`). The voice-agent-specific consumption angle is early, but the standardized-tool-exposure gap itself is actively being closed by Google and Microsoft, which is squarely the SATURATED bar.

### P5: Interruption vs. backchannel vs. noise is still a hand-tuned classification problem, fragmented across vendors
- **What it is**: Every voice-agent vendor (LiveKit, Cartesia, Deepgram, Quiq, poly.ai) ships its own heuristic for telling a real interruption from a short backchannel ("yeah," "okay") or background noise, with no shared benchmark or consensus approach — each treats it as a bespoke classification layer bolted onto turn detection.
- **Evidence**: WebSearch (`"voice agent" interruption handling "has anyone built"...`) surfaced parallel, non-interoperable write-ups from LiveKit ("turn detection and interruption handling," "adaptive interruption handling"), Cartesia (`docs.cartesia.ai/line/agent-patterns/interruption-handling`), Deepgram (`flux-tts/interrupt-handling`), and Quiq ("why the interruption problem is architecture"); one guide frames it as still "widely treated as an unsolved problem in AI-powered voice agents."
- **Why it looks unbuilt/untested**: No shared dataset, benchmark, or open classifier for backchannel-vs-interruption-vs-noise surfaced across five+ vendor write-ups — each vendor re-solves it internally, which is itself the complaint-shaped signal (an "unsolved problem" repeatedly re-described, not converged on).
- **Maturity**: PARTIAL
- **Verdict notes**: Found closer prior art than the digest implied: academic benchmarks (Sesame's TurnBench, Full-Duplex-Bench v1/v1.5) explicitly score interruption-vs-backchannel false positives, and a Hugging Face `bargein-classifier` model exists trained on AMI/ICSI meeting corpora. But the classifier's own card flags English-only coverage, a domain gap vs. real voice-agent audio, and weak-supervision labels (not human-audited barge-in judgments), and the benchmarks are research evaluation tools, not a reusable production classifier vendors have converged on. The fragmentation complaint stands even though isolated pieces exist.

### P6: Full-duplex models as a structural fix to turn-taking, replacing heuristic interruption detection
- **What it is**: Instead of layering interruption/backchannel classifiers on top of a half-duplex (strictly-alternating) voice pipeline, some vendors are adopting full-duplex models that listen and speak simultaneously, sidestepping the turn-detection problem at the architecture level rather than patching it with heuristics.
- **Evidence**: WebSearch (`voice AI agents multimodal agents news November 2026`, aggregated via voiceaispace.com) — "Retell AI added OpenAI's GPT-Live-1 for phone agents... It is a full-duplex model. The full-duplex model talks to the caller directly while the agent's existing [pipeline runs]" (Nov 2, 2026).
- **Why it looks unbuilt/untested**: Reported as a single vendor integration via an aggregator, with no independent benchmark in this run comparing full-duplex architectures against the heuristic approach in P5 on interruption/backchannel accuracy.
- **Maturity**: SATURATED
- **Verdict notes**: This is already well-resourced-team territory: OpenAI's GPT-Live (shipped, integrated by Retell AI for phone agents per the digest's own evidence), Kyutai's open-weight Moshi, and Google/Gemini Live are all shipped full-duplex systems, plus independent academic benchmarks exist to compare them head-to-head against heuristic pipelines (Full-Duplex-Bench v1/v1.5, FLEXI, "A Harness for Synthesizing Diverse Naturalistic Full-Duplex Conversations" fine-tuning Moshi). GitHub also shows open full-duplex implementations (`adventists-ai/sophon-realtime`, Apache-2.0, OpenAI Realtime/GPT-Live compatible). The structural shift is underway with multiple shipped products and papers, not just one vendor's integration.
