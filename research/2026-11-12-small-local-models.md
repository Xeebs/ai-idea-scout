## Candidate patterns

### P1: Pre-purchase hardware-fit benchmarking for local LLMs
- **What it is**: A standalone tool that lets someone simulate/feel the generation speed a given local LLM would have on a *specific* piece of hardware before they buy that hardware, rather than guessing from spec sheets or secondhand benchmarks.
- **Evidence**: Hacker News, "Show HN: Llmspeed – feel how fast a local LLM runs before you buy the hardware" — 331 points, 86 comments (2026-10-17), the highest-engagement item in either run.
- **Why it looks unbuilt/untested**: The sheer engagement (331pts/86cmt, far above every other item collected) on a single hobby project suggests the "will my hardware run this model well" question is widely felt but under-served by existing tooling — the pitch itself is "feel it before you buy," implying no good pre-purchase answer existed.
- **Maturity**: SATURATED
- **Verdict notes**: `llmfit` (Rust, MIT, open-source, actively promoted via multiple 2026 blog posts) detects local CPU/RAM/GPU and ranks models by quality/speed/fit/context plus a "plan" mode for hypothetical hardware; the very `llmspeed` tool in the digest's own evidence already ships 30-machine × 15-model estimates with documented accuracy caveats; `llm-checker`, `inferbench`, and multiple GitHub hardware-benchmark repos (gauravvij/llm-hardware-benchmarking, sclliang/LLMBench, MarcelDIY/Benchmark) round out the space. Multiple maintained tools already squarely answer "will my hardware run this model."

### P2: Multi-device distributed local inference over consumer hardware (MLX + RDMA)
- **What it is**: Splitting a large model's inference workload across multiple local machines (e.g., several Mac Studios) connected via RDMA, so a model too big for one device's memory can still run entirely locally with no cloud component.
- **Evidence**: Hacker News, "Local and Distributed Large LLM Inference with MLX and RDMA on Mac Studio" (Apple ML research), 8 points/1 comment (2026-10-16).
- **Why it looks unbuilt/untested**: Low engagement (8pts) relative to topic importance suggests this is still research-stage/niche rather than a packaged, easy-to-adopt workflow — no evidence of a turnkey product wrapping this technique for non-Apple-research users.
- **Maturity**: SATURATED
- **Verdict notes**: `b4rtaz/distributed-llama` (3,137 stars, pushed 2026-11-10, "connect home devices into a cluster to accelerate LLM inference") and `firstbatchxyz/dnet` (75 stars, "Distributed LLM Inference for Apple Silicon Clusters") are maintained, general-purpose answers to the exact "split a too-big local model across several consumer/Apple Silicon machines" problem; `gh search repos "distributed llm inference"` additionally surfaced a dozen actively-pushed 2026 projects (exo-cuda, rig, llmlet, Ghostlink, QuantumFlow). The specific MLX+RDMA paper is research-stage, but the general gap it targets is already closed by multiple maintained OSS clusters.

### P3: Offline model + static knowledge-corpus bundles for zero-connectivity assistants
- **What it is**: Pairing a small local LLM with an offline knowledge base (Kiwix's offline Wikipedia mirror) packaged together on removable media (a USB stick) so the combination works with no network at all — framed explicitly as a "survival assistant."
- **Evidence**: Hacker News, "Offline survival assistant – local LLM and Kiwix, runs from a USB stick," 29 points/16 comments (2026-11-05).
- **Why it looks unbuilt/untested**: Framed as a single hobbyist's README-documented project (github.com/sdalberto/ia-da-sobrevivencia), not a maintained product category — the engagement (16 comments) suggests real interest in the "model + corpus, zero connectivity" pattern beyond this one implementation.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub search for "offline survival assistant" alone returned at least 8 independent, actively-pushed 2026 implementations of this exact pattern (local LLM + offline knowledge/RAG, zero connectivity): dylanfeltus/survival-device, irron/offline-survival-assistant, vorptix-droid/AspenbyBushnet, boddyeric1-gif/aegis-survival, salty-yv/offline-lifeline, RaccoonOnion/ash (56 emergency-response RAG packs, on-device Gemma 4), agentsmill/lastbox (Raspberry Pi + LoRa radio). Many trace to the "Gemma 4 Good" Kaggle hackathon, confirming this is a well-populated, actively-worked genre rather than an unmet need, even though no single dominant long-term-maintained product has emerged yet.

### P4: Browser-native small LLM via WebGPU, no install and no server
- **What it is**: Running a small local model directly inside the browser tab via WebGPU to power an app (a file/notes organizer, an incremental game) with zero install and no backend server.
- **Evidence**: Hacker News, "Show HN: Rocus: Browser local LLM that organizes your websites, notes and files," 4 points (2026-10-28); and "Show HN: Harness Corp – An incremental game powered by a local LLM using WebGPU," 4 points (2026-10-28) — two independent Show HN launches of the same underlying pattern in the same week.
- **Why it looks unbuilt/untested**: Both are individual Show HN launches with low initial traction, not an established framework/library that other builders are standardizing on — the pattern (small model fully in-browser via WebGPU) is being reinvented per-app rather than shared as infrastructure.
- **Maturity**: SATURATED
- **Verdict notes**: `mlc-ai/web-llm` is exactly this infrastructure — 19,368 stars, pushed 2026-11-10, "High-performance In-browser LLM Inference Engine" via WebGPU, with starter kits (lablab-ai's Next.js/Chrome-extension/simple-chat templates) already built on top of it. The two Show HN apps in the evidence are almost certainly consumers of WebLLM (or equivalent) rather than evidence of unmet infra need; the shared infrastructure the digest claims is missing already exists and is widely adopted.

### P5: Pure-JVM (non-Python) local inference runtime
- **What it is**: A local LLM inference engine that runs entirely inside the Java Virtual Machine with no Python dependency, positioned explicitly as the successor to the existing Jlama project, for use inside JVM-based agent frameworks.
- **Evidence**: GitHub, "Feature request: Add jinfer (Quixotic) as a local, in-JVM inference provider - the successor to Jlama," embabel/embabel-agent#2208, 4 reactions (2026-10-28). Requester's own framing: "In my mind it's the new, much improved Jlama: pure-Java LLM inference that runs entirely inside the JVM - no Python."
- **Why it looks unbuilt/untested**: It is a feature *request* on someone else's project, not a shipped integration — the requester is asking because the enterprise-Java path to local inference is currently a gap serious enough to name explicitly and ask for.
- **Maturity**: SATURATED
- **Verdict notes**: `tjake/Jlama` — the project this request names as the thing to succeed — is itself a maintained, 1,300+ star, pure-Java LLM inference engine already integrated into Quarkus and LangChain4j (per Quarkus.io and Quarkiverse docs), i.e. the pure-JVM pattern is already a working, documented, ecosystem-integrated category, not just a request. Additional current entrants (oujingzhou/vllm4j, DenzoSOFTHub/LLMPlayer, jarorosFork/modelJ, CodyEdwin/JInfer) confirm multiple independent, actively-pushed 2026 implementations of "pure-Java, no-Python local LLM inference." The specific "jinfer/Quixotic" project itself could not be confirmed to exist via web search, but the category it would occupy is already filled.

### P6: Native-mixed-precision-preserving quantization of fine-tuned checkpoints
- **What it is**: A quantization workflow (RTN) applied directly to a fine-tuned model checkpoint while matching the model's own native mixed-precision tensor format, rather than converting to a generic quantization format, to minimize deployment-footprint loss and keep compatibility.
- **Evidence**: GitHub, vllm-project/llm-compressor#3372, "[Research Hub Proposal] Native-format RTN quantization of an ms-swift fine-tuned DeepSeek-V4-Flash checkpoint," 7 comments (2026-10-23). Submitter's own comment thread walks through inspecting "tensor names, shapes, dtypes, scales, and configuration" to match the native format before quantizing.
- **Why it looks unbuilt/untested**: Framed by the author as a "Research Hub Proposal" with a from-scratch custom `DSV4FlashNativeQuantizer` class built because no existing converter handled this specific fine-tuned-checkpoint-to-native-format path — a one-off, not a reusable tool yet.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos` for "RTN quantization" and "quantization checkpoint native format" returned no dedicated tool for this exact native-format-preserving path on arbitrary fine-tuned checkpoints. The proposal does live inside `vllm-project/llm-compressor`, a large maintained production quantization framework — so the surrounding infrastructure is mature, but the specific capability (auto-detecting and preserving a model's own native mixed-precision tensor layout through RTN on a fine-tuned checkpoint) is still a hand-built, unmerged one-off within it, not a general reusable feature. Real gap, but narrow enough that calling it fully OPEN would overstate it given the mature host project.

### P7: Interactive neuron-level ablation/visualization for small local models
- **What it is**: A tool that opens a local LLM as a navigable 3D graph of its internals, letting a user cut out parts of the network interactively and observe what breaks, as a hands-on interpretability/debugging technique.
- **Evidence**: Hacker News, "NeuronDump: Open a local LLM as a 3D graph, cut parts, see what breaks," 3 points (2026-10-25).
- **Why it looks unbuilt/untested**: Single hobbyist GitHub project (github.com/aymen94/NeuronDump) with minimal traction so far — framed by its own title as exploratory ("see what breaks"), not a validated interpretability methodology with broader tooling support.
- **Maturity**: PARTIAL
- **Verdict notes**: NeuronDump itself is the only tool found combining a navigable 3D graph, live ablation/steer/patch, and loading everyday local GGUF files (Ollama/LM Studio/llama.cpp) — it's real but solo/early. Mature adjacent tooling exists for pieces of this (`TransformerLensOrg/TransformerLens`, long-maintained mechanistic-interpretability library; `TransformerLensOrg/CircuitsVis` for activation visualization; `FailSpy/abliterator` for ablation; Meta's LM Transparency Tool ACL 2024 demo), but none of these are a consumer-friendly 3D explorer for local GGUF models the way NeuronDump pitches itself — a serious build combining mature mechinterp libraries with a polished UI for everyday local-model users would be meaningfully differentiated.

### P8: Real-time interactive world-model generation on consumer-tier GPUs
- **What it is**: A local generative "world model" that converts a still image into an interactive, real-time-controllable video, explicitly tuned to run on consumer GPUs (RTX 3060/4060-class), not datacenter hardware.
- **Evidence**: Reddit r/LocalLLaMA, "I'm releasing a Local World Model Ive been building that turns images into interactive videos you control in real time. It works on RTX 3060, 4060 and anything above" (2026-11-11), self-reported by the builder as having been in development "for a few months" on that subreddit, linking a Hugging Face model (lucidml/gta).
- **Why it looks unbuilt/untested**: Solo-builder release on a single weekend, hosted via a personal demo site rather than integrated into any established local-inference tooling (Ollama/LM Studio-style ecosystems) — the "world model that fits on a 3060" niche currently has one independent implementation.
- **Maturity**: PARTIAL
- **Verdict notes**: Several well-resourced teams are actively shipping "real-time interactive world model on consumer GPU" research (Overworld's Waypoint-1/1.5 with papers and HF releases, reportedly running on RTX 3090 through RTX 5090 with a 360p variant aimed at lower-end hardware; Skywork AI's Matrix-Game 4.0 on RTX 5090; InSpatio-WorldFM, open-source, ~10 FPS on RTX 4090). None of these confirm RTX 3060-class performance specifically (the digest's `lucidml/gta` claims a lower floor than any verified competitor), and none are integrated into mainstream local-inference tooling (Ollama/LM Studio) or independently evaluated — real research momentum, but genuinely entry-level-GPU support and evaluation remain unproven, so PARTIAL rather than SATURATED.

### P9: Latency/incentive-aware coordination for idle-consumer-GPU distributed training
- **What it is**: Splitting model training into small tasks distributed to volunteers' idle consumer GPUs in exchange for credits, as described in a Microsoft patent filing — the pattern is crowd-sourced/volunteer distributed training coordination for models, as an alternative to centralized datacenter training.
- **Evidence**: Reddit r/LocalLLaMA, "Microsoft files a patent application to train AI models on idle consumer GPUs" (2026-11-11). Top discussion point from the poster themselves: no advertised payout rate, and "home internet latency feels like the bigger problem" — a direct complaint about the unsolved coordination/incentive design.
- **Why it looks unbuilt/untested**: The source is a patent *application*, not a working system, and the community's own reaction names the two unresolved problems (latency tolerance, incentive/payout economics) that would need solving before this is viable — an explicit "this isn't figured out yet" signal.
- **Maturity**: PARTIAL
- **Verdict notes**: Multiple 2026 projects already attempt idle-consumer-GPU distributed training with incentive layers — Dispersed (training network explicitly targeting idle home/office GPUs, names the bandwidth problem as its core obstacle), CrowdGPT (open-source volunteer training of a 1B-param model), Gensyn (cryptographic training verification, reported 500k+ GPU network, unconfirmed primary source), SynonAI/AIyield/Neurolov (token-incentive layers). However, web coverage is almost entirely project marketing/press/blog posts with no independent evaluation of throughput, payout fairness, or latency tolerance — the community's named unresolved problems (latency, incentive economics) match what these projects claim to solve but haven't publicly proven, so PARTIAL: real but unevaluated/narrow attempts exist, leaving room for a credibly evaluated entrant.
