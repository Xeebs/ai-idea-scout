## Candidate patterns

### P1: Managed/abstracted retrieval that removes pipeline maintenance from app developers
- **What it is**: A retrieval layer that lets a team ship an AI application without owning chunking, embedding refresh, index management, and the general upkeep of a RAG pipeline — the pipeline becomes an API call, not infrastructure the team maintains.
- **Evidence**: Hacker News, Show HN: "We wanted to build an AI application, not maintain RAG pipelines" (akropolys.cloud, 2026-11-10, 3pts/1cmt) — the submission title itself is complaint-shaped.
- **Why it looks unbuilt/untested**: The Show HN post is a single low-traction submission (3 points), suggesting an early, unvalidated attempt rather than an adopted solution; no competing high-traction product surfaced in the same run.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple shipped, well-resourced products already close this exact gap — Vectara (full managed pipeline, enterprise pricing), Ragie (managed ingestion/chunking/indexing/retrieval API), Amazon Bedrock Managed Knowledge Base (GA June 2026, connects SharePoint/Confluence/Drive/S3), Google Vertex AI RAG Engine, Azure AI Search, Pinecone Assistant, and Contextual AI. The Show HN post is one hobbyist re-discovering a category that AWS/Google/multiple funded startups already ship.

### P2: Automated golden-set regression testing for RAG retrieval quality
- **What it is**: Lightweight eval harnesses that run a RAG pipeline's retrieval+generation against a maintained "golden set" of question/answer pairs to catch quality regressions when chunking, embeddings, or prompts change.
- **Evidence**: Hacker News, Show HN: "Python script to evaluate your RAG pipeline against a golden set" (github.com/infrixo-systems/rag-evaluation-starter, 2026-10-24, 4pts).
- **Why it looks unbuilt/untested**: Framed as a standalone "script," not a maintained product; low engagement (4pts, 0 comments) suggests this remains a one-off tool rather than something teams have standardized on.
- **Maturity**: PARTIAL
- **Verdict notes**: Real implementations exist but are fragmented and mostly small/single-maintainer: EvalFlow (DEV Community open-source CI regression gate), golden-dataset-studio (tiny PyPI package pairing RAGAS+DeepEval), TruLens and RAGAS-based CI patterns, and AGRO (self-described as "good for regression, not leaderboard-style benchmarking"). Braintrust and Traceloop offer this as part of broader paid eval platforms. No single dominant standard tool found — a differentiated, well-evaluated build remains viable.

### P3: Leakage auditing specific to agent memory, distinct from raw-RAG retrieval leakage
- **What it is**: An evaluation tool category that measures how much sensitive/private information leaks through an agent's persistent memory layer as opposed to its raw retrieval step — treating "memory" and "retrieval" as separately-auditable attack surfaces.
- **Evidence**: Hacker News, Show HN: "Raw RAG leaks 0%, but agent memory leaks 67%" (github.com/harishbalasubramanian/sentinel-eval, 2026-11-09, 3pts) — the title reports a stark gap between the two leakage rates it measured.
- **Why it looks unbuilt/untested**: Single low-traction Show HN (3pts, 0 comments) with no visible follow-on adoption; the 67% figure is self-reported by the tool's own author with no independent corroboration found in this run.
- **Maturity**: PARTIAL
- **Verdict notes**: Academic benchmarks now exist that specifically separate memory-channel from retrieval-channel leakage — MEXTRA (ACL 2025, black-box memory-extraction attack, up to 42% extraction efficiency), AgentLeak (IEEE Access 2026, 1,000-scenario benchmark instrumenting inter-agent messages/shared memory/tool I/O), and CIPL (arXiv 2609.21686, channel-aware framework explicitly reporting memory-based leakage as "near-saturated" vs. retrieval-mediated as "partial"). These validate the gap's premise but are research artifacts, not maintained audit products teams can run — no commercial/open tool with adoption was found beyond the original single-author sentinel-eval.

### P4: Structure-preserving / re-ingestion-cheap chunking strategies
- **What it is**: Chunking approaches that keep document structure (e.g., keeping a policy together with its exception) rather than flattening documents into fixed-size chunks, specifically designed so that changing the chunking strategy later doesn't require re-ingesting the entire corpus.
- **Evidence**: WebSearch supplement (`RAG chunking strategy reddit "I wish" complaints developers`) surfaced a developer write-up aggregating RAG failure modes (chunking, stale index, hybrid search) and a blog citing a Reddit discussion arguing chunking is the source of most quality issues and that structure should be preserved rather than flattened; recurring theme across the aggregated sources: "a bad chunking strategy requires re-ingesting the entire corpus, which makes changing strategy expensive."
- **Why it looks unbuilt/untested**: All surfaced evidence is blog commentary describing the problem (cost of re-chunking, structure loss) — no specific named implementation of a "cheap-to-re-chunk" or structure-preserving system was found in this run; the underlying Reddit thread itself could not be directly located, only paraphrased via a blog.
- **Maturity**: PARTIAL
- **Verdict notes**: The structure-preserving half is saturated as a primitive (LangChain/LlamaIndex header/markdown splitters, widely documented "structure-first-then-semantic" hybrid pattern), but "cheap to change chunking strategy later without full re-ingestion" is only described as a DIY engineering pattern in blogs (content-hash-per-chunk versioning so only changed chunks re-embed) — no named open-source library or product packages both properties together. GitHub search for "structure preserving chunking RAG" / "semantic chunking RAG" turned up only personal/hackathon/learning repos, nothing maintained at scale.

### P5: Automated graph-maintenance for GraphRAG (re-extraction/re-summarization on document change)
- **What it is**: Tooling that automatically re-extracts entities and re-summarizes affected parts of a knowledge graph whenever source documents change, so a GraphRAG deployment doesn't silently degrade from a stale graph.
- **Evidence**: WebSearch supplement surfaced a Reddit thread (r/Rag, dated Aug 2025 per the mirror snapshot, 80 upvotes/36 comments) where a poster concluded GraphRAG "wasn't mature enough" for production use at their company, scales poorly, and reliable production methods are sparsely documented; a second post titled "The GraphRAG Trap: Why I Uninstalled Neo4j for My Personal Assistant" cites a "maintenance tax" as the reason for abandoning it.
- **Why it looks unbuilt/untested**: Both pieces of evidence describe abandoning GraphRAG rather than any team shipping an automated-maintenance solution; several practitioner blogs state generically that "teams that don't automate this maintenance end up with stale graphs" without naming a tool that does.
- **Maturity**: PARTIAL
- **Verdict notes**: Implementations exist but are narrower/clunkier than "automatic": Microsoft's own GraphRAG ships an `update` CLI command that preserves existing entities/relationships when adding new documents, but requires matching index/tool versions and manual invocation; nano-GraphRAG hashes chunks to detect new ones but still recomputes community detection on every update; research (EraRAG, arXiv 2506.20963; Temporal GraphRAG, arXiv 2510.13590) targets the update-cost problem but isn't productized. This explains why practitioners (the r/Rag and "GraphRAG Trap" posts) still describe abandoning GraphRAG over maintenance tax despite these existing update paths — the gap between "has an update command" and "doesn't need babysitting" is real and unclosed.
