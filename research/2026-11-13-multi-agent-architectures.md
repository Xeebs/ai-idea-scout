## Candidate patterns

### P1: Cross-agent debugging via correlation IDs and heartbeat logs (observability gap)
- **What it is**: A tracing layer that stitches together what happened across multiple agent boundaries in one multi-agent run — correlation IDs stamped on every message/tool call, plus a "heartbeat log" per wave of agent execution, so a failure can be localized to a specific handoff rather than re-read from scratch across agents.
- **Evidence**: A DEV Community guide (dev.to/whoffagents) opens with "the debugging guide I wish I had when we started" and recommends the heartbeat-log pattern. A getmaxim.ai practitioner report says Langfuse shows wrong per-agent inputs in supervisor orchestration and Arize Phoenix requires manual context propagation for multi-agent trace consolidation, concluding none of the current tools deliver this reliably.
- **Why it looks unbuilt/untested**: Multiple existing observability vendors (Langfuse, Arize Phoenix) are explicitly named as inadequate for this specific multi-agent case by a practitioner who tried them; the DEV post is a self-authored stopgap guide, not a tool.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirms general agent tracing is mature (Langfuse, LangSmith, Arize Phoenix, AgentOps, AG2's OpenTelemetry spans — all maintained products/libraries), but a 2026 DEV Community roundup (dev.to/nicolas_fainstein) explicitly names cross-agent correlation and fleet-wide heartbeat dashboards as the still-immature area these tools don't cover; no dedicated correlation-ID+heartbeat tool found on GitHub or web search. A real but narrow/unmet gap inside a saturated adjacent category.

### P2: Org-design governance primitives applied to agent failures (decision rights, escalation, termination)
- **What it is**: Borrowing organizational-design concepts — explicit decision rights, escalation triggers, and termination conditions — as first-class constructs in a multi-agent framework, instead of leaving them implicit in prompt text or ad hoc code.
- **Evidence**: aiweekly.co's "agentlas_org_chart Applies Org Design to Agent Failures" write-up argues undefined decision rights/escalation/termination conditions cause many multi-agent failures, and explicitly notes that as of May 2026 it is unknown whether LangChain, CrewAI, or AutoGen plan to adopt these concepts.
- **Why it looks unbuilt/untested**: The source itself flags that none of the three dominant frameworks have committed to integrating this; it's presented as a proposed framework/concept, not an adopted standard.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed via `gh repo view agentlas-ai/agentlas_org_chart` — it exists (1 star, created 2026-05-24, last pushed 2026-06-05, ~5 months stale as of this digest), a single early-stage project, not an adopted standard. WebSearch found only adjacent enterprise-governance commentary (Gravitee, Institute for Autonomous Companies, techstrong.ai) discussing decision-rights/escalation concepts in prose, none of it a shipped framework. LangChain/CrewAI/AutoGen integration unconfirmed anywhere.

### P3: Runtime self-repair for failed multi-agent runs
- **What it is**: A system that inspects a multi-agent run in-flight and amends it when something goes wrong, rather than requiring a full restart or post-hoc log analysis — repair as a runtime capability, not a debugging afterthought.
- **Evidence**: An October 13 aiagentstore.ai weekly roundup covers "ARIA" (Runtime Inspection and Amendment for Multi-Agent Systems), described as a data-driven framework and dataset posted to arXiv on 2026-10-14; the same roundup mentions a separate "steering-agent" design for goal drift.
- **Why it looks unbuilt/untested**: This is a freshly-posted arXiv research artifact, not a shipped tool — exactly the "research paper, no product" gap shape.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed arXiv 2610.20780 (Shen & Dong, 2026) with code at github.com/LabRAI/ARIA — real implementation exists (24k+ trajectories, 4 frameworks, 6 benchmarks, 8 host models) but `gh repo view` shows only 1 star, created 2026-08-31, last push 2026-10-12 — a research codebase, not a shipped/adopted runtime tool. No product or second implementation found.

### P4: Standardized shared-memory / blackboard layer across agent protocols
- **What it is**: A shared-state layer that multiple agents read/write to coordinate (the "blackboard pattern"), filling the gap that neither MCP (agent-to-tool) nor A2A (agent-to-agent) actually define — today teams hand-roll this via a database rather than using any standard.
- **Evidence**: sentra.app's "MCP vs A2A" piece states neither protocol defines shared memory and that no standard agent-memory protocol has foundation backing yet. Cockroach Labs' blog argues "the coordination point is the database, not the task message, and that's exactly what the protocol leaves undefined." A Blck Alpaca knowledge-base article describes teams manually implementing the blackboard pattern as a workaround, recommending hybrid shared-state-plus-messaging with single-threaded writes.
- **Why it looks unbuilt/untested**: Three independent infra-vendor sources converge on the same gap (no standardized shared-memory layer) and describe the current state as DIY/hand-rolled, not a mature, adopted spec.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search turns up many independent blackboard/shared-memory implementations — whiteducksoftware/flock (126 stars, actively maintained, pushed 2026-11-03) is the most mature, plus arvarik/bmas (4 stars), GennoBou/gnb-memorymcp (0 stars), and several student/toy projects — but each is its own framework-specific convention, not a cross-protocol standard. WebSearch confirms neither MCP nor A2A define shared memory and no standards-body spec exists as of 2026; "proprietary/framework-internal" is the consistent characterization. Point implementations exist, standardization doesn't.

### P5: Pre-build single-vs-multi-agent cost/latency linter
- **What it is**: A lightweight pre-flight check that estimates the token-cost and latency multiplier of a proposed multi-agent design before it's built, to counter the pattern of defaulting to multi-agent architectures that end up slower and less reliable than a simpler design.
- **Evidence**: An r/AI_Agents-sourced discussion (summarized via aicompass.dev/infinisynapse write-ups) gives a rule of thumb ("two or more yeses is multi-agent; otherwise use single agent with good tools"). A dev.to post (lars_winstand) reports a developer's 6-agent pipeline being "slower and less reliable than my old 2-agent one," complaining "benchmark posts all conveniently end right before deployment." An indiehackers.com post cites multi-agent architectures consuming 1.6-6.2x more tokens than comparable single-agent workflows (unverified secondary figure). This sits inside the broader Anthropic-multi-agent-research vs. Cognition's "Don't Build Multi-Agents" debate referenced on Pat McGuinness's Substack.
- **Why it looks unbuilt/untested**: The rule of thumb and cost complaints are informal community heuristics repeated across several blog write-ups; nobody cited has turned this into an actual pre-build estimation tool — it's all post-hoc "we built it and regretted it" commentary.
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos` for "agent architecture decision tool", "multi-agent cost linter", "should I use multi-agent" returned nothing. WebSearch found only generic per-call cost calculators — "Price My Agent" (ProductHunt, 8 upvotes, 9 comments) compares model pricing tiers on a single workflow, explicitly does not compare single-vs-multi-agent architecture or estimate latency (a commenter requested latency support, maker said "planned"). No tool anywhere does the specific pre-build single-vs-multi-agent cost/latency-multiplier estimate; only blog rules-of-thumb and after-the-fact regret posts exist.
