## Candidate patterns

### P1: Decision guidance for choosing a multi-agent orchestration pattern (vs. just listing them)
- **What it is**: A tool or guide that helps a builder decide *when* to use Graph vs. Swarm vs. Workflow vs. single-agent, rather than just documenting what each pattern is. Currently docs present the taxonomy flat with no decision logic.
- **Evidence**: GitHub PR `docs(site): clarify multi-agent pattern decision process` on strands-agents/harness-sdk (https://github.com/strands-agents/harness-sdk/pull/5553, 2026-10-26, 5 comments) — the PR description states the existing "Coordinate multiple agents" page "listed Graph, Swarm, and Workflow side by side without helping readers decide" which pattern to use.
- **Why it looks unbuilt/untested**: The evidence is a docs PR actively trying to patch this exact gap in one framework's docs — it's being hand-fixed in prose, not solved with a reusable decision tool/heuristic that could travel across frameworks (Microsoft Agent Framework, Google Cloud's taxonomy, CrewAI, LangGraph all ship their own flat pattern lists per the WebSearch supplement).
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found several single-author decision aids — Agentica's decision-tree docs, Dojogenesis's interactive 5-question "Pattern Selector" (dojogenesis.github.io/orchestration-guide/patterns.html), and a Glukhov practical guide — plus Claude-Code-specific skill pages (orchestkit, agent-skills) touching pattern selection. `gh search repos` for "multi-agent orchestration pattern decision" returned zero results. None is a maintained product or framework-agnostic tool with real adoption; they're scattered blog/single-page implementations, so the gap (a portable, well-adopted decision tool) is real but a serious build would be differentiated.

### P2: Durable, resumable goals that persist across agent handoffs and restarts
- **What it is**: Multi-agent systems today treat each delegation as a one-shot task; people want a "goal" object that survives across multiple agent handoffs, owner check-ins, and process restarts until its completion criteria are actually met.
- **Evidence**: GitHub feature request "Feature request: durable goal orchestration across agent handoffs" on agentprojectcontext/apx (https://github.com/agentprojectcontext/apx/issues/83, 2026-10-15, 2 comments). Maintainer reply: "This is a larger new feature: a goal that keeps going across agent results, owner answers and restarts until its criteria are met." A commenter (lufermalgo) describes their own stopgap: "a config-only supervisor stand-in (event-gated routine, one bounded task per wake, resume-same-session rules)."
- **Why it looks unbuilt/untested**: The maintainer explicitly frames it as unbuilt ("larger new feature," still at proposal stage), and the one person with a working approximation calls it a hand-rolled "stand-in," not a product.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch surfaced multiple maintained, well-resourced implementations squarely covering durable/resumable goal state across restarts and handoffs: Microsoft Agent Framework's Durable Extension (persists sessions, checkpoints workflow progress, recovers across distributed workers), Temporal's durable-workflow pattern for agent loops, Resonate's documented multi-agent example with checkpointed handoffs and human-in-the-loop suspension/resume, and Ambient Desktop's shipped "durable goals" feature (writes objective/plan/validation evidence to disk, reconciles on restart) — the apx issue's specific framing is narrow but the broader goal-persistence problem is already solved by several production-grade runtimes.

### P3: Vendor-agnostic relay layer for handing a coding session between different AI coding agents
- **What it is**: Infrastructure that lets a coding task move between different vendors' coding agents (e.g., Claude Code, Codex, other CLIs) mid-session rather than locking a workflow to one vendor's agent.
- **Evidence**: Show HN post "Agent-relay for multi-vendor coding sessions" (https://github.com/saranyan/agent-relay, posted to Hacker News 2026-10-27, 8 points, 1 comment).
- **Why it looks unbuilt/untested**: Single Show HN submission with only 1 comment and no visible adoption signal — a first attempt at a gap (vendor lock-in within multi-agent coding workflows) rather than an established pattern.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found a crowded field of maintained cross-agent handoff tools: `casr`/`continues` (session resume across agents), `handoff` CLI (PyPI package, reads one agent's transcript and injects into another, three-way mode incl. The specific `saranyan/agent-relay` Show HN repo is a minor entrant into an already well-populated space.

### P5: Agents that build cumulative shared history instead of resetting as ephemeral task teams
- **What it is**: Most multi-agent systems spin up agents as disposable "task teams" for one job and discard context afterward. The gap is agents that accumulate and share a persistent history/memory across tasks and teammates, so coordination improves over time instead of restarting cold each run.
- **Evidence**: Aggregated discussion summary titled "most multi-agent systems are task teams. what about agents developing shared history?" (https://bittide.aicompass.dev/article/26d597ac-d3d7-4910-9dae-a46492fa0599), surfaced via WebSearch on `site:reddit.com ... "has anyone built"`.
- **Why it looks unbuilt/untested**: Framed explicitly as an open question ("what about...") rather than a described solution; no implementation was surfaced for it in either the engine run or the WebSearch supplement.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up WebSearch found this is already a shipped-product category: Mem0 (maintained, widely-used open-source project with a dedicated "multi-agent memory systems" product line and a documented LlamaIndex cookbook passing one shared Mem0 memory object across agents/sessions) and Evermind.ai's "Shared Memory of AI Agents" feature both squarely target persistent, cross-task/cross-session agent memory instead of ephemeral per-task context. Supporting guidance from JumpCloud, GreenNode, and Cockroach Labs describes the same central-store pattern as established practice, not a hypothetical.

No sophisticated, general-purpose synchronization layer was found; the practitioner complaint holds, and the fragmented tooling that exists is narrow/unmaintained enough that a serious build would be differentiated.
