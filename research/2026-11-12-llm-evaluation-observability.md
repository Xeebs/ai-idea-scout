## Candidate patterns

### P1: Coding agents that create/manage LLM-judge evals through an API or MCP tool fail silently or get rejected by API validation they don't understand
- **What it is**: When autonomous coding agents use PostHog's AI-evaluation MCP tools/API to set up LLM-as-judge evals, they repeatedly hit friction the product itself had to patch around: trying to enable a judge with no working provider key (silently retried as a disabled draft, nobody told), and calling the eval-run endpoint with the wrong evaluation-target type.
- **Evidence**: GitHub `PostHog/posthog` PR #128104, "fix(aio): tell agents how to get LLM judges running without a key" (2026-11-03, 5 comments): "Coding agents creating evals through MCP often try an enabled LLM judge in a project with no working AI provider key. The API rejects it, and the agent usually retries the same judge as a disabled draft without telling anyone. Keys can't be added through MCP, so that judge never runs." Companion PR #129079, "fix(aio): tell agents llma-evaluation-run takes generation evals only" (2026-11-04, 4 comments): "Agents call `llma-evaluation-run` with trace- and session-target evaluations, and the API rejects every call with `evaluation_target_mismatch`. This bucket holds most of the tool's validation errors over the last 14 days, across many users."
- **Why it looks unbuilt/untested**: These are first-party bug-fix PRs papering over a missing general capability — there's no evidence of a standard "agent-friendly" eval-creation protocol (clear capability discovery, actionable errors, credential bootstrapping) that other eval platforms have solved; each vendor is patching the same class of failure ad hoc.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search found only narrow adjacent pieces, not an integrated solution: `mcp-eval` ships `doctor`/`validate` diagnostic commands for config/API-key setup, and Descope's agent-auth pattern returns an authorization link instead of throwing on a missing credential — but nothing combines capability discovery + actionable validation errors + credential bootstrapping specifically for LLM-judge eval creation. PostHog's own fixes (PR #128104, #129079) remain ad hoc per-bug patches, confirming no general protocol exists yet.

### P2: Observability traces that surface a real LLM/agent failure rarely get converted into a persisted eval case — the loop from "trace shows a bug" to "eval prevents regression" is manual and mostly skipped
- **What it is**: Agents (and humans) read LLM/agent traces through observability tooling, spot failures, but there's no mechanism nudging that discovery into a durable regression eval; the connection has to be built by hand, repo by repo.
- **Evidence**: GitHub `PostHog/posthog` PR #128267, "chore(aio): point agents reading traces to online evals" (2026-11-03, 4 comments): "Coding agents read a lot of LLM traces through the PostHog MCP, but rarely go on to set up an online evaluation for what they find. The planned 'Related' footer after trace queries (#121244) can't land: #127791 removed discovery hint footers from MCP tool results."
- **Why it looks unbuilt/untested**: PostHog's own attempted fix (a footer nudge) was blocked/removed by another change, meaning even the vendor that owns both the tracing and eval surfaces hasn't closed this loop yet — no evidence any observability product auto-promotes a traced failure into a regression test.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple maintained implementations close this exact loop: Braintrust's "Loop" feature (shipped, well-resourced vendor product) clusters production traces into datasets and auto-drafts scorers before deploy; Arize's open-source `phoenix2pytest` generates pytest regression tests from labeled failure traces; a separate OTel-native `toad-eye` CLI exports Jaeger traces into eval-YAML datasets. PostHog's specific MCP footer-nudge UX is unbuilt, but the underlying "trace failure → eval case" pattern is already well covered elsewhere.

### P3: LLM-as-judge eval pipelines don't degrade gracefully under BYOK provider rate limits — one 429 burst can silently lose every evaluation on that key
- **What it is**: Teams running their own API keys (OpenAI/Azure OpenAI/Anthropic/Gemini) through an eval platform lose evaluation results whenever the provider rate-limits that key, and recovery isn't automatic.
- **Evidence**: GitHub `PostHog/posthog` PR #128370, "fix(aio): retry byok 429s from first-party providers" (2026-11-03, 7 comments): "BYOK teams on OpenAI, Azure OpenAI, Anthropic or Gemini lose every LLM judge evaluation on a key after a burst of 429s. Recovery takes a key re-validation plus a re-enable on each evaluation. #123445 added retries for custom endpoints only."
- **Why it looks unbuilt/untested**: The referenced prior fix (#123445) only covered custom endpoints, confirming first-party-provider retry/backoff for eval pipelines specifically was still missing as of this cycle — a narrow but concrete reliability gap in production eval infrastructure.
- **Maturity**: PARTIAL
- **Verdict notes**: Generic 429/backoff handling for LLM calls is well solved (Python `tenacity`/`backoff`, LangSmith's built-in SDK retry with `Retry-After` honoring, `llmfuse`'s multi-provider failover) — but no product specifically addresses the BYOK-eval-platform failure mode of silently losing evaluation results and requiring manual key re-validation plus per-evaluation re-enable after a 429 burst. Building blocks exist; the specific eval-pipeline recovery UX gap PostHog describes (PR #128370) does not appear solved elsewhere.

### P4: Catching agent regressions without relying on an LLM-as-judge at all
- **What it is**: A deterministic/behavioral approach to detecting that an agent's behavior has regressed between versions, explicitly avoiding the cost, latency, and inconsistency of using another LLM as the evaluator.
- **Evidence**: Hacker News Show HN, "Apgar – Catch agent regressions without an LLM judge" (2026-10-29, 3 points, https://github.com/oimo-ai/apgar).
- **Why it looks unbuilt/untested**: Posted as a brand-new Show HN with only 3 points and no visible discussion — a single early-stage tool, not an established pattern; the "I wish eval didn't require an LLM judge" need is implied by the framing but the solution space is essentially untested in the wild.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub search found `hidai25/eval-view` (142 stars, pushed 2026-10-16, maintained) doing exactly this — deterministic snapshot/diff of agent tool calls in CI for LangGraph/CrewAI/OpenAI/Anthropic agents, explicitly positioning the LLM judge as optional. Web search also surfaced Prefactor's open-source no-LLM evals (deterministic wrong-tool-use/stuck-loop CI checks) and Refine AI's `agentdbg` behavioral CI gate, plus an arXiv paper on layer-isolated no-LLM regression harnesses. Apgar itself (3-point Show HN) is one of several competing implementations, not a novel gap.

### P5: Evaluating agentic retrieval against plain embeddings using a concrete production failure metric ("how often the LLM got handed the wrong page") instead of generic recall/MRR benchmarks
- **What it is**: Rather than benchmarking RAG retrieval with standard IR metrics, measure the rate at which the final context handed to the LLM is simply the wrong document/page, comparing an agentic retrieval approach ("Jev") against a pure-embeddings baseline on that failure rate.
- **Evidence**: Hacker News, "Jev handed our LLM the wrong page a tenth as often as our embeddings" (2026-10-13, 14 points, 3 comments, https://sayora.ai/many-hands/jev-vs-embeddings/).
- **Why it looks unbuilt/untested**: Single vendor blog post reporting its own internal comparison; no independent benchmark, leaderboard, or reusable eval harness built around this "wrong-page rate" metric was found — it reads as a one-off internal eval, not a adopted methodology.
- **Maturity**: OPEN
- **Verdict notes**: Web search for a standard "wrong page rate" retrieval-failure metric or reusable harness came up empty — the closest academic analogues (RAGTrace's "Retrieval Failure Value," RAGCap-Bench, LayerRAG-Bench) use different hit-rate/entropy-based formulations, and the search explicitly concluded "I didn't find a standard 'wrong page' retrieval failure rate metric... you may have to define it yourself." Only the single Sayora/Jev vendor blog post uses this exact framing; no independent benchmark or adopted harness was found.

### P6: Audit/observability layer for AI-agent side effects that survives checkpoint crash-and-resume without re-firing irreversible actions (payments, refunds)
- **What it is**: When a LangGraph-style agent crashes right after calling an external side-effecting API (e.g., issuing a payment/refund) but before the checkpoint records that it happened, resuming from the last checkpoint re-triggers the same side effect — a gap in agent observability/audit trails around exactly-once side-effect recording.
- **Evidence**: Reddit r/LangChain, "If a LangGraph node crashes right after a payment call, resuming the thread sends the payment again. Here is how I'm handling it" (2026-11-08, https://www.reddit.com/r/LangChain/comments/1xr6i79/): "I'm building Sevenbox, a decision audit layer for AI agents... With a checkpointer, if a node calls a payment API and fails before it returns, the last saved checkpoint i[s stale and resuming re-sends the payment]."
- **Why it looks unbuilt/untested**: Framed by the poster as a gap they personally tested and are building a product around (Sevenbox); no evidence that LangGraph or other major agent-orchestration frameworks ship this as a built-in audit/idempotency guarantee — only one small vendor addressing it so far.
- **Maturity**: PARTIAL
- **Verdict notes**: General-purpose durable-execution engines (Temporal, Restate) already provide journal-replay/idempotent-activity primitives that solve the underlying "don't re-fire a side effect on resume" problem, and multiple blog tutorials (theneuralbase.com's "idempotency-safe-re-execution" guide, tianpan.co's "Agent Idempotency" posts) document DIY idempotency-key patterns specifically for LangGraph. But these are generic building blocks and how-to posts, not a purpose-built agent audit/observability layer with exactly-once guarantees — Sevenbox remains the only vendor packaging this as a dedicated product, so the specific gap is real but narrow.
