## Candidate patterns

### P1: Hand-rolled "from scratch" multi-agent architectures instead of adopting a framework
- **What it is**: Builders are writing their own multi-agent orchestration layer rather than standing on an existing framework (LangGraph, AutoGen/Microsoft Agent Framework, etc.), then publishing the architecture as a from-scratch tutorial.
- **Evidence**: Hacker News, "Building a Multi-Agent System from Scratch: Architecture Patterns" (2026-11-05, 106 points, 45 comments) — surfaced directly by the last30days engine run. Corroborated by moridinamael's blog "Agent Orchestration is Not the Future," which recounts building a multi-agent system twice and concluding an orchestration framework wasn't worth adopting (via WebSearch).
- **Why it looks unbuilt/untested**: No single implementation is being converged on; each builder re-derives the pattern independently rather than reusing a shared, tested abstraction.
- **Maturity**: SATURATED
- **Verdict notes**: GitHub search for "multi-agent orchestration framework" returns a crowded, actively maintained field — kyegomez/swarms, VRSEN/agency-swarm, Kocoro-lab/Shannon, foreveryh/mentis (on LangGraph), swarms-rs, all pushed within the last week of this search. WebSearch corroborates: a DEV Community 2026 guide calls DIY orchestration a "technical debt trap," and multiple vendor/practitioner pieces (Tallyfy, RaftLabs, ChatFin) debate framework-vs-custom as a mature, ongoing tooling debate rather than an absence of tooling. The "re-derivation" framing describes developer preference/complexity-aversion, not a missing capability — multiple maintained frameworks already squarely cover this.

### P2: "Orchestrators are bad" sentiment with no agreed-upon replacement
- **What it is**: A recurring complaint that current multi-agent orchestration frameworks are the wrong abstraction, paired with explicit "has anyone built" asks for something better — specifically, per-agent sandboxing (e.g., one Docker container per agent) with the ability to delegate control to an agent while still being able to step in and inspect what it's doing.
- **Evidence**: Hacker News item "I don't see any good orchestration system for AI agents" (Facundo, 2026-06, low engagement but explicit ask) and the blog post "Agent orchestrators are bad," plus MindStudio's framing of orchestration as "the biggest unsolved problem in the AI stack" (all via WebSearch).
- **Why it looks unbuilt/untested**: The HN poster names the exact missing piece (containerized per-agent delegation with step-in/inspect capability) and says they know of partial pieces (Claude Code images, task-trigger libraries) but no widely adopted solution that combines them.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found scattered component pieces — OpenClaw's docs describe per-agent sandbox scope (one container per agent, with override/inheritance rules for sub-agents) and a Docker "Agent" `sub_agents` delegation config, plus Arcade's "Docker sandboxes aren't enough for agent safety" post and an OpenAI sandboxing guide warning against running the harness inside the sandbox. No GitHub repo or product was found that combines containerized per-agent isolation + live delegation + step-in/inspect into one widely-adopted solution, matching the HN poster's own framing that only partial pieces exist.

### P3: Identity-and-permission re-scoping at every agent-to-agent handoff
- **What it is**: A proposed architecture pattern where each handoff in a multi-agent chain (e.g., triage agent → specialist agent → action agent) re-establishes the receiving agent's identity and permission scope, rather than silently inheriting the previous agent's full context and privileges.
- **Evidence**: Substack piece ("Enterprise Data & AI Realities") arguing multi-agent systems break at the handoff, not in the model, and recommending scope/identity be reissued at each step (via WebSearch).
- **Why it looks unbuilt/untested**: Described as a recommended practice in a single analyst piece, not as a reusable library, SDK primitive, or tested reference implementation — no named project implements it as a drop-in handoff guard.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch surfaced only vendor/commentary content making this recommendation — Okta's blog describes an Early Access "Agent-to-Agent Connections" feature (allowlists + scoped permissions, not GA), plus NHI Identity Journal, Arthur.ai, and BigID pieces recommending attenuation/short-lived workload identity (SPIFFE/SPIRE, OIDC) at each hop as best practice. No GitHub-native reusable "handoff guard" library or SDK primitive was found; the closest real implementation is Okta's not-yet-GA feature and Alter (see P7), both still early. The gap is real but a well-resourced vendor (Okta) is already moving into it, so a standalone build would need to differentiate quickly.

### P4: Scope-chain / tiered shared memory for multi-agent systems, still ungoverned
- **What it is**: A memory architecture pattern — a global, read-mostly layer of shared facts/business rules writable only by privileged processes, plus per-agent namespaced working state kept separate from the shared layer — proposed as the fix for flat shared memory causing cross-agent context pollution.
- **Evidence**: GreenNode's "How to design shared memory for multi-agent AI" guide describes the scope-chain pattern (via WebSearch). Contrasted with a March 2026 paper on "Governed Memory" (cited secondhand via VentureBeat's coverage of Tencent's Team Memory) that names governance fragmentation and silent quality degradation as still-unsolved structural risks in shared agent memory — explicitly flagged as having "no governance yet for when it's wrong."
- **Why it looks unbuilt/untested**: Vendors (Tencent Team Memory, Mem0, EverMind) are shipping shared-memory layers, but the cited paper and the VentureBeat framing both say governance/validation for when shared memory is wrong is still missing — this is vendor-claim-heavy evidence and needs independent verification before trusting the "ungoverned" framing.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed independently: VentureBeat's coverage of Tencent's Team Memory explicitly states there's no documented conflict-resolution/correction mechanism when two agents' writes contradict ("whose memory wins"), and Mem0's own "Organizational memory" page (private beta) markets a governance layer without explaining the conflict-resolution mechanism — both shipped/beta products, both acknowledged-incomplete on governance. GitHub search for "multi-agent shared memory governance" found only `liaiaaa/dsh-evolution-os`, a 0-star repo (created Sept 2026) claiming drift detection/tiered write rules — an unevaluated proof of concept, not a tested reference implementation. The scope-chain pattern is thus real and open at the governance layer despite shipped memory products.

### P5: Agent-stack breakdown past a coordination threshold (~10 agents)
- **What it is**: A claimed scaling cliff where adding more agents to a system stops paying off and coordination overhead exceeds the parallelism benefit — the fix being structural limits/roles rather than more agents.
- **Evidence**: IndieHackers posts "Why your AI agent stack will break at 10 agents and what to do about it" and "Stop adding more agents, start giving them structure" (via WebSearch) — both self-published practitioner posts, not peer-reviewed.
- **Why it looks unbuilt/untested**: No tooling identified that detects or warns when a system is approaching this coordination cliff; the posts are after-the-fact narrative accounts, not a diagnostic or guardrail product.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found genuine research quantifying the cliff — "Towards a Science of Scaling Agent Systems" (180 controlled experiments, reports 39-70% degradation on sequential-reasoning tasks past a threshold) and a separately proposed "Coordination Bottleneck Index" and "Agent Coordination Bound" (n(n-1)/2 communication-channel growth heuristic) — but these are academic metrics/papers, not deployed diagnostic tooling or a product that warns a running system it's approaching the cliff. No GitHub repo implementing either CBI or ACB as a runnable guardrail was found. Real, measured gap; no shipped tooling closes it yet.

### P6: Missing failure-mode taxonomy / diagnosis layer for multi-agent systems (specification vs. coordination failure)
- **What it is**: A diagnostic classification that splits multi-agent production failures into "specification failures" (the task/plan was wrong) versus "coordination breakdowns" (the plan was right but agents failed to execute it together), cited at roughly 42% and 37% of failures respectively in secondhand blog coverage.
- **Evidence**: Figures referenced in practitioner blog posts summarizing a cited study (via WebSearch); also referenced in the "Genie Lessons: Nobody Wants Agents" summary (Kent Beck's site). These numbers are secondhand/aggregator citations, not a primary source we verified directly — treat as low-confidence evidence pending the original study.
- **Why it looks unbuilt/untested**: No named tool or library was found that automatically classifies a failed multi-agent run into one of these buckets; the taxonomy currently exists only as commentary, not instrumentation.
- **Maturity**: SATURATED
- **Verdict notes**: This is already closed at the research-tooling level — the cited taxonomy is the peer-reviewed MAST paper ("Why Do Multi-Agent LLM Systems Fail?", arXiv 2503.13657, NeurIPS 2025 poster), whose authors open-sourced both a 1,600+-trace annotated dataset and a working LLM-as-a-judge classifier pipeline (GitHub org `multi-agent-systems-failure-taxonomy`, inter-annotator kappa ~0.88) that automatically assigns failed runs into the taxonomy's 14 modes under 3 categories (specification / inter-agent misalignment / task verification) — directly the "diagnosis layer" the pattern describes. A third-party repo (`hugomn/mast-taxonomy-production-telemetry`) has already applied this classifier to 639K+ execution steps of real production telemetry, confirming it's reused beyond the original paper. The secondhand 42%/37% split cited in the digest is a looser paraphrase of this same paper's categories, not a separate unverified claim.

### P7: Access control specifically for multi-agent (not just multi-user) systems
- **What it is**: Permission/access-control infrastructure scoped to agent-to-agent delegation chains, distinct from traditional multi-user access control.
- **Evidence**: Hacker News, "Launch HN: Alter (YC S25) – Access control for multi-user agents" (2026-10-21, 69 points, 63 comments) — surfaced directly by the last30days engine run.
- **Why it looks unbuilt/untested**: A funded startup (YC S25) is actively building in this space right now, which is itself evidence the gap was open until very recently — the gap-analyst should check whether Alter (or comparable launches) already closes this for the population in question.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed via WebSearch: Alter (YC S25, alterauth.com) shipped a beta product giving each agent its own identity, fine-grained RBAC/ABAC, default-deny policies, and audit logging — but its own launch materials describe this as "access control for multi-user agents" (one agent, many human users) and explicitly list agent-to-agent (A2A) support as "coming soon," i.e. not yet shipped. Okta's "Agent-to-Agent Connections" (Early Access, see P3) is the other close comparable, also not GA. So the multi-user case is being closed by a funded team right now, but the multi-agent-to-agent delegation-chain case this pattern specifically names is still ahead of what's shipped — real differentiated room remains, but narrowing fast.

- **Evidence**: IndieHackers post describing a builder who open-sourced "AgentsMesh" specifically to fix multi-agent "chaos" they'd hit in production (via WebSearch) — a self-reported duct-tape-and-release pattern.
- **Why it looks unbuilt/untested**: The builder's own framing ("fix the chaos problem") implies no existing tool solved it for them; evidence is a single IndieHackers post, so independent corroboration is needed.
- **Maturity**: SATURATED
- **Verdict notes**: Independent corroboration found, and it changes the verdict: AgentsMesh (github.com/AgentsMesh/AgentsMesh) is a real, actively maintained project — roughly 2,170-2,200 GitHub stars, latest release v0.44.7, now also offered as a hosted service (agentsmesh.ai) with a Runner daemon for self-hosting, Kanban-style fleet command center, isolated pods/Git worktrees, and centralized multi-agent visibility. What started as a solo duct-tape release (Show HN, March 2026, 3 points) has since grown into a well-resourced, actively shipped product squarely covering this exact "coordination chaos" gap — this specific instance of the pattern is no longer open, though the broader behavior (new builders still duct-taping their own tools before discovering AgentsMesh or peers) may recur.
