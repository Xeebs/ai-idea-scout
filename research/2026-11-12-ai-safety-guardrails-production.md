## Candidate patterns

### P1: Splitting agent guardrails into two enforcement planes — model-gateway content/topic control vs. tool-call guarding
- **What it is**: Treating "what the model is allowed to say/discuss" (content & topic control, enforced at the model gateway) and "what the agent is allowed to do" (tool-call guarding) as two distinct policy surfaces that need separate engines, rather than one generic "guardrails" layer.
- **Evidence**: GitHub issue `awslabs/open-agentic-platform#144`, "agent-guardrails: runtime content and topic control at the model gateway" (8 comments). Contributor elamaran11 writes: "I went in expecting it to be unrelated to this issue — a tool-call guard, not content control. That was wrong, and it bears on a choice..." and separately asks whether the Bifrost gateway "has a usable content-guardrail plugin," noting its AWS Bedrock Guardrails integration is "documented under Enterprise."
- **Why it looks unbuilt/untested**: the maintainers themselves didn't realize a cross-referenced project (Dogwood, a tool-call guard) was related to their content/topic-control proposal until mid-discussion, and they're still unsure whether an existing gateway (Bifrost) has a real pluggable content-guardrail story outside enterprise-tier features. No shipped open framework unifies both planes yet.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found multiple maintained products explicitly splitting these two planes: TrueFoundry's AI Gateway runs guardrails on four hooks (LLM input, LLM output, MCP pre-tool, MCP post-tool), agentgateway.dev ships the same input/output-vs-tool-call guard split, and OpenAI Guardrails (MIT-licensed, on PyPI) has distinct input/output content guardrails plus tool guardrails applied to every function call. The specific awslabs issue thread shows one team's confusion, but the architectural split itself is already a shipped, maintained pattern across at least three gateway products.

### P2: Fail-closed defaults when the jailbreak/safety detector service itself is unavailable
- **What it is**: Ensuring an agent or LLM pipeline blocks (fails closed) rather than silently allows (fails open) when the guardrail detector it depends on is down or unreachable.
- **Evidence**: GitHub PR `NVIDIA-NeMo/Guardrails#2588`, "fix(jailbreak): fail closed when the detector is unavailable" (merged 2026-11-10 into NVIDIA's NeMo Guardrails, the most prominent open-source guardrails framework).
- **Why it looks unbuilt/untested**: this is a live bug fix in the flagship open-source guardrails project — meaning until very recently, a production deployment of the most popular guardrails framework could fail open on detector downtime. If the reference implementation only just fixed this, smaller/custom guardrail stacks almost certainly still have the same gap, and there's no general pattern or checklist being discussed for it.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found extensive practitioner guidance (Splunk's "AI Guardrails" guide, a gateway doc describing a `fail_open` flag defaulting to fail-closed, multiple blogs recommending fail-closed for toxicity/PII/injection and fail-open only for advisory checks) but no evidence of a general, tested, cross-framework pattern or checklist — the guidance is prose advice per-vendor, and the NeMo Guardrails bug (merged 2026-11-10) shows even the flagship implementation only just closed this gap in one specific detector path. Real but inconsistent coverage, not a solved problem.

### P3: Guardrail classifiers with silently dead detection branches ("documented to catch X, never does")
- **What it is**: Safety/intent classifiers inside a guardrail layer that are documented to return a given category (e.g., `off_topic`) but whose code path for that category is unreachable as written, so the stated protection never actually fires.
- **Evidence**: GitHub PR `Mikecranesync/MIRA#4894`, "fix(hub): notebook chat answers off-topic turns with a fixed scope reply" — PR body states: "`classify_intent()` (`mira-bots/shared/guardrails.py:1155`) is documented to be able to return `off_topic`, but as literally written it never does — every branch that doesn't match falls through to the final return."
- **Why it looks unbuilt/untested**: a real production guardrail function shipped with a dead branch for one of its documented safety categories, undetected until this fix. No tooling surfaced in the research (branch-coverage or mutation testing aimed specifically at guardrail classifiers) that would catch "documented category never actually returned" automatically.
- **Maturity**: OPEN
- **Verdict notes**: Searched GitHub (no relevant repos surfaced for guardrail-classifier branch/mutation coverage) and web for "guardrail classifier dead code branch coverage mutation testing" and "coverage criteria for classifiers" — found only adjacent, non-matching work: a May 2026 arXiv paper on formal input-space verification of guardrail classifiers (huggingface.co/papers/2605.10901, a different problem — decision-boundary safety holes, not unreachable code branches) and generic mutation-testing background (arxiv.org/pdf/1506.07330). No tool or technique specifically targeting "documented-but-unreachable guardrail classification branch" was found; the gap looks genuinely unaddressed.

### P4: Register/style-based and encoding-based prompt injection that guardrails aren't tuned for
- **What it is**: Jailbreaks that bypass content guardrails not through forbidden topics but through linguistic register mimicry (e.g., formal legal phrasing) or payload encoding that keeps the malicious instruction invisible to the filter until after it's decoded.
- **Evidence**: Hacker News post "Prompt Injection, Esq.: pwning AI agent guardrails with lawyerspeak" (mrnice.dev, 2026-11-11, 3pts). Corroborating WebSearch evidence: HiddenLayer's "Policy Puppetry" technique described as able to "break the safety guardrails of all major generative AI models"; Adversa AI's "Cryptographic Context Injection," reported to xAI 2026-06-03, which "hides malicious instructions until they're decrypted inside a trusted execution environment, so safety filters classify the text without ever seeing it run."
- **Why it looks unbuilt/untested**: three independent write-ups in roughly the same window target the same blind spot — guardrails evaluating surface content/topic rather than register or encoded payloads — and none of the production guardrail write-ups surfaced (NeMo Guardrails, Bifrost, Spring AI Privacy Guardrails) advertise a defense aimed specifically at register-mimicry or decode-then-execute payloads.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found the attack side well documented across multiple papers (arxiv.org/html/2510.01529 on controlled-release/encoded jailbreaks, arxiv.org/html/2504.11168 on character-injection evasion tested against six detectors including Azure Prompt Shield, mindgard.ai on invisible-character bypasses) but no shipped defensive product or library specifically tuned for register-mimicry or decode-then-execute payloads — only generic advice to "red-team guardrails against encodings and ciphers." Attacks are a saturated research topic; a targeted defense is not, so this stays PARTIAL rather than OPEN per the tie-break rule.

### P5: Rootless sandbox + human-in-the-loop approval firewall as a default wrapper for autonomous agents
- **What it is**: A drop-in sandboxing and approval layer (not a cloud VM, a rootless container-style jail) that intercepts an autonomous agent's destructive or irreversible actions and routes them through human approval before execution.
- **Evidence**: GitHub PR `gsxdsm/awesome-paperclip#56` (2026-10-21) adds "agent-jail" and "lazy-agentd" to a curated agent-tooling list, described as a "Rootless Bubblewrap sandbox and human-in-the-loop security firewall for Paperclip and autonomous AI agents. Prevents catastrophic [actions]" (project: `apravint/agent-jail`).
- **Why it looks unbuilt/untested**: the tool was only just added to a community "awesome list" on 2026-10-21 — i.e., brand new, not yet a widely adopted or maintained dependency — while most agent frameworks referenced elsewhere in the research (NeMo Agent Toolkit, open-agentic-platform) still ship without a default sandbox+approval layer, leaving builders to hand-roll or bolt one on.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found a crowded field of maintained implementations beyond `agent-jail`: IronCurtain (provos/ironcurtain, ~500 GitHub stars per AgentIndex/HN Showcase snapshots, Apache-2.0, extensive press coverage from helpnetsecurity.com and techstrong.ai, built by security researcher Niels Provos) is a rootless-sandbox-plus-policy-engine with human-approval escalation; SafeAgent (jamesburchill) runs a non-root Docker sandbox with policy-driven approval; NVIDIA's NemoClaw/OpenShell, Airlock, Sandclaw, and yolo-cage all implement the same allow/deny/escalate-to-human pattern around sandboxed agent actions. `agent-jail` being new doesn't mean the category is open — multiple other maintained projects already cover it, one with real adoption signals.

### P7: No tooling to reason about compounding failure rates across a layered guardrail stack
- **What it is**: A way to model or test how accuracy compounds (or doesn't) when multiple independent guardrail layers are stacked in a pipeline, and to decide per-layer fail-open vs. fail-closed policy based on that math rather than intuition.
- **Evidence** (WebSearch supplement): a Tian Pan production-guardrails write-up warns that "stacking five guardrails at 90% accuracy each yields overall system correctness of about 59%." A Galileo guide on production guardrails notes that high-severity safety/compliance checks "typically fail closed," while lower-severity tone/formatting checks "fail open" — a per-layer policy choice described in prose, not computed by any referenced tool.
- **Why it looks unbuilt/untested**: the compounding-error math is presented as a cautionary rule of thumb in a blog post, and the fail-open/fail-closed choice is manual guidance — no tool surfaced in this research that lets a team simulate or visualize their actual stacked-guardrail reliability before shipping.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found an existing interactive Monte Carlo simulator (annie2000.github.io/consistency-tax — adjusts per-step accuracy, pipeline length, and run count to show end-to-end success and variance effects) and a layer-redundancy Python snippet on agentpatterns.ai, so the "no tool exists" framing is too strong. But both are one-off academic/blog artifacts, not a maintained product integrated into any guardrail framework (Guardrails AI's "Guard" primitive stacks validators but doesn't model compounding reliability) — a real build here would clearly differentiate.
