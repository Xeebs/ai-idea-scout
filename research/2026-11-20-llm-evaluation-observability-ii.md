## Candidate patterns

### P1: No turnkey pipeline turns production LLM logs into a privacy-safe, deduplicated, labeled eval dataset end to end
- **What it is**: Teams want to go from raw production traces straight to a usable "golden" evaluation dataset, but every documented path requires manually stitching together a log source, a clustering/sampling step, a privacy review, and a labeling pass.
- **Evidence**: Fireworks AI's "Turning Production Logs into Evaluation Datasets" (fireworks.ai/blog) describes pulling traces from Langfuse/Braintrust, clustering by meaning, and sampling per cluster via an open-source integration. A dev.to post ("Your LLM traces are write-only," vola-trebla) describes a single-author CLI (`toad-eye`) that exports a Jaeger trace into a YAML eval dataset with generated assertions, with the author explicitly noting a second mode ("inline scoring of every span") is "still in progress." OneUptime's guide "How to Build a Golden Evaluation Dataset from Real LLM Production Failures" (2026-08-31) frames privacy review, reproducibility checks, and rubric calibration as manual steps the reader must perform themselves.
- **Why it looks unbuilt/untested**: Three independent sources each describe a *partial* workflow (a vendor integration that stops at sampling, a one-author CLI admittedly mid-build, a manual-steps guide) rather than one tool that handles privacy scrubbing, deduplication, and labeling together. WebSearch for this exact combination surfaced no single product claiming to close that loop.
- **Maturity**: PARTIAL
- **Verdict notes**: Re-verified via WebSearch ("turn production LLM traces into evaluation dataset tool github"): Fireworks' Eval Protocol x Lilac integration (open-source, clustering via embeddings/UMAP/HDBSCAN) stops at sampling, not privacy-scrubbing or labeling; `toad-eye` is a single-author CLI with its second mode explicitly "still in progress"; Braintrust and Microsoft Foundry offer commercial trace-to-dataset features but neither advertises an integrated privacy-review step. No GitHub repo search or product found closing the full loop (privacy + dedup + labeling) end to end — narrow/partial implementations only.

### P2: Golden-prompt drift monitors conflate "the app drifted" with "the judge/evaluator itself drifted"
- **What it is**: Teams running scheduled golden-prompt checks to catch silent output drift discover that the judge model or grading logic can itself change behavior over time, producing false drift signals that get misattributed to the application being monitored.
- **Evidence**: OneUptime's "How to Monitor Silent LLM Output Drift with Scheduled Golden-Prompt Runs" (2026-11-16) explicitly recommends "recording the returned model identifier and checking whether the evaluator itself changed before blaming the application" — a direct acknowledgment that this confusion is a live failure mode, not hypothetical. A dev.to post ("I broke a chatbot with a prompt change then I built the tool that would've caught it," decimozs) is a builder's own incident narrative followed by hand-building a fix.
- **Why it looks unbuilt/untested**: Both pieces of evidence are one author's own ad hoc recipe or one-off tool built after getting burned, not a packaged product. PromptLayer's drift-detection glossary entry and promptfoo's CI-based before/after diffing (Medium, "Testing LLM prompts like code") both track application-level drift but neither isolates judge/evaluator drift as a separately monitored signal.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search ("judge drift") turned up a dozen+ small repos, almost all narrow/one-off: `homayoun-safarpour/judge-drift-sentinel` (created 2026-11-08, days old, PyPI upload "still pending" per its own listing), `avalyset/inspect-judge-drift`, `Priyanshi0907/llm-regression-detector`, several unlabeled student/POC repos (`judge-drift`, `llm-as-judge` "POC"). An arXiv paper (2606.15474, "Who Drifted: the System or the Judge?") proposes an attribution method academically, not a shipped tool. No mainstream observability vendor (Galileo, Arize, Evidently, WhyLabs, Langfuse) was found tracking judge-version drift as a distinct signal. Real but immature/narrow implementations exist — PARTIAL, not OPEN.

### P3: Human annotation queues have no capacity-aware triage against a stated reviewer-time budget
- **What it is**: Eval pipelines generate review volume that grows with traffic, while human reviewer time stays roughly flat, and nothing in the annotation-queue tooling actively re-prioritizes or trims the queue against that mismatch — it just accumulates.
- **Evidence**: A Tianpan blog post (tianpan.co, cited via search) states the mismatch directly: "your eval pipeline emits 800 traces per week for human review, while your annotators have about ninety minutes a week budgeted for it... adding more reviewers buys you a constant factor, while the eval pipeline keeps growing geometrically." Arize's overview of annotation queues independently flags that such queues are "cheap, biased toward extreme reactions, and rarely based on a rubric." Future AGI's post recommending routing by risk/confidence/disagreement is vendor advisory content, not a described shipped feature.
- **Why it looks unbuilt/untested**: Existing shipped tooling (Datadog LLM Observability annotation queues, Arize annotation queues) provides the queue mechanism itself, but WebSearch found no product that actively re-triages the queue against a declared reviewer-capacity budget — the routing-by-risk idea exists only as advisory blog content, not a feature any named tool was confirmed to ship.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch confirmed the gap is real but not wholly unaddressed: an arXiv queueing-theory paper (2603.13870, Lin & Zhang) models judge-vs-human routing under a reviewer budget; Arize's own docs give a worked manual example (400 flagged traces → 150-review budget, 20% overlap) but this is a sizing exercise the human does, not an automated re-triage feature; Tianpan's and ACT-as-Human's (arXiv 2511.09833) budget-aware sampling ideas are advisory/research, not shipped product features. GitHub search for "annotation queue triage budget" returned no matching repos. Academic framing + manual practitioner workarounds exist, no shipped automated feature — PARTIAL (tie broken toward PARTIAL per rubric).

### P4: No serving stack logs full per-request provenance (prompt + model + retriever/index + judge versions bound together) as one unit
- **What it is**: Catching a regression after any pipeline change (prompt, model, RAG index, or judge) requires knowing exactly which version of each component produced a given response — but that binding isn't logged as a single first-class record in most production stacks.
- **Evidence**: An arXiv paper (cited via search, "The Grand Software Supply Chain of AI Systems") argues that without per-request metadata recording which artifact versions produced each response, even detecting a regression requires a behavioral baseline that current serving stacks don't maintain.
- **Why it looks unbuilt/untested**: This is framed as an academic argument about a structural gap, not a shipped library or feature. WebSearch for this specific combination (prompt version + model version + retriever/index version + judge version bound per-request) found no observability vendor advertising that as a unified logged record.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found the individual pieces already shipped separately: MLflow's "audit-ready LLM logs" feature explicitly links an output to its inputs, retrievals, guardrail decisions, and model version in one tamper-evident request-level record; OneUptime's guide recommends attaching prompt/index/evaluator versions per-stage. But the exact combination the pattern names — prompt + model + retriever/index + **judge** version bound as one first-class unit — was not found in any named product; "judge version" never appeared alongside the other three in results (closest is "evaluator/rubric version," handled as a separate evaluation-stage attribute, not fused into the per-request record). Components are real and shipped; the specific unified record is not — PARTIAL.

### P5: The "observability tax" — stacked, overlapping per-seat tracing/cost/eval tools that cost more than the LLM calls they monitor
- **What it is**: Teams end up running APM, dedicated LLM tracing, a separate cost dashboard, and alerting as four overlapping, separately-billed tools, and the monitoring stack's own cost becomes a line item bigger than expected relative to inference spend.
- **Evidence**: Tianpan's "the observability tax when monitoring your AI costs more than running it" (2026-04-12, cited via search) describes exactly this stacking pattern with overlapping per-seat charges. Enterprise DNA's practitioner review of Helicone corroborates from the usage side: latency overhead is "lower than people feared" for typical workloads but "fits less well for high-throughput batch jobs where latency overhead adds up" — i.e., the cost/overhead problem is real but workload-dependent, not resolved by any one tool.
- **Why it looks unbuilt/untested**: The Tianpan post's own proposed fix is "sampling often answers the question" — a manual mitigation a team applies themselves, not a product. WebSearch found no consolidated LLM-observability tool positioned as replacing the stack (APM + tracing + cost + alerting in one bill) rather than adding a fifth overlapping layer to it.
- **Maturity**: SATURATED
- **Verdict notes**: This claim doesn't hold up against a fuller search. Multiple well-resourced, actively maintained vendors squarely market themselves as the fix for exactly this stacking/billing complaint: New Relic explicitly pitches "AI agent monitoring that consolidates your observability stack" (one platform, one bill, vs. a separate vendor/contract/pipeline/invoice per tool); OpenObserve makes the identical pitch (cost/latency/score on the same span, no second platform); Datadog LLM Observability and Elastic Observability both fold LLM tracing into their existing unified APM billing. The narrower nuance (tracing overhead cost for very high-throughput batch workloads specifically, per Enterprise DNA's Helicone review) is real and unresolved by sampling-as-a-feature, but the core gap as stated — overlapping, separately-billed tools costing more than expected — is already being closed by multiple shipped, maintained consolidation products from well-resourced teams.

### P6: CI-based prompt regression testing still requires a human to read the before/after diff by hand
- **What it is**: Tools that run eval suites on prompt changes inside CI (e.g., on every pull request) produce a before/after comparison, but deciding which differences are real regressions versus noise-level fluctuation is still left to a human scanning the diff.
- **Evidence**: A Medium walkthrough ("Testing LLM prompts like code: regression evals in CI/CD with promptfoo") describes promptfoo's GitHub Action running evals on prompt-file changes and surfacing a before/after comparison for the reviewer to read. A dev.to comparison post (cited via search) notes that promptfoo, DeepEval, LangSmith, and Braintrust "offer varying degrees of regression detection, with some relying on manual diffs or experiment tracking" — explicitly naming manual diff-reading as current practice across multiple named tools, not an edge case.
- **Why it looks unbuilt/untested**: No tool was found in this pass that auto-calibrates a pass/fail threshold or auto-flags only the regressions likely to matter versus normal run-to-run variance — every named tool still hands the reviewer a diff to interpret.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed via targeted WebSearch on promptfoo/DeepEval specifically: both gate CI on a fixed, user-set threshold (DeepEval's `assert_test()`, promptfoo's fail-on-threshold CLI flag) — neither has a documented feature that compares against a stored baseline with statistical tolerance for judge-score noise. A Langfuse guide explicitly frames baseline-diff-with-tolerance as a custom CI step teams must write themselves, not a built-in feature, and one source flags the exact noise problem (a 0.7 gate scoring 0.71 today, 0.68 tomorrow) as unresolved by fixed thresholds. Real, widely-used tools (promptfoo, DeepEval, LangSmith, Braintrust) exist but all stop at fixed-threshold/manual-diff — the auto-calibration/auto-flagging layer the pattern describes is genuinely unbuilt in any of them — PARTIAL.
