## Candidate patterns

### P1: Cross-client/cross-project context continuity for coding agents
- **What it is**: A standing unmet need for a way to carry an AI coding agent's accumulated context (decisions, conventions, in-progress state) across different clients (Claude Code, Codex, Cursor, etc.) and across different projects/repos, rather than re-establishing it from scratch each session.
- **Evidence**: Ask HN thread "How do you manage your AI agents' context across clients and projects?" (Hacker News, 2026-11-07, 99 points, 60 comments) — a question thread, not an announcement, indicating the community is actively trading ad-hoc solutions rather than pointing to one accepted tool.
- **Why it looks unbuilt/untested**: The thread is framed as an open question ("how do you...") rather than a pointer to a known solution, and it drew 60 comments — a sign of many competing one-off approaches rather than consensus tooling.
- **Maturity**: SATURATED
- **Verdict notes**: Multiple actively-maintained tools already target exactly this: `akitaonrails/ai-memory` (Rust, claimed 3,200+ stars, cross-agent handoffs for Claude Code/Codex/Cursor), `leesgit/passbaton` (updated 2026-11-07, shared local DB across Claude Code/Codex/Gemini CLI with compaction handover), `aictx` (PyPI, repo-local continuity runtime, multiple active forks), and `cli-continues`/`yigitkonur` (resumes sessions across ~7 tools). GitHub search also surfaced `team-strange-loop/agent-context-portability`. The HN question thread is community members not yet knowing about or converging on these tools, not an absence of implementations.

### P2: Model-judged context pruning for junk tool output
- **What it is**: Instead of keeping every raw tool-call result in context, let the model itself replace a tool output it judges useless/junk with a one-line summary immediately, paying the summarization cost once rather than re-reading noisy output every subsequent turn.
- **Evidence**: Filed independently as a feature request in two different agent-tooling repos with near-identical wording — `google-gemini/gemini-cli` issue #30152 (2026-11-05, 6 comments) and `google-antigravity/antigravity-cli` issue #1429 (2026-11-05, 2 reactions, 2 comments). The TL;DR in both: "When a tool call returns junk the model didn't intend, let the model swap that output for a one-line summary before the turn ends. Pay for it once; keep the context clean for the rest of the session."
- **Why it looks unbuilt/untested**: The same feature request was independently filed against two separate, unrelated agent CLIs on the same day — a sign the gap is a general one in agent harnesses, not idiosyncratic to one tool, and that neither maintainer had already shipped it.
- **Maturity**: SATURATED
- **Verdict notes**: `championswimmer/pi-context-prune` (and active forks/variants: `syansunyang-collab/pi-context-prune` claiming -63% context tokens over 6 A/B rounds, `prjct-app/pi-context-prune`, `nourhelmi/pi-jev-compaction`, `carbon-ni/pi-context-pruner`; most recently updated 2026-11-12, today) ships exactly this — an "agentic-auto" mode where the model itself decides to prune/summarize finished tool-call output, keeping originals one query away. Separately, the established Agno agent framework shipped "automatic tool output compression" to keep runs within context limits (agno.com changelog), and the Squeez research system (arXiv 2604.04979) released code/model for task-conditioned tool-output pruning. Two unrelated gemini-cli/antigravity-cli issues not being fixed by those specific maintainers doesn't mean the pattern is unbuilt elsewhere — it already is, in multiple maintained places.

### P3: Automatic context compaction silently dropping the active task
- **What it is**: A recurring reliability failure where an agent's automatic context-compaction step loses track of the task actually in progress — the continuation after compaction receives only environment-level context, not the task state, and the agent silently abandons the work mid-turn.
- **Evidence**: `openai/codex` issue #57608, "Automatic compaction loses active task: continuation receives environment-only user context despite preserved rollout" (2026-10-28, 5 reactions, 16 comments). Comment thread shows independent reproduction across releases/platforms: one commenter adds "an independent Windows occurrence from October 28, 2026"; another follow-up (after a newer release, 0.165.0) says "this is still occurring" after inspecting the 10 most recently active sessions.
- **Why it looks unbuilt/untested**: Multiple independent reproductions across versions and platforms, with maintainers still chasing root cause rather than having shipped a fix — a live, unresolved gap in a widely-used coding agent's compaction logic.
- **Maturity**: OPEN
- **Verdict notes**: WebSearch for a shipped fix turned up only more bug reports across tools (community.openai.com threads on "context compression caused Codex to attribute the previous approval error to this task", "automatic compaction does not trigger task-state recovery", `openai/codex` issues #19558/#22107/#29356, claudeissues.com reports of the same failure mode in Claude Code's Auto-Compact) and one third-party forum post describing an unofficial local patch that reattaches the active-goal prompt mid-compaction. No maintainer-shipped fix, library, or product found — only discussion and one person's private workaround, which does not rise to a credible implementation.

### P4: Archiving the full compaction transcript (not just raw messages) to an external memory store
- **What it is**: Treating the moment of context compaction as a data-capture hook — reading the full transcript (not the raw message list) with role/text structure and sending it to a separate, durable memory service before the context is actually compacted away.
- **Evidence**: `mindroom-ai/openviking-plugin` PR #6, "Archive the compaction transcript instead of raw messages" (2026-10-28, 1 reaction, 7 comments): "The `compaction:before` hook now reads `ctx.transcript`... and sends each line to OpenViking with its role and text."
- **Why it looks unbuilt/untested**: This is a single plugin built by one project (mindroom-ai) bolting external durable memory onto another tool's compaction hook — a workaround rather than a built-in capability of the host agent runtime, which suggests the host tools don't yet treat compaction as an opportunity to persist context elsewhere.
- **Maturity**: SATURATED
- **Verdict notes**: Beyond the single mindroom-ai plugin, this is already a built-in capability of multiple maintained frameworks/products: Cloudflare's "Agent Memory" (announced at Agents Week, beta per InfoQ/Heise coverage) explicitly ships the full conversation to a separate durable memory service during compaction instead of discarding it; PraisonAI's documented memory lifecycle hooks fire on compaction and are designed to mirror writes to an external vector store; Swarms' `ContextCompressor` (docs.swarms.world) archives the raw transcript to disk at compaction time. That's one major vendor product plus two open-source agent frameworks already doing this, not an unaddressed gap.

### P5: Session-scale storage bottlenecks breaking compaction on very large agent sessions
- **What it is**: Long-lived agent "main sessions" accumulating tens of thousands of events and hundreds of megabytes hit multi-second storage-layer reads and outright compaction failures at scale — the compaction system that's supposed to keep context small breaks down exactly when sessions get large enough to need it most.
- **Evidence**: `openclaw/openclaw` issue #181084, "Very large main session (35k events / 228 MB) causes multi-second SQLite snapshot reads; sessions compact fails with 'admission is closed', also right after a gateway restart" (2026-10-22, 1 reaction, 7 comments) — filed by an AI assistant on behalf of its user, with measured numbers from the user's own gateway.
- **Why it looks unbuilt/untested**: The filer explicitly measured and reported real numbers rather than citing an existing fix; the bug report format itself ("anything not measured is marked as hypothesis") signals this is fresh, unresolved territory, not a known/patched issue.
- **Maturity**: PARTIAL
- **Verdict notes**: No implementation found that fixes this specific failure mode (multi-second SQLite snapshot reads / "admission is closed" at 35k events / 228MB). An arXiv preprint ("The Compaction Cliff in Long-Running AI Agent Memory", arXiv 2608.22752) documents a related failure class (hierarchical-truncation compaction preserving only ~50% of safety constraints across 50 real agent configs) and several practitioner write-ups (fast.io, dev.to) converge on the same generic mitigation — externalize state to durable storage before compacting rather than fixing in-place storage performance — but none implements a fix for the storage-layer bottleneck itself. Real, documented gap with only generic advice, not a working solution, behind it.

### P6: Verifying agent memory authenticity (detecting counterfeit/tampered memory)
- **What it is**: A proposed evaluation technique to check whether an AI agent's claimed long-term memory is genuine (actually derived from its own prior experience) versus fabricated/counterfeit — using LLM judges to tell the difference.
- **Evidence**: Hacker News, "Three LLM judges couldn't tell an AI agent's real memory from a counterfeit one" (2026-10-17, 5 points), linking to a write-up at kairos-experiment.com/checks.html.
- **Why it looks unbuilt/untested**: The headline itself reports a negative result — the straightforward approach (ask LLMs to judge) failed — meaning no working memory-authenticity verification method is demonstrated yet, only a documented gap.
- **Maturity**: PARTIAL
- **Verdict notes**: Active but narrow/unevaluated research exists on the adjacent "memory poisoning/forged-reasoning" framing: `MemSentry` (arXiv 2609.08747, open-source provenance-based pre-commit checks), "Proof-of-Execution Memory" (arXiv 2608.16032, MIT-licensed, checks a tamper-evident execution ledger instead of inspecting memory content), and a forged-reasoning-attacks survey covering `A-MemGuard` consensus checks. Critically, a Manifund grant writeup reports its own headlined detection mechanism "performed no better than chance" under a preregistered test — corroborating the original evidence that naive judge-based detection doesn't work. These are research-grade, not production-evaluated, implementations — real gap, differentiated build still viable.

### P7: Structured "context intents" and relationship packets as a native memory format
- **What it is**: Instead of storing/replaying raw transcript or ad hoc key-value memory, encode an agent's context as explicit structured objects — "context intents" and "current relationship packets" — that capture what the agent is trying to do and how entities relate, as first-class data the agent runtime understands natively.
- **Evidence**: `unbraind/pm-rust` PR #154, "feat: native context intents and current relationship packets" (2026-11-06, 1 reaction, 46 comments — a large review thread for a single feature PR).
- **Why it looks unbuilt/untested**: This is a single project's in-progress feature branch (not a released, documented pattern), and the unusually long review thread (46 comments) suggests the design is still being contested/iterated rather than settled.
- **Maturity**: PARTIAL
- **Verdict notes**: The exact terms "context intents"/"relationship packets" don't appear elsewhere, but closely related structured-memory formats are already shipping or standardizing: the IETF Internet-Draft PAMSPEC (draft-infantado-agent-memory-architecture-00, July 2026) defines a persistent-state plane of Memory Objects and Relationship Objects distinct from the context window; Emergence AI's CRAFT "Context Packs" (docs.emergence.ai) are a shipped platform feature grouping typed memory records; LocusGraph uses typed relationship link arrays. No implementation found that captures agent *intent* as a first-class object the way `unbraind/pm-rust`'s PR proposes, and that PR itself remains unmerged/contested — real, still-narrow gap for a differentiated build.
