## Candidate patterns

### P1: Dual-index chunking — separate indexes for retrieval precision vs. agent actionability
- **What it is**: Instead of one chunking strategy serving both the embedding-retrieval step and the agent's downstream action step, maintain two indexes: small chunks tuned for retrieval recall/precision, and larger, coherent chunks tuned for what an agent can actually act on.
- **Evidence**: Tian Pan's blog post "Chunking for Agents vs. RAG: Why One Strategy Breaks Both" (tianpan.co, May 2026, found via WebSearch) argues chunk sizes tuned for retrieval leave agents with fragments too small to act on, and recommends separate indexes. FutureAGI's glossary entry on "agentic chunking" (found via WebSearch) calls it a "measurable reliability surface" that can raise token-cost-per-trace "without a clear payoff."
- **Why it looks unbuilt/untested**: Both sources are a solo blog post and a vendor glossary explainer proposing the architecture conceptually — FutureAGI explicitly flags the ROI as unproven. No maintained open-source implementation surfaced in search.
- **Maturity**: SATURATED
- **Verdict notes**: The core architecture (small chunks indexed for retrieval, larger coherent chunks returned for use) already ships as a mature, maintained feature in both major RAG frameworks — LangChain's `ParentDocumentRetriever` (separate child/parent splitters + docstore) and LlamaIndex's `AutoMergingRetriever` (hierarchical node parser that merges retrieved children back to parents). Redis also documents the same "parent-child indexing" pattern as a standard technique. The "agent actionability" framing (preconditions/rollback steps, not just more context) is a thin reframe of an already-solved architecture, not a new gap.

### P2: Automated retrieval-vs-chunking-vs-generation failure attribution
- **What it is**: Tooling that automatically classifies each wrong RAG answer as a retrieval failure, a chunking failure, or a generation failure, instead of engineers manually guessing which stage broke.
- **Evidence**: Multiple 2026 production-RAG writeups surfaced via WebSearch (including "Production RAG Systems — 7 Lessons We Learned the Hard Way" and a RAG-evaluation framework guide) recommend teams "attribut[e] each wrong answer to retrieval, chunking, or generation" and note that teams "lacking an evaluation framework often don't know their system is broken."
- **Why it looks unbuilt/untested**: Described as manual triage practice/advice across several blog posts — no named shipped tool automates the classification per the search results.
- **Maturity**: OPEN
- **Verdict notes**: Genuine multi-channel search (GitHub, web, papers) found only diagnostic methods, not an automated classifier: the "known-good context" manual test, RAGChecker's claim-level analysis (which separates retrieval from generation but doesn't address chunking), and a TU Delft academic failure taxonomy. A LangChain forum thread ("When is it actually a failure? Diagnosing agent behavior beyond LangGraph traces") explicitly states that tools which detect post-retrieval failures can't trace them back to specific insufficient chunks and calls that runtime attribution layer missing. No shipped tool automating the 3-way (retrieval/chunking/generation) classification surfaced anywhere.

### P3: Confidence-gated retrieval abstention ("say I don't know below threshold")
- **What it is**: The RAG system explicitly abstains with "I don't know" when retrieval similarity/confidence falls below a threshold, instead of always generating an answer from weak or irrelevant retrieved context.
- **Evidence**: A production RAG writeup surfaced via WebSearch reports a team that cut their hallucination rate "from 12% to under 2%" specifically by instructing the model to abstain when retrieval fell below a confidence threshold.
- **Why it looks unbuilt/untested**: Reported as one team's internal fix inside a blog post, not a standard parameter or library feature available off-the-shelf in mainstream RAG frameworks per the search results.
- **Maturity**: PARTIAL
- **Verdict notes**: The raw mechanism (fixed similarity-score cutoff that returns "I don't know" before generation) already ships in LangChain and LlamaIndex as a basic retriever filter, and one arXiv study (2509.01476) finds retrieval-augmented models can use uncertainty estimates to abstain via thresholds. But every source agrees fixed thresholds are an uncalibrated, weak fix (one practitioner post: "raising the threshold helps a little and then stops helping"); the only named calibration-focused library, KnowOrNot, is unverified/unconfirmed by a second source. No mature, calibrated, off-the-shelf abstention system exists — the gap (calibrated confidence, not raw score filtering) is real.

### P4: Freshness-decay + hybrid BM25/vector ranking inside agentic retrieval loops
- **What it is**: Combine recency-decay weighting with hybrid BM25-plus-vector search specifically inside multi-step agent retrieval loops (not classic single-pass RAG), since agents re-query repeatedly and stale or off-target chunks compound across steps.
- **Evidence**: An r/AI_Agents thread (found via WebSearch) argues most agent RAG failures are retrieval problems — "chunking errors, lack of freshness signals, and reliance on pure vector search" — and recommends "structural chunking, decay-based ranking, and hybrid BM25 plus vector search."
- **Why it looks unbuilt/untested**: Framed as a Reddit poster's argument/recommendation; no shipped library or benchmark implementing this specific combination was named in the search.
- **Maturity**: PARTIAL
- **Verdict notes**: Hybrid BM25+vector fusion with a recency adjustment is a known, even productized pattern for single-pass RAG — Ragie's docs ship a "recency bias" feature (50/50 score blend with recency tiebreak), and multiple tutorials (theneuralbase, joinstash.ai) give working exponential/half-life decay code. But a Weaviate forum thread confirms this is still an open, unresolved pain point in practice ("hybrid search still favors a 3-year-old chunk over yesterday's"), and nothing found specifically addresses the compounding effect across multi-step *agentic* retrieval loops as opposed to single-pass RAG — that specific angle remains a real, narrower gap.

### P5: Chain of Noting (CoN) for robust retrieval under noisy context
- **What it is**: A retrieval technique where the agent writes intermediate "notes" that summarize and filter retrieved passages before composing the final answer, intended to improve robustness when retrieved documents are noisy, partially irrelevant, or contradictory.
- **Evidence**: GitHub PR `arakoodev/EdgeChains#844`, "feat(ai): implement Chain of Noting (CoN) for robust RAG retrieval" (2026-11-10), surfaced directly by the last30days engine's GitHub source.
- **Why it looks unbuilt/untested**: Single PR in one project, CLA just signed by the contributor, only 4 comments at time of capture — an early-stage implementation, not yet an adopted or benchmarked pattern elsewhere.
- **Maturity**: PARTIAL
- **Verdict notes**: Chain-of-Note is a published technique (Yu et al., arXiv 2311.09210, EMNLP 2024, Tencent AI Lab) with a prior LangChain "chain-of-note-wiki" template implementation — but that template now only survives as an archived git mirror (not in LangChain's current maintained templates per search), and is prompt-only/Wikipedia-scoped. The new EdgeChains PR is a second, independent, equally early-stage attempt. Two abandoned/nascent implementations, no adopted or benchmarked production version — real gap for a maintained, general-purpose implementation.

### P6: Per-query routing between naive RAG and agentic/multi-hop RAG
- **What it is**: A routing layer that decides, per incoming query, whether to serve it with cheap single-pass ("naive") RAG or escalate to expensive agentic multi-hop RAG — rather than locking a whole system into one architecture regardless of query complexity.
- **Evidence**: The last30days engine surfaced GitHub docs PR `ojungo69/oboete#609`, which cites arXiv 2610.30755, "Is Complex Agentic Memory Always Needed? Naive RAG Is Stronger Than We Thought," next to spec lines on raw retrieval vs. reranking. WebSearch supplements found practitioner guides stating the naive-vs-agentic choice "is not a question with a universal answer," describing routing conceptually: "default to RAG for narrow lookups and escalate to long context or agentic paths for cross-document synthesis."
- **Why it looks unbuilt/untested**: The cited paper directly challenges the premise that agentic complexity is usually warranted; guides describe routing only conceptually — no named shipped router or decision benchmark that automates this per-query choice turned up in search.
- **Maturity**: SATURATED
- **Verdict notes**: This is an established technique, not a new gap. `starsuzi/Adaptive-RAG` is the original paper's own repo (Jeong et al., NAACL 2024 — trains a T5-Large classifier to route queries among no-retrieval/single-step/multi-step paths), and GitHub search surfaced 10+ independent reimplementations (`Adaptive-RAG-Routing`, `adaptive-rag-router`, `rag-biomed`, `adaptive-rag-oracle-gap`, an evaluation-vs-baselines repo, etc.) plus production write-ups describing the same pattern as standard practice (LLM/rule-based/learned routers). Well-resourced teams and the original academic authors have already closed this gap.

### P7: Draft standardized reference architecture for agentic RAG on MCP/Kubeflow
- **What it is**: A documented, standardized stack for running agentic RAG over an organization's own documents using MCP (FastMCP Streamable HTTP transport) plus Kubeflow, including a runtime-configuration table (collections, ports, transport) meant to be reusable across teams.
- **Evidence**: GitHub issue `cncf/endusers#2114`, "[Reference Architecture:] Agentic RAG on Kubeflow — Implementation Deep Dive" (2026-11-08, 4 reactions, 2 comments, authored for the CNCF Agents Working Group), surfaced by the last30days engine's GitHub source.
- **Why it looks unbuilt/untested**: The issue is explicitly marked "Draft for community review," and its linked working repo (`kubeflow/docs-agent`) is new — not yet validated at scale or adopted beyond this one proposal.
- **Maturity**: PARTIAL
- **Verdict notes**: Pieces of this exist separately but nothing combines them: Red Hat's `RHEcosystemAppEng/RAG-Blueprint` is a maintained Kubeflow-Pipelines-based RAG reference but is non-agentic and doesn't use MCP; AMD's documented Agentic RAG solution blueprint uses a LangGraph agent calling retrieval tools over MCP on Kubernetes/Helm, but not Kubeflow; Google Cloud's ADK reference uses MCP for agent-tool standardization on Cloud Run, not Kubeflow. No source combines agentic RAG + MCP + Kubeflow into one standardized, reusable stack — the CNCF issue's own "Draft" status and brand-new linked repo confirm this specific combination is still unvalidated.

### P8: Compute-efficient retrieval algorithms to cut RAG latency/cost
- **What it is**: Retrieval-step algorithms engineered specifically to reduce the compute cost of retrieval itself (distinct from generation-side cost cutting) while preserving RAG answer quality.
- **Evidence**: Hacker News thread "Faster Retrieval for Better, More Efficient RAG" linking to Apple Machine Learning Research (2026-11-11), surfaced by the last30days engine with 233 points and 38 comments — the single highest-engagement item across both engine runs, indicating strong latent community interest in retrieval-cost efficiency.
- **Why it looks unbuilt/untested**: A fresh research-paper discussion/announcement rather than an available, ergonomic library; the high HN engagement signals demand for a packaged implementation that doesn't yet exist per the search.
- **Maturity**: SATURATED
- **Verdict notes**: The general category — algorithms that cut retrieval compute cost while preserving quality — is an extremely mature, multiply-maintained field: FAISS, ScaNN, HNSWlib, Spotify's `voyager`, Milvus, Qdrant, pgvector, and DiskANN all exist specifically to solve this, with multiple actively maintained repos (`spotify/voyager` committed within the last day of search). Apple's specific contribution (learned MIPS routing via "SupportNet"/"KeyNet," reportedly tied to ICML 2026, claiming faster retrieval than centroid routing on Natural Questions) is incremental research layered on top of an already-saturated space, not evidence of an open gap — it will likely get absorbed into one of the existing libraries rather than need a new one built from scratch.
