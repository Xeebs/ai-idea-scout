## Candidate patterns

### P1: Retrieval-gated tool exposure for over-tooled agents
- **What it is**: Instead of handing an agent every MCP tool definition at once, a retrieval/router layer exposes only the handful of tools relevant to the current step, loading the rest on demand. Pitched as the fix for agents picking the wrong tool as server counts grow.
- **Evidence**: Multiple independent write-ups converge on the same finding — archestra.ai's "How many MCP tools is too many?", natoma.ai's "The invisible tax killing your AI agents at scale," and a run of tianpan.co posts ("Tool Explosion Problem," "Over-Tooled Agent Problem," "Tool Selection Problem") all cite the RAG-MCP benchmark: full tool-list-in-prompt scored 13.62% correct tool choice vs ~43% when only the relevant subset was retrieved, same model and tools (via WebSearch, hackernoon.com writeup of the preprint).
- **Why it looks unbuilt/untested**: Sources disagree sharply on the safe tool-count threshold (10-20 vs ~40 vs 40-50), and every mitigation described (retrieval, hierarchical routing, sub-agent splitting) is a DIY pattern assembled per-team, not a packaged, benchmarked product — one source explicitly flags that bad retrieval just trades "too many tools" for "wrong tools."
- **Maturity**: SATURATED
- **Verdict notes**: Anthropic shipped the Tool Search Tool + `defer_loading` on the Claude Developer Platform (beta header dated Nov 2025, per Anthropic's own "advanced tool use" engineering post) and Claude Code applies it automatically, with third-party reports of 85-95% token reduction. Atlassian independently open-sourced `mcp-compressor` (built into Rovo Dev, claims up to 97% reduction). Both are shipped, maintained products from well-resourced teams squarely targeting this gap, on top of smaller OSS implementations (`memoverflow/rag-mcp`, 21 stars, a direct RAG-MCP paper port; `rocket-connect/mcp-rag`, 6 stars).

### P2: Pre-install trust/verification layer for MCP servers
- **What it is**: A verification/attestation layer that checks an MCP server's provenance and behavior before an agent or human installs it, distinct from the protocol's own auth — closer to a package-registry trust score than OAuth.
- **Evidence**: Show HN post "USB: A trust layer for AI skills and MCP servers" (news.ycombinator.com, 11pts/3cmt, 2026-11-09, via engine run 2); corroborated by WebSearch hits on broader "MCP sucks" security critique threads (one cited at 311pts/291cmt per gradientflow.com's roundup) and evokesecurity.com's framing that "an MCP server can do anything the host process can do."
- **Why it looks unbuilt/untested**: The HN submission itself is a single low-traction weekend-project-shaped post (3 comments), not an adopted standard; the broader security discourse treats this as an open, first-order design gap rather than a solved one.
- **Maturity**: PARTIAL
- **Verdict notes**: Broader search (beyond the one HN post) found several real but fragmented attempts: Trust3 AI's "MCP Security" product (launched May 2026, registry-based server verification + scoped tokens), JetStream Security's "Verified MCP Governance Layer," an npm v0.1.0 attestation SDK from AgentLair, and an open-source TEE/RA-TLS-based `attestable-mcp-server` (co-browser/Kontext). None has adoption data or is treated as a default; a reviewer note explicitly frames server-side attestation as still "Phase 2" work beyond today's gateway-boundary claims. Real, differentiable gap remains despite multiple narrow attempts.

### P3: Cross-client MCP server manager / unified TUI
- **What it is**: A single terminal UI to install, enable/disable, and configure MCP servers across multiple AI coding tools (named targets: Claude Code and Codex) instead of hand-editing each tool's own config format.
- **Evidence**: Show HN "One TUI to Manage MCP Servers for Claude Code and Codex" (toolshed.run, 8pts, 2026-11-09, via engine run 2).
- **Why it looks unbuilt/untested**: Low engagement (8 points, no recorded comments) for a real pain point implied by the post itself — that each client currently needs its own separate MCP config — suggesting the fragmentation is acknowledged but no dominant tool has emerged yet.
- **Maturity**: SATURATED
- **Verdict notes**: A dominant tool has in fact emerged — `pathintegral-institute/mcpm.sh` (1,026 stars, pushed within the last 2 days, "CLI MCP package manager & registry for all platforms and all clients," with router/profile features) squarely covers cross-client management. Also actively maintained: `kinhunt/mcpdog` (20 stars, explicitly supports Claude Desktop, Claude Code, Cursor, Gemini CLI) and `vlazic/mcp-server-manager` (24 stars, cross-platform single binary). The specific toolshed.run TUI is low-traction, but the underlying gap it names is already closed by better-adopted tools.

### P4: OAuth as the dominant silent-failure point for production MCP servers
- **What it is**: A workflow/debugging gap around MCP's remote-server OAuth flow — failures are described as silent and hard to trace, pushing teams toward static API keys instead of the intended auth flow.
- **Evidence**: WebSearch surfaced a cited "2026 survey" claim (via a practitioner write-up) that OAuth is the largest blocker for production MCP servers and that "over half of remote servers fall back to static keys" because OAuth failures are silent; Speakeasy's engineering blog ("we were wrong about the hard problem") independently reframes the hard part of MCP in production as distribution/management rather than building, which runs alongside this complaint.
- **Why it looks unbuilt/untested**: No named tool was found that specifically diagnoses/traces MCP OAuth handshake failures; the fallback-to-static-keys behavior described is itself evidence teams are working around the gap rather than it being solved.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up search found named tools doing exactly this: Postman's dedicated MCP OAuth Debugger (phase-by-phase pass/fail trace, redacts DCR secrets), Anthropic's own MCP Inspector, and the OSS tool `authprobe/authprobe` (16 stars, maintained, literally described as "pinpoints MCP OAuth failures"), plus MCPLab's OAuth Debugger and vendor troubleshooting guides (TrueFoundry, LiteLLM). The specific-tool gap the digest flagged as empty is not empty.

### P5: Tool-description context compression / caching for agent usage limits
- **What it is**: Tooling that trims or caches the context consumed by tool schemas and prior tool-call history specifically to stretch an agent's usage-limit budget, as a distinct product category from general prompt caching.
- **Evidence**: Show HN "Thinker – Trim context and cache knowledge to extend agent usage limits" (thinker.sh, 4pts/2cmt, 2026-11-05, via engine run 2); motivating complaint corroborated by WebSearch finding a conference quote (reported secondhand) attributing to Perplexity's CTO the claim that MCP tool descriptions consume "40-50% of available context windows before agents do any actual work."
- **Why it looks unbuilt/untested**: The one concrete shipped example (Thinker) has single-digit HN points and 2 comments — early/unvalidated; the 40-50% context-tax claim itself is repeated across secondary sources but traces to one conference remark, not a benchmark.
- **Maturity**: SATURATED
- **Verdict notes**: Same category as P1 but even more directly productized: Atlassian's `mcp-compressor` is a shipped, open-source proxy built into their Rovo Dev product specifically to cut tool-schema token cost (claims up to 97% reduction with a documented accuracy trade-off), and `headroomlabs-ai/headroom` ships as a library/proxy/MCP server explicitly compressing tool outputs "same answers, 20-95% fewer tokens." Thinker itself is unvalidated, but the gap it targets is already covered by better-resourced shipped tools.

### P6: Narrow single-purpose MCP servers shipping faster than any review/curation layer
- **What it is**: A wave of small, single-API MCP servers (messaging, travel/eSIM purchase, weather data) shipping as weekend Show-HN projects, each wrapping one external API with no shared quality bar.
- **Evidence**: Three separate Show HN posts in one month from the engine run: "WhatsApp MCP" (3pts/6cmt, 2026-10-23), "Atli – MCP server that lets AI agents buy and install travel eSIMs" (6pts/1cmt, 2026-11-17), "Meteosource MCP server, weather data for AI assistants" (3pts/1cmt, 2026-11-04); paired with "Rebuilding the Metabase MCP server: lessons for MCP tool design" (metabase.com engineering blog, 11pts/1cmt, 2026-11-17) describing a vendor having to redo their own server because the first attempt got the tool design wrong.
- **Why it looks unbuilt/untested**: Every one of these is independent and uncoordinated — no shared scaffold, linter, or design-review checklist referenced across them; the Metabase post is explicitly a "we got it wrong the first time" retrospective, implying the mistakes P6 describes are still being made fresh by each new server author.
- **Maturity**: PARTIAL
- **Verdict notes**: Real curation/linting tools do now exist — `blackwell-systems/mcp-assert` (27 stars, pushed today, found 4,794 schema issues across 55 real servers), `mcp-conform` (pre-publish conformance linter targeting the 2026-07-28 spec), and Glama's per-server quality/security ratings — but none is referenced or required by the narrow Show-HN servers surveyed, the official registry itself only checks namespace/metadata (not safety), and `awesome-mcp-servers`' own README tells users to vet servers themselves. Tooling exists; adoption/enforcement does not, so the gap is real and buildable (e.g., a CI gate wired into the registry submission flow).

### P7: Stateless MCP server architecture for horizontal scaling
- **What it is**: Redesigning remote MCP servers to avoid holding session state per-connection, so they can scale behind a normal load balancer instead of requiring sticky sessions.
- **Evidence**: WebSearch surfaced dev.to's "AI Weekly: Coding Tool Shakeups and Stateless MCP" and a companion "AI Weekly: Codex Goes Long, MCP Goes Stateless," plus portkey.ai's "From standard to ecosystem: the new MCP updates" discussing the same scaling-friction framing.
- **Why it looks unbuilt/untested**: Coverage is at the newsletter/roundup level (secondary summarization of a spec-direction discussion), not a shipped reference implementation or adoption report — the pattern is described as a response to friction, not yet a settled practice.
- **Maturity**: PARTIAL
- **Verdict notes**: Found a dedicated, actively-maintained framework — `vitemcp/server` (25 stars, pushed yesterday, "A TypeScript framework for building stateless MCP servers") — plus several individual production stateless servers (KalvadTech's Redmine/Woodpecker MCP servers, PeronGH's Cloudflare Workers-based servers). This shows real adoption beyond newsletter talk, but there's still no dominant reference architecture, adoption report, or benchmark comparing stateless vs. sticky-session designs at scale — early and scattered rather than solved.

### P8: Hardened/sandboxed runtime for executing third-party MCP servers
- **What it is**: A sandbox or firewall layer that runs an untrusted MCP server's code with restricted filesystem/network/exec access, so a malicious or buggy server can't act with the full privileges of the host agent process.
- **Evidence**: WebSearch corroboration: evokesecurity.com's framing that "an MCP server can do anything the host process can do" (read files, exfiltrate data, run arbitrary code); the earlier pre-research WebSearch (recorded in this run's setup) surfaced a reference to a large-scale audit of ~25,000 MCP tools reportedly finding a remote-code-execution class issue nicknamed "ClawBleed" that turns local servers into exfiltration endpoints.
- **Why it looks unbuilt/untested**: The "USB" trust-layer project (P2) and GitHub's own `gh-aw-firewall` project (seen as noise in engine run 1 but concretely active — PRs on "pinned installs without runtime attestation lookups" and routing, both merged/open in the last 30 days) show organizations actively building toward this, but no single sandboxing layer was found treated as a default/standard; the ClawBleed claim itself traces to a single secondary newsletter summary, not a primary disclosure, so it should be re-verified before being treated as confirmed.
- **Maturity**: PARTIAL
- **Verdict notes**: Confirmed a crowded but fragmented field: GitHub's own `gh-aw-firewall`, plus OSS sandboxes/firewalls actively pushed in the last 30 days — `ressl/mcp-firewall` (22 stars), `technosiveuk-ui/SentinelMCP` (14 stars), `caiovicentino/jev-shield` (claims 94% block recall, 0 false positives), `jeliasson/mcp-sandboxd` (Docker/K8s isolated execution), `mcp-hub-corp/mcp-cage`. Many active attempts, none consolidated into a default hardened runtime; the ClawBleed audit claim remains unverified secondary-source info as originally flagged. Tie between PARTIAL and SATURATED resolved to PARTIAL per the fragmentation and lack of a standard.
