## Candidate patterns

### P1: Auto-converting observed traces into regression evals ("close the loop")
- **What it is**: A mechanism that, when an engineer or agent reads a production LLM trace (via a tracing UI or MCP tool) and spots a failure, automatically offers to promote that trace into a saved eval case — instead of the trace being read once and discarded.
- **Evidence**: PostHog's own `posthog/posthog` repo, PR `chore(aio): point agents reading traces to online evals` (2026-11-03, 4 comments): "Coding agents read a lot of LLM traces through the PostHog MCP, but rarely go on to set up an online evaluation for what they find," and notes the planned "Related" footer nudge "can't land" because a prior PR removed MCP discovery-hint footers. WebSearch (`LLM observability 2026 discussion pain points...`) surfaced the same macro gap: "most teams treat evals as a CI/CD concern and observability as a production concern" and one vendor's stat that "89% of teams have agent observability instrumented, but only 52% run offline evaluations."
- **Why it looks unbuilt/untested**: Even the vendor (PostHog) building this natively couldn't land the nudge due to an internal regression, and the industry-wide stat shows a ~37-point gap between instrumentation and actual eval practice — teams observe but don't systematically convert findings into regression tests.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub has a cluster of recent hobby repos attacking exactly this (`wwb-bill/trace-to-eval`, `r-bug-r/trace-to-eval`, `AthenaTheOwl/trace-to-eval-harness`, `a-bhimava/agent-trace-to-evals`, all created Jul–Oct 2026, all 0 stargazers) — genuine but unvalidated one-off attempts. Established vendors cover adjacent ground manually/semi-automatically: Confident AI auto-curates traces into eval datasets, Langfuse/LangSmith support linking a trace to a dataset example via SDK or UI, but none offer the automatic "offer to promote while reading a trace" loop PostHog itself couldn't land.

### P2: Behavioral/strategy-level trace analysis beyond pass/fail
- **What it is**: A trace viewer or analysis layer that answers "what strategy did the agent use and why" across a long multi-step trace, rather than only "did it pass or fail."
- **Evidence**: `AEBench/AEBench` PR #151, "[feat] Add 'Graphectory-esque' implementation to trace viewer" (2026-10-27): "As AI agents grow more capable, their execution traces become massive and difficult to comprehend. A linear trace viewer works well for determining whether an AI agent passed or failed. However, it does not support higher-level behavioral analysis, such as understanding what strategies [were used]."
- **Why it looks unbuilt/untested**: Framed explicitly as a missing capability in an existing open benchmark/eval tool's own viewer, not a hypothetical — the PR exists because the maintainers don't have this yet.
- **Maturity**: PARTIAL
- **Verdict notes**: `Intelligent-CAT-Lab/Graphectory` is a real published artifact (OOPSLA'26 paper, "Process-Centric Analysis of Agentic Software Systems") doing strategy-level trace analysis, which is exactly why AEBench's PR cites a "Graphectory-esque" viewer as the thing it still lacks. It's an academic research tool, not a maintained product; vendor viewers (Braintrust "Analyze trace," Monte Carlo loop/step detection) do adjacent diagnosis but not strategy-level behavioral analysis across long multi-step traces.

### P3: Cross-framework multi-agent tracing
- **What it is**: Tracing that correctly follows a request across multiple agent frameworks/runtimes stitched together (e.g., a LangGraph agent calling a CrewAI sub-agent calling a raw tool-use loop), as a single coherent trace rather than fragments.
- **Evidence**: WebSearch surfaced a dev.to review, "I evaluated every AI agent observability tool on the market, here's what's actually missing" (Utibe Okodi): names cross-framework multi-agent tracing as "broken in every existing tool" tested. A second dev.to post found via the same search (Soufian Azzaoui, "I tried LangSmith, Langfuse, Helicone, and Phoenix") reports none of the four covered his needs, so he built a custom tool ("AgentLens") instead.
- **Why it looks unbuilt/untested**: Independently named as broken across an entire market sweep of tools, and corroborated by a second practitioner resorting to a bespoke build rather than adopting an existing product — the textbook "we hacked together" signal.
- **Maturity**: PARTIAL
- **Verdict notes**: Single-framework instrumentation is heavily built out (Arize Phoenix/OpenInference, Langfuse, AgentOps, MLflow, LangSmith each cover LangGraph, CrewAI, AutoGen individually, per vendor docs), but no source found confirms true single-coherent-trace stitching across heterogeneous frameworks in one request. Two independent dev.to practitioner reviews (Utibe Okodi's market sweep; Soufian Azzaoui, who built a bespoke "AgentLens" after trying LangSmith/Langfuse/Helicone/Phoenix) both call this specific sub-problem unsolved — real gap, not saturated by the broad per-framework coverage that does exist.

### P4: Verifying that a traced tool call actually executed correctly, not just that a span exists
- **What it is**: Observability that checks the real-world outcome/side-effect of a tool call an agent made (e.g., did the API call actually succeed and have the claimed effect), rather than just recording that a span with an output string was emitted.
- **Evidence**: Same dev.to market-sweep review (via WebSearch): "tools trace the span, record the output, and move on, never verifying that the tool was actually executed."
- **Why it looks unbuilt/untested**: Named as a market-wide gap by someone who evaluated the full current tool landscape, not an isolated complaint.
- **Maturity**: PARTIAL
- **Verdict notes**: `sierra-research/tau-bench` and `tau2-bench` (actively maintained, commits as recent as today 2026-11-14) are real, used benchmarks that measure exactly this property — did the tool call actually change the world correctly, not just return a span — but only inside narrow synthetic sandboxed domains (retail/airline), not as a general production observability feature. Web search (Arize, Openlayer, Octavus) confirms practitioners agree this is unaddressed in general tooling: "I didn't find a single standard tool that does this automatically."

### P5: RL-trained specialist error-finders as an alternative to prompted LLM-as-judge
- **What it is**: A dedicated model trained (via RL, not prompting a general-purpose LLM) specifically to find errors inside agent execution traces — a narrower, purpose-built alternative to the generic "ask GPT/Claude to grade this trace" pattern.
- **Evidence**: Hacker News, "Launch HN: Laminar (YC S24) – RL-trained model that finds errors in agent traces" (2026-10-19, 59 points, 35 comments) — meaningful engagement for a Show/Launch HN post.
- **Why it looks unbuilt/untested**: This is a fresh YC launch (one data point), and the comment volume suggests active community debate about whether a specialist trained model beats prompted LLM-judges for this task — not yet a settled or widely-replicated approach.
- **Maturity**: PARTIAL
- **Verdict notes**: Laminar (`lmnr-ai/lmnr`, 3,488 GitHub stars, YC S24) actually shipped "flow-1," an RL-trained model squarely matching this pattern (reads traces end-to-end to find silent errors, claims 20–23x cost advantage over prompted LLM judges per the company's own benchmark). It's real and shipped, but it's a single-vendor launch from Oct 19 2026 with unverified installation/weights per third-party reporting and active comment-thread debate over whether the approach actually beats prompted judges — unevaluated independently, so PARTIAL rather than SATURATED.

### P6: LLM-as-judge fails to detect fabricated/counterfeit agent memory or internal state
- **What it is**: Using an LLM (or panel of LLMs) as a judge to verify claims an agent makes about its own internal state (e.g., "I remember X") is unreliable — judges can't reliably distinguish a genuine memory read from a fabricated one.
- **Evidence**: Hacker News, "Three LLM judges couldn't tell an AI agent's real memory from a counterfeit one" (2026-10-17, 5 points), linking to `kairos-experiment.com/checks.html`.
- **Why it looks unbuilt/untested**: Low engagement (5 points) but a direct, concrete demonstrated failure mode of the dominant LLM-as-judge evaluation technique — a gap in a widely-used method, not a feature request.
- **Maturity**: PARTIAL
- **Verdict notes**: Active but early research front: an audit found an LLM judge on the LoCoMo benchmark accepted up to 63% of deliberately wrong answers; HaluMem (operation-level hallucination benchmark for memory) and MemLeak (3-judge ensemble majority vote) are real papers attacking adjacent sub-problems; the `memtrust` project reports a vendor's unreproducible 100% LongMemEval score was pulled after scrutiny. No settled or adopted solution found — just competing early attempts, which is PARTIAL by rubric (tie goes to PARTIAL), not OPEN.

### P7: Coverage-honesty — surfacing partial/truncated AI review coverage instead of claiming 100%
- **What it is**: When an automated AI reviewer/evaluator has to truncate or chunk a large file/input before the model sees all of it, the system should visibly flag which parts were actually reviewed rather than reporting blanket full coverage.
- **Evidence**: `amoai-tech/mdeai` PR #730, "SAN-1634 · Show partly reviewed giant files instead of claiming 100% AI coverage" (2026-11-04, 21 comments): "An actual four-chunk NVIDIA PR-Agent review ... detected that one huge documentation patch ... was clipped before the model saw its full contents. The existing strict reviewer verifier correctly rejects incomplete coverage, b[ut] ..." (cut off in source, implying other paths still report full coverage).
- **Why it looks unbuilt/untested**: A real incident (not hypothetical) with 21 comments of discussion, describing exactly the kind of silent eval-coverage gap that erodes trust in AI-based review/eval pipelines.
- **Maturity**: PARTIAL
- **Verdict notes**: Cursor's Bugbot has actually shipped a version of this (reports when a review is partial and lists which files were left out), proving the fix is buildable and that at least one well-resourced vendor has it narrowly. But it's a single vendor's feature: Qodex silently caps diffs at 200KB before the model sees them, Claude Ultrareview has open bug reports for large diffs returning zero findings with no partial-coverage notice, and a GitHub issue explicitly requests this exact feature — the failure mode is still widespread across the market.

### P8: Normalizing fragmented agent-trace schemas across tools (OTel GenAI conventions still immature)
- **What it is**: A translation/normalization layer that reconciles the different attribute names and span shapes that LangSmith, Langfuse, Arize Phoenix, Datadog, etc. each use for agent traces, since the underlying OpenTelemetry GenAI semantic conventions for agents are not yet stable.
- **Evidence**: WebSearch (`LLM observability 2026 discussion pain points...`) found: "OpenTelemetry's semantic conventions for AI agents were still in 'Development' status as of March 2026, covering individual LLM calls but lacking standard attributes for agent orchestration, tool call semantics, multi-agent communication, memory," and "different tools use different attribute names, so a token dashboard may read three different fields depending on the span."
- **Why it looks unbuilt/untested**: The standards body itself (OTel) has not finished the spec; every vendor is filling the gap with incompatible conventions, and no cross-vendor normalization layer was surfaced in any search.
- **Maturity**: OPEN
- **Verdict notes**: GitHub search for schema-normalization repos ("OpenTelemetry GenAI semantic conventions normalize", "trace schema normalization LLM observability", "unified agent trace schema") returned zero results. WebSearch confirms OTel's agent/tool-call conventions are explicitly still "in Development" status, and found no source documenting a shared cross-vendor normalization layer across LangSmith/Langfuse/Phoenix/Datadog — Phoenix's OpenInference is "the closest thing to a common target" per the search summary, but it's one vendor's internal format, not a translation layer reconciling all of them. Genuine multi-channel search found only discussion of the fragmentation, not a tool that fixes it.

### P9: Logging the reasoning behind an agent's branch decision, not just the action taken
- **What it is**: Observability that captures *why* an agent chose one path at a decision point (e.g., "use search tool vs. answer from memory") as structured data, instead of only logging which action it ultimately took.
- **Evidence**: WebSearch (`LLM observability 2026 discussion pain points...`) surfaced a practitioner recommendation: "If your agent branches ('should I use the search tool or answer from memory'), log the decision and the reason, not just the action taken."
- **Why it looks unbuilt/untested**: Framed by the practitioner as something teams should start doing, implying current common practice (and default tooling) logs actions only — the reasoning/rationale layer is a manual, not-yet-standard addition.
- **Maturity**: PARTIAL
- **Verdict notes**: Galileo markets a shipped "decision spans" feature (structured record of what an agent chose and why, distinct from downstream-consequence spans) and Datadog has announced an "execution flow" view of decision paths — both established vendors. GitHub also shows a cluster of very recent (Nov 2026), low/no-star narrow attempts at the same idea (`ZIZKA-AI-SL/ZizkaDB`, `Superone77/TraceVista`, `Providex-AI/rootsign`, plus an independent "why layer" dev.to project). No standard schema or widely adopted convention found — narrow/fragmented rather than closed.
