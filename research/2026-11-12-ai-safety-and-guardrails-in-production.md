## Candidate patterns

### P1: Tiered guardrail pipeline with severity-based fail-open/fail-closed policy
- **What it is**: A layered enforcement chain — a cheap, fast first-pass classifier (e.g., a small prompt-guard model) ahead of a heavier hazard classifier, orchestrated by a policy layer, where high-severity categories (safety/compliance) fail-closed and low-severity categories (tone/formatting) fail-open rather than blocking the whole response.
- **Evidence**: Vendor engineering writeups surfaced via WebSearch: a GMI Cloud post (Sept 2026) describing an 86M-param fast gate ahead of an 8B hazard classifier orchestrated by NeMo Guardrails; a separate guide citing fail-closed-for-high-severity / fail-open-for-low-severity as the dominant 2026 pattern; a November 2026 Openlayer how-to (`openlayer.com/blog/llm-guardrails-enforcement-framework`) covering layered enforcement and audit records. On the engine side, `opendatahub-io/opendatahub-tests` PR #2670 (2026-11-06) shows a live team refactoring NeMo Guardrails admin-port tests to better model real in-cluster call patterns.
- **Why it looks unbuilt/untested**: Every source describing the tiered/fail-open-closed pattern is a vendor blog post or a single team's internal test refactor — no shared open benchmark or reusable reference implementation for "which severity tier fails open vs. closed" was found. The accuracy-stacking problem (below, P3) suggests nobody has solved the composition math either.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub/web search found mature general-purpose guardrail toolkits (NVIDIA NeMo Guardrails, 7.5k stars, pushed 2026-11-11; Guardrails AI, 7.6k stars, pushed 2026-11-11; LLM Guard, 3.2k stars) and a TrueFoundry gateway doc describing an "enforce but ignore on error" per-validator failure mode, but none exposes severity-tiered fail-open/fail-closed composition as a named, reusable feature — only cascading-latency and per-hook failure-mode guidance in vendor blogs (Splunk, Coralogix). The specific severity-tier composition gap is real; a build on top of existing toolkits would be differentiated.

### P2: Guardrail policy decoupled from agent redeployment (centralized dynamic policy service)
- **What it is**: Instead of hardcoding guardrail rules into each agent's code, a shared policy service that every agent instance queries at runtime, so a policy update propagates without redeploying dozens of individual agents.
- **Evidence**: Splunk's observability blog (`splunk.com/.../evals-to-guardrails.html`, found via WebSearch) states plainly: "hardcoded guardrails create structural drag, since updating one policy across dozens of agents means redeploying each one" — framed as a current pain point, not a solved problem.
- **Why it looks unbuilt/untested**: The complaint is stated as an unsolved operational cost by a vendor describing the current state of the art, not as a feature their product already ships; no GitHub repo or product name for a dedicated "guardrail policy CDN/service" turned up in the same search.
- **Maturity**: SATURATED
- **Verdict notes**: A follow-up search found exactly this already shipped: `maximhq/bifrost` (9,507 stars, pushed 2026-11-12 — actively maintained) is an open-source AI/MCP/agent gateway that enforces guardrail policy centrally per call across any number of agents without redeploying them; Galileo's "Agent Control" centralized control plane, Akto's Argus Guardrails (centralized gateway + dashboard), Gravitee, and Kore.ai all market the identical "define policy once, apply across many agents" capability as a current, sold feature, not a roadmap item. Multiple independently-built, actively maintained products close this gap.

### P3: Guardrail staleness / silent drift detection
- **What it is**: Guardrails tuned and evaluated once against a snapshot of traffic silently degrade as real input patterns shift, with no continuous recalibration or drift-alerting loop analogous to model/data drift monitoring.
- **Evidence**: Decagon's glossary entry on "guardrail evaluation" (via WebSearch) explicitly states a guardrail that passed evaluation six months ago may no longer hold against today's input patterns — framed as a known, unaddressed gap.
- **Why it looks unbuilt/untested**: The same search surfaced guardrail-vs-eval comparison posts (Arize, FutureAGI) but no tooling that treats guardrail accuracy itself as a monitored, drifting metric the way model performance dashboards do.
- **Maturity**: PARTIAL
- **Verdict notes**: Follow-up search found only adjacent generic tooling — IBM's runtime-monitoring docs (async dashboard + threshold tuning) and Galileo's threshold-based drift alerts — plus more opinion/blog content (Dynamo AI, Alpesh Nakrani guardrail book, a DEV Community post titled "Your guardrails are decaying and you aren't measuring it") restating the gap rather than closing it. No product or repo was found that specifically monitors guardrail-check accuracy itself as a drifting metric (as opposed to model output drift or agent behavior drift); the generic drift-monitoring building blocks exist but nobody has pointed them at guardrails specifically.

### P4: Register/formality-based jailbreak bypass ("lawyerspeak" prompt injection)
- **What it is**: A prompt-injection technique that defeats agent guardrails specifically by wrapping malicious instructions in formal legal/contractual language rather than casual phrasing, exploiting guardrails tuned mostly on adversarial-sounding or casual-toxic inputs.
- **Evidence**: Hacker News (via engine run): "Prompt Injection, Esq.: pwning AI agent guardrails with lawyerspeak" (mooreds, 2026-11-11, 3pts) — `https://www.mrnice.dev/posts/heavyweight-guardrails/`.
- **Why it looks unbuilt/untested**: This is a single blog-post disclosure with low HN engagement (3 points) and no visible response thread, repo, or classifier fix cited — a fresh attack class with no defense tooling surfaced in the same run.
- **Maturity**: OPEN
- **Verdict notes**: Targeted WebSearch for "lawyerspeak"/"legal register" prompt injection and jailbreak defenses found nothing matching — only CourtGuard (arXiv 2510.19844, a multiagent "defense/prosecution attorney" classifier architecture, which uses legal framing as a detection *method*, not a defense against register-shifted attacks) and generic jailbreak surveys (arXiv 2512.19011, 2505.04806) that don't mention formality/register as an attack vector. No repo, product, or paper addresses this specific bypass technique.

### P5: Agent scope/goal-drift risk as distinct from content-safety guardrails
- **What it is**: Framing "losing the plot" — an agent silently drifting from its original task/goal over a long multi-step run — as a safety category guardrails don't currently cover, since content/output guardrails check individual messages, not trajectory coherence across a session.
- **Evidence**: Hacker News (via engine run): "Agentic AI's real risk: losing the plot" (alokashtikar, 2026-11-03, 4pts) — `https://alokda.wordpress.com/2026/11/01/scared-of-falling-behind-on-ai-thats-not-where-the-risk-is/`. Reinforced by Arthur.ai's point (via WebSearch) that pre-deployment test suites are insufficient because "agents are non-deterministic, multi-step, and tool-using."
- **Why it looks unbuilt/untested**: Both sources describe the gap conceptually; neither cites a shipped trajectory-level guardrail product. Low engagement (4pts) suggests the framing hasn't yet attracted builders.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up search found this is already an active product category: PointGuard AI (enterprise security vendor, formerly AppSOC, cited in Gartner AI-security coverage) sells "Agent Mission Control" and "Guardian Agent," both marketed explicitly around detecting goal drift / "agent going rogue" at runtime via OpenTelemetry-style trajectory tracing, with automatic circuit-breaker response. Independently, an arXiv preprint "Trajectory Guard" (2601.00516, Jan 2026) proposes a Siamese-RNN anomaly detector for exactly this (tool-call-sequence drift, F1 0.88-0.94 on its own benchmark), and contrasts itself against a second prior approach (Praetor, DFA-based tool-sequence enforcement). Two independent lines of work (a sold commercial product plus academic model work building on a still-earlier approach) already squarely target this gap, even though the community posts themselves have low engagement.

### P8: Automatic conversion of offline eval suites into inline runtime guardrails
- **What it is**: Treating evaluation (batch, async, pre-deployment) and guardrails (inline, synchronous, in the request path) as two views of the same underlying checks, with tooling to promote a passing offline eval into a live inline guardrail automatically rather than re-implementing it by hand.
- **Evidence**: Splunk's "How Evals Become Guardrails" post (via WebSearch, `splunk.com/en_us/blog/observability/evals-to-guardrails.html`) frames this transition explicitly; Galileo's eval-engineering book chapter draws the same batch-vs-inline distinction.
- **Why it looks unbuilt/untested**: Sources describe the conceptual transition and the problem it would solve; no automated eval-to-guardrail compiler/product was named in either search — teams appear to be doing this translation manually today.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up search found this is already built and shipping in multiple places: `openlayer-ai/jevals` is an open-source Python library (120 stars, pushed 2026-11-07) that defines a check once and runs it both as an offline eval and an inline runtime guardrail with typed pass/block/human-review decisions; Galileo's "eval-to-guardrail lifecycle" compresses offline evaluator criteria into runtime-fast Luna-2 models (vendor-claimed 152ms vs. 3200ms for GPT-4o-as-judge) as a shipped product feature; Waxell's "Eval-Driven Governance" and LangWatch's "run an evaluator as a guardrail" API both ship the identical define-once/enforce-anywhere pattern today. At least three independently-built, shipping implementations close this gap.
