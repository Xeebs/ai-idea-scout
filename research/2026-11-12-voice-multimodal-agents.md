## Candidate patterns

### P1: Speculative/predictive tool calling to hide voice-agent latency
- **What it is**: Instead of waiting for the LLM to finish reasoning before firing a function call, the agent starts likely tool calls while the user is still speaking (from partial ASR transcript), caches results, and cancels/corrects if the final utterance changes the intent. Goal: eliminate the multi-second dead-air gap while a voice agent "decides" which function to use.
- **Evidence**: Hacker News post "Speculative tool calling: cutting voice AI agent latency" (tazolabs.com, 2026-10-13, 3pts/2cmt) from the engine run. WebSearch corroboration: a practitioner blog post framed as "how do you handle speculative tool calling in a voice loop to prevent the 3 second silence while the LLM decides which function to use" (Stream engineering blog), plus two arXiv preprints (2610.07641, 2605.13360) and an AI Weekly writeup on "Heartbeat Thinking" reporting latency cuts (5.79s→4.60s median time-to-first-audio; 6.90s→4.39s on FDBench v3).
- **Why it looks unbuilt/untested**: The framing itself is a practitioner's open question ("how do you handle X"), and the reported results are all preprints or single-vendor blog posts with no independent replication — no widely-adopted open-source library implements this as a drop-in component for arbitrary voice-agent stacks.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search found no general-purpose open-source library. WebSearch found two arXiv preprints (Speculative Interaction Agents 2605.13360; PASTE control-flow prediction) reporting 1.6–2.2x speedups, a "Heartbeat Thinking" vendor writeup (6.90s→4.39s on FDBench v3), and one shipped-but-narrow vendor feature (Deepgram Voice Agent "speculative replies," which speculates on replies but still waits for confirmation before firing tool calls). No independent replication and no drop-in library for arbitrary stacks exists, so the gap for a reusable, stack-agnostic implementation is real.

### P2: Standardized decision framework for cascaded vs. unified speech-to-speech voice pipelines
- **What it is**: Teams building voice agents must choose between a cascaded pipeline (separate ASR → LLM → TTS models) and a unified speech-to-speech model (e.g., ElevenLabs Realtime, OpenAI Realtime) where recognition, turn-taking, reasoning and synthesis are tuned together. Right now each team runs its own ad hoc bake-off.
- **Evidence**: GitHub issue `changtimwu/elevenlabs-exp#1` "Evaluate ElevenLabs Realtime (speech-to-speech) models for our agents" — "Do our samples use it today? No. Both agents use the cascaded pipeline (three separate models)." GitHub issue `thomaseude/t3code-voice#7` "Voice engine choice" — explicitly lists comparison criteria: "French quality including technical vocabulary, end-to-end latency, barge-in/interruption handling, tool calling" against "OpenAI Realtime (speech-to-speech)" vs. "a pipeline (Whisper or another STT + LLM + TTS)."
- **Why it looks unbuilt/untested**: Both are open, unresolved issues in small individual repos — each team is building its own private evaluation criteria from scratch rather than using a shared, reusable benchmark/rubric for this exact decision.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found one academic benchmark (EVA-Bench, arXiv 2605.13841, live multi-turn simulation across S2S and cascade architectures) and numerous vendor comparison posts (AWS/Nova Sonic, Inworld, Coval, Dograh, JustCall) offering ad hoc heuristics with conflicting latency numbers (e.g., Coval says S2S is faster, Inworld says a well-engineered cascade can beat it) — no single reusable, cross-vendor decision tool or rubric exists that teams actually adopt instead of running their own bake-off.

### P3: Interruption handling treated as a classification policy, not a binary toggle
- **What it is**: Rather than "interruptible: true/false," a more fine-grained pattern classifies spoken interruptions into categories (true correction, backchannel like "mm-hm", accidental noise, DTMF keypress, silence timeout, safety escalation) and responds differently to each, instead of either always stopping or never stopping when the user speaks over the agent.
- **Evidence**: WebSearch surfaced a practitioner runbook (hamming.ai) explicitly recommending treating interruption handling "as a policy to design, not a toggle," with the six-way classification above; PolyAI's engineering blog states barge-in occurs in roughly 1-in-5 calls and that mishandling it measurably lowers call-quality scores; vendor docs (Smallest AI) show only a per-node binary interruptibility setting as the current state of the art.
- **Why it looks unbuilt/untested**: No cross-vendor, open implementation of the policy-based classifier exists — every source is either a single vendor's glossary/docs page describing their own narrow toggle, or a runbook arguing for a better approach that it does not ship as reusable code.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found one directly relevant open-source artifact — a Hugging Face "bargein-classifier" model (bnovikov) that distinguishes interruption from backchannel — but its own docs flag it as English-only, trained on meeting audio (not voice-agent audio), weakly supervised, and recommended only for shadow-mode deployment. No library implements the fuller 6-way classification (correction/backchannel/noise/DTMF/timeout/safety-escalation) described in the hamming.ai runbook; vendor docs (Smallest AI) still ship only a binary toggle. Early, narrow prior art confirms the gap is real.

### P4: Self-hosted, open-source voice-agent platforms as an alternative to hosted SaaS (Vapi/Retell-style lock-in)
- **What it is**: A self-hostable stack that replicates what hosted voice-agent platforms (Vapi, Retell) offer — telephony integration, STT/LLM/TTS orchestration, call management — without sending call data through a third-party SaaS.
- **Evidence**: Hacker News "Show HN: OpenRing – Open-source, self-hosted voice AI agent platform (Vapi alternative)" (github.com/elifalanrocha/openring, 2026-11-04, 3pts/1cmt).
- **Why it looks unbuilt/untested**: Brand-new Show HN post with essentially no engagement yet (3 points, 1 comment) — too early to tell if it's a maintained alternative or a weekend project; the explicit "Vapi alternative" framing signals an unmet want (self-hosting) that existing hosted platforms don't serve.
- **Maturity**: SATURATED

Multiple maintained, well-documented implementations already squarely cover this gap.

- **Evidence**: GitHub issue `Farstax/agent-bridge#1057`, "Deferred: natural live voice conversation with existing Agent Bridge workstreams" — "Offer live two-way spoken conversations with an existing Agent Bridge coding session from a phone or browser... Low-latency speech would add audio service costs, session and interrup[tion handling complexity]."
- **Why it looks unbuilt/untested**: The issue is explicitly titled "Deferred" — the team scoped it and decided not to build it yet, which is a direct "we want this but it's too costly/complex right now" signal rather than a shipped feature.
- **Maturity**: SATURATED

Multiple independently maintained, non-trivial implementations (one with 172 stars and a packaged release) already bridge a live voice channel onto an existing coding-agent session without re-architecting it.

### P6: Retrofitting true hands-free, multi-turn voice conversation onto agents originally built for text/visual or push-to-talk interaction
- **What it is**: Adding a continuous, hands-free spoken conversation mode to an agent whose primary interface is visual/text, where the user starts a voice session once and then holds a natural multi-turn conversation without pressing a button between each turn.
- **Evidence**: GitHub issue `heckenmann/visual-agent#482`, "feat(audio): add TTS playback and hands-free voice conversations" — "Users must be able to hold a natural multi-turn spoken conversation after starting a voice session once, without pressing a button between questions and answers."
- **Why it looks unbuilt/untested**: Open feature request (not yet merged) on a project whose core product is visual/text-first — voice is being bolted on after the fact, and the hands-free, no-button-press requirement is called out explicitly as not yet met by the existing push-to-talk-style flow.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found the general retrofit pattern already shipped broadly, not just requested: Claude's own mobile app ships a documented hands-free voice mode (with an explicit fallback to push-to-talk in noisy/multi-voice settings), AgentsRoom ships a "Voice Mode" with auto-reopening mic for continuous hands-free exchange, LMSA and Convai ship similar continuous/VAD-based modes. The specific `heckenmann/visual-agent` repo hasn't shipped it yet, but the pattern itself is mature and widely productized elsewhere.

### P7: AI "coworker" agents joining live multi-human calls with low-latency spoken turn-taking
- **What it is**: An agent that currently only listens/transcribes in a meeting gets upgraded to actually speak — streaming STT → LLM-with-memory-tools → TTS piped into the meeting bot's audio output, so the agent can participate as a live voice participant on calls, not just a silent note-taker.
- **Evidence**: GitHub issue `anote-ai/Panacea#362`, "[Coworker · Phase 2] Real-time voice agent: low-latency speech in calls with natural turn-taking" — "A coworker that can only listen still needs you on the call. To run calls it has to talk, and latency is the make-or-break engineering problem." Scope section explicitly lays out the streaming pipeline as a to-do.
- **Why it looks unbuilt/untested**: Explicitly labeled "Phase 2" of a roadmap — the listening-only version exists today, the speaking/turn-taking version is planned but not yet implemented.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found shipped products attempting exactly this — MeetStream AI (Product Hunt-launched, agent joins Google Meet as a real participant and speaks mid-call), Behalf.ai (hackathon-stage, OpenAI Realtime + semantic VAD), Softcery/Pipecat+Attendee case study, and VideoSDK's TurnV2 turn-detection models — but the sources themselves (a LiveKit/AssemblyAI case study on Boardy) explicitly state one-on-one turn-taking is "largely solved" while multi-party turn-taking (deciding who's addressing the agent among several humans) remains the open, unsolved problem, with avatar/voice latency still 1-3+ seconds. Real but narrow/unevaluated implementations plus an admitted unsolved core sub-problem.

### P8: A unified multi-provider gateway for speech (TTS/STT) APIs, analogous to LLM routing gateways
- **What it is**: An API gateway that lets an application call one consistent interface for text-to-speech/speech-to-text and have it route to whichever backend (Azure AI Speech, Vertex/Gemini TTS, ElevenLabs, etc.) is configured, the same way LLM gateways (OpenRouter-style) abstract multiple model providers.
- **Evidence**: Two GitHub PRs from the engine run building exactly this: `maximhq/bifrost#9281` "docs: azure speech apis" — "documentation for using Bifrost as a drop-in replacement for an Azure AI Services resource... Azure AI Speech REST, Voice Live and Azure OpenAI on a single base URL"; and `txehq/bifrost#189` "TXE-6540: Vertex serves Gemini text-to-speech, buffered and streamed, through generateContent" — adding a second TTS channel so an existing gateway contract covers Vertex as well as the first provider.
- **Why it looks unbuilt/untested**: Both are in-progress PRs (docs and provider-coverage additions) to the same still-expanding gateway project — provider coverage for speech is being built out piecemeal, issue by issue, rather than existing as a mature, broadly-adopted standard the way LLM gateways already are.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch found this category is already well-served beyond Bifrost: Speko ("OpenRouter for Voice," YC S26, Launch HN'd, $0.09/min all-in router across STT/LLM/TTS), OpenRouter itself (now ships native unified TTS and STT endpoints across providers), Telnyx STT Router and TTS Router (Whisper, Deepgram, AssemblyAI, xAI, Speechmatics, ElevenLabs, etc. behind one API), VoiceRun's Realtime STT Router, and SLNG's Voice AI Gateway.
