## Candidate patterns

### P1: In-house eval framework reinvention because off-the-shelf tools don't fit the team's data model
- **What it is**: Teams repeatedly hand-roll a bespoke eval CLI/harness (test-runner + model-graded checks) instead of adopting an existing framework, because generic tools don't match their internal data model or workflow.
- **Evidence**: Mura engineering wrote an in-house eval framework called BOLT and reports that "most teams we spoke with had rolled their own" (per [mackey.substack.com](https://mackey.substack.com/p/bolt-how-mura-wrote-an-in-house-llm)). Corroborating complaint-shaped signal: an "Ask HN: What tools are you using for AI evals? Everything feels half-baked" thread (June 2025, ~4pts/2-4cmt across mirrors) where the poster says they tried OpenAI Evals, LangSmith, W&B, Humanloop, and Braintrust and found limitations in each.
- **Why it looks unbuilt/untested**: No framework has converged as the default; practitioner opinion is split between "build a thin layer" and "stop building your own" vendor posts, and the HN poster's half-baked framing after trying five named tools is the strongest complaint signal — a gap between what's sold and what teams can actually adopt without a rebuild.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search (`"LLM eval framework"`) surfaces a crowded field of frameworks (top result 66 stars, most 5-15, several zero-star/abandoned-looking), and the market also has well-resourced, maintained products (LangSmith, Braintrust, Humanloop, promptfoo, DeepEval, W&B Weave) — but none of these "squarely covers" the specific complaint (generic data model, needs a rebuild to fit), which is exactly the half-baked framing the HN poster used after trying five of them. Breadth of competing tools exists but the fit gap itself remains real and unaddressed by any single product, so PARTIAL rather than SATURATED or OPEN.

### P2: No standard tolerant-parsing layer for LLM-judge output across providers
- **What it is**: Every team hand-rolls its own parser to handle judge-output format drift — different providers return labels on different lines, reasoning models burn token budget on hidden thinking and return truncated/empty judge responses, and friendly prose wrapped around JSON breaks naive parsers.
- **Evidence**: A hackernoon engineering write-up on catching and fixing an "LLM scoring bug" reports recovering 39 of 88 failures only by re-parsing *saved raw outputs* with an improved parser, and names bare arrays, comma-separated object lists, and trailing remarks as the actual failure modes; a judge-format paper documents that the same model scores systematically differently when output format changes (1-5 vs. True/False) (arXiv, [judge circuits paper](https://arxiv.org/pdf/2605.16023)); MLflow's own judge utilities append "JSON-only" instructions and strip markdown fences as a workaround ([mlflow.org source](https://mlflow.org/docs/3.5.1/api_reference/_modules/mlflow/genai/judges/utils.html)).
- **Why it looks unbuilt/untested**: Every source describes an ad hoc, per-project fix (keep raw outputs, add stricter prompts, bigger token budgets) rather than a shared, reusable, provider-agnostic parsing/validation library; MLflow's fix is bundled inside one framework, not a standalone tool other stacks can adopt.
- **Maturity**: SATURATED
- **Verdict notes**: WebSearch surfaces multiple mature, widely-adopted, provider-agnostic libraries that do exactly this: Instructor (Pydantic-based, works across 15+ providers), LiteLLM (unified interface + structured output), LangChain's `with_structured_output` (native structured output or tool-calling fallback across OpenAI/Anthropic/Gemini), Outlines/XGrammar (constrained decoding for local/open models), and BAML (cross-language schema DSL); a Comet engineering post ("Structured Generation for LLM-as-a-Judge Evaluations") explicitly applies this tooling to the judge-output case. The gap as framed (no reusable, provider-agnostic tolerant-parsing layer) is closed by well-maintained, widely-used tooling, even though individual teams may not know to reach for it.

### P3: "Eval evidence" as an ad hoc PR convention, not a reusable CI gate
- **What it is**: At least one team (kodustech/kodus-ai) has built an internal convention where every PR touching review/judge logic must include an "Eval evidence" section linking a CI run and reporting before/after metric deltas (e.g., "funnel-verify 96.7% → 96.7%", "Opus 5.5 final F1: main 43.0 → branch 45.3").
- **Evidence**: Observed directly in kodustech/kodus-ai PRs #2376 and #2284 (GitHub, via last30days engine run, 2026-11-03/2026-10-28, each with CI Actions run links and explicit before/after scores in the PR body).
- **Why it looks unbuilt/untested**: This is a single repo's self-built convention, not a packaged, repo-agnostic CI gate/action that any team can drop in to require an eval diff on every prompt/model-touching PR — no generalized tool for this surfaced in search.
- **Maturity**: PARTIAL
- **Verdict notes**: `gh search repos "prompt regression CI"` and `"eval gate CI prompt"` surfaced several named attempts (HARDIK-WEB-OSS/evalci, muhammadwaqasmbd/prompt-regression-ci, ar1vit0r/prompt-regression-ci, gireeshvuyyuru501-design/prompt-regression-ci-framework) — all 0 stars, created within the last ~6 months, reading as individual demo/portfolio projects rather than adopted tools. No generalized, repo-agnostic GitHub Action or CI gate with real traction surfaced. Implementations exist but are narrow/unevaluated, matching PARTIAL.

### P4: No retroactive per-tenant cost reconstruction for multi-tenant LLM traces
- **What it is**: Multi-tenant SaaS teams need to attribute LLM spend to individual tenants/customers, but every practitioner guide agrees this only works if tenant IDs are tagged on every call at instrumentation time — there is no tool that can reconstruct or backfill tenant-level cost attribution from traces that weren't tagged that way originally.
- **Evidence**: A practitioner tutorial states flatly "you cannot retroactively split traces by tenant," framing tenant tagging as a hard requirement rather than an afterthought (cited via WebSearch across multiple dev.to/vendor cost-attribution guides, e.g. [dev.to/void_stitch](https://dev.to/void_stitch/how-finops-teams-trace-per-request-ai-costs-through-multi-tenant-gateways-3m6d), [particula.tech](https://particula.tech/blog/per-tenant-llm-cost-attribution-multi-tenant-saas)); another source notes a small fraction of users typically drives a large share of spend, making this a recurring FinOps pain point once discovered late.
- **Why it looks unbuilt/untested**: No tool addresses the "we didn't tag tenant_id until it was already a problem" case — every existing solution is forward-looking instrumentation advice, not a recovery/backfill approach (e.g. inferring tenant boundaries from request metadata, API keys, or timing after the fact).
- **Maturity**: OPEN
- **Verdict notes**: `gh search repos "per-tenant cost attribution"` / `"LLM FinOps multi-tenant"` and `"LLM cost attribution tenant"` returned only unrelated, mostly 0-star/1-star reference/portfolio repos describing forward-looking instrumentation (e.g. jeanmalaquias/ai-platform-reference, propel-bz/CostTracker), none addressing retroactive reconstruction. WebSearch across dev.to/FinOps practitioner guides confirms the consensus is explicitly that this can't be done without prior tagging — one practitioner's workaround is a collector transform that tags *future* unlabeled spans with a sentinel, not a true backfill of already-untagged historical traces. No credible implementation or product found after a genuine multi-channel search; this stays OPEN.

### P5: Agent tool/history/attachment-failure context not surfaced back to the model
- **What it is**: When a tool call, history retrieval, or attachment fetch fails inside an agent loop, the LLM is often never told — it keeps answering from a stale or wrong picture of the conversation instead of being handed an explicit failure signal it can reason about.
- **Evidence**: mattermost/mattermost-plugin-agents PR #1130, "Tell the model what happened when tools, history, or attachments fail" (2026-10-21, GitHub via last30days engine): "Fixes places where the LLM was not told what happened, so it answered from a wrong picture of the conversation."
- **Why it looks unbuilt/untested**: This is a one-off, codebase-specific patch in a single plugin, not a general pattern/library for surfacing agent-infrastructure failures into LLM context in a structured way that other agent frameworks could reuse.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found that LangGraph's prebuilt `ToolNode` already catches tool exceptions and reports them back to the model as a message so the agent can retry — a real, maintained framework feature covering the narrower "tool call failure" slice of this pattern. But it's inconsistent (a cited LangGraph GitHub issue reports this error handling became disabled by default after v1.0.1) and doesn't generalize to history-retrieval or attachment-fetch failures, which remain ad hoc per-project patches (mattermost's PR, CrewAI's documented pattern is just "wrap in try/except and return text"). Partial, narrow coverage rather than a solved general pattern.

### P6: Judge-score instability caused by the requested output format itself
- **What it is**: The same judge model produces systematically different scores depending on the output format it's asked to use (e.g., 1-5 Likert vs. True/False), meaning published eval/judge comparisons may partly be measuring a brittle formatting stage rather than the underlying judgment.
- **Evidence**: arXiv paper "Judge Circuits Explain Format-Induced Inconsistency in LLM-as-a-Judge" ([arxiv.org/pdf/2605.16023](https://arxiv.org/pdf/2605.16023)) — found via WebSearch, argues the judgment signal is mapped through a fragile, format-specific output stage.
- **Why it looks unbuilt/untested**: The paper diagnoses the problem; no tooling surfaced that automatically normalizes/calibrates judge scores across output-format choices so teams can compare judge configurations fairly.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch surfaced related research code — `github.com/penfever/bias-bounded-evaluation` (measures judge sensitivity to biases including format) and `github.com/UW-Madison-Lee-Lab/LLM-judge-reporting` (a plug-in accuracy-correction implementation) — plus practitioner posts (tianpan.co's bias-audit piece) recommending manual mitigations (format-neutrality rubric language, rewrite-in-three-formats bias tests). These are narrow, academic, unevaluated-in-production implementations rather than an adopted normalization tool, matching PARTIAL exactly.

### P7: Fragmented, vendor-siloed telemetry semantic conventions for eval scores
- **What it is**: Observability vendors are independently inventing their own metric names and schemas for attaching eval scores to traces (e.g., Datadog's `ml_obs.evaluation.count` / `ml_obs.evaluation.score`), in contrast to tracing itself, where OpenTelemetry/OpenLLMetry has become a converged standard (reinforced by ServiceNow's acquisition of Traceloop/OpenLLMetry).
- **Evidence**: DataDog/documentation PR #40934, "[LLM Obs] Document evaluation metrics (ml_obs.evaluation.count, ml_obs.evaluation.score)" (2026-10-22, GitHub via last30days engine); WebSearch corroboration that "several 2026 guides describe attaching eval scores directly to production traces as the common pattern" with "ServiceNow's March 2026 acquisition of Traceloop/OpenLLMetry... cited as a sign OpenTelemetry has become the standard base for LLM observability" — i.e., tracing converged, eval-score schemas did not.
- **Why it looks unbuilt/untested**: No cross-vendor semantic-convention standard (OTel GenAI SIG or otherwise) for eval-score attributes surfaced in search; each platform (Datadog, New Relic's new November 2026 AI Evaluation preview, Arize, Langfuse) defines its own eval-metric shape, meaning eval data doesn't portably travel between observability backends the way trace spans now do.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch found that the OpenTelemetry GenAI attributes registry actually does define `gen_ai.evaluation.name`, `gen_ai.evaluation.score.value`, `gen_ai.evaluation.score.label`, and `gen_ai.evaluation.explanation`, and a TrueFoundry write-up describes a proposed `gen_ai.evaluation.result` event — but the same source notes the GenAI conventions moved to a separate repo in June 2026 with no official release as of August 2026, and Dash0/Bedrock AgentCore docs show vendors already layering their own rules on top. A real, well-resourced standardization effort (OTel/CNCF) exists and is in progress but unstable/unreleased, so the gap is real but not OPEN — PARTIAL.

### P8: No reusable tool for the shadow-test → canary-rollout decision on LLM/prompt changes
- **What it is**: Multiple practitioner blog posts describe the same manual playbook for rolling out a new prompt or model version safely — run it in shadow mode against real traffic without serving its output, then canary a small traffic slice, then promote — but this is advice to implement yourself, not a packaged, LLM-aware tool (distinct from generic feature-flag/canary infra, because it needs prompt+model version pairing per logged event and judge-based shadow comparison, not just error-rate thresholds).
- **Evidence**: A single practitioner (tianpan.co) has written at least four separate posts walking through this exact playbook in 2026 (`llm-gradual-rollout-shadow-canary-ab-testing`, `canary-deploys-llm-model-upgrades`, `gradual-rollouts-fail-ai-features`, `staging-environment-lie-ai-systems`), each re-explaining why generic canary/A-B infra doesn't transfer cleanly to LLM changes; a vendor post (featbit.co) independently converges on the same three-stage "Offline Eval → Shadow Test → Canary Rollout" framing.
- **Why it looks unbuilt/untested**: Despite repeated, independent blog coverage of the exact same three-stage playbook, no implementation surfaced (open-source or product) that automates version-pairing, shadow-sample-rate selection, and judge-based promote/rollback decisioning specifically for LLM changes — every source is advice prose, not a tool.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search for shadow/canary LLM rollout tools returned no real implementations (`"shadow deployment LLM"` empty, `"canary LLM rollout"` empty, `"prompt canary rollout"` only a 0-star simulator repo). WebSearch found that LaunchDarkly AI Configs ships "Online Evaluations" (judge-scored Accuracy/Relevance/Toxicity judges feeding guarded rollouts/experiments) and Statsig has an "AI Evals" product (prompt/model versioning, online evals, automated grading) — real shipped features from well-resourced vendors covering judge-based rollout gating. But both are explicitly beta/early-access with conflicting availability claims across their own docs/blogs (Statsig no longer accepting new beta customers as of June 2026; LaunchDarkly's online evals described as both "closed beta" and "early access" in different pages), and no vendor documents a native shadow-mode feature specifically. Real but immature/narrow vendor coverage — PARTIAL, not SATURATED.
