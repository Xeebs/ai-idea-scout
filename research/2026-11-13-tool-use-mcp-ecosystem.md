## Candidate patterns

### P1: Tool-definition context bloat at scale
- **What it is**: As agents are wired to dozens of MCP servers, the JSON tool-schema definitions injected into the system prompt consume a large, growing slice of the context window before the agent does any work — independent of whether those tools get used.
- **Evidence**: WebSearch supplement cites a tracked pain-point roundup (DEV Community, "we tracked 29 MCP pain points across 7 communities") reporting Cloudflare's standard MCP server consumed 1.17M tokens in production; secondary sources cite a 50+ tool catalog costing ~72K tokens before any tool call, and tool definitions eating 25-30% of a 200k-token window, growing as more servers are added (jentic.com "the MCP tool trap"; hackernoon "AI agents pick the wrong tool more often as you add tools").
- **Why it looks unbuilt/untested**: The cited mitigation (Cloudflare's "Code Mode" workaround, loading tools on-demand rather than eagerly) is described as a one-off vendor patch, not a standardized or widely-adopted pattern across MCP clients — no general-purpose "lazy tool loading" layer was surfaced.
- **Maturity**: SATURATED
- **Verdict notes**: Already solved at the vendor/native level, not just by hobby patches: Anthropic shipped MCP Tool Search as a default-on Claude Code feature (Jan 2026), OpenAI ships an equivalent tool-search feature, and Cloudflare's Code Mode generalized beyond the one-off patch the digest cited. On top of that there are maintained gateway products with "MCP Code Mode" built in (maximhq/bifrost, arek-e/mcpx) and dedicated proxy packages (PyPI `mcp-lazy`, `lazy-mcp`) that do on-demand/lazy tool loading for any MCP client. The community gap is closing via well-resourced teams, not left to one vendor hack.

### P2: Tool-selection accuracy degradation as catalog size grows
- **What it is**: Agents with many available (especially overlapping) tools increasingly mis-select or ignore required tools; errors compound across multi-step runs because an early wrong pick cascades into retries.
- **Evidence**: WebSearch supplement surfaced hackernoon's "AI agents pick the wrong tool more often as you add tools and research shows why" and tianpan.co's "advanced tool use in production AI agents" (Jan 2026), both discussing benchmark gaps where isolated-tool tests overstate real multi-tool reliability; one source claims (unverified) that cutting 50 definitions down to 3-5 per request drops token use ~85%.
- **Why it looks unbuilt/untested**: Sources describe mitigations (on-demand tool discovery, sub-agent tool partitioning, RAG-style tool retrieval) only as recommendations/blog proposals, not as a shipped, broadly-adopted library or MCP-client feature.
- **Maturity**: SATURATED
- **Verdict notes**: The academic groundwork and shipped tooling both already exist: the RAG-MCP paper (arXiv:2505.03275) benchmarks exactly this problem, raising tool-selection accuracy from 13.62% to 43.13% and cutting prompt tokens >50%, and there are maintained open-source implementations of the idea (rocket-connect/mcp-rag indexing 90+ tools via graph-vector search; memoverflow/rag-mcp). Both Anthropic and OpenAI now ship native tool-search features in production specifically to address mis-selection at scale, so this is being closed by well-resourced teams, not left to blog proposals.

### P3: No cross-client MCP server lifecycle manager
- **What it is**: Each AI coding tool (Claude Code, Codex, etc.) keeps its own separate MCP server config/registration, so a developer running multiple agent clients has to install, enable, and update the same MCP servers redundantly per client.
- **Evidence**: Hacker News, "Show HN: One TUI to Manage MCP Servers for Claude Code and Codex" (toolshed.run), 2026-11-09, 7 points — a Show HN launch, meaning someone just started building this and it has not yet gained traction/validation.
- **Why it looks unbuilt/untested**: Low point count (7) for a Show HN launch signals this is a brand-new, unvalidated attempt at a problem that is apparently common enough to motivate the post but has no entrenched incumbent solution yet.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub search turns up a genuinely crowded field already attacking this exact niche — CC-Switch CLI and farion1231/cc-switch (Claude Code, Codex, OpenCode, Gemini CLI), heyitsjakub/KyttoMCP (Claude Desktop, Claude Code, Cursor, VS Code, Codex, with health checks and tool-safety scanning), and mcp-hub-tui — but every one of these checked via `gh api` is brand-new (created/pushed within days, 0 stargazers, 0 forks) with no evidence of adoption or long-term maintenance. The gap is real and actively being attempted by many small unvalidated projects simultaneously, which is squarely a PARTIAL (narrow/unevaluated implementations), not SATURATED (no maintained, widely-used incumbent) and not OPEN (multiple working attempts already exist).

### P5: MCP client trust / dynamic-registration phishing risk
- **What it is**: A blog post argues that letting end users "trust" their own MCP clients via OAuth dynamic client registration opens a phishing-style redirect vector — i.e., the newly-shipped enterprise OAuth 2.1 authorization layer for MCP has a trust-UX gap that attackers could exploit via malicious redirect URIs.
- **Evidence**: Hacker News, "Letting users trust their own MCP clients, without opening a phishing hole" (streamvessel.com/blog/mcp-trusted-redirect-uris), 2026-11-04, 35 points, 6 comments.
- **Why it looks unbuilt/untested**: The post is framed as raising/patching a specific gap in the brand-new (2026-07-28 spec revision) MCP authorization layer rather than citing an existing adopted fix — i.e., the enterprise auth layer itself is only months old and this trust-UX edge case is still being worked out in public, not solved.
- **Maturity**: PARTIAL
- **Verdict notes**: The problem is confirmed real and large at the implementation level — a May 2026 preprint (arXiv:2605.22333) tested 119 OAuth-enabled remote MCP servers and found dynamic-client-registration flaws in 96.6% of them — and the spec is actively mitigating it (DCR downgraded SHOULD→MAY in the 2025-11-25 revision; SEP-837/Client ID Metadata Documents added in 2026-07-28 as a DCR replacement; a documented CVE-2025-4143 for redirect_uri validation). But there is no shipped, broadly-adopted product or library that closes the client-side trust-UX gap itself — a live Cursor forum thread (v3.14.27) shows the exact flaw this pattern describes still unresolved in a major client. Spec evolution + unresolved client bugs = real, differentiated gap, not saturated.
