## Candidate patterns

### P1: Persistent agent memory as an adversarial attack surface ("memory poisoning")
- **What it is**: Injecting a dormant malicious payload into an agent's long-term/persistent memory store during one session so it activates and acts maliciously in a later, unrelated session — a two-phase (inject, then activate) threat distinct from ordinary single-turn prompt injection because it survives across sessions and users.
- **Evidence**: A July 2026 arXiv preprint ("GhostWriter", arXiv 2607.06595, authors Torres/Shrestha/Misra) reports ~98% injection success and 60% average activation across five memory-enabled agents spanning four model families. A University of Washington paper ("Bad Memory," arXiv 2607.14611) argues persistent memory changes the threat model for prompt injection. Radware's January 2026 "ZombieAgent" is a documented proof-of-concept showing ChatGPT's connector+memory features can be chained into cross-session persistent injection. OWASP added a dedicated category, ASI06 (Memory & Context Poisoning), to its Top 10 for Agentic Applications 2026.
- **Why it looks unbuilt/untested**: Practitioner defenses found are ad hoc (Forcepoint's write-up tags memory entries with a raw boolean field like `"confirmed_by_user": false` rather than any systematic provenance/trust-scoring layer). One source explicitly frames "the fundamental vulnerability of persistent memory to indirect prompt injection" as "an open research problem" — no maintained, general-purpose defense product or library surfaced in search.
- **Maturity**: SATURATED
- **Verdict notes**: `gh search`/WebSearch found OWASP's own official reference implementation, `OWASP/www-project-agent-memory-guard` (203 stars, created Feb 2026, pushed as recently as 2026-11-14 — actively maintained), a runtime layer with trust-scoring, quarantine, rollback and drop-in adapters for LangChain/OpenAI Agents/AutoGen/CrewAI/mem0 — exactly the systematic provenance/trust-scoring layer the digest's evidence said was missing. It has a real surrounding ecosystem (GitHub Action scanners, framework examples, a conda-forge feedstock). Separately, `Drakon-Systems-Ltd/ShieldCortex` is an actively published npm product (v5.20.0, modified 2026-11-12) doing per-write trust scoring and memory scanning for Claude Code/OpenClaw/Hermes. Two independently maintained, adopted implementations closing this exact gap outweighs the single stale practitioner anecdote the digest evidence leaned on.

### P3: Context compaction/trimming that ignores prompt-cache economics
- **What it is**: Techniques that reduce token count (summarizing, trimming, re-ordering context) to extend usage limits typically rewrite or shift the prompt prefix, which invalidates the model provider's prompt/KV cache — so a technique built to cut cost can increase effective cost and latency unless compaction is designed around cache-boundary placement specifically.
- **Evidence**: A January 2026 arXiv paper ("Don't Break the Cache," arXiv 2601.06007), run across 500+ agent sessions with 10K-token system prompts on OpenAI/Anthropic/Google, found prompt caching cuts API cost 41-80% and improves time-to-first-token 13-31%, but that "strategic cache boundary control outperforms naive full-context caching" and that full-context caching "can paradoxically increase latency." Separately, a Show HN post ("Thinker – Trim context and cache knowledge to extend agent usage limits," 2026-11-05, 4pts/2cmt) is explicitly pitched at this exact trimming-vs-caching tension. A practitioner slide deck frames summarization bluntly: "rewriting the prefix throws the cache away."
- **Why it looks unbuilt/untested**: The Thinker Show HN post drew only 4 points/2 comments and no documentation of its approach was discoverable — a one-off hack, not an evaluated tool. No general practice or library for "cache-boundary-aware compaction" (as opposed to pure token-count-aware compaction) surfaced.
- **Maturity**: SATURATED
- **Verdict notes**: The Thinker hack specifically is a one-off, but a broader, well-resourced field already covers cache-boundary-aware compaction: `headroomlabs-ai/headroom` is a massively adopted, actively maintained (pushed 2026-11-14) open-source project — 79,620 stars per `gh api` — whose default rolling-window strategy explicitly preserves the system prompt/cache prefix and removes tool call/response pairs atomically, with a real integration ecosystem (Zed extension, Swift package, AWS Strands Agents, Oh My Pi). Also found: `sqz-engine` (Rust crate that detects cache boundaries from Anthropic `cache_control` markers), `CosmoNaught/claude-code-cmv` (83 stars, reference implementation of cache-aware session trimming), and Hermes Agent's documented compressor that aligns boundaries to avoid splitting tool_call/tool_result groups. Multiple maintained, adopted implementations — this gap is closed.

- **Evidence**: Multiple 2026 vendor/practitioner posts (Atlan, tianpan.co, arkforge.tech, MintMCP) independently describe this gap; one explicitly calls "the conflict between GDPR deletion and AI Act record-keeping... the hardest architectural problem in agent memory in 2026." ### P6: Deterministic replay / time-travel debugging for non-deterministic context assembly
- **What it is**: Recording every source of non-determinism in an agent run — retrieval order, timestamps, tool outputs feeding into context assembly — so a run can be replayed step-by-step with deterministic stubs standing in for the recorded calls, specifically to debug *why* a given context window produced a bad outcome (not just to debug the model's output).
- **Evidence**: A practitioner piece (tianpan.co, 2026-04-12) states plainly that "setting temperature to zero does not make an agent reproducible," calling that a "myth," because context assembly itself is non-deterministic. A described record-and-replay approach intercepts and serializes external interactions (one arXiv submission, "agrepl," proposes a CLI doing this via an MITM proxy) and "fails loudly if the agent makes a call that was never recorded." A separate June 2026 arXiv paper on coding-agent memory (PROJECTMEM) estimates reconstructing project context can consume 5,000-20,000 tokens per session, underscoring why cheap replay (vs. re-running the full pipeline) matters.
- **Why it looks unbuilt/untested**: Sources describe this as early-stage — one checkpoint-based proposal flags that "checkpoint storage is costly" (megabytes per checkpoint) as an open problem, and the arXiv "agrepl" listing's own submission date is flagged by the search summary as needing verification. No mature, widely-adopted tool for context-assembly-specific deterministic replay (as distinct from general LLM-call replay/mocking) surfaced.
- **Maturity**: PARTIAL
- **Verdict notes**: WebSearch/GitHub turned up a crowded but immature field of small, young tools: `reeltime`, `agentrr` (PyPI, mock-LLM based record/replay), `Taiwrash/agrepl`, `sixty-north/langchain-replay`, `Victorchatter/AgentVCR`, `tstanmay13/agent-replay`, `forkline`, `litmus`, `rewind`, plus Microsoft's documented Azure "agent replay for production debugging" pattern. None of these specifically targets context-assembly-level non-determinism (retrieval order, timestamps feeding context) as distinct from general LLM-call/tool-call replay — they're general-purpose record/replay debuggers, several with no verified star counts or maintenance status checked. Real, multiple attempts exist but none evaluated or mature enough to call this closed — PARTIAL.
