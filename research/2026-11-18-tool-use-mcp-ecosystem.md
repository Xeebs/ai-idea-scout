Multiple independently maintained tools already close this gap.

### P6: Failure-injection test harnesses for tool-calling agents
- **What it is**: A deterministic stub placed in front of an agent's tools that injects timeouts, HTTP 429s, and malformed responses, to verify the agent degrades or recovers safely instead of only being tested on the happy path.
- **Evidence**: WebSearch result citing a practitioner write-up (kunalganglani.com, "How to Do Agent Tool Call Failure Testing [2026 CI Harness]") describing a hand-built harness of this kind for a multi-agent publishing pipeline; corroborated by the arXiv paper "Beyond Function Calling: Benchmarking Tool-Using Agents under Tool-Environment Unreliability" (arxiv.org/pdf/2606.25819) making the same "correct function calls are not sufficient" argument.
- **Why it looks unbuilt/untested**: The practitioner piece describes a one-off, self-built harness rather than a reusable/adopted tool; the arXiv paper is a benchmark proposal, not shipped infrastructure — no shared open-source implementation was surfaced.
- **Maturity**: PARTIAL
- **Verdict notes**: Found several fault-injection packages beyond the practitioner write-up — `deepankarm/agent-chaos` (35 stars, narrow adoption), `langchain-chaos-middleware`, `balagan-agent`, `agentfuzz`, and a chaos-testing module inside AWS's `strands-agents/evals` (260 stars, actively pushed) — but each is either low-adoption, narrow, or a sub-feature of a broader eval SDK rather than a dedicated, widely-adopted CI harness purpose-built for timeout/429/malformed-response injection. No implementation squarely and maturely closes the specific gap described.

### P7: Trajectory-level evaluation of tool-calling agents (vs. terminal-success-only)
- **What it is**: Evaluating agents on the full ordered sequence of tool calls, their arguments, and intermediate results — not just whether the final call "succeeded" — because terminal success can mask wrong actions or wrong arguments earlier in the chain.
- **Evidence**: WebSearch result citing getautonoma.com ("an agent can pass these checks and still be wrong about the app's actual state") and aident.ai's analysis of 4,187 production tool calls (78.3% terminal success rate), which argues execution success doesn't confirm the agent chose the right action/arguments.
- **Why it looks unbuilt/untested**: Both sources are vendor blog posts describing their own in-house approach; no shared, open-source trajectory-evaluation framework was cited — each vendor appears to have built its own version of this independently.
- **Maturity**: SATURATED
- **Verdict notes**: LangChain's `agentevals` (760 stars, actively maintained, from a well-resourced company) directly implements trajectory-level evaluation with strict/subset/superset tool-call matching and LLM-as-judge scoring; Comet's Opik ships built-in trajectory evaluators too, and LangSmith documents the same pattern. This is a maintained, adopted, shared open-source framework from a well-resourced team — not each vendor reinventing it in isolation as the digest's evidence implied.
