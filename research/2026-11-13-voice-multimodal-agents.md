### P1: Filler/holding-audio to mask tool-call latency in voice agents
- **What it is**: Playing a short "thinking" sound or holding phrase while a voice agent's tool call is in flight, so the dead-air silence (which callers read as the agent being broken) disappears even though the underlying latency hasn't changed.
- **Evidence**: Hugging Face's "Voice Agent Latency Playbook" (practitioner blog, surfaced via WebSearch) frames this as a standard workaround; Soniox's voice-agent-tool-calling wiki and a Speechify post both independently describe tool-call silence as a production pain point. A Netguru article notes "why is my bot slow when the model is fast" is a recurring complaint echoed on Reddit voice-AI threads (secondhand mention, no direct thread link retrievable).
- **Why it looks unbuilt/untested**: Every source describes this as a bespoke technique engineers wire up themselves per-project (what sound, when to trigger it, how to sequence it with barge-in) rather than a reusable, provider-agnostic primitive or SDK feature.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub has `AgoraIO-Conversational-AI/recipe-agent-filler-words` (1 star, last pushed 2026-09-19 — a vendor recipe, not a standalone reusable library) and `livekit/agents`' `examples/voice_agents/fast-preresponse.py` (a single example, not timeout-driven per community reports). Deepgram and getstream.io each describe their own bespoke "filler as a tool-call" or "speculative tool calling" pattern in docs/blog form only, and AWS Builder describes a hand-rolled S3-cached-clip approach. No provider-agnostic SDK primitive or standalone package was found across GitHub/web search — only scattered vendor-specific recipes and blog patterns.

### P2: Mid-tool-call interruption/barge-in orchestration
- **What it is**: Handling the case where a caller interrupts the voice agent while a backend tool call is still executing — deciding whether to cancel, let it finish silently, or restart — and stopping TTS output fast enough that the interruption doesn't feel ignored.
- **Evidence**: Soniox's wiki states explicitly that "the orchestrator has to handle an interruption that arrives while a tool call is still in flight." FutureAGI's barge-in/turn-taking guide puts a hard number on it: TTS audio must stop within 60ms of barge-in or the agent reads as unresponsive. A Quiq blog is titled "why the interruption problem is architecture" — i.e., not a solved library feature.
- **Why it looks unbuilt/untested**: Multiple independent vendor blogs are each re-explaining this problem from scratch in 2026, which is the pattern of a shared gap rather than a shared solution — no single orchestration layer is cited as the default answer.
- **Maturity**: PARTIAL
- **Verdict notes**: GitHub has a dedicated `rogerchappel/bargekit` ("local-first VAD, barge-in, and turn-taking primitives," created 2026-09-17) plus narrower repos like `rmsdev0/telnyx-onset` (barge-in latency benchmark harness) and `Suman1108-beep/livekit-barge-in-agent`. Framework docs (Pydantic AI realtime, Smallest.ai, NVIDIA's voice-agent blueprint) all cover general barge-in/TTS-stop, but explicitly disagree or stay silent on what happens to an in-flight tool call specifically — Smallest.ai lets it finish, one SDK's docs say cancel-and-discard, NVIDIA's blueprint doesn't address tool calls at all. No single implementation resolves the mid-tool-call decision the pattern describes; real gap remains despite several turn-taking libraries existing.

### P3: Screen-state loss and precision-task routing in voice+vision agents
- **What it is**: In multimodal agents that pair voice with live screen/vision understanding, the model loses track of on-screen state during a session, and small on-screen text or precision details get missed by the general multimodal model.
- **Evidence**: A production write-up (alexcloudstar.com, 2026 multimodal-agents-in-production post, surfaced via WebSearch) calls screen-state loss "the most common preventable failure mode" in its evaluation set, and notes p99 time-to-first-audio rises once image/screen steps are added. getstream.io's multimodal-agent-architecture guide independently recommends routing precision tasks (e.g., small on-screen text) to a dedicated CV model instead of relying on the general multimodal model.
- **Why it looks unbuilt/untested**: The routing decision ("send this sub-task to a specialized CV model vs. the multimodal model") is described as manual, case-by-case advice in blog posts, not an available middleware/router component.
- **Maturity**: PARTIAL
- **Verdict notes**: Academic work exists on each half separately — screen/toggle-state tracking (`ZrW00/StaR`, with code+benchmark) and difficulty-based VLM routing ("Adaptive Vision-Language Model Routing for Computer Use Agents," arXiv 2603.12823, pointing to `vllm-project/semantic-router`) — plus a BLIP-based GUI agent (`neerajanand321/AFRAgent`). None combines screen-state persistence with precision-task routing to a dedicated CV model as a single reusable middleware/router component; getstream.io's and alexcloudstar.com's recommendation to route precision tasks to a specialized CV model remains manual blog advice, not packaged tooling.

### P5: Session-length degradation of video/screen understanding (~30s window)
- **What it is**: Continuous video or screen-share understanding in a multimodal agent session degrades noticeably after roughly 30 seconds of continuous streaming, per one practitioner's testing.
- **Evidence**: alexcloudstar.com's write-up states video understanding "gets weaker in longer continuous sessions, especially after roughly 30 seconds."
- **Why it looks unbuilt/untested**: Described purely as an observed limitation with no mitigation pattern (e.g., periodic re-grounding/re-sampling of visual context) named or cited as existing tooling.
- **Maturity**: PARTIAL
- **Verdict notes**: Active 2026 research directly targets this failure mode — ViSAGE (arXiv 2607.28678, entity-anchoring against degradation, reports 79.1% vs 74.2%/61.8% baselines on Video-MME-long), LensWalk (adaptive re-sampling across a multi-round loop), VideoBrain and VideoExplorer (adaptive/query-driven re-sampling), APVR (training-free hierarchical retrieval). These are papers/research code, not production middleware wired into a live voice+vision agent session — no tooling cited that applies periodic re-grounding specifically inside a real-time 30-second-window agent loop, so the applied-engineering gap the community describes is still real.
