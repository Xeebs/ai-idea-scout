### P3: Deliberate periodic reset with state-handoff memo, replacing compaction, to fight "context inertia"
- **What it is**: Drew Breunig's "The State of Context Engineering" names a failure mode — "context inertia" — where long-running agents plateau or fixate on dead-end hypotheses even with huge context windows; the proposed fix is a periodic deliberate reset that hands off state via an explicit memo, instead of the agent silently compacting its own history.
- **Evidence**: Hacker News front-page thread (275 points, 67 comments, 2026-10-25, https://www.dbreunig.com/2026/10/24/the-state-of-context-engineering.html), pulled by the last30days engine and cross-checked via WebSearch (query "dbreunig.com 'The State of Context Engineering' 2026"), which notes the piece was trending on HN and frames prompt engineering (2023) → context engineering (2025) → harness engineering (2026) as one continuous line of work.
- **Why it looks unbuilt/untested**: The essay names the failure mode and sketches the fix as a principle; no shipped harness-level feature (reusable "reset + handoff memo" primitive) was cited anywhere in the thread or coverage — every mention is conceptual.
- **Maturity**: PARTIAL
- **Verdict notes**: Narrow tools exist but nothing consolidated or "context inertia"-branded specifically: `simen/mcp-memento` ("Context Travel MCP" — checkpoint/reset tools for Claude agents, MIT-licensed, scale/traction unconfirmed), `ctxio` (PyPI CLI with a token-capped handoff snapshot file), `marcj/handover` (status-line nudge for when a handover is due). Two open Claude Code feature-request issues (self-checkpoint-and-reset, self-managed context degradation) confirm it's still requested, not shipped as a harness primitive. The term "context inertia" itself appears in only one source outside the digest's own HN thread — conceptual, not built.

### P5: Cross-tool context silos (the same project means separate, un-shared context in Claude Code vs. Cursor vs. other agents)
- **What it is**: A project's context built up inside one coding agent (e.g., Claude Code) doesn't carry over to another tool used on the same codebase (e.g., Cursor), so builders are manually re-deriving or duplicating context across tools.
- **Evidence**: Cursor community forum thread "How are people handling context across different AI coding tools?" - **Why it looks unbuilt/untested**: The cited fixes are DIY folder conventions (e.g., `/context/global`, `/context/clients`, `/context/projects` loaded selectively) built by individual practitioners, not a tool or protocol that makes context portable across different vendors' agent harnesses.

- **Why it looks unbuilt/untested**: The summary frames this as an internal practice/approach at one lab, not a released, reusable mechanism other teams can adopt; the cross-agent visibility gap it names is described as a current limitation, not something resolved.
- **Maturity**: SATURATED
- **Verdict notes**: Follow-up search found this is further along than the digest's framing suggests. - **What it is**: Multiple practitioners report that simply enlarging an agent's context window (e.g., 200k → 1M tokens) made outputs worse, not better — yet the instinct to solve memory problems by adding window size rather than adopting retrieval/eviction architecture persists.

- **Why it looks unbuilt/untested**: The gap between stated belief ("memory matters") and actual implementation (4%) plus the recurring "bigger context made it dumber" anecdote suggests the standard retrieval-vs-raw-context tradeoff still isn't packaged into an easy default architecture builders reach for instead of just cranking window size.

- **Verdict notes**: The specific claim that this isn't "packaged into an easy default architecture" doesn't hold up: `mem0ai/mem0` is a maintained, actively-pushed (last push 2026-11-18, the day before this digest) drop-in memory/retrieval layer with 69,228 GitHub stars, explicitly marketed as a context-manager alternative to stuffing the window (vendor benchmark: <7K tokens/call vs 25K+ for full-context). The community pattern described is an adoption/behavior gap (builders not reaching for existing mature tools), not a missing product — the well-resourced-team bar is clearly met.
