# Evidence Hold: A Tool-Call Evidence Retention Layer for Context Compaction

Ask any developer running a long coding-agent session what happens when the context window finally fills up, and they'll tell you compaction quietly rewrites history — the model's own tool outputs get boiled down into prose, and whatever didn't survive the boiling is just gone. The agent doesn't know it lost anything. It just starts guessing, confidently, about what a diff three steps ago actually said.

## The Gap

In the last 30 days, two unrelated teams ran into this same wall from two different directions and shipped two different patches. `onyx-dot-app/onyx` opened a PR titled "fix(chat): retain tool evidence until context compaction." Separately, `AstralBeamAI/astralbeam` shipped a default-on compaction middleware built on TanStack AI — compacting every agent session automatically, no opt-in required. Neither team seems aware of the other. Neither PR shares an abstraction with the other. They're independently patching adjacent slices of the exact same problem: naive compaction summarization flattens tool outputs — file diffs, command stdout/stderr, search hits — into lossy prose, discarding the one thing later reasoning actually depends on.

A broader search for anything resembling a dedicated fix came back nearly empty. `gh search repos` for "tool call evidence summarization," "lossless context compaction agent," and "structured memory compaction tool output" all returned zero results — there's no shared library anyone can point to. The closest thing to a real answer is TrueFoundry's open-source TrueForge harness, which does architect around keeping a persisted session event log (including tool calls) separate from the lossy compacted context the model actually sees. That's a real, shipped product proving the underlying architecture already works — but it's a general-purpose harness feature, not a benchmarked, dedicated tool built to solve evidence fidelity specifically. One practitioner-grade harness plus two narrow, unreviewed PRs is thin coverage — real enough to be a genuine gap, not thin enough to call it solved.

## The Project

The fix is almost embarrassingly mechanical once you see it: before a compaction summarization pass runs, intercept every tool-call result and write it, verbatim, to a local content-addressed evidence store keyed by a short reference ID. Then instruct the compaction summary to *cite* evidence by ID — "see diff `#a3f1`" — instead of paraphrasing its contents inline. A lightweight resolver tool lets the agent re-fetch the real artifact by ID whenever it actually needs the exact content, so later reasoning checks the genuine diff or command output instead of trusting a summary's lossy retelling of it.

It's deliberately narrow. This is not task-state continuity (that's a sibling idea, Task Anchor's territory) and it's not trust/authority tagging against injected instructions (that's Provenance Seal's). It's just fidelity: did the thing the compaction summary claims actually say what it claims. The components are correspondingly small — a tool-call interceptor writing to a hash-keyed store (diffs, stdout/stderr, search-hit payloads), a compaction-prompt modifier that nudges the summarizer toward citation instead of paraphrase, an evidence resolver the agent can call post-compaction, and a confabulation-probe eval harness that plants a factual-recall question about an earlier tool output and checks whether the agent's answer actually matches the stored artifact.

## Tangible Impact

**Population**: Developers running long-horizon coding agents (Claude Code, Codex, Cursor) on real repositories across sessions that cross one or more automatic compaction boundaries — the same long-running-agent cohort evidenced in this digest's compaction bug reports, narrowed further to the subset whose downstream correctness depends on the exact content of a prior tool output (what a failing test's stack trace actually said, what lines a diff three steps ago actually changed), not just whether an approach was already tried.
**Mechanism**: Today, naive compaction paraphrases tool outputs into lossy prose, so when the agent later needs to reason about the literal content of a diff or command result, it either confabulates a plausible-sounding but wrong detail or burns time/cost re-running the tool just to recover information it already had once. A verbatim, ID-referenceable evidence store means the agent's later reasoning can cite or re-fetch the real artifact instead of operating on a paraphrase it has no way to verify.
**Measure**: (1) Confabulation rate — agent claims about a prior tool output that don't match the stored artifact — on a benchmark of long sessions with forced compaction plus a planted factual-recall probe, with vs. without the evidence store. (2) Rate of redundant tool re-execution purely to recover already-obtained information. (3) Evidence-store token/storage overhead as a percentage of total context budget, to confirm the fix doesn't just relocate the bloat it's meant to prevent.

## Try It

There's already a companion skill: [`skills/compaction-tool-evidence-retention/`](../skills/compaction-tool-evidence-retention/). Per its `SKILL.md`, it's a "one-shot forensic audit of an already-compacted agent session — finds claims in the compacted summary that depend on a tool output's exact content (a line number, error string, diff hunk, test result, specific value) but only survived as a paraphrase, then reconstructs a corrected context block reattaching the verbatim evidence."

This is the review half of the idea, not the always-on infrastructure half — it doesn't hook into a live compaction pipeline, it audits a session you already have in hand. Use it either way: paste its `README.md` into any AI chat tool along with your compacted summary and the original tool outputs it was derived from, or drop the `skills/compaction-tool-evidence-retention/` folder into `~/.claude/skills/` if you're running Claude Code and want it available on demand. It's meant for the moment an agent just gave you an answer about an earlier diff or test failure and you're not sure it's actually right — not for wiring the evidence store into a live pipeline, which is a separate infrastructure build.
