# Escalation Ledger: An Auditable, Severity-Conditional Crisis-Escalation Policy Engine for Voice AI Agents

Somewhere right now, a voice AI agent is talking to someone in crisis, and the rule that decides whether it reads a hotline number or stays on the line through a warm transfer to a human is sitting inside a feature flag that only an engineer can change. That's not a hypothetical — it's a real, merged pull request from a real voice AI vendor. The rule works. It's also the only rule like it, hardcoded, un-auditable from the outside, and one-off.

## The Gap

The evidence for this gap is uncomfortably concrete: a GitHub pull request, `ferni-ai/voiceai#3748`, titled "feat(crisis): conditional 911 line after 988 in the severe script," ships exactly one narrow, internal, feature-flagged rule — `CRISIS_SELF_HARM_911_LINE` — that appends an extra escalation line to a severe self-harm/suicide script, gated on imminence, language, and topic detection. It's a single production vendor's internal rollout of a single escalation rule, written the way most safety-critical logic quietly ends up written in production: as application code behind a flag, not as a declared, reviewable policy.

That wouldn't be interesting if it were an outlier, but the research digest found no general pattern or library for composable, auditable crisis-escalation policy logic — the kind of thing you'd want for a decision this consequential: severity threshold, then disclosure script, then feature flag, then gradual rollout. A targeted GitHub search for "crisis escalation voice AI agent," "suicide risk detection conversational agent," and "988 911 escalation chatbot" returned zero repos. A broader web search turned up only narrow, vendor-specific, or outright proprietary pieces: a commercial wellness/EAP vendor's proprietary "988 Warm-Handoff Safety Matrix," a community Claude-skill crisis-response-protocol document, an NYU policy-proposal framework, and VERA-MH, which is a genuinely open evaluation rubric but not an escalation *engine* — it tells you how to score a response, not how to decide and log one. So this isn't a blank slate; it's a space with scattered proprietary and academic fragments and no shared, reusable, auditable core.

## The Project

The idea is a policy engine that sits between a voice AI agent's risk-detection layer (the imminence/language/topic classifiers, which are already mature off-the-shelf) and its response generator. Instead of a team hardcoding "if severe and self-harm and English, append this line" into application code, they declare escalation rules as data: severity threshold, language, topic, script variant, rollout percentage. Every decision the engine makes gets logged with the inputs that triggered it — classified severity, language, topic, which rule fired, which exact script variant was spoken — so a clinical or incident reviewer can reconstruct, after the fact, exactly what the agent decided and why.

It ships with a default rule set modeled on the public 988/911 warm-handoff pattern, which teams then override per jurisdiction or language — a config change instead of a new feature-flagged PR every time a new escalation condition shows up (a new language, a new region's crisis-line number, a different imminence threshold). The novel pattern here isn't the risk classifier — that part is already commodity. It's the policy-and-audit layer wrapped around it, which right now gets re-derived, invisibly, inside each vendor's own codebase.

## Tangible Impact

**Population**: callers in active mental-health crisis reaching an AI-voice-staffed line. The 988 Suicide & Crisis Lifeline alone received an estimated 7.4 million contacts in FY2025 per a GAO report (23% up from FY2024, roughly 600k-700k contacts/month per KFF's tracking) — a growing volume that crisis organizations and commercial wellness/EAP vendors (like the one evidenced in this digest) are increasingly handling with voice-AI triage and response layers rather than purely human staff.

**Mechanism**: today each vendor hand-codes each escalation rule as application logic behind a feature flag (as in the evidenced PR), meaning a new at-risk condition (a new language, a new jurisdiction's crisis-line number, a new imminence threshold) requires an engineering PR and redeploy before it reaches callers, with no standard audit trail proving which rule fired for a given call if an outcome is later reviewed. A declarative, logged policy engine lets a clinical safety team change escalation rules without an engineering cycle and gives incident reviewers a complete record of what the agent decided and why.

**Measure**: time from "clinical team identifies a new escalation condition is needed" to "it's live for callers" (target: hours via config change, not a PR-and-deploy cycle); percentage of escalations with a complete, reviewable audit trail (target: 100%, vs. ad hoc logging today); false-negative rate on a labeled set of simulated crisis-severity scenarios (did the correct escalation fire).

This is, by its own admission, the highest-stakes idea to come out of this research cycle, and the risks are worth stating as plainly as the upside. A bug in a policy engine like this could mean a real at-risk caller doesn't get escalated — which means any MVP plan needs clinical/safety-expert review built in from the start, not bolted on afterward. The one production example found, `ferni-ai/voiceai`, is proprietary, so without access to real crisis-call data the test set has to be synthetic, which puts a ceiling on how confidently any false-negative rate generalizes to real calls. And the commercial vendor's own proprietary "988 Warm-Handoff Safety Matrix" is a signal that at least one company has already solved a version of this in-house — meaning this project only earns its keep if it's meaningfully more composable, auditable, and open than what that vendor already built quietly for itself. Regulatory and liability exposure — this is suicide-prevention response logic — likely needs legal review independent of and before any technical build.

## Try It

A companion Claude Code skill exists for the lower-stakes, design-side half of this idea: `skills/voice-ai-crisis-escalation-policy-engine/`. Its one-line description, straight from `SKILL.md`:

> Audits a voice/chat AI team's existing crisis-escalation logic (script, flag-config, or policy description) against a 10-point safety checklist before launch or after an incident, flagging missing imminence thresholds, language gaps, and audit-logging holes. Use when a team has crisis-adjacent escalation logic already written and wants a structured gap check before shipping a change or reviewing an incident — not for live crisis detection.

This is explicitly a documentation/design audit, not a live safety system — it doesn't watch real calls and doesn't replace clinical or legal sign-off. To use it: paste the skill's `README.md` into any AI chat tool (ChatGPT, Claude, etc.) along with your own crisis-escalation script, flag config, or policy description, and it'll walk the 10-item checklist against what you pasted. For Claude Code, drop the whole `skills/voice-ai-crisis-escalation-policy-engine/` folder into `~/.claude/skills/` and invoke it the same way.
