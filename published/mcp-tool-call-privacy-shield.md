# Shade: An In-Flight Privacy Shield for MCP Tool Calls

MCP has made it trivially easy to wire an agent up to a third-party tool — and just as easy to forget that every tool call is a trust boundary. Conversation history that gets stuffed into a "context" argument, a secret that gets echoed back in a result, a customer's SSN riding along in a CRM lookup: none of it gets inspected on the way out or the way back in. It just crosses the wire, lands in someone else's logs, and flows back into the model's context unexamined. As the MCP server registry climbs past 20,000–30,000 listed servers and regulated industries start adopting the protocol in earnest, that's not a theoretical risk — it's a leak surface that's been quietly growing with every new integration, and almost nobody is watching it.

## The Gap

The clearest signal here is how little signal there is. A single Hacker News post — "In-memory privacy shield to prevent context leaks in MCP tools," pointing at `github.com/rohan-protocol/sdk` (2026-10-20, 10 points, 1 comment) — is the only attempt anyone has made at this, and it's early-stage, low-traction, and not integrated as a default in any mainstream MCP client. A four-way GitHub search ("MCP guardrail context," "MCP data leak guard," "MCP PII redaction proxy," "LLM tool call data leak prevention") turned up nothing else. No dedicated product, no paper, no second entrant.

That absence isn't a fluke of one search pass — it recurred independently a cycle later. A separate research run on context engineering and memory surfaced the exact same `rohan-protocol/sdk` post again as its own finding, and this time the verdict search found a little more texture around it: a single-maintainer OSS project called `mcp-pvp` that tokenizes PII and resolves it at tool-call time, plus general DLP-vendor guidance (Strac.io, SecureAuth) on PII filtering for AI traffic. It also turned up a batch of Gravitee "MCP PII Filtering" pages that read like programmatic SEO content rather than a real shipped feature — URLs sitting next to unrelated slugs about "sieges of Gassantoda Castle" — and got discounted rather than counted as evidence. Strip those out and what's left is: one early SDK, one more single-maintainer tokenizer project, and a lot of general-purpose advice. Nothing evaluated, nothing adopted, nothing that specifically targets in-session, cross-tool-call leakage as opposed to generic pre-LLM redaction.

A companion idea — auditing an MCP server's tool manifest for leak risk *before* connecting to it — turns out to be a crowded space already: OWASP's Secure Agent Playbook, Invariant Labs' `mcp-scan`, and at least five other pre-connection scanners exist. But that's a different problem. Scanning a manifest tells you what a tool *could* do; it says nothing about what actually crossed the wire on a given call. That in-flight question — redacting or blocking content as it moves, in real time, through a live tool call — is the one nobody has shipped.

## The Project

The shield is a transparent interceptor — SDK middleware, or a local sidecar proxy — sitting between the agent runtime and every outbound and inbound MCP tool call. It inspects call arguments on the way out and results on the way back in, looking for the shapes sensitive data actually takes in practice: a secret echoed back verbatim in a tool result, a free-text "context" field that got the whole conversation history stuffed into it, a PII value crossing into a third-party server's logs. When it finds one, it redacts or blocks before the call leaves the local process, or before the result re-enters the model's context — never after.

Policy is the part that makes this usable rather than a blunt kill switch: configurable per-field and per-server, not one global on/off toggle. A team can decide that a specific argument on a specific tool is always allowed through unredacted (because it's genuinely needed and genuinely safe) while locking down everything else by default. That granularity is what separates a shield a team can actually ship from one they'll disable the first time it breaks something.

## Tangible Impact

**Population**: Teams deploying agents with third-party MCP tool integrations inside regulated or sensitive environments — e.g. healthcare software teams wiring agents to EHR-adjacent MCP tools, fintech support teams wiring agents to ticketing/CRM MCP tools — where a leaked SSN, account number, or API key in a tool call is a reportable incident. This is a growing subset of the thousands of orgs drawing from the registry's 20,000–30,000 listed MCP servers as adoption climbs in regulated industries.
**Mechanism**: Today nothing inspects what actually crosses the MCP wire; sensitive values that slip into a tool argument or get echoed back in a result travel through third-party server logs and back into model context unexamined. The shield intercepts both directions against configurable PII/secret patterns and redacts or blocks before the leak completes, shrinking the leak surface from "every tool call, unexamined" to "only what policy explicitly allows through."
**Measure**: % of planted-secret test calls caught and redacted on a red-team harness; added latency per tool call; count of real incidents/near-misses logged post-deployment vs. a pre-deployment baseline period.

## Try It

There's no companion skill for this one, and that's a deliberate downgrade, not an oversight. A skill angle was explored — "audit this server for leak risk before I connect it," reviewing a server's manifest for fields that could carry sensitive context and seeding the runtime policy from that review — but the skill-synthesizer's own search found six or more close public equivalents already doing pre-connection manifest auditing (OWASP's Secure Agent Playbook, Invariant Labs' `mcp-scan`, PolicyLayer's `mcp-precheck`, and others). That space is occupied. The runtime, in-flight shield this writeup is actually about remains untouched by any of those tools — but it's a project to build, not a prompt to paste, so there's nothing here to drop into `~/.claude/skills/` yet.

Two caveats worth sitting with before anyone builds this. First, detection here is inherently heuristic and pattern-based — regex plus lightweight NER will catch planted secrets in a red-team harness and will still miss novel leak shapes nobody thought to test for. Second, and more structurally: a well-resourced MCP client vendor could ship this as a built-in feature at any point, which would obsolete a standalone project fast. The gap is real today, but it's the kind of gap a platform owner is well-positioned to close unilaterally the moment they notice it.
