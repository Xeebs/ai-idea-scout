# Red Team the Agent: A Pre-Deployment, Action-Level Attack Simulation Harness for Autonomous Agents

An autonomous agent doesn't fail the way a chatbot fails. A chatbot that gets manipulated says something bad. An agent that gets manipulated *does* something bad — moves money, books a flight, changes an account, collects a debt — and by the time anyone notices, the action already happened. That distinction is why "we red-teamed the prompts" is quietly becoming an unsafe sentence for teams shipping agents with real-world transactional authority, and why the tooling built for the first kind of failure doesn't cover the second.

## The Gap

The evidence for this isn't theoretical. A live exploit write-up — "The AI Repo Man: Exploiting Agentic AI Debt Collection Platforms" — landed inside the last 30 days documenting an attacker manipulating an autonomous agent's real-world transactional actions in production, after the fact, in a debt-collection platform. Around the same window, two early, low-engagement tooling launches (Intrusive.ai's open-source attack simulator, a Zero-Trust-for-agentic-AI analysis) show the community reaching for a fix, but both are one-off and unevaluated. Meanwhile the mature end of red-teaming — Microsoft's PyRIT, NVIDIA's Garak, Promptfoo's red-team mode — is explicitly called out by a Cloud Security Alliance piece evaluating PyRIT for agentic use as *not* covering agent-specific architecture risk: tool-use exploitation, memory poisoning, credential misuse, chained real-world actions. The gap sits precisely between "we red-team the model's text output" and "we red-team what the agent actually does when it acts" — and United Airlines' decision to simply ban agent-initiated bookings outright, rather than trust any accountability layer, is a pretty blunt signal of how unresolved that gap currently feels to the people who'd otherwise be shipping this.

## The Project

The core idea is a simulation harness that stands up a sandboxed clone of a team's actual autonomous agent — same tool definitions, same memory and credential-scoping configuration — pointed at disposable test resources instead of production ones. Then it drives that clone through a library of agent-specific adversarial scenarios: a poisoned memory entry engineered to bias a later decision, a tool-chaining sequence that escalates privilege across two individually-safe tool calls, a credential-scope probe testing whether the agent can be tricked into using a broader grant than the task needs, and a scripted replay of the real AI Repo Man exploit pattern adapted to the team's own domain.

The thing that makes this different from prompt-level red-teaming isn't the scenario list — it's the evaluation method. Every scenario is judged by its actual effect on the sandbox's state (did the unauthorized action actually execute?), not by an LLM judge scoring a transcript. The centerpiece is testing what the agent *does*, not what it *says*. Concretely, that breaks into four pieces: a sandbox provisioner that clones a team's tool/credential configuration against disposable test resources; a scenario library covering memory poisoning, tool-chaining privilege escalation, and credential-scope misuse; an outcome-verification layer that checks the sandbox's actual post-scenario state directly; and a pre-deployment report flagging which scenarios succeeded against the agent as configured.

## Tangible Impact

**Population**: Engineering and security teams at startups and mid-size companies shipping autonomous agents with real-world transactional authority — payments, bookings, account changes, debt collection — the same category of company implicated by both the live AI Repo Man debt-collection exploit and United Airlines' decision to ban agent-initiated bookings outright rather than trust any accountability layer. As agent-payment protocols (Google's AP2, Visa's Trusted Agent Protocol, Mastercard Agent Pay) roll out through 2026, the population of companies authorizing agents to transact in the real world is growing fast from a small base — plausibly thousands of engineering teams within the next year.

**Mechanism**: Today a team ships an autonomous agent with real-world action authority, red-teams its prompts with PyRIT or Garak if anything, and discovers architecture-specific exploits (memory poisoning, chained privilege escalation, credential misuse) only after an incident like the AI Repo Man case — or avoids the risk entirely by banning agent access outright, as United did. A pre-deployment harness that actually executes agent-specific attack scenarios against a sandboxed clone surfaces those exploits before launch, turning "we hope our agent's actions are safe" into a measured, pre-deployment pass/fail report a team can act on before anything real is at stake.

**Measure**: (1) Number of agent-specific scenarios — memory poisoning, tool-chaining escalation, credential misuse — that succeed against a team's sandboxed agent pre-launch, versus the number of comparable incidents that previously surfaced only in production. (2) Time from a new exploit class being publicly disclosed (like the AI Repo Man pattern) to that scenario being added to the harness's library and re-run against existing deployments. (3) Reduction in post-launch security incidents tied to agent action/tool misuse, measured on pilot teams before vs. after adoption.

## Worth Weighing Before You Build

This idea's own risk list is worth repeating here, not softening. A faithful sandboxed clone of a team's real tool/credential configuration is itself nontrivial to build — if the sandbox diverges from production in its auth flow or stubbed side effects, a "pass" in the harness may not transfer to real safety. It's also plausible that PyRIT, Garak, or a security vendor extends existing prompt-level tooling to cover agent-action scenarios directly, which would narrow this project's differentiation down to the sandbox-provisioning and outcome-verification layers rather than the scenario library itself. And the evidence base, while concrete, is thin on the demand side: the two tooling launches cited above (Intrusive.ai, the Zero-Trust analysis) are each low-engagement posts — the stronger half of the case is the live exploit and the coverage-gap analysis, not loud community demand for a tool yet. A few practitioner interviews should precede any heavy build.
