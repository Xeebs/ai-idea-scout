# Hold Line: A Provider-Agnostic Filler-Audio Sequencing Layer for Voice Agent Tool-Call Latency

A voice agent goes quiet for a second and a half while it looks up an order status, and the caller doesn't experience that as "the backend is slow" — they experience it as "the call dropped" or "the bot broke," and they hang up or call back. The fix — play a short holding phrase while the real work finishes — is so obvious that practically every voice-AI team has already built their own version of it. None of them has built it as something the next team can just install.

## The Gap

Hugging Face's "Voice Agent Latency Playbook" treats playing a filler phrase during an in-flight tool call as standard production practice at this point — not a nice-to-have, a workaround everyone eventually reaches for. Soniox's voice-agent-tool-calling wiki and a Speechify post independently describe tool-call silence as a recurring pain point from the other direction — teams that haven't handled it yet. A Netguru article frames the caller-facing symptom bluntly: "why is my bot slow when the model is fast" is a complaint that recurs regardless of how fast the underlying model actually is, because the model isn't what the caller is waiting on.

What's missing isn't the idea — it's a shared implementation of it. Every one of these sources describes filler audio as something each team wires up from scratch: what phrase to play, when exactly to trigger it, how to cancel it cleanly if the caller interrupts or the result comes back first. GitHub turns up `AgoraIO-Conversational-AI/recipe-agent-filler-words`, a one-star vendor recipe, and `livekit/agents`' `fast-preresponse.py`, a single non-timeout-driven example — not a reusable primitive either way. Deepgram, getstream.io, and AWS Builder each have their own bespoke write-up of essentially the same pattern. Nobody has shipped the provider-agnostic version; everybody has shipped a slightly different one-off.

## The Project

Hold Line is middleware that sits on a voice agent's tool-execution lifecycle. Once a tool call has been pending past a configurable latency threshold (700ms by default) without a result, it starts a contextually appropriate spoken filler through the agent's existing TTS pipeline — "let me check that for you," "one moment while I pull that up," not a generic beep dropped in to fill dead air. It kills that filler the instant either of the two things that make filler audio feel worse than silence happens: the tool call actually resolves, or the caller barges in. Those are the two specific failure modes worth naming, because getting them wrong is worse than doing nothing — "it's still talking after I interrupted" and "dead air came back because the filler never started in the first place" are both more broken-feeling than the problem filler audio was meant to solve.

The phrase selection isn't generic either — it's aware of what kind of tool is running (a lookup, a transaction, an open-ended search), and it escalates ("still working on it...") rather than looping the same clip if the wait drags on. Under the hood it's four pieces: a per-tool latency-threshold watcher, a configurable contextual-phrase library, a barge-in/completion cancellation hook, and a telemetry log of filler-onset timing and cancellation correctness for after-the-fact debugging. It ships as thin adapters for LiveKit Agents and Pipecat — the same plugin footprint as this project's own sibling, the already-published Speculate (`voice-agent-speculative-tool-calling-middleware`). The two are explicitly complementary, not competing: Speculate fires calls early when it can predict them; Hold Line covers the calls nobody can predict or speed up — a slow third-party API with no usable partial signal, for instance.

## Tangible Impact

**Population**: callers to AI voice agents whose calls invoke at least one backend lookup or transaction with latency the system genuinely can't eliminate — insurance claims intake, order-status checks, benefits-eligibility lookups — within the segment Forrester's 2026 Wave research reports now carries roughly 19% of inbound contact-center volume (up from 6% in 2024), where 79% of callers still say they'd rather talk to a human, meaning every stretch of unexplained silence reinforces that preference.
**Mechanism**: an unfilled silence during a slow tool call reads to a caller as "the bot is broken" or "the call dropped," driving early hang-ups and repeat calls; a correctly sequenced filler phrase signals the system is still working, reducing the perception of failure without changing the underlying backend latency at all — a cheap fix for calls where the latency itself genuinely can't be removed.
**Measure**: call-abandonment rate during tool-call-pending segments before vs. after adoption; caller perceived-naturalness/satisfaction score on an A/B pilot comparing filler-on vs. silent calls; rate of cancellation-correctness failures (filler audio still playing after barge-in or after the tool result returns — target near zero in a labeled test suite).

## Try It

A companion Claude Code skill, [`skills/voice-agent-filler-audio-middleware/`](../skills/voice-agent-filler-audio-middleware/) — "Filler Coverage Designer" — is already written: *"Designs the filler-audio (holding-phrase) policy for a voice agent's slow tool calls — which tools need it, what to say, and when to cancel — from a pasted tool/latency manifest, before anyone wires it into the runtime."*

It's the design-time half of this idea, not the runtime engine itself. You hand it a manifest of your agent's tools (name, what each does, and rough latency — p50/p95 if you have real numbers, a typical/worst-case range if that's all you've got), and it comes back with a coverage table of which tools actually cross the filler-worthy threshold, a phrase set per tool category, an escalation ladder for the slow outliers, and an explicit cancellation-policy spec naming the two signals (tool-result-ready, barge-in) the runtime needs to wire up. It flags anything under-specified — an unclassified tool, a tool with no latency data, or unreliable barge-in detection in your stack — rather than guessing past the gap. To use it: paste the `README.md` into any AI chat tool, or drop the `skills/voice-agent-filler-audio-middleware/` folder into `~/.claude/skills/` if you're on Claude Code.

## Risks & Open Questions

Badly tuned filler audio can land as patronizing or robotic and make the experience worse than silence — that's a real-listener-testing problem, not something engineering correctness on cancellation timing alone solves. The project has to stay clearly positioned as complementary to speculative tool-calling (this repo's own published Speculate), not a second fix for the same latency — the differentiator is covering the calls speculation genuinely can't help, truly unpredictable third-party latency with no useful partial signal. There's a real chance a framework vendor — LiveKit, Deepgram — ships its own opinionated filler feature before an independent library gets any adoption, so the differentiation has to be the pre-built, tool-category-aware phrase libraries and cross-framework sequencing policy, not just "we play a sound." And the whole thing depends on barge-in detection being reliable in the first place, which is itself a documented adjacent gap — if barge-in lags, filler audio risks talking over a caller who already started speaking.
