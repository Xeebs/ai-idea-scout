# Provenance Gate: A Unified Trust Layer for MCP Servers and Agent Skills

Right now, if you want to give your coding agent a new MCP server or a new skill, the actual vetting process at most shops is: someone reads the README, shrugs, and clicks install. There are somewhere between 20,000 and 30,000 MCP servers listed in the official registry as of September 2026, and a growing pile of community skills alongside them — and the registry only lists. It doesn't vet. The security review step that should sit between "someone found this on GitHub" and "this now has tool-calling access to your agent" barely exists, and the people trying to build it keep rediscovering that fact in public, one small Show HN at a time.

## The Gap

The clearest tell is a Hacker News post from November 9, 2026: "USB: A trust layer for AI skills and MCP servers," linking to a fresh GitHub repo (`PeepSick/usbplus`) that picked up 11 points and 3 comments. What's notable isn't the traction — it's the framing. The HN discussion treats this as a new proposal worth floating, not a pointer to an existing standard everyone already uses. That's a strong signal nothing dominant has converged yet.

It's also not an isolated signal. A second independent research pass a day later turned up the same gap again, this time citing the same USB project but surfacing a wider field around it: `dotsetlabs/countersign` (Sigstore-based signing), ToolHive's build-provenance checks, NVIDIA's documented internal "agent skill trust pipeline," a draft spec called `PromptSign/spec` for keyless skill-signing, and an independent Merkle-tree/Ed25519 attestation layer called STSS. Even a formal feature request asking Anthropic for "an official verified marketplace for Skills, MCP Servers, and Custom Agents" got filed against Claude Code — and was closed without one shipping. The Cloud Security Alliance was still describing combined MCP-and-skill trust as an open problem as of September 2026.

So this is the rare gap that's genuinely crowded and genuinely unsolved at the same time. `stacklok/toolhive` is the strongest single data point against a quick dismissal — 2,339 stars, updated within the last day, offering real disabled/warn/enabled verification for MCP server images. It proves the MCP-server half of this problem is buildable and adoptable. What none of these five-plus projects do is treat MCP servers and skills as one unified install-time decision with one auditable ledger. Each is narrow: signing, or provenance, or server-image scanning, or a draft spec nobody's shipped against yet. The honest read, carried straight from the gap-analyst's verdict, is PARTIAL, not OPEN — a serious build here has to differentiate against real competition, not invent a category from nothing.

## The Project

Provenance Gate is a policy-enforcement gateway that sits in front of the moment an agent host loads a new MCP server connection or a new skill, and treats both as the same kind of decision. Before anything runs, it checks the artifact against layered policy: a known-publisher allowlist, a static manifest scan comparing declared permissions against declared function (does this thing that claims to "read calendar events" also ask for arbitrary network egress?), a signature or provenance check where one is available, and a community trust score pulled from how the artifact has behaved elsewhere. The default posture is warn, not block — only sources that clear the bar get promoted to fully enabled — and every decision, allow or warn or block, writes to an auditable ledger a security team can actually review later instead of reconstructing from memory.

The centerpiece isn't any one check — toolhive already does signature verification well, and the point solutions above each do their own slice competently. The centerpiece is refusing to split MCP servers and skills into two review pipelines when they're the same risk to an agent host: untrusted third-party code with tool-calling access. Nobody currently treats that as one ledger, one policy file, one install-time gate.

## Tangible Impact

**Population**: Platform/security teams at organizations running Claude Code or other agent hosts with third-party MCP integrations who must approve what gets installed — a population that scales with the registry itself (20,000–30,000 listed MCP servers by Sept 2026, plus a growing skills ecosystem) and includes every org with a security review gate around agent tooling.
**Mechanism**: Replaces ad hoc or absent manual review with an automatic layered check at install time, turning "no one looked at this" or "someone eyeballed the README" into a documented allow/warn/block decision with reasoning — shrinking both approval latency and the chance an unreviewed server or skill slips through unexamined.
**Measure**: Median time from "developer requests a new server/skill" to "security-approved"; % of installs with a documented trust decision vs. none before adoption; detection rate of planted high-risk installs in a red-team test set (false-negative tracking).

## Try It

There's no shipped skill yet — this idea is tagged Format: BOTH, but no `skills/mcp-skill-trust-attestation-layer/` directory exists in this repo at this stage. The idea file sketches what that companion skill would do once built: hand Claude a URL, repo, or manifest for an MCP server or skill, and get back a one-shot structured trust review — permissions requested versus advertised function, declared network calls, signer/provenance, red flags against known attack patterns — with a pass/warn/fail verdict and reasoning. That's usable standalone, without ever running the always-on gateway, and it's deliberately a point-in-time review rather than an enforcement service: the skill helps someone decide before they install; the project is what keeps watching after.

Worth sitting with before anyone builds the full version, because the idea file names it directly: toolhive or the official registry could absorb this scope themselves given the momentum both already have, eroding the differentiation fast. Cryptographic provenance and signing aren't standardized across MCP yet, so verification may have to stay heuristic rather than cryptographically guaranteed for a while. And overly strict defaults risk the same approval-fatigue failure mode as having no gate at all — a policy layer that warns on everything teaches people to click through warnings, which is a different flavor of the same unsolved problem.
