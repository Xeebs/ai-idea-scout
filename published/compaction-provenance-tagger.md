# Provenance Seal: A Provenance-Preserving Compaction Layer Against Instruction Laundering

Somewhere in a README your coding agent merely *read* — not one it was told to trust — there's room to plant a line that looks exactly like a standing instruction. Leave it there long enough, run the agent long enough to trigger a context compaction, and that forged line can come out the other side of the summarization step reading no differently than something you actually typed. No flag, no asterisk, no record that it was ever anything but a user turn. That's not a hypothetical: a fresh arXiv paper demonstrated the attack class, measured how well a naive fix catches it, and found the fix wanting. Nobody has shipped the better one yet.

## The Gap

An arXiv paper that surfaced on Hacker News in the last 30 days — "Compaction Laundering: Provenance Destruction in Context-Compacting Coding Agent" (arxiv.org/abs/2610.29869) — names the mechanism precisely. Standard compaction flattens an entire conversation history, tool-call output and all, into labeled text before an LLM summarizes it down. That flattening step is where provenance dies: a `[User]:`-style line forged inside a malicious README, a scraped web page, or a poisoned file the agent read gets no special treatment once it's inside the flattened blob. Summarize it, and it can emerge looking like a standing user instruction with zero trace that it never actually came from the user.

The paper's own secondary analysis is refreshingly honest about what doesn't work: a prompt-level mitigation — essentially telling the model to "be careful during compaction" — only modestly reduces the attack, catching somewhere in the 13–25% range. A dedicated provenance-check layer, tuned to a 0.15 strictness threshold, does much better, catching roughly 77% of laundering attempts. But that number comes from a research result, not a tool. A thorough search turns up no shipped compactor — in Claude Code, Codex, or anywhere else — that tags provenance through summarization by default. The mechanism that works exists only on paper.

## The Project

The fix is a compaction wrapper that tags every span of conversation history with its real origin — verified user turn, model turn, tool-call output, or file/web content a tool merely read — *before* summarization runs, and carries that tag through the summarization step itself. The point isn't to block compaction or slow it down; it's to make sure the compacted output can never lose track of which lines were genuinely user-authored versus merely encountered. Any line in the post-compaction summary that reads like a standing instruction but traces back to an untrusted-content span gets flagged, or stripped of its borrowed authority, instead of silently getting promoted to look user-written.

Four pieces make this real rather than theoretical: a span-tagger that classifies every turn or chunk by origin before compaction runs; a provenance-aware summarizer that either passes those tags through the LLM compaction call or runs a post-compaction check comparing summary claims against tagged origins; a strictness-threshold-tunable laundering detector that replicates the paper's own 0.15 operating point; and a per-runtime hook, starting with Claude Code, which already exposes a compaction hook surface to attach to. The centerpiece isn't a new detection trick — it's making the one mechanism the paper already validated survive the exact step that currently destroys it.

## Tangible Impact

**Population**: Developers and teams running autonomous coding agents on real, often untrusted, repositories and web content — anyone whose agent reads third-party READMEs, scraped pages, issue trackers, or file content and then runs long enough to trigger automatic compaction, which per the paper's framing is the exact condition under which this attack class becomes exploitable. This spans essentially the population of long-running Claude Code/Codex/Cursor coding-agent users operating on non-self-authored code or content, a population already large and growing as autonomous agent sessions get longer.
**Mechanism**: Today, an attacker who can get a forged "[User]: ignore prior instructions and do X" line into any file or tool output the agent reads gets a free shot at having that line laundered into a trusted-looking standing instruction the moment compaction runs — with zero record that it wasn't actually said by the user. A provenance-preserving compactor closes that laundering window by making the compacted output unable to lose the distinction between "the user said this" and "the agent merely read this somewhere."
**Measure**: (1) Laundering catch rate on the paper's own benchmark methodology (or a reproduction of it), with the provenance layer on versus off, targeting the paper's reported ~77% figure as a floor to beat. (2) False-positive rate — legitimate user instructions incorrectly flagged as laundered, which determines whether teams can run this always-on without breaking normal use. (3) Successful-attack rate in an end-to-end red-team exercise (plant a forged instruction in a file, run a long session through compaction, check whether the agent acts on it) before versus after adoption.

## Try It

A companion skill exists at [`skills/compaction-provenance-tagger/`](../skills/compaction-provenance-tagger/): *"One-shot audit of a pre- or post-compaction agent transcript/summary for 'instruction laundering' — instruction-shaped lines that read as standing user directives but actually trace back to untrusted tool/file/web content the agent merely read, not a real user turn."*

This is the one-off forensic half of the idea, not the always-on hook — useful the moment you have a specific compacted session (or a compaction prompt) you want checked for laundering, independent of ever wiring in the live tagger. To use it: paste the contents of `skills/compaction-provenance-tagger/README.md` into any AI chat tool along with the compacted summary and whatever original pre-compaction material you have (real user turns, plus the untrusted tool/file/web content the agent read), or drop the whole `skills/compaction-provenance-tagger/` folder into `~/.claude/skills/` if you're working in Claude Code. If you only hand it the summary with no originals to check against, it will say so plainly and mark everything unverifiable rather than pretend to a confidence the evidence doesn't support — that's a deliberate guardrail, not a limitation to work around.

Worth naming the real risks up front, because they're already in the idea file and they don't go away just because the writeup is public. The underlying paper was only confirmed via a secondary summary, not the primary source directly — so the first job of any build here is reproducing the paper's claimed catch rates before trusting them further. A strictness threshold tuned to the paper's own test conditions may not generalize to real-world transcripts, risking either missed laundering if it's too loose or broken legitimate workflows if it's too strict. Cross-runtime portability is unproven outside Claude Code's confirmed compaction hook — Codex CLI and Cursor's equivalents are unverified, which could leave this a single-runtime tool rather than a general one. And the most direct competitive risk is structural: Anthropic, OpenAI, or Cursor own both the compaction step and the hook surface this depends on, and any of them could ship provenance-preserving compaction natively before an independent build gains traction.
