# Bottleneck Watch: A Runtime Coordination-Overhead Diagnostic for Scaling Multi-Agent Stacks

Every team that scales a multi-agent stack past a handful of agents eventually hits the same wall: performance that was fine at five agents quietly falls apart at ten, and nobody saw it coming because nothing was watching for it. There's now a controlled study putting hard numbers on that wall — and still not one shipped tool that tells a team, in real time, that they're walking toward it.

## The Gap

IndieHackers posts titled "Why your AI agent stack will break at 10 agents and what to do about it" and "Stop adding more agents, start giving them structure" describe this cliff the only way anyone currently can: after the fact, as a war story. Teams add agents assuming more parallelism keeps paying off, and only learn otherwise once output quality has already visibly cratered.

What's new is that this folklore now has a number attached to it. A controlled study, "Towards a Science of Scaling Agent Systems," ran 180 experiments and measured 39–70% quality degradation on sequential-reasoning tasks past a coordination threshold — and researchers have proposed two concrete metrics to track it, a Coordination Bottleneck Index (CBI) and an Agent Coordination Bound (ACB, built on the n(n-1)/2 growth of communication edges as agent count rises). But a search for anyone turning either metric into a runnable guardrail against a live agent stack came up empty. No GitHub repo computes CBI or ACB from a real running system today. The gap isn't the insight — it's that the insight still lives only in a paper, while practitioners are still finding out about the cliff the hard way.

## The Project

Bottleneck Watch is a monitor that sits on top of a running multi-agent stack and continuously computes a coordination-load score against the degradation curve the cited study measured — not a one-time audit, but an always-on early warning system. It ingests the stack's live communication graph (who's calling whom, how often, with what latency) straight from the agent framework's own orchestration or tracing output, then tracks how close the current load sits to the empirically-measured failure threshold. When the trend line starts bending toward that threshold, it alerts — and pairs the alert with a concrete recommendation drawn from the same practitioner advice that motivated this idea in the first place: consolidate roles, introduce hierarchical sub-teams, give the agents structure instead of just adding more of them.

The pieces: a per-framework log/trace ingestion adapter (reading OpenTelemetry GenAI spans, or a framework's native execution logs — LangGraph and CrewAI both already produce this data, it's just never been read this way); a CBI/ACB computation engine; a threshold-alerting policy seeded from the study's observed degradation curve; a dashboard plotting current coordination load against the measured safe zone; and a structural-fix recommendation module that fires once a threshold is crossed. The centerpiece is turning an academic metric that currently exists only in a paper into an operational signal a team actually watches.

## Tangible Impact

**Population**: Teams operating production multi-agent stacks with 8+ concurrently coordinating agents — the exact population the IndieHackers posts and the 180-experiment study describe — who today only discover the coordination cliff once output quality has already visibly degraded, since nothing watches for its approach.
**Mechanism**: Teams add agents assuming more parallelism keeps helping, with no instrumentation measuring when communication overhead starts exceeding that benefit; by the time a quality regression is noticed, the team must retroactively diagnose which agent or interaction pattern caused it. This monitor computes the coordination-load metric continuously, so a team sees the trendline rising toward the measured failure threshold and can act — consolidate roles, restructure topology — before quality visibly drops, not after.
**Measure**: (1) Lead time — how many agent-additions or task-cycles before measured quality degradation the tool's alert fires, versus zero lead time today. (2) Correlation between the tool's CBI/ACB score and actual task-success rate, validated against the cited study's published degradation curve. (3) Fraction of pilot teams who restructure after a raised alert versus teams who only discover the cliff after the fact, pre/post adoption.

## Try It

A companion skill is already written: [`skills/multiagent-coordination-bottleneck-diagnostic/`](../skills/multiagent-coordination-bottleneck-diagnostic/). Its one-line description: "Scores an already-decided multi-agent architecture (agent count, communication topology, task type) against the published scaling-cliff research (coordination overhead growing with agent-to-agent edges, ~39-70% quality degradation reported past a threshold on sequential-reasoning tasks) to estimate how close it is to that cliff, and recommends structural fixes."

This is the one-shot, design-time cousin of the full project above — it doesn't read live traces, it reasons from a description you give it (agent count, who talks to whom, task type), and it's useful the moment you've settled on a multi-agent shape and want a sanity check before you scale it further. To use it: paste the contents of `skills/multiagent-coordination-bottleneck-diagnostic/README.md` into any AI chat tool along with a description of your agent setup, or drop the whole `skills/multiagent-coordination-bottleneck-diagnostic/` folder into `~/.claude/skills/` if you're running Claude Code. If you actually have a running stack with trace or log data and want continuous tracking rather than a one-time estimate, that's the larger project described above — the skill will tell you so rather than pretend to be that.

Worth knowing before you build or adopt either: CBI and ACB are new, unvalidated metrics outside their originating paper, and the ~10-agent cliff was measured specifically for sequential-reasoning tasks — the real threshold for other topologies and workloads is likely different, and a framework vendor like LangGraph or CrewAI could ship something similar quickly since the underlying message-graph data is already theirs to instrument.
