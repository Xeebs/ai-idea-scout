# Breaker: A Cost-Aware Circuit Breaker for Repeatedly-Failing Agent Tool Calls

An agent that fails is normal. An agent that fails the same way four times in a row, each time billing you for the privilege, is a bug nobody has bothered to fix — because the fix most teams reach for is a hard-coded timeout, and the fix nobody has shipped yet is a general-purpose breaker that notices the *shape* of a doomed retry and stops it before the meter runs out.

## The Gap

The clearest evidence isn't a complaint thread — it's a merged pull request. In `github/gh-aw-firewall` PR #11280 ("fix: gate PR Sous Chef agent launches on trusted refresh," 2026-11-07), the team reports that 29 of 35 inspected agent runs failed while repeatedly re-selecting the same already-failed PR, burning roughly 10 AIC per run without producing anything usable. Their fix was exactly what you'd expect from a team with no off-the-shelf option: a single hard-coded precondition bolted onto one internal tool, solving their one case and nobody else's.

That's the pattern across the whole space. The practice of circuit-breaking agent loops is written about constantly — a substack literally titled "The Agentic Circuit Breaker," walkthroughs from Gravitee and FutureAGI, a string of dev.to posts — but writing about a pattern isn't shipping it. OneUptime has a docs page for an "AI Agent Circuit Breaker," and it reads like a recipe: stitch together your existing budget tracker, your trace monitor, and a stop endpoint you write yourself. GitHub's own search turns up only brand-new, narrow point tools — `devsoniclk/tripwire` and `rejisterjack/fuse`, the latter created days before this writeup — neither established enough to call a real option. The gap-analyst's verdict was PARTIAL, not SATURATED, for exactly this reason: plenty of talk, no maintained product. By the next research cycle the same gap resurfaced independently, this time corroborated by a cluster of six-plus separate indie repos (AgentBrake, agent-guard-mcp, loopguard/ai-loopguard, `@monetisebg/circuit-breaker`, NakshGuard, Agent Firewall) all converging on the same idea within the same month — unevaluated against each other, each reinventing the wheel alone.

## The Project

Breaker is a framework-agnostic middleware that wraps tool-call execution for any agent loop — a Claude Agent SDK pipeline, a LangGraph graph, a raw MCP client — and tracks a sliding-window failure signature per (tool, argument-shape, session) tuple. When a configurable threshold of repeated failures is crossed, it trips: pausing the loop, escalating to a human or a different recovery path, or aborting the run outright, before more cost gets spent on something that was never going to succeed.

Three detection strategies do the actual noticing. The first catches the easy case — identical arguments retried against a call that already failed. The second catches the same error code repeating regardless of argument changes. The third, and the hardest, catches the "same target, reworded" pattern: an agent re-selecting the same PR, ticket, or file under slightly different phrasing, which is exactly what sank 29 of those 35 gh-aw-firewall runs and exactly what a hard-coded precondition can't generalize to catch. Every trip gets logged against a cost-saved ledger, so a team isn't left inferring the breaker's value from a vibe — they get a dollar figure for every run it stopped from burning further.

The four components: a drop-in tool-call execution wrapper, the sliding-window failure tracker with its three strategies, a pluggable trip action (pause/escalate/abort), and the cost-saved ledger.

## Tangible Impact

**Population**: Engineering teams running agentic workflows in automated, metered contexts at real scale — CI/CD coding-agent pipelines (GitHub Actions-based agents, PR-review bots), scheduled batch agent jobs, and any team paying per-API-call or per-compute-unit for agent runs that can get stuck in a doomed retry loop. The source evidence's own measured case (gh-aw-firewall) shows 83% of inspected runs (29 of 35) hitting this exact waste pattern — a cohort that scales with the growing adoption of agentic CI tooling (Claude Code's GitHub Action, Codex, and similar).
**Mechanism**: Today, an agent loop that hits a doomed-to-fail pattern (re-selecting the same already-failed target, retrying an unfixable error) keeps spending API/compute cost until it hits an unrelated timeout or budget ceiling, because nothing inspects the *shape* of repeated failure mid-run. A pluggable breaker halts the loop at the moment the failure signature repeats past threshold, converting open-ended wasted spend into a bounded, measured cost.
**Measure**: (1) % reduction in wasted API/compute cost from repeated-failure loops on a team's own run history, replaying the gh-aw-firewall case's measured baseline (29/35 runs, ~10 AIC/run wasted) as a validation target. (2) Median time-to-trip — how much sooner the breaker halts a doomed loop compared to the loop's natural timeout or budget ceiling. (3) False-positive trip rate — legitimate retries incorrectly halted, which must stay low enough that teams trust the breaker rather than disabling it.

## Try It

A companion skill already exists: [`skills/agent-tool-call-cost-circuit-breaker/`](../skills/agent-tool-call-cost-circuit-breaker/). Its one-line description: "Analyzes a pasted batch of agent tool-call logs/traces to find repeated-failure loops that burn API/compute cost without progress, quantify the waste, and recommend starting threshold/window parameters for a circuit-breaker before you build or buy one."

This is a retrospective diagnostic, not the live breaker itself — it's the thing you run *before* building or deploying one, to find out if you even have the problem and what thresholds would make sense. Two ways to use it: paste the `README.md` into any AI chat tool along with a batch of your own agent run logs (tool name, arguments, success/fail status, and cost-per-call if you track it), or drop the whole `skills/agent-tool-call-cost-circuit-breaker/` folder into `~/.claude/skills/` if you're running Claude Code, so it's available automatically the next time you hand it a log batch.

Worth noting before you reach for the live version: the hardest of the three detection strategies — catching "same target, reworded" — is also the most valuable one, and the idea file is honest that if it can't be made reliable, the standalone project degrades to the same narrow identical-argument gating the existing ad hoc fixes already do. Agent frameworks could also ship this as a built-in primitive eventually (some teams are already moving that direction internally), which would narrow a standalone library's edge down to cross-framework portability and the pluggable-strategy design. Worth knowing going in, not something to discover after building it.
