# MemLeak Bench: Separating Retrieval Leakage from Agent-Memory Leakage

Two numbers from a three-point Show HN post should be setting off alarms in every team shipping an AI product with persistent memory: raw RAG leaked 0% of cross-tenant content in testing, agent memory leaked 67%. Same product, two very different failure rates, and almost nobody is measuring them separately. Most "leakage" tooling still reports one collapsed number, which means a team patching the wrong layer can walk away thinking they fixed the hole.

## The Gap

The evidence trail starts with a specific repo: github.com/harishbalasubramanian/sentinel-eval, posted to Hacker News on 2026-11-09 under the title "Show HN: Raw RAG leaks 0%, but agent memory leaks 67%." It's the first public measurement to put those two numbers side by side rather than averaging them into one leakage rate — and the split itself is new as a tested claim, not as a suspicion. A `gh repo view` on the project confirms it's brand new and narrow: 2 stars, pushed the same day it was posted. A broader web search turned up academic work that studies agent-memory leakage on its own — PersistBench, CIPL, Entity-Collision, MEMPROBE — but none of it pairs that with a RAG-retrieval leakage harness in the same evaluation. So the gap sits in a specific, narrow place: not "nobody studies memory leakage" and not "nobody studies RAG leakage," but nobody measures both together, attributed to the layer that actually caused each one.

That attribution gap matters because the two failure modes need completely different fixes. Retrieval leakage means a document chunk the current user shouldn't see got pulled into the answer — the fix is access-control-aware retrieval, filtering by tenant or owner before the similarity search runs. Memory leakage means something written to the agent's own persisted memory store, from a different user or an earlier session, resurfaced where it shouldn't — the fix is memory-write and memory-read isolation, scoping storage and retrieval by session or tenant ID. Collapse both into one leakage percentage and a team has no way to know which of those two very different fixes they actually need.

## The Project

MemLeak Bench is an open benchmark plus a lightweight instrumentation library for exactly this: agent systems that combine document RAG with persisted agent memory. It runs two independent test harnesses, not one blended score. The retrieval-leakage harness probes a multi-tenant document corpus with access-control labels and checks whether a chunk the querying user shouldn't have access to ever gets retrieved. The memory-leakage harness probes a multi-user memory store with cross-session queries and checks whether information written by one user or session resurfaces in another's. Each harness produces its own metric and its own remediation guidance, so a team fixing a leak is fixing the layer that's actually broken — not patching retrieval access control because that's the familiar playbook, while the real hole sits open in memory writes (or the reverse).

The library layer is meant to be instrumented into an existing stack rather than requiring a rebuild: point it at the retrieval path and the memory store, and it runs both probes against whatever architecture is already in production. Part of the roadmap is explicitly testing whether leakage behavior is architecture-dependent — running the same probes against a summarized-history memory, a vector-memory, and a structured-fact-store, to see whether the 0%/67% split from the source repo is a general pattern or an artifact of one specific implementation.

## Tangible Impact

**Population**: Developers of consumer and enterprise AI products with persistent cross-session memory — AI companion/assistant apps and enterprise copilots that remember prior conversations across sessions or users — who must demonstrate to privacy auditors, enterprise security reviewers, or regulators (under GDPR/CCPA-style data-isolation requirements) that one user's private information cannot surface in another user's session via the memory layer. The source benchmark's own finding (0% vs. 67% leakage) shows this is a live, not hypothetical, risk for exactly this population.
**Mechanism**: Correctly attributing a leak to retrieval vs. memory lets a team apply the right fix (access-control-aware chunking vs. memory-write isolation/scoping) on the first try, instead of misdiagnosing a memory leak as a retrieval problem and leaving the real hole open.
**Measure**: leakage rate broken out by failure class on the benchmark, before and after a targeted remediation; number of previously-misclassified leak incidents correctly re-attributed in a case study; adoption as a pre-release or CI gate (number of projects integrating the harness).

## Try It

A companion skill exists at [`skills/rag-agent-memory-leakage-benchmark/`](../skills/rag-agent-memory-leakage-benchmark/): *"Classifies a suspected cross-user/cross-session privacy leak in a RAG + agent-memory system as retrieval-layer, memory-layer, compound, or unresolved, and recommends the layer-matched fix. Use this when a leak incident, red-team probe, or audit finding needs root-cause attribution before anyone starts patching."*

This is the one-off version of the project — useful the moment someone has a concrete leak incident in hand and needs to know which layer caused it, without standing up the full two-harness benchmark. It works through an incident by independently checking the retrieved-chunk list and the memory-store contents for a match to the leaked content, then classifying the incident as RETRIEVAL, MEMORY, COMPOUND (both layers independently carried the leak — the dangerous case where fixing only one looks like a fix while the other path stays open), or UNRESOLVED when the evidence is missing or inconclusive. To use it, paste the contents of `skills/rag-agent-memory-leakage-benchmark/README.md` into any AI chat tool along with the leaked content, the retrieved chunks, and the memory-store entries for the session in question, or drop the whole `skills/rag-agent-memory-leakage-benchmark/` folder into `~/.claude/skills/` if you're working in Claude Code.

Worth being honest about before leaning on either version: the 67% figure comes from one 2-star, days-old repo, and it hasn't been independently replicated — treat it as a strong first signal, not a settled industry rate, until it's been tested on more than one implementation. It's also possible the real gap here is smaller than "build both harnesses from scratch" — the existing academic work on agent-memory leakage alone (PersistBench, CIPL, MEMPROBE) may already cover enough ground that pairing it with a RAG-retrieval harness is the actual lift, not a full rebuild. And demand signal is thin: a 3-point HN post is a spark, not proof of pull, so validating interest with teams who actually run this architecture is worth doing before committing to the full build.
