# True Use: A Multimodal AI Auditor for Real Assistive-Tech Interaction, Not Just WCAG Markup

95% of the top 1,000,000 homepages have at least one WCAG failure, and the tools meant to catch those failures only find 30-40% of them. The other 60-70% — the ones that actually decide whether a blind, switch-access, or voice-control user can complete a task — stay invisible until a human tries to use the page and gets stuck. Nobody has built a tool that closes that gap at scale. One research prototype comes close, on exactly one platform.

## The Gap

WebAIM's 2026 report (cited via IT Brief Australia) is blunt about the ceiling on automated testing: it "detects only about 30% to 40% of WCAG success criteria failures." Cognizant frames multimodal AI as "beginning to close" that gap by generating real-time descriptions of visual content, and Salesforce goes further, calling what's left "a gap in process," not technology. But a University of Maribor paper pushes back hard on the premise that AI already fixes this: it concludes LLM-based accessibility auditors "lack the stability and accuracy required to properly support human accessibility auditing." Silktide's 2026 commentary lands in the same place from a different angle — no scanner can yet judge whether alt text actually makes contextual sense, only whether it exists.

The one real counter-example is ScreenAudit (arXiv 2504.02110), an LLM-driven checker for Android TalkBack that was validated against six accessibility experts, including a blind screen-reader user, and it outperformed existing rule-based checkers. AudioEye has also announced "Agentic Audits," though without public detail on what it actually catches. Put those together and the shape of the gap is precise: the *idea* of an AI auditor that reasons about real interaction instead of just markup is validated — on one platform, one interaction mode — and the stability critique that would make it trustworthy more broadly hasn't been answered yet anywhere.

This is a different mechanism from this pipeline's own `accessibility-scanner-divergence-gap-map` idea, not just a different name for the same thing. That project is a static, continuously-validated lookup telling a human which WCAG criteria automated scanners can't be trusted on, so they know where to go check by hand. This project is the thing that does the checking — it runs the actual interaction sequence a real assistive-tech user would run, and tells you exactly where it breaks.

## The Project

Take ScreenAudit's validated approach — an LLM reasoning about actual interaction sequences instead of DOM markup — and generalize it past Android TalkBack to the other ways people with disabilities actually operate a page: screen-reader navigation on the web via NVDA/VoiceOver scripting, switch-control scanning order, and voice-control command coverage. Each run simulates one of those interaction modes against a real page or app. Instead of handing back a free-form LLM opinion — the exact brittleness the Maribor paper is complaining about — it returns a structured, reproducible trace per failure: the specific interaction step, what a real assistive-tech user would experience at that step, and the evidence behind the call. "Tab order skips the search button." "The switch scan sequence never reaches the submit control." "No voice command matches the visible 'Cancel' action."

The stability problem gets a direct answer instead of a hand-wave: every flagged failure is re-run multiple times and only surfaces if it reproduces. That's the whole bet of this project — not that an LLM auditor is magically stable, but that repeat-until-stable verification is a cheap, checkable way to filter out exactly the noisy, one-off judgments the Maribor paper caught.

## Tangible Impact

**Population**: The roughly 61 million U.S. adults with a disability (CDC) who use assistive technology — screen readers, switch access, voice control — to navigate websites and apps, and the small-to-mid-size organizations maintaining the 95% of the top 1,000,000 homepages WebAIM found have at least one WCAG failure, who cannot afford a full manual audit for every release.

**Mechanism**: Catches the 60-70% of real usability failures automated scanners structurally miss (WebAIM's own figure) before a disabled user hits them in production, closing the specific gap Cognizant and Salesforce both describe as still open — without requiring a full-cost manual audit cycle for every release, and without the instability the University of Maribor paper found in less-constrained LLM auditors.

**Measure**: (1) agreement rate between the tool's flagged failures and an independent panel of real assistive-tech users doing manual testing on the same pages, replicating ScreenAudit's 6-expert validation methodology at larger scale and across the added interaction modes; (2) reproduction/stability rate of flagged failures across repeated runs on the same unchanged page, directly answering the Maribor paper's stability critique; (3) number of real interaction failures caught pre-release vs. a markup-only scanner baseline on a held-out test corpus of real sites.

## The Honest Risks

The University of Maribor paper's stability and accuracy critique isn't a footnote here, it's the central risk the whole project has to actually overcome — the repeat-until-stable design is a hypothesis about how to answer that critique, not a proven fix, until it's tested against real assistive-tech users. AudioEye's "Agentic Audits" product may already cover more of this ground internally than its public announcement discloses, so evaluating AudioEye's actual output directly, rather than assuming a clean greenfield, is a reasonable first move before building much. Recruiting real assistive-tech users — especially switch-access and voice-control users, smaller and harder-to-reach populations than screen-reader users — for validation is a genuine, known bottleneck across this entire problem space, not something specific to this project. And there's a real tension in the scope itself: ScreenAudit's credibility came partly from how narrow it stayed, one platform, one interaction mode, validated end to end. Generalizing across three interaction modes risks diluting exactly the depth that made the original result trustworthy, which is why the MVP deliberately adds only one new mode — switch-control navigation via Playwright — rather than attempting all three at once.
