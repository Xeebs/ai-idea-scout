# Split Core: A Stable/Volatile Splitter and Auto-Regenerator for Agent Rule Files

Your `AGENTS.md` or `CLAUDE.md` started as ten clean lines about build commands and trade-off priorities. Eight months later it's three hundred lines of build commands, trade-off priorities, last Tuesday's TODO list, a status snapshot from a migration that finished in June, and a half-dozen "currently working on" notes nobody deleted — and it gets re-pasted into every single request. Two teams hit the same wall in the same week and reached for the same fix independently, by hand, with no shared tool between them. That's the gap: everyone agrees the file needs splitting, and everyone is still doing it themselves.

## The Gap

Two r/ContextEngineering threads, posted days apart, describe the identical failure mode. One team's `AGENTS.md` grew "one justified-looking addition at a time" until the agent started butchering its own edits to the file — misreading or corrupting the very rules meant to guide it. Another team, running a multi-agent pipeline split across architect/builder/auditor roles, hit the same wall once their file crossed roughly 150 lines and carved out a separate raw `TOKENME.txt` to hold the dynamic state, just to stop the bleeding. Neither built anything reusable. Both built a one-off, repo-specific convention and moved on.

A search for a shared tool or naming convention — "AGENTS.md splitting static rules dynamic repo state," "claude.md dynamic state generator" — turns up nothing. What exists instead are adjacent half-measures: nested per-directory `AGENTS.md` files where "nearest file wins," Cursor's `.cursor/rules/*.mdc` convention, and guidance to push procedural content into Agent Skills instead of prose. None of these actually solve the problem both Reddit threads describe, which isn't "where do rules live" but "how do I stop a file that mixes permanent instructions with decaying status notes from silently rotting, and keep the split clean once I've made it." Splitting a file once is a Tuesday afternoon. Keeping the split from drifting back into a mess over the next two hundred commits is the part nobody has packaged.

## The Project

The core idea is a classifier plus a regeneration guard, not just a one-time file split. A CLI (and a companion skill for the one-shot version) parses an existing monolithic rules file and sorts every line into **stable** — build flags, test commands, lint boundaries, naming conventions, trade-off priorities, anything that rarely changes — or **volatile** — dated TODOs, "currently working on" notes, file-count or status snapshots, anything that was true once and is now stale. The stable lines stay in a small, sacred `CLAUDE.md`. The volatile lines move to a separate `STATE.md` that the tool regenerates on a schedule or git hook, pulled from live repo signals — git log, test/lint exit codes, open-PR and TODO scanners — instead of being hand-edited into staleness again.

The genuinely hard part isn't the first split. It's a drift guard that diffs every regeneration pass and flags anything that looks like it silently swallowed a stable rule into the auto-overwritten file, and that stops the regenerated file from growing without bound either. Get that wrong and you've built a tool that quietly deletes someone's hand-written invariant six weeks after they forgot it was there — worse than the manual mess it replaced.

## Tangible Impact

**Population**: Developers and small teams running AI coding agents (Claude Code, Codex, Cursor) against repos whose rules file has grown past the point of being hand-maintainable — concretely, the kind of team both evidenced Reddit threads describe: running local multi-agent pipelines where every fix gets appended and nothing is removed until the agent starts mis-following its own rules. This is a large and growing population given how widely `AGENTS.md`/`CLAUDE.md` conventions have been adopted across Claude Code, Codex, and Cursor users in 2026.
**Mechanism**: Today, teams either let the rules file grow until the agent starts "butchering" parts of it, or hand-roll a bespoke split (as both evidenced posters did) that nobody else can reuse and that drifts out of sync as soon as someone forgets to update it manually. A tool that performs the split once and then keeps the volatile half fresh automatically removes both the token tax of re-pasting a bloated file every request and the silent-misfollowing failure mode caused by stale or oversized rules.
**Measure**: (1) Rules-file token count before vs. after split, and the resulting per-request token-cost reduction. (2) Agent rule-adherence rate on a labeled set of "does the agent follow its own stated constraints" test prompts, before vs. after the split. (3) Drift incidents — cases where the regenerated `STATE.md` silently absorbed or lost a stable rule — caught by the guard vs. missed, on a multi-week simulated commit history.

## Try It

A companion skill exists at [`skills/rules-file-stable-volatile-splitter/`](../skills/rules-file-stable-volatile-splitter/): *"Splits a bloated AGENTS.md/CLAUDE.md into a trimmed stable rules file plus a draft STATE.md of volatile status content, flagging ambiguous lines for human confirmation. Use when a rules file has grown past the point of being hand-maintainable and is starting to get mis-followed."*

This is the one-shot half of the idea — a cleanup pass, not the persistent auto-regeneration hook (that part needs a standing CLI/git-hook and stays project-shaped). To use it: paste the contents of `skills/rules-file-stable-volatile-splitter/README.md` into any AI chat tool along with the full current text of your `AGENTS.md`/`CLAUDE.md`, or drop the whole `skills/rules-file-stable-volatile-splitter/` folder into `~/.claude/skills/` if you're working in Claude Code. It won't touch your repo directly — it hands back a stable-file draft, a `STATE.md` draft, and a table of anything ambiguous for you to call, so you review and save the split yourself.

A few honest caveats. The classification itself is a judgment call — mis-filing a genuinely stable rule into the auto-regenerated file makes things worse than the status quo, not better, since the next regeneration pass can quietly overwrite it. The regeneration logic also has to generalize across very different repo shapes (a monorepo's git-log signal looks nothing like a small library's) without per-repo hand-tuning, or the "auto" part collapses back into manual maintenance. And it's worth naming the biggest competitive risk directly: Anthropic, OpenAI, or Cursor could ship a native stable/volatile convention straight into their own agent tooling at any point, since they own the rules-file format itself — the kind of risk an independent build in this space can't engineer around, only move faster than.
