# Re-Ground: Keeping Voice+Vision Agents From Forgetting What's On Screen

Ask a voice agent to walk someone through a multi-step software fix, or to read a screen aloud for a blind user, and it works beautifully for the first half-minute. Then something subtle breaks: the agent tells you to click a button that moved three steps ago, or describes a layout that's already changed. Nobody crashed. Nothing threw an error. The agent just quietly stopped seeing what's actually there — and because the failure looks exactly like the model "being wrong" rather than a known, named limitation, almost nobody has built the fix into a running system yet.

## The Gap

A 2026 production write-up from alexcloudstar.com states it plainly: continuous video/screen understanding in a multimodal agent "gets weaker in longer continuous sessions, especially after roughly 30 seconds." That's not a vague vibe — it's a measured, named degradation window from someone running these agents in production. And the research world has already proven the fix pattern works: ViSAGE's entity-anchoring approach reports 79.1% accuracy against 74.2% and 61.8% baselines on Video-MME-long, and LensWalk, VideoBrain, VideoExplorer, and APVR each independently validate adaptive or query-driven re-sampling as a way to stop this decay. Five separate research threads converging on the same failure mode is a strong signal the problem is real and the fix pattern is sound.

What's missing is the boring, load-bearing part: none of this lives inside an actual running agent. Every one of those results was evaluated offline, against a fixed video corpus, with no real-time constraint. Nobody has wired "periodically re-ground the model before it drifts" into the actual turn-by-turn loop of a live voice+vision session, where the system has to decide, on the fly and inside a latency budget, whether and what to re-sample right now.

## The Project

Re-Ground is a middleware scheduler that sits inside a voice+vision agent's session loop and periodically re-anchors its visual context before the ~30-second window where things start to slip. At each anchor point it re-samples key frames and re-injects a compact summary of what's changed since the last anchor — effectively resetting the model's internal "clock" on context staleness. Rather than firing on a dumb fixed timer, it adapts its cadence to what's actually happening on screen: faster re-anchoring during a burst of on-screen change, slower during a static view, borrowing exactly the adaptive-re-sampling logic that LensWalk and VideoExplorer already validated offline — except running it live, in the loop, during a real call.

The pieces: a frame-change detector that drives the adaptive cadence, a re-anchoring prompt/summary injector, a session-level diff log of "what's changed since the last anchor" for debugging, and an evaluation harness built from real multi-minute screen-share-plus-voice sessions that measures task accuracy before and after the 30-second mark, with and without re-anchoring turned on.

## Tangible Impact

**Population**: users of voice-driven screen-sharing support, walkthrough, and accessibility agents whose sessions routinely run past 30 seconds — multi-step software troubleshooting calls, live tutoring/onboarding walkthroughs, and voice-first screen-reading assistance for blind and low-vision users (the same population named in this repo's published "Beyond the Pilot" voice-first browsing idea), all of which involve exactly the kind of extended, continuous visual engagement where this digest's cited degradation window becomes operationally relevant rather than a benchmark footnote.
**Mechanism**: without re-anchoring, a session that starts accurate degrades silently past 30 seconds, so the agent starts giving instructions based on stale on-screen state — telling a user to click a button that's no longer there, or describing a screen that's already changed — which is indistinguishable to the user from the agent simply being wrong, driving repeated corrections, abandoned self-service sessions, or (for accessibility users with no independent way to verify the screen state themselves) real navigation errors.
**Measure**: task accuracy on a fixed benchmark of real multi-minute screen-share sessions, measured in the pre-30s window vs. post-30s window, with and without re-anchoring; rate of user-initiated corrections ("that's not what's on my screen") per session length bucket; added latency per re-anchoring event (must stay inside the voice turn's latency budget to be viable).

## Try It

A companion skill, [`skills/voice-vision-session-reanchoring-middleware/`](../skills/voice-vision-session-reanchoring-middleware/), handles the design step that comes before anyone builds the live scheduler. Its one-line description: "Reviews a voice+vision agent's architecture (session length, what it watches, how fast the screen/scene changes, latency budget) and produces a visual-grounding degradation risk estimate with a recommended re-anchoring cadence and payload — the design step before wiring up a live re-anchoring scheduler."

Hand it a description of your agent — typical session length, what it's watching, how fast the screen changes, your latency budget — and it comes back with a risk read, a recommended cadence (fixed fallback plus an adaptive rule), what each anchor should contain, and an evaluation plan to confirm the recommendation against your own sessions. It runs on manual input only; it doesn't read a live video stream itself, that's the runtime middleware's job. To use it: paste the contents of `skills/voice-vision-session-reanchoring-middleware/README.md` into any AI chat tool as a prompt, or, if you use Claude Code, drop the whole `voice-vision-session-reanchoring-middleware/` folder into `~/.claude/skills/`.

Worth noting honestly: the 30-second figure behind all of this comes from one practitioner's testing, not a peer-reviewed benchmark, and if the underlying multimodal models' native context handling improves enough in the near term, the need for this middleware could shrink fast. Both the skill and the project treat that 30-second number as a flag to validate, not a constant to build on faith — which is exactly why the evaluation harness exists in the first place.
