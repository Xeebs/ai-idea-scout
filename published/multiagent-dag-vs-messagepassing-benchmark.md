# Orchestration Face-Off: A Bring-Your-Own-Tasks Benchmark for DAG Planners vs. Message-Passing Agents

Pick an architecture for your multi-agent system and you're picking blind. Teams building on LangGraph, CrewAI, or AutoGen choose between a DAG planner/replanner — an explicit planner that emits a subtask graph and revises it on failure — and free-form peer message-passing, where agents negotiate and hand off work with no pre-committed plan. Right now that choice gets made by whichever blog post's prose argument sounded more convincing, not by a number.

## The Gap

Someone on r/AI_Agents described a DAG-based planner/replanner design and asked the obvious next question: has anyone benchmarked this against message-passing approaches? Nobody had an answer to point to. In the same 30-day window, the single highest-engagement item in the whole research run was an HN post, "Building a Multi-Agent System from Scratch: Architecture Patterns" (106 points, 45 comments) — directly about comparing architecture patterns, and still landing without resolving which one actually wins on real tasks.

The frustrating part is that half the work already exists. Three separate 2026 papers — OrchBench (arXiv:2607.25656), VMAO (arXiv:2603.11445), and an enterprise typed-DAG paper (arXiv:2606.20058) — each evaluate a DAG planner/replanner design on its own terms. None of them, or anything else a `gh search repos "multi-agent DAG planner"` or a web search for "DAG orchestration vs message passing benchmark" could surface, runs the same tasks through both architectures on the same models and tools to produce an actual head-to-head. The academic groundwork for one side of the comparison is sitting there, unmatched.

## The Project

This is a benchmark harness, not a one-shot verdict. A team supplies its own multi-step task suite — the same tasks it actually cares about — and the harness runs it through two reference implementations built on identical underlying scaffolding: one model config, one tool-calling layer, so the comparison isolates architecture choice rather than implementation quality. On one side, a DAG planner/replanner: a planner emits a subtask graph, a replanner revises it when something fails. On the other, free-form peer message-passing: agents negotiate and hand off work via unstructured turn-taking with no pre-committed plan.

Both architectures get built to a comparable quality bar — deliberately, because a strawman on either side makes the whole comparison worthless — and scored on identical tasks for success rate, total cost, wall-clock latency, and a tagged failure-mode breakdown: stuck loops, wrong subtask ordering, miscommunicated handoffs, premature termination. The centerpiece isn't a leaderboard of someone else's self-reported numbers; it's the two well-built reference implementations plus the scoring harness that makes them comparable at all. Components: two reference agent implementations sharing one tool-calling layer and base model config; a task-suite ingestion format (prompt plus rubric or expected-output per task); a scoring runner computing success rate, cost, latency, and failure-mode tags per architecture; and a comparison report generator.

## Tangible Impact

**Population**: Engineering teams building custom multi-agent pipelines on frameworks like LangGraph, CrewAI, and AutoGen who are choosing between a DAG/plan-based orchestration style and free-form peer message-passing before committing engineering time — concretely the same cohort visible in the digest's r/AI_Agents thread, the 45-comment HN architecture-patterns discussion, and the broader base of teams represented by LangGraph's and CrewAI's combined installed base (each in the tens of thousands of GitHub stars), most of whom currently pick an architecture from a blog post's prose argument rather than a number.
**Mechanism**: Today, a team choosing between these two architectures has to trust a blog author's qualitative argument or build both themselves to find out — an expensive, rarely-done experiment, so most teams commit to one architecture based on which pattern the tutorial they read happened to use. A harness that runs their own tasks through both reference architectures turns that choice into a measured decision made before most of the pipeline is built, instead of a rebuild discovered is needed after the system is in production.
**Measure**: (1) Success-rate delta between the two architectures on a pilot team's own task suite, with the failure-mode breakdown attributing *why* one won. (2) Cost and wall-clock latency delta per completed task between architectures on the same suite. (3) Number of pilot teams whose stated pre-benchmark architecture preference flips after seeing their own results, tracked across the first 10-15 teams who run the harness.

## Try It

This one doesn't have a Claude Code skill companion — it's flagged `Format: PROJECT` deliberately. The whole point of the comparison is isolating architecture from implementation quality on *your* tasks with real reference builds, which isn't something a prompt template can shortcut; a skill version would just be a thin wrapper around someone's opinion, which is exactly the problem this project exists to fix.

To try the idea in its current form: bring your own 10-30 task multi-step task suite with a scoring rubric or expected-output checklist per task (that's the whole data requirement — no external connector needed, because the thing being measured is your own workload). The MVP sketch in the idea file is buildable in 3-4 weeks by 1-2 people on a single model/tool-calling stack, using LangGraph primitives for the DAG side and a bare message-passing loop for the peer-chat side, validated first against 2-3 borrowed public task domains before pointing it at a real pilot team's tasks.

## Worth Knowing Before You Build This

Any single pair of reference implementations is contestable as not representative of "the" DAG approach or "the" message-passing approach — the bring-your-own-task-suite design sidesteps the worst of that, but the reference implementations themselves still have to be defensibly well-built on both sides, or a loss on either side gets dismissed as a strawman. Parity of implementation effort between the two architectures is the hardest part of this build, not the scoring logic — a badly-tuned DAG planner or an unusually disciplined message-passing protocol could swing results either way regardless of which architecture is actually better. And there's a real chance one of the three academic groups already cited — OrchBench, VMAO, or the enterprise typed-DAG paper's authors — runs this exact comparison first, since all three already have one half of the harness built. Multi-agent orchestration patterns are also still moving fast enough that a one-time benchmark snapshot would go stale quickly, which is the whole argument for the harness itself — re-runnable against new task suites and new reference implementations — being the durable deliverable, not any single published number.
