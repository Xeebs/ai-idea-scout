# Tool Hold: A Mid-Tool-Call Interruption Disposition Engine for Voice Agents

A caller interrupts a voice agent mid-sentence to correct a mistake — "wait, no, Tuesday, not Wednesday" — and somewhere in the backend, a reschedule call that was already in flight either finishes anyway, silently, or gets yanked without anyone checking what state it left things in. Every voice-agent vendor has solved the easy half of barge-in: stop the audio fast. Almost none of them have agreed on what to do with the tool call still running underneath it.

## The Gap

Soniox's wiki states the problem plainly: "the orchestrator has to handle an interruption that arrives while a tool call is still in flight." FutureAGI's barge-in guide puts a hard number on the half everyone *has* solved — TTS audio has to stop within 60ms of an interruption or the agent reads as broken — and a Quiq blog post is titled, bluntly, "why the interruption problem is architecture," not a solved library feature. Multiple vendor blogs re-explain this same problem from scratch across 2026, which is the pattern of a shared, unresolved gap, not a shared solution everyone's quietly converged on.

It's not that nobody's built barge-in tooling — `rogerchappel/bargekit` ships local-first VAD, barge-in, and turn-taking primitives; `rmsdev0/telnyx-onset` benchmarks barge-in latency; `Suman1108-beep/livekit-barge-in-agent` exists too. Framework docs from Pydantic AI, Smallest.ai, and NVIDIA's voice-agent reference blueprint all cover stopping the audio. But ask what happens to the backend tool call underneath that audio, and they disagree or go silent: Smallest.ai's docs let it finish; another SDK's docs say cancel-and-discard; NVIDIA's blueprint doesn't mention tool calls at all. Several turn-taking libraries exist. None of them resolves the actual decision.

## The Project

Tool Hold is a disposition engine that sits alongside a voice agent's tool-execution layer. On every barge-in event, it looks up a per-tool policy — declared once at config time, not improvised mid-call — and decides what happens to whatever was already running: let it finish silently and cache the result for later use, cancel it immediately and discard any partial result, or let it finish but re-confirm with the caller before trusting it, in case their intent changed in the meantime.

The policy runs off tool metadata a team already has to think through anyway — idempotent vs. side-effecting, cheap vs. expensive, cacheable vs. not — rather than a single blanket rule applied to every tool call regardless of what it actually does. Every decision gets logged, so a team can audit afterward exactly why a given call was kept, cancelled, or held for confirmation.

It's built from four pieces: a tool-metadata schema (idempotency, cost, cacheability, staleness tolerance), a decision engine that consumes barge-in events against in-flight call state, a short-TTL result cache for the "finish silently, use later if still relevant" path, and a decision log for post-call debugging. It ships as middleware for the frameworks — LiveKit Agents, Pipecat — that now expose both tool-call lifecycle and barge-in events in the same event loop, which is what makes this a cross-cutting plugin instead of a framework fork.

## Tangible Impact

**Population**: callers to AI voice agents that execute backend lookups or transactions mid-call — account lookups, appointment rescheduling, order-status checks, benefits eligibility checks — in the same high-volume segment PolyAI measures a roughly 1-in-5 barge-in rate for, and which Forrester's 2026 Wave reports now carries ~19% of inbound contact-center volume (up from 6% in 2024). The overlap of "calls with a barge-in" and "calls where a tool was mid-flight when it happened" is the population this specifically targets — a meaningful slice of every deployment that both performs real backend actions and gets interrupted regularly.
**Mechanism**: today a mishandled mid-tool-call interruption either silently discards a cheap, still-useful lookup result (wasting the latency/cost already spent and forcing a repeat round-trip) or, worse, commits a side-effecting action the caller just tried to correct (e.g., proceeding with a reschedule to the wrong time after the caller interrupted to change it). A declared per-tool policy stops both failure modes by making the disposition decision explicit and testable instead of accidental.
**Measure**: rate of "wasted re-fetch" (a cancelled call that, re-run, returns an identical result) before vs. after; rate of a side-effecting action completing after a caller's correction attempt (the safety-critical failure mode, target: zero in a labeled test suite); call-completion time delta on calls involving at least one mid-tool-call interruption.

## Risks & Open Questions

Getting the side-effecting/idempotent classification wrong for even one tool is the dominant risk here — a misclassified payment or booking tool that's allowed to "finish silently" is the exact harm this exists to prevent. Caching a finished-but-discarded result and reusing it later also risks staleness if the caller's intent genuinely changed between the interruption and the next turn; the "finish-then-confirm" policy exists for that case but adds a conversational step some teams will want to skip. There's a real chance a framework vendor — LiveKit, Pipecat — ships its own opinionated default disposition policy before an independent, configurable engine gains any adoption, so the differentiation has to be the per-tool declarative policy itself, not just "we handle it, trust us." And none of this matters if barge-in detection isn't reliable in the first place — this engine inherits whatever error rate sits upstream of it.
