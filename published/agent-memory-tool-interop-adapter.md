# Memory Mesh: A Universal Adapter Layer Across Fragmented Agent Memory Tools

Pick any three agent-memory tools shipping right now and you'll get three incompatible answers to the same question: where does this fact live, and how do I get it back out? Mem0, Letta, Zep, Cognee, Supermemory — each is a credible product solving a slice of memory and retrieval well, and none of them talk to each other. A team building a real agent ends up either betting everything on one vendor's weakest capability, or hand-writing glue code to bolt two of them together and praying the two don't disagree about the same fact at the same time.

## The Gap

A practitioner on r/ContextEngineering put it bluntly after spending close to a year building their own memory infrastructure from scratch and clearing 99% recall on their own benchmark: "There are dozens of memory management tools available today... they are scattered. Segmented. They solve the memory and retrieval problems but they solve specific issues and one is better than the other." That's not an isolated complaint. A WebSearch pass turned up at least eight actively maintained, non-interoperable tools — Mem0, Letta, Supermemory, Zep, Cognee, Hindsight, OpenMemory, and plain pgvector-on-Postgres — each with its own schema, API, and retrieval semantics, and no sign of the category consolidating. The only things calling themselves "unification" are vendor comparison posts that pick a winner rather than bridge the gap, one enterprise-only cross-tool memory graph (Sentra) that doesn't touch the open-source/indie-builder case, and a competitor's self-promotional "portability" blog post. Nothing lets a team actually combine two of these tools without reconciling two different data models by hand.

## The Project

The fix isn't another memory store — it's a thin, open-source translation layer sitting on top of the ones that already exist. Call it a memory mesh: one consistent interface — `remember(fact, type, ttl, scope)` and `recall(query, type, scope)` — that routes each call to whichever backend a team has declared is best suited for that memory type, via a config they write once instead of integration code they maintain forever. Underneath, per-backend adapters translate that common interface into each tool's native calls (Mem0, Letta, Zep, and Cognee to start, with Supermemory as the thinner-documented stretch target), and a reconciliation layer handles the genuinely hard part: what happens when two backends both have an opinion about the same fact — say, Zep's temporal graph and Mem0's fact store disagreeing about "what's the user's current plan" — by deferring to whichever backend the config marks authoritative for that memory type.

The routing-and-reconciliation layer is the entire product here, not a feature bolted onto something else. The MVP scopes this down deliberately: adapters for just Mem0 and Zep — the two most architecturally different of the bunch, a fast key-fact store versus a temporal graph — a single declarative config format, and one conflict-resolution strategy (authoritative-backend-wins). The validating experiment is concrete: wire both into a toy agent that needs "what's the user's name" (Mem0) and "what changed between session 3 and session 7" (Zep), confirm a single `recall()` call routes correctly, and confirm a deliberately conflicting write resolves per config instead of silently picking whichever backend happened to answer first.

## Tangible Impact

**Population**: engineering teams building production AI agents with multiple distinct memory needs (temporal/session history, fast fact recall, long-horizon narrative summarization) who today either over-commit to a single vendor's memory API and accept its weakest capability, or hand-write bespoke glue code to run two tools side by side — exactly the position the digest's evidenced practitioner was in before building their own stack from scratch. This is the same population every memory-tool vendor is competing for; the gap is that none of them currently lets a team combine two vendors instead of picking one.
**Mechanism**: a team that would otherwise spend 2-4 weeks hand-building glue code (as the digest's practitioner did, for a year, to get there) instead configures a declarative mapping and gets a working multi-backend memory layer in under a day; switching or adding a backend later is a config change and a migration-tool run instead of a rewrite.
**Measure**: time to add a second memory backend to an existing agent (target: under 1 day vs. the multi-week bespoke-integration baseline implied by the digest's evidence); number of lines of custom adapter code a team has to write themselves (target: near zero for the four mature backends); successful reconciliation accuracy when two backends disagree about the same fact, measured against a hand-labeled test set of deliberately conflicting writes.

## Try It

A companion skill, `skills/agent-memory-tool-interop-adapter/` ("Memory Stack Advisor"), is already written: it "recommends which agent-memory backend(s) (Mem0, Letta, Zep, Cognee, Supermemory) to use for each distinct memory need an AI agent has, flags conflicts between backends, and outputs a ready-to-use declarative routing config." It's a design/decision aid for the moment *before* you commit to a memory architecture, not the runtime adapter itself — hand it a plain-language description of what your agent needs to remember and get back a routing config stub.

To use it: paste the contents of `skills/agent-memory-tool-interop-adapter/README.md` into any AI chat tool and describe your agent's memory needs, or drop the whole `skills/agent-memory-tool-interop-adapter/` folder into `~/.claude/skills/` if you're running Claude Code.

Worth knowing going in, honestly: if one of the larger, better-funded players in this space (Mem0 or Letta are the likeliest candidates) ships its own first-party adapter to a competitor, this project's value proposition shrinks fast to whatever's left in the long tail — that's the first thing worth re-checking on GitHub before sinking real engineering time into the runtime layer. The reconciliation logic is also the least precedented part of the whole idea; there's no existing literature on "which backend wins" when two memory systems disagree, so a wrong answer there is worse than shipping no unification at all.
