On November 11th, 2026, Datadog shipped a fix for its own product that admitted something uncomfortable: LLM evaluation and experiment data riding inside a general-purpose APM trace can get silently truncated or dropped before anyone scores it. Not logged as an error. Not flagged anywhere. Just gone, quietly, because the pipeline it was traveling through was never designed to carry what an LLM eval payload actually looks like.

If a funded, maintained observability vendor only caught this in its own pipeline days before this writeup, the obvious next question is: whose pipeline hasn't caught it yet?

## The Gap

The fix landed in `dd-trace-py` PR #21690, titled "fix(llmobs): send experiment spans directly and truncate oversized events field by field." The PR description is blunt about the failure mode it's closing: "Experiment spans can be silently lost when they ride inside APM traces. By default... an experiment row's LLMObs event is attached to the APM span. It then inherits every limit and drop in the APM pipeline." That's the whole bug in one sentence — eval data was never given its own lane, so it quietly absorbed whatever size limits the general tracing pipeline happened to enforce.

Datadog isn't the only place this shows up, either — it's just the one that got publicly fixed. Web search turns up the same root cause, patched differently and separately, across the rest of the observability landscape: Langfuse caps ingested events at roughly 2MB and rejects anything larger outright. Groundcover truncates spans past 10KB. Lumigo cuts any single field longer than 2KB. Braintrust caps OTLP payloads at 10MB. A live GitHub issue on the Vercel AI SDK describes span attributes getting truncated below the value a developer explicitly configured. Every one of these is a vendor-specific patch for the same underlying mismatch — eval payloads (long prompts, verbose judge rationales, multi-turn transcripts) are shaped nothing like the short request/response spans APM tooling was built for, and nobody has shipped a general, cross-vendor answer to it. Just narrow fixes, arriving one outage-shaped realization at a time.

Which means any team that bolted LLM eval tracing onto an already-deployed APM stack — which is most teams, since incumbent APM adoption (Datadog alone claims over 27,000 customers) predates the LLM-eval tooling wave by years — has no way to know today whether the eval dashboard they trust is actually complete.

## The Project

A vendor-agnostic diagnostic-and-mitigation pair, built around the exact failure Datadog just admitted to.

The diagnostic half fires synthetic, deliberately oversized eval-shaped payloads — long prompts, verbose judge rationales, multi-turn transcripts — through a team's real OTel/APM export path, then diffs what was sent against what actually arrived. It cross-references the result against the per-vendor limits already catalogued above (2MB/event, 10KB/span, 2KB/field, and so on) to tell a team exactly what's being silently truncated or dropped, and at which stage of their own pipeline it's happening. No more trusting the dashboard on faith.

The mitigation half generalizes what Datadog just shipped for itself into something stack-agnostic: a drop-in OpenTelemetry span-processor that detects when a span is eval- or experiment-shaped (via `gen_ai.*` / LLMObs-style attributes) and reroutes it onto a dedicated side-channel export path — either a direct-send route or an offload-to-blob-with-reference pattern — bypassing whatever limits the general APM pipeline inherited from a world where spans were short. Datadog built this for Datadog. Nobody's built it for everyone else.

## Tangible Impact

**Population**: Engineering teams who bolted LLM eval/experiment tracing onto an already-deployed general-purpose APM or OTel collector (Datadog, New Relic, Grafana/Tempo, a self-managed OTel collector) instead of adopting a dedicated LLM-eval platform from day one — realistically most mid-size engineering orgs shipping LLM features, since incumbent APM adoption (Datadog alone reports over 27,000 customers) predates the LLM-eval tooling wave by years, so the default path for most teams is "extend what we already pay for," not "switch vendors."
**Mechanism**: Today these teams trust their eval dashboards and judge scores as complete, when in fact a meaningful share of long prompts, completions, or judge rationales were silently truncated or dropped before scoring — exactly DataDog's own admitted failure mode. The diagnostic turns an invisible assumption ("our eval data is intact") into a measured fact before anyone trusts a score built on it; the side-channel exporter then removes the root cause going forward, independent of which APM vendor the team is locked into.
**Measure**: (1) % of synthetic oversized payloads correctly flagged as truncated/dropped across tested backends, targeting ~100% detection matched against each vendor's documented cap. (2) Bytes of eval payload preserved after deploying the side-channel exporter vs. the measured baseline loss on the same traffic. (3) Number of backtested judge-score discrepancies (score computed on a truncated payload vs. the same input replayed intact) a pilot team's historical traces reveal once probed.

## Try It

A companion Claude Code skill already exists at [`skills/eval-telemetry-apm-silent-drop-detector/`](../skills/eval-telemetry-apm-silent-drop-detector/) — a one-time, description-based audit, distinct from the runtime diagnostic/exporter pair described above. Its one-line description: "Audits a team's description of its LLM eval/experiment tracing setup (vendor, SDK/collector version, custom span-processor config) against known per-vendor payload-size limits to flag which attributes (long prompts, judge rationales, multi-turn transcripts) are likely being silently truncated or dropped before scoring. Use when someone asks 'is our eval data actually intact?' or is about to trust eval/experiment scores built on top of a general-purpose APM/OTel pipeline they didn't design for LLM payloads."

To use it: paste the skill's `README.md` into any AI chat tool along with a description of your tracing setup — vendor/SDK/collector name and version, any custom span-processor or exporter config, and a rough sense of your typical payload sizes — or drop the `skills/eval-telemetry-apm-silent-drop-detector/` folder into `~/.claude/skills/` if you're working in Claude Code. It matches your stack against the catalogued per-vendor limits, flags architecture-level risk (are eval spans riding inside the general APM pipeline with no separate path?), and ranks mitigations by effort — but it will never tell you your data is intact. It's explicit that only an actual synthetic-payload probe through your live pipeline, which the skill itself does not run, can confirm that.

Worth knowing before you build on this: every major APM/observability vendor could ship Datadog's own fix pattern (a dedicated direct-send path for LLM spans) natively within months, which would narrow this project to a stopgap for teams on slower release cycles. And firing synthetic oversized payloads into a live production pipeline needs careful scoping — tagged, sandboxed traffic only — so the diagnostic doesn't itself become the cost or noise problem it's meant to catch.
