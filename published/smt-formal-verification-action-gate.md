# Hard Gate: A Portable SMT Verification Layer for Agent Actions, Benchmarked Against LLM-as-Judge

Ask an LLM-as-judge whether an agent's proposed action is okay to execute and you get a probability dressed up as a verdict. For a chatbot reply, that's fine. For a `transfer_funds` call, an IAM change, or a clinical order, "probably fine" is not a sentence an auditor wants to read in an incident report. There is a deterministic alternative — solver-based, SAT-or-UNSAT, no vibes — and the last 30 days of community and vendor activity show real people reaching for it. Nobody has packaged it as something portable, and nobody has run the one experiment that would tell teams whether it's worth the switch.

## The Gap

The clearest signal is a small open-source project fixing its own bugs in public: `QWED-AI/qwed-verification`'s November 2026 pull requests (#604, #605) patch cases where its verifier reported the wrong verdict — "verify-process is UNVERIFIABLE and DENY, never VERIFIED" — while the project's own enforcement checklist insists on "no path bypasses verification" and "fail closed: all failure paths block, not degrade." That is a team that wants deterministic, SAT/UNSAT-style gating badly enough to build it themselves, warts and all, for one project.

The appetite doesn't stop at one hobby repo. A March 2026 academic paper evaluates SMT/Z3-based policy checking for tool-using LLM agents on TauBench. AWS shipped a real, production feature — Bedrock's Automated Reasoning checks, built on its Cedar policy layer — squarely aimed at the regulated-industry buyer who needs an auditable admit/deny decision, not a probabilistic score. And there's already a commercial product listing, PolicyLayer, offering an SMT-backed `check_action` gate. That's an academic paper, a funded cloud vendor, and a startup, independently arriving at the same architecture inside the same month — a strong tell that the pattern is right.

What's missing is just as telling. AWS's own documentation concedes the step that turns a plain-English policy into a formal constraint is itself LLM-assisted and "unproven at scale" — the exact weak point that AWS, of all companies, is naming out loud. Nobody has built a version of this that isn't locked to one cloud vendor. And nobody — not the academic paper, not AWS, not PolicyLayer — has run the comparison that would actually tell a team whether solver-gating is worth adopting: a head-to-head benchmark against LLM-as-judge on the identical set of proposed actions, measuring catch rate, false positives, latency, and cost side by side.

## The Project

A standalone SMT-backed (Z3) action gate that sits in front of any agent's tool-call execution path, built around two equally central pieces.

The gate itself: teams author policy as explicit formal constraints — "a `transfer_funds` call is admissible only if `amount <= daily_limit AND recipient IN approved_list`" — compiled through a minimal declarative DSL into Z3 constraints. Every proposed action gets checked deterministically before it executes and comes back SAT (admit) or UNSAT (deny, with the specific violated constraint named, not a bare "denied"). Any timeout or evaluation error fails closed — no path silently defaults to allow, the same non-negotiable that qwed-verification's own checklist insists on.

The second piece is the part nobody has built: a dual-track benchmark harness that runs the identical set of proposed actions through both the solver gate and an LLM-as-judge baseline, and reports catch rate, false-positive rate, latency, and cost for each, side by side. That comparison is the thing every one of the projects above skipped — the evidence a team would actually need to decide where formal gating earns its keep and where probabilistic judging still has to carry the load.

Rounding it out: adapters for 3-4 common tool-call interception points (an MCP server wrapper, LangChain/CrewAI/Claude Code hooks), so the gate drops into whatever stack a team already runs instead of requiring a rewrite.

## Tangible Impact

**Population**: Teams building agents in domains where "mostly right most of the time" is not an acceptable bar — financial-services agents executing transfers or trades, healthcare agents ordering clinical actions, infrastructure agents making IAM/deploy changes — where an auditable, deterministic admit/deny decision is a compliance or safety requirement, not a nice-to-have. This is explicitly the buyer AWS itself targets with Bedrock's Automated Reasoning checks' regulated-industry marketing, minus the lock-in to one agent stack.
**Mechanism**: Today these teams either accept LLM-as-judge's probabilistic risk on actions that genuinely need a hard yes/no (unacceptable for an auditor or a regulator), lock into AWS's proprietary Bedrock-only feature whose translation step AWS itself flags as unproven, or hand-build a bespoke SMT layer in-house the way qwed-verification is doing in public, bugs and all. A portable, benchmarked solver gate gives them a vendor-neutral, auditable, fail-closed verification step plus hard evidence of exactly where it outperforms or falls short of LLM-as-judge on their own action set.
**Measure**: (1) SAT/UNSAT decision accuracy against a hand-labeled test set of admissible/non-admissible proposed actions, targeting near-100% given formally expressible rules, benchmarked against the LLM-as-judge baseline's measured error rate on the identical set. (2) False-admit rate on deliberately violating actions = 0% under adversarial testing (the fail-closed requirement). (3) Per-decision latency and cost versus an LLM-as-judge call on the same action, establishing whether solver-gating is cheap enough to run on every action rather than a sampled subset.

## Try It

No companion skill ships with this idea. A skill angle was explored — drafting the formal constraint for a plain-English policy rule and flagging what resists clean translation — but the skill-synthesizer's search found it NOVELTY_FAIL against two shipped equivalents already doing the same decompose/route/flag job: AWS's own Dogwood/AgentCore Policy Authoring tooling and a third-party `rule-spec-drafting` skill from Corsa. The runtime solver-gate described above is unaffected by that — its differentiator is portability and the benchmark evidence, not the drafting step — so it stays a project to build, not a skill to install today.

Worth knowing before you build: natural-language policies often resist clean formal reduction — the exact bottleneck AWS's own caveat names — so the translation problem could end up the real limiting factor rather than the solver itself. AWS or another well-funded agent-security vendor could generalize their own formal-verification feature across frameworks before this ships, given they've already done the hard solver-integration work. And solver-gating structurally can't catch "this action is a bad idea for reasons outside the ruleset" — it complements LLM-as-judge rather than replacing it, which qwed-verification's own ongoing correctness bugs are a live reminder of: this stays a correctness-hard problem even scoped to one small project, and a generalized library inherits that risk at a larger surface area.
