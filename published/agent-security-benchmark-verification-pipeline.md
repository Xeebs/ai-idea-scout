# Show Your Work: An Independent Verification Pipeline for Self-Reported Agent-Security Benchmark Claims

Every agent-security vendor publishes the same kind of number: a clean, round, reassuring percentage. "100% unsafe-action prevention across 22 agentic scenarios." "An audited 0.00% violation rate." Nobody checks these numbers before a buying decision gets made — and when someone finally did check, at scale, the result was damning: a third-party survey of 100 agents found that 83% of claimed defenses carried zero independent verification. The industry has been grading its own homework, and almost nobody has been asking for the work shown.

## The Gap

The clearest tell comes from inside the industry's own tooling. `icecreamyoubest/awesome-agentic-ai-security`'s automated update-review bot, in PR #28, states plainly that it "proposes reviewable evidence changes only; maintainers should verify claims before merging" — even the bot built to track this space defers verification to a human, rather than attempting it itself. Meanwhile the claims keep rolling in from the vendor side: a tool reporting "100% unsafe action prevention across 22 agentic scenarios" with no public dataset behind it, another claiming "an audited 0.00% violation rate" that no one could trace to a primary source. AIRQ's third-party survey of 100 agents turned the anecdote into a statistic: 83% of claimed defenses have no independent verification at all. The "has anyone actually checked this" step is, industry-wide, explicitly unautomated.

To be fair, the field isn't standing still. AIUC-1 now offers accredited-auditor certification (Sierra went through a Schellman audit to get it). An academic audit protocol exists (arXiv 2609.18272). OpenZeppelin manually audited OpenAI's own EVMbench and found data contamination in it — proof that even a frontier lab's self-published benchmark isn't immune. But every one of these efforts is manual, accredited-auditor-driven, or a one-off research pass. None of them is a tool that takes a claim as input and automatically re-runs it. That's the gap: four independent threads (AIUC-1, AIRQ, the academic protocol, OpenZeppelin) all converging on the same unsolved problem from different directions, and nobody has automated the fix.

## The Project

The pipeline takes a published agent-security benchmark claim as input — a vendor blog post, a README table, a paper excerpt — and does the thing nobody currently automates: it extracts the claimed metric, the scenario count, and whatever test methodology is described, then tries to locate or reconstruct the actual underlying test scenarios. Sometimes that's a linked public dataset. Sometimes it's a named agentic-safety benchmark suite. Sometimes, when nothing public exists, it's generating comparable adversarial scenarios from the description alone.

Once it has a scenario set, it re-runs the vendor's tool — where that tool is open-source or reachable via API — inside an isolated sandbox, because the test cases are adversarial by design and running them against anything live would be reckless. The output is a side-by-side "claimed vs. independently re-run" comparison, carrying an explicit confidence rating that reflects how much of the original methodology could be reconstructed exactly versus approximated. A claim with a public, well-documented dataset gets a high-confidence re-run; a claim with nothing but a one-line summary gets flagged as barely checkable — and that distinction is itself useful information for a buyer.

## Tangible Impact

**Population**: engineering and security teams evaluating which agent-security/guardrail tool to adopt, the same buyer population AIRQ's 100-agent survey covered, where 83% of claimed defenses carried zero independent verification at the time a buying decision was being made.
**Mechanism**: today a buyer either trusts a vendor's self-reported number outright or commissions a manual, accredited audit (AIUC-1-style — costly and slow, taking months). An automated re-run pipeline gives a fast, repeatable, confidence-rated second opinion on the specific published claim they're evaluating, closing the exact gap the awesome-list PR bot names as still manual, without requiring every buyer to become their own security auditor.
**Measure**: (1) the number of vendor claims the pipeline can fully or partially re-run vs. "unreconstructable" (where methodology is too opaque), as a coverage metric; (2) the delta between a vendor's claimed metric and the pipeline's independently-measured one on re-run cases — the thing buyers actually need to know; (3) time from "a vendor publishes a new claim" to "an independent re-run result exists" (target: days, not the months an accredited audit takes).

## Try It

There's no companion Claude Code skill shipped for this one yet — the project's core value depends on a sandboxed agent-execution environment to safely replay adversarial scenarios, infrastructure that doesn't exist as a lightweight paste-and-prompt wrapper. A future skill version is scoped as a lighter-weight due-diligence check: a buyer pastes or links one specific vendor claim before a purchase decision, and the skill assesses whether enough methodology detail exists to meaningfully check it, attempts a lightweight reconstruction of the described test conditions, and flags red flags — vague scenario counts, no linked dataset, metrics that don't match the described test. That's a one-shot sanity check, not the full automated re-run the project does; watch `skills/` in this repo for when it lands.

## The honest caveats

This idea comes with real open questions, not just upside. Most vendor claims won't come with enough methodology detail to reconstruct faithfully, which means the pipeline may spend most of its effort on claims it can only approximate — weakening the credibility of exactly the comparisons it exists to produce. Vendors could push back hard, or threaten legal action, over public "your claim doesn't hold up" comparisons, which means this needs a transparent, defensible, methodology-disclosure-first process from day one, not an afterthought. Safely re-running an adversarial benchmark requires a genuinely isolated sandbox, and building that correctly is itself a nontrivial, safety-relevant piece of engineering — not a side detail. And there's a real risk that a well-funded entrant like AIUC, or the awesome-list maintainers themselves, extends into automated re-testing once this gap is named this publicly, which would shrink the addressable opportunity for an independent project.

None of that makes the gap less real today. It just means whoever builds this needs to start small — one well-documented claim, reconstructed and re-run by hand first, before automating anything — exactly as the idea's own MVP sketch proposes.
