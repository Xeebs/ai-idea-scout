Most agent test suites only ever see the tools behave. The payment API returns a clean 200, the CRM answers in 40ms, the JSON always parses. Then one day in production the payment API times out, or returns a response missing the `amount` field, and the team finds out — in real time, in front of a user — whether their agent retries safely, surfaces a sane error, or quietly treats garbage as a real balance and keeps going.

## The Gap

A practitioner write-up (kunalganglani.com, "How to Do Agent Tool Call Failure Testing [2026 CI Harness]") describes hand-building exactly this kind of deterministic stub — injecting timeouts, HTTP 429s, and malformed responses in front of a multi-agent publishing pipeline's tools — specifically because the team's existing tests only ever exercised the happy path. That instinct has academic backing: the arXiv paper "Beyond Function Calling: Benchmarking Tool-Using Agents under Tool-Environment Unreliability" (arxiv.org/pdf/2606.25819) introduces ToolBench-X, a benchmark built around the same finding — agents that look fine against reliable tools fail once you inject recoverable hazards like timeouts, dropped specs, or malformed output, because what breaks is less the model's raw tool-use ability and more its hazard diagnosis and recovery.

Both sources point at the same hole: nobody has turned this into shared, adopted infrastructure. The practitioner's harness is a one-off, built for one pipeline and thrown away after. The arXiv paper is a benchmark proposal, not something a team drops into its own CI. Widening the search turns up real activity in the space — `deepankarm/agent-chaos`, `langchain-chaos-middleware`, `balagan-agent`, `agentfuzz`, and a chaos-testing module tucked inside AWS's `strands-agents/evals` — but each is either low-adoption (agent-chaos sits at 35 stars), narrow, or a sub-feature of a broader eval SDK rather than a dedicated, widely-used CI harness purpose-built for timeout/429/malformed-response injection. Several independent attempts, each solving a corner of the same problem, and none of them has become the thing everyone just installs.

## The Project

The project is a pytest/CI-integrated Python package that wraps the MCP SDK's transport layer with a small, deliberate fault-injection DSL: `inject_timeout(tool, after_ms)`, `inject_429(tool, retry_after)`, `inject_malformed(tool, shape)`. It sits in front of an agent's real tools — not mocks standing in for them — and lets a team trigger exactly the failure modes that show up in production, on command, in CI, before merge.

The harness alone isn't the point; the point is pairing fault injection with an assertion layer that checks the agent's *declared* recovery behavior per tool: does it retry with backoff instead of looping forever, does it surface a graceful message instead of an uncaught exception, and — the highest-severity failure mode — does it ever treat a malformed response as valid data and silently carry on with a fabricated result. That requires a per-tool recovery-policy spec, because "safe degradation" isn't universal: retrying a `get_balance` call on timeout is fine, retrying a `charge_card` call with no idempotency key is not. Four pieces make up the whole: the fault-injection DSL and transport interceptor, the per-tool recovery-policy spec, the pytest/CI plugin and assertion library, and a failure-mode report generator that turns a run into something a team can actually read.

## Tangible Impact

**Population**: engineering teams shipping tool-calling agents to production that depend on external APIs which can legitimately fail — grounded by LangChain's June 2026 practitioner survey finding 57.3% of respondents already have agents running in production, and by the arXiv/ToolFailBench research line finding agents that perform well against reliable tools fail under recoverable hazards like timeouts and malformed responses. This is a population of tens of thousands of teams now running tool-calling agents live, most of whom — per this digest's own cited practitioner write-up — are relying on happy-path testing alone today.

**Mechanism**: today an agent's tool-calling layer is tested, if at all, against a happy-path mock; teams discover its actual degradation behavior (sane retry vs. infinite loop, graceful failure vs. fabricated result treated as real) only when a real dependency times out or rate-limits in production. A deterministic stub that reliably injects these conditions on command turns "does this agent degrade safely" into a pre-merge, repeatable CI check instead of an incident post-mortem.

**Measure**: (1) count of unsafe-degradation bugs (infinite retry, fabricated-result-treated-as-real, uncaught exception reaching the user) caught in CI pre-merge vs. discovered in production, on pilot teams adopting the harness; (2) time to add a new fault scenario for a given tool vs. the hand-built bespoke harness described in the source write-up; (3) pass/fail stability of the same suite across 2–3 model families, since recovery behavior is partly a model-reasoning property, not purely a transport-layer one.

## Worth Weighing

This gap sits right next to the idea index's own `mcp-agent-tool-call-test-rig.md` — that project asserts call *order* against a recorded transport, this one injects synthetic failure conditions and asserts *recovery* behavior. Different failure class, but the overlap is close enough that the two need to stay clearly differentiated, even though they could plausibly share a transport-mocking layer. There's also a real risk this closes itself: AWS's `strands-agents/evals` chaos module already has 260+ stars and active maintenance, and could simply be extracted and generalized into a standalone package by a team that's already resourced to do it. And "safe degradation" is genuinely task-dependent — an infinite retry is sometimes correct — so the harness needs a declarative per-tool policy rather than a one-size-fits-all pass/fail, which is real design complexity beyond "just build a stub." Fault injection at the transport layer can be deterministic; what the model decides to do about it is not, which cuts against a clean "deterministic CI gate" pitch unless the two layers are scoped separately from the start.
