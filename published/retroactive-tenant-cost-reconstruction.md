Every multi-tenant LLM SaaS team eventually gets the same question from finance, a board member, or an angry customer disputing a bill: "what did this specific tenant actually cost us last quarter?" And every team that didn't tag `tenant_id` on every request from day one gets the same answer from the FinOps literature: you can't know. Not "it's hard" — "you cannot retroactively split traces by tenant." That's treated as the end of the conversation. It shouldn't be.

## The Gap

Multiple practitioner guides converge on the same flat statement: tenant-level LLM cost attribution only works if tenant IDs were tagged on every call at instrumentation time. A dev.to walkthrough on tracing per-request AI costs through multi-tenant gateways and a particula.tech piece on per-tenant LLM cost attribution both frame missing tenant tagging as an unrecoverable dead end rather than a forensic problem to be worked. That's a strange place for the conversation to stop, because the pain this creates is predictable and recurring: a small fraction of tenants typically drives a disproportionate share of spend, and teams usually only discover that fact after a cost spike or a billback dispute forces them to look — by which point months of untagged history already exist and the "just tag it going forward" advice is cold comfort for the period that already happened.

A search across GitHub for "per-tenant cost attribution," "LLM FinOps multi-tenant," and "LLM cost attribution tenant" turned up nothing better: a scatter of 0- and 1-star reference repos, all describing forward-looking instrumentation, none attempting a backfill from data that was never tagged. The closest thing to a "solution" found anywhere was a collector transform that tags *future* unlabeled spans with a sentinel — a fix for tomorrow's traces, not an answer for last quarter's.

## The Project

Cost Forensics is a one-time forensic reconstruction pass, not another instrumentation reminder. It ingests two things most teams already have sitting around even if they never thought to tag tenants: raw provider billing/usage exports (OpenAI's Usage API, Anthropic's Admin/usage API — both mature and documented today) and whatever request metadata their observability stack already captured by default — API keys, session IDs, timestamps, endpoint patterns — even though nobody thought to log `tenant_id` specifically.

The core move is refusing to collapse everything into one falsely-precise number. Instead it clusters requests by API-key exclusivity, session/timing correlation against known tenant activity windows, and endpoint-pattern matching (a webhook path that structurally encodes a tenant slug is as good as a label), and sorts the result into explicit confidence tiers: high (a uniquely-scoped key, or a self-identifying endpoint), medium (a timing cluster that lines up with one tenant's known window and no competitor active in it), low (a shared key or overlapping windows, allocated only proportionally), and — critically — an honest unattributed bucket that nothing gets forced into just to make the report look cleaner. Where a team happens to have even a short overlapping period where tenant tagging *did* exist, the tool masks it, reruns the reconstruction blind, and reports measured tier-by-tier accuracy against the real ground truth, turning the confidence tiers from an assertion into a calibrated number. Components: billing/usage API ingesters, a metadata correlator, a confidence-scoring model calibrated against any overlapping tagged period, and a reconstruction report that keeps high-, medium-, and low-confidence dollars visibly separate rather than blended.

## Tangible Impact

**Population**: Platform/finance engineering teams at multi-tenant SaaS companies offering LLM-powered features who didn't instrument tenant_id from day one — realistically most early-stage AI SaaS startups, since tenant-level cost tracking is a FinOps best practice teams adopt only after being burned, not before. A particularly acute case: companies approaching a board/investor review or a customer billback dispute who need a historical cost-per-customer number for a period that already passed.
**Mechanism**: Today these teams face a binary choice when tenant_id wasn't tagged historically — either tell stakeholders "we genuinely cannot know" for that period, or spend weeks manually cross-referencing API keys and logs by hand for a rough, undocumented guess. A forensic reconstruction tool turns that into a structured, confidence-scored report produced in hours, with an honest accounting of which dollars are solidly attributed versus statistically inferred, rather than either a false "we have no idea" or a false-precision single number.
**Measure**: (1) percentage of historical spend attributed at high confidence (clean API-key-to-tenant mapping) versus requiring statistical inference, on a pilot team's real billing export; (2) accuracy of the inferred (non-high-confidence) attribution when validated against a held-out period where tenant tagging actually existed, compared against the current alternative of zero attribution; (3) time to produce a usable historical cost-per-tenant report, dropping from "we can't do this" or weeks of manual cross-referencing to under a day.

The strongest honest counterpoint belongs here too, straight from the idea file's own risk list: the practitioner consensus this project is pushing back on isn't wrong for every team. If a team's API keys were never tenant-scoped and tenant sessions overlapped heavily, the tool's honest output for that period could legitimately be "low confidence across the board" — which is still more useful than silence, but it's not a universal fix, and confidence-scoring quality is the entire product. A tool that reports false confidence would be worse than today's honest "we don't know."
