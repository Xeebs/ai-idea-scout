On October 21, someone posted a modest write-up titled "What Claude Code's multi-agent code review costs and finds." Three points, four comments on Hacker News — the kind of thread that scrolls past in a second. But two weeks later, in an entirely separate research pass, the same exact question resurfaced independently: one team on GitHub was mid-pull-request, chaining three different review bots on top of a coding agent, when one of them stalled out — "paused because your workspace is out of credits." Two unrelated sightings of the same unanswered question, three weeks apart: does multi-agent code review actually pay for itself, and compared to what?

## The Gap

The honest answer right now is: nobody knows, and everyone is guessing from different, incompatible numbers. Qodo publishes a benchmark reporting recall, precision, and cost for its own product — numbers a vendor has every incentive to present favorably. Independent practitioners (Kilo, LeadDev, a Concordia University study on token allocation, a hyrax.dev write-up) have each measured something real but narrow: one team's repo, one configuration, one slice of the question. The Concordia study is the closest thing to a hard number in the whole pile — it found code review dominates 59.4% of token spend in a multi-agent coding pipeline — but it's a study of where the tokens go, not whether the defects caught were worth that spend. A GitHub search did turn up one genuine attempt at the comparison (PROrunner926/copilot-cache-scout, 114 stars), but it's a single project, not a standard other teams can run against their own code. Put plainly: a team deciding today whether to turn on multi-agent review has to choose between a vendor's self-graded homework and a stranger's blog post about a codebase that looks nothing like theirs.

That gap is getting more expensive to leave open, not less. Multi-agent review features are shipping by default across major tools right now, which means teams are making this adopt/skip call constantly, usually with nothing better than vibes and a vendor PDF.

## The Project

ReviewMeter is the benchmark that doesn't exist yet: an open, independently-run harness that takes a corpus of real pull requests with known, confirmed defects, runs them through several review configurations side by side — Claude Code's native multi-agent review, CodeRabbit, Qodo, a hand-built LangGraph pipeline, and a single-pass-LLM baseline — and reports tokens, latency, and defects caught/missed/false-positived in one table. Not five separate blog posts measuring five separate things; one methodology, applied consistently, with a neutral party running it instead of the vendor whose product is being scored.

The part that makes this more than an academic exercise is the "bring your own repo" mode: a team points the harness at their own pull request history instead of trusting that a benchmark built on someone else's codebase, language, and PR size transfers to theirs. The three load-bearing components are a curated PR corpus with ground-truth-labeled defects, a set of adapters so each review configuration plugs into the same harness, and a reporting layer that forces every configuration's output into the same cost/latency/defect-rate shape — so the comparison is actually apples to apples instead of each vendor's own preferred metric.

## Tangible Impact

**Population**: Engineering leads at small-to-mid-size software teams — the cohort generating both the HN writeup and the independent blog posts cited (Kilo, LeadDev, hyrax.dev) — deciding whether to adopt a multi-agent code-review product or pipeline, currently working only from vendor-marketed numbers or one team's informal blog post.

**Mechanism**: Today a team adopts or rejects multi-agent code review based on vendor claims or a single blog post that may not match their codebase, language, or PR size. An independent, re-runnable benchmark against the team's own PR history replaces "should we trust this vendor's number" with a measured cost-per-defect figure for their actual code, making the adoption decision evidence-based rather than marketing-based.

**Measure**: (1) Variance between vendor-claimed defect-catch rates and the benchmark's measured rates on the same PR corpus. (2) Cost-per-defect-caught (tokens+latency converted to $) across configurations, standardized for apples-to-apples comparison. (3) Number of teams that change their review-tool choice after running the benchmark against their own repo.

## Try It

A companion skill already exists at `skills/multiagent-code-review-cost-benchmark/`. Its one-line description: "Takes a team's description of their current PR-review setup plus a small sample of real recent PRs and produces a quick, honestly-caveated cost-vs-defect-catch estimate comparing their candidate multi-agent/AI code-review configuration against their current baseline, ending in a directional adopt/pilot/skip recommendation."

This is explicitly not the full harness — it's the five-minute gut-check you'd run before deciding whether the full benchmark is even worth building out. Hand it a description of your team's setup (size, stack, typical PR size, current review process) plus three to ten real recent PRs from your own repo — diffs, descriptions, and whatever defects you already know about — and it comes back with a confidence-capped recommendation: adopt, pilot further, or skip for now, plus the one fact that would flip that call. It deliberately refuses to issue a confident adopt/skip verdict below three PRs, and it will not compute a cost-per-defect number if your baseline cost is unquantified rather than silently guessing one. To use it, paste the `README.md` from that folder into any AI chat tool along with your setup description and PR sample, or drop the whole `skills/multiagent-code-review-cost-benchmark/` folder into `~/.claude/skills/` if you're working in Claude Code.

Worth being upfront about the risk that undercuts this fastest: Qodo or another vendor could simply publish their own neutral-framed benchmark next quarter and close most of this gap on their own. There's also a harder structural problem the full harness can't fully dodge — "defects caught" is only as good as the labeled corpus behind it, and building a large, well-labeled set of real, historically-confirmed bugs is genuinely expensive, which is exactly why nobody's done it yet. And any single benchmark, however neutral, will have blind spots across languages and codebase sizes that limit how far its numbers travel — which is the whole reason the "bring your own repo" mode matters more than the headline comparison table.
