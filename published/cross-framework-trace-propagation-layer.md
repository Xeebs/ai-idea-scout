# One Trace: A Cross-Framework Context-Propagation Layer for Multi-Agent Tracing

Multi-agent systems in production rarely stick to one framework. A LangGraph orchestrator hands off to a CrewAI specialist crew; that crew drops into a raw tool-use loop for one narrow task. Every framework in that chain has decent tracing on its own — and the moment a request crosses from one into another, the trace falls apart into disconnected fragments that a human has to manually stitch back together by eyeballing timestamps.

## The Gap

A dev.to market sweep of agent observability tools — "I evaluated every AI agent observability tool on the market, here's what's actually missing" (Utibe Okodi) — names cross-framework multi-agent tracing as "broken in every existing tool" tested. That's not one disgruntled user; it's a conclusion reached after testing the full current landscape. A second, independently written dev.to post (Soufian Azzaoui, "I tried LangSmith, Langfuse, Helicone, and Phoenix") corroborates it from the other direction: he tried four of the market's best-known observability products, found none of them covered his multi-framework needs, and ended up building his own tool, "AgentLens," rather than adopting any of the four. Two practitioners, searching independently, hit the identical wall — and one of them resorted to the textbook "we hacked something together ourselves" response, which is usually the clearest signal that a gap is real rather than a matter of looking harder.

The twist is that nothing here is actually missing at the component level. Arize Phoenix (via OpenInference), Langfuse, AgentOps, MLflow, and LangSmith each instrument LangGraph, CrewAI, and AutoGen individually, and do it well — per each vendor's own documentation, single-framework tracing is a solved, heavily built-out problem. What's missing is the glue: nothing stitches a trace ID across the boundary when one framework calls into another, so instead of one coherent trace you get two or three fragments that happen to describe the same request.

## The Project

The fix is a lightweight context-propagation library that sits at exactly the point where one agent framework hands control to another — a LangGraph node calling into a CrewAI crew, or a CrewAI agent dropping into a raw tool-use loop. At that handoff, it reads the current trace context from the calling framework's own instrumentation, injects it into the called framework's instrumentation before execution starts, and makes sure both sides' spans land under one shared trace ID — in whatever backend the team already has (Phoenix, Langfuse, or a plain OTel collector). The payoff is a single, zoomable trace spanning the entire heterogeneous call chain, instead of separate exports a human has to manually correlate by timestamp and gut feeling.

Concretely, that means: per-framework context-extraction/injection shims, starting with LangGraph, CrewAI, and the OpenAI Agents SDK; a propagation contract defining exactly how trace context crosses a framework-boundary call; a backend-agnostic exporter that confirms the stitched trace actually renders correctly as one tree in Phoenix and Langfuse; and a validation harness that runs a synthetic cross-framework call chain and checks the result is a single connected trace, not disjoint fragments pretending to be unrelated.

The MVP scopes down hard: build the LangGraph-to-CrewAI direction only. A small shim extracts the live OTel trace context inside a LangGraph node right before it invokes a CrewAI crew, injects that context into CrewAI's own trace hooks, and both frameworks' spans export under one trace ID to a shared Phoenix instance. The experiment is simple and falsifiable: run a synthetic two-hop task ten times and confirm Phoenix renders it as one connected tree every time, not two separate traces. Two to three weeks, one to two people.

## Tangible Impact

**Population**: Engineering teams building multi-agent systems that deliberately mix frameworks — a common pattern when one team's specialist sub-agent (built in CrewAI) is called from another team's orchestrator (built in LangGraph), or when a raw tool-use loop handles a narrow task inside a larger framework-managed flow. Both independent dev.to reviews surfaced this from real production debugging needs, not a hypothetical team.
**Mechanism**: Without propagation, debugging a failure that crosses a framework boundary means manually correlating two or three separate trace exports by timestamp and guessing at causality — slow and error-prone, and the reason Soufian Azzaoui built a bespoke tool rather than use an existing one. A shared trace ID across the boundary turns that manual correlation into a single click-through in the existing viewer.
**Measure**: (1) fraction of a seeded cross-framework call chain's spans that land under one shared trace ID vs. fragmented into separate traces, target 100% for the supported framework pairs; (2) time to localize a failure to the specific framework-boundary hop in a seeded test, stitched vs. manually-correlated; (3) number of distinct framework pairs (LangGraph↔CrewAI, CrewAI↔raw tool loop, etc.) demonstrated stitching correctly at launch.

## Try It

A companion skill already exists at [`skills/cross-framework-trace-propagation-layer/`](../skills/cross-framework-trace-propagation-layer/) for the half of this problem that doesn't require installing anything ahead of time. Its one-line description: "Reconstructs a single correlated timeline from two or more separately-exported agent-framework trace files (e.g. one LangGraph export, one CrewAI export) covering the same failing multi-framework request, so you can see the likely call order and handoff points without live trace-ID propagation installed."

In other words — if you already have a mess of disconnected trace exports from a failed multi-framework request and no propagation middleware installed, you don't need to build the full project first. Paste the skill's `README.md` into any AI chat tool and hand it your per-framework trace export files, or drop the `skills/cross-framework-trace-propagation-layer/` folder into `~/.claude/skills/` if you're working in Claude Code, and it will reconstruct a best-effort merged timeline across the fragments — with explicit caveats anywhere the correlation is inferred rather than certain. The live propagation library above is the fix that prevents the fragmentation in the first place; this skill is the triage tool for when it already happened.

Worth noting honestly: the per-framework instrumentation hooks this leans on can change shape between library versions without warning, which makes the shim side of this an ongoing maintenance commitment, not a one-time build — the same risk this pipeline has already flagged for related schema-normalization work. And at MVP scope, only a handful of framework pairs get covered; a team on an unsupported combination gets no benefit until someone writes a new shim for it.
