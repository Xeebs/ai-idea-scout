# Intent Check: A Second-Opinion Reviewer That Verifies Agent PRs Against the Original Task, Not Just the Diff

Your AI coding agent opens a pull request. A second AI reviews it, calls the code clean, consistent, well-structured — and approves it. Nobody notices it solved the wrong problem until a user files a bug three weeks later. That's not a hypothetical: it's the exact blind spot a 60-point, 93-comment Hacker News thread surfaced on 2026-11-17, citing Harvard research that the engineering bottleneck has moved from writing code to reviewing it. The uncomfortable part is what the "fix" most teams have already reached for — pointing a second AI pass at the first one's output — quietly fails to catch.

## The Gap

The second-AI-reviews-the-first-AI pattern has become the default review gate for agent-authored PRs, and it's built on a false sense of assurance. The reviewer checks whether the code is internally consistent with itself — does it compile, does it read cleanly, does it match the style of the rest of the diff — not whether it actually satisfies the task that was asked for in the first place. A PR can be perfectly coherent and still implement the wrong thing, and today's generic review layer has no mechanism to catch that, because nothing in the pipeline ever goes back and checks the diff against the original spec.

Every name that comes up when teams look for a fix — CodeRabbit, Greptile — is a general-purpose review-automation layer, not an intent-verification layer. There is exactly one vendor positioned squarely against this specific gap: Aviator's "Verify" product, which captures session intent and runs acceptance criteria against the running app, explicitly marketed against the "same-model-reviews-itself" weakness. But a 2026 conference writeup of Aviator's own co-founder describes it as still "piloting" — not something most teams can adopt today. A targeted GitHub search for intent-verification-specific tooling came back empty. This is a confirmed, named, acute gap with exactly one early-stage player in it — which is a narrow window, not a crowded one.

## The Project

The idea is a CI-integrated gate that treats "does this match what was asked for" as its own, separate review pass — distinct from, and run alongside, whatever generic code-quality bot a team already has. The moment a PR links to an issue or ticket, the gate pulls that originating task, extracts a small set of testable acceptance criteria from it with an LLM, and checks the diff against those criteria specifically. Where a criterion is behaviorally checkable — "returns a 400 on invalid input" — it tries to map that to an existing test or generate a minimal one and actually run it against the app, rather than just asking a model to eyeball the diff. Where the criterion is structural — "uses the existing auth middleware, not a new one" — it runs a targeted static check instead.

The output isn't folded into the generic review comment stream; it's a distinct intent-alignment report, pass/fail/uncertain per criterion, with the exact diff region cited for each. A human reviewer gets, at a glance, the thing a "looks consistent with itself" review can never tell them: where the implementation drifted from the ask. Under the hood, the pieces are an issue-to-acceptance-criteria extractor, a criteria-to-diff mapper with both a test-execution path and a structural-check path, a PR-comment formatter kept visually separate from code-quality comments, and an outcome ledger that tracks which flagged criteria later correlated with a revert or hotfix — so the extraction quality can be calibrated against real outcomes over time, not just vibes.

## Tangible Impact

**Population**: Engineering teams that have adopted AI coding agents for PR authorship and rely on a second AI pass (generic bots like CodeRabbit/Greptile, or a custom LLM reviewer) believing it catches intent drift — the exact blind spot the digest's sourced commentary names. The same digest cites secondary-aggregator figures (flagged unverified) that AI-agent PRs take 4.6–5.3x longer for a human to pick up and contain ~1.7x more defects than human PRs — a proxy for how large and under-served this reviewing cohort already is.
**Mechanism**: Today a generic AI reviewer validates that code is internally coherent — it can approve a PR that perfectly implements the wrong thing, because nothing checks the diff against what was actually asked for. Extracting acceptance criteria from the linked task and checking the diff against those specifically, separately from code-quality review, surfaces spec drift before merge instead of after a user files a bug against behavior that technically "passed review."
**Measure**: (1) % of historical merged PRs (sampled from an OSS repo with linked issues) where the gate's intent-alignment check would have flagged a criterion that a generic code-quality reviewer passed clean. (2) Correlation between flagged-and-ignored criteria and later reverts/hotfixes on those PRs, validating the flag actually predicts spec-drift bugs. (3) Added review-cycle time from the intent-check step vs. reported time saved by catching spec mismatches pre-merge rather than post-merge.

## Risks worth taking seriously

The honest read on this idea includes the reasons it might not be worth building. Aviator Verify is VC-backed and building toward exactly this gap — if it ships broadly before a competing approach gets traction, the differentiation shrinks to "open" or "cheaper," which may or may not be enough on its own. The whole mechanism is also only as good as the tickets it reads: acceptance-criteria extraction is bounded by how well-written the originating issue is, and a vague ticket in produces a vague, useless criterion out. And there's a sharper risk baked into the core design — if an LLM ends up judging "does this diff satisfy criterion X" without an independently runnable test behind it, the gate quietly reproduces the exact self-referential weakness it exists to fix. The test-execution path has to stay the primary mechanism, with LLM judgment strictly a fallback, or the whole premise collapses into the same blind spot it's supposed to close.

A GitHub Action triggered on PR-closes-issue events is the smallest version worth testing: pull the issue body, extract 3–5 criteria, map what can be mapped to real tests and run them, LLM-judge the rest against the diff, post a structured comment. The validating experiment is running it against 20–30 real closed PRs from an active OSS repo with linked issues and checking whether the flags correlate with which of those PRs were later reverted or needed a follow-up bugfix — buildable by one or two people in three to four weeks.
