In one week of November 2026, six different people independently wrote a project called something like "agent identity broker." Not a feature request, not a design doc — six working repositories, from six unrelated authors, all solving the same problem the same way, all appearing within days of each other. That's not a coincidence; that's a load-bearing gap in how AI agents are given access to things, surfacing simultaneously in six garages because nobody has shipped the shared version yet.

## The Gap

The problem each of those six repos is circling is simple to state and currently unsolved in practice: when an AI agent needs to call an API, it almost always inherits a standing credential — the same full-privilege key a human developer or backend service already uses. A Show HN post that kicked off the week, "Agentic Identity Broker, OAuth Delegation for AI Agents" (github.com/zalando-incubator/agentic-identity-broker), proposed the obvious fix — issue the agent a short-lived, narrowly-scoped credential for one task instead — and it struck a nerve. Within days, five more projects had sprung up chasing the same idea: worksomaganesh/agent-identity-broker, an ideksec proof-of-concept, anurag27397's version, infamousjoeg's idira-disco-mcp, and more. A second, independent research pass a day later found the same convergence again — this time including an individual IETF draft (draft-sweeney-wimse-credential-delegation) proposing a credential-delegation protocol, and a separate HN thread, "Trust Under Fire: How Agentic AI Tests Zero-Trust," flagging the same architectural problem from the security side.

What none of those six-plus projects amount to, yet, is a maintained standard. Every one is days old, narrowly scoped to its author's own stack, with no shared schema and no adoption outside the repo that spawned it. The Zalando project is the most credible entry — 76 stars and a push on the day of writing — but "most credible of six one-week-old repos" is a low bar. This is a textbook case of a gap everyone can feel but nobody has converged on solving together: the standing-privilege-key model that was fine for a human developer clearly isn't fine for an agent that acts unsupervised at machine speed, and the fix is obvious enough that six people reached for it in the same seven days without talking to each other.

## The Project

The shape of the fix is a broker that sits between an agent and every API it calls. Instead of an agent carrying a developer's or service account's standing key, it asks the broker for a credential scoped to exactly one task — specific endpoints, specific record IDs or resource prefixes, a tight time-to-live — and the broker mints that token, logs the issuance, and lets it expire or revokes it the moment the task finishes. A prompt-injected or simply malfunctioning agent is now bounded to whatever one task needed, not to everything the underlying account could ever touch.

The part that has to be right — and the part none of the six nascent repos can yet claim to have solved — is the scoping logic itself. It's not a bolt-on feature; it's the whole point. Given a declared task intent ("read customer record #4821, do not write"), the broker has to derive the minimal permission set that satisfies it and refuse anything broader, which means the system needs a real mapping from task language to API scope, not a config file of role names.

A first build needs: a broker API for issue/revoke/introspect; a declarative task-intent-to-scope mapping language; a revocation and expiry daemon; and an audit log recording every credential issued, which agent it went to, for what task, and whether it was ever used outside its declared scope. The practical path is to front one or two backends first — a generic REST API behind a scoped proxy token, plus an OAuth-native target like GitHub or Google — rather than trying to solve arbitrary backend permission models on day one.

## Tangible Impact

**Population**: Platform and security engineers at mid-size companies (roughly 50–2,000 employees) deploying LLM agents with access to production APIs or internal tools — the same cohort already building six independent, throwaway versions of this broker in a single week, and the broader set of teams who haven't built one yet but are running agents on full-privilege service-account keys today.
**Mechanism**: Today, an agent that calls an internal API typically inherits a long-lived, broad-scope key (the same one a human developer or backend service uses), so a prompt-injected or malfunctioning agent can act anywhere that key can reach. A scoped-credential broker converts "this agent's key can touch our whole customer database" into "this agent's token can read exactly record #4821 for the next 90 seconds," so the worst a single compromised task can do is bounded and auditable after the fact.
**Measure**: (1) Blast-radius reduction — the ratio of an agent's granted scope (resources/endpoints reachable) to its task's actual need, pre- vs. post-adoption, on a pilot team's agent fleet. (2) Time-to-revoke a compromised credential, compared to today's practice of rotating a shared key (which also breaks every other consumer of that key). (3) Count of out-of-scope access attempts caught and blocked by the broker's introspection log per month.

## Try It

You don't need to wait for anyone to ship the broker to get value out of the underlying analysis. A companion skill at `skills/agent-scoped-credential-broker/` does the design/audit half by hand: "Audits an AI agent's API/credential integration and derives a minimal-scope, time-boxed permission spec (plus a flagged list of unused standing privileges) from its declared task — a design/review exercise for teams about to wire an agent into production APIs with a full-privilege key."

Hand it a description of what your agent integration does (the task, the actual API calls it makes, the credential it currently holds, and how often/how long it runs) and it hands back the minimal scope that task actually needs, plus a flagged list of everything the current key grants that the task never touches. It never asks for or echoes a real secret — only the scope description. To use it, either paste the `README.md` from that folder into any AI chat tool along with your integration details, or drop the whole `skills/agent-scoped-credential-broker/` folder into `~/.claude/skills/` if you're working in Claude Code.

Worth being honest about before anyone builds the runtime version: this is a crowded moment, not an empty field. Six repos appeared in a single week, and a well-funded identity vendor — Okta, Auth0, or one of those six early movers itself — could standardize this faster than an independent build gains adoption; the field is moving within days here, not months. Deriving a correct minimal scope from a stated task intent is also a genuine judgment call that can fail in either direction: too broad defeats the purpose, too narrow breaks the agent mid-task. And many internal APIs have no native fine-grained scoping at all, which forces a broker to implement its own proxy-level authorization rather than delegate to the backend — a meaningfully bigger build than the clean OAuth-native case. If LangGraph or OpenAI's Agents SDK ship a built-in scoped-credential primitive, a standalone broker's remaining edge narrows to cross-framework portability alone.
