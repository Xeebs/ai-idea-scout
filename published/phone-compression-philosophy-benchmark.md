# Honest Compare: An Independent Head-to-Head Benchmark for On-Device Compression Philosophies

Two camps are selling you opposite routes to a phone-sized model, and both are grading their own homework. PrismML says its ternary-from-scratch Bonsai models hold onto 94–95% of full-precision quality at well under a gigabyte. The compress-from-large crowd — shrinking a 27B+ model down after the fact — points at its own numbers and says it's the better trade. Neither side has been checked by anyone who didn't build the model. One commentator said as much directly: don't trust the vendor's retention numbers until someone reproduces them independently. As of this writing, nobody has.

## The Gap

Search both camps and you find plenty of self-reported benchmarks and no neutral referee. PrismML's Ternary Bonsai 27B claims an AIME26 score of 90.8 against a conventional 2-bit quant's 57.5 on the same base model — a huge gap, but it's PrismML's own test, on PrismML's own hardware, using PrismML's own task selection. The compress-from-large analysis around Bonsai 27B frames itself explicitly as "the opposite path: compress a model that was born large," but it, too, only has vendor-reported figures to point to. No independent, third-party, same-hardware comparison of the two philosophies has surfaced anywhere — not GitHub, not a paper, not a blog post running both model families through the same task suite on the same device.

There's a second gap hiding underneath the first. A builder quote surfaced in the same research window claims "input handling, not inference, was the bottleneck on low-end phones" — meaning the entire compression-philosophy debate might be solving the wrong problem for a meaningful share of real deployments. Only one unverified blog post on incremental tokenization even gestures at this, and nothing dedicated measures it. Both vendors are optimizing a step that, for some tasks and devices, might not be where the time actually goes.

## The Project

Honest Compare is a reproducible, continuously-updated benchmark harness that runs the same task suites — tool-calling accuracy, vision-grounded QA, general reasoning — across matched pairs of ternary-native and compress-from-large models at comparable final file sizes, on the same physical phone and SBC hardware tiers. It reports accuracy, cold-start latency, steady-state tokens/sec, peak memory, and battery draw side by side with each vendor's own claimed numbers, so the gap between claim and reality is visible rather than asserted.

A second module tackles the hidden bottleneck question directly: it profiles the full request lifecycle — tokenization and image-preprocessing time versus model-forward time versus detokenization/output time — to settle, per task and hardware tier, whether input handling actually dominates latency the way the builder quote claims, or whether that's folklore. Four pieces make it work: a model-pair registry pulled live from the Hugging Face Hub, matching ternary-native and compress-from-large releases by on-disk size; a device-farm execution harness running identical task suites on both; the latency-breakdown profiler; and a published, re-runnable leaderboard that flags any vendor claim it couldn't reproduce within a stated tolerance.

## Tangible Impact

**Population**: Indie developers and small teams building on-device AI features for budget and mid-range Android phones — the devices that make up roughly 70% of global smartphone shipments by unit volume in emerging markets (per Counterpoint Research's global shipment-tier breakdowns), where RAM and thermal headroom are the binding constraint, not GPU-cloud budget. These builders currently have to choose a compression philosophy based on each vendor's own self-reported numbers with no way to check them against their own target device.

**Mechanism**: Today a developer picking between a ternary-native model and a compressed-from-large model for a budget-phone deployment relies on each vendor's cherry-picked benchmark, run on that vendor's own hardware and task set — a choice that can cost weeks of integration work if the model later performs far worse on the developer's actual device and task than advertised. An independent, re-runnable benchmark on real budget-tier hardware, plus the latency-breakdown profiler, tells a developer up front (a) which philosophy actually wins for their task/size budget and (b) whether their real bottleneck is even the model at all versus their own input-handling code, potentially saving them from compressing/swapping a model when the fix was elsewhere.

**Measure**: (1) the delta between each vendor's self-reported accuracy/latency numbers and this project's independently reproduced numbers on the same task and hardware tier (target: published for every model pair, however large the delta); (2) developer time-to-decision when choosing a compression philosophy for a target phone tier (target: under a day using the published leaderboard, versus the multi-vendor research currently required); (3) the share of total end-to-end latency attributable to input-handling vs. inference, per task and hardware tier, settling whether the community's "it's the preprocessing, not the model" claim holds generally or only in specific cases.

## Try It

A companion skill is already written at `skills/phone-compression-philosophy-benchmark/`. Its one-line job: "Recommends a specific on-device model (ternary-native vs. compress-from-large) and compression philosophy for a developer's target task, phone tier, and latency/accuracy constraints — every number tagged vendor-reported or independently verified, never blended." Until the Honest Compare leaderboard itself exists as a running service, the skill operates in manual research-fallback mode — it pulls current vendor-reported numbers via web search and labels them plainly as unverified, rather than pretending a benchmark exists that doesn't yet. Use it by pasting the `README.md` prompt template into any AI chat tool, or by dropping the `skills/phone-compression-philosophy-benchmark/` folder into `~/.claude/skills/` for Claude Code.

## The Catch

The methodology itself is contestable before a single result ships: vendors can and likely will argue that any reproduced-number gap comes from quantization calibration data or task-set choice, not a real quality difference — which is exactly why the harness needs to publish its exact methodology and invite rebuttal rather than presenting one number as settled truth. "Matched final file size" is also a shakier comparison axis than it looks, since the two philosophies may trade size against different things — one preserving vision better, the other tool-calling — so the MVP needs per-capability breakdowns, not a single blended score. The input-handling-bottleneck claim that motivates half this project traces back to a single unverified blog post, which means the profiler has to be built skeptical of its own premise, ready to report "the model actually was the bottleneck" as a legitimate finding. And "budget Android phone" itself spans wildly different NPU, RAM, and thermal designs, so the MVP has to name 2–3 specific hardware tiers rather than claim one number speaks for the whole category.
