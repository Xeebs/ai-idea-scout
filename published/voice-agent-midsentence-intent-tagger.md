# Mid-Sentence: A Combined Intent/Dialog-Act/Safety Streaming Tagger for Voice Agents

Every voice agent today is a patient listener and a slow responder: it waits for you to finish your entire sentence — sometimes your entire turn — before it does anything at all. But a human on the other end of the line doesn't wait. "I want to cancel my—" is already an unambiguous intent before the word "subscription" arrives, and "I'm going to hurt mys—" is already a crisis before the sentence completes. The gap isn't the ASR; word-by-word streaming transcripts have been a commodity feature for two years. The gap is that nobody has packaged what you do with those words the instant they arrive.

## The Gap

The clearest evidence is a single builder who went looking for this and found nothing to adopt. An r/MachineLearning poster described building, from scratch, a small model that tags intent, dialog act, entities, numbers, PII, profanity, and safety risk word-by-word as speech arrives, writing: "We listen and type word by word, yet most AI only acts per turn. That wastes time and tokens, and it misses intent that was already clear halfway through the sentence." They built it themselves because there was nothing to reach for.

A dedicated search backs that up, and backs it up in an interesting way: this isn't an area with zero prior art, it's an area with prior art that never converged. Streaming spoken-language-understanding research goes back years — word-level incremental intent-closing detection, RNN-T slot-tagging work, a 2022 caller-intent-detection study — but each paper tackles one slice (intent timing, or slot tags, or dialog acts) in isolation, and none of it shipped as a maintained, current tool. GitHub search for a packaged streaming tagger that bundles intent + dialog-act + entities + PII + profanity + safety-risk into one component came back empty. The gap-analyst's verdict was PARTIAL, not OPEN, precisely because those academic pieces exist — but a PARTIAL verdict on something this operationally important is still a green light: every team that wants this today is, like the original poster, hand-rolling it from a standing start.

The signal itself is thin — one low-engagement personal post, not a chorus — and that's worth saying plainly rather than hiding it. But this is also a pattern that resurfaced independently a day later, as its own separate "Arc Tagger" build on r/speechtech, which is the kind of recurrence this pipeline treats as a reason to take a thin single source more seriously, not less.

## The Project

The idea is a lightweight tagger that sits on a voice agent's streaming ASR output and emits structured tags incrementally, word by word: intent, dialog act (statement/question/command/backchannel), named entities, numbers, PII spans, profanity, and safety-risk flags — each with a confidence score that climbs as more of the utterance is heard. A voice agent (or speculative tool-calling middleware sitting downstream) subscribes to tag-confidence crossing a threshold and acts before the speaker finishes: firing a lookup, escalating a safety-risk utterance immediately, or redacting PII before it's ever logged, instead of buffering the whole turn and reacting only at the end.

The deliberate bet is that this is multi-tag, not single-purpose. Today's point solutions handle at most one of these tag types — an intent classifier, or a PII redactor, or a profanity filter — in isolation. The original gap the builder named is exactly that nobody bundles them: a safety-risk flag firing mid-sentence matters just as much as an intent flag firing mid-sentence, and treating them as five separate systems means five separate integration efforts and five separate latency budgets instead of one shared stream of tagged tokens.

Concretely, that's four pieces: a streaming adapter normalizing partial-transcript events from two or three major ASR providers into one token-arrival stream; a small fine-tuned sequence tagger — not an LLM call per token, since this has to run at ASR speed — emitting the multi-tag output with running confidence; a per-tag-type threshold/action-trigger config; and a replay harness that re-runs recorded conversations token-by-token to validate tag timing against ground truth before anything goes live.

## Tangible Impact

**Population**: Teams building production voice agents for latency-sensitive use cases — customer-support IVR replacements, crisis/support hotlines, and voice-first accessibility agents (several of which already exist as ideas in this index) — where every second of per-turn wait before the agent reacts is a measurable degradation in call experience or, in the crisis-hotline case, a safety-relevant delay.
**Mechanism**: Without this, a voice agent waits for end-of-turn (or a fixed silence timeout) before any tool call, safety check, or response planning starts, even when the relevant content was clear from the first half of the utterance — "I want to cancel my—" already signals intent before "subscription" finishes. A mid-sentence tagger lets the agent begin acting (pre-fetching data, flagging risk, routing) while the speaker is still talking, cutting the dead-air gap between end-of-speech and agent-response, and surfacing a safety-risk or PII flag the instant it's spoken rather than after the full turn is logged.
**Measure**: (1) Median time-from-intent-clear to agent-first-action, comparing mid-sentence tagging on vs. off, on a recorded conversation benchmark. (2) Tag-confidence calibration — how early (in tokens) a tag crosses a usable confidence threshold without false-triggering, across intent/safety-risk/PII tag types separately. (3) False-trigger rate (acting on a tag that reverses once the sentence completes) at the chosen threshold.

## Try It

A companion Claude Code skill already exists: [`skills/voice-agent-midsentence-intent-tagger/`](../skills/voice-agent-midsentence-intent-tagger/) — the "Tag Taxonomy Architect."

> Drafts a domain-specific tag taxonomy (intent, dialog act, entities, PII, profanity, safety-risk) and per-tag confidence-threshold/action policy for a streaming voice-agent tagger, so mid-sentence actions only fire where the cost of being early is actually worth it. Use when a team is designing or revising what their voice agent should react to before the full utterance finishes, not when running the live tagger itself.

It's deliberately the design step, not the runtime: hand it a plain-language description of your voice agent's domain (support hotline, crisis intake line, reservation line), some example or realistic transcripts, and a list of actions the agent can actually take, and it drafts the intent/dialog-act/entity/PII/safety-risk tags for that domain, flags which ones are safe to act on mid-sentence versus which consequences are too irreversible to ever trigger early, and assigns first-draft confidence thresholds for a human to tune against real call logs. It will not run this against live audio — the parent idea's runtime tagger is the piece that taps the live Deepgram/AssemblyAI/Azure Speech partial-transcript stream; this skill only ever processes what you paste. To use it, either paste the contents of its `README.md` into any AI chat tool as a prompt template, or drop the whole `voice-agent-midsentence-intent-tagger/` folder into `~/.claude/skills/` if you're running Claude Code.

Worth knowing before you build on this: tagging accuracy on partial, grammatically incomplete input is a genuinely hard ML problem on its own, since early-arriving tokens are inherently more ambiguous — the false-trigger risk could outweigh the latency win if thresholds aren't carefully set. Bundling five tag types into one small model also risks each individual tag underperforming a dedicated specialist model, which needs real validation rather than being assumed away. And if a major ASR vendor ships this as a built-in feature on their own streaming API — plausible, since the plumbing underneath is already mature — a standalone cross-provider tagger's differentiation narrows to portability alone.
