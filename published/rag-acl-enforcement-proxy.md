# Perm Filter: A Retrieval-Time ACL Enforcement Proxy for RAG

Ask most RAG teams how they stop a chatbot from surfacing a document a user shouldn't see, and the honest answer is: a line in the system prompt. That's not a security control — it's a request the model can be talked out of. Across 2026, enterprise RAG write-ups keep arriving at the same conclusion from different directions: permission checks are happening too late, too softly, or not at all, and nobody has shipped the obvious fix.

## The Gap

Multiple independent 2026 vendor and practitioner write-ups converge on the same failure mode. A tianpan.co post, "The PII Leak in Your RAG Pipeline," frames it bluntly: chatbots end up "knowing things they shouldn't." A named enterprise-RAG compliance guide calls broken access-control inheritance "the most common compliance failure in enterprise RAG deployments." OWASP's own guidance goes further, warning that system-prompt restrictions on sensitive information can be bypassed by prompt injection — meaning a prompt instruction was never a valid access control to begin with.

What's actually happening in most pipelines: document-level permissions get checked, if at all, *after* retrieval, or only via that prompt instruction — never as a hard filter baked into the retrieval query itself. Permission metadata gets separated from the chunk somewhere between the source system and the vector index. The result is that revoked or restricted documents keep surfacing through stale index entries, caches, citations, and logs — and a query that's merely semantically adjacent to a restricted document can pull it in with no malicious intent required.

This isn't a hypothetical gap waiting for a clever startup to fill it quietly — a GitHub search turns up a dozen-plus repos attempting ACL-filtered RAG retrieval (sagarhande/rag-access-control, elliotaplant/role-based-rag, AgentPostmortem/VaultRAG, tohfas/RAG-Access-Control, and others), and every single one tops out at 19 stars, with most abandoned since 2023-2024. The generic building blocks exist — Zanzibar-style authorization via SpiceDB or OpenFGA, document-level security in OpenSearch — but nobody has wired those primitives into a maintained, broadly-adopted "ACL-filtered RAG retrieval" product. What exists is prescriptive guidance about how it *should* work, not a reference implementation that actually does it.

## The Project

Perm Filter is a drop-in proxy that sits between the application and the vector database, intercepting every retrieval query and filtering candidate chunks against a live permission check *before* any of them reach the LLM's context window. The core design decision is what makes this different from a prompt instruction or a stale cached permission flag: it resolves the requesting user's effective permissions against the source system's native ACLs at *query time*, not at index time. A revocation on the source system — someone leaves the company, a document gets reclassified — is enforced on the very next query, not whenever the corpus happens to get re-indexed.

Four components do the work: a per-chunk permission-tag indexer that tags each chunk with a reference to its source document's ACL at ingestion (not a frozen copy of the permission state, which would just reintroduce staleness); a query-time resolver that checks current permissions against the identity provider live; a filtered-retrieval wrapper for the common vector databases; and an audit log of every blocked and allowed chunk per query, so compliance teams get a real trail instead of trusting that the prompt behaved.

## Tangible Impact

**Population**: Employees at mid-size-to-large enterprises deploying internal RAG chatbots over permission-segmented content stores (SharePoint, Confluence, Google Drive, internal wikis) — a population numbering in the millions of knowledge workers, since internal AI-assistant-over-documents deployments have become a default enterprise AI project in 2025-2026 at companies of all sizes with departmental access tiers (HR, legal, finance vs. general staff).
**Mechanism**: Today, a terminated employee's revoked Drive access, or a salary spreadsheet restricted to HR, can still surface through a RAG chatbot's stale index or cache for a semantically-adjacent query, because the check happens nowhere except an easily-bypassed prompt instruction. This proxy makes the chunk itself unretrievable the moment the source-system permission says so, closing the gap between a revocation and its enforcement from "until the next re-index" to "the next query."
**Measure**: percentage of restricted-document leak attempts blocked in a red-team eval (target: near-100% vs. today's prompt-only baseline); latency overhead added per query (target: low-tens-of-milliseconds); time between a source-system permission revocation and effective enforcement at retrieval (target: next query vs. today's stale-until-reindex).

## Try It

No companion skill exists for this idea yet — it's tagged `Format: PROJECT` because the real work here is systems integration (wiring a resolver into a vector DB and an identity provider), not a repeatable prompt-driven task. There's nothing to paste into a chat tool for this one; the MVP is a proxy you'd actually deploy — start with one vector DB (pgvector or Qdrant) and one source system (Google Drive's Permissions API), implement per-chunk permission-tagging at ingestion, and validate with a red-team suite of revoked-access queries before and after the proxy sits in front of retrieval.

Worth being honest about the risks before anyone sinks two weeks into this: resolving permissions against a live source-system API on every query adds latency, and the temptation to cache that permission state to speed things up reintroduces the exact staleness problem the project exists to kill. Source systems also don't agree on how permissions work — inherited folder permissions, group membership, link-sharing — so supporting more than one well is a real integration cost, not a thin adapter. And the honest counterargument: a sufficiently motivated enterprise team could plausibly build this in-house on top of OpenFGA or SpiceDB rather than adopt a third-party proxy, since the hard part is integrating with their specific source systems, not the filtering logic itself. That's exactly why the dozen GitHub attempts never grew past a handful of stars — each one got built once, for one company's stack, and then stopped.
