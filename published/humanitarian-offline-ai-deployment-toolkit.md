# FieldPack: A Reusable Offline-Deployment Toolkit for Humanitarian AI Across Problem Domains

Two humanitarian AI projects, built by two different teams for two different crises on two different continents, independently arrived at the same unglamorous engineering problem — and then each spent precious budget solving it alone. SHIFA, built for health work across Sudan, DRC, Somalia, Nigeria, and Rwanda, states its own operating assumption plainly: "internet that drops in and out, if it exists at all." VectorCam, an open-source smartphone tool for identifying disease-carrying mosquitoes, was built from scratch to run with zero internet access too. Neither project shares so much as a packaging format with the other. That's not a coincidence of bad planning — it's a sign that the plumbing every humanitarian AI deployment needs simply doesn't exist yet as something you can reuse.

## The Gap

Model packaging, intermittent-connectivity sync, and on-device inference are not the interesting part of a humanitarian AI project — triage logic, vector identification, crop advisory are. But right now, every team building for a crisis zone has to re-derive the boring part from zero before it can even start on the part that matters. SHIFA and VectorCam are proof: separately funded, separately engineered, built for entirely different problem domains (clinical triage vs. mosquito identification), and yet each independently built the same category of thing — a model-packaging-plus-sync-plus-runtime stack tolerant of a connection that might not show up for days. No shared toolkit exists between them in any search result turned up for this gap. The closest thing to a general-purpose attempt, `offline-mcp` on PyPI (an Ollama wrapper with an open-weights directory and an offline/sync deployment guide for East Africa), has roughly 68 weekly downloads and a single maintainer — real, but nascent enough that a better-resourced build would be a clear improvement rather than a duplicate. Wakoma's "OfflineAI" is only a catalog of existing tools, not a toolkit itself. Everyone building in this space is either reinventing the wheel or relying on a one-person project to keep it spinning.

## The Project

FieldPack is the plumbing, not the product. It's a reusable deployment layer that any humanitarian AI project — health diagnosis, disease-vector ID, crop advisory, disaster logistics — can adopt instead of re-solving "how do we run AI with no reliable internet in a crisis zone" every single time. Three pieces do the work: a standard packaging format that bundles a quantized open-weight model with its runtime dependencies into one versioned unit; a sync protocol that queues and reconciles updates and logs over whatever connectivity window shows up — a satellite burst, an occasional Wi-Fi signal, an SMS-triggered pull — without ever assuming a persistent connection; and a thin inference-runtime abstraction wrapping llama.cpp, MediaPipe, or ONNX runtime, so a project can swap models without re-engineering its deployment pipeline every time. FieldPack deliberately builds none of the domain logic itself. It is the plumbing SHIFA and VectorCam each built independently, made reusable so the next project doesn't have to be the third or fourth team to build it from scratch.

## Tangible Impact

**Population**: Humanitarian AI projects and the communities they serve across connectivity-constrained crisis and low-resource settings — SHIFA's own deployment footprint spans five countries (Sudan, DRC, Somalia, Nigeria, Rwanda), and the broader population is the estimated 2.6 billion people the ITU reports remain offline or on severely constrained connections globally, who are the end beneficiaries whenever a humanitarian AI project succeeds at actually deploying under these conditions.

**Mechanism**: Today, each humanitarian org building an AI tool for a connectivity-constrained setting spends a meaningful share of its engineering budget re-solving packaging and sync from scratch — time and money that doesn't go toward the actual domain problem (triage, vector identification, crop advice). A shared toolkit shifts that engineering cost from "rebuild the plumbing" to "configure the plumbing," freeing resource-constrained humanitarian tech teams to spend more of a fixed budget on the domain-specific model and evaluation work that actually determines whether the tool helps anyone.

**Measure**: (1) engineering time-to-first-working-offline-deployment for a new project using the toolkit vs. the multi-month from-scratch timelines implied by SHIFA/VectorCam's independent builds; (2) sync reliability — percentage of queued updates/logs successfully reconciled within a defined window under simulated intermittent-connectivity conditions; (3) number of independent humanitarian-AI projects across distinct problem domains adopting the toolkit within a year, the direct test of whether the "reusable across domains" claim holds in practice.

## Try It

There's a companion Claude Code skill: [`skills/humanitarian-offline-ai-deployment-toolkit/`](../skills/humanitarian-offline-ai-deployment-toolkit/) — *"Drafts a concrete offline/intermittent-connectivity AI deployment plan (packaging format, sync cadence, inference runtime, field-condition test checklist) for a humanitarian or low-resource project, given its domain, model, and device/connectivity profile. Use at project kickoff, before any packaging/sync infrastructure gets built."*

It's a one-time planning aid, not the infrastructure itself: describe your project's domain, your target model, and your device/connectivity profile, and it drafts the packaging-and-sync plan you'd otherwise have to work out from first principles the way SHIFA and VectorCam each did. To use it, either paste the skill's `README.md` into any AI chat tool and follow the prompt template, or — if you use Claude Code — drop the whole `humanitarian-offline-ai-deployment-toolkit/` folder into `~/.claude/skills/` and it's available automatically.

Worth being honest about the risk here before you build on this: `offline-mcp` already exists in this space, even if thinly maintained, and this toolkit only earns its keep if it's a genuine technical improvement over that project rather than a better-marketed rebuild of the same thing. The cross-domain reuse claim is also still a hypothesis — a mosquito-ID phone app and a clinic-laptop triage tool have different enough hardware and connectivity realities that "reusable across domains" needs to survive contact with a second real project, not just a solo MVP demo.
