# Memory Wall: A Pre-Retrieval Sanitizer for Prompt Injection Arriving Through Agent Memory and RAG Content

Every guardrail you've heard of watches the front door — the live message a user types in. Almost none of them watch what an agent pulls out of its own memory, or out of a RAG index, three turns later. That's the gap a lone student OJT project just stumbled into and nobody has shipped a real answer for yet.

## The Gap

In this run's evidence, GitHub issue `Sumit-ai-dev/Adaptive-Agent-Memory-OJT-G146#39` is one of five separate, from-scratch guardrail implementations that showed up independently in the same 30-day window — teams at `labsai/EDDI`, `nishit546/OpenPrep-AI`, `Prajna0106/PayPal-Seed`, and `kamisaberi/xtorch-examples` all hand-rolled their own input/output sanitizer or jailbreak filter rather than reaching for an existing library. That duplication is itself a complaint-shaped signal: nobody reaches for a shared solution first. But almost every one of those five is solving the same problem — guarding the live request a user types. The Sumit-ai-dev project is the outlier: it specifically wraps *memory* content in delimiter tags before it re-enters the prompt, because an agent that writes its own memory from a prior turn can be poisoned once and keep re-serving that poison to itself indefinitely. A live-input filter does nothing about that. Neither does a RAG pipeline's ingestion-time document scan, if the payload is instruction-shaped text that passed ingestion looking harmless and only reveals its intent once it's pulled back into context.

Nothing maintained currently closes this specific boundary. The handful of adjacent open-source packages that exist — early-stage efforts targeting roughly this layer — are each sitting at v0.1.0, single-maintainer, or demo-stage, alongside a cluster of academic papers doing active research on retrieval-stage memory poisoning but no shipped tool. There's a validated technique here (delimiter encapsulation) and real, independently-recurring demand, but no library a team could actually adopt today.

## The Project

The fix is a middleware layer that sits between an agent's memory or vector store and its prompt-assembly step — not a filter on what the user says, a filter on what comes *back out* of storage. Every chunk of retrieved memory or RAG content gets wrapped in strict, model-enforced delimiter tags before it ever reaches the prompt, then scanned for instruction-shaped content: imperative phrasing addressed to "the assistant," known delimiter-escape patterns, and nested-injection attempts trying to break out of the tag it's sitting in. Flagged content gets stripped, routed to a human review queue, or passed through carrying a reduced-trust annotation the system prompt tells the model to treat accordingly.

It ships as adapters for the vector-store and memory backends teams are already running — Chroma, pgvector, Mem0 — rather than one more bespoke per-project integration, consolidating a pattern that several early-stage packages are each independently reinventing at v0.1.0 right now. The MVP is deliberately narrow: build the delimiter wrapper and a regex/heuristic scan pass first, wire up one adapter (Chroma), assemble a labeled test set combining the evidenced delimiter-tag technique with known nested-injection and escape patterns from current academic work, and measure bypass rate and false-positive rate before adding more backends.

## Tangible Impact

**Population**: teams running agents with persistent memory or RAG retrieval where the stored or retrieved content itself may not be fully trusted — agents that write their own memory from prior interactions (making memory a write-once, read-many attack surface for a poisoned earlier turn), and RAG agents retrieving from any corpus that includes third-party or user-contributed content. This is distinct from this index's existing `rag-knowledge-base-poisoning-scanner` idea, which targets documents at ingestion time, rather than an injected instruction surviving inside already-indexed or already-stored content as it's pulled into context on a given turn.
**Mechanism**: closes a boundary every other guardrail in this run's evidence misses — a live user-input filter does nothing to catch an injection planted in memory three turns ago, or buried inside a retrieved chunk that passed ingestion-time scanning but still carries an instruction-shaped payload. Strict delimiter encapsulation plus a scan at the retrieval boundary stops that payload from being read by the model as an instruction regardless of how it entered memory or the index in the first place.
**Measure**: bypass rate on a labeled test set of memory/RAG-delivered injection payloads (adapting known delimiter-escape and nested-injection techniques), before/after the sanitizer; false-positive rate on legitimate memory/RAG content that happens to contain imperative or instructional language; latency overhead added per retrieval call (must stay low enough not to undermine agentic-loop responsiveness).

## Try It

A companion skill already exists at [`skills/memory-retrieval-injection-sanitizer/`](../skills/memory-retrieval-injection-sanitizer/) — its one-line job: "One-time forensic scan of a pasted/exported batch of agent memory entries or RAG-retrieved chunks for prompt-injection payloads planted in stored content (not live user input) — flags instruction-shaped text, delimiter-escape attempts, and nested-injection patterns with a risk-ranked report. Use when auditing what an agent's memory or retrieval system already holds, not for building the live retrieval-time middleware itself."

That's the cheap, no-integration version you can run today, before committing to building the full middleware. If you suspect an agent's memory or a RAG corpus is carrying a planted instruction, export the entries and paste the skill's `README.md` into any AI chat tool (Claude, ChatGPT, Gemini) along with the batch, and it will come back with a risk-ranked list of suspect entries. If you're working in Claude Code, drop the whole `skills/memory-retrieval-injection-sanitizer/` folder into `~/.claude/skills/` and invoke it directly.

Worth going in with eyes open, per the idea's own risk notes: this overlaps conceptually with pre-ingestion scanning (the existing `rag-knowledge-base-poisoning-scanner` idea in this index) but targets a genuinely different layer — retrieval-time, content already sitting in the store — so the two need clear positioning to avoid looking redundant. A sufficiently clever injection could still escape strict delimiters if the underlying model itself is vulnerable to delimiter-confusion attacks, which is a model-level weakness no middleware fully closes. And the strongest reason this might not be worth building: the evidence for the *specific* memory-boundary technique traces to one OJT-labeled student project, not a production team — whether engineering orgs beyond academic and early-stage packages actually want this, rather than a general-purpose filter, is the open question a real build would need to answer first.
