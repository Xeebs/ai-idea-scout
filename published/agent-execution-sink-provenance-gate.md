# Trace Gate: A Provenance-Tagged Execution-Sink Gate for Agent Tool Calls

Your sandbox doesn't matter if the attacker never needs to escape it. The latest wave of agent-security advice is still mostly about containing a breakout — rate limits, resource caps, deny-by-default network rules — but a CVE that landed this year shows a simpler, nastier path: convince the agent's own reasoning to call a tool it was already allowed to call, with parameters the attacker controls. No sandbox was breached. The agent just did what it normally does, pointed at the wrong target.

## The Gap

Prompt injection doesn't need to breach a sandbox perimeter if it can redirect the agent's own reasoning into calling a legitimate, already-permitted tool — an `eval()`-backed tool, say — with attacker-controlled input. That's a "goal hijack," not an escape, and it's exactly the shape of [CVE-2026-26030](https://predictionguard.com/blog/ai-agent-code-execution-security-explained), a real prompt-injection-to-`eval()` vulnerability in semantic-kernel, a widely used agent orchestration framework. OWASP's own Agentic Top 10 (2026) names this failure class under goal hijack / unexpected code execution. And yet every mitigation source lists the same generic best practices — deny outbound network by default, cap resources and timeouts, require approval for high-risk actions — as things teams *should* do, not a shipped provenance-tracking layer that actually follows untrusted content through an agent's reasoning into which tools it's allowed to call next.

It's not that nobody's working on this. Three separate 2026 academic prototypes target the identical gap with real evaluation numbers: Agent-Sentry (provenance-graph gating, reporting 94.3% injection block / 95.1% benign-action pass on AgentDojo/AgentDyn), Agentic Reference Monitor (runtime tool-call/result tagging), and Risk-Aware Causal Gating (claiming zero injection success on a controlled benchmark). But all three are research-stage, unreplicated, single-author or unreviewed preprints. A dedicated GitHub search for a shipped, production-grade version of this came up empty. The research de-risking is done; nothing has moved from paper to a deployable interceptor.

## The Project

The idea is a provenance-tagging interceptor that sits between an agent's reasoning loop and its tool-call dispatch. Content entering the agent's context gets tagged at ingestion with a trust label — a direct user instruction is trusted, a fetched web page, email, or tool result is not — and that tag propagates through the model's working context as it reasons. Before any call reaches a tool the deploying team has explicitly marked as an execution sink in a sink manifest (a code-interpreter, an `eval`-backed tool, shell-exec, file-write), the gate checks whether that call's parameters trace back to untrusted content. If they do, it blocks the call, requires human approval, or routes it to a sandboxed dry-run — instead of letting it through purely on the model's own judgment.

This is deliberately scoped to a single agent's own reasoning-to-tool-call path, not the handoff between two agents or the sanitization of retrieved memory before it ever enters a prompt — those are separate, related gaps with their own interceptors. The pieces here are a content-ingestion tagger wrapping fetch/email/tool-result adapters, a context-propagation tracker following provenance spans through working context, the execution-sink manifest itself, block/approve/sandbox-dry-run gating logic, and a red-team eval harness that reproduces CVE-2026-26030-style attacks plus runs against the AgentDojo/AgentDyn benchmark — an independent replication check against those self-reported academic numbers, not a repeat of them.

## Tangible Impact

**Population**: teams deploying single agents with both broad tool access (code-interpreter/eval-backed tools, shell-exec, file-write) and exposure to untrusted content in the same context — email-processing assistants, coding agents that fetch and act on web content or issue trackers, support agents that read attachments. This directly targets the vulnerability class demonstrated in CVE-2026-26030 in semantic-kernel, a widely-used agent orchestration framework, so any of its production deployments sit in this population today.
**Mechanism**: today, a legitimate, already-permitted execution-sink tool call fires whenever the model's own reasoning decides to call it, with no structural check on whether the content that drove that decision came from the user or from something the agent merely read. The gate converts "trust the model's judgment" into "trust is structurally revoked once untrusted content enters the decision chain," stopping a goal-hijacked call even though no sandbox escape ever happened.
**Measure**: (1) block rate on a reproduced CVE-2026-26030-style attack suite plus the AgentDojo/AgentDyn benchmark, as an independent replication check against Agent-Sentry's self-reported 94.3%; (2) benign-task pass-through rate, compared against Agent-Sentry's reported 95.1% baseline; (3) added latency per gated tool call.

## Try It

A companion skill already exists at [`skills/agent-execution-sink-provenance-gate/`](../skills/agent-execution-sink-provenance-gate/): "Audits a described agent tool catalog for goal-hijack exposure — pairs of 'reads untrusted external content' tools and 'execution sink' tools with no trust boundary between them — and recommends a sink manifest and provenance-tag placement."

It's not the runtime interceptor described above — it's a one-time, by-hand design/review pass you can run today, before that runtime gate ever gets built. Paste a description of your agent's tool catalog (tool names, what fills their parameters, where their output comes from, what their action does) into any AI chat tool using the skill's `README.md` as the prompt template, or drop the `skills/agent-execution-sink-provenance-gate/` folder into `~/.claude/skills/` if you're running Claude Code. You'll get back a tool inventory, flagged ingestion-to-sink pairs with a risk tier, a recommended sink manifest, and where the provenance boundary should sit — the same design decision the full runtime gate would enforce, worked out by hand first.

Worth noting honestly: provenance propagation through an LLM's own context is leaky by nature — a model can paraphrase untrusted content into text that carries an attacker's goal with no obvious literal taint marker, and the three academic results this is benchmarked against are unreplicated, single-author preprints whose numbers may not hold outside their own controlled benchmarks. And if semantic-kernel or another major framework patches this CVE class with a built-in provenance gate of its own, a standalone interceptor's value narrows mainly to cross-framework portability.
