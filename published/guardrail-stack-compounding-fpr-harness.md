# Shadow Check: A Compounding False-Positive Rate Harness for Guardrail Stacks

Nobody ships a single guardrail anymore. A customer-facing LLM product today gets a PII filter, a jailbreak classifier, a content-policy check, and a tone guard all chained in series — each one validated in isolation against its own adversarial benchmark, each one reporting a tidy 90%-plus accuracy number. What almost nobody measures is what happens when you run all four at once against real traffic. Stack five 90%-accurate guards and, by the illustrative math practitioners keep citing, you can land at a 40% false-positive rate — and the team that flips enforcement on without checking finds out from a wave of support tickets instead of a dashboard.

## The Gap

The clearest evidence this is unsolved comes from inside a project built specifically to solve guardrail problems: `humanbound/humanbound-firewall#55` is an open, unresolved issue where the maintainer of a dedicated guardrail-firewall admits the repo has "no evals for the firewall's decisions" — it ships without ever checking whether its chained checks let normal users through. That's not a hobby project cutting corners; it's the team closest to this exact problem saying out loud that they haven't measured it.

The surrounding advice confirms it's a known, recurring pain rather than a one-off complaint. One widely-cited practitioner guide lays out the failure mode in plain language: "teams add aggressive guardrails early, generate a 15% false positive rate, train users to route around them." The standard mitigation everyone recommends — run a new guardrail in shadow/monitor mode for one to two weeks before enforcing — shows up again and again across vendor advisory content. But every single description of that practice frames it as manual discipline: watch the logs yourself, eyeball the would-be verdicts, decide when you feel comfortable. Nobody has turned "measure the blended false-positive rate before you flip the switch" into an actual tool. A `gh search repos` for "guardrail false positive stack" and "guardrail evaluation pipeline false positive" comes back with zero matches. Adjacent eval tooling exists — promptfoo's red-team suite, Splunk's evals-to-guardrails loop, NeMo's own eval harness — but none of it is purpose-built to compute a multi-guard stack's real compounding FPR on a team's own traffic.

## The Project

Shadow Check is a proxy that sits in front of a team's existing multi-guard pipeline — NeMo Guardrails, Guardrails AI, LLM Guard, or a custom classifier stack — and runs every real request through all configured guards in shadow mode: logging what each guard *would have* decided without actually blocking anything. From that log it computes the thing nobody currently measures: the actual blended false-positive rate across the full stack on live traffic, plus per-guard attribution of which specific check is driving the compounding effect.

The attribution is the part that turns a number into an action. Knowing your stack blocks 18% of benign traffic is interesting; knowing that 14 of those 18 points trace back to one overly aggressive tone guard is what lets a team fix the actual problem instead of disabling the whole stack out of frustration. And because guardrail stacks don't stay static — teams add a guard, retune a threshold, see a new input pattern show up — the harness keeps running after enforcement goes live, so the next change gets re-measured before it quietly reproduces the same "users learn to route around it" failure that started this whole problem.

## Tangible Impact

**Population**: engineering and trust-safety teams chaining 3+ independent guardrail classifiers (PII, jailbreak, content-policy, tone) in front of a customer-facing LLM product — a proxy for scale is the combined ~18k GitHub stars across NeMo Guardrails, Guardrails AI, and LLM Guard, implying thousands of teams already composing multiple checks by hand without measuring the compounded result.
**Mechanism**: today teams validate each guard in isolation against adversarial benchmarks, then enable blocking in production without ever measuring the *stack's* real-traffic FPR; per the cited math, five 90%-accurate guards can blend to ~40% FPR. A shadow-mode harness surfaces that blended number, and which guard is driving it, before enforcement goes live — turning a reactive discovery (support tickets after launch) into a pre-launch gate.
**Measure**: (1) blended FPR measured in shadow mode before enforcement vs. the FPR a team would otherwise discover post-launch via support tickets; (2) reduction in benign-user complaints attributable to guardrail false positives after adopting a measured rollout, vs. the team's prior ungated rollout baseline; (3) time from a guardrail-stack change to a trustworthy blended-FPR estimate (target: days of shadow traffic, not weeks of user complaints).

## Try It

A companion skill already exists at [`skills/guardrail-stack-compounding-fpr-harness/`](../skills/guardrail-stack-compounding-fpr-harness/): *"Computes the real, empirical blended false-positive rate of a multi-guard LLM guardrail stack from an actual sample of per-guard verdict logs (not self-reported accuracy numbers), attributes which guard is driving the false blocks, and gives a go/no-go read on whether the stack is safe to enforce."*

This is the one-shot version of the idea above — instead of standing up the always-on shadow-mode proxy, you hand it a sample of per-guard verdict logs you've already exported (which guard fired, block or pass, and a benign/malicious label where you have one), and it reports the blended FPR, per-guard attribution, and a readiness read before you commit to enforcing. To use it: paste the full README.md into any AI chat tool along with your exported log sample, or drop the `guardrail-stack-compounding-fpr-harness/` folder into `~/.claude/skills/` if you're running Claude Code.

## The Honest Risk

The strongest reason this might not be worth building standalone: a guardrail vendor could ship this shadow-mode dashboard directly — Netskope already ships an adjacent monitoring-only view, and the pieces (monitor-mode logging, disagreement diffing, FPR measurement) exist separately enough that a vendor stitching them together is a real possibility, not a stretch. There's also a data problem baked into the premise — computing a real FPR requires a labeled-benign ground-truth sample, and plenty of teams asking for this won't have one ready, forcing a bootstrap from support-cleared history before the tool can say anything useful. And the compounding-FPR math motivating this entire idea is illustrative blog arithmetic, not an independently validated dataset — which is exactly why the MVP is designed as a backtest against real traffic, to confirm or kill that premise rather than assume it. Finally, shadow mode has an obvious failure mode of its own: it's easy for "let's keep measuring a little longer" to become a permanent excuse to never enforce anything, so the tool needs a clear readiness threshold built in, not just a number on a dashboard.
