# Framework Bridge: A Neutral Compatibility Shim Between LiveKit Agents and Pipecat

Pick a voice-agent framework in 2026 and you're not just choosing an API — you're choosing a set of regrets. LiveKit Agents and Pipecat have become the two dominant open orchestration layers, they're architecturally incompatible, and teams are already quietly paying the switching cost by hand instead of waiting for someone to fix it properly.

## The Gap

The lock-in isn't theoretical — it's showing up in the commits. A real GitHub PR, `berkerbatur/speechready` #11 (2026-11-02), manually ports turn-segmentation hooks to both frameworks' current APIs, one by one. NVIDIA's own `nemotron-voice-agent` blueprint went further: PR #219 (2026-11-19) restructured the whole repo into a one-package-per-framework layout specifically so it could support both side by side. And a widely read comparison piece on forasoft.com sums up the mood bluntly: choosing between them is "same models, same latency, different regrets" — the kind of framing that only shows up once a community has stopped hoping either option is simply correct.

The closest things to a fix fall short in telling ways. `berkerbatur/speechready` is a single-maintainer repo with narrow turn-segmentation hooks, not a general shim. SignalWire's "LiveWire" exposes LiveKit-shaped class names on SignalWire's own infrastructure, but it only goes one direction (LiveKit→SignalWire) and treats STT/TTS/VAD/turn-detection plugin parameters as no-ops — meaning it looks wired up but silently isn't. Pipecat's own LiveKit transport is just a transport adapter, not an Agents-API-level bridge. Nobody has shipped a neutral, bidirectional layer that lets a team write its logic once and run it on either framework.

## The Project

The fix is a small, framework-agnostic core abstraction — pipeline stages (STT→LLM→TTS), turn/VAD events, and tool-call hooks — paired with two thin adapter packages: one mapping that core API onto `livekit-agents`' current classes, one onto `pipecat-ai`'s `Frame`/`Processor` model. A team writes its turn-taking, interruption, and tool-dispatch logic exactly once against the core API, and the adapters translate calls and events in both directions — the thing LiveWire doesn't do and `speechready` doesn't attempt at scale.

It's versioned against both frameworks' current stable releases (`livekit-agents 1.8.10` and `pipecat-ai 1.15.0` at time of writing), with CI that fails the moment either upstream API drifts — a real risk, since both frameworks have already shown they evolve fast and in different directions: LiveKit leaning WebRTC/multi-participant-centric, Pipecat leaning pipeline-flexibility-centric. Scoped tightly for a first build: just the three highest-value surfaces — turn/VAD events, STT/TTS stage wiring, and tool-call dispatch — for the current stable release of each framework, validated by porting `speechready`'s own segmenter example through the shim and confirming identical behavior on both frameworks without touching the segmenter's own code.

## Tangible Impact

**Population**: Indie and small-team voice-agent builders choosing between LiveKit Agents and Pipecat today — a population in the tens of thousands given LiveKit's own reported ~400,000 weekly PyPI downloads for Agents (vs. ~90,000 for Pipecat, per LiveKit's January 2026 comparison page) and a 2026 voice-AI-agent software market estimated at $3.5–5.1B (Grand View Research, Meticulous Research) built substantially on these two frameworks.
**Mechanism**: A team that writes turn-taking/interruption/dispatch logic against the shim stops needing to pick a framework before writing a line of business logic, and stops re-deriving `speechready`'s or NVIDIA's own one-off porting work. Switching frameworks later (for latency, licensing, or hosting reasons) becomes a dependency swap instead of a rewrite.
**Measure**: time-to-port an existing non-trivial agent (e.g. a 5-stage pipeline with custom turn logic) from one framework to the other with vs. without the shim; number of framework-specific API calls a real agent needs outside the shim's coverage; CI pass rate against each framework's latest release over a 90-day window as a proxy for how well the shim tracks upstream drift.

## Try It

No companion Claude Code skill has been written for this one yet, but the idea file already sketches what one would do: a "framework portability reviewer" — given a pasted LiveKit Agents or Pipecat agent script, it would flag which constructs are framework-specific (no shim coverage yet), which are already portable, and draft the equivalent call against the other framework's current API, letting a team assess migration risk or dual-framework feasibility before committing to the shim's infrastructure build. Until that skill exists, the project itself is the thing to build: a Python package with the adapter classes described above, plus a shared test agent (echo + one tool call + barge-in) run against both adapters in CI, targeting 2-4 weeks for one or two people.

Worth being honest about the risks before anyone builds this. Both frameworks evolve fast; the shim could become a permanent maintenance tax chasing two moving targets, which only pencils out if it stays scoped to the stable 80% of each API rather than every escape hatch. If either framework's next major version formally adds first-class portability — unlikely but possible — this shim becomes redundant, so it's worth re-checking both roadmaps before a large build commit. A shim inherently can't expose a framework-unique feature (LiveKit's native multi-participant room semantics, for instance) without breaking neutrality, so it needs an explicit "escape hatch" story rather than silently papering over the gap. And LiveWire's plugin-param no-ops are a cautionary tale sitting right there in the evidence: this project only earns trust if its docs are honest about which calls are fully wired versus stubbed, unlike LiveWire's current framing.
